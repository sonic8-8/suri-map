# Matt Pocock과 Uncle Bob의 반복 개발·문서 관리 방식

조사 기준일: 2026-09-07. 공개 1차 자료에 나타난 주장과 개인 실천을 확인한다. 아래 적용 해석은 Suri-Map의 확정 계약이나 작업 규칙을 변경하지 않는다.

## 결론

두 사람 모두 명세를 없애자고 주장하지 않는다. Matt는 대화로 합의한 내용을 spec으로 남기며, Bob은 요구사항을 실행 가능한 인수 테스트로 표현하는 방식을 강조한다. 공통점은 문서 작성 자체보다 합의한 동작을 구현하고 검증하는 과정을 중시한다는 것이다. [Matt의 직접 설명](https://www.aihero.dev/5-agent-skills-i-use-every-day), [Bob의 인수 테스트 설명](https://blog.cleancoder.com/uncle-bob/2013/09/26/AT-FAIL.html)

Suri-Map에는 큰 문서 체계를 다른 체계로 통째로 교체하기보다, 한 번에 확인할 수 있는 사용자 동작을 작업 단위로 삼고 필요한 기록을 함께 갱신하는 방식이 적합하다고 판단한다. 이는 아래 자료와 현재 저장소를 비교한 제안이지, 채택된 규칙이나 방법론의 우월성을 입증한 결론은 아니다.

## Matt Pocock: 대화로 합의하고, 작은 동작으로 구현한다

공식 저장소의 `main`을 조회해 확인한 커밋은 `3cca18b368ae95cdbdebbff572ccafa662551015`다. 아래 소스 링크는 이 시점으로 고정했다. 공개 스킬은 바뀔 수 있으며, 로컬 설치본을 업데이트하지 않았다.

### 1. 문서를 쓰기 전에 서로 같은 동작을 생각하는지 확인한다

Matt는 에이전트가 사용자의 의도를 충분히 이해하기 전에 계획 문서를 만드는 문제를 지적한다. 먼저 질문과 코드 탐색으로 이해를 맞추고, 그다음 `to-spec`으로 대화 내용을 정리한다. 이 스킬의 이전 이름은 `to-prd`였다. 따라서 그의 방식도 PRD·spec을 배제하지 않는다. [5 Agent Skills I Use Every Day, 페이지 표시 갱신일 2026-03-16](https://www.aihero.dev/5-agent-skills-i-use-every-day)

`to-spec`에는 사용자 관점의 문제와 해결, 사용자 시나리오, 합의된 구현·테스트 결정, 제외 범위가 들어간다. 쉽게 낡는 파일 경로나 코드 복제를 피하지만, 사용자 시나리오는 상세하게 작성하도록 요구한다. Matt의 spec이 항상 짧다는 해석도 부정확하다. [to-spec 원문](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/to-spec/SKILL.md)

### 2. 작업은 계층별 산출물이 아니라 확인 가능한 동작으로 나눈다

`to-tickets`는 DB 작업 전체, API 작업 전체, UI 작업 전체로 나누지 않고 필요한 계층을 관통하는 작은 동작으로 나눈다. 각 작업은 완료 직후 독립적으로 시연하거나 검증할 수 있어야 한다. 다만 전역 이름 변경처럼 이런 분할이 불가능한 기계적 리팩터링은 새 형식 추가 → 호출부 이관 → 이전 형식 제거라는 예외를 둔다. 작은 변경은 별도 티켓 분할을 생략할 수 있으며, 대화에서 바로 티켓을 만들 수도 있다. [The /to-tickets Skill, 2026-08-24](https://www.aihero.dev/skills-to-tickets)

`implement`는 합의한 작업을 구현하며, 미리 정한 관찰 지점에서 TDD를 수행하고 타입 검사·테스트·코드 리뷰로 확인한다. 공개 가이드도 잘못 나눈 티켓을 이 스킬이 자동으로 바로잡아 주지는 않는다고 설명한다. 스킬을 호출했다는 사실만으로 좋은 작업 단위나 검증이 보장되지는 않는다. [The /implement Skill, 2026-08-24](https://www.aihero.dev/skills-implement)

### 3. 용어와 결정 이유는 역할을 나누어 필요한 때 기록한다

| 기록 | Matt의 공개 지침 |
|---|---|
| `CONTEXT.md` | 합의한 용어의 뜻을 기록하는 용어집이다. 구현 상세·작업 계획·spec을 넣지 않는다. 용어가 정해지면 그때 갱신한다. |
| ADR | 되돌리기 어렵고, 배경 없이 보면 의아하며, 실제 대안을 비교해 선택한 결정에 한해 제안한다. 모든 선택을 ADR로 만들지 않는다. |

문서와 디렉터리도 기록할 내용이 생길 때 만든다. [domain-modeling 원문](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/domain-modeling/SKILL.md)

ADR은 배경·결정·이유를 담은 짧은 문단만으로도 충분하다. 상태, 비교한 대안, 결과 항목은 도움이 될 때만 추가한다. [ADR 형식 원문](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/domain-modeling/ADR-FORMAT.md)

## Uncle Bob: 확인되는 원칙과 실천

### 1. 작은 배포와 고객 협력을 기술 실천에 묶는다

Bob이 공동 저자로 참여한 Agile Manifesto는 문서·계약·계획의 가치도 인정하면서 작동하는 소프트웨어, 고객 협력, 변화 대응을 더 중시한다. “문서는 필요 없다”는 선언이 아니다. [Manifesto for Agile Software Development, 2001](https://agilemanifesto.org/)

그의 XP 설명은 우선순위에 따른 짧은 증분, 잦은 작은 배포, 단순한 설계, 자동화된 개발자·고객 테스트, 지속적 리팩터링을 함께 다룬다. 요구사항을 책임지는 사람이 개발팀에 꾸준히 응답할 수 있어야 한다는 On-Site Customer도 포함한다. 티켓·스프린트 운영만 도입하자는 설명이 아니다. [Extreme Programming, a Reflection, 2013-12-10](https://blog.cleancoder.com/uncle-bob/2013/12/10/Thankyou-Kent.html)

### 2. 명세를 없애는 대신, 실행 가능한 명세로 소통한다

그는 요구사항의 오해를 줄이는 두 수단을 나란히 제시한다.

> “Shorten the feedback loop between specification and execution.”
> “Formalize the specification.”

짧은 반복은 요구사항 오해가 쌓이기 전에 문제를 드러내고, 인수 테스트는 기대 행동과 완료 조건을 전달한다. 업무 측이 원하는 행동을 QA 등과 함께 명시하는 것이 목적이므로, 개발자 혼자 자기 가정을 테스트로 다시 쓰는 것만으로 고객 소통을 대신할 수 없다. 이 글은 잘못된 사업 가설과 요구사항 전달 오류를 구분하므로, 테스트 통과가 제품의 유용성을 증명한다는 근거도 아니다. [A.T. FAIL!, 2013-09-26](https://blog.cleancoder.com/uncle-bob/2013/09/26/AT-FAIL.html)

### 3. 짧은 사전 설계는 하되, 구현의 발견에 따라 고친다

그는 FitNesse 기능 구현 전에 대안을 한두 시간, 큰 기능은 하루 이틀 검토했고 때로 UML도 그렸다고 직접 설명한다. 그러나 TDD가 다른 방향을 알려 주면 초기 계획을 바꾼다. [The Scatology of Agile Architecture, 2009-04-25](https://sites.google.com/site/unclebobconsultingllc/uncle-bob-consulting-llc/articles/the-scatology-of-agile-architecture)

2014년에도 코딩 전 사고와 스케치를 권하면서, 초기 생각이 나중 생각보다 더 정확한 것은 아니므로 사전 사고를 짧게 하고 코드의 피드백으로 연결한다고 설명한다. 반대 대상은 사고·설계 자체가 아니라 검증 없이 초기 계획을 고정하는 태도다. [When Should You Think?, 2014-03-11](https://blog.cleancoder.com/uncle-bob/2014/03/11/when-to-think.html)

### 4. 테스트로 행동을 기록하고, 아키텍처도 반복 중에 재검토한다

Bob은 잘 설계된 테스트를 읽어 기대 행동을 이해할 수 있다는 의미에서 “So the tests are documents.”라고 쓴다. 빠르고 신뢰할 수 있는 테스트가 변경과 정리에 대한 자신감을 준다는 점도 강조한다. [First, 2014-05-19](https://blog.cleancoder.com/uncle-bob/2014/05/19/First.html)

그의 TDD 설명에는 실패하는 테스트 → 필요한 구현 → 정리라는 짧은 주기뿐 아니라, 대략 한 시간마다 전체 시스템의 중요한 경계를 돌아보는 주기도 있다. 따라서 아키텍처를 최초 단계에서 한 번 끝내거나, 개별 테스트에만 맡기는 설명이 아니다. [The Cycles of TDD, 2014-12-17](https://blog.cleancoder.com/uncle-bob/2014/12/17/TheCyclesOfTDD.html)

### 귀속과 적용의 한계

- 위 근거는 2001년 공동 선언과 2009~2014년 직접 글이다. 당시 주장·개인 실천의 근거이지, 2026년의 개인 AI 작업 방식이나 방법론의 우월성을 입증한 실험 자료는 아니다. 날짜는 원문 게시일이다. 2009년 글은 [본인 홈페이지의 Old Articles](https://cleancoder.com/)에서 연결한 원문 보관소에 있다.
- 특정 Markdown 파일명, PRD → ADR → task 체계, ADR 상태 전환·갱신 절차를 Bob의 표준으로 지정할 근거는 확인하지 못했다. 이런 운영안을 제안한다면 Suri-Map용 적용 설계라고 표시해야 한다.
- 적용 해석: 테스트는 검증 대상 행동을 기록하지만 문제 선택 이유·기각한 대안·미확인 사용자 가설을 자동으로 보존하지 않는다. 행동은 테스트로 확인하고 결정 맥락은 필요한 만큼 기록하는 편이 타당하며, “테스트가 모든 문서를 대체한다”는 결론은 내리지 않는다.

## 두 방식을 동일한 절차로 취급하지 않는다

공통 원칙이 있어도 세부 절차까지 같지는 않다. 예를 들어 조사 시점 Matt의 `tdd`는 한 번에 테스트 하나와 최소 구현을 진행하고 리팩터링은 리뷰 단계에 두도록 명시한다. Bob은 짧은 RED → GREEN → REFACTOR 주기 안에서 정리한다. 어느 쪽도 Suri-Map에 새 테스트 도구나 대규모 테스트 체계를 자동으로 추가할 근거는 아니다. [Matt의 tdd 원문](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/tdd/SKILL.md), [Bob의 The Cycles of TDD](https://blog.cleancoder.com/uncle-bob/2014/12/17/TheCyclesOfTDD.html)

## Suri-Map에서 확인된 사실과 해석

### 기존 방식에도 사용자 피드백과 실행 검증 규칙은 있었다

[조사 당시 PRD](https://github.com/sonic8-8/suri-map/blob/93072f1d728f8085bc6d13d6c466bb0788ee076d/docs/prd.md)는 경찰 대면 인터뷰를 반영한 이력을 담고 있고, 조사 당시의 에이전트 작업 가이드도 RED → GREEN → 재검증과 관찰 가능한 완료 근거를 요구했다. 해당 가이드는 조사 이후 제거됐지만, 기존 개발을 사용자 협력이나 테스트가 없는 방식이었다고 단정할 수는 없다.

반면 조사 당시 문서에 지정된 [대표 사건 ID](https://github.com/sonic8-8/suri-map/blob/28f8d4dfc13096295142e3b807e1bc869ad268cf/docs/spec/harness-scenarios.md)는 [좌표 알림 hook의 추가 UUID 조건](../../frontend/src/features/markerNotifications/presentation/hooks/useIncidentMarkerNotifications.ts)에 걸려 알림용 SSE 연결을 시작하지 못했다. 당시 코드 탐색과 브라우저 재현에서 확인한 공통 계약과 실제 연결 동작의 불일치 사례다. 이후 수정 상태와 구분한다.

여기서 확인되는 것은 문서와 규칙의 존재만으로 실제 동작까지 보장되지는 않았다는 점이다. 이 사례 하나로 SDD 전체의 실패나 과거 모든 검증의 부재를 증명할 수는 없다. 문서 부담과 별개로, 완료 판단이 실제 사용자 동작까지 확인했는지를 점검해야 한다.

### 조사 당시 운영 제안과 이후 합의

아래 표는 조사 당시 제안이다. 2026-09-18 사용자와 논의한 결과, 모든 개발 작업을 Issue에 모으자는 부분은 채택하지 않았다. 이후 문서 정리에서 ADR도 [개별 결정과 이력 요약](../adr/README.md)으로 바꿨다. 현재 기록의 용도는 [문서 사용 기준](../../AGENTS.md#문서-사용)을 따른다.

| 기존 기록 | 제안하는 역할과 갱신 시점 |
|---|---|
| PRD | 제품의 문제·목적·범위·하지 않는 일을 설명한다. 제품 방향이 바뀔 때 갱신하고, 작은 버그 수정마다 다시 작성하지 않는다. |
| Issue | 이번에 해결할 문제, 기대 동작, 범위, 확인 방법을 합의한다. 작업에 필요한 짧은 spec을 이곳에 둘 수 있다. 원인 분석·변경·검증 결과는 댓글로 이어서 남겨 최초 가설과 이후 발견을 구분한다. |
| `CONTEXT.md` | 새 용어의 의미를 합의했을 때 갱신한다. 이미 있는 API·DB 계약을 별도로 복제하지 않는다. |
| ADR | 나중에 코드만 보고 이해하기 어려운 중요한 선택과 이유를 남긴다. 조사 당시에는 기존 본문·archive의 운영부터 확인하자고 제안했다. 이후 사용자 합의에 따라 개별 파일로 정리했으며, 이를 Matt나 Bob이 요구한 고정 절차로 간주하지 않는다. |
| API·event·DB·fixture 계약 | 여러 구현이 함께 지켜야 하는 현재 기준이다. 승인된 계약 변경은 관련 코드·검증과 함께 반영한다. 구현이 다르다는 이유만으로 계약을 코드에 맞춰 덮어쓰지 않는다. |
| TODO·Lane 작업 기록 | 새 작업의 상세 내용은 Issue에 두고 TODO는 다음 순서와 링크에 집중하는 구성을 제안한다. 과거 Lane 기록의 보관·진행 상태 기준 변경은 별도로 합의한다. |

행동을 검증하는 테스트와 실행 결과는 해당 Issue에서 연결한다. 테스트가 다룬 범위, 실행 환경, 측정 조건을 남겨 “확인함”과 “아직 확인하지 않음”을 구분한다. 테스트는 약속한 동작의 검증 수단이며, 고객 피드백이나 결정 이유를 모두 대체하지 않는다.

### 다음 SSE 작업에서 적용할 수 있는 짧은 반복

1. 현재 동작과 실패를 함께 확인한다. 이미 확정한 내용은 기록에서 읽고, 미정 사항만 설명과 근거를 제시한 뒤 논의한다.
2. 이번에 확인할 사용자 동작을 좁힌다. 예를 들면 접근 권한이 있는 대표 사건에서 알림 이벤트가 화면 표시까지 이어지는 동작이다. UUID 조건 제거 등 구현 방법은 이 문서에서 확정하지 않는다.
3. 합의한 동작을 관찰하는 기존 테스트 지점을 우선 사용해 실패를 확인하고 최소한으로 수정한다.
4. 코드 리뷰와 관련 테스트에 더해 실제 화면에서 같은 흐름을 확인한다. 성능 주장은 필요한 측정으로 별도 검증한다.
5. 변경 이유·코드 동작·실행 결과를 사용자가 확인한 뒤 다음 작업을 정한다. 결과는 Issue에 남기고, 실제로 달라진 계약·용어·중요 결정만 해당 기록에 반영한다.

학습·포트폴리오 목적에서는 에이전트가 통과 결과만 전달하는 것으로 끝내지 않고, 사용자가 변경 전후의 동작과 선택 이유를 이해할 수 있도록 작은 변경 단위로 설명하는 과정이 중요하다. 사용자가 현재 프로젝트의 제품 결정을 담당하더라도, 현장 적합성이나 실제 수색 운영의 성과까지 검증됐다고 표현하지는 않는다.

조사 당시에는 에이전트 지침과 Lane 작업 인덱스에 계약 우선순위·권한 규칙이 남아 있어, 운영안을 채택하기 전에 참조 관계와 진행 상태 기준의 변경 범위를 합의해야 했다. 이 조사는 기존 문서 삭제·이동, 에이전트 규칙 변경, 제품 코드 수정, Issue 게시를 포함하지 않았다. 이후 합의한 현재 작업 규칙은 [AGENTS.md](../../AGENTS.md)에서 확인한다.
