# [Android] GPS 수집 주기 5초, 전송 주기 10초에 대한 근거 부족 문제

## 문제 배경

수리맵 Android 앱은 수색 중 GPS 좌표를 최소 5초 간격으로 요청한다. 문서와 화면에는 이 동작이 `GPS 5초 / 전송 10초`로 표시되어 있다.

하지만 5초와 10초를 정할 때 현장에서 경로를 측정하거나 업무폰의 배터리 소모량을 비교한 기록은 없다. 지휘 화면에서 대원의 위치가 몇 초까지 늦게 보여도 되는지도 정하지 않았다.

GPS 수집 주기는 지도에 그려지는 경로의 모양과 배터리 사용량에 영향을 준다. 좌표를 서버로 보내는 주기는 지휘 화면의 위치 반영 속도, 네트워크 요청 수, 오프라인 상태에서 업무폰에 쌓이는 요청 수에 영향을 준다. 근거 없이 숫자만 정하면 현재 설정이 수색 현장에 맞는지 판단할 수 없다.

공개 자료에서도 모든 수색·지도 서비스가 함께 따르는 하나의 주기는 찾지 못했다.

- [소방공무원 현장 소방활동 안전관리에 관한 규정](https://www.law.go.kr/%ED%96%89%EC%A0%95%EA%B7%9C%EC%B9%99/%EC%86%8C%EB%B0%A9%EA%B3%B5%EB%AC%B4%EC%9B%90%ED%98%84%EC%9E%A5%EC%86%8C%EB%B0%A9%ED%99%9C%EB%8F%99%EC%95%88%EC%A0%84%EA%B4%80%EB%A6%AC%EC%97%90%EA%B4%80%ED%95%9C%EA%B7%9C%EC%A0%95)과 [재난현장 표준작전절차](https://www.daegu.go.kr/cmsh/daegu.go.kr/119/files/%EC%9E%AC%EB%82%9C%ED%98%84%EC%9E%A5%ED%91%9C%EC%A4%80%EC%9E%91%EC%A0%84%EC%A0%88%EC%B0%A8.pdf)는 현장 통신과 대원 위치 관리를 요구하지만 초 단위 GPS 주기는 정하지 않는다.
- [CalTopo/SARTopo](https://training.caltopo.com/all_users/mobile/tracks), [ATAK](https://github.com/deptofdefense/AndroidTacticalAssaultKit-CIV/blob/master/atak/ATAK/app/src/main/java/com/atakmap/comms/ReportingRate.java), [ArcGIS Field Maps](https://doc.arcgis.com/en/field-maps/android/use-maps/track.htm)는 이동 상태, 통신 방식, 위치 사용 목적에 따라 서로 다른 주기를 사용한다.
- [Android 공식 안내](https://developer.android.com/develop/sensors-and-location/location/battery)는 서비스 목적을 만족하는 범위에서 가장 긴 수집 주기를 사용하도록 권한다. 요청한 주기는 정확한 실행 시각을 보장하지 않으므로 실제 기기에서 측정해야 한다.

코드를 확인한 결과, 현재 `10초 전송`은 10초마다 HTTP 요청을 보내는 타이머가 아니다. 첫 번째 대기 좌표부터 10초가 지난 뒤 새 좌표가 들어오거나 좌표가 120개 쌓이면 한 묶음을 Outbox에 저장한다. Outbox는 서버로 보내지 못한 요청을 업무폰에 보관하는 공간이다. 실제 HTTP 요청은 Android의 백그라운드 작업 도구인 WorkManager가 실행된 뒤 시작한다.

```mermaid
flowchart LR
    A[GPS 좌표를 최소 5초 간격으로 요청] --> B[좌표 누적]
    B -->|10초 경과 또는 120개 누적| C[Outbox에 요청 저장]
    C --> D[WorkManager 실행]
    D --> E[서버로 HTTP 요청]
    E --> F[지휘 화면의 지도 갱신]
```

따라서 문서에 적힌 `10초 전송`과 실제 서버 전송 간격이 같은지도 실기기에서 확인해야 한다. 현재 설정 때문에 경로 누락이나 과도한 배터리 소모가 발생한다고 확인한 단계는 아니다. 지금 확인한 문제는 `5초 수집·10초 전송`을 선택한 근거가 없다는 점이다.

## 원인 분석과 선택지

현재 문서에는 GPS 수집, 좌표 묶음 저장, 서버 전송, 지도 갱신이 하나의 `5초·10초` 기준처럼 적혀 있다. 그러나 네 동작은 목적이 다르므로 각각 기준이 필요하다.

```text
GPS 수집 주기        -> 수색 경로의 모양과 배터리 사용량
현재 위치 갱신 기준  -> 지휘 화면에서 허용할 위치 지연
좌표 전송 기준       -> 네트워크 요청 수와 지도 반영 시간
오프라인 복구 기준   -> 밀린 기록을 모두 반영하는 데 허용할 시간
```

다른 서비스의 기본값을 그대로 적용하는 방법을 검토할 수 있다. 하지만 제품마다 사용자, 이동 속도, 통신 환경과 위치 정보의 사용 목적이 다르다. 외부 사례는 비교 자료로만 사용하고 수리맵의 기준으로 그대로 복사하지 않는다.

수리맵의 사용 환경을 기준으로 직접 정하는 방법도 있다. 같은 업무폰과 이동 경로에서 수집 주기를 바꾸며 좌표 수, 경로 모양, 배터리 사용량을 비교한다. 수집 주기를 정한 뒤에는 전송 주기만 바꾸어 네트워크 요청 수와 지휘 화면 반영 시간을 측정한다. 현직 경찰관이나 수색 지휘 경험자에게는 대원 위치가 몇 초 이상 늦게 보일 때 업무에 문제가 되는지 확인한다.

이번 Issue에서는 이 측정과 현장 의견을 바탕으로 네 가지 기준과 선택 근거를 정한다.
