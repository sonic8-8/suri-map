# [BE] 수색 경로 길이에 따라 GPS 좌표 묶음 추가 요청의 처리 시간이 증가하는 문제

# 본문

## 문제 배경

- **기대 상태:** 이전 경로가 8분, 30분, 8시간 또는 24시간 동안 누적돼도 새 GPS 좌표 6개를 붙이는 처리 비용이 기존 경로 전체 길이에 비례해 계속 증가하지 않아야 합니다. 지원하는 경로 길이마다 `31 RPS`(초당 요청 31건)를 5분 동안 보내는 시험을 시간 초과 없이 처리해야 합니다.
- **초기 로직:** 새 좌표 6개를 기록할 때마다 기존 좌표와 구간을 모두 읽고, 새 좌표를 이어 붙인 전체 경로 도형을 다시 계산해 저장했습니다. 기존 구간도 모두 삭제한 뒤 새 구간을 포함한 전체 구간을 다시 저장했습니다.
- **초기 현상:** 같은 `31 RPS`에서 30분 경로는 5분 동안 처리됐지만, 좌표와 구간이 16배 많은 8시간 경로는 두 번 모두 약 13초 만에 시간 초과가 발생했습니다.
- **초기 판단:** 경로 길이에 따라 증가하는 작업이 서버 처리량에 영향을 준다는 사실은 확인했습니다. 다만 이 시점에는 전체 조회, 도형 재계산, 구간 재저장과 응답 생성 중 어느 단계가 지배적인 병목인지 분리하지 못했습니다.

### 초기 저장 방식: 새 좌표를 이어 붙일 때 기존 경로 전체를 다시 처리

현재 로직의 핵심은 요청으로 들어오는 데이터의 크기와 서버가 처리하는 데이터의 크기가 다르다는 점입니다. 업무폰은 새 GPS 좌표 6개만 보내지만, `SearchPathService.appendPointsOnce()`는 이 좌표를 기존 경로에 이어 붙이기 위해 누적된 경로 전체를 다시 처리합니다.

1. 기존 GPS 좌표, 구간과 제외 좌표를 모두 조회합니다.
2. 새 좌표 6개와 새 구간을 메모리의 수색 경로에 추가합니다.
3. 기존 좌표와 새 좌표 전체로 지도에 표시할 경로 도형을 다시 계산하고, 수색 경로 행에 저장합니다.
4. 기존 구간 행을 모두 삭제합니다.
5. 각 구간의 도형을 다시 만든 뒤, 새 구간을 포함한 전체 구간을 하나씩 저장합니다.
6. 기존 GPS 좌표 행은 유지하고 새로 받은 좌표 6개만 추가로 저장합니다.
7. 전체 경로 도형, 전체 구간과 제외 좌표를 응답으로 만듭니다.

즉, 기존 GPS 좌표와 수색 경로 자체는 삭제하지 않습니다. 수색 경로 행에는 새로 계산한 전체 경로 도형을 저장하고, 구간 행은 모두 삭제한 뒤 전체를 다시 삽입합니다. 제외 좌표도 같은 방식으로 다시 저장하지만, 이번 시험에서는 제외 좌표가 한 건도 없었으므로 성능 저하의 근거로 사용하지 않습니다.

이 구조에서는 요청 한 건이 추가하는 좌표가 6개로 같아도 기존 경로가 길수록 읽고 계산하고 다시 저장할 데이터가 늘어납니다. 현재 공개 API는 전체 경로 도형과 구간을 응답하므로, 저장 방식을 개선하더라도 응답 데이터의 크기는 경로 길이에 따라 늘어날 수 있습니다. 따라서 모든 요청의 응답 시간을 밀리초 단위로 같게 만드는 것을 기준으로 삼지는 않습니다. 고정된 크기의 좌표 묶음을 추가하는 저장 비용이 누적 경로 길이에 비례해 계속 증가하다가 시간 초과로 이어지는 구조를 해소하고, 지원하는 경로 길이에서 같은 부하 기준을 충족하는 것이 목표입니다.

### 시험 부하: 업무폰 468대의 주기적 요청률을 31 RPS로 고정

Suri-Map의 업무폰은 수색 중에 수집한 GPS 좌표를 묶어 `POST /api/search-paths/batch`로 전송합니다. Android Outbox는 네트워크가 불안정해도 요청을 잃지 않도록 전송할 내용을 로컬에 보관하는 대기열입니다. 이 대기열은 한 업무폰의 요청을 저장된 순서대로 하나씩 전송합니다.

이번 긴 경로 시험에서는 차량 수색에서 발생할 수 있는 가장 잦은 수집 조건을 사용했습니다. GPS 좌표를 2.5초마다 수집하고 좌표 6개를 한 요청으로 묶으면 업무폰 한 대가 약 15초마다 요청 한 건을 만듭니다. 업무폰 468대가 같은 방식으로 전송할 때 전체 요청률은 초당 약 31건, 즉 `31 RPS`가 됩니다.

`prepopulated-long-path` 시나리오는 Android의 순차 전송 자체를 재현하는 시험이 아닙니다. 부하 테스트 도구인 k6의 `constant-arrival-rate` 실행기를 사용해 응답 속도와 관계없이 초당 요청 31건을 시작하고, 서버가 이 요청률을 지속해서 처리할 수 있는지 확인합니다. 경로 길이의 영향만 비교할 수 있도록 요청률과 실행 시간은 같게 두고 처음부터 저장돼 있는 경로 길이만 바꿨습니다.

### 시험 결과: 30분 경로 통과와 8시간 경로 시간 초과

기존 부하 시험에서는 30분 동안 수집한 좌표를 다뤘기 때문에, 수색이 길어질 때 요청 한 건의 처리 비용이 어떻게 달라지는지는 확인하지 못했습니다. 이를 확인하기 위해 30분 경로에는 업무폰마다 좌표 720개와 구간 120개를, 8시간 경로에는 좌표 11,520개와 구간 1,920개를 미리 저장했습니다. 8시간 경로가 가진 좌표와 구간은 30분 경로의 16배입니다.

다음 표의 `p95`는 전체 HTTP 요청 중 95%가 해당 시간 안에 응답받았다는 뜻입니다. `dropped_iterations`는 k6가 목표 요청률에 맞춰 요청을 시작해야 할 때, 동시에 요청을 처리할 가상 사용자(VU)가 부족해 시작하지 못한 반복 실행 수입니다.

| 초기 경로 | 실행 ID | 결과 | HTTP 응답 시간 p95 |
|---|---|---|---:|
| 30분 | `20260902T034859Z` | 요청 9,301건 완료, 시간 초과 0건, `dropped_iterations` 0건 | 149.02ms |
| 30분 | `20260902T035650Z` | 요청 9,301건 완료, 시간 초과 0건, `dropped_iterations` 0건 | 147.36ms |
| 8시간 | `20260902T040951Z` | 약 13초 후 중단, k6 집계 요청 121건 중 시간 초과 21건 | 9.99초 |
| 8시간 | `20260902T041909Z` | 약 13초 후 중단, k6 집계 요청 111건 중 시간 초과 11건 | 9.98초 |

30분 경로 시험은 새 시험 데이터로 두 번 실행했으며, 두 실행 모두 예정한 5분을 마쳤습니다. 반면 8시간 경로 시험은 시간 초과가 발생해 모든 검사가 통과해야 한다는 중단 조건을 위반했고, 두 번 모두 약 13초 만에 종료됐습니다. 8시간 시험의 p95는 정상적인 처리 성능이 아니라 10초 시험 상한에 도달한 결과입니다. 이 상한은 Android가 사용하는 OkHttp의 기본 시간 제한을 근사한 값이며 서비스 수준 목표(SLA)는 아닙니다.

8시간 경로 시험에서는 서버가 요청 처리에 재사용하는 데이터베이스 커넥션 10개가 모두 사용됐고, 커넥션을 기다리는 요청이 최대 190개까지 쌓였습니다. 시험이 중단된 뒤에도 서버는 이미 시작한 요청을 각각 408건과 407건까지 처리했습니다. PostgreSQL에는 요청당 좌표 6개가 저장됐고, 제외되거나 중복된 좌표가 없었습니다. 같은 요청을 다시 보내도 중복 저장하지 않도록 남기는 멱등성 처리 기록도 모두 `COMPLETED` 상태였습니다.

8시간 조건에서 데이터베이스 커넥션 대기와 시간 초과가 반복됐기 때문에 24시간 경로의 `31 RPS` 본시험은 서버 보호를 위해 진행하지 않았습니다.

### 업무폰 영향: 성공 확인과 후속 좌표 전송 지연

따라서 이번 시험에서 데이터 손실이나 중복 저장은 확인되지 않았습니다. 문제는 서버가 데이터를 결국 저장하더라도 업무폰이 제한 시간 안에 저장 성공 여부를 확인하지 못한다는 점입니다. Android Outbox는 네트워크 시간 초과를 재시도 가능한 실패로 남기고 다음 요청을 순차적으로 처리하므로, 느린 응답은 같은 업무폰의 재시도와 후속 좌표 전송도 지연시킵니다.

## 초기 원인 분석과 선택지

### 초기 병목 판단: 경로 길이의 영향 확인과 지배 단계 미확인

요청 한 건이 추가하는 좌표 수는 항상 6개였고, 두 조건에서 바꾼 값은 처음부터 저장된 경로 길이뿐이었습니다. 경로 길이를 16배로 늘렸을 때 시간 초과와 데이터베이스 커넥션 대기가 두 번 반복됐습니다. 따라서 기존 경로 길이에 따라 증가하는 조회, 계산, 저장 또는 응답 작업이 서버 처리량에 영향을 준다고 판단할 수 있습니다.

그러나 현재 지표만으로는 전체 경로 조회, 경로 도형 재계산, 구간 전체 재삽입과 응답 생성 중 어느 단계가 처리 시간을 지배하는지 단정할 수 없습니다. 데이터베이스 커넥션 풀이 포화된 것은 요청이 실패한 직접적인 조건이지만, 커넥션을 오래 점유하게 만든 작업은 단계별 실행 시간을 측정해야 확인할 수 있습니다.

### 초기 해결 방향: 단계별 측정 후 확인된 병목만 개선

현재 검토할 수 있는 방법은 세 가지입니다.

- **단계별로 측정한 뒤 확인된 병목만 개선합니다.** 변경 범위와 회귀 위험을 줄이면서 개선 전후의 차이를 같은 지표로 검증할 수 있습니다. 이 방법을 우선 적용합니다.
- **전체 경로 처리 흐름을 한 번에 증분 방식으로 변경합니다.** 기존 경로 전체를 다시 처리하지 않고 새 좌표와 구간만 처리하므로 여러 비용을 함께 줄일 가능성이 있습니다. 그러나 측정 없이 좌표·도형·구간 저장 방식을 모두 바꾸면 변경 범위와 데이터 일관성 위험이 커집니다.
- **데이터베이스 커넥션 풀이나 HTTP 시간 제한만 늘립니다.** 시간 초과 시점을 늦출 수는 있지만 경로 길이에 따라 작업량이 증가하는 구조는 남으므로 근본적인 해결 방법으로 선택하지 않습니다.

먼저 전체 경로 조회, 경로 도형 재계산, 구간 삭제·재삽입과 응답 생성에 걸리는 시간을 나누어 측정하겠습니다. 저장 단계가 병목이면 공개 API 응답 계약을 유지한 채 증분 저장할 범위를 검토합니다. 전체 응답 생성이나 전송이 병목이면 `docs/api/api-spec.md`의 계약과 Android에 미치는 영향을 별도로 검토한 뒤 수정 범위를 정합니다. 백엔드 저장소 구현은 현재 기준대로 MyBatis와 명시적인 SQL을 사용합니다.

- **1차 수정: 누적 데이터 재처리 제거**

  - **문제:** `31 RPS` 부하 테스트에서 30분 경로는 처리됐지만, 8시간 경로는 두 번 모두 약 13초 만에 시간 초과가 발생했습니다. 요청 경로를 추적한 결과, 업무폰이 보낸 GPS 좌표 6개 묶음을 추가할 때마다 누적 좌표, 구간과 제외 좌표를 모두 읽고 기존 구간과 제외 좌표 전체를 삭제한 뒤 다시 저장하고 있었습니다.
  - **변경:** 누적 좌표, 구간과 제외 좌표를 불러오지 않고, 요청으로 받은 좌표 묶음에서 새로 생긴 좌표, 구간과 제외 좌표만 추가로 저장하도록 변경했습니다. 기존 구간과 제외 좌표는 유지하고, 새 구간과 제외 좌표는 각각 한 번의 SQL로 묶어서 저장합니다.

- **2차 수정: 전체 경로 LineString을 조회 시점에 생성**

  - **문제:** 1차 수정 뒤에도 좌표 묶음을 추가할 때마다 기존 전체 경로에 새 좌표를 이어 붙여 LineString을 다시 저장했습니다. 실제 좌표 패턴으로 도형 갱신 시간을 측정하니 중앙값이 30분 경로 `0.517ms`, 8시간 경로 `5.986ms`, 24시간 경로 `17.607ms`로 증가했습니다.
  - **변경:** 새 GPS 좌표는 전체 경로 LineString에 합치지 않고 좌표 단위의 행으로 추가하며, 전체 경로 LineString은 좌표 추가 시점에 갱신하지 않도록 변경했습니다. 전체 경로를 조회할 때 저장된 좌표를 순서대로 이어 LineString을 만듭니다.

- **검증 결과:** 30분, 8시간과 24시간 경로를 각각 두 번 시험했으며, 총 6번 모두 `31 RPS`를 5분 동안 시간 초과와 누락 없이 처리했습니다.
- **트레이드오프:** 좌표 추가 비용은 누적 경로 길이와 분리됐지만, LineString 조립 비용은 전체 경로를 조회하는 시점으로 이동했습니다. 24시간 경로의 좌표 34,560개를 LineString으로 조립하는 시간은 중앙값 약 `54ms`였지만, 상황판의 동시 조회 부하는 이번 시험에 포함하지 않았습니다.

### 문제 발견: 8시간 경로에서 시간 초과

처음부터 저장된 경로 길이만 바꾸고 `31 RPS`를 5분 동안 보내는 부하 테스트를 진행했습니다. 30분 경로는 두 번 모두 끝까지 처리됐지만, 좌표와 구간이 16배 많은 8시간 경로는 두 번 모두 약 13초 만에 중단됐습니다. HTTP 응답 시간 p95는 약 10초까지 늘었고, 데이터베이스 커넥션 10개를 모두 사용한 상태에서 커넥션을 기다리는 요청이 최대 190개까지 쌓였습니다.

이 결과로 서버의 전체 처리 한계가 아니라, 누적 경로가 길어질수록 좌표 추가 요청의 처리 비용이 증가하는 문제를 확인했습니다. 어느 단계가 비용을 키우는지 찾기 위해 `SearchPathService.appendPointsOnce()`부터 MyBatis SQL까지 실제 요청 경로를 추적했습니다.

### 1차 수정: 누적 데이터 재처리 제거

기존 구현은 새 GPS 좌표 6개를 추가하기 위해 누적된 GPS 좌표, 구간과 제외 좌표를 모두 읽었습니다. 전체 구간을 삭제하고 새 구간을 포함한 모든 구간을 다시 저장했으며, 누적 경로 도형과 새 좌표 도형을 `ST_MakeLine`으로 이어 새 LineString을 저장했습니다. 요청 크기는 같아도 기존 경로가 길수록 읽고 계산하고 저장하는 데이터가 늘어나는 구조였습니다.

GPS 좌표 묶음 자체는 변경 전에도 한 번의 SQL로 저장했습니다. 커밋 [`64786ddc`](https://github.com/sonic8-8/suri-map/commit/64786ddceca94b32c4148b8ca10cf04afe3db279)에서 바꾼 핵심은 이 묶음을 처리하기 위해 누적 경로 전체를 불러오던 흐름입니다. 좌표를 추가할 때 경로 메타데이터와 다음 `point_order`만 잠금 조회하고, 요청으로 받은 좌표에서 새 구간과 제외 좌표만 만듭니다. 기존 구간과 제외 좌표는 삭제하거나 다시 저장하지 않으며, 새 구간과 제외 좌표는 각각 한 번의 SQL로 묶어서 저장합니다. 구간 보정도 대상 구간과 경로 버전만 갱신하도록 범위를 줄였습니다.

### 추가 비용 발견: 좌표 추가 때 전체 경로 LineString 재생성

1차 수정으로 누적 좌표와 구간의 재처리는 제거했지만, 수정 범위를 검증하기 위해 요청 경로를 다시 추적하던 중 PostgreSQL이 기존 `search_path.geometry`와 새 좌표를 `ST_MakeLine`으로 이어 전체 LineString을 다시 저장하는 작업은 남아 있음을 발견했습니다. 따라서 구간 저장을 증분 방식으로 바꾼 것만으로는 누적 경로 길이에 비례하는 작업을 모두 제거한 상태가 아니었습니다.

### 병목 측정: 전체 LineString 재생성과 압축 저장

1차 수정 뒤 같은 조건으로 부하 테스트를 다시 실행하자 시간 초과와 데이터베이스 커넥션 대기는 사라졌습니다. 그러나 HTTP 응답 시간 p95는 30분 경로 `23.95~27.14ms`, 8시간 경로 `37.16~37.35ms`, 24시간 경로 `65.63~65.69ms`로 증가했습니다. 누적 경로 길이에 비례하는 작업이 남아 있다고 보고 실제 Mapper의 도형 갱신 SQL을 경로 길이별로 분리해 측정했습니다.

| 초기 경로 | 저장된 LineString 크기 | 도형 갱신 중앙값 | PostgreSQL CPU | 디스크 쓰기 |
| --- | ---: | ---: | ---: | ---: |
| 30분 | 약 5KB | 0.517ms | 약 39% | 약 1.3MB/s |
| 8시간 | 약 78KB | 5.986ms | 약 73% | 약 9MB/s |
| 24시간 | 약 235KB | 17.607ms | 약 130% | 약 31MB/s |

마지막 `point_order` 조회는 경로 길이와 관계없이 약 `0.02~0.03ms`였고, GPS 좌표와 구간 삽입도 각각 약 `0.03~0.07ms`였습니다. 24시간 경로에서 GiST 인덱스 유무에 따른 차이는 약 `0.5ms`였으며 전체 테이블 스캔도 발생하지 않았습니다. 반면 24시간 LineString의 도형 갱신은 기본 `pglz` 압축에서 `17.607ms`, `lz4` 압축에서 `3.873ms`가 걸렸습니다.

따라서 지배적인 병목은 누적된 전체 LineString을 요청마다 다시 만들고, 큰 값을 별도로 보관하는 PostgreSQL의 TOAST 영역에 도형을 압축해 저장하면서 복구용 변경 로그인 WAL을 기록하는 과정으로 판단했습니다. 압축 방식만 바꾸면 비용을 줄일 수 있지만 경로가 길수록 갱신 시간이 늘어나는 구조는 남기 때문에, 전체 LineString 갱신 자체를 좌표 추가 경로에서 제거하기로 했습니다.

### 2차 수정: 전체 경로 LineString을 조회 시점에 생성

커밋 [`0cf81955`](https://github.com/sonic8-8/suri-map/commit/0cf8195500344f11adc9cf5dde0a38db636f4da1)에서는 좌표 추가 시 `search_path.geometry`에 저장된 전체 경로 LineString을 다시 만드는 작업을 제거했습니다. 새 GPS 좌표는 기존처럼 좌표 단위의 행으로 추가하고, 좌표 추가 요청에서는 새 구간과 `search_path` 버전만 함께 저장합니다. 전체 경로를 조회할 때 저장된 GPS 좌표를 `point_order` 순서로 이어 LineString을 만듭니다. 이 변경은 전체 경로 LineString에만 적용하며, 새 구간의 LineString은 계속 저장합니다.

리팩터링 과정에서 종료된 근무의 경로와 요청한 운영 기간이 아닌 다른 운영 기간의 경로에도 좌표를 추가할 수 있었던 검증 누락을 발견했습니다. 좌표를 저장하기 전에 활성 근무와 경로의 운영 기간을 확인하고, 조건이 맞지 않으면 기존 데이터를 변경하지 않도록 함께 보완했습니다.

### 트레이드오프: 전체 경로 조회 시 LineString 생성

전체 경로 조회와 수색 이력 요약에서 경로 도형이 필요하면 `search_path_gps_point`에 저장된 좌표를 `point_order` 순서로 이어 LineString을 만듭니다. GPS 좌표가 없는 기존 경로는 저장된 `search_path.geometry`를 계속 사용하므로 기존 데이터와의 호환성은 유지합니다.

이 방식은 쓰기 요청이 기존 LineString의 길이에 영향을 받지 않게 하는 대신 조회 시점에 누적 좌표를 읽고 도형을 만드는 비용이 발생합니다. 24시간 경로에 저장된 좌표 34,560개를 LineString으로 조립하는 시간은 중앙값 약 `54ms`였습니다. 전체 경로를 자주 조회하거나 여러 사용자가 동시에 조회하는 조건의 성능은 별도로 확인해야 합니다.

### 저장 결과: 좌표 누락·중복과 커넥션 대기 0건

각 실행이 끝난 뒤 k6의 실제 `iterations`와 PostgreSQL 저장 결과를 대조했습니다. 요청이 9,300건인 실행에는 GPS 좌표 55,800개가, 9,301건인 실행에는 GPS 좌표 55,806개가 저장됐습니다. `pointId`는 모두 고유했고 제외된 좌표는 없었습니다. 멱등성 처리 기록 수도 실제 요청 수와 같았으며 모두 `COMPLETED` 상태였습니다.

데이터베이스 커넥션은 최대 2개까지 사용했고 커넥션 대기는 모든 실행에서 0건이었습니다. App 서버 CPU는 최대 14.68%, Ops 부하 발생기 CPU는 최대 34.62%였습니다. 부하 발생기나 데이터베이스 커넥션 풀이 먼저 포화돼 결과를 제한한 정황은 없었습니다.

로컬에서는 `cd backend && ./gradlew test`를 실행해 GPS 좌표 순서, 전체 경로 조회와 기존 geometry 호환성 테스트를 포함한 전체 Backend 테스트가 통과하는 것을 확인했습니다. 시험을 마친 뒤 전용 테스트 데이터와 인증 정보를 삭제했고, PostgreSQL autovacuum이 정리를 완료한 뒤 Backend 상태가 `UP`인지 다시 확인했습니다.

1차 수정 뒤에도 경로 길이에 따라 응답 시간이 증가하자 도형 갱신, 마지막 좌표 순서 조회, GPS 좌표·구간 삽입을 같은 조건에서 분리해 측정했습니다. 이 결과로 전체 LineString 재생성과 압축 저장을 지배적인 병목으로 특정했고, 해당 작업을 제거하는 2차 수정의 근거로 사용했습니다. 24시간 경로의 전체 경로 조립 시간도 별도로 측정했지만, 여러 사용자가 동시에 전체 경로를 조회하는 조건은 이번 부하 테스트 범위에 포함하지 않았습니다.

### 해결 판단: 좌표 추가 문제 해결과 조회 성능 분리

새 GPS 좌표를 추가할 때 기존 경로 전체를 다시 처리하던 동작을 제거했고, 변경 전 실패했던 8시간 조건과 더 긴 24시간 조건을 각각 두 번 통과했습니다. Backend 테스트로 좌표 순서를 확인했고 부하 테스트의 멱등성 처리와 저장 개수도 일치하므로, 이 Issue에서 확인한 좌표 추가 문제는 해결됐다고 판단합니다.
