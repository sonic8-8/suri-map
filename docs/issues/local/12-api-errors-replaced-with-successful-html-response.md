# 제목

[Infra] 서버 재시작 중 API 오류가 HTTP 200의 HTML 페이지로 바뀌는 문제

# 본문

## 문제 배경

상황판은 서버에서 변경 알림(SSE)을 받은 뒤 최신 마커·경로를 다시 조회합니다. 서버가 재시작 중이어서 요청을 처리할 수 없다면, 클라이언트가 실패를 구분할 수 있도록 API의 오류 상태가 유지돼야 합니다.

2026-09-28 `d1717bc6` 배포 후 복구 시험에서, SSE 재전송 요청에 HTTP 200과 HTML 페이지가 내려왔습니다. 기대한 `text/event-stream`과 이벤트 순번이 없어 검사가 실패했습니다. 같은 서버가 기동된 뒤에는 같은 DB 이력 조회가 정상 동작했습니다.

이 응답을 SSE 이력이 사라졌다는 증거로 해석할 수는 없습니다. 요청한 API 주소·응답 유형·프록시의 오류 처리를 구분해 확인합니다. [상황판 조회의 커넥션 대기 문제](11-board-query-database-connection-pool-exhaustion.md)와도 원인을 구분합니다.

### 문제 해결: 체크리스트

- [x] 수리맵 API의 upstream 오류 상태·본문을 유지하고 정상 웹 페이지로 대체하지 않는가?
- [x] 서버 재시작 중의 HTTP 오류와 기동 후의 정상 SSE 응답을 구분해 검증하는가?
- [x] 수리맵의 일반 웹 화면·로그인과 다른 서비스의 프록시 설정을 유지하는가?

# 댓글

## 수정 전: 확인한 원인과 영향

- 원인: App 서버의 Nginx가 수리맵 upstream의 502·503·504를 정적 HTML 페이지로 대체합니다. 이 설정이 일반 화면뿐 아니라 `/api/` 요청에도 적용됩니다.
- 영향: SSE 요청에 이벤트가 아닌 HTML이 HTTP 200으로 반환됩니다. 검증 도구도 `/api/health`의 상태 코드만 확인해, 아직 준비되지 않은 서버를 정상으로 판단했습니다.
- 범위: 서버의 Nginx 설정은 아직 수정하지 않았습니다. 검증 도구의 준비 확인만 실제 API 응답 본문의 `status: UP`·`service: suri-map-api` 확인으로 보완했습니다. 이는 프록시 문제의 해결과 다릅니다.

### 응답 확인: SSE 대신 HTML 반환

실패한 요청의 주소는 원래 수리맵 사건 SSE 주소였고, 리다이렉트도 없었습니다. 응답은 HTTP 200·`text/html`·615바이트, HTML 제목은 `Suri Map`이었습니다. SSE 순번과 연결 안내는 없었습니다. 따라서 이벤트 목록이 비었다는 것과 이벤트 저장·조회가 실패했다는 것을 구분해야 합니다.

마커를 수정하지 않는 축소 시험에서도 재현했습니다. 서버 재시작 전에는 순번 33·34를 받았지만, 재시작 후 HTTP 성공 여부만 보고 보낸 같은 요청은 HTML을 받았습니다. 반면 실제 API의 `UP` 본문을 기다리는 앞선 비교 시험은 재시작 전후 이력 조회가 모두 통과했습니다. 마커 쓰기나 관찰 탭의 오프라인 설정 없이도 실패할 수 있습니다.

### 프록시 설정: API까지 적용된 대체 페이지

실제로 로드된 `/etc/nginx/sites-enabled/apps.conf`의 `suri-map.sonic8-8.com` 서버 블록을 확인했습니다.

```nginx
location / {
    proxy_pass http://127.0.0.1:18081;
    proxy_intercept_errors on;
    error_page 502 503 504 = @suri_map_placeholder;
}

location @suri_map_placeholder {
    try_files /index.html =502;
}
```

API도 `location /`을 거쳐 오류 대신 `/var/www/suri-map/index.html`을 받는 구조입니다. 저장소의 [Frontend Nginx](../../../frontend/nginx.conf)만 바꿔서는 이 바깥쪽 호스트 설정을 해결할 수 없습니다. 같은 파일에는 다른 서비스의 서버 블록도 있으므로 수정 범위는 수리맵으로 제한해야 합니다.

## 수정 전: 검증 결과와 남은 작업

기동된 서버의 이력 조회와 관찰 브라우저의 온라인·오프라인·온라인 복귀 비교는 통과했습니다. 커넥션 풀 대기·timeout은 0이었으며, 이번 HTML 응답을 기존 DB 커넥션 풀 고갈의 재발로 집계하지 않습니다.

시험용 마커는 매번 정상 WEB API로 원래 좌표를 복원했고 변경 이력은 보존했습니다. HTML 응답으로 실패한 두 시험 후 마커 9개·전송 작업 626개·마지막 순번 34·기준 마커 버전 19를 확인했습니다.

다음은 API 요청에서 오류 상태를 보존하도록 호스트 프록시의 수정 범위를 정하고, 실제 재시작 중 응답과 기동 후 브라우저 복구를 다시 확인하는 작업입니다. 일반 화면의 대체 페이지 유지 여부는 API 오류 처리와 별도로 정합니다. 새 프록시 설정은 적용하지 않았으며, GitHub에도 아직 등록하지 않은 로컬 이슈입니다.

준비 검사를 보완한 뒤에는 같은 탭의 순번 34 → 35 이어받기·상황판 재조회·지도 이동·원래 좌표 복원이 통과했습니다. 최종 상태는 마커 9개·전송 작업 628개·마지막 순번 36·버전 21입니다. 서버가 실제로 준비된 뒤의 복구 성공이며, 재시작 중 오류를 성공 HTML로 바꾸는 설정은 그대로입니다.

실패·비교 명령과 로그는 [배포 검증 기록(로컬 전용)](../../../_workspace/board-pool-deploy-20260928.Uq0mCy/RESULTS.md)에 보존합니다.

## 수정 결과: API 오류 상태 보존

- 문제: 서버 재시작 중 API의 502·503·504가 HTTP 200의 정상 웹 페이지로 바뀌었습니다.
- 변경: 호스트 Nginx에서 `/api`·`/api/...` 요청을 별도로 처리하고 upstream 오류 상태·본문을 그대로 전달하도록 했습니다. 일반 웹 화면의 대체 페이지와 다른 서비스 설정은 유지했습니다.
- 결과: 실제 재시작 중 health·SSE 요청이 502를 반환했고, 기동 후 같은 상황판의 이력 이어받기·지도 갱신·원래 위치 복원까지 통과했습니다.

### 프록시 수정: API와 일반 화면 분리

[API 전용 설정](../../../infra/nginx/suri-map-api.locations.conf)을 서버의 `/etc/nginx/snippets/`에 설치하고 수리맵 HTTPS 블록에서만 포함했습니다. 인증·채널·재전송 헤더, 요청 경로와 Frontend 전달 포트는 유지했습니다. 애플리케이션 코드를 바꾸거나 API 오류를 새로운 JSON 형식으로 변환하지는 않았습니다.

원본은 `/srv/apps/suri-map/backups/nginx-api-errors.G88YUb/apps.conf`에 백업했습니다. 설정 검사 후 reload했고, 실제 로드된 include와 파일 해시도 확인했습니다. [적용 설명](../../../infra/nginx/README.md)에 범위·백업·검사 순서를 남겼습니다. 이 파일은 Jenkins가 자동 설치하지 않으므로 애플리케이션 배포와 구분합니다.

### 수정 전후 비교: 같은 검사로 실패와 통과 확인

서버의 동일한 Nginx 바이너리를 격리된 loopback 포트에서 실행했습니다. 합성 upstream이 502를 반환했을 때 기존 설정은 200·HTML로 바꿔 검사에 실패했습니다. 수정 설정은 같은 검사를 통과했습니다.

총 14항목에서 API의 502·503·504 상태·본문·Retry-After 보존, 비 API 경로의 기존 대체 페이지, GET·PATCH의 메서드·주소·인증·채널·재전송 헤더를 확인했습니다. 시험용 Nginx는 검증 후 종료했습니다.

### 실제 재시작: 오류 응답부터 지도 복구까지 확인

DB 백업 후 기존 시험용 마커 하나로 확인했습니다.

1. 상황판 연결을 끊고 마커를 이동했습니다. DB에는 37번 이벤트·버전 22가 저장됐고, 관찰 탭이 아직 받지 않은 상태에서 Backend를 재시작했습니다.
2. 재시작 중 health·사건 SSE 주소가 모두 502를 반환했습니다. 본문은 Nginx의 HTML 오류 페이지이며, 200의 정상 웹 페이지로 대체되지 않았습니다. 기동 후 health는 UP JSON, 비인증 SSE는 원래의 401 JSON으로 돌아왔습니다.
3. 인증된 HTTP 요청과 같은 관찰 탭이 순번 36부터 37번을 이어받았습니다. 새로고침 없이 상황판 재조회·지도 이동을 확인했고, 정상 WEB API로 원래 위치를 복원한 38번 이벤트도 반영됐습니다.

최종 상태는 마커 9개·전송 작업 630개·마지막 순번 38·시험 마커 버전 23입니다. 다른 마커와 기존 이력은 보존했고, 이번 이동·복원 이력 2개도 남겼습니다. 브라우저 JS 오류 0, 최종 데이터베이스 커넥션 사용 0·유휴 10·대기 0·timeout 0을 확인했습니다.

새 Backend 프로세스의 수집 시점까지 ERROR는 0건이었습니다. 38번 전송 중 쓰기에 실패한 SSE 연결을 제거한 WARN 1건은 남았지만, 관찰 탭의 해당 이벤트 수신·복원은 통과했습니다. [끊긴 연결 정리 문제](5-sse-initial-send-disconnect-cleanup.md)까지 해결한 것으로 보지는 않습니다.

실제 로그인·마커 수정·SSE 수신도 통과했습니다. 수리맵과 다른 두 서비스의 루트 주소는 적용 전후 모두 200이었지만, 다른 서비스의 모든 기능을 시험한 것은 아닙니다.

명령·실패와 통과 로그·복구 화면은 [이번 검증 기록(로컬 전용)](../../../_workspace/api-proxy-fix-20260928.I6nUvL/RESULTS.md)에 보존합니다. 세 확인 항목은 완료했으며, SSE 전체 요구 검증이나 상황판 부하 시험의 완료를 뜻하지는 않습니다. 커밋·푸시·GitHub 등록은 아직 하지 않았습니다.
