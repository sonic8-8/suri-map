# 제목

[BE] SSE 초기 전송 중 연결 종료 시 요청 정리 로그와 연결 해제 여부 확인

# 본문

## 문제 배경

상황판은 SSE 연결로 서버의 새 이벤트를 받습니다. 새로고침이나 화면 이동으로 브라우저가 연결을 끊으면 서버도 해당 연결을 정리해야 합니다. 새 업무 이벤트가 없다는 이유로 끊어진 연결을 계속 보관해서는 안 됩니다.

2026-09-15 로컬 알림 검증 중 Tomcat이 요청을 정리하면서 `CoyoteAdapter$RecycleRequiredException` INFO 로그를 남겼습니다. 접근 거부는 없었고 지도·알림 표시도 통과했습니다. 그러나 화면이 정상이라는 사실만으로 서버의 연결 정리까지 정상이라고 판단할 수 없어, 종료 후 연결 목록과 콜백을 따로 확인했습니다.

### 문제 해결: 체크리스트

- [x] MVC·Servlet 대역 검사에서 응답 준비 후 초기 전송을 시작하고, 시작 전 종료·전송 오류·작업 제출 거부 시 구독을 정리하는가?
- [ ] 실제 HTTP 초기 전송 중 연결을 끊어도, 다음 업무 이벤트에 의존하지 않고 해당 연결을 정리하는가?
- [ ] 실제 연결 종료를 반복해도 정상 연결·재연결은 이벤트를 받고, 종료한 연결만 정리되는가?

## 원인 분석과 선택지

### 최초 가설: 초기 전송 실패가 종료 콜백 등록을 건너뜀

수리맵·DB·보안 필터를 제외한 최소 서버에서도 같은 로그가 나타났습니다. 초기 데이터를 받자마자 연결을 끊는 10회 검사에서는 8회 발생했지만, 반복 검사에서는 0회였습니다. 당시 오류·완료 콜백도 관측되지 않았습니다. 초기 전송과 연결 종료의 타이밍이 관련돼 보였지만, 이 결과만으로 원인이나 영구적인 리소스 누수를 확정하지 않았습니다.

Spring이 초기 버퍼를 보낸 뒤 종료 콜백을 등록한다는 점에서, 전송 중 예외가 등록을 건너뛸 수 있다는 가설을 세웠습니다. 콜백은 연결의 오류·완료 시 실행할 정리 코드입니다. [최초 비교와 소스 조사](../../../_workspace/notification-followup-20260915.Ilboqt/RESULTS.md) 이후 실제 수리맵의 연결 관리 코드를 붙여 실패 위치를 확인했습니다.

### 추가 진단: 다음 이벤트를 보낼 때 남은 연결 제거

2026-09-15 실제 `SseStreamService`·`SseConnectionRegistry`·메모리 재전송 저장소를 최소 서버에 연결했습니다. DB·보안 필터·브라우저 화면은 제외하고 실제 HTTP 연결을 끊었습니다. 환경은 Java 17·Spring Boot 3.5.14·Spring 6.2.18·Tomcat 10.1.54이며, 마지막 비교는 이전 연결의 영향을 없애려고 조건별로 서버를 새로 시작했습니다.

| 조건 — 각각 연결 20개 종료 | 새 이벤트 전 연결 목록 | 새 이벤트 후 연결 목록 | 새 이벤트 후 오류·완료 콜백 | Tomcat 로그 |
|---|---:|---:|---|---:|
| 초기 기록 100개 전송 중 종료 | 20개 | 0개 | 각각 0회 | 20회 |
| 초기 기록 없이 연결 후 종료 | 20개 | 0개 | 각각 20회 | 0회 |

초기 기록이 있는 조건은 반복 검사와 Fetch 요청 취소에서도 같은 로그가 각각 20회 발생했습니다. 100개·20회는 동작 비교를 위한 진단 입력이며 부하 한계나 허용 지연 기준이 아닙니다.

초기 이벤트는 서비스의 `emitter.send()` 호출 시 버퍼에 담겼다가 Controller가 반환된 뒤 실제로 전송될 수 있습니다. 계측 결과 `ResponseBodyEmitter.initialize()` → `sendInternal()`에서 `AsyncRequestNotUsableException`이 발생했고, 뒤에 있는 종료 콜백 등록까지 도달하지 못했습니다. [Spring 6.2.18 소스](https://github.com/spring-projects/spring-framework/blob/v6.2.18/spring-webmvc/src/main/java/org/springframework/web/servlet/mvc/method/annotation/ResponseBodyEmitter.java)의 실행 순서와 일치했습니다.

다음 이벤트를 보내자 `SseConnectionRegistry`가 `UncheckedIOException`을 처리하며 남은 연결을 제거했습니다. 따라서 다음 전송 이후에도 남는 누수는 확인하지 않았습니다. 반면 새 이벤트가 없는 동안의 자동 정리도 확인하지 못했습니다. [재현 코드·조건별 로그·실패 스택](../../../_workspace/sse-connection-cleanup-20260915.OVWEwb/RESULTS.md)은 로컬 전용 자료입니다.

### 수정 방향: 응답 준비 후 전송과 주기적인 연결 확인을 구분

먼저 초기 버퍼 전송이 콜백 등록보다 앞서는 경로를 피하도록, 응답 준비 이후에 초기 전송을 시작하는 방식을 선택했습니다. 로그 수준을 낮추거나 인증 검사를 생략하는 변경은 하지 않습니다.

주기적인 연결 확인은 별도 문제입니다. 당시 구현에는 시작 주석만 있고 주기 전송이나 emitter 만료 시간이 없었습니다. Spring은 끊어진 연결을 감지하도록 데이터나 빈 SSE 주석을 주기적으로 보내는 방법을 안내합니다. 다만 이 방법만으로 초기 전송 로그까지 사라진다고 보지는 않습니다. [Spring MVC 연결 종료 설명](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html#webmvc-ann-async-disconnects).

## 변경 내용과 트레이드오프

- 변경: `SseEmitter`는 유지하고 초기 전송을 MVC 응답 준비 이후의 컨테이너 작업으로 옮겼습니다.
- 남은 확인: 실제 HTTP 종료 실험은 다시 실행하지 않았으므로, Tomcat 로그와 새 이벤트가 없을 때의 연결 정리까지 해결됐다고 판단하지 않습니다.

2026-09-27 초기 전송 시작 전에 연결이 종료되면 전송하지 않도록 수정했습니다. 초기 쓰기 실패 시 사건·계정 구독을 해제하고, 작업 제출 거부나 내부 오류가 발생해도 열린 응답을 남기지 않도록 처리했습니다.

## 검증 결과

| 검증 범위 | 결과 |
|---|---|
| MockMvc의 MVC 반환 처리·Servlet 대역 | 시작 시점, 시작 전 종료·시간 초과·오류, 초기화 중 오류, 작업 제출 거부, 전송 오류, 종료 사건 재접속 검사 통과 |
| 관련 Controller·Stream·Registry | 각각 16개·6개·10개 통과 |
| Docker 연결 후 전체 Backend 재실행 | 1,293개 통과, 실패·오류·건너뜀 0개, 4분 23초. 기본 성능 태그 제외 |
| 실제 HTTP 연결을 끊는 기존 20회 실험 | 수정 후 미실행 |

처음에는 Docker 부재로 DB 검사가 건너뛰어졌습니다. 이후 `cd backend && ./gradlew test --rerun-tasks --console=plain`으로 다시 실행한 전체 결과에는 실제 PostgreSQL/PostGIS의 Service 20개·Mapper 11개·Worker 12개가 포함됩니다. 재검증 중 코드·테스트를 바꾸지는 않았습니다.

첫 번째 해결 기준은 대역 검사 범위에서 충족했습니다. 실제 HTTP 연결 정리와 반복 재접속의 두 기준은 미완료입니다. 주기적인 연결 확인, DB 이력 재전송·실시간 전환·대기량 제한은 [이벤트 전달의 후속 범위](../../features/event-delivery.md#sse-재연결과-중복-처리)에서 이어갑니다. 이 문서는 GitHub에 등록하지 않은 로컬 이슈입니다.
