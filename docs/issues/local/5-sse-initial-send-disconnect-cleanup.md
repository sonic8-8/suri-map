# 본문

## 문제 배경

브라우저는 새로고침이나 화면 이동으로 SSE 연결을 끊을 수 있습니다. 서버는 끊어진 연결의 처리를 마무리하고, 사용하지 않는 연결을 계속 보관하지 않아야 합니다.

로컬 알림 검증 중 Tomcat의 `CoyoteAdapter$RecycleRequiredException` INFO 로그가 남았습니다. 접근 거부는 없었고 최종 지도·알림 검증도 통과했지만, 로그만으로 연결 정리까지 정상이라고 판단할 수는 없습니다.

### 문제 해결: 체크리스트

- [x] 실제 SSE 연결 종료에서 로그를 재현하고 최근 인증 수정과 구분했는가?
- [x] 수리맵·DB·보안 필터가 없는 최소 서버에서도 같은 로그를 확인했는가?
- [ ] 초기 전송 실패가 어떤 내부 종료 경로를 거치는지 확인했는가?
- [ ] 실패 후 수리맵의 연결 참조와 콜백이 정리되는지 확인했는가?
- [ ] 영향이 확인되면 정상 연결·재연결을 보존하는 최소 수정과 반복 검증을 마쳤는가?

## 확인 결과와 남은 가설

실제 앱과 같은 Java 17·Spring Boot 3.5.14·Spring 6.2.18·Tomcat 10.1.54의 최소 서버를 사용했습니다. 초기 데이터를 미리 담아 보내고 첫 데이터를 읽은 클라이언트가 연결을 끊자, 10회 검사에서 같은 로그가 8회 발생했습니다. 그러나 같은 검사를 반복했을 때는 0회였습니다. 초기 데이터를 보내는 도중 끊기는 타이밍이 관련될 수 있지만, 정확한 발생 조건은 아직 확정하지 않았습니다.

관측 구간의 오류·완료 콜백은 0회였습니다. Spring 소스는 초기 버퍼를 보낸 뒤 Handler의 콜백을 등록하므로, 초기 전송 실패가 콜백 등록을 건너뛸 수 있다는 가설을 남깁니다. 해당 내부 예외 지점을 직접 계측한 것은 아니며, 초기 데이터가 없는 비교에서도 콜백은 관측되지 않았습니다. 영구 리소스 누수로 단정하지 않습니다.

Tomcat 로그는 미정리 요청·응답을 정리하면서 남기는 진단 기록입니다. 예외 이름이 출력됐다는 이유만으로 업무 요청 실패나 최근 인증 문제의 재발로 보지 않습니다. 반대로 로그 수준만 낮춰 문제를 없어진 것으로 처리하지도 않습니다.

## 2026-09-27 수정: 응답 준비 후 초기 전송 시작

`SseEmitter`를 유지하면서 초기 이벤트 전송을 MVC 응답 준비 이후의 컨테이너 작업으로 옮겼습니다. 초기 버퍼 전송이 종료 콜백 등록보다 먼저 실행되던 경로를 피하려는 변경입니다. 시작 전에 연결이 종료되면 전송하지 않고, 초기 쓰기가 실패하면 사건·계정 구독의 등록을 해제합니다. 작업 제출 거부와 내부 전송 오류도 열린 응답을 남기지 않도록 처리했습니다.

MockMvc의 실제 MVC 반환 처리와 Servlet 대역으로 시작 시점·시작 전 종료/timeout/오류·초기화 도중 오류·작업 제출 거부·I/O/내부 오류·종료 사건 재접속을 검사했습니다. 관련 Controller 16개·Stream 6개·Registry 10개는 통과했습니다. 처음에는 Docker 부재로 DB 검사가 건너뛰어졌지만, Docker 연결 후 `cd backend && ./gradlew test --rerun-tasks --console=plain`으로 다시 실행해 **전체 1,293개 통과·실패/오류/건너뜀 0개**를 확인했습니다(4분 23초, 기본 성능 태그 제외). 실제 PostgreSQL/PostGIS의 Service 20개·Mapper 11개·Worker 12개도 포함하며, 재검증 중 코드·테스트 수정은 없었습니다.

실제 HTTP 연결을 끊던 위 20회 실험은 아직 다시 실행하지 않았습니다. 따라서 Tomcat 로그 문제가 해결됐거나 새 이벤트 없이도 모든 연결이 자동 정리된다고 결론내리지 않으며, 마지막 체크리스트는 미완료로 유지합니다. DB 재전송 연결·순서·대기량 제한·주기적인 연결 확인도 별도 후속 작업입니다. [변경 범위와 검증 한계](../../features/event-delivery.md#sse-재연결과-중복-처리).
