# 제목

[BE/FE] 누적 수색 경로가 있는 상황판을 열 때 조회 대기 오류 발생

# 본문

## 문제 배경

지휘관은 상황판에서 업무폰들이 기록한 수색 경로를 확인합니다. 상황판은 서버에서 경로·마커 등을 조회해 지도에 표시하고, 변경 알림(SSE)을 받으면 최신 자료를 다시 조회합니다. 이전 경로가 쌓여 있더라도 이 과정이 완료돼야 현장 상황을 확인할 수 있습니다.

2026-10-01 배포 `c3109c10`에서 업무폰 468대가 각각 30분 동안 기록한 경로를 준비하고 상황판 하나를 열었습니다. GPS 좌표는 총 336,960개이며, 새 좌표나 마커를 보내기 전의 읽기 전용 검사였습니다.

기존 SSE 이벤트 48개를 받는 동안 상황판 조회 시작이 50회 기록됐습니다. 조회 완료 기록은 1회였고, 지도 표시 완료는 확인하지 못했습니다. 서버에는 데이터베이스 커넥션 풀의 커넥션 10개가 모두 사용 중인 상태에서 추가 커넥션을 30초 동안 얻지 못했다는 오류가 남았습니다. 커넥션 풀은 SQL 실행에 필요한 DB 연결을 빌려주는 곳이며, 반환되는 연결이 없으면 다른 요청도 기다리다가 실패합니다.

브라우저가 지도 준비를 끝내지 못해 종료했고, 예정한 GPS·마커 쓰기 Smoke와 본 부하테스트는 시작하지 않았습니다. 기록되지 않은 나머지 조회 49회가 모두 HTTP 오류였다고 판단한 것은 아닙니다. 임시 DEBUG 설정은 원복했고 기존 마커·경로의 내용이 유지되는지 확인했습니다.

### 문제 해결: 체크리스트

- [ ] 업무폰 468대의 30분 경로가 있는 상황판 하나를 열고 기존 SSE 이벤트를 받는 조건에서, 커넥션 획득 대기 오류 없이 경로 조회와 지도 표시를 완료하는가?

## 원인 분석과 선택지

현재는 커넥션이 모두 사용 중이었다는 사실까지 확인했습니다. 조회 한 번이 오래 걸리는지, 여러 조회가 겹치는지, 브라우저의 지도 처리나 측정 도구가 표시를 지연시키는지는 분리해서 확인해야 합니다. 커넥션 풀 크기를 늘리기보다 새 쓰기 없이 재현되는 최소 조건을 찾고, 조회 요청 수와 각 요청이 커넥션을 사용하는 구간을 먼저 측정하겠습니다.

[로컬 이슈 11](11-board-query-database-connection-pool-exhaustion.md)은 상황판 조회가 기존 커넥션을 잡은 채 패키지 상태 조회에서 두 번째 커넥션을 요구하던 문제를 수정한 기록입니다. 이번 오류도 커넥션 대기로 나타났지만 같은 원인인지는 아직 확인하지 않았습니다. 이번 이슈에는 누적 경로 조건에서 새로 발견한 현상을 남기고, 분석 결과와 수정·재검증은 발견 시점의 본문과 구분해 기록합니다.

## 변경 내용과 트레이드오프

- 변경: GPS 좌표를 Java 객체로 읽을 때마다 발생하던 생성자 접근 예외를 제거했습니다. 기본 생성자의 `protected` 제한과 SQL·공개 API는 유지했습니다.
- 결과: 같은 누적 경로의 첫 응답이 수정 전 17.75–17.95초에서 수정 후 5.33–6.81초로 줄었습니다.
- 남은 범위: 조회 비용이 아직 남아 있으며, 새 GPS·마커의 지도 반영과 본 부하테스트는 진행하지 않았습니다. 최초 장애 전체를 이번 원인 하나로 설명하지 않습니다.

### 조회 중 반복된 생성자 접근 예외

지도와 SSE를 제외하고 경로 API만 호출해도 응답이 느렸습니다. 서버의 요청 처리 스레드를 살펴보니, DB에서 읽은 좌표를 `GpsPoint` 객체로 만드는 과정에서 `IllegalAccessException`이 발생하고 있었습니다.

MyBatis는 `protected` 기본 생성자를 먼저 호출하고, 접근이 거부되면 접근을 허용한 뒤 다시 호출했습니다. 객체는 결국 만들어지지만 좌표를 읽을 때마다 예외를 만들고 호출 경로를 기록하는 비용이 반복됐습니다. 실제 MyBatis와 `GpsPoint`를 사용한 로컬 검사에서도 객체 1,000개를 만들 때 내부 접근 예외 1,000개가 발생했습니다. HTTP 요청 자체가 1,000번 실패했다는 뜻은 아닙니다.

### 생성자 접근 제한을 유지한 수정

기본 생성자를 `public`으로 바꾸는 대신, 호출 전에 접근을 준비하도록 객체 생성 방법을 바꿨습니다. `MyBatisObjectFactory`에서 기존 Spring의 `BeanUtils.instantiateClass`를 사용하고 `MyBatisConfig`에 등록했습니다. 도메인 객체의 생성자 제한은 그대로 유지합니다.

이 설정은 GPS Mapper에만 적용되는 것이 아니라 MyBatis의 기본 객체 생성 경로에 공통 적용됩니다. 생성자 인자를 명시한 경우와 컬렉션 구현 선택은 기존 MyBatis 동작을 유지했습니다. 새 의존성이나 캐시는 추가하지 않았습니다. 생성에 실패하면 원인을 보존해 전달하지만, 내부 예외 체인과 상세 메시지는 이전과 달라질 수 있습니다.

## 검증 결과

### 실제 Mapper의 반복 예외 제거

PostgreSQL/PostGIS에 저장한 좌표 2개를 실제 Mapper로 조회했습니다. 수정 전에는 생성자 접근 예외가 2개 발생했고, 수정 후에는 0개였습니다. 조회한 좌표 값·수집 순서·null 처리도 기존대로 유지됐습니다.

로컬 Backend 전체 검사와 배포 CI에서 각각 1,360개 테스트가 통과했습니다. 실패·오류·건너뜀은 0개이며, 기본 설정상 `performance` 태그는 제외했습니다. 수정 커밋 `d6612362`는 Jenkins #55로 배포했고 배포 소스 일치와 health 200을 확인했습니다.

### 같은 누적 경로의 조회 시간 비교

업무폰 468대가 각각 30분 동안 기록한 GPS 좌표 336,960개를 유지하고, 같은 사건의 경로 API를 배포 전후 각각 2회 조회했습니다. 지도·SSE가 없는 브라우저에서 공개 HTTP/2 경로로 순차 요청했으며 모두 HTTP 200을 받았습니다.

| 측정 구간 | 수정 전 | 수정 후 |
|---|---:|---:|
| 요청 시작부터 응답 헤더 수신까지 | 17.75–17.95초 | 5.33–6.81초 |
| 요청 시작부터 전송·JSON 파싱 완료까지 | 19.19–19.41초 | 6.75–9.45초 |

각 범위는 2회 측정한 값입니다. JVM의 준비 상태와 외부 네트워크 영향을 따로 통제하지 않았으므로 p95나 운영 성능 보장값으로 해석하지 않습니다. 이번 수정의 개선 효과는 확인했지만 남은 조회 비용까지 제거한 것은 아닙니다.

### 실제 상황판 확인과 남은 검증

실제 HTTP/3 상황판을 180초 관찰했습니다. 경로 조회 3건은 모두 HTTP 200으로 완료됐고, 동시 조회는 최대 1건이었습니다. 관찰 중 SSE 종료는 없었으며 종료 시 2개 연결이 활성 상태였습니다. DB 커넥션 풀의 배포 후 누적 timeout도 0건이었습니다. 확인 대상 데이터 건수·내용 해시와 SSE 순번 48·전송 작업 640개·마커 알림 8개는 유지됐습니다.

화면에서 타일·경로·마커 표시를 확인했습니다. 다만 지도 렌더링 계측에는 표시 여부를 확인하지 못한 경로 식별자 597개가 3회 남았습니다. 이전 배포 검사에도 같은 기록이 있었으며, 실제 누락인지 계측 한계인지는 아직 확인하지 않았습니다. 따라서 모든 경로의 표시를 검증했다고 보지 않고 본문의 해결 체크리스트를 미완료로 유지합니다. 첫 응답에 남은 5–7초도 추가 확인 대상이지 새로 정한 실패 기준은 아닙니다.
