[BE] 전체 배포 중 SSE 인증 거부와 상황판 화면 이동

# 본문

## 문제 배경

수리맵 상황판은 로그인 토큰을 붙여 SSE에 연결하고, 서버에서 변경 신호를 받으면 경로와 마커를 다시 조회합니다. 배포 중 연결이 끊기더라도 로그인이 유효하다면, 서버 복구 후 새로고침 없이 연결과 지도 갱신이 재개되어야 합니다.

2026-09-30 `74324faa`를 배포한 Jenkins #47은 성공했지만, 열어 둔 상황판의 화면 이동 검사는 실패했습니다. 검증 도구가 기록한 이동 횟수는 배포 전 2회에서 배포 후 4회로 늘었습니다. 같은 배포의 접근 로그에는 SSE 요청이 401로 거부된 기록도 있었습니다.

당시 도구는 실제 이동한 주소를 남기지 않고 종료됐습니다. 따라서 그 탭이 로그인 화면으로 이동했다고 단정할 수는 없지만, 배포 후에도 지휘관이 같은 상황판을 계속 볼 수 있는지는 확인하지 못했습니다. Backend만 따로 재시작했을 때의 자동 재연결·지도 갱신 성공과는 구분해야 합니다.

### 문제 해결: 체크리스트

- [x] 수정 배포 후, 유효한 로그인 상태로 열어 둔 상황판이 전체 배포 중에도 로그인 정보를 유지하고 서버 복구 뒤 새로고침 없이 SSE 재연결과 지도 갱신을 재개하는가?

## 원인 분석과 선택지

Backend는 로그인 토큰의 서명을 검증할 때 Keycloak이 제공하는 공개 키를 사용합니다. 이번 배포에서는 Keycloak도 재생성됐으며, SSE 401은 13:55:54 KST에 발생했고 Keycloak 기동 완료는 13:55:56 KST였습니다.

키를 가져올 수 없는 상태를 잘못된 토큰으로 처리했을 가능성이 있습니다. 다만 당시 Backend 예외와 토큰의 만료 여부를 확보하지 못했으므로, 실제 토큰 만료나 서명 문제도 배제하지 않았습니다. 시각이 가깝다는 이유만으로 원인을 확정하지 않고, 유효한 토큰은 그대로 둔 채 키 서버 상태만 바꿔 인증 결과를 비교합니다. 이후 확인한 결함과 수정 결과는 아래 댓글에 기록합니다.

## 변경 내용과 트레이드오프

- 확인한 결함: 서명 검증용 키를 가져오지 못한 경우도 잘못된 토큰과 같은 401로 처리했습니다.
- 변경 내용: 잘못된 토큰은 401을 유지하고, 키 조회 등 검증기 장애는 503으로 구분했습니다.
- 검증 범위: 수정 배포 후 실제 인증 서버 장애에서 로그인 유지·재연결을 확인했고, 별도 재시작 시험에서 지도 갱신도 확인했습니다. 최초 배포의 401과 동일 원인인지는 확정하지 못했습니다.

### 같은 토큰으로 키 조회 실패 재현

[SecurityConfigTest.java](../../../backend/src/test/java/com/surimap/SecurityConfigTest.java)에 실제로 서명한 유효 토큰과 로컬 HTTP 키 서버를 연결했습니다. Spring의 `NimbusJwtDecoder`가 실제 키 조회와 서명 검증을 수행하도록 하고, 제품 인증 필터를 통해 JSON API와 SSE 요청을 검사했습니다. 실제 Keycloak을 중단한 검사는 아닙니다.

키 서버가 503을 반환하면 두 요청 모두 401로 거부됐습니다. 키 서버를 정상 상태로 바꾸자 같은 토큰으로 API 요청이 성공했습니다. 이 결과를 두 번 재현해 토큰 자체가 아니라 키 조회 실패의 처리에 문제가 있음을 확인했습니다.

이때 발생한 예외는 `RemoteKeySourceException`을 원인으로 가진 `JwtException`이었습니다. 기존 인증 필터는 모든 `JwtException`을 인증 정보 없음으로 처리했습니다. 한편 웹의 [SSE 응답 처리](../../../frontend/src/shared/api/eventStream.ts)는 401을 받으면 저장된 세션을 삭제하는 경로로 이어집니다. 서버의 일시 장애가 사용자의 로그인 종료로 이어질 수 있는 구조였습니다.

### 잘못된 토큰과 검증기 장애 분리

[OidcBearerAuthenticationFilter.java](../../../backend/src/main/java/com/surimap/account/security/OidcBearerAuthenticationFilter.java)에서 만료·서명 오류를 나타내는 `BadJwtException`은 기존처럼 401로 처리하고, 그 외 `JwtException`은 503과 `{"error":"authentication_unavailable"}`을 반환하도록 수정했습니다. 진단 로그에는 예외 종류만 남기고 토큰 원문은 남기지 않습니다.

Keycloak 기동을 기다리는 설정만 추가하면 운영 중 발생하는 키 조회 장애를 구분하지 못합니다. 따라서 JSON API와 SSE가 함께 사용하는 인증 필터를 수정하고, 웹의 기존 503 재연결 처리는 그대로 사용했습니다. Frontend·Android 코드와 DB·Keycloak 설정은 바꾸지 않았습니다.

로그인 정보를 유지한다고 검증하지 못한 요청을 허용하는 것은 아닙니다. 인증 필터에서 요청을 차단하므로 키 조회가 복구되기 전까지는 요청이 실패할 수 있습니다. 이번 수정은 장애 자체를 없애는 것이 아니라, 장애를 로그인 실패로 잘못 전달하지 않도록 하는 변경입니다.

## 검증 결과

### 로컬 인증 검사와 브라우저 응답 대조

키를 캐시하지 않은 상태에서 시작한 인증 테스트의 결과입니다.

| 조건 | 수정 전 | 수정 후 |
|---|---|---|
| 유효 토큰·키 서버 503, JSON API 요청 | 401 | 503 |
| 유효 토큰·키 서버 503, SSE 요청 | 401 | 503, 스트림 시작 안 함 |
| 키 서버 복구 후 같은 토큰으로 API 요청 | 200 | 200 |
| 키 서버 정상·만료 또는 잘못된 서명의 토큰 | 401 | 401 |

별도로 배포된 웹에 로그인한 뒤, 해당 브라우저의 SSE 응답 한 건만 401 또는 503으로 바꿔 비교했습니다. 401에서는 토큰이 삭제되고 `/login`으로 이동했습니다. 503에서는 토큰과 상황판 주소가 유지됐으며, 화면 이동 없이 다음 SSE 연결이 200으로 성공했습니다. 이는 브라우저 응답 주입 검사이며 수정한 Backend와 실제 Keycloak을 함께 배포한 검증은 아닙니다.

### 실제 배포와 인증 서버 장애 복구

2026-10-01 인증 수정 `447e1a33`을 Jenkins #48로 배포했습니다. CI의 Backend 테스트 1,349개가 모두 통과했습니다. 배포 전부터 열어 둔 상황판은 로그인과 마지막 수신 순번 44를 유지했으며, 새로고침이나 추가 화면 이동 없이 SSE에 다시 연결됐습니다.

배포 확인과 별도로 Keycloak을 일시정지하고 Backend를 재시작했습니다. Backend가 캐시한 검증 키 없이 실제 키 조회 실패를 겪게 만든 조건입니다. SSE는 `503 authentication_unavailable`을 반환했고, Keycloak 복구 후 같은 토큰으로 200 재연결됐습니다. 이 과정에서 502·504도 관측했지만 401이나 화면 이동은 없었습니다.

지도 갱신은 별도 시험으로 확인했습니다. 상황판을 오프라인으로 둔 동안 시험용 마커 하나를 수정하고 Backend를 재시작했습니다. 같은 상황판이 DB의 45번 이벤트를 이어받아 마커를 재조회하고 실제 지도 위치를 갱신했습니다. 이후 WEB API로 원래 좌표·내용을 복원했습니다. 해당 시험 종료 시 순번은 46, 마커는 9개였고 변경·복원 작업 2개 모두 전송 완료 상태였습니다. 다른 마커와 기존 순번 없는 전송 이력도 보존됐습니다.

앞선 실패 시도도 남겼습니다. Keycloak을 완전히 중단한 첫 시험은 컨테이너 IP가 바뀌면서 프록시가 404를 반환해 인증 복구를 확인하지 못했습니다. 다음 시험은 SSE 503을 관측했지만 보조 조회 요청이 검사 도구의 15초 제한을 넘었습니다. 최종 시험에서는 보조 요청 대신 실제 SSE 오류 본문과 재연결을 관측해 통과했습니다. 프록시 주소 갱신 결함은 [로컬 이슈 17](17-nginx-stale-container-address.md)로 분리해 수정했고, Jenkins #49 배포 후 실제 IP 변경에서도 자동 복구를 확인했습니다.

이 결과로 본문의 로그인 유지·재연결·지도 갱신 기준을 충족했습니다. 다만 최초 Jenkins #47의 401 원인은 당시 예외를 확보하지 못해 여전히 미확정입니다. 장애 중 모든 요청의 성공이나 부하 처리 한계를 검증한 결과는 아닙니다.
