# 제목

[BE] 마커 권한 조회를 통합했지만 성능 개선 여부 미확인

# 본문

## 문제 배경

수리맵은 마커를 생성하거나 수정·삭제하기 전에 사건이 진행 중인지, 요청한 계정이 해당 사건에 배정돼 있는지 등을 검사합니다. 이 검사에 필요한 정보는 MyBatis Mapper의 SQL로 PostgreSQL에서 조회합니다.

마커 리팩토링 과정에서 권한 검사에 필요한 정보를 최대 5번에 나눠 조회하던 코드를, 서브쿼리 5개를 포함한 SELECT 한 번으로 변경했습니다. 조회 결과는 `MarkerWriteAccessData`에 담고, `MarkerWriteAccessValidator`가 요청을 허용할지 판단합니다. 여기서 조회 횟수는 이 권한 검사에 해당하는 SQL만 센 값이며, 마커 조회·저장 등 요청 전체의 SQL 횟수는 아닙니다.

애플리케이션과 DB 사이의 왕복 횟수는 줄일 수 있지만, 이것만으로 권한 검사나 요청 처리가 빨라졌다고 판단할 수는 없습니다. 요청에 따라 다섯 값 중 일부만 필요하고, 첫 번째 검사에서 거부할 수 있는 경우도 있기 때문입니다. 현재는 두 방식의 처리 시간과 DB 부하를 비교하지 않아, 통합 조회의 이점이 추가 조회 비용보다 큰지 확인하지 못했습니다.

이 이슈는 확인된 지연이나 장애를 해결하는 작업이 아니라, 개별 조회와 통합 조회를 같은 조건에서 비교해 유지할 방식을 결정하는 검증 과제입니다.

### 문제 해결: 체크리스트

- [ ] 서버·DB 환경, 데이터와 요청 조건을 같게 두고 두 방식의 SQL 호출 횟수, 권한 검사 시간, 요청 응답 시간과 DB 부하를 비교했는가?
- [ ] 생성 성공, 수정·삭제 성공과 검사 중간에 거부되는 요청을 나눠 비교하고, 각 경우에 필요하지 않은 조회가 포함되는지 확인했는가?
- [ ] 같은 입력에서 권한 허용·거부 결과와 여러 거부 조건이 겹칠 때 반환하는 오류의 우선순위가 유지되는지 확인했는가?
- [ ] 측정 결과와 코드 복잡도를 함께 검토해 유지할 조회 방식을 결정하고, 선택 이유와 검증하지 못한 범위를 기록했는가?

## 원인 분석과 선택지

### 조회 범위: 요청에 필요한 정보와 실제로 조회하는 정보의 차이

통합 조회가 가져오는 값은 사건 상태, 현재 수색 차수 ID, 계정의 전체 배정 수, 해당 사건의 배정 수와 진행 중인 근무교대 ID입니다. 배정 수는 해제되지 않은 배정만 계산합니다.

기존 개별 조회와 현재 통합 조회를 코드 기준으로 비교하면 다음 차이가 있습니다. 아래 횟수는 실행 측정값이 아니라 검사 흐름과 SQL에서 확인한 값입니다.

- 생성 권한 검사를 모두 통과하면 기존 코드는 다섯 정보를 순서대로 조회했습니다. 통합 조회는 다섯 정보를 한 번에 가져옵니다.
- 수정·삭제의 공통 권한 검사는 사건 상태와 두 배정 수만 사용합니다. 기존 코드는 최대 3번 조회했지만, 통합 조회는 검사에 사용하지 않는 수색 차수와 근무교대까지 가져옵니다.
- 종료된 사건이면 기존 코드는 사건 상태를 조회한 뒤 나머지 조회 없이 거부했습니다. 통합 조회는 다섯 값을 가져온 뒤 Validator에서 거부합니다.

따라서 SELECT 호출을 한 번으로 줄여도 DB 내부의 다섯 조회 작업이 없어지는 것은 아닙니다. 왕복 비용 감소가 유리할 것이라는 가설과, 필요하지 않은 조회 때문에 이점이 줄거나 비용이 늘 수 있다는 가설을 함께 검증해야 합니다.

### 비교 선택지: 필요한 정보만 순차 조회하거나 한 번에 통합 조회

- **개별 조회를 사용합니다.** 요청에 필요한 정보만 조회하고 거부 조건을 만나면 다음 조회를 생략할 수 있습니다. 다만 검사를 모두 통과하는 요청은 애플리케이션과 DB 사이를 여러 번 왕복합니다.
- **통합 조회를 유지합니다.** 다섯 정보를 한 번의 SQL 호출로 가져옵니다. 다만 일부 값만 필요한 요청이나 중간에 거부될 요청도 전체 조회 비용을 부담합니다.

아직 어느 방식을 유지할지는 결정하지 않았습니다. MyBatis와 PostgreSQL의 실제 조회를 비교하며, JPA·QueryDSL 사례의 성능 결과를 이 변경의 근거로 사용하지 않습니다. `MarkerWriteAccessData`를 별도 클래스와 내부 클래스 중 어디에 둘지도 성능과 별개의 구조·가독성 문제이므로 이번 검증 범위에서는 제외합니다.

개별 조회의 비교 기준은 `9eb36d0f` 커밋의 `MarkerAccessMapper`와 `RuntimeMarkerWriteGuardAdapter`입니다. 통합 조회의 비교 대상은 작성 시점의 로컬 변경 코드인 [MarkerAccessMapper.xml](../../../backend/src/main/resources/mapper/marker/MarkerAccessMapper.xml)과 [MarkerWriteAccessValidator.java](../../../backend/src/main/java/com/surimap/domain/marker/MarkerWriteAccessValidator.java)입니다. 측정 결과와 최종 선택 이유는 댓글에 기록합니다.
