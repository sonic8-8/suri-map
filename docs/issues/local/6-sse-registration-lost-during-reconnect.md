[BE] SSE 재접속과 이전 연결 정리가 겹치면 새 연결이 이벤트를 받지 못하는 문제

# 본문

## 문제 배경

상황판은 SSE 연결로 서버의 새 이벤트를 받습니다. 새로고침으로 새 연결을 등록하는 동안 이전 연결의 종료 처리가 겹칠 수 있습니다. 이전 연결을 정리하더라도 새 연결은 목록에 남아 이후 이벤트를 받아야 합니다.

2026-09-27 DB 재전송 연결을 준비하면서, 마지막 기존 연결을 해제하는 작업과 새 연결 등록을 동시에 실행했습니다. 두 작업이 모두 끝난 뒤 이벤트를 보냈지만 새 연결의 수신 횟수는 기대한 1회가 아니라 0회였습니다. 사건·계정 구독에서 모두 재현했습니다.

새 연결이 등록된 것으로 처리돼도 이벤트를 받지 못하면 상황판이 이후 변경을 놓칠 수 있습니다. 다만 최초 검사는 실제 `SseConnectionRegistry`와 스레드 두 개만 사용했습니다. HTTP·DB·브라우저를 연결하지 않았으므로 운영 화면에서 같은 누락을 관측한 결과는 아닙니다.

### 문제 해결: 체크리스트

- [x] 사건·계정 구독의 등록·해제를 동시에 실행해도 새 연결이 다음 이벤트를 받는가?
- [x] 기존 연결 종료·전송 실패 처리와 전체 Backend 회귀 검사가 통과하는가?
- [x] 배포한 서버에서 새로고침·화면 복귀 후 새 이벤트를 받고 상황판을 갱신하는가?
- [ ] 실제 HTTP 연결의 등록·해제 시점을 강제로 겹친 반복 검사에서도 새 연결이 이벤트를 받는가?

## 원인 분석과 선택지

초기 가설은 연결 목록의 조회·추가·삭제가 따로 실행돼 새 등록이 사라진다는 것이었습니다. 등록이 끝나기 전에 이벤트를 보낸 경우와 구분하려고, 두 작업이 모두 끝날 때까지 기다린 뒤 수신 횟수를 세었습니다. 네트워크는 제외해 전송 오류의 영향도 줄였습니다.

같은 구독 대상의 등록·해제를 함께 처리하는 방향을 검토했습니다. 목록 전체를 잠그기보다 기존 동시성 Map의 키별 갱신을 사용하면 서로 다른 구독 대상까지 한 잠금으로 묶지 않아도 됩니다. 이벤트 전송이나 HTTP 연결 종료는 이 갱신 작업에 포함하지 않기로 했습니다.

## 변경 내용과 트레이드오프

- 변경: 같은 구독 대상의 연결 목록을 조회·수정·제거하는 동안 다른 등록·해제가 끼어들지 못하도록 묶었습니다.
- 유지: 이벤트 전송·연결 종료는 목록 갱신 밖에서 수행합니다. 전체 구독을 묶는 전역 잠금은 추가하지 않았습니다.
- 검증 범위: 코드의 동시성 검사와 배포 후 일반 재접속은 통과했습니다. 실제 HTTP 등록·해제를 강제로 겹치는 검사는 남아 있습니다.

### 연결 목록: 조회와 변경을 한 번의 갱신으로 처리

수정 전 [연결 관리 코드](../../../backend/src/main/java/com/surimap/global/sse/ServerSentEventConnectionRegistry.java)는 Map에서 목록을 찾은 뒤 별도 작업으로 새 연결을 넣었습니다. 그사이 마지막 기존 연결이 해제되면서 Map에서 목록이 제거되면, 새 연결은 더 이상 조회되지 않는 목록에 들어갔습니다. 빈 목록인지 확인한 뒤 제거하기 전 새 연결이 추가되는 경우도 있었습니다.

2026-09-27 `compute`·`computeIfPresent`로 같은 구독 대상의 목록 조회·변경을 각각 한 번의 원자적 갱신으로 처리하도록 수정했습니다. 사건·계정 구독 모두 같은 등록 메서드를 사용합니다. 기존 테스트는 등록·해제를 순차 실행했으므로, 실제 스레드로 두 작업을 동시에 수행하는 검사를 추가했습니다.

### 배포 범위: 누적 변경을 Backend·Frontend에 함께 적용

9월 28일 사전 확인에서는 기존 컨테이너가 9월 7일부터 실행 중이었고, 이미지의 정확한 커밋은 알 수 없었습니다. 로컬 `6a256834`와 원격 `develop`의 `8e82edf5` 사이에는 73개 커밋·제품 소스 248개 파일의 차이가 있었습니다. 이번 연결 수정만 배포하는 상황은 아니었습니다.

상황판 응답의 `toast` → `marker_notification` 변경도 포함돼 있어 Backend·Frontend를 함께 배포해야 했습니다. 사용자가 기존 Jenkins 자동 배포를 선택했으며, 미커밋 FCM·관측·배포 설정은 제외했습니다. 사전 확인의 공개 웹·API는 200이었고 DB는 열린 사건 1개·완료 작업 592개·migration 39개였습니다. 당시에는 SSE 순번 컬럼이 없었습니다.
