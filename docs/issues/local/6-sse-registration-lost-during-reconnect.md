# 제목

[BE] SSE 재접속과 이전 연결 정리가 겹치면 새 연결이 이벤트를 받지 못하는 문제

# 본문

## 문제 배경

상황판이 다시 연결되는 동안 이전 연결의 종료 처리가 실행될 수 있습니다. 새 연결 등록이 끝났다면 이후 이벤트는 새 연결로 전달돼야 합니다.

2026-09-27 DB 재전송 연결을 준비하면서, 마지막 기존 연결을 해제하는 작업과 새 연결 등록을 동시에 실행했습니다. 두 작업이 모두 끝난 뒤 이벤트를 보냈지만 새 연결의 수신 횟수는 기대한 1회가 아니라 0회였습니다. 사건·계정 구독에서 모두 재현했습니다.

이 검사는 실제 `SseConnectionRegistry`와 스레드 두 개를 사용합니다. HTTP·DB·브라우저는 연결하지 않았으므로, 운영 상황판에서 같은 누락이 발생했다고 확정한 결과는 아닙니다.

### 문제 해결: 체크리스트

- [x] 같은 조건을 반복해 사건·계정 구독의 새 연결 누락을 재현했는가?
- [x] 기존 연결 해제와 새 등록이 겹쳐도 새 연결이 이벤트를 받는가?
- [x] 전체 Backend 테스트와 기존 종료·실패 처리를 확인했는가?
- [ ] 실제 HTTP 재접속·종료가 겹치는 조건에서도 검증했는가?

## 원인 분석과 선택지

초기 가설은 연결 목록의 조회·추가·삭제가 따로 실행돼 새 등록이 사라진다는 것입니다. 등록 완료 전에 전송한 경우와 전송 처리 자체의 실패도 구분합니다. 테스트는 두 작업의 완료를 기다린 뒤 네트워크 없이 수신 개수만 세도록 작성했습니다.

목록 전체에 별도 전역 잠금을 추가하기보다, 기존 동시성 Map의 키별 갱신으로 등록과 해제를 처리하는 방식을 검토합니다. 이벤트 전송이나 HTTP 연결 종료까지 이 갱신 작업 안에 넣지는 않습니다.

## 수정과 검증

수정 전 [연결 관리 코드](../../../backend/src/main/java/com/surimap/eventhub/stream/SseConnectionRegistry.java)는 Map에서 목록을 찾는 작업과 목록에 연결을 넣는 작업을 분리했습니다. 그 사이 마지막 연결의 해제가 Map에서 목록을 제거하면, 새 연결은 더 이상 조회되지 않는 목록에 추가됩니다. 빈 목록인지 확인한 뒤 Map에서 제거하기 전 새 연결이 추가되는 경합도 가능합니다.

`compute`·`computeIfPresent`로 같은 구독 대상의 목록 조회·수정·제거를 각각 한 번의 원자적 갱신으로 처리하도록 바꿨습니다. 사건·계정 구독은 같은 등록 메서드를 사용합니다. 전송·연결 종료 호출은 갱신 작업 밖에 유지하며, 새 클래스·전역 잠금·설정·의존성은 추가하지 않았습니다.

[재현 테스트](../../../backend/src/test/java/com/surimap/eventhub/stream/SseConnectionRegistryTest.java)의 수정 전 3회 실행에서 사건·계정 구독 모두 수신 0회로 실패했습니다. 최초 실패 회차는 각각 `37/19`, `19/42`, `77/9`였습니다(0부터 센 반복 번호). 처음에는 최대 10,000회, 마지막 재현과 회귀 검사는 최대 1,000회로 줄였습니다. 반복 횟수와 대기 제한 10초는 테스트 실행 제어용이며 운영 부하·지연 기준이 아닙니다.

기존 등록·해제 반복 검사는 두 작업을 순차 실행해 이 경합을 확인하지 못했습니다. 같은 검증 대상에 실제 동시 실행 후 새 연결의 수신 여부를 확인하는 검사를 추가했으며, 내부 자료구조를 Mock으로 바꾸지 않았습니다.

수정 후 연결 관리 테스트 12개와 별도 경합 재실행 2개가 통과했습니다. `cd backend && ./gradlew test --console=plain`도 **222개 클래스·1,296개 모두 통과**했습니다(실패·오류·건너뜀 0, 3분 48초, 기본 성능 태그 제외). 실제 PostgreSQL/PostGIS의 Service·Mapper·Worker 검사도 포함합니다. 변경 Java 2개 파일의 포맷과 공백 검사도 통과했습니다.

실제 HTTP 재접속·DB 재전송 전환·느린 연결과 부하 검증은 남아 있습니다. 9월 27일 검증 당시에는 커밋·GitHub 등록·푸시·배포를 하지 않았습니다.

재현 명령(`backend`에서 실행):

```bash
./gradlew test --tests 'com.surimap.eventhub.stream.SseConnectionRegistryTest.concurrent_registration_and_unregistration_keeps_new_connection' --console=plain
```

## Hetzner 배포 전 확인: 현재 서비스와 검증할 버전이 다름

- 실행 이미지: Backend `sha256:9ee904bb810dd9d856397912f5945fa8ec3a41571533c6291e6d4549b8cb00a8`, Frontend `sha256:6cfda35415bb60cebbe63f1a64b3f989da8fcd8f555dbff403832534c3eb04bd`입니다.
- DB: Flyway migration 39개가 적용돼 있고, 최신 버전은 `20260721.001`입니다. 사건 1개는 `OPEN`, 전송 작업 592개는 모두 `COMPLETED`입니다. `incident.last_sse_sequence`·`event_dispatch_job.sse_sequence`는 아직 없습니다.
- 로컬 `6a256834`는 확인한 원격 `develop`의 `8e82edf5`보다 73개 커밋 앞서 있습니다. 두 커밋 사이 Backend·Frontend 제품 소스 변경은 248개 파일이며, 이번 연결 경합 수정만의 배포가 아닙니다. 이 비교를 실행 이미지와의 정확한 차이로 간주하지 않습니다.
- 상황판 응답 슬롯의 `toast` → `marker_notification` 변경은 Backend·Frontend에 함께 반영돼 있습니다. 현재 소스 전체를 배포하려면 양쪽의 호환성을 맞춰야 합니다. 새 migration과 worker도 포함되지만, 재접속은 아직 메모리 이력을 읽으므로 배포만으로 DB 재전송이 완성되지는 않습니다.
- 서버의 실제 FCM 설정은 `mock`, OpenAI는 비활성입니다. 기존 브라우저 검증 도구는 로컬 주소·시험 사건을 고정하고 마커 생성과 연결 종료를 수행하므로 원격 서버에 그대로 실행하지 않았습니다.

사전 확인 때는 기존 서비스 교체와 별도 DB·앱 검증을 선택지로 제시했습니다. 이후 사용자가 **임시 커밋을 푸시해 기존 Jenkins 자동 배포를 사용하도록 결정**했습니다. 별도 검증 환경은 만들지 않으며, 기존 미커밋 FCM·관측·배포 설정은 이번 SSE 수정 커밋에 섞지 않습니다.

위 사전 확인에서는 원격 파일·DB·컨테이너를 변경하지 않았습니다. HTTP 상태·DB 조회는 정상 동작과 재접속을 브라우저에서 검증한 결과가 아니므로 위 체크리스트는 미완료로 유지합니다.

배포 준비로 기존 백업 스크립트를 실행해 `/srv/apps/suri-map/backups/suri-map-before-load-20260927T183858Z.dump`를 만들고 `pg_restore --list` 검사를 통과했습니다. 실제 복원 시험은 아니며, 푸시·Jenkins 결과·브라우저 검증은 각각 따로 확인합니다.

Frontend의 `npm run typecheck && npm run build`도 통과했고 기존 500 kB 초과 번들 경고는 남았습니다. 앞선 Gradle 작업 프로세스의 통신 오류와 이후 성공을 구분하며, 이번 결과도 Jenkins의 커밋 단위 검증·실제 배포 완료를 대신하지 않습니다.
