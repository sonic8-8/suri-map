# 본문

## 문제 배경

같은 사건을 보는 상황판 중 하나의 통신이 느려져도 다른 상황판에는 변경 알림을 전달해야 합니다. 과거 이력을 다시 보내는 동안뿐 아니라, 재전송을 마친 뒤 새 이벤트를 보내는 상황에도 필요한 동작입니다.

2026-09-28~29 로컬 점검에서, 재전송을 마친 연결의 응답 쓰기를 멈추자 뒤에 등록된 정상 연결도 이벤트를 받지 못했습니다. 느린 연결의 쓰기를 풀면 정상 연결의 전달도 끝났습니다. 기존 검사는 재전송 중의 격리를 확인했지만 이 실시간 전송 조건은 포함하지 않았습니다.

공용 전송 스레드의 대기, 연결 사이의 공유 잠금, 테스트의 등록 오류를 구분해 확인합니다. 실제 운영 장애가 발생했다는 보고나 지연 시간·최대 처리량의 측정 결과는 아닙니다.

- [x] 전송을 분리해도 연결별 순서·중복 처리·DB 이력 이어받기를 유지하는가? — 로컬 회귀 검사 통과

# 댓글

## 재현 결과: 느린 연결을 풀어야 다음 연결에 전달 (2026-09-28~29 진단 당시)

- 조건: 실제 Spring MVC 반환 처리·SSE emitter를 사용하고 Servlet 응답 쓰기만 대역에서 멈췄습니다. 정상 연결은 전달 호출을 기록하는 대역입니다.
- 비교: 쓰기를 멈추지 않은 조건은 통과했습니다. 같은 준비에서 실시간 쓰기만 멈추면 정상 연결의 전달 검사가 실패했습니다. 연결 두 개의 등록을 확인했고, 멈춤을 풀면 뒤 연결에도 전달됐습니다.
- 반복: 최초 단독 검사, 대조 조건 추가, 스택 수집, 진단 출력 제거 후에도 같은 실패를 확인했습니다. 1초는 검사 대기 한도이지 서비스의 허용 지연 기준이 아닙니다.

### 확인한 원인: 같은 스레드에서 연결을 순서대로 전송

[SseConnectionRegistry](../../../backend/src/main/java/com/surimap/eventhub/stream/SseConnectionRegistry.java)는 연결별 `send()`가 돌아와야 다음 연결로 넘어갑니다. [SseEmitterLiveEventSink](../../../backend/src/main/java/com/surimap/eventhub/stream/SseEmitterLiveEventSink.java)는 재전송 중에는 새 이벤트를 대기시키지만, 실시간 단계에서는 호출 스레드가 바로 `emitter.send()`를 실행합니다.

막힌 스택에서도 `dispatchLive → sendToRegisteredSinks → sendNow → SseEmitter.send → Servlet 응답 flush`가 같은 호출 흐름에 있었습니다. 등록 누락이 아니라, 앞 연결의 쓰기를 기다리는 동안 뒤 연결로 진행하지 못하는 문제입니다.

[EventDispatchJobWorker](../../../backend/src/main/java/com/surimap/eventhub/adapter/EventDispatchJobWorker.java)도 단일 스레드에서 이 호출의 완료를 기다립니다. 따라서 뒤 전송 작업에도 영향을 줄 수 있다는 것은 코드에 따른 추론입니다. 여러 사건이 함께 지연되는 운영 시험까지 실행한 것은 아닙니다.

### 남은 작업: 연결별 전송 방식 결정

기존 Spring MVC·DB 이력은 유지하면서 실제 응답 쓰기를 연결별로 분리하는 방향부터 검토합니다. 전송 순서·대기량·종료 처리와 함께 정해야 하므로 worker 스레드 수만 늘리거나 새 라이브러리를 임의로 추가하지 않았습니다. 종료 중인 전송은 [로컬 이슈 14](14-terminal-incident-race-sends-stale-events.md)와 함께 확인합니다.

재현 패치·명령·JUnit 결과는 [검증 기록(로컬 전용)](../../../_workspace/sse-boundary-check-20260928.Y8ZAsQ/RESULTS.md)에 보존했습니다. 실패 재현용 변경은 일반 테스트에서 제거하고 진단 패치로 남겼습니다. 제품 코드 수정·서버 배포·GitHub 등록은 하지 않았으며 체크리스트는 미완료입니다.

## 수정 내용: 실제 응답 쓰기를 연결별로 분리 (2026-09-29)

- 문제: 실시간 이벤트는 공용 worker가 각 연결에 직접 썼습니다. 앞 연결의 쓰기가 끝나지 않으면 뒤 연결로 넘어가지 못했습니다.
- 변경: 실시간 이벤트도 기존 연결별 대기열에 넣고, Servlet 비동기 작업에서 보냅니다. 연결 하나에는 전송 작업 하나만 예약·실행하며, 재전송 뒤 실시간으로 전환할 때도 같은 순서로 처리합니다.
- 보호: 기존 1,000개·직렬화한 UTF-8 1MiB 한도를 실시간에도 적용합니다. 쓰기 중인 데이터도 한도에 포함하고, 초과한 연결만 해제합니다. DB 이력과 마지막 수신 순번부터 이어받는 방식은 유지합니다.

### 검증 결과: 느린 쓰기·대기 한도·종료 처리 회귀 검사

진단 패치의 재현 코드를 정식 테스트에 반영했습니다. 수정 전 5개 중 3개 실패를 다시 확인한 뒤, 수정 후 관련 127개 검사가 모두 통과했습니다. 실제 MVC 응답 처리를 사용하며, 느린 쓰기는 응답 대역의 `flushBuffer()`에서 재현합니다. 계정 구독에서 서로 다른 사건의 같은 순번이 누락되지 않는 조건도 포함합니다.

이번 결과는 실제 느린 네트워크의 처리량 측정이 아닙니다. Servlet 컨테이너의 기존 실행기를 사용하므로 느린 연결이 많으면 실행기 자체가 고갈될 수 있습니다. 연결별 한도도 전체 JVM·소켓 메모리 한도를 뜻하지 않습니다. 새 실행기·라이브러리·운영 한도는 추가하지 않았습니다.

커밋 대상만 추출한 Docker 전체 테스트도 223개 클래스·1,345개가 통과했습니다(5분 14초, 실패·오류·건너뜀 0, 기본 성능 태그 제외). 배포·브라우저 검증 전 결과이며, 명령과 JUnit은 [이번 검증 기록(로컬 전용)](../../../_workspace/sse-live-fix-20260929.UfJY85/RESULTS.md)에 보존합니다. GitHub에는 등록하지 않았습니다.
