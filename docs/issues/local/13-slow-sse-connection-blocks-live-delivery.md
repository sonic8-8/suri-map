### 확인한 원인: 같은 스레드에서 연결을 순서대로 전송

[SseConnectionRegistry](../../../backend/src/main/java/com/surimap/global/sse/ServerSentEventConnectionRegistry.java)는 연결별 `send()`가 돌아와야 다음 연결로 넘어갑니다. [SseEmitterLiveEventSink](https://github.com/sonic8-8/suri-map/blob/c6205dba18c648f668f8331f67305009365957f4/backend/src/main/java/com/surimap/eventhub/stream/SseEmitterLiveEventSink.java)는 재전송 중에는 새 이벤트를 대기시키지만, 실시간 단계에서는 호출 스레드가 바로 `emitter.send()`를 실행합니다.

막힌 스택에서도 `dispatchLive → sendToRegisteredSinks → sendNow → SseEmitter.send → Servlet 응답 flush`가 같은 호출 흐름에 있었습니다. 등록 누락이 아니라, 앞 연결의 쓰기를 기다리는 동안 뒤 연결로 진행하지 못하는 문제입니다.

[EventDispatchJobWorker](../../../backend/src/main/java/com/surimap/global/sse/ServerSentEventJobWorker.java)도 단일 스레드에서 이 호출의 완료를 기다립니다. 따라서 뒤 전송 작업에도 영향을 줄 수 있다는 것은 코드에 따른 추론입니다. 여러 사건이 함께 지연되는 운영 시험까지 실행한 것은 아닙니다.

3. 재전송 중 종료: 이미 쓰기 시작한 첫 프레임은 끝내지만, 같은 페이지의 남은 경로 대신 종료 알림을 보내고 응답을 닫습니다.

토큰 해석·계정 변환·재전송 조회는 대역입니다. 실제 DB 저장·조회는 기존 Service·Mapper 검사로 확인하며, 이 HTTP 검사만으로 Keycloak·사건 접근 권한·운영 복구까지 검증했다고 보지 않습니다. 4개·256KiB·3초는 재현 조건이지 운영 권장값이 아닙니다.

코드 리뷰에서는 종료 알림 뒤에도 재전송 페이지 참조가 남는 점을 보완했습니다. 수신 즉시 참조를 해제하고 초기 조회가 뒤늦게 끝나도 다시 보관하지 않습니다. TCP 검사는 종료 순서·응답 종료를 확인하며 메모리 회수 시점을 측정한 것은 아닙니다. Controller 반환 규칙 검사도 SSE 전용 응답만 허용하도록 보완했습니다. 일반 JSON의 `ResponseEntity` 규칙은 유지합니다.

관련 48개와 최종 Backend 전체 **224개 클래스·1,352개 검사**가 모두 통과했습니다(5분 8초, 실패·오류·건너뜀 0, 기본 성능 태그 제외). 전체 검사는 실제 PostgreSQL/PostGIS를 포함하며 무관한 기존 미커밋 변경도 함께 읽은 작업 트리 결과입니다. 규칙·합의 동작을 나눈 코드 리뷰에서도 수정 후 남은 지적은 없습니다. 실행별 실패·수정·JUnit은 [제품 연결 검증 기록(로컬 전용)](../../../_workspace/sse-nonblocking-impl-20260929.DOocJf/RESULTS.md)에 보존했습니다. 커밋·푸시·배포·브라우저 재검증은 하지 않았으며, 마지막 DB 조회 이후 종료·파기가 커밋되는 [로컬 이슈 14](14-terminal-incident-race-sends-stale-events.md)는 별도로 남아 있습니다.

### 후속 테스트 정리: 반환 타입 선언 대신 HTTP 응답 검증

사용자와 필요성을 재검토해 `ControllerResponseEntityContractTest`를 삭제했습니다. 이름을 바꾼 전수 검사기는 만들지 않았으며 일반 JSON Controller의 `ResponseEntity` 작성 규칙은 유지합니다.

기존 `EventStreamControllerTest`에 정상 구독의 SSE Content-Type 검증을 보완했습니다. 앱 계정의 계정·사건 구독 거부와 재전송 이력 부족 시에는 오류 상태·JSON 형식·본문을 확인하고 스트림을 시작하지 않는지도 검증합니다. 운영 코드는 변경하지 않았습니다.

정리 후 Docker에서 전체 Backend **223개 클래스·1,352개 검사**가 통과했습니다(5분, 실패·오류·건너뜀 0, 기본 성능 태그 제외). Controller 45개와 실제 TCP 3조건을 포함하며, 삭제한 검사는 실행 목록에 없습니다. 원본은 위 검증 기록의 `run.x02oSN`에 보존했습니다. 커밋·푸시·배포는 하지 않았습니다.
