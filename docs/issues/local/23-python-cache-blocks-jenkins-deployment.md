# 제목

Python 캐시의 삭제 권한 오류로 Jenkins 배포 중단

# 본문

## 문제 배경

Jenkins는 테스트가 통과하면 App 서버에 소스를 동기화하고, 이미지를 빌드해 서비스를 배포합니다. 커밋 `b5c93363`의 실행 #66에서는 Backend 테스트가 통과했지만 파일 동기화가 실패했습니다.

동기화 도구인 rsync가 서버에만 남은 `infra/k6/__pycache__/prepare-search-path-batch-fixtures.cpython-312.pyc`를 삭제하다가 `Permission denied (13)` 오류로 종료했습니다. 이후 이미지 빌드와 배포는 실행되지 않아, 수정본의 상황판 반영 시험을 시작하지 못했습니다.

### 문제 해결: 체크리스트

- [x] 같은 커밋 `b5c93363`의 Jenkins 테스트·파일 동기화·배포가 통과하고 실제 서비스에 반영됐는가?

## 원인 분석과 선택지

배포는 `deploy` 계정으로 실행되지만 캐시 디렉터리는 `root:root`, 권한은 `755`였습니다. `deploy`에는 그 안의 파일을 삭제하는 데 필요한 디렉터리 쓰기 권한이 없었습니다.

캐시를 임시 폴더에 복사해 같은 계정으로 rsync를 실행하자 동일한 삭제 오류와 종료 코드 23이 나왔습니다. 복사본의 캐시 디렉터리 소유자만 `deploy`로 바꾸면 종료 코드 0으로 통과했습니다. 이 대조로 소유권과 삭제 권한이 동기화를 막은 직접 원인임을 확인했습니다.

기존 인증 준비 도구는 해당 Python 모듈을 불러옵니다. root로 실행할 때 캐시를 만들었을 가능성은 있지만, 실제 생성 주체와 시점까지 확인하지는 못했습니다.

복구 방법은 캐시 소유권을 바꾸거나 캐시를 배포 소스 밖으로 이동하는 것입니다. 이번에는 제품 데이터가 아닌 캐시만 이동·보존하고 같은 커밋을 재배포합니다. 이후 진단용 Python 실행에는 `-B`를 적용해 캐시 생성을 막습니다. 소스 전체의 권한 변경이나 CI 검사 생략은 필요하지 않습니다.

본문 작성 시점에는 원인 재현까지 완료했으며 캐시 이동과 재배포는 아직 수행하지 않았습니다. 배포가 복구되더라도 경로 표시 지연의 개선 여부는 별도 시험으로 확인해야 합니다.

# 댓글

## 변경 내용과 트레이드오프

문제 캐시를 배포 소스 밖의 별도 보관 폴더로 이동했습니다. 이동 전후 SHA-256 해시가 같아 파일이 그대로 보존됐으며, 제품 데이터와 소스 권한은 변경하지 않았습니다.

이후 인증 준비 도구는 `python3 -B`로 실행합니다. 이 옵션은 Python이 모듈을 불러올 때 바이트코드 캐시를 쓰지 않도록 합니다. 캐시를 활용하는 대신 다시 읽는 비용이 있지만, 이번 일회성 진단에서는 배포 소스에 root 소유 부산물을 남기지 않는 쪽을 택했습니다.

## 검증 결과

같은 커밋 `b5c93363`로 Jenkins #67을 실행했습니다. Backend 테스트가 5분 42초 만에 통과했고, 파일 동기화·이미지 빌드·Backend 상태 확인·Frontend 배포까지 모두 성공했습니다. #66에서 발생했던 캐시 삭제 권한 오류는 재발하지 않았습니다.

새 컨테이너의 실행 상태와 Backend health `UP`을 확인했습니다. 서버의 index.html과 실제 브라우저가 불러온 번들도 `/assets/index-BsRA0pmi.js`로 일치해 서비스 반영을 확인했습니다.

`python3 -B`로 모듈 import를 검증한 뒤 실제 인증 준비 도구도 같은 옵션으로 실행했습니다. 두 경우 모두 소스에 캐시가 다시 생기지 않았습니다. 임시 인증 자원·프로필 복원과 제품 데이터 지문 일치를 확인했고, 시험 준비 후 임시 인증 파일도 제거했습니다.

이번 완료 범위는 배포 복구입니다. 경로 표시 지연의 개선 여부는 별도 GPS 시험으로 확인해야 합니다.
