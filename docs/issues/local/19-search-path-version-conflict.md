# 제목

좌표 추가와 상태 변경이 겹칠 때 수색 경로 버전이 중복되거나 감소하는 문제

# 본문

## 문제 배경

수색 경로에는 GPS 좌표와 기록 상태가 저장됩니다. 업무폰이 좌표를 추가하거나 기록을 일시정지·재개·종료하면, 해당 경로의 변경을 구분하는 숫자인 `version`도 증가해야 합니다.

상황판에서 전체 경로를 반복해서 읽는 비용을 줄이기 위해, 마지막으로 확인한 버전 이후의 변경분만 조회하는 방식을 설계하고 있었습니다. 이 과정에서 좌표 추가와 상태 변경이 같은 경로를 동시에 수정하더라도 버전이 계속 증가하는지 확인할 필요가 생겼습니다. 두 동작이 경로를 읽고 버전을 저장하는 방식이 달랐기 때문입니다.

버전이 중복되거나 이전 값으로 내려가면, 이를 기준으로 새 변경을 판단하는 조회에서 변경분을 놓칠 수 있습니다. 새 변경분 API는 아직 구현하지 않았으며, 실제 상황판의 누락을 관측한 것은 아닙니다. 본문에는 발견 당시의 가설을, 아래 댓글에는 재현·수정·검증 결과를 기록합니다.

### 문제 해결: 체크리스트

아래 항목은 로컬 DB 검증 결과를 기준으로 표시했으며, 배포 완료를 뜻하지 않습니다.

- [x] 같은 경로의 좌표 추가와 상태 변경이 겹쳐도, 저장된 GPS 좌표를 유지하면서 각 변경의 경로 버전이 중복되거나 감소하지 않는가?
- [x] 일시정지·재개·종료가 좌표 추가·구간 보정과 같은 경로의 쓰기 순서를 따르고, 앞선 변경이 반영된 최신 상태를 기준으로 처리 여부를 판단하는가?

## 원인 분석과 선택지

상태 변경 코드는 경로를 조회한 뒤, 읽어 둔 버전에 1을 더해 저장하고 있었습니다. 이 조회에는 행 잠금이 없고, 저장할 때도 그사이 버전이 바뀌었는지 검사하지 않았습니다. 따라서 조회와 저장 사이에 좌표 추가가 완료되면, 상태 변경이 오래된 값으로 버전을 덮어쓸 수 있다는 가설을 세웠습니다.

좌표 저장을 끝낸 뒤 상태를 변경하는 경우와, 상태를 먼저 읽은 뒤 좌표 저장을 끼워 넣는 경우를 실제 DB에서 비교하기로 했습니다. 가설이 확인되면 좌표 추가·구간 보정에서 이미 사용하는 경로 행 잠금을 상태 변경에도 적용하는 방향을 검토했습니다. 행 잠금은 같은 경로를 수정하는 다른 트랜잭션이 끝날 때까지 기다리게 하는 장치입니다.

# 댓글

## 변경 내용과 트레이드오프

- 변경: 일시정지·재개·종료도 기존 경로 행 잠금을 사용하도록 조회 한 곳을 교체했습니다. 좌표 추가·구간 보정과 같은 경로의 쓰기를 순서대로 처리합니다.
- 결과: 버전이 감소하던 회귀 테스트가 수정 후 통과했고, 로컬 Backend 전체 검사도 통과했습니다. 아직 배포하지 않았습니다.
- 트레이드오프: 같은 경로의 요청은 앞선 쓰기가 끝날 때까지 기다릴 수 있습니다. 부하 상황에서의 대기 시간은 아직 측정하지 않았습니다.

### 동시 요청에서 확인한 버전 덮어쓰기

2026-10-03 로컬 PostgreSQL/PostGIS에서 실제 Spring 서비스와 MyBatis를 연결하고, 두 요청의 실행 순서를 제어했습니다. 시작 버전은 1이며, 좌표는 묶음당 2개를 사용했습니다.

1. 일시정지 요청이 버전 1을 읽은 뒤 기다리게 했습니다.
2. 다른 DB 연결에서 좌표 한 묶음을 저장하고 커밋했습니다. 경로 버전은 2가 됐습니다.
3. 일시정지를 이어서 처리했습니다. 이미 읽어 둔 1에 1을 더해 다시 2를 저장했습니다. 두 변경이 완료됐으므로 기대 버전은 3이지만 실제 값은 2였습니다.

일시정지를 기다리게 한 동안 좌표 두 묶음을 각각 저장하면 버전이 3까지 증가했다가 2로 내려갔습니다. 반대로 좌표 한 묶음의 저장을 끝낸 뒤 일시정지를 시작한 대조 조건에서는 정상적으로 3이 됐습니다.

GPS 좌표와 요청 완료 기록, 이벤트는 모두 남아 있었습니다. Mapper 조회와 DB 직접 조회의 버전도 같았습니다. 좌표 저장이 취소되거나 조회 결과만 오래된 것이 아니라, 상태 변경이 이미 증가한 버전을 덮어쓴 것이 원인이었습니다.

### 상태 변경에도 적용한 경로 행 잠금

`AppSearchPathService.patchLoadedPath()`에서 `findPathById()` 대신 기존 `findPathMetadataForUpdate()`를 사용하도록 바꿨습니다. 이 조회는 `FOR UPDATE OF sp`로 해당 경로 행을 잠급니다.

이제 상태 변경은 앞선 좌표 저장이나 구간 보정이 끝나기를 기다린 뒤 최신 버전과 상태를 읽습니다. 잠금은 트랜잭션이 끝날 때까지 유지하므로, 읽은 값으로 변경을 처리하는 사이 다른 쓰기가 끼어들지 못합니다. 버전뿐 아니라 일시정지·재개·종료가 가능한 상태인지도 최신 값으로 판단합니다.

새 잠금 장치나 저장소를 추가하지 않고 기존 조회를 재사용했습니다. SQL·DB 스키마·공개 API·상태 전이 규칙은 변경하지 않았으며, 변경분 조회 API도 이번 수정에 포함하지 않았습니다.

## 검증 결과

### 같은 회귀 테스트의 실패와 통과

잠금이 추가된 코드에서도 검증할 수 있도록, 좌표 두 묶음을 저장한 트랜잭션을 유지한 채 다른 연결에서 일시정지를 시작하는 테스트를 작성했습니다. DB의 실제 잠금 대기를 확인한 뒤 첫 트랜잭션을 커밋했습니다. 수정 전에는 상태를 저장할 때 기다렸고, 수정 후에는 최신 상태를 읽기 전에 기다렸습니다.

- 수정 전: 기대 버전 4와 달리 실제 버전이 2여서 실패했습니다.
- 수정 후: 같은 테스트에서 버전 4, GPS 좌표 4개, 이벤트 버전 1·2·3·4를 확인했습니다.

처음의 진단 실험과는 실행 순서를 제어하는 방법이 다릅니다. 위 전후 비교는 동일한 회귀 테스트로 수행했으며, 첫 번째 체크리스트의 버전 증가와 좌표 보존을 확인했습니다.

### 동시 쓰기와 전체 Backend 검증

기존 `AppSearchPathServiceTest`에 동시 쓰기 11조건을 추가했습니다. 좌표 추가·구간 보정과 상태 변경이 겹치는 경우, 일시정지 후 재개, 종료 후 일시정지 거부, 일시정지·종료 후 대기하던 좌표 저장 거부를 검사했습니다. 성공한 요청의 재시도로 이벤트가 중복되지 않고, 거부한 요청의 좌표·이벤트·처리 예약이 남지 않는지도 확인했습니다. 두 번째 체크리스트의 쓰기 순서와 최신 상태 판단을 이 검사로 확인했습니다.

관련 Service·Mapper 테스트 53개가 통과했습니다. 이어 로컬 Docker에서 `./gradlew --no-daemon test`로 Backend 전체 검사를 실행해 1,377개가 통과했습니다. 실패·오류·건너뜀은 0개이며, 기본 설정상 `performance` 태그는 제외했습니다.

이번 결과는 로컬 DB와 서비스 수준의 검증입니다. 운영 발생 빈도, 실제 HTTP·SSE·브라우저 동작, 부하 영향은 확인하지 않았습니다. 수정 코드는 아직 커밋·푸시·배포하지 않았습니다.
