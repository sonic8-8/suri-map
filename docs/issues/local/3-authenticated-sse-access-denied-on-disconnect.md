## 문제 배경

수리맵 상황판은 로그인한 사용자의 토큰으로 SSE에 연결해 마커 변경을 수신합니다. 화면을 떠나거나 네트워크가 끊기면 서버도 해당 연결을 정리해야 합니다. 이미 인증된 요청을 마무리하는 과정에서 사용자를 인증되지 않은 상태로 판단해서는 안 됩니다.

2026-09-14 로컬 마커 알림 검증 중 서버에 `AuthorizationDeniedException: Access Denied`가 기록됐습니다. SSE 연결은 HTTP 200으로 열렸고 마커 생성도 HTTP 201로 성공했지만, 연결 종료 처리에서는 접근 거부 예외가 발생했습니다. 정상적인 연결 종료에도 인증 오류가 섞이면 실제 권한 문제와 통신 오류를 구분하기 어려워집니다.

### 인증 누락 원인: 최초 요청의 인증 정보가 비동기 종료 처리에서 사라짐

[OidcBearerAuthenticationFilter.java](../../../backend/src/main/java/com/surimap/account/security/OidcBearerAuthenticationFilter.java)는 토큰을 검증한 뒤 인증 객체를 `SecurityContextHolder`에 넣습니다. 그러나 이 객체를 같은 HTTP 요청에서 다시 꺼낼 수 있도록 저장하는 처리는 없습니다.

처음 SSE에 연결할 때는 `SuriMapAuthentication`이 확인됐습니다. 이후 연결 종료를 위해 같은 요청이 `ASYNC`로 다시 처리될 때는 토큰 헤더와 `WEB` 채널이 남아 있었지만, 인증 객체는 `AnonymousAuthenticationToken`으로 바뀌었습니다. `ASYNC`는 브라우저가 새 요청을 보낸다는 뜻이 아니라, Servlet 컨테이너가 기존 요청의 비동기 처리를 다시 진행한다는 뜻입니다.

현재 필터가 상속한 `OncePerRequestFilter`는 기본적으로 이 비동기 재진입에서 실행되지 않습니다. 따라서 토큰으로 인증 객체를 다시 만들지도 않고, 앞서 만든 객체를 저장소에서 복구하지도 못합니다. [SecurityConfig.java](../../../backend/src/main/java/com/surimap/config/SecurityConfig.java)는 `SuriMapAuthentication`이 아니므로 요청을 거부했습니다.

### 수정 후보: 인증 정보를 같은 HTTP 요청의 종료 시점까지 보관

임시 실험에서는 인증 성공 직후 `RequestAttributeSecurityContextRepository.saveContext()`를 호출했습니다. 이 저장소는 인증 정보를 다른 요청이나 DB가 아니라 현재 HTTP 요청의 속성에 보관합니다. 그러자 비동기 종료 처리에서도 기존 인증 객체가 확인됐습니다.

이는 인증 정보를 읽기만 하고 자동 저장하지 않는 `SecurityContextHolderFilter`의 동작과 맞습니다. Spring Security는 명시적 저장이 필요하며, 요청 속성 저장소로 서로 다른 dispatch 사이에서 인증 정보를 유지할 수 있다고 설명합니다. [Spring Security 6.5 공식 문서](https://docs.spring.io/spring-security/reference/6.5/servlet/authentication/persistence.html)

현재 권한 검사를 유지하면서 인증 정보의 수명을 요청 종료까지 맞추는 방식을 수정 후보로 남깁니다. `ASYNC`를 무조건 허용하는 방식은 실제 인증 정보 누락을 해결하지 않으므로 채택하지 않았습니다.

## 검증 결과

격리된 로컬 PostGIS DB, 현재 Backend와 실제 Keycloak 로그인으로 얻은 토큰을 사용했습니다. 증상 재현에는 브라우저 화면 대신 직접 HTTP 연결을 사용해 화면 처리의 영향을 제외했습니다.

| 비교 조건 | 최초 SSE 응답 / 마커 생성 응답 | 비동기 종료의 인증 객체 | 접근 거부 예외 로그 |
|---|---|---|---|
| 현재 코드 + 인증 상태 진단 로그 | 200 / 201 | `AnonymousAuthenticationToken` | 2회 기록 |
| 현재 요청에 인증 정보 보관 추가 | 200 / 201 | `SuriMapAuthentication` | 0회 기록 |

2회는 같은 종료 처리에서 예외가 중복 출력된 횟수이며, 사용자 요청 2건이 거부됐다는 뜻은 아닙니다. 임시 코드를 제거한 뒤에는 기존 구독의 영향을 제외하기 위해 Backend를 다시 시작했고, 같은 재현 명령에서 오류가 다시 발생했습니다.

임시 변경 상태에서도 토큰 없는 상황판 조회는 HTTP 401로 거부됐습니다. 다만 이것만으로 전체 인증·권한 동작이 보존됐다고 판단하지 않으며, 영구 수정 시 추가 검증이 필요합니다.
