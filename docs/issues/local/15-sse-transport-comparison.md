# 제목

[BE] SSE 전송 구조의 복잡성과 대안의 성능 비교 부재

# 본문

## 문제 배경

수리맵은 서버와 상황판 사이에 SSE 연결을 유지하면서 지도와 알림의 변경을 전달합니다. 통신이 느린 상황판이 있더라도 정상인 다른 상황판의 갱신까지 늦어져서는 안 됩니다.

[로컬 이슈 13](13-slow-sse-connection-blocks-live-delivery.md)에서는 느린 연결의 전송을 기다리느라 다른 연결과 일반 HTTP 요청도 대기하는 문제를 재현했습니다. 이를 해결하기 위해 현재 코드는 Servlet의 쓰기 가능 여부를 확인하고, 보낼 수 없으면 작업을 멈췄다가 다시 보낼 수 있을 때 이어가는 방식으로 변경했습니다.

이 과정에서 쓰기·재개·종료 상태를 제품 코드에서 직접 관리하게 됐습니다. 확인하려는 것은 Spring의 `SseEmitter`와 가상 스레드를 활용해 이 코드를 줄이면서도, 기존 전송 동작과 성능을 유지할 수 있는지입니다.

아직 두 방식을 같은 조건에서 비교하지 않아, 직접 관리하는 코드를 유지할지 Spring 기능으로 대체할지 판단할 근거가 부족합니다. 현재 구현이 느리거나 대안이 더 빠르다는 뜻은 아닙니다.

### 문제 해결: 체크리스트

- [ ] 현재 구조의 테스트 조건과 부하 측정 결과를 기록했는가?
- [ ] `SseEmitter + 가상 스레드` 조합을 비교 검증하고 결과와 한계를 기록했는가?

## 원인 분석과 선택지

### 전송 방식: Servlet 직접 제어와 SseEmitter 활용 비교

현재 [ServerSentEventStream](../../../backend/src/main/java/com/surimap/global/sse/ServerSentEventStream.java)은 `DeferredResult<Void>`로 응답의 종료를 관리하고, Servlet의 `isReady()`·`WriteListener`로 전송을 멈추고 재개합니다. 느린 소켓을 기다리는 동안 공용 스레드를 계속 점유하지 않도록 한 대신, 이 상태 전환을 직접 유지보수해야 합니다.

- **현재 Servlet 비차단 구조 유지:** Java 17·Spring MVC를 유지할 수 있고 느린 연결에 대한 로컬 회귀 검증 결과가 있습니다. 다만 직접 작성한 전송 상태 관리 코드는 남습니다.
- **`SseEmitter + 가상 스레드` 비교:** Spring의 전송·완료 기능을 재사용해 직접 관리할 코드를 줄일 수 있는지 확인합니다. 연결마다 전송 순서를 지키는 실행 흐름이 필요하며, 대기량 제한·재접속 복구·종료 처리까지 자동으로 해결되는 것은 아닙니다.

[현재 빌드](../../../backend/build.gradle)와 [배포 이미지](../../../backend/Dockerfile)는 Java 17을 사용하므로 가상 스레드를 비교하려면 JDK 변경도 필요합니다. [기업 사례와 기술 조사](../../research/sse-slow-client-handling-research.md)는 대안을 찾는 근거이며, 수리맵에서 성능이나 유지보수 효과를 검증한 결과는 아닙니다.

### 검증 순서: 현재 구현 측정 후 가상 스레드 방식 비교

먼저 현재 구현을 배포해 연결·복구 동작을 확인하고 부하테스트 결과를 남깁니다. 그다음 `SseEmitter + 가상 스레드` 조합을 비교합니다. 현재 구조의 측정값부터 확보해야 전환으로 얻는 효과와 비용을 구분할 수 있기 때문입니다.

2026-09-30 기준 현재 비차단 구현은 로컬 회귀 검증을 마쳤지만 아직 배포하지 않았습니다. 대안도 구현·측정 전입니다. 부하 조건·비교할 JDK 버전·판정 기준은 시험 전에 정하며, JDK와 전송 구현을 함께 바꾼 결과를 전송 구현만의 효과로 해석하지 않습니다.

이번에 정한 것은 비교 순서입니다. 대안 채택이나 운영 JDK 변경은 확정하지 않았으며, 기존 느린 연결 결함의 수정·검증 기록은 로컬 이슈 13에 유지합니다.
