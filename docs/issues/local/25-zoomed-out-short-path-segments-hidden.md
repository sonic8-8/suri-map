# 제목

[FE] 축소한 상황판 지도에서 짧은 수색 경로 구간이 그려지지 않는 문제

# 본문

## 문제 배경

상황판 지도는 업무폰이 보낸 수색 경로를 구간 단위로 그립니다. 2026-10-08 당시에는 짧은 구간 하나하나를 지도 도형 하나로 그렸습니다. 지도 라이브러리 MapLibre는 GeoJSON 도형을 화면용 타일로 바꿀 때, 축척에 맞춰 선의 꼭짓점을 줄이는 단순화를 적용합니다.

2026-10-08 실서버 상황판(Chrome 147, 화면 1440×900)에서 기존 시험 경로에 새 좌표 6개를 보냈습니다. 서버는 228ms 만에 저장 응답을 보냈고 DB의 값과 순서도 일치했지만, 해당 좌표가 지도에 그려졌는지 확인하는 검사는 실패했습니다. 약 1분씩 두 번 더 재현해도 같았습니다. 세 번째 실행에서는 새 좌표가 지도 라이브러리의 source 데이터에 들어간 것까지 해시로 확인했습니다. 그런데도 화면 범위 안에 있던 해당 경로의 구간 8개가 지도의 도형 조회(`querySourceFeatures()`, `queryRenderedFeatures()`)에서 0개였습니다.

지휘관은 지도를 축소해 넓은 범위를 볼 때, 수색한 길 중 짧은 구간이 빠진 지도를 보게 됩니다. 방금 들어온 새 좌표도 지도에 나타나지 않을 수 있습니다.

### 문제 해결: 체크리스트

- [x] 작은 축척(zoom 약 10.9)에서도 화면 범위 안의 수신 구간이 지도에 그려지는가?
- [x] 새로 저장한 좌표의 구간이 같은 축척에서 지도에 그려지는가?

## 원인 분석과 선택지

### 단순화 기준보다 짧은 선이 타일에서 빠지는 동작

새 좌표는 서버에 저장됐고, 브라우저가 받았으며, 지도 source 데이터에도 들어 있었습니다. 구간도 화면 범위 안에 있었습니다. 따라서 HTTP 응답 누락이나 화면 밖 좌표로는 설명되지 않았고, source 데이터를 화면용 타일로 바꾸는 단계가 남았습니다.

새 좌표를 쓰지 않고 같은 경로의 수신 구간 9개(zoom 약 10.921, 모두 화면 범위 안)로 대조했습니다. 같은 GeoJSON, 같은 지도, 같은 선 레이어 설정으로 임시 source 두 개를 만들고 단순화 기준(`tolerance`)만 바꿨습니다.

| 조건 | 화면용 타일의 도형 수 | 화면에서 조회된 도형 수 |
|---|---:|---:|
| 기본값 `tolerance: 0.375` | 0 | 0 |
| `tolerance: 0` | 36 | 9 |

타일 도형 36개는 타일마다 중복으로 담긴 수이며, 두 source의 입력은 같은 9구간입니다.

경로 source는 단순화 기준을 지정하지 않아, 설치된 MapLibre 5.24.0의 기본값 0.375를 썼습니다. 타일을 만드는 `@maplibre/geojson-vt` 6.1.0은 단순화 기준보다 짧은 선을 타일에 넣지 않습니다. 경로를 짧은 구간마다 도형으로 그리는 방식에서는 이어 보면 긴 경로도 작은 축척에서는 조각마다 기준보다 짧아 통째로 빠질 수 있습니다.

### 경로 source에만 단순화를 끄는 방법 선택

`tolerance: 0`은 원본 GPS를 바꾸지 않지만, 타일에 남는 도형과 좌표가 늘어 지도 처리 비용이 커집니다. 모든 지도 source에 적용하면 이 비용이 경로와 관계없는 도형에도 생기므로, 문제가 난 경로 source에만 적용하기로 했습니다.

비용은 로컬 Chrome에서 합성 구간 56,160개(zoom 약 10.921)로 비교했습니다. 각 3회 중앙값이며 예열 1회는 제외했습니다.

| 설정 | 그려진 구간 | 새 구간 표시 | 첫 처리 | 구간 1개 추가 처리 |
|---|---:|---|---:|---:|
| 기본값 `0.375` | 0 / 56,160 | 실패 | 551ms | 311ms |
| `0` | 56,160 / 56,160 | 통과 | 2,093ms | 2,246ms |

기본값이 빠른 것은 그려야 할 선이 사라졌기 때문이라 성능 이점으로 볼 수 없습니다. 이 비교는 배경 타일 없는 독립 지도의 라이브러리 수준 검사이며, 실제 상황판의 HTTP, React, 실시간 갱신 비용은 포함하지 않습니다.

# 댓글

## 변경 내용과 트레이드오프

`SearchMapCanvas.tsx`가 경로 source를 만들 때만 `tolerance: 0`을 지정하도록 바꿨습니다(32887624). 다른 지도 도형의 단순화 설정과 원본 좌표는 그대로입니다.

대가로 경로 지도 처리 시간이 늘었습니다. 위 합성 비교에서 첫 처리는 2,093ms, 구간 1개 추가 처리는 2,246ms였습니다. 이후 2026-10-20에 같은 표시의 이웃 구간을 선 하나로 이어, 실서버 시험 사건의 도형 수를 57,097개에서 810개로 줄였습니다([로컬 24번](24-board-entry-full-path-map-delay.md)). 이때도 경로 source의 `tolerance: 0`은 유지했습니다.

## 검증 결과

- **회귀 검사:** `SearchMapCanvas.test.ts`가 실제 source 생성 함수의 옵션을 MapLibre와 설치된 타일 변환기에 넘깁니다. 수정 전에는 zoom 10에서 구간 1개가 사라져 실패했고, 수정 후에는 zoom 10, 11, 15에서 구간이 남고 다른 source의 설정도 유지됐습니다. Frontend 321개 테스트, 타입 검사, 빌드가 통과했습니다.
- **배포본 검사:** 첫 배포 시도(Jenkins #61)는 서버의 Python 캐시 권한 문제로 파일 동기화에서 멈췄고, 앱은 기존 버전을 유지했습니다. 캐시만 옮겨 보존하고 같은 커밋으로 다시 실행한 #62가 성공했습니다.
- 배포본의 실제 상황판(Chrome 147, 1440×900, 응답 한도 1/80/480)에서 다음을 확인했습니다.
  - 경로 source에 `tolerance: 0`이 적용됐습니다.
  - zoom 10.921에서 대상 경로의 수신 구간 9개가 모두 화면에서 조회됐습니다. 첫 번째 체크 항목의 근거입니다.
  - 새 좌표 6개가 저장됐고(DB 값과 순서 일치, HTTP 291ms), 그 좌표의 구간이 화면에서 조회됐습니다. 두 번째 체크 항목의 근거입니다.
  - 시험 전 기존 GPS 341,003개와 구간 57,086개의 모든 열 해시가 시험 후에도 같았습니다(추가분 제외).
  - 약 68.7초 관찰 동안 경로 조회 55건에서 HTTP 실패와 JavaScript 오류는 0건이었습니다.

### 확인한 범위의 한계

- 표시 판정은 지도 라이브러리의 화면 도형 조회와 좌표 일치 검사이며, 픽셀 색 전수 검사가 아닙니다.
- 대상 경로의 구간 9개를 확인한 것이며, 전체 구간 57,087개가 모두 그려졌다는 검증은 아닙니다.
- 도형 잇기(2026-10-20) 뒤에 작은 축척의 짧은 구간 표시를 따로 다시 검사하지는 않았습니다.
- 전체 경로 로딩 지연은 이 변경으로 해결하지 않았으며 [로컬 20번](20-slow-paged-search-path-display.md), [로컬 22번](22-repeated-search-path-page-queries.md), [로컬 24번](24-board-entry-full-path-map-delay.md)에서 다룹니다.
