# [Android/BE] 계정 변경 후 오프라인 요청이 다른 사용자의 기록으로 저장될 수 있는 문제

## 문제 배경

수색 경로에서 `accountId`와 `policePhoneId`의 역할을 나누던 중 Android의 오프라인 재전송 코드를 확인했다. 이 과정에서 요청을 만든 사람과 서버가 작성자로 기록하는 사람이 달라질 수 있는 코드를 발견했다.

Android 앱은 네트워크가 끊기면 마커, 수색 경로, 인수인계 메모 같은 현장 기록을 바로 보내지 못한다. 앱은 보내지 못한 요청을 Room DB의 Outbox에 보관한다. Outbox는 서버로 보내지 못한 요청을 임시로 저장하는 공간이다. WorkManager는 네트워크가 복구되면 저장된 요청을 다시 보낸다.

현재 Outbox에는 요청을 만든 사람의 `accountId`가 없다. 요청을 저장한 업무폰의 `policePhoneId`만 남는다. WorkManager도 사건 ID와 업무폰 ID가 같은 요청을 찾아 재전송한다.

하지만 서버로 요청을 보낼 때는 요청을 처음 만든 시점의 계정 정보가 아니라 재전송 시점에 로그인한 계정의 OIDC 토큰을 사용한다. OIDC 토큰은 현재 로그인한 사람이 누구인지 서버에 알려 주는 값이다.

예를 들어 계정 A가 업무폰 P에서 오프라인 요청을 남긴 뒤 계정 B로 바꾸어 로그인할 수 있다. 이때 Outbox에는 업무폰 P만 기록되어 있으므로 WorkManager가 계정 A의 요청을 다시 찾는다. 요청에는 계정 B의 토큰이 붙기 때문에 서버는 계정 B가 보낸 기록으로 처리할 수 있다.

```mermaid
flowchart LR
    A[계정 A가 오프라인 요청 작성] --> B[업무폰 ID만 Outbox에 저장]
    B --> C[계정 A 로그아웃]
    C --> D[같은 업무폰에 계정 B 로그인]
    D --> E[WorkManager가 업무폰 ID로 이전 요청 조회]
    E --> F[계정 B의 토큰으로 서버에 전송]
    F --> G[서버가 계정 B의 기록으로 처리]
```

계정 A와 B가 같은 사건에 배정되어 있다면 서버의 사건 배정 검사도 통과할 수 있다. 수색 경로와 마커에는 계정 B가 작성자로 남고, 인수인계 기록도 실제 작성자와 달라진다. 다음 근무자는 누가 어느 경로를 수색하고 어떤 현장 기록을 남겼는지 정확히 알기 어렵다.

코드에서 확인한 내용은 다음과 같다.

| 확인한 위치 | 확인한 내용 |
|---|---|
| `OutboxEntity` | `policePhoneId`는 저장하지만 `accountId`는 저장하지 않음 |
| `OutboxDao` | 사건 ID와 업무폰 ID로 재전송할 요청을 조회함 |
| `OutboxWorker` | 작업을 실행하는 시점에 현재 OIDC 토큰을 읽음 |
| `HttpOutboxSender` | 현재 OIDC 토큰과 Outbox에 저장된 업무폰 ID를 한 요청에 넣음 |
| 계정 변경 처리 | OIDC 로그인 정보는 지우지만 Outbox 요청과 예약된 WorkManager 작업은 지우거나 취소하지 않음 |

`accountId`는 사람을 구분하고 `policePhoneId`는 업무폰을 구분한다. 네트워크가 복구된 뒤에도 현장 기록의 작성자는 요청을 처음 만든 사람으로 유지되어야 한다. 업무폰 ID만으로 요청을 관리하면 같은 업무폰을 이어서 쓰는 두 사람의 기록이 뒤섞일 수 있다.

## 원인 분석과 선택지

Outbox는 업무폰 ID로 요청을 묶지만 서버는 OIDC 토큰의 계정 ID로 작성자를 판단한다. 요청을 저장할 때 작성자 정보를 남기지 않으므로 재전송 시점의 로그인 계정이 작성자가 된다.

해결 방법은 세 가지 조건을 만족해야 한다. 네트워크가 복구된 뒤에도 요청을 처음 만든 사람이 작성자로 남아야 한다. 서버가 받지 못한 현장 기록을 지워서도 안 된다. 이전 사용자의 미전송 요청 때문에 다음 사용자의 계정 전환이 막혀서도 안 된다. 이 기준으로 세 가지 방법을 검토했다.

### 계정 전환 전에 미전송 요청 모두 보내기

가장 단순한 방법은 계정을 바꾸기 전에 Outbox의 요청을 모두 서버로 보내는 것이다. 미전송 요청이 남아 있으면 로그아웃을 막기 때문에 두 계정의 기록이 섞이지 않는다.

하지만 네트워크 장애나 서버 오류가 발생하면 Outbox에 미전송 요청이 남을 수 있다. 이때 로그아웃을 막으면 다음 근무자가 업무폰을 넘겨받아도 자신의 계정으로 전환하지 못한다. 계정 전환 여부를 이전 사용자의 전송 결과에 맡길 수 없으므로 이 방법은 제외한다.

### 계정마다 별도 Outbox 사용

계정 전환을 허용하면서 기록을 나누려면 계정마다 별도의 Room DB를 둘 수 있다. 각 계정의 요청이 다른 DB에 저장되므로 이전 사용자의 기록이 새 사용자의 Outbox에 섞이지 않는다.

이 방법은 DB 생성과 전환뿐 아니라 마이그레이션과 오래된 계정 데이터 정리까지 따로 관리해야 한다. Outbox 요청마다 작성자를 구분하면 해결할 수 있는 문제에 비해 변경 범위가 크다.

### Outbox 요청마다 작성자 `accountId` 저장

Room DB를 계정마다 나누지 않고 각 Outbox 요청에 작성자를 남기는 방법이다. 현장 기록을 저장할 때 요청을 만든 `accountId`를 함께 보관한다. `policePhoneId`는 Outbox 요청의 작성자나 소유자를 판단하는 기준에서 제외한다.

이렇게 하면 같은 업무폰을 다른 사람이 이어서 사용해도 누가 요청을 만들었는지 알 수 있다. 하지만 `accountId`는 작성자를 적어 둔 값이지, 그 계정이 직접 보낸 요청이라는 증명은 아니다. 서버는 Keycloak이 발급한 OIDC 토큰으로 현재 요청자를 확인한다.

계정 A가 로그아웃한 뒤 계정 B의 토큰으로 A의 요청을 보내면 서버는 B를 작성자로 판단한다. 반대로 서버가 Outbox의 `accountId`만 믿으면 B가 A의 이름으로 요청을 보낼 수 있다. 따라서 작성자를 Outbox에 보존하는 일과 서버가 지연된 요청의 작성자를 확인하는 일은 따로 해결해야 한다.

계정 A에게 다시 로그인하라고 요구하는 방법은 선택하지 않는다. 네트워크가 복구되면 사용자가 조작하지 않아도 기록을 자동으로 보내야 한다는 오프라인 요구사항과 맞지 않기 때문이다. 로그인 상태가 끝난 뒤에도 서버가 해당 요청을 계정 A가 만든 기록으로 확인할 수 있는 정보가 필요하다. 현재 수리맵에는 이런 정보가 없다.

이 확인 방법부터 먼저 만들지는 않는다. 우선 별도로 관찰된 오프라인 현장 기록 자동 전송 지연을 재현하고 해결한다. 같은 계정에서 자동 재전송이 정상적으로 끝나는지 확인한 다음, 계정을 바꾸는 상황을 테스트한다. 그때도 작성자가 달라지는 문제가 재현되면 Keycloak과 서버가 위조 여부를 확인할 수 있는 최소한의 방법을 정한다.

Heartbeat, FCM 토큰, 오프라인 패키지 상태처럼 업무폰 자체를 다루는 기능은 별도 범위다. 이런 단말 전용 기능에는 `policePhoneId`를 유지하되, 일반 현장 기록의 작성자나 Outbox 소유자를 결정하는 데는 사용하지 않는다.
