# [Android] 네트워크 복구 후 오프라인 현장 기록이 지도에 반영되지 않는 문제

## 문제 배경

수리맵 Android 앱은 통신이 끊겨도 수색 경로와 마커가 사라지지 않도록 현장 기록을 Room DB에 먼저 저장한다. 서버로 보내지 못한 요청은 Outbox에 쌓아 두고, 네트워크가 복구되면 WorkManager로 다시 전송한다.

하지만 실기기 테스트에서는 네트워크가 복구된 뒤 30분 이상 지나도 오프라인 현장 기록이 지도에 나타나지 않은 경우가 있었다. 여기서 `30분`은 허용 가능한 반영 시간이 아니라 실제로 기다린 시간이다. 사용자가 다시 전송하거나 로그인하지 않은 상태에서 Outbox 요청 전송과 지도 반영이 끝나지 않았다.

당시에는 단계별 로그를 남기지 못했다. Outbox 요청이 서버로 출발하지 않았는지, 서버 저장 후 변경 알림이나 지도 재조회가 멈췄는지 확인하지 못했다. 현상은 관찰했지만 원인은 아직 확인하지 못했다.

```mermaid
flowchart LR
    A[Room DB에 현장 기록 저장] --> B[Outbox에 전송 요청 저장]
    B --> C[WorkManager 실행]
    C --> D[서버 API 저장]
    D --> E[변경 이벤트 발행]
    E --> F[SSE 수신]
    F --> G[지도 데이터 재조회]
```

이 문제가 남아 있으면 지휘 상황판에서 현장 대원이 기록한 경로와 마커를 확인할 수 없다. 다음 근무자도 이전 수색 기록이 전송을 기다리는 중인지, 실제로 사라졌는지 구분하기 어렵다.

## 원인 분석과 선택지

WorkManager는 실행 시점에 전송할 수 있는 Outbox 요청을 모두 조회한 뒤 순서대로 처리한다. 현재 설정에서는 GPS 좌표를 모으기 시작한 지 10초가 지나거나 120개가 쌓이면 한 묶음으로 저장한다. 묶음 하나가 `POST /api/search-paths/batch` 요청 하나가 된다.

WorkManager가 요청 하나만 보내고 끝나는 것은 아니지만, 쌓인 요청 전체를 HTTP 요청 하나로 합치지도 않는다. 오프라인 시간이 길어지면 GPS 묶음이 여러 Outbox 행으로 쌓이고, WorkManager는 각 행을 서버에 차례로 보낸다.

코드에서 확인한 원인 후보는 다음과 같다.

### Debug 빌드가 네트워크 연결을 기다리지 않음

Release 빌드는 네트워크가 연결되어야 Worker를 실행하지만, Debug 빌드는 이 조건을 사용하지 않는다. Debug 빌드에서는 네트워크가 끊긴 상태에서도 전송을 시도할 수 있다. 요청이 계속 실패하면 WorkManager의 재시도 간격도 점점 길어진다.

실기기 테스트에 사용한 빌드 종류와 Worker 실행 이력을 확인하지 못했으므로, 이 조건이 원인이라고 단정할 수는 없다.

### Outbox와 WorkManager가 서로 다른 시각에 재시도

전송에 실패한 Outbox 행에는 다음 전송 가능 시각인 `nextAttemptAt`이 저장된다. 서버는 `Retry-After` 응답으로 얼마 뒤에 다시 보내야 하는지 알려 줄 수 있다. 이 응답에 따라 `nextAttemptAt`은 10초보다 길어질 수 있다. WorkManager는 이 값과 별도로 계산한 시각에 다시 실행된다.

WorkManager가 `nextAttemptAt`보다 먼저 실행되면 전송할 수 있는 행이 0개가 된다. Worker는 이때 성공으로 종료한다. 이후 작업을 다시 예약하는 코드가 보이지 않아 새 요청이나 사용자 재시도가 없으면 기존 행이 Outbox에 남을 수 있다. 이 경로는 재현 테스트로 확인해야 한다.

### 쌓인 Outbox 요청을 한 건씩 전송

장시간 오프라인 상태에서는 GPS 묶음이 여러 Outbox 행으로 쌓인다. WorkManager는 각 행을 별도의 HTTP 요청으로 보내므로 요청 수가 많을수록 전체 전송 시간이 길어질 수 있다.

아직 쌓인 요청 수와 요청별 응답 시간을 측정하지 않았기 때문에 이 구조를 원인으로 볼 수는 없다. 일괄 전송 API를 먼저 추가하면 어느 요청까지 중복으로 볼지, 실패했을 때 어느 묶음부터 다시 보낼지 새로 정해야 한다. 요청 수가 실제 원인으로 확인되기 전에는 현재 구조를 바꾸지 않는다.

먼저 같은 계정을 유지한 채 Debug와 Release 빌드에서 현상을 재현한다. WorkManager 실행 시각과 Outbox 상태, `nextAttemptAt`, 서버 요청과 응답을 차례로 기록한다. 이어서 서버 변경 알림인 SSE 수신 시각과 지도 재조회 시각도 확인한다.

재시도 예약이 끊긴다면 WorkManager를 다음 전송 가능 시각에 다시 예약하는 최소 변경부터 검토한다. 요청 수가 원인일 때만 GPS 묶음을 합치며, 계정 변경과 작성자 확인은 GitHub Issue #6에서 따로 다룬다.

이번 Issue에서는 네트워크 복구 후 Outbox 요청이 사용자 조작 없이 서버에 저장되고 지도에 나타나는지 확인한다. 몇 초 안에 반영해야 하는지는 GPS 수집·전송 주기와 함께 별도 실험에서 정한다.
