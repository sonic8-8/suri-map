# [BE] 수색 경로를 DB에서 다시 읽을 때 GPS 수집 시각과 정확도가 임의 값으로 바뀌는 문제

> GitHub Issue에 옮기기 위한 초안이다. 구현 전에 확인한 사실과 선택지만 기록했다. 변경 내용과 검증 결과는 작업을 마친 뒤 추가한다.

## 문제 배경

Android 앱은 수색 경로를 기록할 때 GPS 측정값을 서버로 보낸다. 측정값에는 좌표뿐 아니라 좌표를 구분하는 `pointId`, 단말이 좌표를 수집한 시각, 이동 속도, GPS 정확도가 함께 들어 있다.

서버는 신뢰할 수 있는 좌표만 골라 수색 경로에 반영한다. 그러나 현재 DB에는 승인된 GPS 측정값을 그대로 저장하지 않는다. `search_path.geometry`에는 여러 좌표를 선으로 이은 PostGIS `LineString`만 저장한다. 이 값으로는 위도와 경도는 다시 읽을 수 있지만 다음 정보는 복원할 수 없다.

- 앱이 보낸 `pointId`
- 단말이 좌표를 수집한 실제 시각
- 당시 측정된 이동 속도
- 당시 측정된 GPS 정확도

`SearchPathService.pointsFrom(...)`은 DB에서 수색 경로를 읽을 때 사라진 정보를 다음 값으로 채운다.

```text
pointId            = db-point-001, db-point-002, ...
clientTs           = 경로 시작 시각부터 5초씩 더한 시각
speedMps           = 0
horizontalAccuracyM = 0
```

위도와 경도는 DB에 저장된 실제 좌표지만 나머지 값은 앱이 보낸 값이 아니다. 특히 정확도 `0`은 측정값을 알 수 없다는 뜻이 아니라 오차가 거의 없다는 값처럼 읽힐 수 있다.

인수인계 타임라인 API는 수색 경로의 원본 좌표를 실제 수집 시각에 맞춰 재생하는 기능을 제공한다. `docs/api/api-spec.md`에는 각 좌표의 `at`, `lat`, `lng`, `accuracyMeters`를 반환한다고 적혀 있다. 다음 근무자는 이 기록으로 이전 근무자가 언제 어디를 수색했는지 확인한다. 따라서 임의로 만든 시각과 정확도를 원본 측정값처럼 반환하면 수색 순서와 좌표의 신뢰도를 잘못 이해할 수 있다.

현재 코드에서 값이 바뀌는 과정은 확인했다. 배포 서버의 실제 응답과 기존 운영 데이터까지 확인한 것은 아니므로, 작업을 시작할 때 DB를 거친 인수인계 API 테스트로 같은 현상을 재현해야 한다.

```mermaid
flowchart LR
    A[Android 앱의 실제 GPS 측정값] --> B[서버의 좌표 검증]
    B --> C[LineString만 DB에 저장]
    C --> D[DB에서 수색 경로 재조회]
    D --> E[사라진 값을 임의 값으로 채움]
    E --> F[인수인계 타임라인이 원본처럼 반환]
```

## 원인 분석과 선택지

커밋 이력을 확인하면 현재 구조가 만들어진 과정을 다음과 같이 정리할 수 있다.

| 커밋 | 확인한 내용 |
|---|---|
| `90c60a34` | `search_path`와 `search_path_segment` 테이블을 추가했지만 승인된 GPS 측정값을 저장할 테이블은 만들지 않음 |
| `9f5fdee0` | 메모리 저장소를 MyBatis로 바꾸면서 `LineString`을 `SearchPathPoint` 목록으로 복원하는 코드 추가 |
| `1b7bc2c1` | 인수인계 타임라인이 경로의 좌표 목록을 원본 측정값으로 사용하기 시작함 |
| `54ca9bee` | Mapper 중심 리팩토링 과정에서도 기존 복원 코드를 유지함 |

MyBatis 전환 당시에는 DB에서 경로를 다시 읽은 뒤 다음 좌표 묶음을 이어 붙이고, 기존 세그먼트를 유지하는 것이 우선이었다. 관련 테스트도 경로 좌표 수와 세그먼트 유지 여부를 확인했다. `pointId`, 수집 시각, 속도, 정확도가 DB를 거친 뒤에도 같은지는 확인하지 않았다.

인수인계 타임라인 테스트는 실제 DB 대신 원본 값이 들어 있는 수색 경로 객체를 사용했다. 응답에 좌표가 세 개 들어 있는지만 확인했기 때문에 실제 DB 조회 후 시각과 정확도가 바뀌는 문제를 발견하지 못했다.

검토한 선택지는 다음과 같다.

### 승인된 GPS 측정값을 별도로 저장

승인된 GPS 측정값을 `search_path_point`와 같은 별도 테이블에 순서대로 저장한다. `search_path.geometry`는 지도를 빠르게 그리기 위한 `LineString`으로 유지한다.

실제값으로 시간순 재생이 가능하고 DB 재조회 후에도 다음 좌표 묶음을 정확히 이어 붙일 수 있다. 대신 GPS 수집 주기가 5초이므로 저장되는 행이 많아진다. 위치 기록은 민감한 정보이므로 사건 데이터 파기 대상에 새 테이블을 포함하고 보관 기간도 함께 정해야 한다.

### 인수인계 타임라인에서 원본 좌표 제거

원본 GPS 측정값을 저장하지 않고 인수인계 타임라인에는 완성된 `LineString`과 세그먼트 시작·종료 시각만 제공한다.

DB 구조는 단순해지지만 실제 시간에 맞춘 경로 재생과 좌표 정확도 표시는 제공할 수 없다. 수색 기록을 시간순으로 되짚어 보는 기능이 약해지므로 수리맵의 인수인계 목적과 맞지 않는다.

### 현재처럼 임의 값으로 복원

DB 구조를 바꾸지 않아도 되지만 실제값과 추정값을 구분할 수 없다. 인수인계 기록의 신뢰도를 떨어뜨리므로 선택지에서 제외한다.

수리맵은 이전 근무자의 수색 경로와 현장 기록을 시간순으로 전달하는 기능을 유지한다. 따라서 승인된 GPS 측정값을 별도로 저장하는 방향을 우선 검토한다. 구현 전에는 저장할 최소 필드, 한 경로 안에서 좌표 순서를 보장하는 방법, `LineString`과 GPS 측정값을 같은 트랜잭션에서 저장하는 방법, 사건 종료 후 파기 범위를 확정해야 한다.
