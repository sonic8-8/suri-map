# 지도 계측·그래픽 처리 방식 대조

2026-10-10, 같은 경로 4,800구간으로 시험 환경과 제품 계측의 영향을 비교했다. **동일 Windows·Chrome에서 응답 후 대기는 소프트웨어 그래픽 2.49–3.48초, 실제 GPU 0.25–0.33초였다.** 계측을 끄는 것만으로 소프트웨어 그래픽의 지연이 없어지지는 않았다.

전체 57,090구간이 아닌 초기 일부를 비교한 결과다. [지난 전체 로딩 측정](search-path-fixed-page-limit-comparison-20261008.md)의 24분 17초를 실제 GPU의 성능으로 일반화할 수 없으며, 전체 로딩 문제가 해결됐다는 결과도 아니다.

## 무엇을 고정하고 비교했는가

- 배포 커밋 `3022dd0b`, 웹 `index-LhL8h6oC.js`, Backend 이미지 `81b5f33df9ea4f5fc327e1b05e80cc569ee95c37dde97a988792c68a52de800e`를 유지했다.
- 사건 1개·수색 차수 1개·경로 481개·전체 구간 57,090개에서 조회했다. GPS·마커 쓰기, fixture 재생성, 서버 재시작·설정 변경은 하지 않았다.
- 기존 한도인 경로당 1구간·전체 80구간·480좌표를 사용했다. 구간 조회 60회와 변경분 확인 7회에서 같은 4,800구간을 받았다. 61번째 구간 요청은 브라우저에서 전송 전에 대기시켜 비교 범위를 맞췄다. 전체 이력 완료가 아니다.
- 모든 실행은 실제 배포 화면·같은 1440×900·DPR 1·같은 지도 중심과 zoom 10.9213·경로 `tolerance: 0` 조건이다. 서버 응답·bundle·지도 레이어를 대체하지 않았다.
- WSL Headless Chrome 147의 계측 켜짐/꺼짐을 먼저 비교했다. 이어 같은 Windows Chrome 154.0.8037.98에서 Intel Iris Xe와 SwiftShader를 각각 계측 켜짐/꺼짐으로 비교했다. 실제 WebGL renderer 값으로 확인했다.
- 조건마다 새 브라우저·임시 프로필을 사용하고 순서대로 실행했다. 제품 계측을 끈 경우에도 공통 HTTP 관찰은 유지했다. 함수별 타이머·CPU 프로파일러는 넣지 않았다.

첫 구간 HTTP 시작부터 60번째 구간 응답 종료까지 비교한다. ‘HTTP 합계’는 Resource Timing의 요청별 시간이며, ‘응답 후 대기’는 이전 응답 종료부터 다음 요청 시작까지의 간격 합계다. 둘은 겹치지 않지만, HTTP 시간을 DB 실행 시간으로 해석하거나 응답 후 대기를 특정 JavaScript 함수의 CPU 시간으로 해석하지 않는다. 마지막 응답 이후의 지도 표시 확인은 이 시간과 분리했다.

표 순서대로 실행했다. 각 조건 1회이므로 반복 분포·p95·작은 차이의 정확한 원인까지 확인한 결과는 아니다. OS·Chrome 버전·Headless 여부가 다른 WSL과 Windows의 차이를 전부 GPU 효과로 계산하지 않는다. 그래픽 처리 방식의 대조는 같은 Windows·Chrome 안에서 해석한다.

Windows의 후반 33개 요청 간격 평균은 실제 GPU에서 4.48ms·4.07ms, SwiftShader에서 61.03ms·94.82ms였다. WSL SwiftShader에서는 425.33ms·579.56ms였다. 여기서 ‘후반’은 **이번 4,800구간 대조의 후반**이지 전체 57,090구간 로딩의 후반이 아니다.

## 수신과 표시가 일치했는가

6회 모두 아래 검사를 통과했다.

- 경로 조회 응답 67개가 모두 200이며, 관측 중 JavaScript 오류는 없었다.
- 4,800개의 수신 ID가 DB의 대상 구간에 포함되고 실행 간에도 전수 일치했다. 중복 수신도 없었다.
- 수신 ID·지도 source의 ID·MapLibre에서 렌더된 feature의 고유 ID가 전수 일치했다. 계측을 켠 실행은 계측이 기록한 지도 전달 ID도 일치했다.
- 화면 크기·지도 중심·축척·단순화 설정이 같았다. 전체 로딩 전이므로 ‘수색 경로 불러오는 중 · 일부만 표시’ 안내는 남았다.

MapLibre feature 대조는 픽셀 색·팝업에 가려지지 않았는지의 검사와 다르다. 이번에는 새 GPS를 전송하지 않았고, 좌표 값·순서를 신규 전송과 대조하는 시험도 하지 않았다. 계측을 끈 실행의 첫 표시 시각은 수집하지 않았다.

수신 ID 목록의 SHA-256은 모두 `b0c1bb0e15d87e9b6b13a2e248ba473e382134805ca4685eaf95b0304892bc9a`다. 시험 후 DB 전체 대상 ID 57,090개의 정렬 목록 해시도 시험 전 목록과 일치했다.

## 무엇을 확인했고 무엇이 남았는가

1. **시험 브라우저 환경이 지연에 영향을 준다.** 같은 Windows·Chrome에서도 SwiftShader를 실제 GPU로 바꾸면 응답 후 대기가 작아졌다. 이전 WSL의 큰 대기 시간을 실사용 GPU의 제품 성능으로 그대로 해석하지 않는다.
2. **계측 제거만으로 해결된다는 근거는 없다.** 두 소프트웨어 그래픽 환경 모두 계측을 꺼도 대기가 남았다. 실제 GPU의 켜짐/꺼짐 차이도 이번 범위에서는 작았다. 전체 이력에서 계측 비용이 커질 가능성까지 배제한 것은 아니다.
3. **조회·왕복 비용은 남아 있다.** 실제 GPU에서도 HTTP 67회의 시간 합계가 약 64–68초였다. 화면 처리 환경을 바꾸는 것만으로 전체 로딩 문제를 해결하지 못한다. HTTP 차이를 DB 하나의 원인으로 단정하지 않는다.

다음은 실제 GPU에서 전체 이력의 계측 켜짐/꺼짐을 비교하고, 수신·표시 완료와 후반 대기를 확인하는 것이다. 그다음 같은 환경에서 응답 한도를 재비교하고, [앞서 개선 근거를 얻은 GPS 일괄 조회](search-path-four-hypotheses-20261008.md#gps를-이번-페이지-단위로-묶어-조회하면-빨라지는가)를 실제 Mapper·Service에 연결해 검증한다. 시험 한도와 성공 기준을 이번 수치만으로 새로 확정하지 않았다.

## 비교에서 제외한 준비 실행

Aside의 Windows 브라우저에서도 Intel Iris Xe를 확인했지만, 지도 첫 load와 경로 source 생성이 진행되지 않았다. [기존 초기화 대기 기록](search-path-map-initialization-diagnosis-20261008.md)과 같은 조건이라 정상 지도 성능 표에서 제외했다. 임시 fetch 관찰기도 이미 생성된 API 클라이언트의 fetch 참조를 가로채지 못해 폐기했다. 이후 독립 Chrome에서 앱 실행 전 계측 설정과 공통 HTTP 관찰을 적용했다.

## 보존 자료와 종료 상태

비공유 `_workspace/board-measurement-gpu-20261010.QxV8d9/`에 `probe.cjs`, `summarize.cjs`, 조건별 `report.json`·`summary.json`, `comparison.json`, DB 대조 결과와 일부 화면 캡처를 보존했다. 요약기는 요청 종류·개수·수신/표시 ID·화면 조건·순차 요청을 assert로 검사한다. 기존 로그인·DB 확인 도구를 재사용했으며 별도 테스트 프레임워크나 의존성을 추가하지 않았다.

실행한 WSL 명령은 아래와 같다. `on`을 `off`로 바꾸면 제품 계측을 끈다.

```sh
node _workspace/board-measurement-gpu-20261010.QxV8d9/probe.cjs on 60
node _workspace/board-measurement-gpu-20261010.QxV8d9/summarize.cjs
```

Windows에서는 같은 파일의 UNC 경로를 `node.exe`로 실행했다. `--software`를 추가한 실행만 SwiftShader를 강제한다. 재실행 전에는 저장한 DB ID 목록과 현재 DB를 다시 대조하고 유효한 비공개 시험 세션을 준비해야 한다. 이번에 만든 세션 사본은 완료 뒤 제거했으며 원래 로그인 계정 파일은 유지했다.

종료 시 경로 481개·GPS 341,027개·구간 57,090개와 대상 경로 마지막 순번 767이 유지됐다. 이전 시험의 추가 18좌표·3구간을 제외한 원본 전체 컬럼 해시와 대상 외 경로 480개의 해시가 시작 시점과 같았다. 조회 감사 기록까지 포함한 DB 전체 무변경 검사로 해석하지 않는다.

독립 시험 브라우저와 직접 연 Aside 탭은 종료했다. Backend health는 `UP`, 기존 이미지·한도 1/80/480·FCM mock을 확인했다. 제품 코드·SQL·schema·서버 설정을 바꾸지 않아 Backend 전체 테스트와 Frontend 빌드를 재실행하지 않았다. 실제 HTTP·DB·브라우저 대조와 임시 도구 구문/결과 검사를 수행했으며 커밋·푸시·배포는 하지 않았다.
