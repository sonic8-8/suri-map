# 상황판 경로 페이지 조회의 브라우저 처리 비용 진단

2026-10-07 [로컬 20번](../issues/local/20-slow-paged-search-path-display.md)의 후속 진단이다. **조회 루프와 캐시의 객체 참조가 달라 불필요한 재비교가 발생하는 패턴을 재현하고 수정했다. 로컬 테스트·타입 검사·빌드는 통과했지만 배포·전체 지연 해소는 아직 확인하지 않았다.** 아래 진단 측정과 마지막의 수정 후 검증을 구분한다.

## 실제 브라우저에서 확인한 범위

배포된 상황판에 기존 지휘 계정으로 접속했다. 경로 481개·구간 57,083개를 조회하는 같은 사건·차수이고, 서버의 응답당 80구간 설정은 유지했다. 새 탭에서 시작했으며 GPS·마커 쓰기와 본 부하를 실행하지 않았다. 이전 실행과 지도 타일 캐시까지 같다고 보장한 비교는 아니다.

기본 Resource Timing과 긴 작업·긴 프레임 관측을 수집했다. 약 314.6초 시점에 완료된 경로 HTTP 287건을 저장했다. 같은 로딩 중 제품 시험용 계측을 켬 → 끔 → 켬으로 바꿨다.

| 계측 상태·관찰 구간 | 마지막 30건 HTTP 평균 | 해당 30건 사이 29개 간격 평균 |
|---|---:|---:|
| 켬·시작부터 약 146.6초 | 698.9ms | 388.3ms |
| 끔·약 146.6–236.2초 | 751.4ms | 698.6ms |
| 다시 켬·약 236.2–314.6초 | 710.0ms | 894.4ms |

요청 사이 간격은 응답 수신 완료부터 다음 요청 시작까지다. 계측을 꺼도 대기가 남았다. 다만 뒤쪽 구간일수록 받은 데이터가 많으므로 위 표로 계측 비용의 비율이나 효과 없음을 판정하지 않는다.

약 202.4초부터 응답 본문 읽기의 시작·완료 시각도 추가했다. 비교 가능한 72쌍에서 네트워크 수신 완료부터 본문 읽기 완료까지 평균 492.8ms, 본문 읽기 완료부터 다음 요청까지 평균 320.3ms였다. 이 시간에는 작업 실행 대기 등이 포함되며 전부 JSON 파싱·CPU·지도 비용으로 볼 수 없다. 기본 긴 작업 기록만으로도 전체 대기를 설명하지 못했다.

이번 실행의 켜진 계측 구간에서는 경로의 첫 렌더 이벤트를 확보하지 못했다. 지도 배경·마커 표시는 캡처했지만, 표시 범위와 지도 내부 처리를 분리하지 않았으므로 이전의 첫 경로 표시 30.685초를 재현하거나 반박한 결과가 아니다. 전체 이력 완료도 확인하지 않았다.

기록 후 사건 목록으로 이동했다. 경로 요청 수가 321건에서 더 늘지 않음을 두 번 확인하고, 제품 계측을 끄고 임시 `Response.text` 관측을 원복한 뒤 진단 탭을 닫았다. 저장 표본 287건과 종료 확인 321건은 서로 다른 시점이다.

## 기존 함수의 분리 측정

네트워크·React 렌더링·지도 Worker를 제외하고 실제 제품 함수와 설치된 TanStack Query를 호출했다. 가상 입력은 경로 481개, 구간당 좌표 6개다. 실제 서버 좌표를 복사하지 않았다.

### 전체 화면 데이터 재생성 비용

기존 구간에 80구간을 추가한 뒤 화면용 경로 변환·GeoJSON 생성·JSON 직렬화를 측정했다. 준비 실행 2회 후 6개 표본의 정렬된 상위 중앙값이다. 계측한 단계만의 시간이며 실제 지도 반영 시간은 아니다.

| 기존 구간 수 | 화면용 경로 변환 | GeoJSON 생성 | 전체 GeoJSON 직렬화 |
|---|---:|---:|---:|
| 481 | 1.11ms | 0.14ms | 1.05ms |
| 9,620 | 4.87ms | 2.14ms | 17.35ms |
| 28,860 | 18.81ms | 5.63ms | 51.02ms |
| 57,720 | 34.61ms | 10.53ms | 109.89ms |

웹은 페이지 단위로 받지만, [화면 데이터 조립](../../frontend/src/features/situationBoard/presentation/hooks/useSituationBoardData.ts)과 [지도 갱신](../../frontend/src/features/situationBoard/presentation/components/map/SearchMapCanvas.tsx)은 누적 경로 전체를 대상으로 한다. 위 결과는 이 비용이 데이터량과 함께 증가함을 보여주며, 실제 지도 Worker·GPU 비용은 포함하지 않는다.

### 이전 구간을 이어 받을 때의 캐시 재비교

첫 분리 측정은 배열 뒤에 새 구간을 추가했다. 실제 최초 로딩은 최근 구간부터 받고 더 오래된 구간을 배열 앞에 채우므로, 경로를 순환하며 80구간씩 24페이지를 받는 입력으로 보완했다. 마지막 12페이지의 평균을 비교했다.

수정 전 [조회 루프](../../frontend/src/features/path/api/searchPathPagesApi.ts)는 병합 결과를 지역 변수 `state`에 보관하고 `client.setQueryData()`에도 전달했다. TanStack Query는 이전 캐시와 같은 부분을 재사용한 객체를 반환하지만, 루프는 이 반환값을 사용하지 않았다. 배열 앞에 구간을 추가한 뒤에는 지역 상태와 캐시의 객체 참조가 달라질 수 있었다.

다음 페이지에서 바뀐 경로는 80개인데, 분리 재현에서는 나머지 401개 경로도 캐시와 다른 객체로 남았다. 라이브러리는 참조가 같으면 생략할 수 있는 내부 값 비교를 다시 수행했다. 진단용 비교안은 캐시에 저장된 반환값을 다음 조회의 상태로 사용했다. 라이브러리의 비교 기능을 끄거나 데이터·정렬·진행 정보를 바꾼 것이 아니다.

| 시작 구간 수 | 현재 방식의 캐시 갱신 | 캐시 반환값을 사용하는 비교안 |
|---|---:|---:|
| 9,620 | 23.53ms | 4.41ms |
| 28,860 | 67.69ms | 12.09ms |
| 57,720 | 125.35ms | 24.97ms |

변하지 않은 경로의 참조 불일치는 비교안에서 401개 → 0개였다. 두 방식의 최종 데이터·버전·조회 진행 정보가 같은지 검사했다. 실행 시각인 `lastSuccessAt`만 값 대조에서 제외했다. 전체 구간 수 검사도 통과했다. 이 비교는 실제 함수·캐시의 반복 처리 패턴을 재현했지만 React 구독자·HTTP·실제 지도까지 연결한 회귀 테스트는 아니다.

## 결론과 다음 검증

- 불필요한 캐시 재비교는 개선 가능한 비용으로 확인했다. 제품의 단일 페이지 병합만 측정하면 이 반복 패턴을 놓친다.
- 누적 경로의 화면 데이터 재생성과 지도 재전달 비용은 별도로 남는다. 캐시 수정 하나로 최초 표시·전체 로딩 문제가 해결된다고 단정하지 않는다.
- 서버 한도 80구간에서는 구간 조회가 최소 714번 필요하다. 페이지 크기 변경 효과는 아직 비교하지 않았다.
- 진단 뒤 실제 조회 훅의 반복 페이지 테스트와 수정은 아래처럼 완료했다. 다음은 같은 서버·브라우저 조건의 배포 후 비교다. 첫 지도 표시와 전체 이력 완료도 별도로 확인해야 한다.

진단 단계에서는 제품 코드·서버 설정·데이터 구조를 변경하지 않았다. 로컬 진단 도구는 `_workspace/path-pages-diagnosis-20261007.y5LH41/measure-client-stages.cjs`, 결과는 `client-stages.jsonl`, 브라우저 원본은 `browser.json`·`browser.png`에 보존했다. 재실행 명령은 `node _workspace/path-pages-diagnosis-20261007.y5LH41/measure-client-stages.cjs`다. 이 진단 원본은 Git 공유 대상이 아니다.

## 캐시 반환값 재사용 수정과 로컬 검증

`useSearchPathPages()`의 초기 캐시 병합·페이지 수신·오류 상태 저장 3곳에서 `setQueryData<SearchPathPages>()`의 반환값을 지역 상태로 사용하도록 수정했다. 캐시가 재사용한 객체를 다음 페이지에서도 유지해 변경 없는 경로의 재비교를 피한다. 새로운 저장소·설정·추상화는 추가하지 않았다.

기존 [조회 훅 테스트](../../frontend/src/features/path/api/searchPathPagesApi.test.tsx)에 두 경로의 최근 구간 → 빈 변경분 → 첫 경로의 과거 구간 → 둘째 경로의 과거 구간을 받는 조건을 추가했다. HTTP 응답만 대체하고 실제 훅·병합 함수·TanStack Query를 사용한다. 캐시의 공개 `structuralSharing` 설정에서 재비교 조건을 관찰한 뒤 기본 `replaceEqualDeep`을 그대로 실행한다. 라이브러리 내부 함수를 대역으로 바꾸거나 임의의 시간 제한을 통과 기준으로 두지 않았다.

수정 전에는 변경 없는 첫 경로도 다른 객체로 전달돼 `expected true to be false`로 실패했고, 수정 후 통과했다. 구간 내용·정렬·두 경로의 완료 상태·이력/변경분 로딩 완료·오류 없음도 확인했다. 이것은 실제 브라우저 표시 시간을 검증하는 테스트는 아니다.

| 실행 항목 | 결과 |
|---|---|
| 추가한 회귀 테스트 | 수정 전 실패 → 수정 후 통과 |
| 경로 모델·조회 훅·상황판 연결 3개 파일 | 22개 통과 |
| `cd frontend && npm test` | 60개 파일·307개 테스트 통과 |
| `cd frontend && npm run typecheck && npm run build` | 통과, 기존 500kB 초과 번들 경고 유지 |
| 변경 코드 Prettier·`git diff --check` | 통과 |

HTTP 계약·페이지 한도·DB·Backend·Android는 변경하지 않았다. Backend/Android 테스트, 커밋·푸시·배포·배포 후 측정은 실행하지 않았다. 앞선 68ms → 12ms 수치는 분리 측정 결과이며 이번 수정의 실제 화면 개선 수치로 사용하지 않는다.
