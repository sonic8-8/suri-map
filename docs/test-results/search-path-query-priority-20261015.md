# 새 좌표 조회의 대기를 줄이기 위한 순서 변경

## 문제와 변경

기존에는 변경분 한 페이지를 받으면 남은 이력 한 페이지를 조회했다. 그 사이 새 좌표 알림이 와도 이력 응답까지 기다렸다. 한쪽 조회의 성공이 다른 쪽의 미복구 오류와 실패 횟수를 초기화하는 문제도 있었다.

- 최초 이력으로 변경 추적 기준을 확보한 뒤 변경분을 최대 2페이지 연속 조회한다. 남은 이력이 있으면 그다음 차례를 준다.
- 한쪽이 실패하면 기존 재시도 대기를 지킨 뒤 다른 종류의 필요한 조회에도 차례를 준다. 최초 이력을 아직 받지 못했다면 이력부터 재시도한다.
- 이력·변경분의 오류와 연속 실패 횟수를 따로 관리한다. 한쪽 성공만으로 다른 쪽 오류를 지우지 않는다.
- 같은 범위의 진행 중 경로 HTTP는 하나로 유지한다. 알림마다 요청을 쌓거나 현재 요청을 반복 취소하지 않는다.

두 페이지는 사용자와 정한 시험 정책이지 검증된 최적값이 아니다. API·DB·GPS 저장 형식과 Android 동작은 바꾸지 않았다.

## 지연 확인을 위한 짧은 추적

지도 전체 계측을 끈 상태에서도 지정 사건의 SSE 수신·갱신 요청·조회 선택·API 응답·병합 완료를 브라우저 시계와 로컬 요청 ID로 연결한다. 설정이 없거나 만료되면 기록하지 않고, 본문·좌표·토큰은 이벤트에 포함하지 않는다.

API 응답 시각은 JSON을 읽은 직후이므로 순수 네트워크 수신 완료 시각이 아니다. 로컬 요청 ID를 서버에 보내지 않아 서버 처리 비용까지 연결한 기록도 아니다. 제품의 만료 검사는 벽시계를 쓰므로, 실제 60초 관찰 상한과 종료 후 정리는 로컬 시험 실행기가 단조시계로 관리한다.

## 검증과 남은 범위

2026-10-15 커밋 전 `npm run test`, `npm run typecheck`, `npm run build`를 다시 실행했다. 62개 파일·339개 테스트와 타입 검사·빌드가 통과했다. 기존 500kB 초과 청크 경고는 남는다. 테스트의 HTTP·시계는 대역이며 실제 성능값을 측정한 것이 아니다.

조회 순서·경량 추적·로컬 시험 실행기는 각각 Claude 읽기 전용 검수를 거쳐 필수 수정 지적을 해소했다. 테스트 실행 주체는 Codex이며 검수자는 지정 코드·근거를 읽었다. 로컬 실행기는 기존 지도 관찰기·GPS 전송·DB 비교를 재사용하며, 시간 부족 시 미전송·불확실한 응답의 재전송 금지·종료 후 목록 복귀 시도를 검사했다. 시험 스크립트와 상세 실행 기록은 비공유 로컬 자료로 유지한다.

이 기록 작성 시점에는 새 코드의 배포·실제 GPS 시험을 하지 않았다. 다음은 Jenkins 배포본 확인 후 기존 시험 경로에 GPS 6개를 한 번 전송하고 최대 60초 관찰하는 것이다. 시험 좌표는 보존한다. 관찰기의 본문 보존·추가 파싱·지도 source 확인 비용이 포함될 수 있으므로 단일 실행을 성능 개선율이나 현장 성능 충족으로 일반화하지 않는다. 전체 이력 완료·서버 내부 비용·부하 조건 비교도 별도 검증 대상이다.
