# 경로 조회 요청의 본문 크기와 응답 대기 비교

2026-10-14, 일반 Aside 탭에서 **작은 요청도 첫 응답까지 약 610ms가 걸렸다.** 본문을 61바이트에서 55,296바이트로 늘렸을 때 중앙값은 약 652ms였지만, 쌍별 차이는 방향과 크기가 일정하지 않았다. 이번 표본으로는 큰 요청 본문이 지연의 주원인이라고 확인하지 못했다. 본문 크기의 영향이 없다는 결론도 아니다.

## 무엇을 비교했나

같은 사건·수색 차수의 첫 구간 페이지를 조회했다. 큰 본문은 JSON 첫 속성 앞에 공백만 추가했으므로 조회 의미는 같다. 55,296바이트는 앞선 실행의 커넥터 수신량을 참고한 탐색값이며 실제 페이지 요청 한 건의 본문을 복제한 값은 아니다.

- 작은 본문 S: 61바이트. 큰 본문 L: 55,296바이트(54KiB).
- 준비 요청 S/L 2건 후, SL → LS → SL → LS 순서의 4쌍을 비교했다.
- 총 10건을 순차 실행했다. 지도 화면을 열지 않고 사건 목록에서 조회만 했다.
- 전송·버퍼링·파싱 등 크기에 따른 비용을 함께 비교한다. 실제 긴 `paths` 배열의 서버 처리 비용이나 네트워크만의 비용을 분리한 시험은 아니다.

## 얼마나 달랐나

준비 요청을 제외한 각 4건의 중앙값이다. 첫 응답 대기는 Resource Timing의 `responseStart - requestStart`, HTTP 전체는 `duration`이다.

| 구분 | 작은 본문 | 큰 본문 |
|---|---:|---:|
| 첫 응답 대기 중앙값 | 609.9ms | 652.3ms |
| HTTP 전체 중앙값 | 617.4ms | 656.6ms |

각 쌍에서 큰 본문−작은 본문의 첫 응답 대기 차이는 **−222.3 / +49.6 / +297.5 / +101.1ms**였다. 4쌍 중 3쌍은 큰 본문이 느렸으며 차이의 중앙값은 +75.4ms다. 표본이 적고 편차가 커서 효과의 크기나 유무를 확정할 수 없다. 특히 두 집단 중앙값의 차이와 쌍별 차이의 중앙값은 다른 계산이다.

준비 요청까지 포함한 10건의 HTTP 시간 합계는 **7.255초**, 같은 URI의 Spring HTTP 타이머 증가량은 **2.374초**였다. 차이 **4.881초**는 Spring 타이머로 설명되지 않는 구간이다. 이를 모두 네트워크 시간으로 부르지 않는다. Spring 값은 전체 합계뿐이므로 작은/큰 본문별 서버 처리 시간도 비교할 수 없다.

## 검증 결과와 한계

- 브라우저 10건·Resource Timing 10건과 서버 경로 조회 증가 10건이 일치했다. 모두 HTTP 200이고 52,024바이트 응답의 SHA-256이 고정 입력의 이전 응답과 같았다. 다른 경로 조회의 카운터 증가는 없었다.
- 조회 감사는 10건 증가했다. Backend 이미지·시작 시각·환경 해시와 선택 80경로의 경로·구간·GPS 해시는 실행 전후 같았다. 전체 DB 불변이나 전체 이력 수신 정합성 검사는 아니다.
- 실행 중 탭은 visible이었고 중단 조건은 발생하지 않았다. 요청열 전체는 약 7.274초였다. 일반 탭은 닫지 않고 사건 목록에 남겼다.
- 첫 시도 `001`은 결과 회수 전에 실패했지만 실제 경로 요청·감사 증가는 0이었다. 원래 예외 내용은 보존되지 않았다. 후속 사전 검사에서 `token_expiring`을 재현했고, 같은 탭의 기관 SSO 로그인으로 갱신한 뒤 `002`를 실행했다. 실패 자료는 덮어쓰지 않았다.
- 서버 설정·재시작·배포·제품 코드·SQL 변경과 GPS 입력은 없었다. 제품 테스트·빌드는 실행하지 않았다.

## 다음 작업

**첫 개선 후보는 한 응답에 받는 구간 수를 늘려 순차 조회 횟수를 줄이는 것이다. 다음 작업은 추가 통신 계측이 아니라, 이미 시험한 한도의 정합성과 표시 지연을 함께 검증하는 것이다.** 기존 설정으로 시험할 수 있으므로 새 캐시·병렬 요청·API를 먼저 만들 필요는 없다. 아직 영구 설정 변경이나 성능 목표 통과를 승인한 판단은 아니다.

### 이 후보를 먼저 확인하는 이유

| 근거 | 판단에 쓰는 범위 |
|---|---|
| [남은 4구간 비교](search-path-tail-page-limit-comparison-20261008.md): 한도 1→4→1에서 요청 4→1→4회, 중앙값 2.362→0.649→2.573초. 구간·좌표·순서 일치 | 작은 입력에서 요청 묶음 확대의 효과와 원복 대조를 이미 확인했다. 다른 배포본·브라우저의 과거 측정이므로 현재 전체 이력의 개선율로 쓰지 않는다. |
| [일반 탭 비교](search-path-normal-tab-page-limit-comparison-20261014.md): 요청 793→206건, 마지막 응답까지 657.420→184.111초 | 현재 배포본에서도 개선 후보를 지지한다. 재시작·실행 시점 차이가 있고 전체 수신 ID는 미검증이므로 채택 근거로는 부족하다. |
| 같은 요청을 연결한 과거 브라우저·Nginx·Spring 기록: 건별 브라우저−Nginx 차이 346.9~422.0ms, Nginx−Spring 차이 약 2.8~4.0ms | 그 표본의 큰 대기를 호스트 Nginx 내부 처리만으로 설명할 수 없다. 특정 프록시 설정의 결함은 확인하지 못했다. 원인 미확정인 HTTP 전달 경로 변경보다 이미 효과를 관측한 후보의 검증을 먼저 한다. |
| 이번 61바이트 요청도 첫 응답 중앙값 609.9ms | 요청 본문 축소만으로 남은 대기를 해결한다는 가설은 지지하지 않는다. 크기 효과 자체를 배제하지 않는다. |

Frontend의 `searchPathPagesApi.ts`는 응답을 받은 뒤 진행 상태를 갱신하고 다음 요청을 보낸다. Backend의 `SearchPathBoardService.queryPage()`는 경로별·응답별 한도에서 반환량을 제한한다. 즉, 페이지를 줄이면 반복되는 HTTP 대기와 요청마다 실행하는 검사도 덜 반복할 가능성이 있다. [Service·Mapper 관측](search-path-request-cost-20261013.md)의 비용을 다른 HTTP 실행에서 빼거나 개선량으로 합산하지 않는다.

### 다음 검증의 범위와 종료 조건

1. **회귀 검증 준비:** 기존 전체 구간·좌표 대조와 새 GPS 관찰 도구를 일반 Aside 탭·지도 내부 계측 OFF 조건에서 재사용할 수 있는지 확인한다. 종료 후 ID를 추출해 대조하고 측정 중 전체 자료를 반복 복사하지 않는다. 관찰 도구가 결과를 회수하지 못하면 성능을 비교하기 전에 그 부분만 보완한다.
2. **이미 시험한 두 조건 비교:** 경로당 1·80구간·480좌표와 경로당 4·320구간·1,920좌표를 같은 입력·시작 조건으로 비교한다. 경로 수 한도 80, 동시 요청 1개, 경로 순환·초기 로딩 중 변경분 우선 반영을 유지한다. 새 GPS 쓰기로 달라진 원본·버전은 별도 대조하고, 추가 원본을 지워 두 실행을 같게 만들지 않는다. 조건 적용·원복과 실행 상한은 기존 승인·안전 절차를 다시 확인한 뒤 실행한다.
3. **결과에 따라 다음 행동 결정:** 전체 수신 구간·좌표·순서와 신규 GPS가 DB와 일치하고 요청 수·전체 수신 시간이 줄면 이 후보의 검증을 진전시킨다. 첫 표시·새 GPS 지연이 악화하거나 정합성이 실패하면 채택하지 않고 응답 처리·지도 갱신 구간으로 돌아간다. 요청 수만 줄고 전체 시간이 줄지 않으면 같은 실행의 HTTP·응답 후 대기를 분리한다. 추가로 한도를 높이거나 캐시를 자동 도입하지 않는다.

[과거 Headless 비교](search-path-fixed-page-limit-comparison-20261008.md)에서는 확대 한도에서도 전체 수신에 24분 17초가 걸렸고, 새 좌표 표시는 2.931초에서 4.230초로 늦었다. 단일 표본·다른 누적량이지만 무시할 수 없는 반례다. 요청 수 감소만으로 충분하다고 판단하지 않는 이유다. 현재 일반 탭 조건의 반복 비교와 현장 표시 목표 합의는 남아 있으므로 작은 차이를 곧바로 채택/기각하는 통계 기준이나 임의 시간 기준은 만들지 않는다.

**추가 원인 측정의 종료 판단:** 기존 근거로 위 후보의 검증 순서를 정할 수 있으므로, 그 전에 프록시·연결 구간을 다시 잘게 나누는 시험은 추가하지 않는다. HTTP 전달 경로의 정확한 지연 원인은 미해결로 보존한다. 이 선택은 첫 검증 후보의 우선순위이며, 모든 비용 귀속이나 통합 진단의 완료는 아니다.

이번에 Nginx를 새로 계측하지 않았다. 과거 Nginx 시간과 이번 Spring 시간을 빼서 새 구간 시간을 만들지 않는다. 호스트 대조는 로컬 `tasks/host-timing/001/work/join.py`를 다시 실행해 `pass`를 확인했으며 신규 HTTP 요청·서버 변경은 없다.
