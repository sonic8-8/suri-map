# 고정 경로의 지도 갱신 비용 확인

## 무엇을 확인했나

2026-10-14, 실제 시험 DB의 57,090구간을 고정 입력으로 읽어 지도만 재생했다. **격리 지도에서는 좌표·구간 불일치가 재현되지 않았다. 다만 실제 상황판의 수 분 지연 원인이나 첫 제품 수정 대상을 확정한 결과는 아니다.**

기존 작업의 2번인 지도 비용 분리를 수행하고, 3번인 첫 수정 대상 선정에 필요한 근거를 대조했다. HTTP 비용 분해를 다시 실행하지 않았고 제품 코드·배포·서버 설정은 바꾸지 않았다.

## 어떤 조건으로 비교했나

- 시험 사건·차수의 구간과 GPS만 `REPEATABLE READ READ ONLY`로 한 번 읽었다. 57,090개 ID가 이전 전체 시험의 기대 집합과 일치했고, GPS 개수·순번 범위·좌표 배열을 대조했다. 과거 좌표 snapshot과 동일하거나 과거 HTTP 도착 순서를 복원했다는 뜻은 아니다.
- 실제 `syncMovementPathSource`·`boardMeasurement`와 MapLibre 5.24.0을 재사용했다. Windows Chrome 153, Intel Iris Xe, 1440×900, DPR 1이었다. 별도 지도에 경로 레이어 하나만 두고 타일 배경·React·HTTP 조회 루프는 제외했다.
- 전체 좌표가 들어오도록 고정한 카메라는 zoom 13.6189다. 과거 전체 관측은 Chrome 154·zoom 10.9213이므로 시간을 직접 비교하지 않는다. Feature에는 ID·경로 ID·경로 버전·실제 좌표를 담았으며 상황판의 모든 표시 속성을 복제하지 않았다.
- 기초 적재와 추가 입력 사이에 기존 Feature 객체의 참조를 재사용했다. 따라서 제품의 변경 비교는 기존 객체의 동일성 확인에서 끝났고, 기존 Feature 전체를 `JSON.stringify`로 비교하는 경로는 실행하지 않았다. 실제 페이지 갱신에서도 참조가 보존되는지는 이번에 확인하지 않았다. 동기 제출 수치는 이 참조 재사용 조건의 값이며, 전체 재비교 가설을 낮추는 근거로 쓰지 않는다.
- 누적 4,800·28,000·57,010구간에 실제 다음 80구간을 추가했다. 마지막 조건은 가짜 80구간을 만들지 않고 최종 57,090구간에 도달하도록 원래 계획의 기준량을 80개 줄였다. 정렬은 경로 ID·시작 순번 내림차순·구간 ID다.
- 크기마다 계측 OFF/ON을 별도 지도에서 예열 각 1회, 순서를 교대한 5쌍으로 비교했다. 총 36개 사례다. 각 사례 60초·그룹 120초의 진단 상한 안에 끝났다. 이 상한은 서비스 합격 기준이 아니다.
- ON은 제품의 구간 표시 계측을 켰다. 별도 시험 쓰기의 좌표별 픽셀 조회·비동기 해시 검사는 껐다. OFF에도 완료 여부를 확인하는 최소 관찰은 있다.
- 실제 입력 비교 전에 합성 80+8구간의 OFF/ON 실행을 한 번씩 확인했다. 위 36개 사례와 성능 집계에는 포함하지 않았다. 실제 상황판의 첫 표시 시각은 측정하지 않았다.

## 얼마나 걸렸나

예열을 제외한 5회 중앙값, 단위는 ms다. 각 행은 80구간 추가 표본이며, 마지막 열은 처리 비용이 아니라 이 시험 환경에서 idle 신호까지 기다린 경과 시간이다.

| 누적 구간 | 동기 제출 OFF / ON | `updateData` → source content OFF / ON | idle 신호까지 대기 OFF / ON |
|---|---:|---:|---:|
| 4,800 | 1.4 / 2.3 | 8.8 / 10.7 | 937.7 / 973.1 |
| 28,000 | 8.6 / 8.6 | 60.7 / 44.2 | 1,693.2 / 1,791.3 |
| 57,010 | 18.2 / 19.2 | 102.3 / 105.4 | 1,249.3 / 1,321.5 |

동기 제출은 제품 함수에 들어가 반환할 때까지, content는 GeoJSON worker 응답 신호, idle은 지도 작업·렌더 이후의 신호다. 서로 다른 경계라 더해서 총시간을 만들지 않는다. 좌표·ID 전수 검사는 시간 측정 뒤 따로 수행했다. 전체 크기에서 그 사후 검사만 중앙값 OFF 626.4ms·ON 576.9ms였으며 제품 처리 시간에 포함하지 않았다.

참조를 재사용한 조건에서도 누적량에 따라 동기 제출·source 처리 경과 시간은 늘었다. 반면 idle 신호 대기는 별도 관측에서 확인한 약 1초 프레임 주기, 기초 적재의 사후 검사 후 어느 시점에 추가를 시작했는지에 영향을 받는다. 프레임 단위로 뛰는 값을 누적 크기나 ON/OFF의 비용 순위에 사용하지 않는다. 비단조적인 idle 값은 렌더·타일 처리 비용의 증가를 지지하거나 반박하는 근거가 아니다. 계측이 전체 지연의 주원인이라는 결론이나 이 값을 전체 페이지 수에 곱한 개선량도 제시하지 않는다.

## 약 1초 대기는 무엇이었나

위 비교와 분리한 4,800구간의 함수 계측에서 다음을 관찰했다. 각각 OFF/ON 한 번이므로 성능 개선율의 근거는 아니다.

- content 이후 `_render` 진입까지: **826.0 / 931.2ms**.
- 실제 동기 `_render` 실행: **6.2 / 32.6ms**.
- 넓은 관측 구간의 `requestAnimationFrame` 간격: 대부분 **1,000~1,009ms**. OFF 최초 간격은 50ms였고, 증분 구간 자체에는 render가 한 번뿐이었다.
- Aside의 `bringToFront()`를 호출한 별도 OFF/ON 표본에서도 약 1초 간격이 유지됐다. 이것만으로 OS 창의 전경 상태나 브라우저 제한 해제를 증명하지 않는다.

이 표본의 idle 대기 대부분은 render 함수에 들어가기 전이었다. 브라우저의 프레임 실행 지연과 부합하지만 비활성 탭 제한·메인 스레드 점유 등 구체 원인은 미확정이다. 과거 전체 시험에도 같은 제한이 있었다고 소급하지 않는다. 함수 계측의 `queryRenderedFeatures` 합계에는 사후 검사도 섞여 있어 제품 ON 비용으로 합산하지 않는다.

## 표시 불일치는 재현됐나

모든 사례에서 기초 적재와 추가 후 원본 Feature의 ID·좌표가 입력과 일치했다. 타일 조회·렌더 조회의 ID도 일치했고, 추가분은 전체 `setData`가 아닌 `updateData`로 제출됐다. ON의 최신 update ID로 렌더된 추가 구간도 80개였다. source 처리·tile 완료·후속 render/idle을 기다렸으며 오류·최신 입력 미제출 상태는 없었다.

**과거 source 3개·render 6개 불일치는 이번 조건에서 미재현이다.** 이전 누락 ID도 현재 입력에 들어 있지만, 입력 순서·카메라·누적 방식이 다르므로 검사 시점 문제나 제품 수정 완료를 확정하지 않는다. 단일 좌표 구간 57개는 API의 표시 형식처럼 같은 좌표 두 점으로 만들었다. 픽셀 가시성·실제 상황판의 연속 입력 검증도 대신하지 않는다. 불일치 재현에는 이전 카메라의 중심·zoom 10.9213과 누락 6개 ID를 포함한 짧은 입력이 필요하며, 가능하면 페이지별 도착 순서도 확보해야 한다.

원시 `dataabort`를 추가 확인한 결과 모든 사례의 generation 2 idle 이전에는 0건이었다. 마지막 abort는 지도 제거 시에도 발생할 수 있으므로 정상 적용 취소나 M2 가설의 반증으로 취급하지 않는다. 당시 이벤트에 tile 구분 정보는 남기지 않았다.

## 첫 수정은 어디부터 하나

**GPS 일괄 조회나 지도 코드를 바로 바꾸는 결정은 보류한다. 반복 요청 수 감소는 잠정 우선 가설이다.** 지도 없이도 요청당 수백 ms의 대기가 반복된다는 앞선 근거는 있지만, 실제 누적 페이지 처리 비용과 같은 경계에서 대조하지 못했다.

현재 `searchPathPagesApi.ts`의 반복문은 HTTP·본문 읽기 뒤 검증 → 병합 → Query cache 반영 → 다음 요청으로 간다. 지도 idle을 기다리는 `await`는 없다. 따라서 위 idle 시간을 요청 사이 공백의 원인으로 그대로 붙일 수 없다. 지도·React의 동기 작업이 간접으로 다음 요청을 늦출 가능성은 남는다.

요청 사이 공백을 확인할 다음 관측은 하나로 묶는다. **계측 OFF의 실제 조회 반복문에서 중간 누적 상태의 짧은 연속 페이지를 잡고, 같은 시계로 응답 종료 → API 반환 → 검증·병합·캐시 완료 → 다음 요청 시작을 나눈다.** 실제 Feature 참조 재사용 여부와 `syncMovementPathSource` 안에서 쓴 시간, rAF 간격도 이 구간과 연결해 기록한다. 결과에 따라 기존 계획의 80→320 시험 한도 대조 또는 병합·캐시 처리 개선을 먼저 검증한다. 운영 한도 변경을 채택한 것은 아니다.

별도로 남은 시험 브라우저의 네트워크 제한·프록시·VPN 여부와 본문 수신 지연 확인도 유지한다. 위 관측 하나로 모든 미귀속을 해소한다고 가정하지 않는다.

## 검증과 남은 범위

- 실제 입력의 독립 집계, 3개 그룹의 원문 재계산, source·좌표·구간·최신 update ID 검사, 기존 완료 판정의 대기·오류·불일치 self-check를 실행했다.
- 첫 실행은 일회성 Aside 세션이 닫히며 탭이 사라져 측정 전에 실패했다. 원문을 보존하고 공식 MCP의 지속 세션으로 바꿔 실행했다. 서버 설정을 우회 변경하지 않았다.
- 이번 범위는 **2번의 격리 지도 대조와 3번의 변경 후보 판단**이다. 첫 제품 수정 확정, 전체 상황판 관찰기 검증, 실제 사용자 지연 해결은 미완료다. 새 SLA도 정하지 않았다.
- 누적 크기별 렌더·타일 처리 비용은 분리하지 못했다. 함수별 프레임 관측은 4,800구간의 단일 OFF/ON 표본에 한정되며, 28,000·57,010구간의 처리 비용을 대신하지 않는다.
- 제품 변경이 없어 Backend·Frontend 빌드/전체 테스트는 다시 실행하지 않았다. 원시 좌표·실행 도구·측정값은 로컬 진단 자료로 보존하고 공개 문서에는 좌표를 싣지 않았다.
