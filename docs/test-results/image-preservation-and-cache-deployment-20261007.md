# 기존 이미지 보존 문제와 캐시 수정 배포 검증

2026-10-07 [로컬 21번](../issues/local/21-missing-running-container-images.md)의 후속 기록이다. 이미지 보존 실패를 분리 재현하고 복구 이미지를 확보했다. `77dfc911`의 Jenkins #59는 두 승인 후 웹까지 배포해 SUCCESS로 끝났다. 브라우저 비교는 아래 후속 결과로 구분한다.

## 이미지 보존 실패의 재현

App 서버의 Docker 29.6.1·containerd image store에서 별도 시험 이미지와 네트워크 없는 컨테이너로 확인했다. 기존 이미지를 조회할 수 있는 상태에서 같은 태그로 다른 이미지를 빌드하자 이전 ID 조회가 `No such image`로 실패했다. 기존 컨테이너는 계속 실행 중이었다. 반대로 빌드 전에 보존용 태그를 붙이면 다음 빌드 뒤에도 기존 ID와 보존 태그가 같은 이미지를 가리켰다. 시험 컨테이너 2개는 제거했다.

이 재현은 실제 배포와 같은 태그 덮어쓰기 패턴이 문제를 일으킬 수 있음을 확인한 것이다. 과거 이미지 제거의 모든 내부 이벤트를 복원한 결과는 아니다. [Moby의 관련 이슈](https://github.com/moby/moby/issues/48907)에도 containerd 환경에서 빌드·불러오기가 기존 태그를 대체할 때 이전 이미지 참조가 보존되지 않는 사례가 있다.

## 복구 이미지 확보

원본 이미지 ID와 manifest ID 조회가 실패했고, 실행 컨테이너의 `docker commit`도 원본 manifest가 없어 실패했다. 이전 배포 커밋 `b6467c27`을 별도 디렉터리에 내보내 `recovered-b6467c27` 태그로 재빌드했다. 서비스 실행 이미지나 #59의 `develop` 태그를 덮어쓰지 않았다.

- Backend·Frontend·mock-112의 고정 파일별 SHA-256이 실행 컨테이너와 일치했다. `/tmp`, `/run`, Nginx 임시 파일, Docker가 주입한 hosts·hostname·resolv.conf, 런타임 Nginx 설정과 JAR은 이 비교에서 제외했다.
- Backend JAR 전체 해시는 달랐지만 내부 1,437개 항목의 이름·내용은 모두 같았다. mock-112의 264개 항목도 일치했다. JAR을 파일 해시 검사에서 제외한 대신 내부 내용을 별도로 검사했다.
- 실행 명령·작업 디렉터리·기본 사용자·공개 포트 설정이 일치했다. 사용자 필드의 빈 문자열과 미지정 값은 기본 사용자로 정규화했다.
- 기존 환경·Compose·컨테이너 설정과 런타임 Nginx 설정을 비공개 파일로 보존했다. 복구 이미지 3개는 별도 태그와 `docker save` 아카이브로 보관했다.

원래 이미지 ID 자체를 복원한 것은 아니다. 실행 중 변경되는 임시 파일까지 동일한 스냅샷이라고 주장하지 않으며, 기존 버전의 실행 파일 내용과 기동 설정을 확인한 복구 이미지다. 실제 서비스 롤백 실행은 하지 않았다.

## 재발 방지 변경

[파이프라인](../../infra/ci/hetzner.Jenkinsfile)의 Build Images 시작 부분에서 현재 앱 3개의 이미지 ID를 확인하고 `before-build-<UTC 시각>` 태그로 보존한 뒤 빌드하도록 변경했다. 조회·태그 생성 실패 시 빌드를 시작하지 않는다. 서비스 중단·DB 백업·두 승인 단계는 유지했다.

Groovy 구문 검사, shell 6개 문법 검사, 보존 후 빌드 순서 검사, 위 실제 Docker 비교 재현을 통과했다. Jenkins inline 설정에 저장하고 로컬 파일과 끝 개행을 제외한 내용 일치를 확인했다. 스크립트 외 작업 설정도 동일하다. 배포 후 Jenkinsfile에서 실제 보존 블록을 추출해 App에서 실행했고 앱 3개에 `before-build-20261006T213311Z` 태그가 생성됐다. 이미 실행 중이던 #59는 이전 스크립트이며, 새 사전 보존 절차를 포함한 전체 CI 실행은 아직 하지 않았다.
