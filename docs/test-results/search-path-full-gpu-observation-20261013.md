# 실제 GPU의 전체 경로 로딩 관측

2026-10-13, 실제 GPU에서도 전체 57,090구간을 받는 데 **14분 48초**가 걸렸다. 첫 경로 표시는 약 1.8초였지만, 전체 수색 이력을 준비하는 지연은 남았다. 제품 코드나 서버 설정을 바꾼 결과가 아니다.

**계측 켜짐/꺼짐 비교는 미완료다.** 계측을 켠 실행은 전체 수신 뒤 지도 내부 구간 ID 검사에서 불일치가 발생했다. 끈 실행은 브라우저가 숨김 상태로 전환돼 중단됐다. 두 실행을 정상 완료한 성능 비교로 사용하지 않는다.

## 비교 조건

- [초기 4,800구간 대조](search-path-gpu-measurement-comparison-20261010.md)를 전체 이력으로 확장했다. 사건 1개·수색 차수 1개·경로 481개·GPS 341,027개·구간 57,090개이며 새 좌표를 전송하지 않았다.
- 배포 커밋 `3022dd0b`, 웹 `index-LhL8h6oC.js`, Backend 이미지 `81b5f33df9ea4f5fc327e1b05e80cc569ee95c37dde97a988792c68a52de800e`를 유지했다.
- 응답 한도는 경로당 1구간·전체 80구간·480좌표, FCM은 mock이다. 재배포·재시작·fixture 재생성·서버 설정 변경은 하지 않았다.
- 독립 Windows Chrome `154.0.8037.98`, Intel Iris Xe / Direct3D11, 1440×900·DPR 1을 사용했다. 매 실행 새 임시 프로필이며 실제 배포 화면의 상황판을 열었다. Aside·소프트웨어 그래픽·응답 대체를 사용하지 않았다.
- 제품 계측만 켜고 끄며 공통 HTTP 관찰은 유지했다. 함수별 진단 타이머는 넣지 않았다. 전체 조회의 관측 상한은 기존 25분을 유지했으며 성공 목표 시간은 아니다.

HTTP 793건은 모두 200이며 관측한 `pageerror`는 없었다. 동시 경로 요청은 최대 1개였다. 수신 ID는 DB의 대상 구간과 전수 일치했고 중복 수신은 없었다. 구간 조회 중 61개 응답은 한 구간만 담았다.

HTTP에는 네트워크·프록시·서버 처리가 포함된다. 이를 DB 실행 시간으로 해석하지 않는다. 요청 사이 간격도 특정 JavaScript 함수의 CPU 시간으로 단정하지 않는다.

792개 요청 간격을 시간 순서대로 198개씩 나눈 평균은 **46.5 → 233.0 → 502.1 → 613.4ms**였다. 실제 GPU에서도 이 실행의 후반 대기가 커졌다. 다만 계측을 끈 전체 실행이 끝나지 않아 계측 비용과 제품 처리 비용을 분리한 결론은 아니다.

### 전체 수신과 지도 표시를 구분한다

상황판 진입부터 889.323초에 로딩 안내가 사라진 것을 관찰했다. 3초 간격 확인값이므로 정확한 마지막 렌더 시각은 아니다. 그 뒤 1.5초를 더 기다려 지도 source와 렌더된 feature를 읽었다.

- 제품의 지도 전달 계측은 57,090개 ID를 기록했다.
- 지도 source에는 3개가 적었고, 렌더된 고유 ID에는 추가로 3개가 적었다.
- 지도는 기존 중심·zoom 10.9213·`tolerance: 0`이었다. 검사 실패 뒤 시험 브라우저를 종료했다.

따라서 **전체 수신은 확인했지만 전체 지도 표시는 확인하지 못했다.** 검사 시점에 지도 처리가 진행 중이었는지, 처리가 끝나도 불일치가 남는지 아직 구분하지 못했다. 렌더된 feature 수는 픽셀 색·가림 여부의 검사도 아니다.

후속 관찰기에 수신 완료 후 최대 60초 동안 source·렌더 ID를 재확인하는 절차를 추가했다. 진단을 위한 관찰 상한이지 허용 지연 기준이 아니다. 다음 실행은 숨김 전환으로 그 단계에 도달하지 못했으므로, 추가 절차로 불일치가 해소됐다고 보고하지 않는다.

## 계측을 끈 실행: 중단

마지막 정상 진행 기록은 518.033초·HTTP 응답 712개·수신 56,400구간이다. 이후 `document.visibilityState`가 `hidden`으로 바뀌어 가시성 검사에서 중단했다. 최소화·탭 전환·화면 잠금 중 실제 원인은 확인하지 못했다.

이 실행은 전체 수신·지도 표시 검사를 완료하지 못했으며, 정상 GPU 성능 비교값에서 제외한다. 중단 전 진행 기록과 실패 메시지는 보존했지만 최초 관찰기의 조기 종료 때문에 최종 HTTP 상세와 구간 ID 목록은 남지 않았다. 관찰기는 이후 숨김 전환 시에도 부분 결과를 저장하도록 수정했고 구문 검사만 통과했다. 이 보완의 실제 중단 동작은 아직 재검증하지 않았다.

## 종료 점검과 다음 검증

시작·두 실행 사이·종료 시점의 `search_path`, `search_path_gps_point`, `search_path_segment` 전체 행 수와 전체 컬럼 기반 해시가 같았다. 대상 구간 ID 목록도 일치했다. 조회 감사 로그를 포함한 DB 전체 무변경 검사라는 뜻은 아니다.

Backend health `UP`, 같은 이미지·환경변수 해시·한도 1/80/480·FCM mock을 확인했다. 독립 시험 Chrome은 종료됐고, 이번에 만든 로그인 세션 사본은 삭제했다. 원래 계정 파일은 유지했다. 제품 변경이 없어 Backend 테스트·Frontend 빌드는 재실행하지 않았다. 임시 관찰기 구문 검사와 실제 HTTP·DB·브라우저 관찰만 수행했으며 커밋·푸시하지 않았다.

## 진단 계획 검수로 바꾼 다음 순서

독립 verifier 검수에서 GPS 일괄 조회를 먼저 구현할 근거가 부족하다는 지적을 수용했다. 기존 JDBC 차이를 전체 페이지에 단순 적용한 절감 규모는 약 21–23초다. 실제 Mapper에서 같은 효과가 난다는 가정의 계산이며 보장값이나 엄밀한 상한은 아니다. 이것만으로 888초 지연을 해결한다고 판단하지 않는다.

1. 초반·후반·꼬리·빈 페이지의 요청 비용을 분해한다. GPS뿐 아니라 경로별 구간 조회, 준비 상태 검사, 기타 Mapper 호출과 서버 밖 미귀속 시간을 구분한다.
2. 고정된 지도 입력으로 계측 비용과 제품의 지도 갱신 비용을 나눈다. 최신 입력 처리 중의 일시적 차이와 처리가 안정된 뒤의 구간 불일치를 구분한다.
3. 확인된 기여도로 첫 수정 대상을 고르고 짧은 전후 대조로 검증한다. 전체 시험은 관찰기와 비교 조건을 검증한 다음 실행한다.

보존된 원문 배열을 사후 대조한 결과, 수신 ID뿐 아니라 지도에 전달한 ID도 기대 목록 57,090개와 전수 일치했다. 원래 실행은 지도 source 단언에서 실패해 전달 ID 단언에 도달하지 못했으므로, 이번 사후 검사로 보충한 결과다. 원래 실행을 통과로 바꾸지 않는다. 지도 source의 부족 ID 3개와 렌더 부족 ID 6개도 따로 보존했으며, 검사 시점 문제인지 실제 표시 문제인지는 여전히 미확인이다.

이 추가 작업은 분석 계획 검수와 보존 결과 대조다. 제품 코드 수정, 새 부하테스트, 성능 개선 완료가 아니다.

켜짐 실행 `on-1791857257014`의 전체 `report.json`, 수신 ID, 응답 개수, 스크린샷, 실패 메시지와 꺼짐 실행 `off-1791858234561`의 브라우저 정보, 마지막 진행 상태, 실패 메시지는 당시 로컬에 보존했다. 당시 최종 측정 스크립트에는 실행 도중 확인한 검사 시점과 중단 기록 보완을 반영했다.
