# 경로 조회 요청의 Service·Mapper 비용

2026-10-13, Hetzner 앱 서버에서 **새 변경분이 없는 요청도 Service 처리에 약 122–131ms가 걸렸다.** 80구간 요청의 반복 조회뿐 아니라 매 요청의 준비 상태 검사 비용이 확인됐다. 제품 코드·SQL을 바꾸거나 전체 로딩 지연을 해결한 결과는 아니다.

## 무엇을 측정했는가

- 실행 중인 Backend의 `/app/app.jar`에 담긴 `SearchPathBoardService`와 실제 Mapper·SQL을 같은 컨테이너의 별도 Java 프로세스에서 호출했다. Spring 애플리케이션 전체를 새로 시작하거나 기존 서버를 재시작하지 않았다.
- 이미지 `81b5f33d…52de800e`, JAR SHA-256 `23d054bbbc3a66b4b0d1237d6768468d17e7b9730e647e7219a7ac6ac52ec713`. Java 17, 힙 상한 256MiB, 기존 DB·MyBatis 객체 생성 설정·fetch size 100을 사용했다.
- 경로당 1구간·전체 80경로/80구간/480좌표·최대 알려진 경로 1,000개를 유지했다. 데이터는 경로 481개·GPS 341,027개·구간 57,090개다.
- MyBatis 세션별 읽기 전용 `REPEATABLE READ`를 직접 설정했다. Service를 직접 호출하므로 Spring의 트랜잭션 프록시는 실행하지 않았다. DB 기본 읽기 전용 설정으로 쓰기도 차단했다. SQL 제한 15초·lock 제한 2초는 진단 프로세스에만 적용했다.
- 각 표본은 예열 1회 후 5회 측정했다. 정순 실행 뒤 새 JVM에서 역순 실행을 추가해 순서 영향을 확인했다. 합계 예열 8회·측정 40회이며 표본별 반복 묶음은 60초 상한 안에 끝났다. 공식 벤치마크 권장 횟수나 서비스 합격 기준은 아니다.

## 입력을 어떻게 고정했는가

| 표본 | 입력과 기대 결과 |
|---|---|
| 초반 | 진행 정보 없이 처음 조회한다. 80구간·443좌표 |
| 후반 | DB에서 읽은 순번으로 경로마다 오래된 구간 3개가 남은 진행 상태를 구성한다. 80구간·452좌표 |
| 꼬리 | 경로 1개에 구간 1개만 남기고 나머지 경로의 진행을 완료 상태로 구성한다. 1구간·4좌표 |
| 빈 변경분 | 모든 경로의 현재 버전까지 이미 반영한 진행 상태다. 0구간·0좌표 |

후반·꼬리 입력은 현재 DB로 만든 유효한 진행 상태이며, 과거 브라우저 요청을 그대로 재생한 것이 아니다. 지휘 계정·실종팀의 WEB 인증 컨텍스트를 시험에서 직접 제공했다. Service 내부 접근 검사는 실제 Mapper로 실행했지만 로그인·토큰·HTTP 접근 검사의 재현은 아니다.

각 응답의 구간 ID·순서는 별도 DB 조회로 만든 기대 목록과 대조했고, 좌표 개수는 구간의 시작·끝 순번과 대조했다. 응답 전체의 값·순서 해시는 반복과 두 실행 사이에 같았다. GPS 필드 전체를 별도 SQL 결과와 전수 대조한 검사는 아니다.

## 무엇을 알게 됐는가

1. **GPS만 묶어도 경로별 구간 조회 80회와 준비 상태 검사는 남는다.** GPS 단독 개선을 전체 해결책으로 확정할 수 없다.
2. **응답할 좌표가 없어도 고정 검사 비용이 발생한다.** 빈 변경분에서는 구간·GPS 조회를 하지 않지만 준비 상태 검사가 실행된다. 검사 생략이나 캐시 도입을 바로 승인한 것은 아니다.
3. **Service 안에서는 Mapper 경계의 비용이 크다.** 하지만 처음 80구간의 시간은 순서 대조에서 크게 변했다. JVM 예열·캐시·서버 변동 중 원인을 특정하지 않았으며 SQL 종류 간 정확한 우선순위를 한 번의 측정으로 정하지 않는다.

## 미측정 범위와 다음 작업

이 프로세스는 HTTP 요청을 받지 않는다. 커넥션 획득·트랜잭션 준비/종료, Spring 필터·인증/감사 AOP·Controller 변환·HTTP 직렬화, 프록시·외부 네트워크·브라우저·지도 렌더링 시간은 Service 타이머 밖이다. DB 커넥션 풀 대신 직접 연결을 사용했다. 따라서 배포 HTTP와 동일 요청 ID로 연결한 시간 분해는 아직 없다.

과거 HTTP 평균 772ms에서 이번 Service 값을 빼서 남은 지연을 네트워크라고 판단하지 않는다. [전체 GPU 관측](search-path-full-gpu-observation-20261013.md)의 888초를 설명하거나 개선한 결과도 아니다. 전체 지연에 대한 짧은 성능 합격/실패 재현은 아직 없으며, 이번 검사는 비용 관측과 입력·결과 보존 검사다.

다음은 같은 고정 입력의 실제 HTTP와 서버 처리 경계를 연결하고, 별도로 지도 계측/갱신 비용을 분리하는 것이다. 그 결과 없이 GPS·준비 상태 SQL 중 어느 하나를 첫 수정으로 확정하지 않는다. 브라우저가 필요한 측정은 Aside로 진행한다.
