# 경로 조회 측정 전 브라우저 상태 확인

2026-10-14. **사용자가 탭을 유지한 재시험에서 세 번째 경로 응답 중단과 사건 목록 복귀를 확인했다.** 서버 경로 요청도 3건 이후 늘지 않았다. 앞선 숨김 중단 기록은 아래에 보존했다. 중간·후반 OFF 측정·수리맵 지연 원인 확정·개선 검증은 아직 하지 않았다.

## 확인한 차이

WSL에서 공식 Aside MCP REPL로 측정했다. 로그인·상황판 진입 없이 `requestAnimationFrame` 간격과 타이머를 관찰했다. 경로 API 요청은 관측 자료에서 0건이다. 로그인 화면의 정적 파일 요청까지 없었다는 뜻은 아니다.

| 조건 | 관측 결과 |
|---|---|
| 기존 탭의 로그인 화면, 약 3.1초 | 간격 2개, 1,008.2~1,008.4ms. visible·focus=true이며 100ms 타이머는 91.8~110.8ms였다. |
| 같은 탭을 빈 화면으로 이동, 약 3.1초 | 간격 2개, 1,000~1,008.4ms. 화면 전환 대기 시간 초과 뒤 snapshot으로 빈 화면을 확인했다. |
| 같은 탭에서 로그인 화면 재진입, 약 3.1초 | 간격 2개, 1,000~1,008.3ms |
| 새 탭의 같은 로그인 화면, 약 6.5초 | 771개 간격, 중앙값 8.3ms, 최댓값 16.6ms, visible·focus=true |
| 별도 새 탭에서 수집 시작 후 호출 반환, 15초 타이머로 종료 | 종료 시 hidden·focus=false. 100ms 타이머가 대체로 약 1초마다 실행됐다. rAF 간격 3개는 약 5.9~7.8초였다. |

마지막 조건은 앞 조건과 관찰 방법·시점도 달라 직접 성능 비교할 수 없다. 시작 시 visibility는 원문에 없고 종료 상태만 있다. 종료 타이머가 실행된 뒤 이미 예약된 rAF가 한 번 더 기록돼 마지막 표본은 약 20.1초 시점이다. 15초 전체가 동일 상태였다는 뜻도 아니다. 30초 동안 반환을 기다린 evaluate는 도구 시간 초과로 결과를 얻지 못해 실패 기록으로 보존했다.

## 사용자가 탭을 선택한 뒤의 관측

같은 target ID의 탭이 활성 상태이고 `/incidents`를 표시하는 것을 확인했다. 이미 인증된 사건 목록이었으며, root는 로그인·새로고침·상황판 열기를 실행하지 않았다. 12초 관찰기를 시작한 뒤 브라우저 호출을 반환하고 나중에 결과만 읽었다.

- 프레임 간격 1,441개: 중앙값 **8.3ms**, 최댓값 **9.4ms**. 0~4초·4~8초·8~12초 각각 480개의 중앙값도 모두 8.3ms였다. 나머지 1개는 12초 직후 종료 전 표본이다.
- 100ms 타이머 120개: 중앙값 **99.9ms**, 범위 93.7~106.5ms. 관찰 종료는 시작 후 12,007ms였다.
- 시작·종료 visibility는 `visible`, 중간 `visibilitychange` 기록은 없었다. focus는 true에서 false로 달랐지만 프레임 지연은 관측되지 않았다. focus만으로 숨김이나 성능 저하를 판정하지 않는다.
- Resource Timing의 경로 API 기록은 전후 모두 0개였다. 수집 종료 시 rAF·timer·visibility listener를 정리했고, 사용자가 선택한 탭은 유지했다.

이번 짧은 사건 목록 관측에서는 종전의 1초 프레임 간격이 재현되지 않았다. 로그인 화면과 사건 목록은 다르므로 사용자 선택만이 원인이라고 단정하지 않으며, 긴 상황판 측정, GPU, 네트워크 적합성 검증도 아니다. 원문, 실행 코드, 통계는 당시 로컬에 보존했다.

## 실제 상황판의 소량 중단 시험

앞서 선택한 탭이 더 이상 열려 있지 않아 새 탭에서 기존 시험 계정으로 로그인했다. 지도 계측 OFF·사건 목록·visible 상태에서 시작했다. 이전 탭의 프레임 결과를 새 탭의 측정 적합성 근거로 재사용하지 않았다.

목표는 경로 응답 2건을 원문 그대로 처리하고 세 번째에서 문서를 사건 목록으로 교체하는 것이었다. 숨김·응답 오류·20초 만료 시에도 중단하며, 별도 루트 프로세스의 25초 복귀 시도를 두었다. 이는 전송 전 전역 요청 제한이 아니라 응답 처리 시점의 중단 장치다.

- 첫 실행기 시도(`path-stop-test/001`)는 비동기 호출을 기다리지 않아 결과가 없었다. 브라우저에 관찰기가 설치되지 않았고 서버의 경로·상황판 요청 카운터도 변하지 않았다. 실패 기록을 보존하고 기다리도록 수정했다.
- 수정 후 시험(`002`)에서 첫 segments 응답은 200이며 원문 52,024자를 반환했다. 시작 후 약 3.07초에 `hidden`을 감지해 사건 목록으로 복귀했다. 이후 관찰기 전역은 없었다. 기록한 시각은 호출·본문 반환 시각이지 지도 표시 완료 시각이 아니다.
- 서버 경로 조회는 **segments 1건 + changes 1건 = 2건** 증가했다. 브라우저가 본문 처리한 1건과 다르므로, 중단 당시 발송 중이던 요청까지 취소됐다고 주장하지 않는다. 복귀 뒤 두 서버 스냅샷 사이에서 경로 조회 카운터 추가 증가는 없었다.
- 일반 상황판 GET은 3건 증가했고 그중 1건에는 IOException이 집계됐다. 사건 목록 복귀와 동시에 응답 전송이 끊겼을 가능성은 있지만, 요청별 추적으로 확정하지 않았다. 조회 감사는 5건 증가해 상황판 GET 3건·경로 조회 2건과 수가 맞는다. 요청별 감사 연결 검증은 아니다.
- 전후 Backend 이미지·재시작 수·환경 지문·경로 응답 한도, Frontend 이미지·시작 시각이 같았다. 선택한 80개 경로의 경로·구간·GPS 해시도 같았다. 전체 DB 무변경 검증은 아니며 정상 조회 감사·연결 관련 기록은 발생한다.

**002에서는 숨김 시 중단만 실제로 확인했다.** 세 번째 응답 중단·20초 타이머·루트 25초 복구·동시 Query 중단·전체 지도 정확성은 당시 검증하지 않았다. 숨김 전환의 원인은 미확정이며 Aside 호출 종료나 사용자 조작 중 무엇 때문인지 단정하지 않는다. 이 시험에는 프레임·타이머 간격 수집도 넣지 않았다.

원문·계획·자체 검사는 로컬 `tasks/path-stop-test/001/`, 수정 실행기·실제 결과·서버 사후 자료는 `tasks/path-stop-test/002/`에 보존했다. 이 중단 뒤에는 긴 OFF 측정을 시작하지 않고 아래의 재시험을 진행했다.

## 탭 유지 후 세 번째 응답 중단 확인

사용자가 같은 새 탭을 선택해 유지한 뒤 `path-stop-test/003`으로 한 번 재시험했다. 사건 목록에서 복귀용 `goto`·snapshot 명령이 반환되는지 먼저 확인했다. 이는 복귀 명령의 검사이지 25초 만료에 따른 자동 복구 시험은 아니다.

상황판 진입 전 12초 관측에서는 숨김 전환이 없었다. 프레임 간격 1,440개의 중앙값은 8.3ms, 최댓값은 9.8ms였다. 100ms 타이머의 최댓값은 109.3ms였고 경로 API 기록은 전후 0건이었다. 과거 약 1초 간격의 지연 상태를 걸러내기 위한 보수적 사전 검사이며, 현장 서비스의 성능 목표는 아니다.

| 실제 조회 순서 | HTTP 상태 | 후속 처리에 넘긴 본문 |
|---|---|---|
| 구간 조회 1 | 200 | 52,024자 반환 |
| 변경분 조회 | 200 | 26,308자 반환 |
| 구간 조회 2 | 200 | 반환하지 않고 중단 |

- 관찰기 설치 후 약 3.17초에 `third_response`로 중단했고 사건 목록으로 복귀했다. 중단 전 숨김 이벤트는 없었고 복귀 후 임시 관찰기 전역도 없었다. 지도 표시 완료를 측정한 시간은 아니다.
- 서버 요청은 구간 조회 2건·변경분 조회 1건으로 정확히 3건 증가했다. 이후 UTC 00:04:15~00:04:32의 두 스냅샷에서 경로 조회 카운터는 같았다.
- 상황판 GET 3건과 경로 조회 3건에 대해 조회 감사는 6건 증가해 수가 맞았다. 요청별 감사 연결은 검증하지 않았다. 사건 목록 GET 1건, 사건 상세 GET 2건, 사건 목록 SSE의 IOException 집계 1건, 타일 요청 18건도 증가했으며, 각각의 발생 원인은 분석하지 않았다. 로컬 요약의 `httpDeltas`는 `/api` 요청만 담으므로 타일 증가량은 당시 원문 서버 스냅샷에서 확인했다.
- 전후 Backend·Frontend 배포 정보와 선택한 80개 경로의 원본 해시는 같았다. FCM은 사전 검사에서 mock이었다. 제품 코드·서버 설정은 바꾸지 않았다.

이번에는 세 번째 응답 중단 조건을 충족했다. 실제 20초 타이머 만료, 루트 25초 복구, 동시 Query, 전체 지도 정확성은 미검증이다. 상황판 진입 뒤에는 visibility만 기록했으며 프레임과 타이머 간격은 수집하지 않았다. 긴 측정의 중간과 후반에서 같은 중단 동작을 보장한 결과도 아니다. 원문과 호출 시작, 반환 시각, 서버 스냅샷은 당시 로컬에 보존했다. 다음 OFF 실행안에는 총 요청과 시간 상한, 실행 중 프레임과 타이머 간격 변화의 관측 및 중단 방법을 고정한다.

## 해석과 다음 작업

- 기존 탭은 빈 화면에서도 느렸고 새 로그인 탭은 빨랐다. 로그인 코드만의 문제나 Aside 전체의 고정 1초 제한으로 단정할 수 없다. 탭 이력·활성 상태·관찰 방식 중 무엇이 원인인지는 미확정이다.
- visible·focus만으로 정상 측정 조건을 판정하지 않는다. 이번 짧은 관측을 기준으로 다음 상황판 진입 전후에도 실제 프레임 간격·타이머·visibility 변화를 확인한다. 숨김으로 바뀌면 중단하며, 프레임 간격이 크게 바뀌면 새 결과를 보존하고 비교 가능성을 다시 판단한다.
- 소량 요청의 세 번째 응답 중단을 확인했으므로 다음은 중간·후반 OFF 실행의 총 요청·시간 상한과 중단을 고정한다. 기존 4,800구간 OFF는 과거 초반 자료로만 재사용하며 새 관측과 같은 조건으로 합치지 않는다. 재사용할 때 날짜·브라우저·실행 방식·배포본과 프레임 기록 유무를 확인한다.
- root가 확인한 현재 Aside Page에는 `addInitScript`·`route`가 노출되지 않았다. 배포 없이 `Response.prototype.text`를 감싼 소량 시험에서 숨김 중단과 세 번째 응답 중단을 확인했다. 본문 읽기 완료는 정확한 API 반환 시각이 아니며, 이 방법의 전체 요청 제한 효과는 미검증이다.
- Windows 프록시·VPN·네트워크 제한과 실제 상황판의 GPU 조건은 확인하지 않았다. 종전 전체 조회 기록에 이번 프레임 결과를 소급 적용하지 않는다.

제품 코드, 서버 설정, 배포 변경은 없다. 초기 원문은 당시 로컬에 보존한 `same-tab.json`, `fresh-login.json`, `detached-collector.json`이며 `failures.json`은 도구 오류의 수기 요약이다. `same-tab.json`의 빈 화면 URL `nullblank`는 관찰기가 origin+pathname으로 만든 표시값이며, 실제 이동, snapshot은 `about:blank`였다. 도구 기능 확인, 인증 조작 여부, 탭 정리는 root 실행 관찰이며 JSON만으로 독립 검증한 사실과 구분한다.
