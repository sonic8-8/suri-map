## 웹 배포와 실제 상황판 표시

Jenkins #62는 `SUCCESS`로 끝났다. 웹은 06:59:51 KST에 시작했고 Backend 시작 시각은 그대로 유지됐다. 공개 사이트와 시험 브라우저가 받은 `index-LhL8h6oC.js`가 새 빌드와 일치했다.

Chrome 147·1440×900·SwiftShader에서 같은 사건·차수의 상황판을 열었다. 경로당 1·전체 80구간·480좌표 조건과 제품 계측을 유지했고, 함수별 진단 타이머·프로파일러·임시 단순화 대조 source는 사용하지 않았다. 초기 이력을 받는 동안 기존 시험 업무폰으로 GPS 6개를 한 번 추가했다.

| 검사 | 결과 |
|---|---|
| 대상 경로 source | 실제 `tolerance: 0` 확인 |
| 같은 축척의 짧은 구간 | zoom 10.921에서 대상 구간 9개 수신·9개 표시, 모두 화면 범위 안 |
| 새 좌표 저장 | 6개 수용·제외 0, DB 좌표·순서 일치, HTTP 291ms |
| 새 좌표 표시 | 전송 좌표 해시와 일치하는 구간의 화면 표시 검사 통과 |
| 기존 원본 보존 | 추가분을 제외한 기존 GPS 341,003개·구간 57,086개의 모든 컬럼 해시가 준비 전과 일치 |
| 짧은 관측 종료 | 약 68.7초·경로 조회 55건 완료·3,761구간 수신 및 지도 전달, HTTP 실패·수집한 JavaScript 오류 0 |

표시 판정은 실제 MapLibre의 화면 feature 조회와 좌표 일치 검사다. 픽셀 색 전수 검사는 아니며, 대상 경로의 수신 구간 9개 확인을 전체 이력 57,087개 표시 검증으로 확대하지 않는다. 캡처에서도 지도와 ‘일부만 표시’ 안내를 확인했지만, 작은 축척과 마커·알림 패널이 있어 개별 짧은 선의 육안 확인을 대신 근거로 쓰지 않았다.

첫 경로 표시는 6.008초였다. 새 좌표는 브라우저에서 원격 전송 명령을 시작한 시점부터 표시 확인까지 8.995초가 걸렸다. 후자는 같은 브라우저 단조 시계의 값이지만 SSH 연결·원격 사전 확인도 포함한다. **HTTP 응답 이후 순수 지도 반영 시간이나 목표 달성으로 표현하지 않는다.**

전체 이력 완료 전에 의도적으로 종료했으므로 ‘일부만 표시’ 안내는 남아 있었다. 마지막 관측에는 요청 1개가 진행 중이었으며 이후 브라우저를 닫았다. 전체 수신 시간·응답 한도별 비교·여러 상황판 부하·실사용 GPU 성능은 이번 결과에 포함하지 않는다.

**짧은 구간의 표시 누락은 배포본 재현 검사까지 통과했다. 전체 로딩 지연은 별도 미해결 문제다.** 다음은 동일한 수정 버전에서 응답 한도별 로딩·새 좌표 반영을 비교하고, GPS 범위 일괄 조회를 실제 Mapper·Service에 연결해 검증하는 작업이다.
