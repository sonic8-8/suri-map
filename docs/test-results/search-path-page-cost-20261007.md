# 경로 페이지 조회의 반복 비용 분석

2026-10-07 [로컬 20번](../issues/local/20-slow-paged-search-path-display.md)의 후속 분석이다. 기존 브라우저 관측을 재집계하고 Hetzner App의 DB에서 조회 실행 계획을 확인했다. 이후 경로당 한도를 잠시 바꿔 브라우저로 관찰했지만, 지도 초기화·화면 범위 차이 때문에 전체 비교를 완료하지 않고 원복했다. 제품 코드는 변경하지 않았다.

## 기존 관측에서 확인한 시간

[캐시 수정 후 전체 이력 관측](image-preservation-and-cache-deployment-20261007.md#전체-이력-완료와-남은-지연)의 같은 표본이다. 경로 481개·구간 57,083개를 받는 데 경로 조회 793건이 완료됐으며, 구간 수신·캐시 반영까지 1,069.873초가 걸렸다. 새 브라우저 실행 결과가 아니다.

- HTTP 시간 합계: 601.432초. DB 실행 시간만이 아니라 네트워크·서버 처리·응답 수신 등을 포함한다.
- 응답 완료부터 다음 요청 시작까지 간격 합계: 462.606초. 이 값 전체를 JavaScript 실행 시간으로 단정할 수 없다.
- 마지막 85구간: 73번 요청, 첫 요청 시작부터 마지막 응답 완료까지 133.911초. 12번은 2구간, 61번은 1구간을 받았다.

| 요청 순서 | HTTP 평균 | 요청 사이 간격 평균 |
|---|---:|---:|
| 1–200 | 783ms | 90ms |
| 201–400 | 726ms | 321ms |
| 401–600 | 810ms | 786ms |
| 601–793 | 712ms | 1,159ms |

간격 평균은 각 묶음 내부만 계산했다. 묶음 사이 3개 간격은 위 전체 합계에는 포함된다. HTTP 평균이 계속 증가하지는 않았지만 후반의 요청 사이 간격은 커졌다. 누적 데이터 병합·캐시·지도 갱신 비용은 별도 계측이 필요하다.

## 코드와 DB에서 확인한 반복 조회

[SearchPathBoardService](../../backend/src/main/java/com/surimap/api/service/path/SearchPathBoardService.java)의 페이지 조회는 다음 순서다.

1. 접근 권한과 요청을 검사하고 조회 범위의 경로 목록을 읽는다.
2. 이전 페이지의 진행 위치와 데이터 준비 상태를 검사한다.
3. 각 경로의 구간을 조회하고, 응답에 담을 각 구간의 GPS 좌표를 따로 조회한다.

현재 경로당 1구간 설정에서 80경로·80구간을 담는 페이지는 구간 조회 80회와 좌표 조회 80회를 호출한다. 권한·메타데이터·진행 위치·준비 상태 조회는 별도다. 이는 코드의 Mapper 호출 구조이며 SQL 추적으로 해당 HTTP의 실제 실행 횟수를 측정한 값은 아니다.

서버의 같은 사건·차수에 대해 [Mapper SQL](../../backend/src/main/resources/mapper/path/SearchPathMapper.xml)의 경로 목록 조회와 준비 상태 검사를 `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)`로 실행했다. 읽기 전용 트랜잭션, SQL 제한시간 15초·잠금 대기 2초를 적용하고 마지막에 롤백했다.

| SQL | 실행 시간 | 실행 계획에서 확인한 내용 |
|---|---:|---|
| `findBoardPathMetadata` | 2.691ms, 1회 | 경로 481개 반환 |
| `hasUnpreparedBoardPaths` | 78.743 / 70.105 / 66.089ms, 3회 | 경로 481개마다 구간 유효성 검사. 인덱스로 경로를 찾지만 유효한 구간도 끝까지 확인 |

준비 상태 검사에서는 매회 shared buffer hit 64,997회가 기록됐다. 서로 다른 블록 64,997개나 디스크 읽기 횟수를 뜻하지 않는다. 준비되지 않은 경로는 발견되지 않았으며, 정상임을 확인하기 위해 구간을 반복 검사한 비용이다. 페이지에 1구간만 담더라도 현재 코드는 이 검사를 같은 범위에 수행한다.

현재 실행 계획은 경로 테이블에서 준비 상태 조건을 검사한 뒤 사건·차수를 조인한다. 다른 사건이 많이 쌓인 조건의 영향은 이번에 측정하지 않았다. 위 SQL 시간은 캐시가 데워진 DB의 독립 실행 결과이며, 앞선 브라우저 HTTP 시간의 세부 내역으로 대입하지 않는다.

## 다음 비교와 검증 한계

- 후속 [브라우저 단계별 통제 시험](search-path-browser-stage-cost-20261007.md)에서 전체 지도 자료 재조립·교체와 계측 비용을 분리했다. 실제 HTTP 간격 전체를 분해한 결과와는 구분한다.
- 경로당 한도만 바꿔 마지막 소량 응답과 요청 수가 줄어드는지 비교한다. 이후 응답 전체 한도를 별도로 비교해 효과를 구분한다. 시험값은 운영 기본값으로 바로 채택하지 않는다.
- 동일 데이터에서 전체 수신 구간 ID가 DB와 일치하는지 확인하면서 요청 수·응답당 구간 수·HTTP 시간·요청 사이 간격을 함께 측정한다.
- 서버의 개별 SQL 반복과 전체 준비 상태 검사는 최적화 후보지만, 아직 지배적인 병목이나 해결 효과를 확정하지 않았다. 브라우저 단계별 처리 비용도 남아 있다.
- 새 GPS 전송·동시 사용자 부하·제품 회귀 테스트는 실행하지 않았다. 이번 결과만으로 이슈나 페이지 한도 비교 작업을 완료 처리하지 않는다.

## 경로당 4구간 시험과 중단

같은 날 21시대 KST에 실제 서버에서 `segments-per-path`만 1에서 4로 바꿨다. 4는 기존 첫 페이지 시험의 후보를 재사용한 값이지 최적값이나 운영 기준이 아니다. 응답 전체 한도는 80경로·80구간·480좌표로 유지했다.

설정 변경 전 Compose 병합 결과에서 해당 값 하나만 달라지는지, 원래 설정이 실행 컨테이너의 환경과 일치하는지, 이미지 태그가 같은 실행 이미지 `03c049ad5850…`를 가리키는지 검사했다. Backend만 재생성했고 `.env`는 수정하지 않았다. 기동 직후 첫 health 요청은 연결 초기화로 실패했으며 후속 요청은 UP이었다. 새 브라우저 관측에서 경로 페이지 실패는 없었다.

| 부분 관측 | 경로당 4구간 | 원복 후 경로당 1구간 |
|---|---:|---:|
| 관측 시점 | 183.852초 | 84.022초 |
| 완료 페이지 | 199건 | 91건 |
| 받은 구간 | 15,280개 | 6,720개 |
| 경로 페이지 실패 | 0건 | 0건 |
| 경로 지도 전달 계측의 마지막 구간 수 | 15,280개 | 0개 |
| 첫 경로 렌더링 계측 | 없음 | 없음 |

두 열은 같은 시간·같은 데이터량의 비교가 아니다. 두 관측 시점 모두 요청 1건이 진행 중이었고 전체 이력 수신은 끝나지 않았다. 따라서 전체 요청 수 감소·완료 시간·전체 구간 ID 일치를 확인한 결과로 사용할 수 없다.

4구간 실행은 99.181초 관측까지 경로 지도 전달 계측이 없었고, 183.852초 관측에서는 전달이 확인됐다. 지도 타일·마커는 보였다. 처음에는 경로 지도 전달 자체가 누락된 것으로 의심했지만, 뒤늦은 전달이 확인돼 영구 누락으로 판정하지 않았다. 원복 후에도 초기 경로 전달 계측이 지연됐으므로 4구간 설정 때문에 발생했다고 단정하지 않는다.

이전 완료 캡처는 경로 주변으로 확대된 화면이고 이번 캡처는 광주 초기 범위였다. 화면 크기도 달랐다. 경로 렌더링 계측은 화면 범위의 영향을 받으므로, 계측 없음만으로 실제 데이터 유실이나 경로 도형 생성 실패를 확정하지 않는다. 지도 초기화와 외부 타일 요청의 영향도 분리하지 못했다.

관측을 보존한 뒤 계측을 끄고 사건 목록으로 이동했다. 원래 Compose로 Backend를 재생성해 경로당 한도 1과 나머지 기존 한도, health UP을 확인했다. 새 GPS·마커 쓰기는 하지 않았고 경로 481개·GPS 340,985개·구간 57,083개의 변경 전후 fingerprint 해시는 모두 같았다. 위치 조회 감사 기록은 남을 수 있으며 DB 전체가 무변경이라는 뜻은 아니다.

다음 실행에서는 같은 화면 크기·지도 범위·초기화 조건을 먼저 고정하고 경로 전달·렌더링 계측이 가능한지 확인한다. 그 뒤 페이지 한도별 전체 수신과 DB 구간 ID 대조를 다시 진행한다. 이번 부분 실행으로 성능 개선이나 문제 해결을 판정하지 않는다.

자료는 `_workspace/path-page-limit-20261007.OleF9V/`에 보존했다. `observation-199.json`은 4구간, `per-path-1-91.json`은 원복 후 관측이며 `per-path-4-partial.png`는 4구간 실행 중 캡처다. `start-observation.cjs`는 Aside REPL 입력, `collect-observation.cjs`는 수집 명령이다. `check-config.py`·`per-path-4.yml`의 서버 사본은 `/srv/apps/suri-map/backups/path-page-limit-20261007/`에 있으며 현재 실행에는 override를 적용하지 않았다.
