# 수색 경로 조회 지연의 네 가설 대조

2026-10-08 [기존 진단](search-path-page-delay-diagnosis-20261008.md)과 [남은 4구간 대조](search-path-tail-page-limit-comparison-20261008.md)에 이어 네 가설을 대조했다. **응답량 확대와 인덱스 범위별 GPS 일괄 조회에서 개선 근거를 얻었다.** 단순 JOIN은 오히려 느렸으며 준비 상태 SQL 교체는 확정하지 않았다. 제품 코드·영구 설정은 변경하지 않았고, 새 좌표 반영 검증은 남았다.

## 응답 한도를 늘리면 전체 로딩이 빨라지는가

같은 이미지·데이터에서 경로당 한도만 1에서 4로 바꿨다. 전체 한도는 80경로·80구간·480좌표로 유지했다. 실제 지도와 계측을 켠 WSL Headless Chrome 147, 화면 1440×900·SwiftShader 조건이다.

| 조건 | 경로 조회 요청 | 첫 경로 표시 | 전체 수신·캐시 반영 |
|---|---:|---:|---:|
| 기존 한도 1 — 앞선 측정 | 793회 | 3.620초 | 734.542초 |
| 경로당 한도 4 | 738회 | 5.308초 | 751.651초 |
| 경로당 4·전체 320구간/1,920좌표 | 206회 | 4.951초 | 296.026초 |

한도 4의 요청은 구간 조회 730회·변경분 조회 8회였다. HTTP 시간 합계 741.493초, 요청 사이 간격 합계 8.380초다. 조회 실패·JavaScript 오류는 없었고, 수신 ID와 지도 전달 ID의 합집합은 DB의 57,083구간과 일치했다.

**경로당 한도만 올려서는 전체 로딩 개선을 확인하지 못했다.** 요청 수는 줄었지만 HTTP 평균과 요청 사이 간격이 앞선 실행과 달라졌다. Backend 재시작·네트워크 변동과 15초 진단 계측을 포함한 단일 실행이므로 첫 표시나 HTTP 차이를 모두 한도 변경의 효과로 단정하지 않는다.

이어 전체 구간 한도만 80에서 320으로 올리고 좌표 한도 480을 유지해 첫 3페이지를 확인했다. 각각 98구간/479좌표, 80구간/480좌표, 80구간/480좌표였다. 구간 한도에 여유가 있어도 좌표 제한 때문에 반환량을 늘리지 못했다. 이 단계는 전체 로딩 시간 측정이 아닌 제한 조건 확인이다.

그다음 좌표 한도를 1,920으로 높인 조건에서 전체 이력을 조회했다. 320구간은 80경로×경로당 4구간, 1,920좌표는 시험 입력의 일반적인 구간당 6좌표에 맞춘 값이다. 운영 최적값이나 공식 권장값이 아니다.

- 전체 최대 80경로·320구간·1,920좌표가 실제 응답에 담겼다. 171개 응답에서 320구간을 받았다.
- 구간 조회 199회·변경분 조회 7회, HTTP 합계 291.383초, 요청 사이 간격 합계 2.950초였다.
- 조회 실패·JavaScript 오류는 없었고, 수신 ID와 지도 전달 ID 합집합이 DB의 57,083구간과 일치했다. 최대 동시 경로 조회는 1개였다.
- 전체 수신은 4분 56초로 줄었지만 여전히 수분 단위다. 마지막 도형의 렌더링 완료나 새 GPS 반영 시간은 아니다.

큰 응답 실행에는 아래 브라우저 가설을 위한 함수별 타이머를 추가했다. 브라우저가 받은 동일 배포 bundle의 정확히 한 호출 지점만 임시 계측했고, 파싱·병합·캐시 함수와 실행 순서·값은 유지했다. 원본·계측본 해시를 보존했으며 서버 파일은 바꾸지 않았다. 따라서 완전히 무계측인 성능 비교나 반복 벤치마크로 설명하지 않는다. 무계측 재확인과 초기 로딩 중 새 좌표 반영을 마치기 전에는 시험 한도를 채택하지 않는다.

## 준비 상태 검사를 같은 판정으로 더 싸게 할 수 있는가

기존 SQL은 경로별 `OR` 조건 안에서 구간과 GPS 존재 여부를 검사한다. 대조 SQL은 먼저 사건·차수 범위의 경로 ID·버전·도형 존재 여부를 고정하고, 같은 세 오류 조건을 `UNION ALL`로 나눠 `EXISTS`로 검사했다. 범위나 오류 검사를 삭제하지 않았고 인덱스도 추가하지 않았다.

| 순서 | 기존 SQL | 분리한 SQL |
|---|---:|---:|
| 1 | 94.568ms | 48.579ms |
| 2 — 역순 | 62.565ms | 52.267ms |
| 3 | 61.476ms | 54.625ms |
| 4 — 역순 | 55.074ms | 60.408ms |

실제 App DB에서 `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)`를 읽기 전용으로 실행했다. 공유 버퍼 hit는 64,997에서 7,887로 줄었고 디스크 read는 모두 0이었다. 기존 계획은 구간 인덱스를 481번 조회했으며, 대조 계획은 구간 57,083행을 한 번 읽고 해시 조인했다. 버퍼 hit는 중복 접근을 포함하므로 고유 페이지 수나 디스크 읽기량이 아니다.

도형 유무·GPS 유무·구간 없음/정상/시작 순번 누락/끝 순번 누락/변경 버전 누락/부모보다 큰 변경 버전/이전 변경 버전/정상과 오류 혼재를 조합한 32조건과 빈 조회 범위 1조건에서 두 SQL의 판정이 기대값과 일치했다. 이는 읽기 전용 CTE 입력으로 검사한 SQL 판정이며 실제 테이블 제약·Mapper·HTTP 회귀 검사를 대신하지 않는다.

**중복 버퍼 접근은 줄었지만 실행 시간은 일부 겹쳤다.** 이 측정만으로 SQL 교체를 확정하지 않는다. 제품 SQL은 그대로 유지한다.

## GPS를 이번 페이지 단위로 묶어 조회하면 빨라지는가

실제 Backend 컨테이너 안에서 같은 JDBC 드라이버 42.7.10·DB 연결·읽기 전용 `REPEATABLE READ`·fetch size 100으로 비교했다. 준비·트랜잭션 커밋 시간을 제외하고, 파라미터 설정부터 전체 결과 수신·값 해시 계산까지 측정했다. 예열 1회 후 5회씩 실행했고 매 회 세 방식의 실행 순서를 뒤집었다. MyBatis 객체 매핑·HTTP·지도 렌더링 시간은 아니다.

| 입력 | 개별 조회 | 단순 JOIN 일괄 조회 | 범위별 LATERAL 일괄 조회 |
|---|---:|---:|---:|
| 80구간·443좌표 중앙값 | 38.540ms | 70.610ms | 9.313ms |
| 같은 조건의 범위 | 31.878–50.250ms | 67.880–86.576ms | 4.456–12.823ms |
| 320구간·1,811좌표 중앙값 | 100.520ms | 101.377ms | 19.119ms |
| 같은 조건의 범위 | 69.342–120.144ms | 87.784–114.570ms | 14.792–23.733ms |
| SQL 실행 횟수 | 80회 / 320회 | 각 1회 | 각 1회 |

**SQL을 하나로 묶는 것만으로는 빨라지지 않았다.** 첫 단순 JOIN 시험도 개별 37.828ms·일괄 77.655ms로 오히려 느렸다. 이 실패 결과는 별도로 보존하고 실행 계획을 확인한 뒤 세 방식으로 다시 비교했다.

단순 JOIN은 GPS 테이블 전체를 병렬 순차 스캔한 다음, 요청한 경로·순번 범위로 걸러냈다. 대조한 `JOIN LATERAL`은 요청 범위별로 정렬된 GPS를 읽도록 표현해, 실제 계획에서 기본 키 인덱스 범위 조회 80회로 실행됐다. 80구간의 `EXPLAIN` 실행 시간은 62.955ms와 1.396ms, 공유 버퍼 hit는 6,415와 409였다. SQL은 한 번 보내지만 DB 내부에서 인덱스를 여러 번 찾는 동작까지 한 번으로 줄였다는 뜻은 아니다. 인덱스나 DB 설정은 바꾸지 않았다.

모든 방식에서 point ID·측정 시각·경도·위도·속도·정확도·공급자·단조 시각의 값과 구간별 순서 해시가 일치했다. `fetch size 100`으로 결과를 받으므로 SQL 실행 1회가 네트워크 패킷이나 결과 수신 왕복도 반드시 1회라는 뜻은 아니다.

동시 저장 검사는 로컬 PostgreSQL의 격리된 시험 schema에서 수행했다. 읽기 연결이 경로 버전 1을 읽은 다음, 다른 연결이 버전 2·추가 좌표·늘어난 구간 범위를 함께 커밋했다. 읽기 연결은 이어서 구간 범위를 읽고 GPS를 일괄 조회했다.

- `READ COMMITTED` 대조: 이전 버전과 새 좌표가 섞였다. 기존 4좌표 대신 5좌표를 받았다.
- 현재와 같은 `REPEATABLE READ`: 버전 1과 기존 4좌표·순서가 함께 유지됐다.

두 격리 수준에서 JOIN과 LATERAL의 값·순서도 일치했다. 공개 애플리케이션 테이블은 수정하지 않았다. 사용한 합성 시험 schema와 서버·컨테이너에 복사한 실행용 임시 파일은 검사 후 제거했다. 로컬 컨테이너의 Java 17에 맞춰 진단 클래스를 다시 컴파일한 뒤 실행했으며, 첫 버전 불일치 시도는 DB에 접근하기 전에 실패했다.

**범위별 일괄 조회를 구현 후보로 삼을 근거를 확보했다.** 다만 이 검사는 JDBC·SQL·트랜잭션의 대조이며 실제 Mapper·Service에 연결한 회귀 검증은 아니다. 320구간보다 큰 입력이나 다른 데이터 분포에서도 같은 실행 계획·개선량을 보장하지 않는다.

## 로딩 후반에 브라우저 계산이 지연을 지배하는가

한도 4의 실제 화면에서 약 45,600구간이 누적된 뒤 15초 동안 프로파일을 수집했다. 지도 canvas를 숨기지 않았다.

- 메인 스레드 `RunTask` 경과 시간 합계: 8.581초, 스레드 CPU 시간 합계: 2.315초.
- 그 안의 `CommandBufferProxyImpl::WaitForGetOffset` 대기: 6.403초.

중첩된 작업이므로 두 항목을 합산하지 않는다. 후반에도 긴 작업을 전부 JavaScript 계산 비용으로 볼 수 없다는 근거다.

큰 응답 실행에서는 실제 호출부의 `parseSearchPathPage` → `mergeSearchPathPage` → `setQueryData` 앞뒤에 타이머를 넣었다. 지도에 45,000구간 이상 전달된 이후의 58개 응답을 집계했다. `parseSearchPathPage`는 이미 JSON으로 변환한 응답의 형식 검증이며, HTTP 수신·JSON 디코딩은 아래 시간에 포함하지 않는다.

| 후반 응답 58개 | 중앙값 | p95 | 최대 | 합계 |
|---|---:|---:|---:|---:|
| 응답 형식 검증 | 0.200ms | 0.300ms | 0.400ms | 9.100ms |
| 기존 경로와 병합 | 0.700ms | 1.300ms | 1.800ms | 33.600ms |
| Query 캐시 갱신 | 14.000ms | 25.600ms | 43.100ms | 683.700ms |

이 실행의 후반 15초 trace에서는 메인 스레드 작업 경과 시간 7.712초·스레드 CPU 시간 2.913초, 그 안의 그래픽 명령 완료 대기 4.806초를 확인했다. 이는 타이머 표의 58개 응답 전체와 관찰 구간이 다르므로 합산하거나 직접 비율로 나누지 않는다.

**캐시 갱신 비용은 있지만 이번 표본에서 응답 검증·병합·캐시 갱신이 수분 지연을 지배한다는 근거는 없다.** 그래픽 대기는 WSL Headless Chrome·SwiftShader 조건의 결과다. 실제 사용자 GPU 환경에도 같은 대기량이 발생한다고 일반화하거나 지도 숨김을 해결책으로 삼지 않는다.

- 준비 상태: `compare-readiness.cjs`, `readiness-queries.json`, `readiness-comparison.json`.

- 원복: `restored-*.json`, `database-before.json`, `database-after.json`. 브라우저 시간·ID 일치 검사와 JDBC 값 해시 검사, SQL 33조건 검사가 통과했다.

첫 전체 시험은 API 측정 전에 기준 ID 목록을 가져오는 SSH 명령이 시간 제한에 걸려 중단됐다. 설정 원복 후, DB의 정렬된 ID 해시와 기존 ID 목록을 대조하도록 바꿔 재실행했다. 중단된 시도는 성능 결과에 넣지 않았다.

종료 후 원래 이미지·전체 환경변수와 `.env` 파일 해시가 유지됐다. 한도는 다시 경로당 1·전체 80구간·480좌표다. Backend health `UP`과 공개 인증 API의 200 응답을 확인했다. 경로 481개·GPS 340,985개·구간 57,083개의 모든 컬럼을 포함한 fingerprint가 시험 전과 일치했다. 조회 감사 기록을 포함한 DB 전체 무변경을 뜻하지 않는다. 인증 정보 임시 사본을 삭제하고 시험 브라우저를 종료했다.

초기 로딩 중 새 GPS 반영은 미실행이다. Ops에 남은 업무폰 요청 fixture 468개의 토큰이 모두 만료됐으며, 기존 준비 도구는 `seed_sql()`에서 `cleanup_sql()`을 호출해 경로·GPS를 다시 만든다. 단순 토큰 갱신인 것처럼 이 도구를 실행하지 않았다. 비교 데이터를 보존하는 인증 준비가 선행돼야 한다.

실제 MyBatis·Service에 연결한 변경, 여러 상황판의 부하 시험과 최종 허용 시간 판정도 남았다. 시험값을 영구 설정으로 채택하거나 커밋·푸시하지 않았다. 제품 코드 변경이 없어 Backend 전체 테스트·Frontend 빌드는 재실행하지 않았다.

## 후속 검증: 기존 데이터를 보존한 인증 준비

같은 날 기존 fixture의 첫 번째 계정·등록 업무폰·기록 중 경로의 연결을 DB에서 확인하고, 업무폰 1대의 APP 토큰을 발급했다. 기존 준비 도구의 인증 함수만 사용했고 `seed_sql()`·`cleanup_sql()`은 호출하지 않았다. 충돌하지 않는 임시 Keycloak 계정·클라이언트를 만들었으며, 발급 후 해당 자원만 제거하고 사용자 프로필 설정의 원복을 확인했다.

준비 전후 모든 컬럼의 내용 해시가 일치했다. 경로 481개(`ac090acc3853a08a4dcdfc332e7504dc`), GPS 340,985개(`5573a3372564b5210f41382962b26dd5`), 구간 57,083개(`5bfcfbf927cef6ebdb91dda610db0ea3`)다. 토큰은 서버의 비공개 시험 파일에만 보관하고 본문·콘솔에 출력하지 않았다. 인증 준비 완료이지 새 좌표 저장·지도 반영 검증 완료는 아니다.

후속 첫 시도는 진단용 Python HTTP 클라이언트의 기본 헤더에서 403·`error code: 1010` 응답을 받아 중단했다. DB에서 시험 좌표 0개를 확인한 뒤, 명시적인 `User-Agent: suri-map-diagnostic/1.0`으로 읽기 요청의 200 응답을 확인하고 다시 시험했다. 토큰·API 권한·서버 보안 설정은 바꾸지 않았다. 중단한 시도는 성능 비교에서 제외한다.

## 후속 검증: 짧은 구간의 표시 누락

아래는 수정 전 배포본의 진단 기록이다. 이후 로컬 수정과 검증은 마지막 절에 구분했다.

**전체 로딩 지연과 별개로, 작은 축척에서 짧은 구간이 표시용 도형에서 빠지는 문제를 확인했다.** 새 GPS는 저장되고 브라우저 지도 데이터에도 들어왔지만 실제 표시 검사는 실패했다. 이 실패를 해결하기 전까지 큰 응답 한도의 재측정은 보류한다.

### 전체 수신 완료와 새 좌표 표시 실패

기존 한도 1·80구간·480좌표, 같은 이미지·Chrome 147·1440×900·SwiftShader에서 함수별 타이머와 프로파일러를 끄고 실행했다. 기존 페이지·지도 계측은 유지했다. 로딩 초반에 기존 시험 경로로 새 좌표 6개를 한 번 전송했다.

- 첫 경로 표시: 5.247초. 전체 이력 수신·캐시 반영: 961.644초, 약 16분 2초.
- 경로 조회: 794회. 조회 실패 0, 최종 진행 기록의 동시 조회 0·지도 전달 구간 수 57,084개.
- 보존한 수신 ID 목록은 시험 후 DB 기준 ID 57,084개와 전수 일치했다. 지도 전달 **개수**와 구간 ID의 실제 화면 표시를 같은 검증으로 취급하지 않는다.
- 새 좌표 6개는 228ms에 저장 응답을 받았고 DB 값·순서가 일치했지만, 해당 좌표의 화면 표시 확인은 실패했다.

첫 실행의 진단 스크립트는 표시 검사를 전체 상세 보고서 저장보다 먼저 수행해, 실패 시 페이지별 상세 보고서를 남기지 못했다. 따라서 위 값은 보존한 진행 기록·수신 ID·쓰기 결과에 근거하며, HTTP 합계나 지도 전달 ID 전수 일치까지 주장하지 않는다. 이후 짧은 재현에서는 실패 전 상세 보고서·좌표 검사·화면을 저장하도록 진단 도구를 수정했다. 제품 코드는 바꾸지 않았다.

새 좌표 표시 실패를 약 1분 관찰로 줄여 두 번 더 재현했다. 각 실행에서 6개씩 추가했고 모두 DB 값과 일치했다. 세 번째 실행에서는 새 좌표 해시가 실제 MapLibre source 데이터와도 일치했다. 해당 경로의 수신 구간 8개는 화면 범위 안에 있었지만 `querySourceFeatures()`와 `queryRenderedFeatures()`에서는 0개였다. 이는 HTTP 응답 누락이나 화면 범위 밖 좌표로 설명되지 않는다.

### 같은 좌표로 단순화 설정만 대조

이어서 새 쓰기 없이 별도 브라우저에서 동일 경로의 수신 구간 9개를 읽었다. 지도 zoom은 약 10.921이었고 모두 화면 범위 안이었다. 같은 GeoJSON·같은 지도·같은 line 레이어 설정의 임시 source 두 개를 만들고 `tolerance`만 바꿨다.

| 조건 | 표시용 타일의 feature 수 | 화면에서 조회된 feature 수 |
|---|---:|---:|
| 기본 `tolerance: 0.375` | 0 | 0 |
| `tolerance: 0` | 36 | 9 |

타일 feature 36개는 타일별 중복을 포함하므로 고유 구간 36개라는 뜻이 아니다. 두 대조 source의 입력은 같은 9구간이다. 임시 source·레이어는 대조 후 제거했고 브라우저도 종료했다. 실행기의 마지막 `PASS` 문구는 당시 공용 종료 문구였으며, 신규 쓰기·전체 이력 완료의 통과를 뜻하지 않는다. 이 대조의 근거는 `map-diagnostic.json`의 실제 결과이며 종료 문구도 검사 종류에 맞게 수정했다.

[지도 source 생성](../../frontend/src/features/situationBoard/presentation/components/map/SearchMapCanvas.tsx)은 경로 source의 단순화 값을 지정하지 않는다. 설치된 MapLibre 5.24.0의 기본값은 0.375이며, `@maplibre/geojson-vt` 6.1.0의 타일 생성기는 단순화 기준보다 짧은 선을 타일에 넣지 않는 분기를 가진다. 전체 경로를 짧은 개별 구간으로 표시하는 현재 방식에서는 여러 구간을 이어 봐야 하는 경로도 작은 축척에서 빠질 수 있다. 이번 같은 입력의 대조는 그 조건에서 단순화가 누락을 일으킨다는 근거다.

`tolerance: 0`은 원인 확인용 대조값이다. 원본 GPS를 바꾸지는 않지만 타일에 남는 도형·좌표가 늘어 표시 비용이 커질 수 있다. 모든 source에 적용하거나 표시 성능까지 해결됐다고 판단하지 않는다. 경로 source에 한정한 수정 범위와 대량 표시 비용을 확인한 다음, 새 좌표 반영 시간과 응답 한도 비교를 다시 진행한다.

### 자료와 정리 상태

- 같은 진단 디렉터리의 `baseline-with-new-gps-retry/`: 전체 진행 기록·수신 ID·쓰기 결과·실패 판정.
- `new-gps-short-probe/`, `new-gps-map-diagnostic/`: 짧은 재현의 상세 보고서·좌표 검사·화면·지도 데이터 진단.
- `map-simplification-control/map-diagnostic.json`: 같은 좌표의 단순화 대조. 실제 픽셀 색 검사가 아니라 MapLibre의 화면 feature 조회 결과다.
- `prepare-preserved-writer.py`, `append-preserved-path.py`, `run-history.cjs`: 비공유 진단 도구. 별도 제품 테스트나 영구 실행 도구로 추가하지 않았다.

시험에서 좌표 18개·구간 3개를 의도적으로 추가했고 보존했다. 기존 자료를 삭제·재생성하지 않았다. 큰 응답 한도는 이번 후속 실행에서 적용하지 않았으며 제품 코드·영구 설정·커밋·푸시는 변경하지 않았다. 인증 임시 파일은 제거했고 시험 브라우저를 종료했다. Backend 전체 테스트·Frontend 빌드는 제품 변경이 없어 재실행하지 않았다.

종료 시 경로 481개·GPS 341,003개·구간 57,086개다. 시험에서 추가한 행을 제외한 기존 GPS·구간의 모든 컬럼 해시는 인증 준비 전과 일치했다. 새 좌표를 추가한 경로의 버전 등은 변경되므로 전체 경로 테이블 무변경으로 표현하지 않는다. Backend health는 `UP`이었다. 문서 링크·TODO 형식·진단 코드 문법, 기존 수신 ID 전수 일치, 신규 좌표의 지도 source 해시 일치, 같은 입력의 단순화 대조를 검사했다. 제품의 새 좌표 **표시** 검사는 실패 상태로 남긴다.

## 경로 source에 한정한 수정과 로컬 검증

`SearchMapCanvas.tsx`의 경로 source에만 `tolerance: 0`을 지정했다. 짧은 구간이 단순화 단계에서 통째로 사라지는 것을 막으며, 다른 지도 도형의 설정과 원본 좌표는 바꾸지 않는다. ponytail 원칙에 따라 기존 source 생성 함수 한 곳을 수정하고 새 모듈·설정 항목·의존성은 추가하지 않았다.

`SearchMapCanvas.test.ts`에서 실제 source 생성 함수의 옵션을 MapLibre와 설치된 타일 변환기에 전달했다. 수정 전 zoom 10에서 구간 1개가 사라져 실패했고, 수정 후 zoom 10·11·15에서 해당 구간 보존과 다른 source의 설정 유지를 확인했다.

- `cd frontend && npm test && npm run typecheck && npm run build`: 61개 파일·321개 테스트, 타입 검사, 빌드 통과. 기존 큰 번들 경고는 남아 있다.
- Backend는 변경하지 않아 테스트를 재실행하지 않았다. 커밋·푸시·배포·서버 설정 변경·새 GPS 저장도 하지 않았다.

### 대량 도형의 표시와 처리 비용

로컬 Chrome·MapLibre·SwiftShader에서 합성 구간 56,160개(468 × 120), 구간당 6좌표, zoom 약 10.921, 1440×900 조건으로 비교했다. 기본값과 수정값을 번갈아 실행했고, 예열 1회씩을 제외한 각 3회의 중앙값이다. 첫 처리는 source·레이어 추가부터 지도 `idle`까지, 추가 처리는 `updateData`로 새 구간 1개를 넣은 뒤 `idle`까지 측정했다.

| 설정 | 표시된 고유 구간 | 새 구간 표시 | 첫 처리 중앙값 | 추가 처리 중앙값 |
|---|---:|---|---:|---:|
| 기본 `0.375` | 0 / 56,160 | 실패 | 551ms | 311ms |
| 수정 `0` | 56,160 / 56,160 | 통과 | 2,093ms | 2,246ms |

모든 실행에서 source 수신 개수·입력 보존·추가 좌표 일치 검사가 통과했다. 표시 여부는 MapLibre의 화면 feature 조회로 확인했으며 픽셀 색 검사는 아니다. 기본값이 빠른 것은 표시해야 할 선이 사라진 상태이므로 유효한 성능 개선으로 볼 수 없다. 반대로 수정값의 약 2.25초도 현장 사용 목표를 충족했다고 판단하지 않는다.

이 비교는 배경 타일 없는 독립 지도에 합성 데이터를 넣은 라이브러리 수준 검사다. 실제 상황판의 HTTP·React·SSE·사용자 GPU·초기 로딩 중 연속 갱신 비용을 포함하지 않는다. 로컬 비공유 `_workspace/path-render-fix-20261008.Xu3zcf/`에 `compare-rendering.cjs`와 `render-comparison.json`을 보존하고 브라우저·로컬 HTTP 서버를 종료했다.

**표시 누락은 로컬 수정·회귀 검사까지 완료했고, 실제 배포본 재검증은 남았다.** 전체 이력 수신에 약 16분이 걸린 문제는 해결하지 않았다. 배포 후 기존·신규 구간 표시를 먼저 확인하고, 응답 한도별 시간 비교와 GPS 범위 일괄 조회의 실제 Mapper·Service 구현을 이어간다.

후속 [Jenkins #62 배포·실제 상황판 검사](search-path-short-segment-deployment-20261008.md)에서 대상 경로의 수신 구간 9개와 새 좌표의 표시·DB 일치 검사가 통과했다. 기존 원본 GPS·구간도 보존했다. 전체 이력 로딩과 응답 한도 비교는 여전히 미완료다.
