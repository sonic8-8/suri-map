# 수색 경로 변경분 지도 반영 검증

2026-10-08 로컬 제품 코드·브라우저 검증 결과다. [앞선 변환 재사용·비교 실험](search-path-browser-stage-cost-20261007.md)에 이어 실제 상황판의 지도 source 갱신을 변경했다. 서버에는 아직 배포하지 않았다.

## 무엇을 바꿨는가

기존에는 일부 경로만 바뀌어도 지도에 전체 경로 도형을 다시 전달했다. 이제 변경하지 않은 도형을 재사용하고, 마지막으로 worker가 반영한 자료와 비교해 추가·수정·삭제분을 전달한다.

- `movementPathSource.ts`: worker 처리 중에는 최신 자료 하나만 보관한다. 반영 완료 후 그 자료와 비교하므로 중간 응답마다 전체 작업을 쌓지 않는다.
- 최초 반영·계측 전환·재사용할 도형이 없는 경우에는 전체를 전달한다. 삭제 ID 목록보다 남길 도형 수가 적을 때도 전체 전달을 사용한다. 전체 비우기는 `removeAll`로 처리한다.
- worker 오류가 나면 증분 기준을 버리고 최신 전체 자료로 한 번 복구한다. 같은 자료의 반복 실패는 로그를 남기고 무한 재시도하지 않는다.
- `boardMapFeatures.ts`: 변하지 않은 도형을 재사용한다. 경로·구간 순서를 `drawOrder`로 명시해 부분 반영 후에도 겹쳐 그리는 순서를 유지한다. 한 경로의 구간 수가 달라지면 그 경로의 기존 구간도 순서 값 갱신 대상이다.
- `SearchMapCanvas.tsx`: 실제 경로 source에 위 처리를 연결하고 선 레이어에 정렬 키를 적용했다. 업무폰 현재 위치 선택 규칙과 현재 위치 source의 전체 교체는 유지한다.
- `boardMeasurement.ts`: 아직 표시되지 않은 이전 묶음의 계측을 보존한다. 부분 갱신에서 실제로 교체·삭제한 도형만 이전 관찰 대상에서 제외한다.

공개 API·DB·좌표 연결 규칙은 바꾸지 않았다. 새 라이브러리는 추가하지 않았다.

## 무엇을 비교했는가

Node 22.22, Chrome 147, MapLibre 5.24, TanStack Query 5.100.6으로 실행했다. 제품의 경로 변환·도형 생성·source 갱신·계측 함수를 직접 불러왔다.

- 합성 경로 481개 × 기존 구간 120개 = 57,720구간. 구간마다 좌표 6개다.
- 매회 서로 다른 80개 경로 앞에 오래된 구간을 하나씩 추가했다. 5회 중 첫 2회를 제외한 3회 평균이다.
- 전체 교체는 전체 자료 변환 후 `setData`, 변경분 방식은 제품의 재사용 변환과 source 갱신 함수를 사용했다. 두 방식 모두 현재 위치 source도 갱신했다.
- 화면은 800×600, 확대 수준 17, 선 레이어 하나와 현재 위치 원 레이어 하나다. SwiftShader와 픽셀 비교용 `preserveDrawingBuffer`를 사용했다.
- 아래 시간은 화면용 자료 조립 시작부터 지도 `idle`까지다. HTTP·페이지 응답 파싱·Query 캐시 병합·검증용 source 조회·픽셀 해시 계산은 포함하지 않는다.

| 화면 계측 | 전체 교체 | 변경분 반영 | 감소율 |
|---|---:|---:|---:|
| 끔 | 1,389.37ms | 888.17ms | 36.1% |
| 켬 | 1,578.33ms | 997.03ms | 36.8% |

빌드·테스트를 동시에 실행하지 않은 최종 역순 비교의 값이다. 조건별 표본이 3개인 로컬 진단이므로 일반적인 성능 보장이나 실제 상황판 전체 로딩 개선율로 해석하지 않는다.

## 정확성·회귀 검증

초기 표시, 과거 구간 추가 5회, 좌표·이동 수단·버전 수정, 구간 삭제, 최신성·색상 변경, worker 처리 중 연속 갱신, 범례 필터·복원, 차수 비우기·복원, 사건 초기화의 15상태를 비교했다.

- 계측 켜기/끄기 × 전체/부분 반영에서 경로·현재 위치 source 내용을 검사했다. 총 120회 고유 ID·geometry·제품 속성이 기준 전체 조립 결과와 일치했다. 계측 revision과 정렬용 속성은 값 비교에서 제외하고 각각 따로 검사했다.
- 계측 켜기/끄기의 15상태씩 총 30쌍에서 실제 canvas 픽셀 해시가 전체 교체와 일치했다. 부분 방식의 정렬 키 순서도 기준 배열 순서와 일치했다.
- 계측을 켠 두 방식에서 수정 좌표가 화면 안에 있고 실제 해당 좌표에 표시됐다는 계측 결과를 확인했다. 표시 기록의 revision이 제출 기록에 존재하는지도 검사했다.
- MapLibre 오류는 0건이었다. worker 실패 복구는 대역 기반 단위 테스트로 검증했으며 실제 브라우저 worker 오류를 주입하지는 않았다.
- `npm run typecheck && npm run build && npm test` 통과: 61파일·320검사. 빌드의 500kB 초과 청크 경고는 남아 있다.
- source 준비 전 갱신, worker 처리 중 연속 갱신, 전체 초기화, 실패 복구, 도형 재사용·정렬, 미표시 묶음 계측 보존을 회귀 검사에 포함했다.

첫 브라우저 실행은 파일 포맷 변경에 따른 Vite 재로딩으로 중단됐다. 진단 서버의 HMR을 끄고 다시 실행했다. 다음 정순 실행은 정확성 검사를 통과했지만 일부 구간에 빌드·테스트가 겹쳐 성능 표에서 제외했다. 최종 역순 실행은 정확성 검사와 수정 좌표 계측을 모두 통과했다.

## 남은 확인

실제 React 상황판 전체·HTTP 반복 요청·실제 지도 레이어 전체를 연결한 시험은 아니다. 제품의 사건/차수 전환 UI나 지도 style 교체도 이 브라우저 진단으로 검증했다고 보지 않는다. Backend·Android 검증과 서버 배포는 실행하지 않았다.

배포 후 동일 DB 데이터에서 첫 표시·전체 이력 완료·페이지 요청 간격을 다시 측정해야 한다. 기존 전체 로딩 17분 49.9초가 얼마나 줄었는지는 아직 모른다. 페이지 한도에 따른 요청 비용 비교도 별도로 남아 있다.
