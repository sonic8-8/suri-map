# 독립 Chrome의 전체 수색 경로 로딩 측정

2026-10-08 [문제 해결 기록 36](../problem-solving-records/36-slow-paged-search-path-display.md)의 후속 검증이다. **첫 경로는 3.62초에 렌더링됐지만, 57,083구간의 전체 이력 수신, 캐시 반영에는 12분 14.54초가 걸렸다.** 수신 구간 ID는 DB와 모두 일치했다. 전체 로딩 지연은 남아 있으며, 성능 문제가 해결됐다고 판단하지 않는다.

## 시험 조건

- Jenkins #60의 `3cd0dc3e`, 공개 서버의 `index-DewxlEbG.js`를 확인했다. 제품 코드·페이지 한도·서버 설정은 변경하지 않았다.
- 시험 지휘 계정으로 사건 1개·수색 차수 1개의 경로 481개, GPS 340,985개, 구간 57,083개를 조회했다. 새 GPS·마커 전송과 동시 사용자 부하는 없다.
- WSL의 독립 Headless Chrome `147.0.7727.57`, 화면 1440×900·DPR 1, SwiftShader 허용 옵션으로 실행했다. 서버는 Hetzner App이고 브라우저는 로컬 실행이다.
- 새 브라우저 세션에서 제품 계측을 켰다. 사건 목록의 3초 검사에서 프레임 콜백 181회·긴 작업 0건을 확인한 뒤 상황판을 열었다. [Aside 실행 환경의 초기화 대기](search-path-map-initialization-diagnosis-20261008.md)는 재현되지 않았다.
- 실제 UI가 보내는 HTTP 응답에서 구간 ID를 수집했다. 추가 조회를 보내지는 않았지만 응답 복사, 집계와 제품 계측의 비용은 포함된다. 따라서 관찰 방식이 다른 결과와는 직접 비교하지 않는다.
- 화면 캡처는 전체 측정이 끝난 뒤에 수행했다. 초기 지도 활성화를 위해 캡처를 반복하지 않았다.

단일 실행이다. 이전 Aside 관측과 OS·브라우저·렌더링 조건이 다르므로 개선율을 계산하지 않는다. 이 시간은 현재 시험 환경의 관측값이지 모든 사용자 환경의 응답 시간 보장이 아니다.

## 완료 시간과 정확성

시작점은 사건 목록에서 상황판 열기를 실행하기 직전이다.

| 항목 | 결과 |
|---|---:|
| 첫 페이지 수신·캐시 반영 | 2.182초 |
| 지도에 첫 경로 전달 | 3.482초 |
| 첫 경로 렌더링 계측 | 3.620초 |
| 전체 이력 수신·캐시 반영 | 734.542초 — 12분 14.54초 |
| 완료한 경로 조회 | 793건: 이력 786건·변경분 7건 |
| HTTP 상태 / 조회 실패 | 전부 200 / 0건 |
| 경로 조회 최대 동시 실행 | 1건 |
| 수신 구간 고유 ID | 57,083개, DB 목록과 완전 일치 |
| 지도에 전달한 구간 ID 합집합 | 57,083개, DB 목록과 완전 일치 |
| 일부 경로만 표시 중이라는 로딩 문구 | 전체 완료 후 사라짐 |
| 수집된 JavaScript·응답 수집 오류 | 0건 |

DB의 같은 사건·차수에서 구간 ID 목록을 측정 전후 조회했다. 두 DB 목록과 브라우저 수신 목록을 정렬해 배열 전체를 비교했다. 건수만 맞춘 검사가 아니다. 수신 목록 SHA-256은 `e3da6fab1ce32fe39ed071d6ebb5cfeddf35a487f577ef26cc30ebb4b2244271`이다(정렬한 UUID를 줄바꿈으로 연결하고 마지막 줄바꿈 포함).

지도 전달 ID 합집합은 모든 구간을 전달했다는 확인이다. 종료 순간 지도 source의 내용 전체, 화면 밖을 포함한 모든 도형의 좌표·픽셀 일치까지 검사한 것은 아니다. 734.542초 역시 마지막 구간의 실제 렌더링 완료 시간이 아니라 수신·캐시 반영 완료 시간이다.

## 어느 구간에 시간이 쌓였는가

브라우저 Resource Timing의 요청 시작부터 응답 수신 완료까지를 HTTP 시간으로, 이전 응답 완료부터 다음 요청 시작까지를 요청 사이 간격으로 집계했다. 제품의 페이지 시작·완료 기록과 Resource Timing을 순서·종류·시간 범위로 대조한 뒤 계산했다.

| 구간 | 합계 |
|---|---:|
| HTTP 시간 793건 | 559.310초, 요청당 평균 705ms |
| 요청 사이 간격 792개 | 173.745초, 간격당 평균 약 219ms |
| 첫 경로 요청 시작부터 마지막 응답 수신까지 | 733.055초 |

HTTP 시간에는 네트워크·프록시·서버 처리 등이 포함된다. 그중 요청 전송 시작부터 첫 응답 바이트까지는 합계 555.496초, 이후 응답 수신은 합계 2.976초였다. 이를 DB 실행 시간이나 서버 CPU 시간으로 해석하지 않는다.

요청 사이 간격도 순수 JavaScript 실행 시간은 아니다. 다만 응답 수신 완료부터 제품의 파싱·병합·캐시 갱신 완료 기록까지 평균 219ms가 걸려, 대부분의 간격이 어느 처리 범위에 있는지는 확인했다. 그 안에서 어떤 함수가 시간을 쓰는지는 별도 프로파일링 대상이다.

| 요청 순서 | HTTP 평균 | 응답 수신 → 파싱·캐시 갱신 완료 평균 |
|---|---:|---:|
| 1–198 | 772ms | 98ms |
| 199–396 | 702ms | 158ms |
| 397–594 | 687ms | 312ms |
| 595–793 | 661ms | 305ms |

HTTP 평균은 후반에 증가하지 않았지만, 응답 후 처리 구간은 초반보다 길었다. 50ms 이상 긴 메인 스레드 작업은 6,738건·총 643.691초로 관측됐다. 이 작업은 HTTP 대기와 겹쳐 실행되므로 위 시간 합계에 다시 더하지 않는다. SwiftShader 허용 Headless 실행과 계측 비용이 포함돼 있어, 이 값만으로 실제 사용자 PC의 CPU 병목이나 특정 함수의 책임을 확정하지 않는다.

## 마지막 85구간에 반복된 조회

마지막 85구간은 73번에 나눠 받았다. 요청당 2구간인 경우 12번, 1구간인 경우 61번이었다. 이 73건의 첫 요청 시작부터 마지막 응답 수신까지 **65.560초**가 걸렸고, 그중 HTTP 시간 합계는 45.857초였다.

경로당 한 번에 1구간을 받는 현재 설정에서 마지막까지 이력이 남은 소수 경로를 작게 나눠 조회하는 비용이 실제로 관측됐다. 한도를 늘리면 요청 수는 줄일 수 있지만, 응답마다 처리할 데이터가 커진다. 경로당 한도와 응답 전체 한도를 한 번에 하나씩 바꿔 비교해야 한다. **경로당 한도만 늘려도 응답당 80구간 한도가 남으면 최소 714번의 조회가 필요하다.** 다른 한도를 함께 바꾸거나 새 값을 운영 기본값으로 확정하지 않는다.

[후속 원인 분석](search-path-page-delay-diagnosis-20261008.md)에서 짧은 API 재현, 반복되는 전체 경로 준비 상태 검사, Headless 브라우저의 그래픽 대기를 분리했다. 긴 메인 스레드 작업 전체를 JavaScript 계산 시간으로 해석하지 않는다.

## 검증 범위와 종료 상태

- 실제 차수·사건·지도 style 전환, 새 GPS 반영, 동시 상황판 부하는 미실행이다. 이 검증을 완료한 것으로 처리하지 않았다.
- 시험 Chrome은 종료했고 시험 계정 인증 정보의 임시 파일 사본도 삭제했다. Backend health는 UP이다.
- 측정 전후 경로·GPS·구간 건수와 기존 fingerprint가 일치했다. 기존 fingerprint는 구간 추적 컬럼 3개를 제외하며, 위치 조회 감사 기록을 포함한 DB 전체 무변경 검사는 아니다.
- 제품 코드 변경·커밋·푸시·배포는 없었다. 진단 스크립트 구문·실행 검사는 통과했고 제품 테스트·빌드는 재실행하지 않았다.

## 재검사 자료

당시 로컬에 아래 자료를 보존했다.

- `measure-history.cjs`: 시험 세션 파일을 인자로 받아 실제 화면을 열고, 전체 수신·지도 전달 ID·로딩 문구·DB 전후 ID를 검사한다. 성공 출력은 `PASS: history complete, partial label cleared, received/map-submitted IDs exactly match DB.`다.
- `history-report.json`, `expected-ids.json`, `received-ids.json`: 시간·ID 집계 원자료. 토큰과 원본 좌표 응답은 기록하지 않는다.
- `summarize.cjs`, `summary.json`: 요청과 Resource Timing 대응을 검사하고 구간별 비용을 집계한다.
- `history-completed.png`: 전체 완료 후 화면. 일부만 표시 중이라는 문구가 사라진 것을 확인했다.

당시 측정 스크립트는 저장소에 보존하지 않았다. 당시 실행에는 유효한 시험 세션과 새 결과 디렉터리가 필요했다. 완료 제한시간 25분은 이전 약 18분 관측보다 길게 둔 진단 중단 장치이며 서비스 합격 기준이 아니다.
