# 상황판 진입부터 전체 경로 지도 반영까지 줄인 근거와 실서버 측정

2026-10-19~20 기록이다. 고정 시험 사건(경로 481개, 구간 57,097개, 좌표 341,069개)에서 "상황판 열기" 클릭부터 전체 경로가 지도에 그려질 때까지를 줄였다. 이전 단계(최초 이력 한 번에 받기, fetch size)는 [2026-10-16 기록](search-path-initial-history-20261016.md)에 있다.

## 결과 요약

같은 측정 방법(아래 [브라우저 측정](#측정-방법))으로 잰 클릭부터 지도 idle까지다.

| 시점 | 커밋 | 클릭 → 그리기 끝 | 비고 |
|---|---|---:|---|
| 배포 전 | 6d2d1002 | 7.53초 | 1회 |
| 지도 도형 잇기 배포 후 | 557a53a4 | 6.10초 | 3회 중앙값 |
| 경로 조회 선시작 배포 직후 | 8835a657 | 5.30초 | 3회 중앙값, 배포 확인 27초 뒤 측정 |
| 같은 배포본 재측정 | 8835a657 | **4.65초** | 3회 중앙값(4.65, 4.41, 4.75초) |

- [경로 표시 목표](../features/situation-board.md#화면과-관측에서-남은-요구)의 "전체 이력 지도 반영 5초 이내"를 아직 판정하지 않았다. 목표는 사용자의 일반 Chrome 탭에서 전체 구간의 지도 반영과 렌더 확인까지를 재도록 정했다. 이 측정은 따로 띄운 Chrome에서 지도 idle까지이며 구간 ID 대조나 렌더 확인은 하지 않았다.
- 마지막 측정의 구성(중앙값): 경로 요청 시작 0.004초, 경로 응답 끝 2.68초, 응답 병합 끝 2.82초, 지도 반영 1.76초.

## 측정 방법

- **서버 안 요청:** 실서버 앱 컨테이너 안에서 `localhost:8080`으로 화면 첫 요청과 같은 본문의 `segments/query`를 보냈다. 서버 시간은 Prometheus `http_server_requests_seconds` 합계 차이다. 토큰은 표준 입력으로만 넘겼다.
- **브라우저 측정:** Windows Chrome 155를 임시 프로필과 개발자 도구 포트로 따로 띄워 실서버에 접속했다. 실제 GPU(Intel Iris Xe, D3D11), 화면 1640×990이다. 정식 SSO 화면으로 로그인하고 조회만 했으며, 측정 뒤 프로필 폴더를 지웠다. 데우기 1회 뒤 3회 쟀다.
  - 단계 표시는 제품의 측정 연결점(`__SURI_MAP_PATH_TRACE__`의 경로 페이지 이벤트, `__SURI_MAP_OBSERVER__.connect`로 받은 지도의 `load`, 경로 source의 `sourcedata`, `idle`)과 Resource Timing이다. 무거운 제품 계측(`__SURI_MAP_MEASUREMENT_ENABLED__`)은 켜지 않았다.
  - 일반 탭(Aside)에서도 1회 쟀다. 단계 시각이 따로 띄운 Chrome과 거의 같았다(클릭 → 그리기 끝 7.57초 대 7.53초). Aside 실행 환경은 CDP를 노출하지 않아 함수 단위 기록은 따로 띄운 Chrome에서 남겼다.
- WSL에서 실서버 DNS 조회가 약 11초 걸리는 현상이 있었다. 측정한 Windows Chrome은 이 영향을 받지 않는다.

## 1. 서버: 좌표를 범위마다 배열로 읽기 (6d2d1002)

- **원인:** 임시 계측(되돌림)으로 서버 안 첫 경로 조회 약 2.9초를 나눴다. 좌표 SQL이 1.86초였고, 그중 JDBC 행 수신 약 1.0초, MyBatis가 좌표 행마다 결과 객체를 만드는 데 약 0.9초였다. DB 실행과 전송만은 약 0.64초였다(psql, 같은 네트워크 경로). 앞선 숫자형 읽기(875eae82)는 열 해석 비용만 줄여 실서버에서 효과가 보이지 않았다.
- **변경:** `findBoardPointRuns`가 요청 범위마다 한 행으로 경도, 위도, 측정 시각(마이크로초) 배열을 `array_agg`로 돌려준다. 294247-01-01 이상이나 무한 시각이 있는 범위만 기존 좌표 행 SQL로 다시 읽는다. 응답 계약은 같다.
- **검증:** 로컬 비교에서 응답 JSON의 SHA-256이 변경 전과 같았다. Codex 검수 pass. 실서버 서버 안 요청은 3.12~3.24초에서 2.32~2.43초(데워진 상태)가 됐다. 브라우저 한 요청은 2.36~2.81초가 됐다(이전 4.05~4.49초).

## 2. 브라우저: 지도 경로 도형을 이어 붙이기 (557a53a4)

- **원인:** 응답 병합 뒤 지도 반영 약 3.8초는 기다림이 아니라 MapLibre 계산이었다(Chrome 성능 기록).
  - 메인 스레드 0.75초: 경로 도형 57,097개를 작업자로 넘기며 객체 전체를 훑는 처리 약 0.49초, React 경로 변환과 슬롯 조립 약 0.19초
  - 작업자: 받기, GC, 색인 0.76초, 이어서 타일 만들기 2.02초(벡터 타일 다시 쓰기 약 0.65초, 선 버퍼 약 0.81초)
- **비교 실험:** 실서버 경로 source 데이터를 저장해, 같은 Chrome과 같은 시점에서 모양만 바꿔 `setData`부터 idle까지 각 3회 쟀다.

  | 변형 | 도형 | 중앙값 |
  |---|---:|---:|
  | 그대로 | 57,097 | 4.20초 |
  | 읽는 곳이 없는 속성 제거 | 57,097 | 3.53초(그대로의 1회차 3.15초보다 모두 느려 효과 미확정) |
  | 속성 제거 + 같은 표시의 이웃 구간 잇기 | 810 | 1.57초 |

  그림은 zoom 11.1, 14, 16에서 픽셀로 비교했다. 그리기 순서 차이는 0픽셀이었다. 이어 붙이기의 차이는 구간마다 둥근 끝과 반투명 레이어가 이음점에서 겹쳐 칠해지던 선 가장자리 픽셀이다(큰 차이는 그려진 픽셀의 0.8~4.3%).
- **변경:** `createMovementPathFeatureMapper`가 같은 경로에서 표시 값이 같고 끝점이 이어지는 구간을 선 하나로 잇는다. 지도 도형에서 읽는 곳이 없는 속성 6개를 뺐다. 원본 값은 화면 경로 데이터와 API에 남는다([도형 단위 요구](../features/situation-board.md#화면과-관측에서-남은-요구)).
- **검증:** 실서버 데이터를 새 함수에 넣으면 실험과 같은 도형 810개가 나왔다. 481경로 끝에 구간이 붙는 증분 갱신에서 바뀐 도형 판정이 약 215ms에서 98ms로 줄었다(로컬 계산). Codex 검수 pass. 배포 후 응답 병합 뒤 지도 반영은 1.93초(3회 중앙값)였다.

## 3. 경로 조회를 상황판 응답과 동시에 시작하기 (8835a657)

- **원인:** 클릭 뒤 경로 첫 조회는 상황판 요청(경로 제외)의 응답이 끝난 0.955초에 나갔다. 경로 조회의 차수 ID를 상황판 응답에서만 얻었기 때문이다. 그 사이 메인 스레드는 거의 쉬었다.
- **비교 실험:** 앱의 경로 조회를 막고 같은 요청을 시점만 바꿔 각 3회 보냈다. 경로 응답 끝 중앙값이 3.65초(상황판 응답 뒤)에서 2.73초(클릭과 동시)가 됐다. 겹쳐 보내도 경로 서버 대기(2.29초 대 2.31초)와 상황판 응답 끝이 늘지 않았다.
- **변경:** 사건 목록 item에 `activeOpId`를 추가했다([API](../api/api-spec.md#get-apiincidents)). 목록의 "상황판 열기"가 이동 상태로 값을 넘기고, 상황판 응답 전에만 이 차수로 경로 조회를 시작한다. 상황판이 같은 차수를 주면 같은 조회를 이어 쓰고, 다르면 상황판 차수로 다시 조회한다. 주소를 직접 연 경우는 이전처럼 상황판 응답을 기다린다.
- **검증:** Backend 전체 1,429개 중 12개 실패(기존과 같은 로컬 HTTP 환경 원인), PostgreSQL 통합 테스트 통과. Frontend 346개 통과. Codex 검수 pass. 배포 후 경로 요청이 클릭 뒤 4~10ms에 나갔고, 3회 모두 목록의 차수가 전달됐다.

## 남은 확인

- 목표 문서의 조건(일반 Chrome 탭, 진입 클릭과 전체 구간 렌더 확인을 같은 브라우저 시계로 기록)으로 다시 재야 "전체 이력 지도 반영" 목표를 판정할 수 있다.
- 새 좌표 반영(목표 3초)은 이번 변경 뒤 재지 않았다.
- 배포 직후 측정(5.30초)에서는 경로 응답이 1회 약 1초 늦었다. 서버가 덜 데워진 영향으로 보이나 확인하지 않았다.
- 남은 큰 구간은 경로 서버 처리(약 2.3초)와 지도 반영(약 1.8초)이다.
