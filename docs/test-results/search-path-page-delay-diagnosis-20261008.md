# 수색 경로 페이지 조회의 지연 원인 분석

2026-10-08 [문제 해결 기록 36](../problem-solving-records/36-slow-paged-search-path-display.md)의 원인을 분석했다. [전체 이력 734.542초 측정](search-path-chrome-history-20261008.md)을 기준으로, 같은 배포본과 데이터를 짧게 반복 조회했다. **작은 응답을 수백 번 순서대로 받고, 요청마다 전체 경로의 조회 준비 상태를 다시 검사하는 비용을 확인했다.** 제품 코드, 서버 설정은 변경하지 않았다.

## 확인한 원인

### 작은 응답을 순서대로 받으며 왕복 시간이 누적된다

응답당 최대 80구간이므로 57,083구간을 받으려면 구간 조회만 최소 714번 필요하다. 실제 전체 측정은 구간 조회 786번·변경분 조회 7번이었다. HTTP 시간 합계는 559.310초, 응답 완료부터 다음 요청까지의 간격은 173.745초였다. 각각 서버 처리 시간과 JavaScript 계산 시간만을 뜻하지는 않는다.

- Backend는 경로를 한 번씩 순회하며 경로당 최대 1구간만 담는다. 응답 전체 한도에 여유가 남아도 같은 경로의 나머지 구간을 더 담지 않는다. [SearchPathBoardService](../../backend/src/main/java/com/surimap/api/service/path/SearchPathBoardService.java)
- Frontend는 응답을 받아 파싱·병합·캐시 갱신한 뒤 다음 요청을 보낸다. 실제 측정에서도 동시 요청은 1개였다. [searchPathPagesApi](../../frontend/src/features/path/api/searchPathPagesApi.ts)
- 마지막 85구간에 73번의 조회와 65.560초가 필요했다. 남은 경로가 적어질수록 경로당 1구간 한도가 응답의 빈자리를 늘린다.

**경로당 한도만 올려도 전체 지연이 해결되지는 않는다.** 응답 전체의 80구간 한도가 남아 있으면 여전히 최소 714번의 조회가 필요하다. 두 한도의 효과를 구분해서 비교해야 한다.

### 한 구간을 받을 때도 전체 경로의 준비 상태를 검사한다

`queryPage()`는 요청마다 `hasUnpreparedBoardPaths()`를 호출한다. 이 SQL은 선택 범위의 경로에 GPS·구간이 있는지, 구간의 순서·변경 버전이 준비돼 있는지 확인한다. 마지막 한 경로의 한 구간을 받을 때도 검사 범위는 줄지 않는다. [Mapper SQL](../../backend/src/main/resources/mapper/path/SearchPathMapper.xml)

실제 App DB에서 같은 입력으로 `EXPLAIN (ANALYZE, BUFFERS)`를 3회 실행했다. 읽기 전용 트랜잭션과 시간 제한을 사용했으며 통계 초기화·확장 설치는 하지 않았다.

| 검사·조회 | 3회 실행 시간 | 확인 내용 |
|---|---:|---|
| 전체 경로 준비 상태 검사 | 56.956–90.391ms | 481경로의 구간 검사 반복, 공유 버퍼 hit 64,997·read 0 |
| 같은 검사를 남은 경로 1개로 제한한 진단 SQL | 0.357–0.954ms | 버퍼 hit 216. 반복 검사 범위의 비용을 분리한 대조군 |
| 경로 메타데이터 | 1.441–2.058ms | 481경로 |
| 조회 진행 위치 검사 | 1.741–2.417ms | 481개 경로의 커서 |
| 남은 구간 선택 | 0.065–0.103ms | 1구간과 다음 구간 존재 여부 조회 |

검사 범위를 줄이는 대조 SQL은 원인 확인용이다. 전체 검사 제거가 안전하다는 검증은 아니며, 데이터 누락·미준비 상태를 발견하는 기존 동작을 보존할 방법은 별도로 정해야 한다. 위 값은 SQL 단독 측정값이지 전체 HTTP 시간의 정확한 분해 결과가 아니다.

또한 현재 코드는 응답에 담을 경로별로 구간을 조회하고, 구간별로 GPS를 다시 조회한다. 경로 80개에서 1구간씩 반환하면 이 두 종류의 Mapper 호출만 160회다. 호출 수는 코드에서 확인했지만 각각의 누적 시간·일괄 조회 효과는 이번에 측정하지 않았다.

### 브라우저의 긴 작업에는 그래픽 처리 대기가 포함돼 있다

실제 상황판의 25번째 페이지 완료 후 15초 동안 Chrome trace를 수집했다. 실행기는 기존 전체 측정과 같은 WSL Headless Chrome이며, GPU 정보에서 SwiftShader와 소프트웨어 합성을 확인했다.

| 15초 표본 | 지도 표시 | 지도 canvas만 숨긴 진단 대조 |
|---|---:|---:|
| 메인 스레드 작업 경과 시간 | 11.241초 | 2.457초 |
| 그 작업의 스레드 CPU 시간 | 1.560초 | 2.202초 |
| 그래픽 명령 완료 대기 | 9.632초 | 0초 |

표시 상태의 trace에서 `Commit → LayerTreeHost::DoUpdateLayers → GLES2::ReadPixels → WaitForGetOffset` 대기를 확인했다. 여기서 `Commit`은 React가 아니라 브라우저의 화면 합성 과정이다. [Chromium 구현](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/cc/trees/proxy_main.cc)

지도만 숨기자 해당 대기가 없어졌다. 따라서 이 실행기의 긴 작업 시간을 전부 경로 병합·캐시 갱신의 계산 비용으로 해석하면 안 된다. 숨김 처리는 원인 분리용이며 제품 수정이나 성능 개선안이 아니다. 초반의 짧은 표본이므로 12분 전체 실행의 대기 비율이나 실제 사용자 PC의 비용으로 확대 해석하지 않는다. 누적 후반의 JavaScript 비용은 아직 분리하지 못했다.

## 짧은 재현과 HTTP 대조

같은 사건·차수의 481경로를 유지하되, 마지막 한 경로에 4구간만 남은 진행 상태로 실제 배포 API를 호출했다. 지도는 열지 않았다. 두 실행 모두 200 응답으로 1구간씩 4번 받았으며, 각각 2.558초·3.102초가 걸렸다.

```text
node _workspace/path-delay-diagnosis-20261008.WGWXUU/reproduce-tail.cjs <시험 세션 JSON>
RED: four remaining segments require four serial HTTP round trips.
```

이 검사는 관찰된 1구간씩 반복 요청하는 패턴에 실패한다. 합의되지 않은 목표 시간을 합격선으로 만든 검사가 아니다. 요청은 모두 조회용이며 GPS·마커를 전송하지 않았다.

같은 마지막 구간 요청을 공개 URL의 Chrome에서 실행하면 요청당 584.691–906.528ms, App 서버 내부의 Backend 주소에서 실행하면 96.170–125.829ms였다. 서버 내부의 첫 80구간 요청은 121.148–149.864ms였다. 외부 왕복이 포함된 HTTP 시간을 DB 시간으로 볼 수 없다는 대조다. 클라이언트·접속 경로가 다르므로 차이를 순수 네트워크 지연으로 단정하거나 전체 측정에 그대로 대입하지 않는다.

## 다음 확인과 보존 자료

후속 [남은 4구간의 한도 1→4→1 대조](search-path-tail-page-limit-comparison-20261008.md)에서 요청 수 감소와 구간·좌표 일치를 확인했다. 전체 이력 표시와 새 좌표 반영은 아래 순서로 별도 검증한다.

[네 가설 대조](search-path-four-hypotheses-20261008.md)에서는 큰 응답의 전체 이력 수신, 준비 상태 SQL 판정·비용, GPS 일괄 조회와 후반 브라우저 비용을 비교했다. 새 GPS 반영과 제품 적용 후 검증은 남아 있다.

1. 동일 브라우저·데이터에서 경로당 한도와 응답 전체 한도를 각각 바꿔 요청 수·첫 표시·전체 완료·수신 ID 일치를 비교한다. 한 번에 한 조건만 바꾼다.
2. 준비 상태 검사의 반복 범위와 구간별 GPS 조회를 줄일 방법을 검토한다. 검사 생략이나 캐시 도입을 먼저 확정하지 않는다.
3. 실제 표시를 유지한 브라우저에서 누적 후반의 계산 비용을 분리한다. 소프트웨어 그래픽 대기를 제품 JavaScript 병목으로 오인하지 않는다.

로컬 비공유 `_workspace/path-delay-diagnosis-20261008.WGWXUU/`에 보존했다. 진단용 파일이며 제품 테스트에 추가하지 않았다.

- API 재현: `prepare-tail.cjs`, `reproduce-tail.cjs`, `tail-*.json`.
- 서버·DB 대조: `compare-origin.cjs`, `database.cjs`, `explain-page.cjs`, `origin-results.json`, `sql-plans.json`.
- 브라우저: `profile-board.cjs`, CPU profile·Chrome trace·GPU 정보.

종료 후 Backend health는 UP이며 경로 481개·GPS 340,985개·구간 57,083개의 건수와 기존 fingerprint가 진단 전과 일치했다. 이 fingerprint는 구간 추적 컬럼 3개를 제외하며, 조회 감사 기록 등 DB 전체 무변경을 뜻하지 않는다. 인증 정보 임시 사본은 삭제했고 시험 탭과 Chrome은 종료했다. 제품 코드·설정 변경, 커밋·푸시·배포는 없으며 제품 테스트·빌드는 재실행하지 않았다.
