# 상황판 경로 페이지 조회 Backend 전환

2026-10-07 Hetzner App 서버에서 Backend·웹·mock-112 배포를 마치고 외부 접근을 재개했다. DB 보완·원본 보존·인증된 HTTP 조회를 확인했다. **브라우저 읽기 검사는 부분 결과다. 전체 이력 완료·새 좌표 반영·부하는 검증하지 않았다.**

## 전환 순서

1. 기존 시험 계정으로 웹 로그인과 사건 목록을 확인했다.
2. 외부 API를 전달하는 수리맵 Frontend와 기존 Backend·mock-112를 중지했다. 공개 API 502, DB의 다른 진행 중 트랜잭션·prepared transaction 없음 확인 후 최종 백업을 생성했다.
3. 외부 네트워크가 없는 임시 PostgreSQL에 백업을 실제 복원했다. 전체 public 테이블의 건수·내용 해시가 백업 전 원본과 일치했다. 검사용 DB만 종료·제거하고 백업은 서버에 보존했다.
4. [합의한 조회 시험 설정](../api/search-path-pages.md#시험-한도와-활성화)을 적용하고 Jenkins #58의 첫 승인을 진행했다.
5. 아래 파일 소유권 문제를 수정한 뒤, 승인받은 Backend 배포 명령을 `deploy` 계정으로 직접 재실행했다. 새 Backend의 Flyway·health·원본 보존·HTTP를 검사했다.

## 전환 도구에서 발견한 문제

환경 파일을 설치할 때 기존 `deploy:docker` 소유권을 보존하지 않아 `root:root`, 권한 600이 됐다. Jenkins #58은 `.env: permission denied`로 Backend 시작 전에 실패했다. 이 시점에는 migration이 실행되지 않았다.

`deploy` 계정의 Compose 설정 검사로 같은 실패를 재현했다. 백업 파일을 기준으로 소유권만 복구하자 같은 검사가 통과했다. 전환 도구에 소유권 보존과 실제 배포 계정의 설정 검사를 추가했다. 파일의 비공개 권한 600은 유지했다.

Jenkins #58은 실패 상태 그대로다. 실제 배포 성공을 Jenkins 성공으로 기록하지 않는다. Backend 검증 후 사용자 진행 요청에 따라 `deploy` 계정으로 파이프라인의 웹 배포 명령을 직접 실행했다. Jenkins의 두 번째 승인 단계가 실행된 것은 아니다.

## 웹 배포와 브라우저 읽기 검사

05:13:52 KST에 새 Frontend(`e12330b39f3f…`)·mock-112(`b0b9cb9b7295…`)를 시작했다. 검증한 Backend의 이미지·시작 시각은 유지했다. 공개 주소 HTTP 200, mock-112 healthy, 기존 지휘 계정 SSO·사건 목록·지도 타일 표시를 확인했다.

실제 브라우저 1개에서 기존 계측을 켜고 05:15:14.560 KST부터 상황판을 관찰했다. 대상은 현재 차수의 기존 경로 481개·구간 57,083개다. 그 안에 이전 468대 × 30분 시험 입력이 포함되며, 순수한 새 468대 쓰기 시험은 아니다.

응답당 80구간이면 이 데이터 전체를 받는 데 구간 조회만 최소 714건이 필요하다. 339건에서 받은 27,120구간과 별도 변경분 7건을 확인했다. 이 시험값을 운영에 적절한 값으로 확정하지 않는다.

기록 시점까지 `path_page_failed`와 브라우저 `error` 이벤트는 0건이었다. 그러나 전체 이력 완료는 확인하지 못했다. 화면과 측정치를 보존한 뒤 계측을 끄고 사건 목록으로 이동해 읽기 검사를 종료했다. **관찰을 중단한 것이며 HTTP timeout·최종 완료 시간·제품 SLA 실패로 해석하지 않는다.** 새 쓰기·본 부하로 넘어가지 않았다.

종료 후 경로 요청 누적 건수가 더 늘지 않음을 확인했다. Backend health UP과 경로·구간·GPS 원본 해시 일치도 다시 확인했다.

첫 데이터 수신과 지도 표시 사이의 지연, 페이지 수 증가와 지도 재전달 비용을 구분해 진단할 필요가 있다. 기존 계측의 `map_data_submitted` 1,740건·`map_update_replaced` 1,734건은 모든 계측 지도 source의 합계다. 이 값만으로 지도 누락이나 원인을 확정하지 않는다. 지도에 전달한 마지막 경로 feature 수는 27,120개였지만 전체 렌더링을 검증한 것은 아니다. 계측 오버헤드·지도 초기화·화면 범위 영향도 아직 분리하지 않았다.

## 저장한 HTTP 시간 기록의 분리

같은 관찰의 완료된 경로 조회 346건을 시작 시각순으로 정렬했다. 첫 요청 시작부터 마지막 완료까지 453.399초 중 HTTP 요청 시작부터 응답 완료까지는 합계 303.858초, 응답 완료부터 다음 요청 시작까지는 합계 149.541초였다. 완료된 요청끼리는 겹치지 않았다. HTTP 시간에는 서버 처리 외 네트워크·전송 등이 포함되므로 DB 실행 시간으로 해석하지 않는다.

| 구간 | HTTP 평균 | 응답 완료 후 다음 요청까지 평균 |
|---|---:|---:|
| 처음 50건 | 724.6ms | 20.3ms |
| 마지막 50건 | 944.0ms | 1,028.8ms |

각 묶음의 요청 사이 간격은 내부 49개만 비교했다. 시간이 흐르면서 응답 사이 간격이 커졌지만, 이 간격을 모두 지도 처리나 CPU 사용 시간으로 단정할 수는 없다. 데이터 병합·화면 갱신·계측·브라우저 스케줄링 영향을 분리해야 한다. 한 번의 기록을 앞뒤로 나눈 관찰이며 통제된 성능 비교가 아니다.

이 분석은 저장한 기록을 다시 집계한 것이며 새 브라우저 실행이나 재현 테스트가 아니다. 재실행 명령은 `node _workspace/path-pages-web-20261007.uzmPgh/analyze-timings.cjs`다. 완료 요청 수와 계측 건수 일치·완료 요청 간 비중첩 검사를 통과했다. 지연 현상과 미확인 원인은 [로컬 20번](../issues/local/20-slow-paged-search-path-display.md)에 기록했다.

## 남은 작업

- 웹과 mock-112는 실행 중이고 외부 접근을 재개했다. Jenkins #58은 여전히 실패 기록이다.
- 페이지 요청 수·첫 지도 표시 지연·반복 지도 갱신 비용을 분리 진단한다. 시험 한도나 제품 코드는 이번 검사 중 변경하지 않았다.
- 그 뒤 전체 이력 완료, 차수 전환, 새 좌표 반영과 재접속을 검증한다.
- Jenkins 재실행 시 첫·두 번째 승인을 다시 확인한다. #58을 성공 처리하거나 실패 단계를 통과한 것으로 가정하지 않는다.
- 실제 화면 측정 후 HTTP 제한시간과 후속 부하 조건을 결정한다.

비밀값을 제외한 실행 기록과 전환 도구는 로컬 `_workspace/path-pages-cutover-20261007.rQY87B/`에, 최종 DB 백업은 App의 `/srv/apps/suri-map/backups/path-pages-final.h3twqC/snapshot.dump`에 보존했다. 백업 크기는 14,340,034바이트, SHA-256은 `1556396510c1ff9f342a604c5a41eefbbbb15335cc9b5c7efd1d1a5142aad4b9`다. 인증 정보와 백업 원문은 공유하지 않는다.
