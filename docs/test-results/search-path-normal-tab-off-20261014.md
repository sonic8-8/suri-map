# 일반 탭에서 경로 조회 시간 재측정

2026-10-14, 사용자가 열어둔 일반 Aside 탭에 연결해 지도 내부 진단 계측을 끈 상태로 측정했다. **793번의 HTTP 요청·응답 구간이 633.457초, 요청 사이 공백이 23.963초였다. 두 시간을 합친 657.420초의 96.4%가 HTTP 구간이었다.** 서비스 지연을 고친 결과가 아니라, 다음 개선 대상을 좁히기 위한 관측이다.

## 무엇을 확인했나

- 일반 탭은 측정 시작부터 종료·재연결까지 유지됐다. 관찰 중 visibility는 visible이었고 중간 회수 24회가 로컬에 저장됐다. 자동화 탭이 사라졌던 정확한 원인은 별도로 미확인이다.
- 브라우저의 경로 요청 793건·본문 반환 793건·서버 요청 증가 793건이 일치했다. 구간 조회 786건, 변경분 조회 7건이며 관측된 HTTP 상태는 모두 200이었다. 응답 내용·구간 ID 전수 대조는 아니다.
- 첫 경로 요청 시작부터 마지막 경로 응답 완료까지 **10분 57.420초**였다. 이 값은 마지막 도형이 화면에 표시된 시간이나 전체 이력의 정합성 검증 완료 시간이 아니다.
- 이후 30초간 새 응답이 없어 `no_progress` 조건으로 사건 목록에 복귀했다. 정체와 자연 완료를 구별하는 조건은 아니므로 전체 로딩 성공으로 처리하지 않았다. 외부 강제 복구·회수 오류는 없었다.

## 어느 구간에서 시간이 걸렸나

요청 1~792의 HTTP 시간과 바로 다음 요청까지 공백을 198개씩 비교했다. 마지막 793번째 HTTP는 전체 합계에만 포함한다.

| 요청 순서 | HTTP 평균 | 다음 요청까지 공백 평균 |
|---|---:|---:|
| 1~198 | 840.8ms | 5.4ms |
| 199~396 | 797.7ms | 19.6ms |
| 397~594 | 794.6ms | 39.4ms |
| 595~792 | 762.6ms | 56.6ms |

공백은 후반에 늘지만 HTTP 구간보다 작았다. 마지막 묶음의 공백 56.6ms는 응답 종료→본문 반환 직전 39.1ms와 본문 반환 직전→다음 HTTP 시작 17.5ms로 나뉜다. 본문 반환 직전은 API 함수 반환이나 React 처리 완료와 다르며, 특정 함수의 CPU 시간으로 해석하지 않는다.

간헐적인 멈춤도 남았다. 프레임 간격 최대625ms, 100ms 타이머 간격 최대891.3ms, 요청 사이 공백 최대597.6ms였다. 평균 공백이 작다는 이유로 화면 끊김이나 새 좌표 반영 지연이 해결됐다고 판단할 수 없다.

[과거 계측 ON 관측](search-path-request-gap-trend-20261014.md)에서는 공백 평균이 46.5→233.0→502.1→613.4ms였다. 이번 실행에서는 그 크기로 재현되지 않았다. 그러나 브라우저·세션·시점·회수 방식이 달라 ON/OFF 차이를 계측의 인과 효과나 제품 개선율로 계산하지 않는다. HTTP에는 서버 처리, 프록시·네트워크, 브라우저 응답 수신이 포함된다. **96.4%를 DB 점유 비율로 읽으면 안 된다.**

같은 요청 수가 증가한 서버의 Spring HTTP 타이머 합계는 **133.216초**였다(구간132.241초+변경분0.974초). 브라우저 HTTP 633.457초의 약21.0%이고, 차이 **500.241초**는 이 서버 타이머 바깥의 미귀속 시간이다. 요청별 ID 대조가 아닌 같은 URI의 전후 집계이며, 프록시·네트워크·TLS·브라우저 수신 중 무엇이 차지했는지는 이번에 분리하지 않았다. Spring 시간도 DB 시간과 같지 않다.

## 다음 개선은 어디부터 검토하나

이번 관측에서 우선 검토할 대상은 **작은 응답을 수백 번 순차 조회하는 비용**이다. 브라우저의 응답 후 처리를 모두 없앤다고 가정해도 이번 요청열의 HTTP 633초가 남는다. 이는 병렬 실행·큰 응답의 실제 효과를 예측한 수치가 아니라 현재 요청열의 시간 분해다.

다음은 같은 일반 탭·계측 OFF 조건에서 응답 한도 확대가 요청 수와 총시간을 줄이는지 비교하는 것이다. 기존 [작은 입력의 한도 비교](search-path-tail-page-limit-comparison-20261008.md)는 왕복 감소 효과를 확인했지만, [전체 이력 비교](search-path-fixed-page-limit-comparison-20261008.md)는 다른 그래픽·계측 환경이었다. 그 결과로 새 기본값을 확정하지 않는다.

비교 조건·한도 변경과 원복 범위를 먼저 확인하고, 구간 누락·중복, 첫 표시, 전체 수신, 초기 로딩 중 새 좌표 반영을 함께 검증해야 한다. 새 좌표를 이 시험에서 전송하지 않았으며 이 글로 설정 변경·추가 부하 실행을 승인한 것은 아니다. 정확한 HTTP 내부 지연 원인과 간헐적 브라우저 멈춤의 원인도 남아 있다.

## 조건과 정리 확인

- 실행기: 14:40:43~14:52:37 KST. 관찰기 구간은688.603초이며 마지막 응답 이후 무진전 대기30초를 포함한다. 실행기 종료까지의 폴링 대기는 위657.420초에 넣지 않았다.
- 기존 Backend·Frontend 이미지와 시작 시각, FCM mock, 응답 한도(경로당1·전체80구간·480좌표)를 유지했다. 선택80경로의 경로·구간·GPS 해시가 전후·후속 확인에서 같았다. 전체 DB 무변경 검증은 아니다.
- 조회 감사는796건 증가했다. 경로793건+상황판 GET3건과 합계가 맞지만 요청별 ID 조인은 아니다. 그 밖에 타일18건, 사건 상세3건, 사건 목록2건과 SSE 종료 IOException 집계4건 등이 증가했다. 이 SSE 집계만으로 전달 장애를 확정하지 않는다.
- 14:52:58과14:53:48 KST 서버 표본에서 경로 요청 카운터와 조회 감사가 더 증가하지 않았다. 사용자 탭은 닫지 않았고 사건 목록에 남겼다. 임시 관찰기는 문서 교체로 제거됐으며 측정 기록은 당시 로컬 파일과 탭 sessionStorage에 보존했다.
- 실제 회수의 page copy는0~0.5ms, CLI 왕복은613~1,315ms였다. page copy가 요청 공백과 겹친 표본은0개다. JSON 직렬화·전송 비용 전체가 없다는 뜻은 아니며, CLI 시간을 제품 CPU 시간으로 더하지 않는다. 문서 교체 후 마지막 회수의 상대 시각은 비교 불가로 제외했다.
- 준비 단계에서 새 기록 형식·미완료 행 복원·시간 기준 변환·중단 중 회수·가짜 증가분40건 전달을 검사했다. 실제 멈춘 WSL CLI의 강제 종료와 디스크 중간 행 손상 복원은 미검증이다.

제품 코드·SQL·배포·영구 설정·커밋·푸시 변경은 없었다. 따라서 제품 전체 테스트·빌드는 다시 실행하지 않았다. 이것은 오프라인 복구 시간이나 새 GPS의 상황판 반영 시간 측정도 아니다.

## 로컬 근거

`run.cjs`는 기존 실행기를 재사용했고 `analyze.cjs`, `check.cjs`, `deadline-check.cjs`, `browser-check.cjs`, `server.py`는 이 진단의 실행, 검산용이다. 준비 검수 기록은 당시 로컬에 보존했다.

당시 측정 스크립트는 저장소에 보존하지 않았다. 당시 `summarize.cjs --check`는 저장된 분석의 동일성과 시간 합계를 재검사했고, 옵션 없이 실행하면 같은 분석과 `server-timing.json`의 계산값을 재생성해 stdout으로 출력했다. 별도 Luna 검산은 `independent-check.json`에 보존했다. 793개 원시 시간, 24회 회수 복원, 선택 원본, 감사 증가의 재계산이 일치했으며 전체 지도 정합성 검증과는 구분한다.
