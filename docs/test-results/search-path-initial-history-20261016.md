# 경로 최초 이력을 한 번에 받도록 바꾼 근거와 로컬 검증

2026-10-15~16 기록이다. 실서버 측정은 각 조건 1회이고, 로컬 검증은 배포 전 결과다. 배포 후 실서버 재측정은 아직 하지 않았다.

## 무엇이 느렸나

같은 일반 브라우저 탭에서 상황판 전체 이력(경로 481개, 구간 약 57,000개, 좌표 약 34만 개)을 응답 한도만 바꿔 받았다. 한도는 경로당 구간 / 응답당 구간 / 응답당 좌표다.

| 한도 | 요청 수 | 첫 표시 | 전체 이력 | 새 좌표 반영 |
|---|---:|---:|---:|---:|
| 1/80/480 (기존, 10-15 수정 전) | 793 | 4.0초 | 652초 | 2.7초 |
| 16/1,280/7,680 | 64 | 5.0초 | 91초 | 8.2초 |
| 200/16,000/64,000 | 19 | 6.8초 | 38초 | 17.8초 |

마지막 두 행은 수신 구간·좌표와 최종 지도 source가 DB와 일치했다. 첫 행은 2026-10-15 같은 탭에서 측정한 기존 한도의 값이다(조회 순서 수정 전, 비공유 원본).

- **요청마다 붙는 고정 비용:** 서버가 거의 일을 하지 않는 요청도 왕복에 약 0.53초가 걸렸다. 경로는 한국 → Cloudflare(LAX) → Hetzner(독일)다. 작은 페이지를 반복하면 이 비용이 요청 수만큼 쌓인다.
- **큰 페이지의 서버 비용:** 서버는 구간마다 좌표 SQL을 실행했다. 200/16,000/64,000의 페이지 1건(약 9,700구간)은 TTFB 3.7~4.1초였다.
- **변경분 조회의 빈 순회:** 변경분 응답 12건 중 11건이 구간 0개, 경로 80개였다. 변경이 없어도 모든 경로를 한 번씩 방문해 진행 정보를 채웠기 때문이다. 새 좌표는 이 순회가 해당 경로에 도달해야 반영돼, 응답이 클수록 늦어졌다.
- 예전 단일 GET(2026-10-02, 좌표 336,960개)은 TTFB 5.3~6.8초였다([로컬 이슈 18](../issues/local/18-board-read-timeout-with-accumulated-paths.md)). 이 API의 약점은 변경마다 전체를 다시 받는 것이었다.

## 바꾼 것

[상황판 요구](../features/situation-board.md#경로-변경분-조회-설계)의 2026-10-16 합의에 따른다.

- `SearchPathBoardService`: 한 페이지의 구간을 `findBoardSegments` 한 번, 좌표를 `findBoardPoints` 한 번으로 읽는다. 좌표는 경로별 순번 범위로 읽고 구간별로 나눈다. 응답 계약·페이지 진행·한도 계산 순서는 기존과 같다.
- 변경분 조회는 기준 버전 이후 바뀌지 않았고 진행 정보가 없는 경로를 방문하지 않는다.
- 최초 이력을 한 번에 받는 것은 서버 설정(응답 한도)으로 정한다. 운영값은 배포 때 확인하며 이 문서 작성 시점에는 1/80/480 그대로다.

## 로컬 검증

- `SearchPathBoardServiceTest` 23개 통과(성능 태그 제외). 새 검사 5개:
  - 경로 1개와 2개의 이력 페이지에서 경로 SQL 실행 수가 같다. 수정 전 4 대 6으로 실패한 것을 확인했다.
  - 기준 버전과 현재 버전이 같고 진행 정보가 없는 경로를 변경분 응답에 담지 않는다. 수정 전 경로가 담겨 실패한 것을 확인했다.
  - 앞서 방문한 경로의 좌표 누락이 뒤 경로의 구간 크기 오류보다 먼저 보고된다(검수 반례). 좌표 누락 단독 사례도 함께 확인한다.
  - 떨어진 두 변경 구간이 사이 구간 없이 각자의 좌표를 받는다.
- 같은 클래스의 성능 측정을 큰 한도로 실행했다. 경로 468개·구간 56,159개·좌표 336,954개를 한 페이지로 읽는 데 Service 조회 5.4~6.4초, JSON 변환 0.13~0.16초, 응답 19.6MB였다. 로컬 PostGIS 컨테이너의 5회 측정이며 실서버 값이 아니다.
  - 실행 명령: `PATH_QUERY_TEST_MAX_PATHS=1000 PATH_QUERY_TEST_SEGMENTS_PER_PATH=120 PATH_QUERY_TEST_MAX_SEGMENTS=60000 PATH_QUERY_TEST_MAX_COORDINATES=336959 ./gradlew test --no-daemon -PincludePerformance --tests '...SearchPathBoardServiceTest.measure_first_page_with_accumulated_paths'`
  - 좌표 한도를 전체보다 1 작게 두어, 기존 측정의 '남은 이력 있음' 확인을 유지했다.
- Backend 전체 1,420개 중 12개 실패. `ServerSentEventStreamTest` 4개, `TomcatProxyTest` 7개, `SecurityConfigTest` 1개다.
  - 원인은 실제 로컬 HTTP 연결의 `Connection refused`와 인증 키 서버 대역 503이다.
  - 이번 변경을 stash한 상태에서도 같은 12개가 실패해 기존 실행 환경 문제로 구분했다. CI 결과로 다시 확인한다.

## 검수

Codex(gpt-6.1-sol, xhigh, 읽기 전용) 검수 2회를 받았다.

- 1차: 오류 코드 우선순위 변경(필수)과 변경분 좌표 과다 조회(선택)를 지적했다.
- 2차: 두 지적 모두 해결된 것으로 통과했다.

남은 선택 지적은 범위 병합 회귀를 검출하는 테스트가 없다는 것이다. 검수 통과는 실서버 성능 통과가 아니다.

## 남은 확인

- 배포 후 같은 조건에서 요청 수·첫 표시·전체 이력·새 좌표 반영과 DB 대조를 측정한다.
- 서버 처리 시간을 Prometheus로 저장한다. 원복 재시작 전에 회수한다.
- 한 번의 응답이 커질 때 서버·브라우저 메모리, 응답 크기 상한의 운영값을 정한다.
