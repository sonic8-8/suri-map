# 경로 최초 이력을 한 번에 받도록 바꾼 근거와 로컬 검증

2026-10-15~16 기록이다. 실서버 측정은 각 조건 1회다. 배포 후 측정은 아래 [배포 후 실서버 측정](#배포-후-실서버-측정)에 있다.

## 무엇이 느렸나

같은 일반 브라우저 탭에서 상황판 전체 이력(경로 481개, 구간 약 57,000개, 좌표 약 34만 개)을 응답 한도만 바꿔 받았다. 한도는 경로당 구간 / 응답당 구간 / 응답당 좌표다.

| 한도 | 요청 수 | 첫 표시 | 전체 이력 | 새 좌표 반영 |
|---|---:|---:|---:|---:|
| 1/80/480 (기존, 10-15 수정 전) | 793 | 4.0초 | 652초 | 2.7초 |
| 16/1,280/7,680 | 64 | 5.0초 | 91초 | 8.2초 |
| 200/16,000/64,000 | 19 | 6.8초 | 38초 | 17.8초 |

마지막 두 행은 수신 구간·좌표와 최종 지도 source가 DB와 일치했다. 첫 행은 2026-10-15 같은 탭에서 측정한 기존 한도의 값이다(조회 순서 수정 전, 비공유 원본).

- **요청마다 붙는 고정 비용:** 서버가 거의 일을 하지 않는 요청도 왕복에 약 0.53초가 걸렸다. 경로는 한국 → Cloudflare(LAX) → Hetzner(독일)다. 작은 페이지를 반복하면 이 비용이 요청 수만큼 쌓인다.
- **큰 페이지의 서버 비용:** 서버는 구간마다 좌표 SQL을 실행했다. 200/16,000/64,000의 페이지 1건(약 9,700구간)은 TTFB 3.7~4.1초였다.
- **변경분 조회의 빈 순회:** 변경분 응답 12건 중 11건이 구간 0개, 경로 80개였다. 변경이 없어도 모든 경로를 한 번씩 방문해 진행 정보를 채웠기 때문이다. 새 좌표는 이 순회가 해당 경로에 도달해야 반영돼, 응답이 클수록 늦어졌다.
- 예전 단일 GET(2026-10-02, 좌표 336,960개)은 TTFB 5.3~6.8초였다([로컬 이슈 18](../issues/local/18-board-read-timeout-with-accumulated-paths.md)). 이 API의 약점은 변경마다 전체를 다시 받는 것이었다.

## 바꾼 것

[상황판 요구](../features/situation-board.md#경로-변경분-조회-설계)의 2026-10-16 합의에 따른다.

- `SearchPathBoardService`: 한 페이지의 구간을 `findBoardSegments` 한 번, 좌표를 `findBoardPoints` 한 번으로 읽는다. 좌표는 경로별 순번 범위로 읽고 구간별로 나눈다. 응답 계약·페이지 진행·한도 계산 순서는 기존과 같다.
- 변경분 조회는 기준 버전 이후 바뀌지 않았고 진행 정보가 없는 경로를 방문하지 않는다.
- 최초 이력을 한 번에 받는 것은 서버 설정(응답 한도)으로 정한다. 운영값은 배포 때 확인하며 이 문서 작성 시점에는 1/80/480 그대로다.

## 로컬 검증

- `SearchPathBoardServiceTest` 23개 통과(성능 태그 제외). 새 검사 5개:
  - 경로 1개와 2개의 이력 페이지에서 경로 SQL 실행 수가 같다. 수정 전 4 대 6으로 실패한 것을 확인했다.
  - 기준 버전과 현재 버전이 같고 진행 정보가 없는 경로를 변경분 응답에 담지 않는다. 수정 전 경로가 담겨 실패한 것을 확인했다.
  - 앞서 방문한 경로의 좌표 누락이 뒤 경로의 구간 크기 오류보다 먼저 보고된다(검수 반례). 좌표 누락 단독 사례도 함께 확인한다.
  - 떨어진 두 변경 구간이 사이 구간 없이 각자의 좌표를 받는다.
- 같은 클래스의 성능 측정을 큰 한도로 실행했다. 경로 468개·구간 56,159개·좌표 336,954개를 한 페이지로 읽는 데 Service 조회 5.4~6.4초, JSON 변환 0.13~0.16초, 응답 19.6MB였다. 로컬 PostGIS 컨테이너의 5회 측정이며 실서버 값이 아니다.
  - 실행 명령: `PATH_QUERY_TEST_MAX_PATHS=1000 PATH_QUERY_TEST_SEGMENTS_PER_PATH=120 PATH_QUERY_TEST_MAX_SEGMENTS=60000 PATH_QUERY_TEST_MAX_COORDINATES=336959 ./gradlew test --no-daemon -PincludePerformance --tests '...SearchPathBoardServiceTest.measure_first_page_with_accumulated_paths'`
  - 좌표 한도를 전체보다 1 작게 두어, 기존 측정의 '남은 이력 있음' 확인을 유지했다.
- Backend 전체 1,420개 중 12개 실패. `ServerSentEventStreamTest` 4개, `TomcatProxyTest` 7개, `SecurityConfigTest` 1개다.
  - 원인은 실제 로컬 HTTP 연결의 `Connection refused`와 인증 키 서버 대역 503이다.
  - 이번 변경을 stash한 상태에서도 같은 12개가 실패해 기존 실행 환경 문제로 구분했다. CI 결과로 다시 확인한다.

## 배포 후 실서버 측정

| 항목 | 기존 1/80/480 | 200/16,000/64,000(수정 전) | **배포 후** |

## 서버 처리 시간 분해와 fetch size

2026-10-16 로컬 측정이다(PostGIS Testcontainers, Docker Desktop on WSL). 경로 468개·좌표 336,960개를 운영 한도로 1페이지에 읽었다. 측정용 계측은 커밋하지 않았다.

| 측정 구간 | 시간 |
|---|---:|
| Service 전체 | 5.30~5.88초 |
| 경로 목록·준비 확인 SQL | 0.03~0.06초 |
| 구간 SQL | 0.84~1.17초 |
| 좌표 SQL | 4.27~5.39초 |
| 좌표 그룹·구간 조립·DTO | 0.03~0.08초 |
| JSON 변환 (Service 반환 후 별도 측정) | 0.13~0.17초 |

- 네 SQL 모두 인덱스를 사용했다. DB 실행 시간(`EXPLAIN ANALYZE`)은 구간 66~172ms, 좌표 142~217ms였다.
- 같은 좌표 SQL을 트랜잭션 밖에서 실행하면 1.8초였다. 차이의 원인은 MyBatis 전역 `default-fetch-size: 100`이다. 조회 트랜잭션 안에서 PostgreSQL JDBC가 100행마다 DB에 다시 요청해, 좌표만 약 3,370번 왕복했다.
- 두 SQL에만 fetch size를 주고 Service 전체를 다시 쟀다.

| 두 SQL의 fetch size | Service 전체 |
|---|---:|
| 100 (기존 전역값) | 5.4~6.4초 |
| 0 (한 번에 전체) | 2.24~3.03초 |
| 10000 | 2.30~2.51초, 2.49~3.41초 (2회 실행) |

- **10000을 선택했다.** 0과 시간 차이가 확인되지 않았다. 0은 드라이버가 원본 행 전체를 동시에 보유하게 한다. 구간 후보는 경로마다 최대 `min(segmentsPerPath, maxSegments)+1`개를 미리 읽고, 좌표 범위가 5,000개를 넘으면 경로 전체 범위로 합친다. 그래서 실제로 읽는 행은 응답 한도보다 많을 수 있다(Codex 검수 지적). 전역값 100은 `SearchPathService.findAll`의 나눠 받기 전제를 지키려고 유지했다.
- 남은 약 2.4초 중 좌표 1.8초는 다음과 같이 나뉜다(트랜잭션 밖 측정).
  - DB 실행 0.15초
  - JDBC 수신 1.1~1.4초: 행마다 경로 ID 문자열을 포함한 34만 행. Docker Desktop 포트 전달 때문에 실서버보다 크게 나올 수 있다.
  - MyBatis 객체 변환 약 0.45초
- 회귀 검사: `SearchPathBoardServiceTest`가 이력·변경분 조회에서 두 SQL이 실제 실행될 때의 fetch size를 확인한다. 수정 전에는 `[100, 100]`으로 실패했다. 이 검사는 성능이나 왕복 수를 직접 증명하지 않는다. 10000 적용 후 `SearchPathBoardServiceTest` 24개가 통과했다. Backend 전체는 1,421개 중 12개가 실패했다. 기존과 같은 로컬 HTTP 환경 원인이다(`ServerSentEventStreamTest` 4·`TomcatProxyTest` 7·`SecurityConfigTest` 1).
- 실서버 효과는 배포 후 확인한다.

[상황판 표시 목표](../features/situation-board.md#화면과-관측에서-남은-요구)(2026-10-16 합의)를 판정하기 전의 참고값이다. 위 [배포 후 실서버 측정](#배포-후-실서버-측정) 1회에서 계산했다.

| 항목 | 목표 | 현재 참고값 | 예산 |
|---|---:|---|---|
| 첫 표시 | 5초 | 진입 기준 미측정. 관찰기 설치 기준 첫 경로 관찰 12.23초 = 요청 전 2.57 + TTFB 5.27 + 다운로드 1.17 + 본문 읽기 0.01 + 본문 수신 후 첫 경로 관찰 3.21 | 관찰기 설치 기준으로 요청 전·다운로드·본문 읽기를 유지하면 TTFB와 첫 경로 관찰에 남는 예산은 약 1.25초다. 조건부 참고 계산이며 진입 기준으로 다시 산출한다. TTFB는 서버 처리 시간만이 아니다. |
| 전체 이력 지도 반영 | 5초 | 미측정(관찰기 설치 기준으로도). 실행기는 첫 경로 관찰만 기록한다. | 첫 표시와 같은 예산 안이어야 한다. |
| 새 좌표 반영 | 3초 | 5.44초 = 저장 응답 0.66 + 변경분 본문 수신 1.72 + 지도 관찰 3.06 | 앞 두 구간을 유지하면 지도 반영 예산은 0.62초다. SSE 전달 지연은 1.72초 안에 섞여 따로 식별하지 못했다. |

- 모든 값은 관찰기 비용을 포함한다.
- 요청당 약 0.53초 왕복은 다른 요청·연결 조건의 하한 참고값이다. 저장·변경분 전체를 고정 네트워크 비용으로 보지 않는다.
