# 경로 표시 수정 후 응답 한도 비교

2026-10-08, [짧은 구간 표시 수정 배포본](search-path-short-segment-deployment-20261008.md)에서 응답 한도와 새 좌표 반영 시간을 비교했다. **기존 한도는 25분 관측 상한에서도 미완료였고, 확대 한도는 24분 17초에 전체 수신을 완료했다. 응답 한도 확대만으로 로딩 지연을 해결하지 못했다.**

## 조건과 측정 방법

- 배포 커밋 `3022dd0b`, 공개 웹 `index-LhL8h6oC.js`, Backend 이미지 `81b5f33df9ea4f5fc327e1b05e80cc569ee95c37dde97a988792c68a52de800e`.
- 실제 사건 1개·차수 1개·경로 481개. 기존 경로·좌표를 삭제하거나 fixture를 재생성하지 않는다. 시험 시작 시 GPS 341,009개·구간 57,087개다.
- 같은 Chrome 147·1440×900·DPR 1·WSL Headless·SwiftShader. 실행마다 새 브라우저를 사용하고 Backend를 같은 이미지로 재시작한다. DB 버퍼·호스트 부하를 초기화한 반복 벤치마크는 아니다.
- 기본 대조는 경로당 1·전체 80구간·480좌표, 확대 대조는 경로당 4·전체 320구간·1,920좌표다. 경로 수 한도 80·FCM mock·나머지 설정을 유지하고 시험 후 원복한다. 확대값은 운영 기본값으로 채택하지 않는다.
- 함수별 진단 타이머·프로파일러·임시 지도 source는 넣지 않는다. 기존 제품의 페이지·지도 관찰 계측은 켠다. 따라서 완전히 계측이 없는 실행은 아니다.
- 각 실행의 초기 로딩 중 기존 시험 경로에 GPS 6개를 한 번 추가한다. 요청 준비·DB 확인은 SSH로 하되 HTTP 요청 자체는 시험 브라우저에서 보낸다. `performance.now()`로 전송 직전·응답 본문 수신 완료·좌표 표시를 같은 시계에서 측정한다.
- 새 좌표의 ID·값·순서를 DB와 대조하고, 동일 좌표 해시·화면 범위·MapLibre 표시 결과를 확인한다. 실제 휴대폰 통신망이나 픽셀 색 검증은 아니다.
- 전체 이력 완료는 모든 페이지의 수신·캐시 반영, 일부 표시 안내 해제, DB 구간 ID와 수신·지도 전달 ID의 전수 일치로 판정한다. 마지막 도형의 렌더링 완료 시간과 구분한다.
- 진단 관측 상한은 25분이다. 서비스 목표나 HTTP timeout이 아니며, 상한에서 끝내면 미완료 결과로 남긴다.

## 측정 방식의 사전 확인

약 62초의 짧은 실행에서 요청 시작 → 지도 표시 2.732초, 응답 완료 0.431초, 응답 완료 → 지도 표시 2.301초를 확인했다. GPS 6개가 수용됐고 제외 0·DB 값/순서 일치·지도 표시 검사를 통과했다. 전체 이력은 의도적으로 끝까지 받지 않았다.

이 쓰기로 GPS 341,015개·구간 57,088개가 됐으며 추가분은 보존한다. 이후 본 비교마다 6좌표·1구간이 늘어나는 차이를 구간 ID 대조와 결과 건수에 반영한다.

## 기존 한도: 새 좌표는 표시됐지만 전체 이력은 미완료

경로당 1·전체 80구간·480좌표 조건에서 첫 경로는 4.173초에 표시됐다. 초기 로딩 시작 약 25.733초에 새 좌표를 전송했고, 응답 본문 완료까지 0.980초·지도 표시까지 2.931초였다. 응답 완료 이후 표시까지는 1.951초다. 6개 좌표의 DB 값·순서와 실제 지도 표시 검사가 통과했다.

25분 관측 상한 뒤 마지막 상세 기록에서 경로 조회 402회 완료·1회 진행 중이었다. 구간 조회 394회·변경분 조회 8회이며 완료된 응답의 수신 ID와 지도 전달 ID는 각각 31,521개였다. DB 대상 57,089개에 포함되는 ID였지만 **전체 일치는 아니며, 로딩 안내도 남았다.** 관측 시 조회 실패·JavaScript 오류 0, 최대 동시 경로 조회 1이었다. 진행 중 요청은 이후 브라우저 종료로 중단됐다.

완료된 요청만 Resource Timing과 순서·종류·시각을 대조했다. 전체 완료를 전제한 기존 요약기는 진행 중 1건 때문에 개수 검사를 거부했으므로, 완료된 요청만 짝짓도록 임시 요약기를 조정했다. 진행 중 요청을 성공으로 세거나 관측 상한을 완료 시간으로 바꾸지 않았다.

| 완료된 402회 관측 | 시간 |
|---|---:|
| HTTP 시간 합계 | 416.529초 |
| 이전 응답 종료 → 다음 요청 시작의 간격 합계 | 1,088.843초 |
| 첫 100회 간격 평균 | 0.509초 |
| 마지막 101회 간격 평균 | 4.956초 |

간격에는 응답 처리·브라우저 실행 대기·지도 처리 등이 포함되며 특정 함수의 CPU 시간은 아니다. HTTP 시간도 DB 실행 시간과 같지 않다. 브라우저 long task의 경과 시간 합계는 1,484.313초로 위 구간들과 겹치므로 더하지 않는다.

관측 중 SwiftShader GPU 프로세스의 `ps` 평균 CPU 값은 약 1,000–1,100%였다(논리 코어 1개 사용을 100%로 표시). 서버의 단일 `docker stats` 표본은 Backend 3.17%·PostGIS 3.85%였다. 수집 구간과 집계 방식이 달라 직접 비율을 비교하거나, 그 표본만으로 서버 병목이 없다고 결론내리지 않는다. **이번 실행의 전체 지연을 DB 비용만으로 설명할 수는 없다.** 실제 GPU 브라우저와 계측 자체의 영향을 분리하는 확인도 필요하다.

실행 후 동일 이미지·전체 환경변수·`.env` 해시 복구와 health `UP`을 확인했다. 시험 Chrome의 GPU·렌더러 프로세스도 종료됐다. 확대 한도는 그 뒤 새 브라우저로 측정한다.

## 확대 한도: 전체 수신 완료, 후반 대기는 지속

경로당 4·전체 320구간·1,920좌표 조건에서 1,456.927초에 전체 수신·캐시 반영을 완료했다. 구간 조회 199회·변경분 조회 8회, 총 207회였다. 수신 ID와 지도 전달 ID가 DB의 57,090구간과 전수 일치했고 ‘일부만 표시’ 안내가 사라졌다. 최대 동시 경로 조회 1·실패 0·JavaScript 오류 0이었다. 완료 캡처도 확인했지만, 픽셀 단위의 전수 렌더링 검증은 아니다.

| 항목 | 기존 80구간·480좌표 | 확대 320구간·1,920좌표 |
|---|---:|---:|
| 첫 경로 표시 | 4.173초 | 3.973초 |
| 전체 수신·캐시 반영 | 25분 관측 상한에서 미완료 | 24분 16.927초 |
| 완료된 경로 조회 | 402회 — 부분 수신 | 207회 — 전체 수신 |
| 수신·지도 전달 구간 | 31,521 / 대상 57,089 | 57,090 / 대상 57,090 |
| 새 GPS 요청 → 응답 본문 완료 | 0.980초 | 1.199초 |
| 새 GPS 요청 → 좌표 표시 | 2.931초 | 4.230초 |
| 응답 완료 → 새 좌표 표시 | 1.951초 | 3.031초 |

두 실행은 각각 초기 로딩 시작 25.733초·26.092초에 GPS를 한 번 전송했다. 그 시점까지 받은 구간은 1,360개·3,515개로 다르다. 각 한도의 실제 로딩 진행 중 반영을 비교한 것이며, 동일한 누적 표시량에서 반복한 지연 분포나 p95가 아니다. 이번 한 번의 4.230초를 확대 한도의 고정 비용·성공 기준으로 채택하지 않는다. 예비 검사까지 합친 3회 쓰기는 모두 GPS 6개 수용·제외 0·DB 값/순서 일치·새 좌표 표시 검사에 통과했다.

확대 한도의 HTTP 시간 합계는 221.009초, 응답 종료부터 다음 요청 시작까지의 간격 합계는 1,223.738초였다. 마지막 52회 간격 평균은 11.211초다. 약 20분 48초에 56,916구간을 받았지만 나머지 174구간을 받는 데도 수분이 더 걸렸다. 작은 마지막 응답이라고 바로 다음 조회로 진행하지 못했다.

기존 한도는 중도 관측 종료이므로 두 요청 수를 전체 로딩의 정확한 감소율로 계산하지 않는다. 큰 응답이 더 적은 요청으로 더 많은 구간을 받은 것은 확인했지만, 이 단일 비교에서 운영 최적값·반복 안정성·실사용 성능까지 검증한 것은 아니다.

## 결론과 다음 확인

- 새 좌표의 저장·화면 반영은 두 조건 모두 확인했다. 확대 한도에서는 전체 구간 수신·지도 전달의 DB 일치도 확인했다.
- 전체 로딩 지연은 미해결이다. 이번 실행은 응답 이후 브라우저 대기가 지배적이었으며, 이를 전부 DB·React 계산 또는 GPU 하나의 확정 원인으로 설명하지 않는다.
- 먼저 같은 자료에서 지도 계측을 끈 대조와 실제 GPU 브라우저 대조로 시험기·계측 비용을 분리한다. 그 결과를 바탕으로 제품 표시 병목과 앞서 확인한 GPS 일괄 조회 개선을 검증한다.
- 현재 시험 자료는 좁은 범위에 합성 경로가 집중된다. [경로 입력 생성기](../../infra/k6/prepare-search-path-batch-fixtures.py)의 좌표 계산과 완료 캡처에서 집중·겹침을 확인했다. 이를 그래픽 지연의 확정 원인으로 삼거나 실제 현장의 경로 분포·실제 사용자 GPU에서도 같은 시간이 걸린다고 일반화하지 않는다.
- 한도를 영구 변경하지 않았다. 제품 코드·SQL·schema를 바꾸지 않았으므로 Backend 전체 테스트·Frontend 빌드는 재실행하지 않았다. 실제 HTTP·브라우저·DB 검사와 문서 링크·diff 검사를 수행했다.

## 종료 상태

두 실행 후 기존 이미지·전체 환경변수·`.env` 해시 복구와 Backend health `UP`을 확인했다. 한도는 경로당 1·전체 80구간·480좌표, FCM은 mock이다. 시험 브라우저는 종료했다.

예비 1회와 본 비교 2회에서 추가한 GPS 18개, 구간 3개는 남겼다. 최종 경로 481개, GPS 341,027개, 구간 57,090개, 대상 경로 마지막 순번 767이다. 추가분을 제외한 기존 GPS 341,009개, 구간 57,087개의 모든 컬럼 해시가 시작 시점과 같고, 대상 외 경로 480개의 해시도 `de6f983b4fe61fa92a24f63acd0933bb`로 유지됐다. 대상 경로의 정상 버전, 마지막 좌표 갱신과 조회 감사 기록까지 무변경이라고 주장하지 않는다. 근거는 당시 `after-comparison.json`에 기록했다.

이번에 만든 로컬 WEB 세션 사본과 서버 APP 토큰 파일은 제거했다. 기존 로그인 계정 파일·원본 데이터·측정 결과·배포 백업은 보존했다.

## 보존 자료

기존 진단의 서버 설정 원복, 브라우저 관측, 인증 함수를 재사용했다. 제품 코드, 의존성, 영구 설정은 바꾸지 않는다.

당시 로컬에 아래 자료를 보존했다.

- `timing-check/`: 사전 확인의 HTTP·동일 시계·좌표·화면 검사.
- `baseline/`: 미완료 실행의 상세 페이지·HTTP·새 좌표 기록, 수신 ID·화면·요약.
- `larger/`: 전체 수신·DB 대조를 통과한 같은 형식의 기록과 완료 화면.
- `before-comparison.json`: 사전 확인 후 기존 GPS 341,009개·구간 57,087개의 모든 컬럼 해시 보존 확인. `before` 파일명이 이번 턴의 추가 쓰기 이전을 뜻하지는 않는다.

인증 준비 전후의 전체 테이블 해시는 경로 `fda32bbd197661a9e568a75c3fd95d38`, GPS `2f91d1b5971cc193b9733f1e2f3a2779`, 구간 `988ebfaa092c86b460873ecd40a5cab8`로 일치했다. 임시 Keycloak 계정·클라이언트는 제거했고 프로필 설정은 원복했다.

당시 임시 실행 도구는 `login.cjs`, `prepare-batch.py`, `measure.cjs`, `run.cjs`, `check-data.cjs`, `summarize.cjs`였다. 서버 원복은 기존 `runtime.cjs`를 재사용했고 결과는 원래 진단 폴더의 `restored-*.json`에도 남겼다.
