# 경로 수신 후 브라우저 처리 비용 분석

2026-10-07 [로컬 20번](../issues/local/20-slow-paged-search-path-display.md)의 후속 분석이다. **추가된 구간 수는 같아도, 누적 경로 전체를 지도 자료로 다시 만들고 교체하는 비용이 커진다.** 실제 프런트엔드 함수와 MapLibre를 사용하는 통제 시험으로 확인했다. 배포 브라우저에서 관측한 요청 사이 간격 462.606초를 전부 분해한 결과는 아니다.

## 코드에서 확인한 흐름

1. [페이지 수신](../../frontend/src/features/path/api/searchPathPagesApi.ts): 응답 검사 → 구간 병합 → Query 캐시 갱신 → 다음 요청 생성.
2. [화면 자료 조립](../../frontend/src/features/situationBoard/presentation/hooks/useSituationBoardData.ts): 경로 배열이 바뀌면 누적 구간 전체를 `toMovementPaths()`와 `assignRouteColorsToMovementPaths()`에 넣는다.
3. [지도 반영](../../frontend/src/features/situationBoard/presentation/components/map/SearchMapCanvas.tsx): 전체 경로·현재 위치 도형을 다시 만들고 `setData()`로 source 자료를 교체한다. 추가한 80구간만 전달하는 구조가 아니다.
4. [측정 코드](../../frontend/src/features/board/model/boardMeasurement.ts): 활성화되면 전체 feature의 좌표 서명·식별 정보·측정용 속성을 만들고, render 이벤트에서 화면 도형을 조회한다. 측정 자체에도 비용이 있다.

페이지 루프는 지도 갱신 완료를 `await`하지 않는다. 지도 worker·렌더링 시간 전체를 HTTP 요청 전 대기 시간으로 더해서는 안 된다. 다만 같은 메인 스레드에서 수행되는 자료 조립·계측·지도 처리 때문에 다른 JavaScript 작업이 늦어질 수 있다.

## 시험 조건

- Linux, Node 22.22.0, headless Chrome 147.0.7727.57, 설치된 MapLibre 5.24.0·TanStack Query 5.100.6.
- 기존 Puppeteer·Vite 도구 재사용. 제품 코드·서버·페이지 한도는 변경하지 않았다.
- 합성 경로 481개, 경로당 기존 구간 1·20·60·120개. 구간당 좌표 6개이며 각 회차에 80개 경로의 더 오래된 구간을 1개씩 추가한다.
- 각 조건 5회, 처음 2회는 예열로 제외하고 나머지 3회 평균을 기록한다. 계측 켜기/끄기 순서는 데이터 크기에 따라 교대했다.
- 지도 크기 800×600, 중심 `[127.0006, 37.00048]`, 확대 17, 빈 배경과 선 레이어 1개. 외부 네트워크 요청을 차단하고 API·타일 없이 실행했다. SwiftShader 옵션을 사용했다.
- 매회 실제 `parseSearchPathPage`, `mergeSearchPathPage`, `setQueryData`, 다음 요청 생성, 지도 자료 변환, 색상·도형·현재 위치 생성, `measureBoardMapUpdate`, MapLibre `setData`를 순서대로 실행했다.
- 각 지도 갱신이 idle에 도달한 후 다음 회차를 시작했다. 실제 앱의 React 재렌더링·동시 지도 갱신·네트워크 흐름 전체를 재현한 것은 아니다.

## 계측을 끈 결과

단위는 ms다. 기존 구간 수는 첫 회차 시작 전이며, 측정 회차에는 각각 240·320·400개가 추가돼 있다.

| 기존 구간 수 | 응답 병합 | 캐시 갱신 | 지도 자료 조립¹ | `setData`부터 idle까지² | 타이머 최대 지연³ |
|---:|---:|---:|---:|---:|---:|
| 481 | 0.17 | 0.33 | 1.93 | 306.90 | 10.93 |
| 9,620 | 0.23 | 2.67 | 10.00 | 291.47 | 68.70 |
| 28,860 | 0.43 | 7.67 | 33.20 | 638.80 | 230.33 |
| 57,720 | 0.77 | 15.43 | 66.77 | 1,306.93 | 462.23 |

¹ 누적 경로 변환·색상 배정·경로 도형·현재 위치 도형 생성의 합계. 전체 React 렌더 비용이 아니다.

² worker 처리·렌더링·대기까지 포함하는 경과 시간이다. `setData()` 호출 자체는 이 시험에서 0.1ms 이하로 반환됐다. 소량 자료에도 약 300ms가 관측돼 이 값을 순수 CPU 시간으로 해석하지 않는다.

³ 10ms 타이머의 예정 간격 초과분 중 각 측정 회차의 최댓값을 구해 평균했다. 10ms는 실행 지연 탐지용 간격이지 제품 목표가 아니다. HTTP 지연이나 연속 CPU 점유 시간의 직접 측정도 아니다. 원래 브라우저의 총간격 462.606초와 단위·의미가 다르다.

약 5만 8천 구간 조건에서는 병합·캐시보다 전체 지도 자료 조립 비용이 컸고, 지도 갱신 중 타이머 실행 지연도 관측됐다. 계측을 꺼도 누적 데이터 증가에 따른 비용이 남았다.

## 계측의 추가 비용

같은 57,720구간 조건에서 계측을 켜면 지도 전달 전 계측 함수가 평균 68.70ms, 지도 갱신 동안 `queryRenderedFeatures()` 호출 합계가 286.20ms였다. 지도 전달부터 idle까지는 1,411.33ms, 타이머 최대 지연 평균은 596.90ms였다.

화면 도형 조회 시간은 idle 경과 시간에 포함되므로 두 값을 더하지 않는다. 단일 브라우저의 적은 표본이며, 켜기/끄기 차이 전체를 계측의 순수 인과 효과로 확정하지 않는다. 다만 함수 내부 시간을 직접 재어 계측도 무시할 수 없는 작업임을 확인했다. 최초 실행에서도 큰 데이터의 지도 idle 시간은 끄기 1,336.13ms·켜기 1,462.77ms였다.

## 검증 결과와 한계

- 8조건 × 5회에서 구간 수·고유 ID 수가 기대값과 일치했다.
- 최종 도구 실행에서는 매회 MapLibre source를 `getData()`로 읽어 ID·geometry가 전달한 원본과 같은지 검사했다. 계측 켜기/끄기의 최종 ID 해시도 크기별로 일치했다.
- 합성 데이터의 지도 source 내용 검사이며, 실제 DB 구간 대조나 모든 픽셀 표시 검증은 아니다.
- 최초 도구 실행은 진단 fixture의 잘못된 색상 토큰으로 실패했다. 기존 `AREA_BLUE_01` 값으로 수정한 뒤 완료했다. 제품 오류로 기록하지 않는다.
- 본 시험의 좁은 지도 범위·선 레이어 1개·headless 환경은 실제 상황판과 다르다. 이 수치로 기존 전체 로딩 17분 49.9초나 HTTP 간격 462.606초를 직접 설명하지 않는다. 전체 상황판의 React·여러 레이어·비동기 요청을 연결한 계측은 남아 있다.

## 변경분만 반영하는 방식의 비교

후속 통제 시험에서는 **바뀐 경로만 다시 계산하고 변경된 도형만 전달하는 방식이 큰 데이터의 갱신 비용을 줄였다.** 제품 코드는 변경하지 않았으며, 실제 상황판 전체 로딩 시간의 개선을 검증한 결과는 아니다.

MapLibre는 고유 feature ID를 전제로 `updateData()`를 제공한다. [공식 API 설명](https://maplibre.org/maplibre-gl-js/docs/API/classes/GeoJSONSource/#updatedata)과 설치된 5.24.0의 구현을 확인했다. 시험에서는 모든 방식에 동일하게 `feature.id = properties.entityId`를 부여했다. 공개 API 식별자나 제품 코드를 변경한 것은 아니다.

### 비교 조건

- 기존 구간 9,620개·57,720개, 회차마다 80개 경로에 오래된 구간 1개씩 추가. 지도·좌표·라이브러리·네트워크 차단 조건은 앞 시험과 같다.
- 세 방식: 전체 자료 조립 후 `setData`, 전체 자료 조립·비교 후 `updateData`, 변경된 경로의 자료만 조립·비교 후 `updateData`.
- 변경 경로 판정에는 실제 페이지 병합과 Query 캐시 갱신 후의 객체 참조를 사용했다. 변경되지 않은 경로의 도형은 재사용했다. 변경 경로 안에서는 모든 구간을 다시 계산하므로 이웃 연결선도 함께 비교한다.
- 계측은 껐다. 방식별 5회 중 처음 2회는 제외하고, 실행 순서를 뒤집어 한 번 더 반복했다. 아래는 방식·크기별 6개 표본 평균이다.
- 초기 전체 자료를 지도에 먼저 올린 후 반복 갱신을 측정했다. 응답 병합·Query 캐시 갱신과 검사 시간은 아래 표에서 제외했다.
- 모든 방식에서 label을 포함했다. 부분 배열의 순서 때문에 기본 `Path N` 이름이 바뀌지 않도록 시험 입력에는 경로 ID 기반의 명시적인 label을 부여했다. 제품의 기본 label 처리까지 검증한 것은 아니다.

### 약 5만 8천 구간에서의 결과

단위는 ms다. 측정 회차의 누적 구간은 57,960·58,040·58,120개다.

| 방식 | 지도 자료 조립 | 비교·도형 캐시 관리¹ | 전달부터 idle까지 | 조립 시작부터 idle까지 | 타이머 최대 지연 |
|---|---:|---:|---:|---:|---:|
| 전체 조립·전체 교체 | 75.85 | 10.77 | 1,325.32 | 1,411.97 | 458.47 |
| 전체 조립·변경분 전달 | 63.98 | 228.78 | 738.30 | 1,031.15 | 351.08 |
| 변경 경로만 조립·변경분 전달 | 10.77 | 38.05 | 729.42 | 778.28 | 115.43 |

¹ 시험용 ID 인덱스·도형 캐시 관리가 포함된다. 전체 교체에도 이 관리 비용이 들어가므로 기존 제품 코드의 실행 시간 자체는 아니다. 변경 비교는 좌표와 정렬한 속성을 JSON으로 비교하는 단순 구현이다. 가장 빠른 비교 알고리즘을 찾은 결과는 아니다.

변경 경로만 처리한 방식은 이 시험의 갱신 경과 시간이 약 45% 줄었다. 다만 **전체를 다시 만든 뒤 차이만 찾는 방식은 비교에 약 229ms가 들었다.** `setData`를 `updateData`로 바꾸기만 하는 것보다 계산 범위도 함께 줄이는 방향에 근거가 생겼다.

기존 9,620구간 조건에서는 전체 교체 258.53ms, 전체 비교 264.38ms, 변경 경로 비교 261.93ms로 전체 경과 시간의 개선이 관측되지 않았다. 변경 경로 방식의 타이머 최대 지연은 70.50ms에서 22.38ms로 줄었다. 데이터 크기·화면 조건과 관계없이 빨라진다고 일반화하지 않는다.

### 정확성 검사와 초기화 실패

- 12조건 각각에서 구간 추가 5회, 끝 좌표·이동 수단·경로 버전 수정, 구간 삭제, 활성 수색 차수 변경, 전체 비우기의 source 내용을 검사했다. 108회 모두 전체 조립 결과와 고유 ID·geometry·모든 속성이 일치했다. 속성 키와 feature 배열 순서는 무시하고 비교했다.
- 오래된 구간 80개를 앞에 붙이면 새 도형 80개뿐 아니라 기존 이웃 도형 80개도 바뀌었다. 변경분은 매회 추가 80개·수정 80개였다. 기존 방식은 측정 회차 평균 58,040개를 전달했다.
- 새 도형만 추가하는 잘못된 대조군을 12조건에서 모두 불일치로 검출했다. 검사가 단순 개수 확인에 그치지 않는지 확인한 것이다.
- 처음에는 전체 비우기를 개별 ID 삭제 목록으로 보냈다. 58,119개를 삭제하는 큰 조건의 변경분 방식 4회 모두 `Maximum call stack size exceeded` 오류가 발생했다. 차수 변경까지는 통과했고, 전체 비우기에서 실패했다. 정확한 라이브러리 내부 발생 행은 확정하지 않았다.
- 전체 비우기만 기존 API의 `{ removeAll: true }`로 변경한 최종 재실행에서는 12조건 모두 통과했고 MapLibre 오류는 없었다. 오류·실패 표본은 별도로 보존했다. 제품은 아직 이 변경분 방식을 사용하지 않으므로 현재 운영 코드에서 발견한 삭제 오류로 해석하지 않는다.

### 제품 적용 전에 남은 확인

- 이 비교는 실제 React 상황판·HTTP 반복 요청을 연결하지 않았다. 원래 전체 로딩 17분 49.9초와 요청 사이 간격 462.606초가 얼마나 줄어드는지는 적용 후 같은 데이터로 재측정해야 한다.
- 지도 source의 내용 일치는 확인했지만 모든 픽셀·도형 겹침 순서의 일치는 검사하지 않았다. 배열 삽입 순서 변화가 실제 레이어 표시에 영향을 주는지 확인해야 한다.
- 현재 위치 도형은 조립 비용에 포함했지만 별도 source에 반영하거나 결과를 검사하지 않았다. 제품에서는 경로 선과 업무폰 현재 위치를 함께 검증해야 한다.
- 실제 기본 label, 배정 색상·업무폰 최신성·차수·사건·지도 style 변경 시 재계산 범위와 캐시 초기화가 필요하다. 이번에는 활성 차수 변경 시 전체를 재계산하는 입력만 검사했다.
- 빠른 연속 응답, worker 처리 중 다음 갱신, 오류 후 재동기화, 계측 활성화는 이 비교에서 제외했다. 제품 적용 범위를 정한 뒤 검증한다.

## 1차 제품 수정: 변경하지 않은 경로 자료 재사용

통제 비교 뒤 화면 자료 변환 단계부터 제품 코드에 연결했다. **1차 수정 시점에는 지도 source의 기존 `setData()` 전체 교체를 유지했다.** 변경분 전달에는 도형 겹침 순서와 기존 화면 계측의 연속 갱신 검증이 필요하므로 다음 단계로 분리했다. 위 `updateData` 비교의 778.28ms를 제품의 지도 갱신 시간으로 인용하지 않는다. 이후 제품 연결·검증은 [2차 변경분 지도 반영 결과](search-path-incremental-map-update-20261008.md)를 따른다.

- `movementPathBoardMapper.ts`: 경로 원본 객체가 같으면 이전 화면용 자료를 재사용한다. 바뀐 경로는 기존 변환·차수 필터·색상 배정 함수를 그대로 호출한다. 경로 전체를 문자열로 비교하지 않는다.
- 사건·차수·서버 시각·업무폰 최신성·구역 배정/도형/색상이 달라지거나 경로가 비면 재사용 자료를 초기화한다. 경로 원본은 Query 캐시에서 관리하며, 새 저장소나 의존성을 추가하지 않았다.
- `boardMapSlots.ts`: 일부 경로만 변환해도 원래 배열의 인덱스로 기본 라벨·ID를 만든다. 구간 순서와 앞 구간의 끝 좌표를 연결하는 기존 규칙은 유지한다.
- `useSituationBoardData.ts`: 화면별 변환 함수를 유지하고 실제 상황판 자료 조립에서 사용한다. 현재 위치 선택과 지도 source 반영 방식은 변경하지 않았다.

실제 수정 함수와 전체 변환을 같은 Chrome에서 비교했다. 기존과 같이 경로 481개에 매회 80구간을 추가하고, 5회 중 첫 2회를 제외했다. 순서를 뒤집은 2회 실행의 6표본 평균이며 **경로 화면 자료 변환·색상 배정 시간만** 측정했다.

| 기존 구간 수 | 전체 변환 | 변경 경로만 변환 |
|---:|---:|---:|
| 9,620 | 8.30ms | 2.43ms |
| 57,720 | 57.33ms | 10.02ms |

20회 모두 전체 변환과 출력 값·현재 위치 도형이 일치했고, 변경되지 않은 경로의 객체 재사용 수도 기대값과 일치했다. 빈 구역 트리의 합성 입력이므로 실제 구역 도형·배정 규모의 변환 비용이나 화면 전체의 성능 개선을 확정하지 않는다.

검증:

- 먼저 기존 전체 변환을 호출하는 대조 구현에서 ‘변경되지 않은 경로 객체 재사용’ 검사 1개가 실패하는 것을 확인했다. 재사용 구현 후 통과했다.
- 신규 5개 회귀 검사로 앞 구간 추가, 이웃 연결선, 수정·삭제·빈 결과, 색상·최신성·차수·사건 변경, 기본 라벨 순서, 실제 상황판 Hook 연결을 확인했다. Hook 검사는 HTTP 페이지 실행을 대역으로 바꾸며 실제 서버 검증은 아니다.
- 최종 `npm run typecheck && npm run build && npm test` 통과. 60파일·312검사 통과, 실패 0. 빌드의 500kB 초과 청크 경고는 남아 있다.
- 경로 Mapper·해당 테스트·공통 슬롯 변환 파일의 ESLint와 `git diff --check` 통과. 전체 저장소 lint 검사는 하지 않았다.

- Backend·API·DB·지도 계측·배포는 변경하지 않았다. 제품 서버의 전체 로딩 재측정은 아직 하지 않았다.
