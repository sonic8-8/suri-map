# 전체 경로 조회의 요청 사이 지연 재분석

2026-10-14, Claude 검수 의견에 따라 새 계측·배포보다 보존한 793건의 요청 기록 분석을 먼저 진행했다. **계측 ON 실행에서는 HTTP 한 건의 평균 시간이 비슷한 반면, 응답을 받은 뒤 다음 요청까지의 공백이 후반에 커졌다.** 이 증가가 제품 처리인지 지도 표시 계측의 영향인지는 아직 구분하지 못했다.

## 어디에서 지연이 늘었나

[기존 전체 GPU 관측](search-path-full-gpu-observation-20261013.md)의 Resource Timing 원문을 재계산했다. 요청 1~792 각각의 HTTP 시간과 바로 뒤 공백을 198개씩 묶었다. 마지막 793번째 HTTP 607.2ms는 전체 합계에는 포함하고 아래 표에서는 제외했다.

| 요청 순서 | HTTP 평균 | 다음 요청까지 공백 평균 | 해당 묶음에서 공백 비중 |
|---|---:|---:|---:|
| 1~198 | 777.9ms | 46.5ms | 5.6% |
| 199~396 | 739.6ms | 233.0ms | 24.0% |
| 397~594 | 791.0ms | 502.1ms | 38.8% |
| 595~792 | 779.0ms | 613.4ms | 44.1% |

전체는 HTTP 합계 **611.936초** + 공백 **276.218초** = **888.154초**다. HTTP가 전체의 68.9%라는 사실과 후반 공백의 증가를 함께 다뤄야 한다. 공백은 경과 시간이며 특정 함수의 CPU 시간으로 단정하지 않는다. 요청 순서도 정확한 누적 구간 수는 아니다.

792개 공백의 중앙값은 243.8ms였다. 100ms 단위 분포는 넓게 퍼졌고, 900~1,100ms는 31개였다. 이 자료로 과거 상황판이 1초 프레임 주기에 묶였다고 결론 내리지 않는다. [별도 지도 재생](search-path-fixed-map-replay-20261014.md)의 프레임 관측은 브라우저·입력·환경이 다른 결과다.

응답 집계에는 80구간 응답 712개와 1구간 응답 61개가 있다. 응답 개수 배열과 timing 배열에 공통 요청 ID가 없어 개별 소량 응답의 시간을 확정해 합산하지 않았다.

## 남은 측정의 제약

- OFF 실행은 숨김 전환으로 중단됐고 개별 요청 시간이 보존되지 않았다. 당시 진행 기록을 ON과 빼서 계측 비용이나 OFF 공백을 만들 수 없다.
- 저장된 long-task 시작 시각은 navigation 기준, HTTP 시각은 관찰 시작 시각을 뺀 값이다. 공통 변환에 필요한 시작값이 report에 없어 둘을 직접 겹쳐 원인을 귀속하지 않았다. 현재 관찰기 파일에는 후속 수정도 있어 실행 당시 소스가 완전히 같았다는 보장은 없다.
- 코드에서 API 반환 → 검증 → 병합 → Query cache 반영 → 다음 호출은 별도 await 없는 흐름이다. 지도 idle을 기다리지 않는다. 응답 종료 후 Promise가 재개되기까지와 그 뒤 동기 처리의 시간을 구분해야 한다.
- 기존 Feature 참조가 모두 유지되는 것은 아니다. 변경된 경로와 구간의 그리기 순서 값이 바뀌면 재생성될 수 있다. 그 발생 빈도·시간은 실제 크기별 관측이 필요하다.

## 다음 순서

1. 중간·후반 누적량을 다룰 OFF 관측 방법을 정한다. 준비에 드는 요청 수·시간 상한, 중단 방법, 조회 감사 증가량과 브라우저 프레임·네트워크 조건을 실행 전에 고정한다. 초반 표본만으로 전체 수정 순위를 정하지 않는다.
2. OFF에서도 공백이 크면 응답 종료→API 반환의 잔여와 이후 동기 처리부터 나눈다. 내부 함수 경계는 현재 배포본에서 노출하지 않아 임시 프런트엔드 계측·배포 또는 차이가 명시된 로컬 앱이 필요하다. 지금은 어느 쪽도 실행하지 않았다.
3. 요청 대기와 브라우저 처리의 기여도를 대조해 첫 수정 한 곳을 고른다. HTTP가 길다는 이유만으로 DB를 원인으로 확정하지 않으며, 네트워크·본문 수신 미귀속과 기존 표시 불일치도 미완료로 유지한다.

위 재분석은 보존 자료 분석과 준비 검증이다. 당시 기존 객체 재사용 테스트 3개는 통과했고 30개는 이름 필터로 제외했다. 아래 후속 관측과 구분한다.

## OFF 후속 관측은 왜 중단됐나

2026-10-14 09:26~09:33 KST, 지도 표시 계측을 끄고 정상 상황판 조회를 한 번 실행했다. **520개 응답까지 진행을 확인했지만, 다음 확인에서 탭이 사라져 상세 시간 기록을 회수하지 못했다.** 이번 실행으로 중간·후반 공백을 비교하거나 지연 원인을 확정할 수 없다. 자동 재실행은 하지 않았다.

- 준비: 새 탭에서 12초간 숨김 전환·경로 요청이 없었다. 프레임 간격 최대9.1ms, 100ms 타이머 간격 최대103.1ms였고 사건 목록 복귀 명령도 확인했다. 기존 탭의 결과를 승계하지 않도록 계획을 수정한 뒤 Claude 재검수는 통과했다.
- 실행 조건: 응답 또는 Resource Timing 800건, 브라우저1050초, 외부 복구 시작1080초로 제한했다. 이는 전송 전 차단이나 절대 시간 보장이 아니다. 본문·개별 시간은 메모리에 쌓고 정상 중단 때 한 번 저장하는 방식이었다.
- 실패: 09:33:17에 두 카운터가520이었다. 09:33:47부터 해당 탭을 찾지 못했고, 기록 회수와 사건 목록 복귀 명령도 실패했다. 이후 브라우저 목록에 수리맵 탭이 없고 해당 Aside 세션 조회도 `Session not found`였다. 삭제 시점·원인은 확인하지 못했으며 사용자 조작이나 자동 정리로 단정하지 않는다.
- 서버 확인: 경로 요청은524건 증가했다. 구간 조회는 정상516건과 `IOException`1건, 변경분 조회는 정상7건이었다. `IOException` 행의 HTTP 상태는200이므로 524건 모두 브라우저 수신 성공이라고 해석하지 않는다. 마지막 브라우저 표본520건과의 차이4건은 후속 요청의 서버 기록이지 수신을 입증하는 자료가 아니다.
- 정리 확인: 09:34:12와09:34:42의 서버 경로 카운터가 같았다. 상황판 GET3건과 경로524건에 대응하는 조회 감사527건이 증가했다. 요청별 ID 대조는 아니다. backend/frontend 배포·시작 시각과 선택80개 경로·구간·GPS 해시가 전후 같았으며 FCM은 `mock`이었다. 전체 DB 무변경을 입증한 것은 아니다.

그 밖에 타일18건, 사건 상세1건, SSE 종료 `IOException`3건, Prometheus 스크레이프107건이 증가했다. 수색 좌표·마커를 쓰는 요청은 보내지 않았지만 조회 감사와 연결 관리 기록은 발생한다.

### 다음에는 무엇부터 바꿔야 하나

긴 조회를 반복하기 전에 탭·세션 유지 방식을 확인하고, **이미 수집한 부분까지 잃지 않도록 새 기록만 주기적으로 회수하는 방식**을 검토한다. 응답마다 커지는 전체 배열을 직렬화하는 방식으로 되돌아가지 않는다. 수집 부담·회수 실패 처리를 먼저 검증한 뒤 한 번의 상한 있는 관측을 다시 준비한다. 현재는 제안이며 수집기 변경·재실행은 하지 않았다.

이번 결과에는 개별 HTTP 시간·응답 후 공백·실행 중 프레임·숨김 타임라인이 없다. polling 시점의 `visible`만으로 전 구간 가시성을 보장하지 않는다. 네트워크 throttle·VPN·proxy, 수신 ID·커서·지도 표시도 미검증이다. 제품 변경·배포·커밋·푸시는 없으며 성능 개선 완료가 아니다.
