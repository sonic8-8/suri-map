# 남은 4구간의 경로당 응답 한도 비교

2026-10-08 Hetzner App 서버에서 경로당 응답 한도만 `1 → 4 → 1`로 바꿔 비교했다. **같은 4구간을 받는 요청은 4회에서 1회로 줄었고, 측정 3회의 중앙값은 2.362초에서 0.649초로 줄었다.** 원복 후에는 다시 4회·2.573초였다. 구간·좌표·순서는 세 조건 모두 DB와 일치했다.

[로컬 22번](../issues/local/22-repeated-search-path-page-queries.md)의 첫 가설을 작은 입력으로 검증한 결과다. 전체 이력의 표시 지연을 해결한 결과는 아니며, `4`를 운영 기본값으로 채택하지 않았다.

## 비교 조건

- 같은 Backend 이미지와 공개 URL을 사용했다. 이미지 ID는 `sha256:32a4db4a1eeb4ef453fcff6b63624514a9dc23e147c3f7a7b6f03820ae677b55`다.
- 같은 WSL Headless Chrome `147.0.7727.57` 프로세스·탭·시험 계정에서 순차 조회했다. 실제 상황판과 지도는 열지 않았다.
- 사건 `aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaa0001`, 차수 `88888888-8888-8888-8888-888888880001`의 481경로를 요청에 유지했다. 그중 `62a996fe-00f8-4d07-a604-9f176fb0e12e`만 4구간이 남은 조회 진행 상태로 만들었다. DB 기록을 줄이거나 수정한 것은 아니다.
- 첫 요청 본문은 52,996바이트이며, 대상 4구간에는 총 15좌표가 있다. 응답 전체의 최대 경로 80개·구간 80개·좌표 480개와 요청의 최대 알려진 경로 1,000개는 유지했다.
- 바꾼 설정은 `SURIMAP_BOARD_SEARCHPATH_SEGMENTSPERPATH` 하나다. 기존 이미지로 Backend만 재생성하고 health `UP`을 확인했다. `.env` 파일은 수정하지 않았다.
- 각 조건에서 전체 4구간 조회를 예열 1회 후 3회 측정했다. 예열은 아래 표에서 제외했다. 모든 요청은 조회 API이며 FCM은 `mock`이었다.

## 측정 결과

| 조건 | 실행당 요청 수 | 1회 | 2회 | 3회 | 중앙값 |
|---|---:|---:|---:|---:|---:|
| 한도 1 — 변경 전 | 4 | 2.362초 | 2.331초 | 2.365초 | 2.362초 |
| 한도 4 — 시험값 | 1 | 0.816초 | 0.646초 | 0.649초 | 0.649초 |
| 한도 1 — 원복 후 | 4 | 3.095초 | 2.573초 | 2.556초 | 2.573초 |

시간은 첫 요청 직전부터 마지막 응답의 내용 검사까지다. HTTP 왕복·응답 본문 수신과 진단 실행기의 처리 비용을 포함하며, 서버나 DB 처리 시간만을 뜻하지 않는다. Backend 재시작 전후의 예열 상태와 네트워크 변동을 완전히 통제한 성능 벤치마크는 아니다. 예열에 걸린 시간은 각각 3.097초·1.227초·4.152초였다.

한도 1에서는 매번 1구간씩 받고 마지막 요청에서 `hasMore=false`가 됐다. 한도 4에서는 첫 응답에 4구간을 받고 곧바로 완료됐다. JSON 응답 본문 합계도 2,624바이트에서 1,608바이트로 줄었다. 이는 같은 구간을 받으면서 반복되는 경로 메타데이터와 응답 구조가 줄어든 결과이며, HTTP 헤더·압축을 포함한 실제 네트워크 전송량은 아니다.

## 데이터 일치와 원복 확인

예열을 포함한 12번의 전체 조회에서 다음 검사를 통과했다.

- 같은 구간 ID 4개를 누락·중복 없이 받았다.
- 구간 버전·좌표 순번 범위·이동 유형·순서대로 나열한 좌표가 DB와 일치했다. 단일 좌표의 표시용 두 점 변환은 응답 규칙에 맞춰 비교했다.
- 마지막 응답에서 대상 경로의 조회 진행 상태가 완료됐고 `hasMore=false`였다.

시험 전후 아래 세 테이블의 건수와 모든 컬럼을 포함한 행 해시 집계가 일치했다. 기존 진단에서 제외했던 구간 추적 컬럼 3개도 이번에는 포함했다.

| 테이블 | 건수 | 전후 동일 fingerprint |
|---|---:|---|
| `search_path` | 481 | `ac090acc3853a08a4dcdfc332e7504dc` |
| `search_path_gps_point` | 340,985 | `5573a3372564b5210f41382962b26dd5` |
| `search_path_segment` | 57,083 | `5bfcfbf927cef6ebdb91dda610db0ea3` |

fingerprint는 각 행의 `to_jsonb` 결과를 MD5로 만든 뒤 정렬·결합해 다시 MD5로 만든 값이다. 조회 감사 기록 등 DB 전체가 변경되지 않았다는 뜻은 아니다.

Backend의 이미지와 전체 환경변수를 시험 전 값으로 복구했고, `.env` 파일 해시도 그대로였다. 원복 후 health `UP`과 공개 API의 정상 응답을 확인했다. 인증 정보 임시 사본을 삭제하고 시험 탭·Chrome을 종료했다.

## 해석과 다음 검증

**한 경로의 남은 구간을 작게 나눠 받는 설정이 불필요한 왕복을 만든다는 가설은 이 입력에서 확인됐다.** 다만 요청 1회의 준비 상태 검사와 개별 GPS 조회 로직은 바꾸지 않았다. 응답 전체 80구간 한도도 그대로여서 전체 57,083구간 조회는 여전히 최소 714번이 필요하다.

다음은 실제 지도 표시를 유지한 전체 이력 비교다. 경로당 한도와 응답 전체 한도를 한 요인씩 바꿔 요청 수·HTTP 시간·요청 사이 간격·첫 표시·전체 수신·초기 로딩 중 새 좌표 반영 시간을 비교해야 한다. 이번 결과만으로 적정 한도나 현장 사용 가능 여부를 결정하지 않는다.

## 실행 자료

로컬 비공유 진단 폴더 `_workspace/path-tail-comparison-20261008.p8Xtnc/`에 보존했다.

- `compare.cjs`: 동일 입력 조회·응답 검사·설정 변경과 원복. 변경 구간은 `finally`에서 원복을 시도하고, 종료 전에 원복 결과를 검사한다.
- `fixture.json`, `a-limit-1.json`, `b-limit-4.json`, `a-restored-limit-1.json`, `summary.json`: 입력과 예열·측정 결과.
- `runtime-before.json`, `database-before.json`, `database-after.json`: 비밀값을 제외한 실행 설정 정보와 데이터 fingerprint.

실행 명령은 `node _workspace/path-tail-comparison-20261008.p8Xtnc/compare.cjs <시험 세션 JSON>`이며, 응답 일치·설정 원복·데이터 무변경 검사까지 통과했다. 제품 코드·영구 설정 변경, 커밋·푸시는 없었다. 제품 테스트·빌드와 전체 이력·동시 저장·부하 시험은 이번에 실행하지 않았다.
