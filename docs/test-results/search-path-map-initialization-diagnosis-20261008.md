# 지도 초기화 대기와 브라우저 실행 환경 비교

2026-10-08, [배포 후 초기화 대기](search-path-map-deployment-20261008.md)를 재현했다. **현재 Aside 실행 환경에서 화면 갱신이 제한되는 현상과 제품의 경로 처리 비용을 구분했다.** 동일 배포본을 독립 Chrome으로 실행하면 지도 초기화와 첫 경로 렌더링이 진행됐다. 제품 코드는 바꾸지 않았으며, 전체 이력 로딩 성능은 아직 판정하지 않았다.

## 무엇을 비교했는가

- 대상: `150bbc38` 배포본, `index-DewxlEbG.js`, 동일 시험 지휘 계정·사건·수색 차수.
- 서버 자료: 경로 481개·GPS 340,985개·구간 57,083개. 새 GPS·마커를 전송하지 않고 조회만 실행했다.
- 비교: Windows Aside와 WSL의 독립 Headless Chrome. Chrome은 1440×900·DPR 1, SwiftShader 허용으로 실행했다. OS·렌더러·확장 기능이 달라 FPS 자체의 우열이나 제품 개선 배율을 비교하는 시험은 아니다.
- 관찰: 약 3초 동안 `requestAnimationFrame` 콜백, 지도 `render`, 50ms 이상 긴 메인 스레드 작업, 첫 `load`와 경로 source 존재 여부를 수집했다. 화면 캡처는 초기 Chrome 관찰 구간 뒤에 수행했다.

지도 없는 사건 목록에서부터 지연이 재현돼 전체 경로 로딩을 기다릴 필요가 없었다. 진단 스크립트는 3초 동안 프레임이 10회 미만이거나 지도에 경로 source가 없으면 종료 코드 1을 반환한다. 이는 현상을 잡기 위한 검사이며 제품 FPS 합격 기준이 아니다.

독립 Chrome은 계측을 끈 실행 1회와 켠 실행 2회 모두 초기화됐다. 마지막 계측 실행에서는 상황판 열기 직전부터 첫 페이지 완료까지 **1.947초**, 첫 경로 전달까지 **3.544초**, 첫 경로 렌더링 계측까지 **3.653초**였다. 종료 전 17페이지에서 800구간을 받았고 수집된 JavaScript 오류는 없었다. 렌더링 시각은 지도에 실제 렌더된 feature를 계측한 값이며, 전체 이력 완료나 모든 구간의 표시를 의미하지 않는다.

독립 Chrome에서도 각 관찰 구간에 긴 작업이 발생했다. 따라서 지도 초기화가 됐다는 이유로 브라우저 처리 비용이 충분히 줄었다고 판단하지 않는다. 기존 Aside 전체 로딩 시간과 이번 짧은 Chrome 관찰값을 성능 전후 수치로 비교하지 않는다.

## 원인을 어디까지 좁혔는가

검사 전 후보는 브라우저 실행 조건, 제품 화면 공통 코드, 지도 초기화 순서였다.

1. **경로 데이터 처리만으로 초당 약 1회의 갱신을 설명할 수 없다.** 지도와 경로 조회가 없는 사건 목록에서도 재현됐고, 긴 JavaScript 작업도 없었다.
2. **제품 계측은 이 현상의 필수 조건이 아니다.** Aside에서는 계측을 꺼도 재현됐다. 독립 Chrome에서는 켜도 초기화됐다.
3. **새 경로 변경분 전달 코드의 필수적인 초기화 실패는 재현되지 않았다.** 같은 배포본의 실제 React 상황판에서 첫 load, source 생성, 첫 경로 렌더링이 진행됐다.

Aside에서는 `visible`·`focused`가 모두 참이어도 프레임이 제한됐다. `bringToFront()`만 호출한 뒤에는 여전히 3초간 3프레임이고 경로 source가 없었다. 이후 화면 캡처를 한 뒤에는 첫 load와 source 생성이 확인됐지만, 다음 3초 관찰의 프레임은 다시 3회였다. 사건 목록은 활성화와 캡처 뒤 한 차례 354프레임을 기록했다. 활성화·캡처·시간 경과가 섞인 결과이므로 어느 동작이 지속적인 해결책이라고 확정하지 않는다.

**브라우저 실행 환경에 따라 재현 여부가 달라진다는 근거는 확보했지만, Aside·Windows·확장 기능·화면 노출 상태 중 정확히 무엇이 제한을 거는지는 미확정이다.** 이를 제품 초기화 순서의 결함이나 Aside 자체의 확정 결함으로 단정하지 않는다. 우선 독립 Chrome을 계측 실행기로 사용하고, 제품 코드의 `load` 순서는 유지한다.

## 별도로 발견한 배포본 확인 문제

Aside에서 루트 주소를 처음 열었을 때 예전 `index-CxihtpDv.js`를 참조하는 HTML과 빈 화면을 받았다. 일반 새로고침 뒤에도 화면이 같았다. 같은 시각 공개 HTTP와 실행 컨테이너의 HTML은 현재 `index-DewxlEbG.js`를 참조했다. 진단용 query를 붙여 새로 요청하자 현재 로그인 화면이 나왔고 이후 현재 bundle을 확인했다.

캐시 계층과 정확한 원인은 아직 확인하지 않았다. 이 빈 화면을 지도 프레임 제한과 같은 원인으로 묶지 않으며, 후속 측정에서도 실제 로드한 bundle을 확인한다.

## 종료 상태와 다음 작업

시험 탭과 독립 Chrome을 종료하고 인증 정보 임시 사본을 삭제했다. Backend health는 UP이고 경로·GPS·구간의 건수와 기존 fingerprint가 이전 기록과 일치했다. 기존 fingerprint는 구간 추적 컬럼 3개를 제외하며, 감사 기록까지 포함한 DB 전체 무변경 검사는 아니다.

다음은 독립 Chrome에서 첫 표시와 전체 이력 완료를 함께 측정하고 수신 구간 ID를 DB와 대조하는 것이다. HTTP 처리 시간과 요청 사이의 브라우저 처리 시간을 분리한 뒤 페이지 한도를 비교한다. 차수·사건·style 전환 검증도 남아 있다.

후속 [독립 Chrome 전체 이력 측정](search-path-chrome-history-20261008.md)에서 첫 경로 3.62초·전체 수신 734.542초와 57,083구간 ID 일치를 확인했다. 전체 로딩 지연과 화면 전환 검증은 여전히 남아 있다.

제품 변경·새 배포·커밋·푸시는 하지 않았다. 이번에는 실행 환경 진단만 했으므로 제품 단위 테스트·빌드를 다시 실행하지 않았다. 기존 [로컬 20번](../issues/local/20-slow-paged-search-path-display.md)의 성능 문제는 해결 완료가 아니다.
