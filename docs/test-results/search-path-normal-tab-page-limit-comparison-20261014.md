# 일반 탭에서 응답 한도를 늘려 경로 조회 비교

최신 확인은 아래 [브라우저 추적 연결](#후속-준비-지도-계측을-끈-브라우저-추적-연결--2026-10-15)이다. 앞선 절의 동작·미검증 표기는 각 시험 당시의 범위다.

2026-10-14, 같은 일반 Aside 탭에서 지도 내부 계측을 끄고 응답 한도를 임시로 늘렸다. **첫 요청부터 마지막 응답까지 10분 57초에서 3분 4초로 줄었다.** 요청 1건이 빨라진 것이 아니라, 작은 응답을 반복해서 받는 횟수가 줄어든 결과와 부합한다. 아직 지도 전체 표시·구간 누락을 검증한 결과나 제품 문제 해결은 아니다.

세 한도를 함께 조정한 ‘응답 크기 묶음’ 비교다. 각 설정의 효과를 따로 분리하지 않았다. 기존에 시험했던 값을 재사용했으며 새 기본값으로 채택하지 않았다.

같은 계정·사건·수색 차수·브라우저 탭과 Backend·Frontend 이미지를 사용했다. 다만 한도 적용을 위해 Backend를 재시작했다. 앞선 측정은 재시작 없는 실행이고 이번은 재시작 후 실행이므로 캐시·JIT 상태가 같지 않다. 네트워크·실행 시점도 고정하지 않은 단일 탐색이며, 엄격한 A/B 개선율로 일반화하지 않는다.

## 후속 확인: 계측 OFF 관찰 도구의 부족한 부분

2026-10-14 코드 점검 결과다. 새 부하 시험이나 관찰 도구 구현·실행 결과가 아니다. 다음 비교의 우선순위는 [후속 후보 선정](search-path-request-body-size-20261014.md#다음-작업)을 따른다.

| 확인할 것 | 기존 도구의 한계 | 필요한 보완 |
|---|---|---|
| 받은 구간·좌표 | OFF 도구는 응답 본문 길이와 시각만 남긴다. | 같은 본문 반환 지점에서 시험 경로 응답을 보존하고, 종료 후 DB와 대조한다. |
| 첫 경로·새 GPS 표시 | `boardMeasurement.ts`는 OFF일 때 이벤트 기록과 지도 검사를 모두 건너뛴다. | 전체 도형을 매 프레임 검사하지 않는 별도 관찰이 필요하다. |
| 전체 수신 완료 | 30초 무응답이면 `no_progress`로 목록에 복귀한다. | 정체·안전 중단과 수신 완료를 구분하고, 복귀 전에 필요한 지도 증거를 회수한다. |

예전 Headless 실행기는 응답 ID 수집과 지도 확인을 갖췄지만 그대로 실행하지 않는다. 시간 관찰은 내부 계측 ON에 의존하고, 지도 객체 탐색은 DOM의 `__reactFiber`·훅 연결 구조를 순회한다. CDP·Headless 실행 방식도 현재의 일반 Aside 탭 비교 조건과 다르다.

현재 `SearchMapCanvas`는 지도 객체를 `mapRef`에 보관하고 `onMapReady`로 전달한다. 호출부 검색에서 이 콜백은 화면 구성에 사용되며 외부 시험 관찰용 연결은 확인되지 않았다. **권장안은 기존 생성·해제 지점에 명시적으로 켠 시험에서만 지도 객체를 전달하는 작은 연결을 두는 것**이다. 일반 실행에는 전역 지도 객체를 남기지 않고, 시험 종료·지도 제거 때 연결을 해제한다. React 내부 구조 탐색을 재사용하는 안은 배포를 피할 수 있지만 버전·컴포넌트 구조에 의존하므로 권장하지 않는다. 제품 코드 변경·배포를 포함하는 권장안은 아직 승인·구현하지 않았다.

관찰기는 아래 범위만 보완한다. 기존 Aside 실행·중간 회수·시간 기록·DB 대조 로직을 재사용하며 새 실행 프레임워크를 만들지 않는다.

- 수신 본문은 시험 사건·차수로 제한하고 보존량에 상한을 둔다. 전체 파싱·좌표 해시 계산은 시간 측정 뒤에 수행한다. 참조 보존·회수도 메모리와 실행 시간을 쓰므로 관찰 비용이 0이라고 주장하지 않는다.
- 완료는 요청 부재만으로 정하지 않는다. 구간·변경분 응답의 진행 상태, 처리 중 요청, 미반영 갱신, DB 구간·좌표 대조를 함께 확인한다. 새 GPS 때문에 같은 구간의 버전이 달라질 수 있으므로 단순 ID 개수나 마지막 도착 순서로 합치지 않는다.
- 첫 표시와 지정한 새 GPS만 관찰하고 실제 관찰 간격·검사 비용을 남긴다. 표본 관찰 시각을 정확한 첫 렌더 시각이라고 부르지 않는다. 지도 source의 전체 원본 일치와 현재 화면의 렌더 확인도 구분한다.
- 새 GPS는 원래 좌표·선분과 구분되는 시험 입력으로 정하고, 입력한 좌표·구간 버전·화면 반영을 연결한다. 같은 위치의 이전 선이 조회됐다는 이유로 새 좌표 표시 성공으로 처리하지 않는다.
- 숨김·오류·상한·정체는 실패 또는 미완료로 종료한다. 회수가 실패해도 안전 종료를 미루지 않고, 이미 저장한 중간 자료와 미회수 범위를 남긴다.

다음 단계는 이 연결 방식의 변경 범위를 확인한 뒤 관찰기를 소량 입력으로 검증하는 것이다. 전체 비교 전에는 두 한도의 재시작·예열 조건, GPS 추가 범위, 중단 상한, 설정 원복을 별도로 확정한다. 이번 점검에서는 브라우저 접속·서버 재시작·GPS 쓰기를 하지 않았으며 전체 비교 항목은 미완료다.

## 시험용 지도 연결 구현 — 로컬 검증

위 제안에 대한 사용자 승인 후 구현했다. 앞 절의 ‘미승인·미구현’은 소스 점검 당시 상태이며, 현재는 **연결 코드와 로컬 테스트만 완료했고 미배포**다.

- `boardMeasurement.ts`의 `connectBoardMapObserver(map)`는 등록된 `window.__SURI_MAP_OBSERVER__`에 같은 지도 객체를 전달한다. 별도의 지도 객체·전역 지도 저장소·타이머·HTTP 요청은 만들지 않는다. 등록이 없으면 아무 작업도 하지 않는다.
- `SearchMapCanvas.tsx`에서 지도 생성 직후 연결하고, effect 정리 때 `map.remove()`보다 먼저 해제를 알린다. 등록을 교체·삭제했더라도 해당 지도에 연결했던 도구로 해제를 보낸다. 관찰 도구의 동기 오류는 경고로 남기고 지도 생성·제거를 계속한다.
- 기존 `__SURI_MAP_MEASUREMENT_ENABLED__`와 독립적이다. 시험 도구가 수행하는 조회·리스너 등록의 비용이 없어지는 것은 아니며, 이번 연결 자체는 표시 시각이나 수신 정합성을 측정하지 않는다.

시험 도구는 **상황판을 열기 전** 같은 브라우저 문서에 다음 형태로 등록한다. 이미 생성된 지도에 소급 연결하지 않는다. 아래는 객체 전달의 최소 사용 예시이며 완성된 성능 관찰기가 아니다.

```javascript
window.__SURI_MAP_MEASUREMENT_ENABLED__ = false;
window.__SURI_MAP_OBSERVER__ = {
  map: null,
  connect(map) { this.map = map; },
  disconnect(map) { if (this.map === map) this.map = null; },
};
```

이후 같은 페이지에서 `window.__SURI_MAP_OBSERVER__.map`으로 MapLibre 메서드를 호출할 수 있다. React 내부 트리 탐색은 필요 없다. 생성 직후에는 style·source가 아직 준비되지 않을 수 있으므로 관찰기가 해당 상태를 확인해야 한다. 지도 객체는 읽기 전용 프록시가 아니므로 도구는 `setData`·`remove` 등 제품 상태를 변경하는 메서드를 호출하지 않는다.

`connect`·`disconnect`는 동기 콜백이다. 실제 관찰기가 추가한 리스너·타이머·객체 참조는 그 도구의 `disconnect`에서 정리한다. 화면을 유지한 채 시험만 끝낼 때도 도구가 먼저 정리하고 등록을 삭제해야 한다. **등록 삭제만으로 현재 연결이 해제되지는 않는다.** React 컴포넌트가 해제될 때 기존 도구의 `disconnect`가 다시 호출될 수 있으므로, 정리 함수는 반복 호출과 연결 도중 실패에 안전해야 한다. 전체 비교 도중 지도 인스턴스가 교체되면 서로 다른 지도의 시각을 합치지 말고 해당 실행을 무효로 처리한다.

탭 종료나 `location.replace` 같은 문서 이동에서는 React 정리 호출이 보장되지 않는다. 관찰기는 이동 전에 증거를 회수하고, 예기치 않은 종료에 대비해 중간 기록도 보존해야 한다. 또한 이 전역 등록은 시험 편의 기능이지 접근 제어 장치가 아니다.

두 실행의 보존 기록에는 `진행 중 changes 완료 → segments 한 페이지 → 새 좌표를 포함한 changes` 순서가 나타났다. 저장 HTTP 응답 뒤 첫 changes가 끝나기까지 남은 시간은 A 52.4ms, B 1,075.3ms였다. 그 다음 segments는 911.8ms·971.1ms였고 요청 사이 공백 합계는 8.1ms·4.3ms였다. 대상 changes가 시작되기까지 기다린 972.3ms·2,050.7ms와 합계가 맞는다. 이는 순서·종류·시간으로 연결한 보조 근거이며 요청 ID 조인은 아니다.

대상 changes 자체도 첫 바이트까지 A 965.8ms·B 1,190.8ms가 걸렸다. 이후 본문 전송은 각각 1.3ms·1.4ms였다. 따라서 이 구간은 큰 응답 다운로드보다 첫 응답 대기의 비중이 크다. 단, 서버 처리와 네트워크 왕복은 분리하지 못했다.

현재 코드와 기록은 직렬 조회 대기와 부합한다. 그러나 당시 SSE 수신·갱신 신호 시각은 계측 OFF로 남지 않았고, 한도 조건과 전송 시점 차이도 섞였다. **조회 순서를 바꾸면 해결된다고 확정한 결과는 아니다.** 기존 정상 동작을 확인하는 관련 테스트 4개 파일·32개는 통과했지만 실제 SSE부터 지연된 조회까지 연결한 재현 테스트는 아니다.

다음은 실제 SSE 수신 훅·공통 갱신·경로 조회 훅을 연결한 로컬 재현이다. 신호가 도착하는 시점과 HTTP 응답 완료를 제어해 요청 순서·신규 버전 반영·이력 진행을 확인한다. 그 뒤 필요한 짧은 실제 추적에서 SSE·조회 선택·동일 요청의 브라우저/서버 시간을 연결한다. 새 계측·GPS 쓰기·서버 설정 변경은 아직 실행하지 않았다.

호출 흐름, 해석, 다음 검증 범위의 Claude 검수는 통과했고 필수 수정 지적은 없다. 검수자가 테스트를 직접 실행하거나 배포본을 확인한 것은 아니다.

## 후속 검증: SSE 도착 시점별 조회 대기 로컬 재현 — 2026-10-15

[useIncidentBoardEvents.test.tsx](../../frontend/src/app/board/useIncidentBoardEvents.test.tsx)에 실제 SSE 파서·수신 훅·공통 갱신·경로 조회·응답 병합을 연결했다. SSE 전송과 경로 HTTP 응답만 대체하고 가짜 시계로 응답 완료 시점을 제어했다. 제품의 조회 정책은 변경하지 않았다.

- 변경분 조회 중 알림은 현재 요청의 남은 시간과 다음 이력 한 페이지를 기다렸다. 잔여 400ms·이력 700ms 입력에서 다음 변경분 요청은 1,100ms 뒤 시작했다.

- 알림 없는 대조는 추가 변경분 조회 없이 끝났다. 신규 버전·좌표 반영, 기존 과거·최근 구간 보존, 동시 경로 요청 최대 1, 중복 eventId 무시를 검사했다.

이 숫자는 조회 순서를 확인하기 위한 입력이지 실제 서비스 지연이나 합격 기준이 아니다. 현재 동작을 검증한 결과이며 성능 수정·배포·실서버 원인 확정은 아니다. 실제 지도 렌더링·DB·나머지 활성 상황판 조회와의 경합은 포함하지 않는다.

첫 Claude 검수에서 다음 이력 한 페이지를 받으면 이력이 모두 끝나는 조건만 검사한 누락을 지적했다. 이력이 계속 남는 상태의 changes 중·segments 중 신호 유/무 4개 사례를 추가했다. 신호가 있으면 변경분을 먼저 받은 뒤 이력을 이어가고, 없으면 이력을 계속 받는 차이를 확인한다. 동시 요청 수·오류 검사는 제품 코드의 예외 처리에 삼켜지지 않도록 대역 밖으로 옮겼다.

수정 후 새 8개 테스트와 프론트엔드 전체 62개 파일·332개 테스트, 타입 검사·빌드·새 파일의 ESLint/포맷 검사가 통과했다. 빌드의 기존 500kB 초과 청크 경고는 남는다. 다음은 전역 지도 계측을 켜지 않고 SSE 도착·조회 선택·동일 HTTP 요청 비용을 연결할 최소 추적 범위와 원복 절차를 정하는 것이다.

Claude 재검수도 통과해 미해결 필수 수정은 없다. 재개 요청 본문의 cursor 정확성, 재접속 경로는 이번 테스트 범위 밖이며 실제 성능값이나 서비스 개선을 검수한 것은 아니다.

## 후속 수정: 조회 우선순위·실패 복구 구현 — 2026-10-15

기존에는 변경분을 받은 뒤 남은 이력 한 페이지를 조회했다. 그 사이 새 변경이 알려져도 다음 변경분 조회까지 기다렸다. 사용자 Q1·Q2의 1번 선택에 따라 다음과 같이 바꿨다.

- 최초 이력으로 변경 추적 기준을 확보한 뒤, 변경분에 최대 두 페이지 연속 차례를 준다. 이어받을 이력이 있으면 그다음에는 이력을 조회한다. 변경분이 없으면 이력을 계속 받고, 이력이 끝났으면 변경분을 계속 받는다.
- 일시 실패 시 재시도 대기시간을 지킨 뒤 다른 종류의 필요한 조회에도 차례를 준다. 최초 이력을 아직 받지 못한 경우에는 이력부터 재시도한다.
- 이력·변경분의 오류와 실패 횟수를 각각 관리한다. 한쪽 성공이 다른 쪽 미복구 오류나 실패 횟수를 지우지 않는다.
- 같은 조회 범위에서 진행 중인 경로 HTTP는 여전히 하나다. 알림별 요청을 쌓거나 매번 취소하는 방식, 병렬 조회, SSE에 좌표를 직접 싣는 방식은 추가하지 않았다.

조회 순서와 실패 복구의 테스트 실패를 먼저 확인하고 구현 후 통과를 확인했다. Claude 1차 검수에서 최초 이력 재시도의 요청 종류를 검사하지 않는 누락을 발견해 순서 단언을 추가했다. 보호 조건을 임시 제거하면 해당 검사가 실패하고 원복하면 통과하는 것도 직접 확인했다. 전체 프론트엔드 62파일·337테스트, 타입 검사·빌드·변경 파일 린트/포맷 검사를 통과했다. 기존 큰 청크 경고는 남는다. Claude 재검수도 통과했고 미해결 필수 수정은 없다. 검수자는 코드를 읽었으며 테스트를 직접 실행한 것은 아니다.
