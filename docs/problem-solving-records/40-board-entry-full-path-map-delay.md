# [BE/FE] 상황판 진입 후 전체 수색 경로가 지도에 그려지기까지 목표 5초를 넘는 문제

## 문제 배경

상황판은 지휘관이 업무폰에서 기록한 수색 경로를 지도에서 확인하는 웹 화면입니다. 사건 목록에서 "상황판 열기"를 누르면 화면은 상황판 정보와 경로 이력을 서버에서 받아 지도에 그립니다. 2026-10-16부터 고정 시험 사건(경로 481개, 구간 57,097개, 좌표 341,069개)의 최초 경로 이력은 응답 한 건으로 받습니다([문제 해결 기록 38](38-repeated-search-path-page-queries.md)).

같은 날 포트폴리오 시험 가정으로 표시 목표를 정했습니다. 사건 목록에서 진입을 클릭한 시각부터, 받은 전체 구간이 지도에 반영되고 그려진 것이 확인될 때까지 5초 이내입니다. 현장에서 확인한 허용 시간은 아닙니다.

배포 후 측정은 이 목표에 미치지 못했습니다. 2026-10-16 배포본을 일반 Chrome 탭에서 1회 쟀을 때, 경로 응답 본문을 다 읽기까지 9.0초, 첫 경로가 지도에서 관찰되기까지 12.2초가 걸렸습니다. 이 측정은 진입 클릭이 아니라 관찰기를 설치한 시각부터 쟀고 관찰기 비용도 포함합니다. 2026-10-19 fetch size 조정을 배포한 뒤에도 경로 요청 한 건이 브라우저에서 4.05~4.49초 걸렸습니다. 요청 하나가 목표 시간의 대부분을 쓰고, 그 뒤에 지도 반영이 이어집니다.

경로가 그려지기 전까지 지휘관은 이미 수색한 곳을 지도에서 확인할 수 없습니다.

### 문제 해결: 체크리스트

- [ ] 사용자의 일반 Chrome 탭에서, 사건 목록의 진입 클릭부터 받은 전체 구간이 지도에 반영되고 렌더가 확인될 때까지의 3회 중앙값이 5초 이내인가?

판정 조건은 [경로 표시 목표](../features/situation-board.md#화면과-관측에서-남은-요구)를 따릅니다. 위 고정 시험 사건과 응답 한도(최초 이력이 응답 1건에 담기는 조건), 실서버(Hetzner 독일, Cloudflare 경유)에서 잽니다. 관찰기 비용을 포함한 시간으로 판정하며, 관찰기가 진입 클릭과 전체 반영 완료를 같은 브라우저 시계로 기록해야 합니다. 같은 합의의 첫 표시(5초)와 새 좌표 반영(3초)은 이 이슈에서 판정하지 않습니다.

## 원인 분석과 선택지

아래 시각표는 첫 번째 변경(서버 좌표 배열 읽기, 6d2d1002)을 배포한 뒤, 따로 띄운 Windows Chrome(실제 GPU, 화면 1640×990)에서 1회 잰 값입니다. 일반 탭에서 1회 잰 값(7.57초)과 흐름이 거의 같았습니다.

| 클릭 뒤 시각 | 사건 |
|---:|---|
| 0.95초 | 지도 생성, 경로 요청 시작 |
| 3.57초 | 경로 응답 본문 수신 끝 |
| 3.69초 | 받은 경로를 화면 데이터에 병합 끝 |
| 7.53초 | 지도가 그리기를 마침(idle) |

7.53초는 경로 요청 전 대기 0.95초, 경로 응답 2.62초, 병합 0.12초, 지도 반영 3.84초로 나뉩니다. 서버 좌표 읽기, 경로 요청 시점, 지도 도형 처리는 서로 독립적으로 고칠 수 있어 구간마다 원인을 확인하고 따로 고쳤습니다.

### 서버가 좌표 행마다 결과 객체를 만드는 비용

회선을 빼고 서버 컨테이너 안에서 직접 보낸 경로 요청도 3.12~3.24초 걸렸습니다. 처음에는 좌표를 읽을 때 숫자와 시각 글자를 해석하는 비용을 의심해 숫자형으로 읽도록 바꿨습니다(875eae82). 로컬 Service 조회는 2.53~3.23초에서 2.14~2.33초로 줄었지만, 실서버 요청은 3.14초에서 3.24초와 3.37초로 측정 흔들림 안에 있었습니다.

그래서 실서버에 임시 계측(측정 후 되돌림)을 넣어 서버 안 시간을 나눴습니다. 데워진 요청 2.9초 중 좌표 SQL이 1.86초였고, 그 안에서 JDBC가 행을 받는 데 약 1.0초, MyBatis가 좌표 행마다 결과 객체를 만들고 값을 넣는 데 약 0.9초를 썼습니다. 열 값을 꺼내는 비용은 -36~133ms로 작았습니다. 같은 SQL을 psql로 같은 네트워크 경로에서 받으면 DB 실행과 전송이 0.64초였습니다. 시간은 DB가 아니라 34만 개 행을 하나씩 다루는 앱 쪽에 쌓였습니다.

좌표 SQL이 행 대신 요청 범위마다 한 행으로 경도, 위도, 측정 시각 배열을 돌려주면, 고정 시험 사건에서 34만 행이 범위 수(481개) 수준으로 줄어듭니다. 행 단위 비용을 없애면서 응답 형식은 그대로 둘 수 있어 이 방법을 선택했습니다.

### 경로 요청이 상황판 응답을 기다리는 대기

경로를 조회하려면 수색 차수 ID가 필요한데, 화면은 이 값을 상황판 응답에서만 얻었습니다. 그래서 경로 첫 요청은 상황판 응답이 끝난 0.955초에야 나갔고, 그동안 메인 스레드는 거의 쉬었습니다.

앱의 경로 조회를 막고 같은 요청을 보내는 시점만 바꿔 각 3회 비교했습니다. 경로 응답이 끝나는 시각의 중앙값은 상황판 응답 뒤에 보내면 3.65초, 클릭과 동시에 보내면 2.73초였습니다. 두 요청을 겹쳐 보내도 경로의 서버 대기(2.29초 대 2.31초)와 상황판 응답이 끝나는 시각은 늘지 않았습니다.

사건 목록은 이미 사건을 알고 있으므로, 목록 응답에 진행 중 차수를 실어 상황판으로 넘기면 상황판 응답을 기다리지 않고 경로 요청을 시작할 수 있습니다. 목록의 차수가 상황판의 차수와 다르면 상황판 차수로 다시 조회해 정확성은 유지합니다.

### 지도가 구간 57,097개를 도형 하나씩 처리하는 비용

병합이 끝난 뒤 지도 반영 3.84초는 기다림이 아니라 지도 라이브러리(MapLibre)의 계산이었습니다. Chrome 성능 기록에서 메인 스레드는 0.75초를 썼습니다. 그중 도형 57,097개를 지도 작업자(Web Worker)로 넘기면서 객체 전체를 훑는 처리가 약 0.49초, React의 경로 변환과 슬롯 조립이 약 0.19초였습니다. 이어서 작업자는 받기, GC, 색인에 0.76초, 화면용 타일 만들기에 2.02초를 썼습니다. 모두 도형 수에 비례하는 일입니다.

실서버의 경로 source 데이터를 저장해, 같은 Chrome에서 모양만 바꿔 데이터 전달(setData)부터 idle까지 각 3회 쟀습니다.

| 변형 | 도형 수 | 중앙값 |
|---|---:|---:|
| 그대로 | 57,097 | 4.20초 |
| 읽는 곳이 없는 속성 제거 | 57,097 | 3.53초 |
| 속성 제거와 이웃 구간 잇기 | 810 | 1.57초 |

속성 제거만 한 변형은 3회 모두 "그대로"의 1회차(3.15초)보다 느려 효과를 확정하지 못했습니다. 같은 경로에서 표시 값이 같고 끝점이 이어지는 구간을 선 하나로 이으면 도형이 810개로 줄고 시간도 크게 줄어, 이 방법을 선택했습니다. zoom 11.1, 14, 16에서 픽셀을 비교했을 때 그리기 순서 차이는 0픽셀이었습니다.

## 변경 내용과 트레이드오프

세 원인에 각각 다음 변경을 적용했습니다.

- **서버 좌표 배열 읽기(6d2d1002, BE):** `findBoardPointRuns`가 요청 범위마다 한 행으로 경도, 위도, 측정 시각(마이크로초) 배열을 `array_agg`로 돌려줍니다. 마이크로초 정수로 담을 수 없는 시각(294247-01-01 이상이나 무한 시각)이 있는 범위만 기존 좌표 행 SQL로 다시 읽습니다. 응답 계약은 바꾸지 않았습니다.
- **지도 도형 잇기(557a53a4, FE):** `createMovementPathFeatureMapper`가 같은 경로에서 표시 값(색, 이동 유형, 활성 차수, 업무폰 최신성)이 같고 끝점이 이어지는 구간을 선 하나로 잇습니다. 지도 도형에서 읽는 곳이 없는 속성 6개(slot, opId, accountId, startedAt, endedAt, label)를 뺐습니다.
- **경로 조회 선시작(8835a657, BE/FE):** 사건 목록 API의 item에 `activeOpId`를 추가했습니다([API](../api/api-spec.md#get-apiincidents)). 목록의 "상황판 열기"가 이 값을 화면 이동 상태로 넘기고, 상황판 응답이 오기 전에만 이 차수로 경로 조회를 시작합니다.

### 트레이드오프와 유지한 범위

- 이은 선은 이음점에서 구간마다 둥근 끝과 반투명 선이 겹쳐 칠해지던 가장자리 픽셀이 달라집니다. 픽셀 비교에서 큰 차이는 그려진 픽셀의 0.8~4.3%였습니다.
- 지도 도형에서 구간 시각, 계정, 차수 값을 뺐습니다. 원본 값은 화면 경로 데이터(`BoardMovementPath`)와 API에 그대로 남습니다. 계획된 경로 재생은 지도 도형이 아니라 인수인계 타임라인 API의 좌표 시각을 쓰도록 요구 문서에 정했습니다([도형 단위 요구](../features/situation-board.md#화면과-관측에서-남은-요구)).
- 목록의 차수와 상황판의 차수가 다르면 먼저 시작한 조회를 버리고 상황판 차수로 다시 조회합니다. 같으면 같은 조회를 그대로 이어 씁니다.
- 주소를 직접 열어 상황판에 들어오면 목록이 넘긴 차수가 없어, 이전처럼 상황판 응답을 기다린 뒤 경로를 조회합니다.

## 검증 결과

같은 방법(따로 띄운 Windows Chrome, 실제 GPU, 정식 로그인, 조회만 함, 데우기 1회 뒤 측정)으로 클릭부터 지도 idle까지를 쟀습니다.

| 시점 | 커밋 | 클릭부터 그리기 끝 | 비고 |
|---|---|---:|---|
| 지도 도형 잇기 배포 전 | 6d2d1002 | 7.53초 | 1회 |
| 지도 도형 잇기 배포 후 | 557a53a4 | 6.10초 | 3회 중앙값 |
| 경로 조회 선시작 배포 직후 | 8835a657 | 5.30초 | 3회 중앙값, 배포 확인 27초 뒤 |
| 같은 배포본 재측정 | 8835a657 | 4.65초 | 3회 중앙값(4.65, 4.41, 4.75초) |

마지막 측정의 중앙값은 경로 요청 시작 0.004초, 경로 응답 끝 2.68초, 병합 끝 2.82초, 지도 반영 1.76초입니다.

변경마다 다음을 확인했습니다.

- **서버 좌표 배열 읽기:** 로컬에서 응답 JSON의 SHA-256이 변경 전과 같았습니다. 실서버 컨테이너 안 요청은 3.12~3.24초에서 2.32~2.43초(데워진 상태), 브라우저 한 요청은 4.05~4.49초에서 2.36~2.81초가 됐습니다.
- **지도 도형 잇기:** 실서버 데이터를 새 함수에 넣으면 실험과 같은 도형 810개가 나왔습니다. 481개 경로 끝에 구간이 붙는 증분 갱신에서 바뀐 도형 판정이 약 215ms에서 98ms로 줄었습니다(로컬 계산). 배포 후 병합 뒤 지도 반영은 1.93초(3회 중앙값)였습니다.
- **경로 조회 선시작:** Backend 전체 1,429개 중 12개가 실패했습니다. 실패는 SSE 4개, TomcatProxy 7개, SecurityConfig 1개로, 변경 전부터 같은 로컬 HTTP 환경에서 실패하던 테스트입니다. PostgreSQL 통합 테스트와 Frontend 346개는 통과했습니다. 배포 후 경로 요청은 클릭 뒤 4~10ms에 나갔고, 3회 모두 목록의 차수가 전달됐습니다.
- 세 변경 모두 Codex 읽기 전용 검수를 통과했습니다.

### 목표 판정이 남은 이유

체크리스트는 체크하지 않았습니다. 4.65초는 따로 띄운 Chrome에서 지도 idle까지 잰 값이고, 판정 조건인 사용자의 일반 Chrome 탭과 전체 구간 렌더 확인(구간 ID 대조)을 적용하지 않았습니다. 관찰기가 진입 클릭과 전체 반영 완료를 같은 브라우저 시계로 기록하도록 보완한 뒤 다시 재야 판정할 수 있습니다.

- 새 좌표 반영(목표 3초)은 이번 변경 뒤 재지 않았습니다.
- 배포 직후 측정(5.30초)에서 경로 응답이 1회 약 1초 늦었습니다. 서버가 덜 데워진 영향으로 보이지만 확인하지 않았습니다.
- 남은 큰 구간은 경로 서버 처리(약 2.3초)와 지도 반영(약 1.8초)입니다.

측정 조건, 단계별 수치와 한계는 [상황판 진입 측정 기록](../test-results/search-path-board-entry-20261020.md)에 있습니다.
