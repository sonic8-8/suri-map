# [BE/FE] 상황판 진입 후 전체 수색 경로가 지도에 그려지기까지 목표 5초를 넘는 문제

## 문제 배경

상황판은 지휘관이 업무폰에서 기록한 수색 경로를 지도에서 확인하는 웹 화면이다. 지휘관이 사건 목록에서 "상황판 열기"를 누르면, 서버에서 받은 상황판 정보와 경로 이력이 지도에 그려진다. 2026-10-16부터 고정 시험 사건(경로 481개, 경로 구간 57,097개, 좌표 341,069개)의 최초 경로 이력은 응답 한 건으로 받는다([문제 해결 기록 38](38-repeated-search-path-page-queries.md)).

같은 날 포트폴리오 시험 가정으로 표시 목표를 정했다. 목표는 사건 목록에서 진입을 클릭한 시각부터, 받은 전체 경로 구간이 지도에 반영되고 그려진 것이 확인될 때까지 5초 이내다. 현장에서 확인한 허용 시간은 아니다.

배포 후 측정은 이 목표에 미치지 못했다. 2026-10-16 배포본을 일반 Chrome 탭에서 1회 쟀다. 경로 응답 본문을 다 읽기까지 9.0초가 걸렸다. 첫 경로가 지도에서 확인되기까지는 12.2초가 걸렸다. 이 측정은 진입 클릭이 아니라 당시의 경로 표시 시간 측정 스크립트를 설치한 시각부터 쟀다. 이 값에는 측정 스크립트 비용도 포함된다. 2026-10-19 fetch size 조정을 배포한 뒤에도 경로 요청 한 건이 브라우저에서 4.05~4.49초 걸렸다. 요청 하나가 목표 시간의 대부분을 쓰고, 그 뒤에 지도 반영이 이어진다.

경로가 그려지기 전까지 지휘관은 이미 수색한 곳을 지도에서 확인할 수 없다.

### 문제 해결: 체크리스트

- [ ] 사용자의 일반 Chrome 탭에서, 사건 목록의 진입 클릭부터 받은 전체 경로 구간이 지도에 반영되고 렌더가 확인될 때까지의 3회 중앙값이 5초 이내인가?

판정 조건은 [경로 표시 목표](../features/situation-board.md#화면과-관측에서-남은-요구)를 따른다. 위 고정 시험 사건과 응답 한도(최초 이력이 응답 1건에 담기는 조건), 실서버(Hetzner 독일, Cloudflare 경유)에서 잰다. 판정에는 측정 스크립트 비용을 포함한 시간을 쓴다. 진입 클릭과 전체 반영 완료는 경로 표시 시간 측정 스크립트로 같은 브라우저 시계에 기록해야 한다. 같은 합의의 첫 표시(5초)와 새 좌표 반영(3초)은 이 이슈에서 판정하지 않는다.

## 원인 분석과 선택지

아래 시각표는 첫 번째 변경(서버 좌표 배열 읽기, 6d2d1002)을 배포한 뒤 잰 값이다. 따로 띄운 Windows Chrome(실제 GPU, 화면 1640×990)에서 1회 쟀다. 일반 탭에서 1회 잰 값(7.57초)과 흐름이 거의 같았다.

| 클릭 뒤 시각 | 사건 |
|---:|---|
| 0.95초 | 지도 생성, 경로 요청 시작 |
| 3.57초 | 경로 응답 본문 수신 끝 |
| 3.69초 | 받은 경로를 화면 데이터에 병합 끝 |
| 7.53초 | 지도가 그리기를 마침(idle) |

7.53초는 경로 요청 전 대기 0.95초, 경로 응답 2.62초, 병합 0.12초, 지도 반영 3.84초로 나뉜다. 서버 좌표 읽기, 경로 요청 시점, 지도 도형 처리는 서로 독립적으로 고칠 수 있다. 그래서 단계마다 원인을 확인하고 따로 고쳤다.

### 서버가 좌표 행마다 결과 객체를 만드는 비용

회선을 빼고 서버 컨테이너 안에서 직접 보낸 경로 요청도 3.12~3.24초 걸렸다. 처음에는 좌표를 읽을 때 숫자와 시각 글자를 해석하는 비용을 의심했다. 그래서 숫자형으로 읽도록 바꿨다(875eae82). 로컬 Service 조회는 2.53~3.23초에서 2.14~2.33초로 줄었다. 하지만 실서버 요청은 3.14초에서 3.24초와 3.37초로, 측정 흔들림 안에 있었다.

그래서 실서버에 임시 계측을 넣어(측정 후 되돌림) 서버 안 시간을 나눴다. 데워진 요청 2.9초 중 좌표 SQL이 1.86초였다. 그 안에서 JDBC가 행을 받는 데 약 1.0초를 썼다. MyBatis가 좌표 행마다 결과 객체를 만들고 값을 넣는 데에는 약 0.9초를 썼다. 열 값을 꺼내는 비용은 -36~133ms로 작았다. 같은 SQL을 psql로 같은 네트워크 경로에서 받으면 DB 실행과 전송이 0.64초였다. 시간은 DB가 아니라 34만 개 행을 하나씩 다루는 앱 쪽에 쌓였다.

좌표 SQL을 고쳐 요청 범위마다 한 행에 경도, 위도, 측정 시각 배열을 담으면, 고정 시험 사건에서 34만 행이 범위 수(481개) 수준으로 줄어든다. 이 방법은 행 단위 비용을 없애면서 응답 형식은 그대로 둘 수 있어서 선택했다.

### 경로 요청이 상황판 응답을 기다리는 대기

경로를 조회하려면 수색 차수 ID가 필요하다. 그런데 이 값은 상황판 응답에서만 받을 수 있었다. 그래서 경로 첫 요청은 상황판 응답이 끝난 0.955초에야 나갔다. 그동안 메인 스레드는 거의 쉬었다.

앱의 경로 조회를 막고, 같은 요청을 보내는 시점만 바꿔 각 3회 비교했다. 경로 응답이 끝나는 시각의 중앙값은 상황판 응답 뒤에 보내면 3.65초, 클릭과 동시에 보내면 2.73초였다. 두 요청을 겹쳐 보내도 경로의 서버 대기(2.29초 대 2.31초)는 늘지 않았다. 상황판 응답이 끝나는 시각도 늘지 않았다.

사건 목록 응답에는 이미 사건 정보가 들어 있다. 그래서 목록 응답에 진행 중 차수를 실어 상황판으로 넘기면, 상황판 응답을 기다리지 않고 경로 요청을 시작할 수 있다. 목록의 차수가 상황판의 차수와 다르면 상황판 차수로 다시 조회해 정확성을 유지한다.

### 지도가 경로 구간 57,097개를 도형 하나씩 처리하는 비용

병합이 끝난 뒤 지도 반영 3.84초는 기다림이 아니라 지도 라이브러리(MapLibre)의 계산이었다. Chrome 성능 기록에서 메인 스레드는 0.75초를 썼다. 그중 도형 57,097개를 지도 작업자(Web Worker)로 넘기면서 객체 전체를 훑는 처리가 약 0.49초였다. React의 경로 변환과 슬롯 조립은 약 0.19초였다. 이어서 지도 작업자는 받기, GC, 색인에 0.76초를 썼다. 화면용 타일 만들기에는 2.02초를 썼다. 모두 도형 수에 비례하는 일이다.

실서버의 경로 source 데이터를 저장해, 같은 Chrome에서 모양만 바꿔 데이터 전달(setData)부터 idle까지 각 3회 쟀다.

| 변형 | 도형 수 | 중앙값 |
|---|---:|---:|
| 그대로 | 57,097 | 4.20초 |
| 읽는 곳이 없는 속성 제거 | 57,097 | 3.53초 |
| 속성 제거와 이웃 경로 구간 잇기 | 810 | 1.57초 |

속성 제거만 한 변형은 3회 모두 "그대로"의 1회차(3.15초)보다 느려서 효과를 확정하지 못했다. 같은 경로에서 표시 값이 같고 끝점이 이어지는 경로 구간을 선 하나로 이으면 도형이 810개로 줄고 시간도 크게 줄었다. 그래서 이 방법을 선택했다. zoom 11.1, 14, 16에서 픽셀을 비교했을 때 그리기 순서 차이는 0픽셀이었다.

### 업로드마다 새로 생긴 경로 구간이 경로 이력 응답을 키우는 비용

위 세 변경을 배포한 뒤에도 판정이 5초 근처에서 갈렸다([판정 보류](#측정-스크립트-비용-분리와-판정-보류)). 그래서 2026-10-31에, 남은 단계 중 가장 긴 경로 이력 요청의 서버 첫 바이트(2.28~2.57초)를 나눠 봤다. 이 원인에 대한 변경은 2026-11-02에 실서버에 적용됐다([변경 내용](#변경-내용과-트레이드오프), [재측정](#경로-구간을-이어-붙인-뒤-실서버-재측정)).

실서버 지표(Prometheus)로 보면 경로 이력 요청의 앱 처리 시간은 평균 2.37초였다. 회선과 Cloudflare, nginx 몫은 약 0.15초였다. 실서버 DB에서 두 SQL을 `EXPLAIN ANALYZE`로 재 보니, 경로 구간 SQL(`findBoardSegments`)은 약 0.2초, 좌표 배열 SQL(`findBoardPointRuns`)은 약 0.76초였다. 좌표 배열 SQL의 식을 하나씩 바꿔 재 보니, 경도와 위도를 float8로 바꾸는 데 약 0.25초가 들었다. 측정 시각을 계산하는 데에는 약 0.17초가 들었다.

나머지 1초 남짓은 앱에서 쓴 시간이다. 그래서 처음에는 앱이 좌표 배열을 받아 바꾸는 단계에 1초 가까이 걸린다고 의심했다. JSON 변환이 0.3초를 넘는다는 가설도 함께 세웠다. 실서버에는 단계별 계측을 넣지 않았다. 대신 같은 규모의 로컬 성능 테스트(`SearchPathBoardServiceTest`, 경로 468개, 좌표 336,960개)에 임시 계측을 넣어 나눴다(측정 뒤 되돌림). 서비스 호출은 0.79초(DB 실행 0.44초, DB 밖 0.35초)였다. JSON 변환은 0.15초였다. 좌표 배열을 받아 해석하는 데는 약 0.16초가 들었다. 두 가설 모두 맞지 않았다. 시간을 혼자 차지하는 단계는 없었고, 데이터 양에 비례하는 일이 단계마다 고르게 나뉘어 있었다. 실서버 CPU(EPYC 2.0GHz)는 코어 하나의 속도가 로컬보다 약 2.5배 느리다. 로컬 합계 0.94초에 2.5를 곱하면 약 2.35초로, 실서버 2.37초와 비슷하다. 실서버에서 단계별로 재지 않았으므로 이 대응은 추정이다.

그래서 처리하는 데이터 양을 살폈다. 10월 31일 경로 이력 응답 본문(약 22MB)을 나누면 다음과 같다.

| 구성 | 크기 | 비율 |
|---|---:|---:|
| 경로 구간 정보(ID, 버전, 순번, 이동 유형, 시각) | 11.68MB | 53% |
| 좌표 숫자 | 7.39MB | 34% |
| 도형 포장(geometry의 type과 괄호) | 2.06MB | 9% |

좌표보다 경로 구간 정보가 더 크다. 실서버 DB를 읽기 전용으로 조회하니 경로 구간 57,097개 중 56,509개가 좌표 6개짜리였다. 가장 긴 경로 구간도 좌표 6개였다. 사용자가 보정한(`MANUAL`) 경로 구간은 없었다.

경로 구간이 이렇게 잘게 나뉜 원인은 저장 방식에 있다. Android에서는 좌표가 120개 모였거나, 2개 이상 모이고 측정 시각 범위가 10초 이상이 되면 좌표 묶음을 올린다. 좌표를 추가할 때는 이번 좌표 묶음의 좌표만으로 경로 구간을 나눈다(`SearchPathService.autoSegments`). 그래서 직전 경로 구간과 이동 유형이 같아도 좌표 묶음마다 새 경로 구간이 생긴다. [용어집](../../GLOSSARY.md)에 적힌 경로 구간의 정의는 "같은 이동 유형으로 구분하는 부분"이다. 하지만 저장된 데이터는 업로드 단위로 나뉘어 있다. 같은 데이터에서 이동 유형이 같은 이웃 경로 구간을 묶으면 810개가 된다. 이 수는 지도 도형 잇기 뒤의 도형 수와 같다. 지도 도형은 받은 뒤에 이어 붙이고 있지만, 서버 응답에는 여전히 경로 구간 57,097개가 담긴다. 그만큼 조회와 변환이 일어난다. 또 경로 구간 도형에는 좌표 묶음 경계의 두 좌표를 잇는 선이 들어가지 않는다. 그래서 경로 구간 도형 길이를 더하는 수색 이력 요약에서 도보 거리와 차량 거리가 실제보다 짧게 나온다.

경로 구간 수만 줄였을 때의 효과를 보려고, 같은 로컬 성능 테스트에서 경로와 좌표 수는 그대로 두고 경로 구간 하나의 좌표 수만 바꿔 쟀다. 테스트에서 경로 구간을 넣는 SQL에, 경로 구간당 좌표 수를 환경 변수로 받는 임시 수정을 넣었다(측정 뒤 되돌림). 응답 한도는 실서버 값(1000/100000/100000/400000)으로 두었다. 값은 예열 2회 뒤 5회의 중앙값이다.

| 실행 | 경로 구간당 좌표 | 경로 구간 수 | 서비스 호출 | JSON 변환 | 합계 | JSON 크기 |
|---|---:|---:|---:|---:|---:|---:|
| 1차 | 6개(당시) | 56,160 | 761ms | 143ms | 904ms | 19.6MB |
| 1차 | 60개 | 5,616 | 570ms | 80ms | 650ms | 7.2MB |
| 1차 | 360개 | 936 | 558ms | 64ms | 622ms | 6.0MB |
| 2차 | 6개(당시) | 56,160 | 811ms | 147ms | 958ms | 19.6MB |
| 2차 | 120개 | 2,808 | 612ms | 68ms | 680ms | 6.5MB |

같은 실행에서 비교하면, 경로 구간당 좌표를 6개에서 120개로 늘렸을 때 합계가 0.28초(29%) 줄었다. JSON은 67% 줄었다. 60개 이상에서는 합계 차이가 0.06초 안이라, 경로 구간을 더 길게 묶어도 얻는 것이 적다. 이 감소를 실서버 CPU 차이로 옮기면 2.37초가 약 1.7초로 줄 것으로 예상했다. 이 예상은 실서버에서 잰 값이 아니다.

경로 구간 수를 줄이는 방법은 다음과 같이 비교했다.

- **저장할 때 이어 붙이기:** 새 좌표 묶음의 첫 경로 구간이 경로의 마지막 경로 구간과 이동 유형이 같으면, 마지막 경로 구간을 늘린다. 용어집의 정의와 맞는다. 응답 형식도 그대로다. 대신 이미 저장된 경로 구간을 한 번 다시 묶어야 한다. 늘어난 경로 구간은 경로 변경분 응답에 통째로 다시 담긴다.
- **응답에서만 묶기:** 저장은 그대로 두고 조회할 때 묶는다. 묶은 경로 구간의 ID와 버전을 새로 정해야 한다. 그래서 경로 구간 ID와 버전으로 경로 변경분을 합치는 화면의 방식이 복잡해진다.
- **좌표를 범위로 참조하기:** 경로 구간끼리 좌표가 겹치지 않는다. 그래서 줄일 수 있는 양이 도형 포장 몫(9%) 정도다.
- **좌표 단순화:** 짧은 경로 구간이 지도에서 사라지는 문제가 이미 있었다([문제 해결 기록 41](41-zoomed-out-short-path-segments-hidden.md)).
- **작은 페이지로 나눠 받기:** 왕복이 늘어 오히려 느려졌다([문제 해결 기록 38](38-repeated-search-path-page-queries.md)).

정의와 맞고 응답 형식을 바꾸지 않는 "저장할 때 이어 붙이기"를 선택했다. 경로 구간 하나의 상한은 좌표 120개로 정했다. 한 좌표 묶음에 올릴 수 있는 좌표가 최대 120개라서, 새 좌표 묶음에서 만든 경로 구간을 자르는 규칙이 필요 없다. 상황판 조회의 좌표 한도도 120개 이상만 허용된다. 그래서 120개 이하 경로 구간 때문에 `SEARCH_PATH_SEGMENT_TOO_LARGE`가 나지 않는다. 사용자가 보정한 `MANUAL` 경로 구간에는 이어 붙이지 않는다. 일시정지 뒤 재개한 좌표 묶음은 이어 붙인다. 작업은 [spec #32](https://github.com/sonic8-8/suri-map/issues/32)로 정리했다. 새 좌표의 저장 규칙은 [#33](https://github.com/sonic8-8/suri-map/issues/33)에서, 이미 저장된 경로 구간을 다시 묶는 일은 [#34](https://github.com/sonic8-8/suri-map/issues/34)에서 진행했다.

## 변경 내용과 트레이드오프

네 원인에 각각 다음 변경을 적용했다.

- **서버 좌표 배열 읽기(6d2d1002, BE):** `findBoardPointRuns`에서 요청 범위마다 한 행으로 경도, 위도, 측정 시각(마이크로초) 배열을 `array_agg`로 돌려주도록 바꿨다. 마이크로초 정수로 담을 수 없는 시각(294247-01-01 이상이나 무한 시각)이 있는 범위만 기존 좌표 행 SQL로 다시 읽게 했다. 응답 계약은 바꾸지 않았다.
- **지도 도형 잇기(557a53a4, FE):** `createMovementPathFeatureMapper`에서, 같은 경로 안에서 표시 값(색, 이동 유형, 활성 차수, 업무폰 최신성)이 같고 끝점이 이어지는 경로 구간을 선 하나로 잇도록 바꿨다. 지도 도형에서 읽는 곳이 없는 속성 6개(slot, opId, accountId, startedAt, endedAt, label)를 뺐다.
- **경로 조회 선시작(8835a657, BE/FE):** 사건 목록 API의 item에 `activeOpId`를 추가했다([API](../api/api-spec.md#get-apiincidents)). 지휘관이 목록에서 "상황판 열기"를 누르면 이 값이 화면 이동 상태로 넘어간다. 상황판 응답이 오기 전에만 이 차수로 경로 조회를 시작하도록 했다.
- **같은 이동 유형의 경로 구간 이어 붙이기(PR #35, BE):** [PR #35](https://github.com/sonic8-8/suri-map/pull/35)를 merge commit 1b26ebcf로 develop에 병합했다.
  - 새 좌표(1333c81a, #33): 새 좌표 묶음의 첫 경로 구간이 경로의 마지막 경로 구간과 이동 유형이 같으면, 마지막 경로 구간에 이어 붙인다. 이어 붙인 경로 구간도 좌표 120개를 넘지 않는다.
  - 기존 경로 구간(9cd5e19b, #34): Flyway migration `V20261102_001`을 추가했다. migration을 실행하면 경로, 경로 구간, GPS 테이블이 잠긴다. 그 뒤 경로마다 순번이 바로 이어지는 같은 이동 유형의 `AUTO` 경로 구간이, 좌표 120개를 넘지 않게 앞에서부터 묶인다. 묶은 경로 구간은 첫 경로 구간의 ID를 유지한다. 범위, 도형, 시작 시각과 끝 시각은 원본 GPS 좌표와 측정 시각으로 다시 만든다. 첫 경로 구간에 합쳐진 나머지 행은 지워진다. 확정할 수 없는 자료가 있으면 CHECK 위반으로 migration 전체가 롤백된다.
  - 응답의 필드와 이벤트 형식은 바꾸지 않았다.

### 트레이드오프와 유지한 범위

- 이은 선은 이음점의 가장자리 픽셀이 달라진다. 전에는 경로 구간마다 둥근 끝과 반투명 선이 겹쳐 칠해졌기 때문이다. 픽셀 비교에서 큰 차이는 그려진 픽셀의 0.8~4.3%였다.
- 지도 도형에서 경로 구간 시각, 계정, 차수 값을 뺐다. 원본 값은 화면 경로 데이터(`BoardMovementPath`)와 API에 그대로 남는다. 계획된 경로 재생은 지도 도형이 아니라 인수인계 타임라인 API의 좌표 시각을 쓰도록 요구 문서에 정했다([도형 단위 요구](../features/situation-board.md#화면과-관측에서-남은-요구)).
- 목록의 차수와 상황판의 차수가 다르면, 먼저 시작한 조회를 버리고 상황판 차수로 다시 조회한다. 같으면 같은 조회를 그대로 이어 쓴다.
- 지휘관이 주소를 직접 열어 상황판에 들어오면 목록이 넘긴 차수가 없다. 그래서 이전처럼 상황판 응답을 기다린 뒤 경로를 조회한다.
- 이어 붙인 경로 구간은 좌표가 늘 때마다 경로 변경분 응답에 통째로 다시 담긴다. 경로 구간 하나가 좌표 120개를 넘지 않으므로, 한 번에 다시 담기는 양도 좌표 120개를 넘지 않는다.
- 사용자가 보정한 `MANUAL` 경로 구간과, 이미 좌표가 120개를 넘은 기존 경로 구간은 이어 붙이지 않는다.
- migration에서 지워진 경로 구간 ID는 되돌릴 수 없다. 원본 GPS 좌표는 남아 있어서 범위는 다시 계산할 수 있다.
- migration 전에 열어 둔 상황판에는 지워진 경로 구간 ID와 무효가 된 이어받기 순번이 남을 수 있다. 이력을 받던 상황판에서 그 순번으로 조회하면 요청이 `invalid_search_path_query`로 거절된다. 그 뒤에는 다음 조회가 일어나지 않는다. 그래서 적용 뒤에는 지휘관이 상황판을 새로고침해야 한다.

변경마다 다음을 확인했다.

- **서버 좌표 배열 읽기:** 로컬에서 응답 JSON의 SHA-256이 변경 전과 같았다. 실서버 컨테이너 안 요청은 3.12~3.24초에서 2.32~2.43초(데워진 상태)가 됐다. 브라우저 한 요청은 4.05~4.49초에서 2.36~2.81초가 됐다.

- **경로 조회 선시작:** Backend 전체 1,429개 중 12개가 실패했다. 실패는 SSE 4개, TomcatProxy 7개, SecurityConfig 1개다. 모두 변경 전부터 같은 로컬 HTTP 환경에서 실패하던 테스트다. PostgreSQL 통합 테스트와 Frontend 346개는 통과했다. 배포 후 경로 요청은 클릭 뒤 4~10ms에 나갔다. 3회 모두 목록의 차수가 전달됐다.
- 위 세 변경 모두 Codex 읽기 전용 검수를 통과했다.
- **같은 이동 유형의 경로 구간 이어 붙이기:** 로컬에서 경로 468개와 좌표 336,960개를 넣고, migration 전과 뒤에 상황판 첫 페이지를 예열 2회 뒤 5회 쟀다(중앙값). JSON은 19,561,678바이트에서 6,504,424바이트로 줄었다. 응답의 경로 구간은 56,159개에서 2,807개로 줄었다. 서비스 호출은 760.6ms에서 559.1ms로, JSON 변환은 137.9ms에서 69.2ms로 줄었다. `./gradlew test`에서 1,457건이 모두 통과했다. 실서버 결과는 [재측정](#경로-구간을-이어-붙인-뒤-실서버-재측정)에 있다.

### 일반 탭 3회 측정과 목표 판정

체크리스트는 체크하지 않았다. 판정 조건으로 처음 잰 3회 중앙값은 5.02초로, 목표 5초를 넘었다. 그런데 측정 스크립트 비용을 분리하려고 다시 재 보니, 상황판 시간이 5초 근처에 있었다. 그래서 3회 중앙값만으로는 판정이 측정 묶음마다 바뀌었다. 이 때문에 판정을 보류했다.

위 4.65초는 따로 띄운 Chrome에서 지도 idle까지 잰 값이어서 판정에 쓸 수 없었다. 판정 조건에 따르면 사용자의 일반 Chrome 탭에서, 받은 전체 경로 구간이 지도에 반영되고 렌더가 확인될 때까지 재야 한다. 그래서 2026-10-29에 [경로 표시 시간 측정 스크립트](../../infra/k6/path-display-timing/)를 다음과 같이 보완했다.

- 상황판 코드에서 진입 클릭(click 이벤트의 `timeStamp`, `board_open_clicked`)과 전체 반영 완료(`all_paths_map_idle`)를 같은 브라우저 시계(`performance.now`)로 기록하도록 했다(77ea65ad). 전체 반영 완료는 전체 이력을 받고 경로 source에 반영한 뒤 처음 맞는 지도 idle이다.
- 지도 도형 잇기 뒤에는 도형 ID에 이은 경로 구간 중 첫 경로 구간의 ID만 남는다. 그래서 경로 구간 ID로는 렌더를 확인할 수 없다. 대신 경로 표시 시간 측정 스크립트에서, 경로마다 지도 source의 좌표를 그리는 순서로 이은 결과가 받은 응답의 경로 구간 좌표 순서와 같은지 비교하도록 했다. 응답도 측정 전후의 DB와 대조하도록 했다(2edac06c).
- 결과에 경로 표시 시간 측정 스크립트의 Git 커밋과 실행 설정을 남기도록 했다(1e41050c).

2026-10-30에 경로 표시 시간 측정 스크립트로 실서버 배포본(96345470)을 쟀다. 사용자의 일반 Chrome 탭을 화면 앞에 두었다. 정식 로그인 뒤 조회만 했다. 경로 표시 시간 측정 스크립트는 커밋 6423197c를 수정 없이 썼다. 두 커밋 사이에 Frontend와 Backend 변경은 없다. 응답 한도가 1000/100000/100000/400000이라 최초 이력이 응답 1건에 담겼다.

| 회차 | 전체 이력 수신 | 첫 표시 | 전체 이력 지도 반영 |
|---|---:|---:|---:|
| 1 | 4.66초 | 4.36초 | 5.02초 |
| 2 | 3.81초 | 4.35초 | 4.68초 |
| 3 | 3.80초 | 4.37초 | 5.11초 |
| 중앙값 | 3.81초 | 4.36초 | **5.02초** |

시각은 모두 진입 클릭부터 잰 값이다. 이 값에는 측정 스크립트 비용이 포함된다. 전체 이력 수신은 경로 이력과 경로 변경분 응답을 모두 받은 시각이다. 첫 표시는 경로 표시 시간 측정 스크립트로 0.25초마다 지도를 확인해 잡은 값이다. 그래서 실제보다 최대 0.25초 늦을 수 있다. 첫 표시는 이 이슈에서 판정하지 않고 기록만 한다.

3회 모두 다음을 확인했다.

- 경로 481개 모두 지도 source의 좌표 순서가 응답의 경로 구간 좌표 순서와 같았다.
- 응답이 측정 전 DB와 일치했다. 측정 뒤 DB도 측정 전과 같았다.
- 측정 전후 서버의 컨테이너 이미지와 환경 설정이 같았다. 측정 중 탭이 가려지지 않았다.

같은 날 경로 표시 시간 측정 스크립트의 동작을 확인하려고 먼저 1회 잰 값(5.72초)은 판정에 넣지 않았다.

5.02초는 측정 스크립트 비용을 포함한 관측 상한이다. 판정 조건에 따라, 상한이 목표를 넘었다는 사실만으로 제품 지연을 확정하지 않았다. 대신 측정 스크립트 비용을 분리해 다시 쟀다. 4.65초와 직접 비교하지 않는 이유는 브라우저 환경과 끝 시점의 정의가 다르기 때문이다.

### 측정 스크립트 비용 분리와 판정 보류

경로 표시 시간 측정 스크립트로 잴 때는 페이지에 경로를 기록하는 코드를 넣는다. 이 코드가 실행되면 경로 응답 본문이 페이지에 보존된다. 지도에 경로가 그려졌는지는 0.25초마다 확인한다. 지도 source 이벤트도 받는다. 이 경로 기록 비용을 떼어 보려고, 경로 기록을 빼고 진입 클릭과 전체 반영 완료 두 시점만 받는 가벼운 모드를 경로 표시 시간 측정 스크립트에 추가했다([PR #30](https://github.com/sonic8-8/suri-map/pull/30)). 상황판에서는 계측 플래그가 켜져 있을 때만 두 시점이 기록된다. 그래서 두 모드 모두 이 플래그를 켠다. 상황판 계측 비용은 두 값에 똑같이 남고, 두 모드의 차이가 경로 기록 비용이다.

2026-10-31에 같은 실서버에서 쟀다. 직전에 Jenkins #102로 d63aedbb가 배포되면서 컨테이너가 다시 기동했다. 하지만 Frontend 번들(`index-D6WC9Fe2.js`)과 Frontend, Backend 코드는 위 측정과 같았다. 응답 한도도 같았다. 경로 표시 시간 측정 스크립트는 d63aedbb를 수정 없이 썼다.

가벼운 모드만 먼저 3회 쟀을 때는 5.98, 5.47, 4.74초(중앙값 5.47초)였다. 경로 기록을 포함한 10월 30일 측정(5.02초)보다 오히려 느렸다. 컨테이너를 다시 띄운 직후였다. 회차마다 빨라졌다. 날짜와 서버 상태가 다른 두 묶음을 비교했기 때문으로 보고, 같은 자리에서 두 모드를 번갈아 다시 쟀다. 먼저 가벼운 모드로 1회를 데우기로 쟀다(5.83초, 판정 제외). 이어서 지금 측정 모드와 가벼운 모드를 번갈아 3쌍 쟀다.

6회 모두 진입 클릭과 전체 반영 완료가 같은 브라우저 시계로 기록됐다. 측정 전후 서버의 컨테이너 이미지와 환경 설정도 같았다. 지금 측정 모드 3회는 경로 481개의 좌표 순서와 DB 대조가 모두 일치했다.

경로 기록을 뺀 가벼운 모드가 더 빠르지 않았다. 차이의 부호도 쌍마다 바뀌었다. 같은 자리에서도 회차마다 4.71~5.35초로 0.6초 넘게 흔들렸다. 그래서 그보다 작은 경로 기록 비용은 떼어 낼 수 없었다.

같은 이유로 판정도 정할 수 없었다. 판정 조건을 그대로 적용하면 10월 30일 3회(5.02초)는 미충족이고, 같은 조건으로 잰 10월 31일 3회(4.78초)는 충족이다. 상황판 시간이 5초 근처에 있어서, 3회 중앙값만으로는 측정 묶음마다 결과가 바뀐다. 그래서 체크리스트를 체크하지 않고 판정을 보류했다. 상황판 계측 비용을 따로 떼는 측정은 하지 않았다. 이 비용도 회차 변동보다 작을 가능성이 높아 판정을 바꾸기 어렵다고 판단했다.

경로 이력 요청은 클릭 뒤 0.02초 안에 나갔다. 응답 본문은 압축 전 약 22MB였다. 전송량은 약 3.3MB였다. 경로 변경분 요청은 경로 이력 응답이 끝나고 0.11~0.14초 뒤에 나갔다. 응답 본문은 52글자였는데도, 걸린 시간 대부분이 서버 대기였다. 경로 변경분 요청에는 경로 이력 응답에 담긴 기준 버전이 필요하다. 그래서 두 요청은 차례로 나간다. 같은 날 경로 변경분 요청을 화면 처리 없이 바로 보내 보니 첫 바이트까지 0.56~0.81초였다. 그중 서버 처리는 약 0.1초였다. 나머지는 독일 서버까지 한 번 왕복하는 시간이었다.

- 판정을 다시 내리려면 5초에 여유가 생기도록 위 단계를 줄여야 한다. 가장 긴 경로 이력 요청은 같은 이동 유형의 경로 구간을 이어 붙여 줄였다([원인 분석](#업로드마다-새로-생긴-경로-구간이-경로-이력-응답을-키우는-비용), [변경 내용](#변경-내용과-트레이드오프)). 적용 뒤에도 여유가 충분하지 않아 판정은 보류했다([재측정](#경로-구간을-이어-붙인-뒤-실서버-재측정)). 회차를 늘리는 식으로 판정 기준을 바꾸는 방법은 정하지 않았다.

- 새 좌표 반영(목표 3초)은 위 네 변경 뒤 재지 않았다.
- 배포 직후나 쉬었다가 처음 잰 회차는 느렸다. 배포 직후 측정(5.30초)에서는 경로 응답이 1회 약 1초 늦었다. 10월 31일 데우기 회차는 5.83초였다. 서버가 덜 데워진 영향으로 보이지만 확인하지 않았다.

### 경로 구간을 이어 붙인 뒤 실서버 재측정

PR #35는 계획보다 먼저 실서버에 적용됐다. develop에 푸시할 때마다 Jenkins 빌드가 돌아 실서버에 배포된다. PR #35를 develop에 병합해 푸시하자 빌드 #111(1b26ebcf)이 2026-11-02 20:04(KST)에 시작했다. 백엔드가 기동하면서 migration이 20:16(KST)에 5,414ms 만에 끝났다. migration 안의 검사는 모두 통과했다. 원래는 배포 전에 읽기 전용 점검을 하고, 현장 앱의 경로 쓰기를 멈추고, DB를 백업할 계획이었다. 하지만 병합 전에 develop 푸시가 곧 배포라는 것을 확인하지 않아서, 세 단계를 모두 하지 못했다. 2026-11-03 04:43(KST)에는 문서만 바꾼 빌드 #112(71902fb2)로, 빌드 #111과 같은 코드의 백엔드와 웹이 다시 배포됐다. Frontend 번들은 `index-D6WC9Fe2.js` 그대로였다.

2026-11-03에 실서버를 읽기 전용으로 조회했다.

- 경로 구간은 57,097개에서 3,461개로 줄었다. 3,461개는 모두 고정 시험 사건의 수색 차수에 속한다. 경로는 481개 그대로다.
- 경로 구간 하나의 최대 좌표 수는 120개였다. 진행 범위(시작 순번과 끝 순번)를 모르는 경로 구간은 없었다.
- 빌드 #111로 기동한 백엔드의 로그에는 `invalid_search_path_query`가 없었다. 확인한 범위는 백엔드가 기동한 2026-11-02 20:16(KST)부터, 빌드 #112로 백엔드가 다시 기동하기 전까지 약 8시간이다.

경로 이력 요청의 서버 처리 시간은 Prometheus로 비교했다. 상황판을 한 번 열면 경로 이력 요청(`segments/query`)이 한 번 나간다. 측정 시간대의 요청당 평균(status 200, 15분 동안의 합계를 요청 수로 나눈 값)은 다음과 같다.

| 시간대(UTC) | 요청 수 | 요청당 평균 처리 시간 |
|---|---:|---:|
| 2026-10-30 15:05~15:20(적용 전) | 약 7건 | 2.28초 |
| 2026-11-02 20:10~20:25(적용 뒤) | 약 4건 | 1.59초 |

KST로 바꾸면 적용 전 시간대는 2026-10-31 00:05~00:20이다. 적용 뒤 시간대는 2026-11-03 05:10~05:25이다. 적용 전 시간대에는 위 판정 보류 절의 10월 31일 측정 묶음(데우기 1회와 3쌍)이 있다. 적용 뒤 시간대에는 아래 가벼운 모드 측정(데우기 1회와 3회)이 있다.

처리 시간은 0.69초 줄었다. PR #35의 로컬 측정([검증 결과](#검증-결과)의 변경별 확인 목록 마지막 항목)에서 줄어든 시간은 서비스 호출 0.20초와 JSON 변환 0.07초, 합계 0.27초다. 여기에 실서버 CPU 차이 2.5배를 곱하면 약 0.68초가 된다. 이 값은 계산한 추정이지만, 실서버에서 줄어든 시간과 크기가 맞다. 원인 분석에서 2.37초가 약 1.7초로 줄 것으로 예상한 것과도 가깝다. 실서버 응답 크기는 재지 않았다.

상황판 진입 시간은 가벼운 모드로 다시 쟀다. 조건은 10월 31일 측정과 같다. 사용자의 일반 Chrome 탭을 썼다. 정식 로그인 뒤 조회만 했다. 응답 한도는 1000/100000/100000/400000이다. 경로 표시 시간 측정 스크립트는 커밋 71902fb2를 수정 없이 썼다. 첫 시도 4회(데우기 1회와 측정 3회)는 탭이 화면에 보이지 않아서 실패했다. 탭이 가려지면 그 회차는 실패로 끝난다. 사용자가 탭을 화면 앞에 띄운 뒤 다시 쟀다. 데우기 1회(4.93초)는 판정에서 뺐다.

| 회차 | 적용 전 가벼운 모드(10월 31일) | 적용 뒤 가벼운 모드(11월 3일) |

중앙값은 0.47초 줄었다. 하지만 같은 조건에서도 회차마다 0.6초 넘게 흔들렸으므로, 이 차이만으로 화면이 빨라졌다고 판단할 수 없다. 진입 시간 4.75초 가운데 경로 이력 요청의 서버 처리는 약 1.6초다. 나머지 약 3.2초가 어느 단계에서 걸리는지는 이번에 나누어 재지 않았다.

체크리스트는 이번에도 체크하지 않았다. 4.75초는 목표 5초보다 0.25초 짧지만, 이 여유는 회차 사이 흔들림보다 작다. 또 가벼운 모드는 판정 조건이 정한 지금 측정 모드가 아니다. 사용자가 판정 보류를 유지하기로 정했다.
