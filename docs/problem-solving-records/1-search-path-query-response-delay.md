# [BE] 수색 경로 조회 API 응답 지연

# 본문

## 문제 배경

수리맵은 지도 위에 수색 경로와 마커를 함께 보여준다. 수색 경로가 추가되거나 수정되면 서버는 SSE로 “바뀐 내용이 있다”는 알림만 보낸다. 클라이언트는 그 알림을 받은 뒤 수색 경로 조회 API를 다시 호출해 최신 지도 데이터를 가져온다.

그래서 이 API가 느리면 지도가 늦게 바뀐다. 현장 요원이 새 수색 경로를 남겼는데 지휘 상황판이 몇 초 동안 예전 경로를 보고 있으면, 서로 다른 정보를 기준으로 움직일 수 있다.

이번 작업에서는 1초 이하를 판단 기준으로 잡았다. 운영 SLO로 확정한 값은 아니지만, [NN/g의 response-time limits](https://www.nngroup.com/articles/website-response-times/)에서는 1초 안팎을 사용자가 작업 흐름을 유지할 수 있는 기준으로 설명한다. 수리맵의 지도 갱신도 사용자가 기다리는 화면 흐름에 가깝기 때문에, 이 기준을 넘는 조회는 개선 대상으로 보았다.

기존 조회를 재현한 테스트에서는 전체 `search_path` 625건 중 실제 필요한 데이터가 25건인 상황에서도 중앙값이 `4247ms`였다. 전체 데이터를 6025건으로 늘리자 중앙값은 `39736ms`까지 증가했다.

실제로 필요한 수색 경로는 25개였지만, 기존 구조에서는 전체 경로를 먼저 가져온 뒤 서버에서 필요한 것만 골라 쓰고 있었다. 데이터가 늘어날수록 지연이 함께 커졌으므로, 조회 범위가 커질수록 악화되는 구조 문제로 판단했다.

## 원인 분석과 선택지

기존 구조에서는 DB에서 전체 수색 경로를 가져온 뒤 애플리케이션 코드에서 사건 id와 수색 차수 id 조건을 적용해 API 응답으로 조립하고 있었다.

수색 경로는 단순한 문자열이 아니라 지도 위의 선 좌표와 구간 정보를 포함한다. 필요 없는 경로까지 가져오면 DB 조회 비용뿐 아니라 좌표 변환과 응답 객체 조립 비용도 함께 늘어난다.

검토한 선택지는 두 가지였다.

1. 애플리케이션 필터링 유지

   구현은 단순하다. 하지만 데이터가 늘어날수록 필요 없는 경로까지 계속 읽고 변환해야 한다.

2. DB에서 먼저 조회 범위 축소

   DB에 처음부터 사건 id와 수색 차수 id 조건을 전달해 필요한 경로만 가져온다. SQL에 조건이 더 들어가지만, 불필요한 좌표 변환과 응답 조립을 줄일 수 있다.

수색 경로 조회 API는 사건과 수색 차수 조건이 명확하고, SSE 알림 뒤 반복해서 호출되는 API다. 그래서 DB에서 먼저 범위를 줄이는 두 번째 선택지를 택했다.

## 변경 내용과 트레이드오프

SQL의 `WHERE` 조건에서 사건 id와 수색 차수 id를 먼저 적용하도록 바꿨다. 전체 수색 경로를 조회한 뒤 애플리케이션에서 걸러내던 처리를, DB에서 필요한 범위만 조회하고 애플리케이션이 응답을 조립하는 방식으로 바꾼 것이다.

트레이드오프는 SQL이 기존보다 조회 조건을 더 많이 갖는다는 점이다. 대신 조회 범위가 크게 줄고, 필요 없는 좌표 변환과 segment 조립을 피할 수 있다. segment는 하나의 수색 경로를 여러 구간으로 나눈 하위 데이터다.

성능 근거를 남기기 위해 `SearchPathQueryPerformanceEvidenceTest`도 보강했다. 이 테스트는 기본 테스트에서는 제외하고, `-PincludePerformance` 옵션을 줄 때만 실행되도록 두었다. 일반 테스트 속도는 유지하면서도 성능 근거가 필요할 때 같은 방식으로 다시 측정하기 위한 선택이다.

## 검증 결과

성능 근거 테스트를 실행했다.

```bash
cd backend
./gradlew test -PincludePerformance --tests '*SearchPathQueryPerformanceEvidenceTest' --rerun-tasks
```

결과는 `BUILD SUCCESSFUL`이었다. 테스트 리포트 기준 `tests=1`, `skipped=0`, `failures=0`, `errors=0`이었다.

측정값은 다음과 같다.

전체 625건, 실제 필요 25건

- 기존 재현 처리: `[4162, 4247, 4330]`, 중앙값 `4247ms`
- DB 조건 조회 처리: `[154, 157, 171]`, 중앙값 `157ms`

전체 6025건, 실제 필요 25건

- 기존 재현 처리: `[39249, 39736, 41683]`, 중앙값 `39736ms`
- DB 조건 조회 처리: `[180, 181, 189]`, 중앙값 `181ms`

백엔드 전체 테스트도 실행했다.

```bash
cd backend
./gradlew test --rerun-tasks
```

결과는 `BUILD SUCCESSFUL`이었다. XML 리포트 합산 기준 `tests=1055`, `failures=0`, `errors=0`, `skipped=0`이었다.

이번 수치는 Testcontainers 기반 테스트 환경에서 측정한 값이다. 운영 트래픽, 실제 사용자 이탈률, 브라우저 렌더링 지연은 이번 검증 범위에 포함하지 않았다.
