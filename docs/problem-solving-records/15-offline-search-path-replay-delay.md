# [BE] 업무폰 468대가 오프라인 수색 경로를 재전송하면 서버 응답이 늦어 전송 대기가 쌓이는 문제

## 문제 배경

GPS 수집과 전송 주기를 검토하던 [Issue #8](https://github.com/sonic8-8/suri-map/issues/8)의 부하 테스트에서 오프라인 수색 경로 재전송이 끝나지 않는 문제를 확인했다. Android 앱은 통신이 끊긴 동안 수색 경로 요청을 Outbox에 보관한다. 통신이 복구되면 업무폰마다 요청을 저장된 순서대로 서버에 보낸다.

개발 서버에서 업무폰 468대가 15초마다 요청을 보낸 실시간 테스트는 5분 동안 9,387건을 모두 처리했다. HTTP 응답 시간 p95는 33.57ms였고 시간 초과는 없었다.

이후 업무폰마다 30분 동안 쌓은 요청 120건을 순서대로 다시 보냈다. 5분 안에 총 56,160건을 보내려 했지만 부하 테스트는 16,572건만 서버로 보냈다. 나머지 39,588건은 전송을 시작하지 못했다. 서버로 보낸 요청 중 115건도 15초 안에 응답을 받지 못했고, HTTP 응답 시간 p95는 13.68초까지 늘었다.

![오프라인 수색 경로 재전송 부하 테스트 당시 Grafana 대시보드](https://raw.githubusercontent.com/sonic8-8/suri-map/develop/docs/test-results/backend/issue-15-offline-replay-load-test.png)

*Grafana에서 2026년 7월 30일 02:12:30~02:20:00 KST 구간을 조회했다. 상단 수치는 이 구간에서 마지막으로 수집한 값이다. 테스트 전체 결과는 위 문단에 적었다.*

5분은 이 부하 테스트에서 세운 목표이며 확정된 현장 복구 기준은 아니다. 다만 실제 요청 115건이 클라이언트의 15초 제한을 넘겨 실패했다. 수정 전 서버는 이 조건에서 오프라인 수색 경로 요청을 모두 받아 처리하지 못했다. Android는 실패한 요청을 Outbox에 남겨 다시 보내므로, 수색 경로가 상황판에 늦게 나타날 수 있었다.

## 원인 분석과 선택지

공통 멱등성 처리 메서드인 `IdempotentWriteService.reserveAndReplay()`에는 `synchronized`가 붙어 있었다. 이 메서드는 한 요청의 처리가 끝나야 다음 요청을 처리할 수 있었다. Spring은 이 서비스를 객체 하나로 사용하므로, 백엔드 프로세스 안의 모든 멱등성 요청이 차례대로 처리됐다.

문제는 멱등성 키를 확인하는 짧은 작업만 순서대로 처리하지 않았다는 점이다. 이 메서드는 `ownerOperation.get()`을 호출해 수색 경로를 조회하고 저장하는 작업까지 기다린다. 따라서 업무폰과 멱등성 키가 달라도 앞 요청의 저장이 끝날 때까지 기다렸다. 부하 테스트 중 PostgreSQL 잠금 대기는 0건이었다.

수색 경로 저장은 요청을 받을 때마다 기존 좌표와 구간을 다시 읽고 구간을 계산한다. 경로가 길수록 처리 시간이 늘어날 수 있지만, 이번 테스트에서는 이 작업의 영향도를 따로 측정하지 않았다.

해결 방법은 두 가지를 검토했다.

1. JVM 안에서 같은 멱등성 키를 가진 요청만 차례대로 처리한다. 서로 다른 키는 함께 처리할 수 있다. 하지만 서버가 여러 대면 각 서버의 메모리를 공유하지 못하고, 사용이 끝난 키를 지우는 코드도 필요하다.
2. Android는 Outbox 요청에 `Idempotency-Key`를 포함해 보낸다. 서버 DB에는 이 키와 요청 경로, HTTP 메서드 조합이 같은 요청을 중복 저장하지 못하게 하는 유일 인덱스가 이미 있다. 서버는 요청 처리 시작 기록과 GPS 좌표를 하나의 트랜잭션으로 저장한다. 이미 처리한 요청이 다시 들어오면 저장된 응답을 반환한다. 예를 들어 서로 다른 업무폰에서 멱등성 키가 다른 요청 A와 B를 함께 보내면, 서버는 요청 A의 처리가 끝날 때까지 요청 B를 기다리게 하지 않고 두 요청을 동시에 처리한다. 이렇게 하면 한 업무폰의 요청이 다른 업무폰의 전송까지 늦추지 않는다. 서버가 같은 시간에 더 많은 요청을 처리하므로 각 업무폰의 Outbox에 쌓인 요청도 더 빨리 줄어든다.

두 번째 방법을 적용했다. 먼저 전역 `synchronized`를 제거하고 같은 재전송 테스트를 다시 실행했다. 시간 초과가 남으면 경로 전체를 다시 읽고 계산하는 비용을 따로 측정한 뒤 후속 이슈로 나누기로 했지만, 다시 실행한 테스트에서 시간 초과는 없었다.

## 변경 내용과 트레이드오프

### 무엇을 바꿨는가?

서버가 서로 다른 요청을 동시에 처리하도록 바꿨다. 커밋 [`a30d4750`](https://github.com/sonic8-8/suri-map/commit/a30d4750)에서 `IdempotentWriteService.reserveAndReplay()`에 걸려 있던 `synchronized`를 제거했다.

### 중복 저장은 어떻게 막았는가?

중복 저장은 두 번째 방법에서 설명한 PostgreSQL 유일 인덱스가 막는다. 서버는 `Idempotency-Key`, 요청 경로, HTTP 메서드가 모두 같으면 중복 요청으로 보고, PostgreSQL에는 이 조합의 처리 기록을 하나만 저장할 수 있다.

### 저장 중 오류가 나거나 중복 요청이 들어오면 어떻게 되는가?

서버는 요청 처리 시작 기록을 남긴 뒤 수색 경로와 응답을 저장한다. 세 저장 작업은 하나의 트랜잭션으로 묶었다. 저장 중 오류가 나면 모두 취소되므로 같은 요청을 다시 보낼 수 있다. 처리가 끝난 뒤 중복 요청이 들어오면 수색 경로를 다시 저장하지 않고 기존 응답을 반환한다.

### 어떤 한계가 남았는가?

기존 PostgreSQL만 사용했기 때문에 운영할 시스템은 늘지 않았다. 대신 서버의 동시 처리량은 DB 연결 풀과 SQL 처리 성능에 따라 달라진다. 이 한계는 후속 용량 테스트에서 확인한다.

## 검증 결과

### 문제가 해결됐는가?

같은 조건으로 다시 테스트한 결과, 서버는 요청 56,160건을 3분 57.3초 안에 모두 처리했다. 초당 평균 236.70건을 처리했고, 모든 요청에 HTTP 200으로 응답했다. 가장 오래 걸린 응답은 6.61초였으며, 시간 초과는 없었다. 이번 테스트에서 정한 5분 완료 기준과 요청당 15초 제한을 모두 충족했다.

### 어떤 조건에서 테스트했는가?

테스트는 2026년 7월 30일 커밋 `a30d4750`을 배포한 Hetzner 개발 서버에서 진행했다. 업무폰 468대가 각각 30분 동안 쌓은 요청 120건을 저장된 순서대로 보냈다. 요청 한 건에는 GPS 좌표 6개를 담았다.

### 수정 전과 비교해 무엇이 달라졌는가?

수정 전과 후의 결과는 다음과 같다.

| 항목 | 수정 전 | 수정 후 |
|---|---:|---:|
| 5분 동안 서버로 보낸 요청 | 16,572건 | 56,160건 |
| 5분 안에 보내지 못한 요청 | 39,588건 | 0건 |
| 15초 안에 응답받지 못한 요청 | 115건 | 0건 |
| HTTP 응답 시간 p95 | 13.68초 | 3.47초 |

### 수색 경로는 누락이나 중복 없이 저장됐는가?

API 응답에서는 GPS 좌표 336,960개를 모두 받아들였으며, 경로에서 제외한 좌표는 없었다.

PostgreSQL을 조회한 결과, 요청 처리 완료 기록과 수색 경로 구간이 각각 56,160개 저장돼 있었다. GPS 좌표는 336,960개였다. 같은 `Idempotency-Key`, 요청 경로, HTTP 메서드 조합의 처리 기록은 중복되지 않았다. 같은 `pointId`를 가진 GPS 좌표도 없었다.

### 서버에는 어떤 한계가 남았는가?

테스트 중에는 DB 연결 10개를 모두 사용했다. DB 연결을 기다린 요청은 최대 190건이었지만, 연결 시간 초과와 PostgreSQL 교착 상태는 발생하지 않았다. 더 높은 부하에서는 DB 연결 풀이 처리량을 제한할 수 있다.

### 어떤 테스트를 통과했는가?

로컬에서 `cd backend && ./gradlew test`를 실행해 `BUILD SUCCESSFUL`을 확인했다. Hetzner App 서버의 PostgreSQL에 연결한 `IdempotentWriteServiceTest` 6건도 건너뛰거나 실패한 테스트 없이 통과했다.

검증을 마친 뒤 테스트 데이터와 부하 테스트용 인증 정보를 삭제했다.

### 아직 무엇을 확인하지 못했는가?

이번 검증은 Hetzner 개발 서버에서 30분치 오프라인 요청만 재전송한 결과다. 실시간 전송, 상황판 조회, SSE가 동시에 발생하는 부하와 8시간 이상 쌓인 경로는 아직 측정하지 않았다.
