# 제목

[BE] 상황판의 전체 경로 로딩에 페이지 왕복과 DB 검사 비용이 누적됨

# 본문

## 문제 배경

수리맵 상황판은 지휘관이 업무폰에서 기록한 수색 경로를 확인하는 화면입니다. 경로를 구성하는 일부 구간을 한 응답으로 받아 먼저 표시하고, 다음 응답으로 이전 구간을 이어받습니다. 전체 이력을 기다리지 않고 경로를 확인하면서 새 좌표도 반영하기 위한 구조입니다.

그러나 2026-10-08 Hetzner App 서버의 사건 1개·수색 차수 1개를 조회했을 때, 경로 481개·구간 57,083개의 전체 수신과 브라우저 캐시 반영에 734.542초, 약 12분 15초가 걸렸습니다. 새 좌표 전송이나 동시 사용자 부하 없이 WSL의 Headless Chrome 1개로 측정한 결과입니다. 첫 경로는 3.620초에 표시됐지만, 전체 수색 경로를 확인하기 위한 로딩은 계속됐습니다.

- 구간 조회 786건·변경분 조회 7건을 순서대로 처리했습니다.
- HTTP 시간 합계는 559.310초, 응답 완료부터 다음 요청까지의 간격은 173.745초였습니다.
- 조회 실패는 없었고 수신한 구간 ID는 DB와 모두 일치했습니다. 데이터 누락이 아니라 로딩 지연을 확인한 결과입니다.

전체 수신 시간은 마지막 구간의 화면 렌더링 완료 시간이 아닙니다. HTTP 시간에는 네트워크·프록시·서버 처리가 포함되므로 DB 실행 시간으로 해석하지 않습니다.

[문제 해결 기록 36](36-slow-paged-search-path-display.md)의 최초 현상 기록은 유지합니다. 이 이슈에서는 후속 진단에서 확인한 페이지 왕복, 반복 DB 검사 비용과 개선 가설을 다룹니다. 브라우저의 지도 초기화, 그래픽 대기는 기존 기록에서 별도로 추적합니다.

### 문제 해결: 체크리스트

- [x] 같은 데이터·브라우저 조건에서 변경 전보다 경로 조회 요청 수와 전체 이력 수신 시간이 줄었는가?
- [x] 수신 구간 ID·좌표·순서가 유지되고, 동시 저장 중에도 한 응답의 경로 버전과 좌표가 일치하는가?
- [x] 정상 자료는 조회하고, GPS·구간·순번·변경 버전이 미비한 자료는 기존과 같이 거부하는가?

위 기준은 상대적인 개선과 기존 동작의 보존을 확인합니다. 최종 허용 시간은 아직 정하지 않았으므로, 시간이 조금 줄었다는 이유만으로 현장 사용에 충분한 성능이라고 판단하지 않습니다. 첫 표시와 초기 로딩 중 새 좌표 반영 시간도 함께 비교합니다.

## 원인 분석과 선택지

- 페이지 한도 조정, 준비 상태 검사 개선, 이번 페이지 GPS 일괄 조회 순서로 검증합니다. 아직 변경 후 개선량은 측정하지 않았습니다.
- 같은 조회 범위의 진행 중 HTTP 요청 1개, 여러 경로를 돌아가며 조회하는 순서, 초기 로딩 중 변경분 반영은 유지합니다.

### 페이지 한도 조정: 반복 요청 감소

현재 응답은 최대 80경로·80구간·480좌표이며, 한 경로에서는 최대 1구간만 반환합니다. 따라서 57,083구간을 받으려면 계산상 구간 조회만 최소 714번 필요합니다. 남은 경로가 적어지면 응답 전체 한도에 여유가 있어도 한 경로의 구간을 더 담지 못합니다. 실제로 한 경로에 4구간만 남긴 두 재현 모두 1구간씩 4번을 요청했습니다.

첫 번째 가설은 한 응답의 실제 반환량을 늘리면 왕복 횟수와 전체 로딩 시간이 줄어든다는 것입니다. 먼저 남은 4구간 재현에서 다른 조건은 고정하고 경로당 한도만 1에서 4로 바꿔, 같은 구간을 1회에 받는지 확인합니다. 4는 재현 입력에 맞춘 시험값이지 운영 최적값이 아닙니다.

그다음 전체 데이터에서 한도를 비교합니다. 구간 한도만 높여도 경로 수나 좌표 수 제한에 걸리면 응답은 커지지 않으므로 실제 반환량을 함께 확인합니다. 큰 응답의 처리·지도 갱신 비용 때문에 전체 시간이 줄지 않거나 첫 표시·새 좌표 반영이 늦어진다면 한도를 더 높이는 방안은 다시 검토합니다.

### 준비 상태 검사 개선: 같은 판정의 비용 감소

서버는 각 요청에서 선택 범위의 경로에 GPS와 구간이 있는지, 구간의 저장 순번과 변경 버전이 준비돼 있는지 검사합니다. 마지막 한 경로의 한 구간을 받을 때도 481개 경로를 검사했습니다. 이 SQL의 단독 실행 시간은 3회 측정에서 약 57–90ms였습니다.

두 번째 가설은 같은 정상·오류 판정을 유지하면서 검사 SQL의 반복 작업을 줄이면 요청 시간이 단축된다는 것입니다. 조건과 실행 계획을 비교하고, 정상 구간을 반복해서 훑는 비용을 줄일 수 있는지 확인합니다. 인덱스 추가 여부도 실행 계획으로 판단합니다.

한 경로만 검사한 진단 SQL은 1ms 미만이었지만, 검사 범위를 줄여도 안전하다는 증거는 아닙니다. 검사 비용이 줄지 않거나 기존에 거부하던 미준비 자료를 놓치면 해당 변경은 채택하지 않습니다.

### GPS 일괄 조회: 구간별 SQL 왕복 감소

현재는 응답에 담을 구간마다 GPS를 별도 SQL로 조회합니다. 80구간을 반환하면 GPS 조회만 80회입니다. 호출 구조는 코드에서 확인했지만, 이 개별 조회들의 누적 시간과 일괄 조회의 개선량은 아직 측정하지 않았습니다.

세 번째 가설은 이번 응답에 담을 구간을 먼저 정하고, 각 구간의 경로 ID와 시작·끝 순번을 모아 GPS를 한 번에 조회하면 DB 왕복 비용이 줄어든다는 것입니다. 조회 대상은 이번 페이지에 필요한 좌표로 제한합니다.

개별·일괄 조회의 SQL 호출 수와 응답 시간을 비교하고, 구간별 좌표·순서와 동시 저장 중 조회 일관성이 유지되는지 확인합니다. 묶은 SQL의 실행·결과 조립 비용이 더 커지면 해당 변경은 채택하지 않습니다.

시험 브라우저에서는 소프트웨어 그래픽 처리 대기도 확인됐습니다. 이를 데이터 병합이나 DB 처리 비용으로 합산하지 않으며, 세 가설을 검증하기 전에 서버 캐시 도입이나 React 추가 수정을 해결책으로 확정하지 않습니다.

## 변경 내용과 트레이드오프

본문의 세 가설은 다음과 같이 정리됐습니다.

- **페이지 한도 조정:** 한도를 키우며 비교한 결과, 최초 이력을 응답 한 건으로 받기로 2026-10-16에 정했습니다. 한도는 서버 설정으로 정합니다.
- **준비 상태 검사 개선:** 바꾸지 않았습니다. 최초 이력이 응답 한 건이 되면서 이 검사는 진입마다 한 번 실행되며, 실서버 DB에서 59ms였습니다.
- **GPS 일괄 조회:** 페이지의 구간과 좌표를 각각 SQL 한 번으로 읽도록 바꿨습니다(342aa440). 이어 트랜잭션 안의 반복 왕복을 없앴습니다(3aab945e).
- 가설 밖에서, 새 좌표 조회가 이력 응답을 기다리던 순서도 고쳤습니다(b5c93363).

### 응답 한도를 키운 비교와 한 번에 받기 선택

2026-10-15~16에 같은 일반 Chrome 탭에서 전체 이력(경로 481개, 구간 약 57,000개, 좌표 약 34만 개)을 응답 한도만 바꿔 받았습니다. 한도는 경로당 구간, 응답당 구간, 응답당 좌표 순서이고 각 조건 1회입니다.

| 한도 | 요청 수 | 첫 표시 | 전체 이력 | 새 좌표 반영 |
|---|---:|---:|---:|---:|
| 1/80/480 (기존) | 793 | 4.0초 | 652초 | 2.7초 |
| 16/1,280/7,680 | 64 | 5.0초 | 91초 | 8.2초 |
| 200/16,000/64,000 | 19 | 6.8초 | 38초 | 17.8초 |

- 서버가 거의 일을 하지 않는 요청도 왕복에 약 0.53초가 걸렸습니다(한국에서 Cloudflare를 거쳐 독일 서버까지). 작은 페이지를 반복하면 이 비용이 요청 수만큼 쌓입니다.
- 반대로 큰 페이지 한 건(약 9,700구간)은 첫 바이트까지 3.7~4.1초였습니다. 서버가 구간마다 좌표 SQL을 실행했기 때문입니다.
- 새 좌표 반영은 한도가 클수록 늦어졌습니다. 변경분 응답 12건 중 11건이 구간 0개, 경로 80개였습니다. 변경이 없어도 모든 경로를 한 번씩 방문하며 진행 정보를 채웠고, 새 좌표는 이 순회가 해당 경로에 닿아야 반영됐습니다.

그래서 왕복 횟수를 줄이는 한 번에 받기를 택하고, 그 대신 커지는 페이지 비용과 변경분의 빈 순회를 아래처럼 고쳤습니다.

### 페이지 안 SQL 일괄화와 변경 없는 경로 건너뛰기

한 페이지에 담을 구간을 `VALUES`와 `LATERAL`을 쓴 SQL 한 번(`findBoardSegments`)으로, 좌표는 이어지는 구간의 순번 범위로 묶어 SQL 한 번(`findBoardPoints`)으로 읽습니다(342aa440). 범위가 5,000개를 넘으면 JDBC 바인딩 인자 상한 안에 들도록 경로별 범위로 합칩니다. 앞서 고른 구간의 좌표 누락을 뒤 구간의 크기 오류보다 먼저 알리는 기존 오류 순서도 유지했습니다.

변경분 조회는 기준 버전과 현재 버전이 같고 진행 정보가 없는 경로를 방문하지 않습니다. 응답과 요청 필드, 페이지 진행 규칙은 그대로라 Frontend는 바꾸지 않았습니다.

### 트랜잭션 안 100행마다의 DB 왕복 제거

배포 후 이력 요청 한 건의 서버 처리는 5.24초였습니다. 로컬 분해에서 좌표 SQL이 조회 트랜잭션 안에서는 4.3~5.4초, 밖에서는 1.8초, DB 실행만은 0.15초였습니다. MyBatis 전역 `default-fetch-size: 100` 때문에 PostgreSQL JDBC가 트랜잭션 안에서 결과를 100행마다 나눠 받아, 좌표만 DB와 약 3,370번 왕복했습니다.

두 SQL에만 `fetchSize="10000"`을 줬습니다(3aab945e). 전체를 한 번에 받는 0과 시간 차이가 확인되지 않았고, 0은 드라이버가 원본 행 전체를 동시에 들고 있게 합니다. 미리 읽는 구간 후보와 합친 좌표 범위가 응답 한도보다 많을 수 있어 0은 쓰지 않았습니다. 전역값 100은 다른 조회(`SearchPathService.findAll`)의 나눠 받기 전제를 지키려고 유지했습니다.

### 새 좌표 조회가 이력 응답을 기다리지 않는 순서

기존 화면은 변경분 한 페이지를 받으면 남은 이력 한 페이지를 조회해, 새 좌표 알림이 와도 이력 응답을 기다렸습니다. 한쪽 조회의 성공이 다른 쪽의 미복구 오류와 실패 횟수를 지우는 문제도 있었습니다. 최초 이력으로 변경 추적 기준을 얻은 뒤에는 변경분을 최대 2페이지 연속 조회하고 남은 이력에도 차례를 주도록 바꿨습니다(b5c93363). 오류와 연속 실패 횟수는 종류별로 따로 관리하고, 같은 범위의 진행 중 HTTP 요청은 하나로 유지합니다. 2페이지는 시험 정책이며 검증한 최적값이 아닙니다.

### 한 번에 받기의 대가

- 응답 한 건이 커졌습니다. 고정 시험 사건의 이력 응답은 서버에서 압축 없이 약 22MB이고, 브라우저까지는 앞단 프록시가 압축해 3.3MB를 보냅니다.
- 전체를 한 번에 지도에 반영하므로 첫 표시가 늦어졌습니다(아래 검증 결과). 2026-10-16에 한 번에 표시하기로 정하면서 예상한 대가입니다.
- 응답 크기 상한(응답당 좌표 400,000개)의 운영값과, 응답이 커질 때의 서버와 브라우저 메모리는 정하지 않았습니다. 응답보다 많이 읽는 구간 후보 조회도 남아 있습니다.

## 검증 결과

배포본(342aa440, Jenkins #68)을 서버 한도 1,000/100,000/100,000/400,000(응답당 경로, 경로당 구간, 응답당 구간, 응답당 좌표)으로 바꿔, 위 비교와 같은 일반 탭과 계정, 사건, 차수에서 1회 측정했습니다.

| 항목 | 기존 1/80/480 | 배포 후 |
|---|---:|---:|
| 경로 요청 수 | 793 | 3 (이력 1, 변경분 2) |
| 전체 이력 수신 | 652초 | 10.1초 |
| 첫 경로 관찰 | 4.0초 | 12.2초 |
| GPS 전송부터 지도 관찰 | 2.7초 | 5.4초 |

- **첫 번째 체크 항목:** 같은 데이터와 브라우저 조건에서 경로 요청 수가 793건에서 3건으로, 전체 이력 수신 시간이 652초에서 10.1초로 줄었습니다. 기존 값은 2026-10-15 조회 순서 수정 전에 같은 탭에서 잰 값입니다.
- **두 번째 체크 항목:** 받은 경로 481개, 구간 57,097개, 좌표 341,069개와 최종 지도 source가 DB와 일치했습니다. 동시 저장은 `SearchPathBoardServiceTest`의 "조회 도중 새 구간이 커밋돼도 최초 페이지와 기준 버전은 같은 시점을 유지한다"가 확인합니다. 조회를 멈춘 사이 다른 트랜잭션이 좌표, 구간, 버전을 함께 추가해도 진행 중이던 응답에는 이전 버전과 그 구간만 담깁니다. 일괄 SQL로 바꾼 뒤 이 테스트를 포함한 23개가 통과했습니다.
- **세 번째 체크 항목:** 바뀐 일괄 읽기 경로에서 응답에 담을 구간의 좌표가 일부 또는 전부 없을 때와, 순번 보완이 끝나지 않은 구간이 있을 때 조회를 거부하는 테스트가 통과했습니다. 경로의 GPS, 구간, 순번, 변경 버전 미비를 판정하는 준비 상태 검사 SQL(`hasUnpreparedBoardPaths`)은 2026-10-08 이후 바뀌지 않았습니다.
- **fetch size:** 로컬 성능 측정(경로 468개, 좌표 336,954개, 한 페이지)에서 Service 조회가 5.4~6.4초에서 2.3~3.4초가 됐습니다. 실서버 배포(Jenkins #70) 뒤 2026-10-19에 잰 이력 요청의 서버 처리는 3.14초(데워진 상태)였습니다. 배포 직후의 5.24초와는 측정일과 조건이 달라 개선량으로 계산하지 않습니다.
- Backend 전체 테스트는 두 커밋 모두 12개가 실패했습니다(SSE 4개, TomcatProxy 7개, SecurityConfig 1개). 변경 전부터 같은 로컬 HTTP 환경에서 실패하던 테스트입니다.

### 첫 표시와 새 좌표 반영의 남은 문제

- 첫 경로 관찰은 4.0초에서 12.2초로 늦어졌습니다. 응답 본문을 다 읽은 9.0초 뒤 전체 경로를 한 번에 지도에 반영하는 데 약 3.2초가 더 걸렸습니다. 이 값은 진입 클릭이 아니라 관찰기를 설치한 시각부터 잰 값이며 관찰기 비용을 포함합니다.
- 새 좌표 반영 5.4초는 초기 로딩이 끝난 뒤(72.8초) 보낸 결과이고, 기존 2.7초는 로딩 중에 보낸 결과라 직접 비교할 수 없습니다. 5.4초는 저장 응답 0.66초, 해당 경로 하나만 담긴 변경분 수신 1.72초, 지도 반영 3.06초로 나뉩니다. 변경분이 바뀐 경로만 담는 것은 확인했습니다. 목표 3초를 넘으며, 초기 로딩 중에 보낸 새 좌표의 반영 시간은 아직 다시 재지 않았습니다.
- 진입부터 전체 경로 지도 반영까지의 지연은 [문제 해결 기록 40](40-board-entry-full-path-map-delay.md)에서 이어서 다룹니다.
