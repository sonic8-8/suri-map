# [BE] SSE 전송을 기다리던 사건이 종료, 파기돼도 뒤 연결에 과거 이벤트가 전달되는 문제

## 문제 배경

사건이 종료·파기되면 과거 경로·마커 내용을 계속 내보내지 않아야 합니다. 전송 시작 시 진행 중이었더라도, 다른 연결을 기다리는 사이 사건 상태가 바뀔 수 있습니다. 이미 통신으로 내보낸 내용을 되돌리는 것과 아직 쓰기 시작하지 않은 이벤트를 막는 것은 구분합니다.

2026-09-28~29 로컬 점검에서, 상태 확인을 통과한 전송을 첫 연결에서 기다리게 한 뒤 DB에 종료, 파기 완료를 저장했습니다. 이후 대기를 풀자 뒤 연결에 이전 `PATH_APPENDED` 이벤트가 전달됐습니다. [느린 연결의 전달 지연](29-slow-sse-connection-blocks-live-delivery.md)과 연관되지만, 전송 직전 상태를 조율하는 문제는 따로 확인해야 합니다.

### 문제 해결: 체크리스트

- [ ] 사건 종료·파기와 아직 쓰기 시작하지 않은 이벤트 전송을 조율하는 기준이 명확한가?
- [ ] 상태 확인 뒤 종료·파기되는 조건에서도 뒤 연결에 과거 내용을 보내지 않는가?
- [ ] 필요한 종료 알림·연결 정리·미완료 작업과 DB 원본 보존을 함께 유지하는가?
- [x] 일반 전송뿐 아니라 재전송·대기분 전송에도 같은 종료 기준을 검증하는가? — 로컬의 전송 직전 상태 검사·종료 알림 처리 검증

## 원인 분석과 선택지

### 재현 결과: DB 상태 변경 뒤에도 과거 이벤트 전달

2026-09-28~29 진단에서는 실제 PostgreSQL/PostGIS, Spring Service, Mapper를 사용했습니다. 연결의 수신 대상만 대역으로 두어 다음 순서를 고정했습니다.

1. 경로 이벤트와 순번을 DB에 저장하고 실시간 전송을 시작합니다.
2. 상태 확인이 끝난 뒤 첫 연결의 전송을 멈춥니다.
3. 별도 DB 연결에서 사건 종료 또는 파기 완료 상태를 저장합니다.
4. 첫 연결의 대기를 풀고 뒤 연결에 전달되는 이벤트를 확인합니다.

진행 중 상태를 유지한 대조 조건은 통과했습니다. `CLOSED`와 파기 `COMPLETED` 조건은 모두 뒤 연결에 경로 이벤트가 전달돼 실패했습니다. 실제 전달 시점에 다시 SQL을 실행해 각각 `status=CLOSED, purged=false/true`도 확인했습니다. 상태 변경이 저장되지 않았거나 과거 상태를 관찰한 결과가 아닙니다.

이 시험은 종료 API 전체나 실제 개인정보 삭제를 실행한 검증이 아닙니다. 테스트 DB의 상태 변경과 전송 사이의 순서를 고정한 재현이며, 운영 사건·자료는 변경하지 않았습니다.

### 확인한 원인: 전송 시작 전의 상태를 계속 사용

[SseStreamService.dispatchLive](../../backend/src/main/java/com/surimap/api/service/sse/ServerSentEventSubscriptionService.java)는 일반 이벤트를 보내기 전에 DB 상태를 검사했습니다. 그 뒤 [연결 목록의 전송](../../backend/src/main/java/com/surimap/global/sse/ServerSentEventConnectionRegistry.java)으로 넘어가면 중간에 DB 상태가 바뀌어도 남은 연결의 전송을 계속했습니다.

기존 검사는 **호출 전부터** 종료·파기된 사건을 차단하는지 확인했습니다. 이번에는 **상태 검사 후, 뒤 연결에 쓰기 전** 상태가 바뀌는 조건을 추가했습니다. 단순히 앞부분의 상태 조회를 하나 더 넣는 것으로 이 시간차가 해결됐다고 보지 않습니다.

### 먼저 적용한 변경: DB 잠금 없이 쓰기 직전에 상태 재확인

연결별 전송 분리와 함께 종료와 파기를 어느 시점부터 반영할지 설계해야 합니다. 이 설계는 아래 "아직 정하지 않은 선택"과 같이 지금도 정하지 않았고, 쓰기 직전의 상태 재확인은 그 과제의 일부로 먼저 적용한 변경입니다. DB 잠금을 네트워크 쓰기 동안 유지하거나 사건 종료를 느린 브라우저가 끝날 때까지 기다리게 하는 방식은 도입하지 않았습니다. 재전송 페이지를 읽은 직후 종료되는 조건은 별도 검증으로 남겼고, 이후 수정의 MVC 검사에서 확인했습니다.

실패 재현용 변경은 일반 테스트에서 제거하고 진단 패치로 남겼습니다. 진단 시점에는 제품 코드 수정과 배포를 하지 않았습니다. 이후 2026-09-29에 일반 이벤트를 실제로 쓰기 직전에 사건 상태를 다시 확인하도록 수정했고, 이 수정을 포함한 `f546da52`를 배포했습니다. GitHub 등록은 하지 않았고, 체크리스트의 앞 세 항목은 지금도 미완료입니다.

### 상태 재확인 뒤 남은 원인: 마지막 조회와 실제 쓰기 사이의 경합

2026-09-29 추가 재현에서는 상태 재확인을 적용한 뒤에도, 마지막 DB 조회 후 종료나 파기가 커밋되면 실제 소켓에 과거 이벤트가 전달됐습니다.

- 조건: `f546da52`의 실제 Spring 트랜잭션, MyBatis, PostgreSQL/PostGIS와 Tomcat, SSE, TCP를 사용했습니다. 마지막 상태 조회의 앞뒤에서만 대기하도록 진단 코드를 넣어 순서를 고정했습니다.
- 문제: 조회 트랜잭션이 끝난 뒤, 아직 소켓에 쓰기 전에 다른 DB 커넥션으로 종료나 파기 상태를 커밋했습니다. 대기를 풀자 `PATH_APPENDED`가 수신됐습니다.
- 대조: 상태 변경을 마지막 조회 앞으로 옮기거나, 대기를 풀기 전에 종료 알림을 연결에 전달하면 과거 이벤트가 차단됐습니다.

| 상태 변경과 알림의 시점 | 사건 종료 | 파기 완료 |
|---|---|---|
| 마지막 조회 전 커밋 | 일반 이벤트 차단 | 일반 이벤트 차단 |
| 마지막 조회 후, 쓰기 전 커밋 | 과거 경로 이벤트 수신 — 실패 | 과거 경로 이벤트 수신 — 실패 |
| 조회 후 커밋하고 종료 알림을 먼저 전달 | 종료 알림만 수신 | 파기 알림만 수신 |

진행 중 상태를 유지한 대조는 세 조건 모두 경로 이벤트를 받았습니다. 종료나 파기 커밋 후 별도로 실행한 상태 검사도 모두 거부됐습니다. 따라서 이 재현은 DB가 과거 상태를 계속 반환한 문제가 아니라, **마지막 상태 조회와 실제 쓰기 사이를 조율하지 못한 문제**입니다.

### 아직 정하지 않은 선택: 종료와 전송 시작의 처리 순서

진단 9개 중 7개 통과, 2개 실패입니다. 종료 API 전체, 실제 개인정보 삭제, 운영 사건은 실행하지 않았으며, 테스트 DB의 상태 변경과 실제 전송 사이의 경합을 확인했습니다. 종료 알림이 먼저 도착한 대조의 성공을 모든 종료 경합의 해결로 확대하지 않습니다.

단순히 상태 조회를 더 넣는 것으로 해결됐다고 처리하지 않습니다. 이미 시작한 전송과 아직 시작하지 않은 전송의 구분, 사건 종료, 파기와 전송 시작의 순서를 함께 정해야 합니다. 느린 네트워크를 기다리는 동안 DB 잠금을 유지하는 변경도 하지 않았습니다. 명령, JUnit, 대조 결과는 당시 로컬에만 보존했으며 제품 코드 수정, 추가 배포, GitHub 등록은 하지 않았습니다.

## 변경 내용과 트레이드오프

2026-09-29에 일반 이벤트를 대기 후 실제로 보낼 때 사건 상태를 다시 확인하도록 바꿨습니다.

- 문제: 전송 시작 전에 확인한 상태를 연결 대기 후에도 그대로 사용했습니다. 재전송 페이지를 이미 읽은 경우에도 같은 시간차가 생길 수 있었습니다.
- 변경: 실시간 대기열과 재전송에서 일반 이벤트를 쓰기 직전, 사건이 진행 중이고 파기가 완료되지 않았는지 SQL 한 번으로 다시 확인합니다. 조회 트랜잭션은 네트워크 쓰기 전에 끝냅니다.
- 종료 처리: 종료나 파기 알림이 도착하면 아직 대기 중인 일반 이벤트를 버리고 종료 알림을 보낸 뒤 닫습니다. 상태를 조회하는 사이 종료 알림이 도착한 경우에도 그 알림을 남깁니다. 이미 진행 중인 응답 쓰기를 회수하지는 않습니다.

이력 보존 기간, payload 파기 기능은 바꾸지 않았습니다.

### 남은 한계: 마지막 상태 조회와 통신 시작은 원자적이지 않음

마지막 SQL이 끝난 직후부터 응답 쓰기가 시작되기 전에도 짧은 간격은 남습니다. 이때 DB 종료나 파기가 커밋되는 모든 경우까지 막았다고 판단하지 않습니다. DB 잠금을 느린 통신 동안 유지하지 않았으며, 종료 API와 실제 개인정보 파기 전체를 동시에 실행한 검증도 아닙니다. 따라서 이 이슈 전체를 해결 완료로 처리하지 않습니다. 이 간격은 이후 추가 재현에서 실제 소켓으로 과거 이벤트가 전달되는 것으로 확인됐습니다(위의 상태 재확인 뒤 남은 원인).

## 검증 결과

체크리스트 넷째 항목은 아래 로컬 검사로 확인했습니다. 첫째 항목은 종료와 전송 시작의 처리 순서를 아직 정하지 않았고, 둘째 항목은 마지막 상태 조회 뒤 종료나 파기가 커밋되면 과거 이벤트가 전달돼 미완료입니다. 셋째 항목도 미완료이며, 종료 API와 실제 개인정보 파기 전체를 실행한 검증은 아직 없습니다.

### 로컬 검사: 재현한 시간차와 재전송, 대기열 조건 통과

실제 PostgreSQL에서 첫 전달을 기다리는 사이 `CLOSED` 또는 파기 `COMPLETED`를 저장한 재현이 통과했습니다. 진행 중 상태를 유지하면 뒤 연결에도 전달합니다. MVC 검사에는 대기열에 넣은 후 상태 거부, 페이지 조회 후 상태 거부, 상태 조회 중 종료 알림 도착, 종료 알림 전송 후 연결 정리도 추가했습니다. 관련 127개 검사는 실패, 오류, 건너뜀 없이 통과했습니다.

커밋 대상만 추출한 Docker 전체 테스트도 223개 클래스, 1,345개가 통과했습니다(5분 14초, 실패, 오류, 건너뜀 0, 기본 성능 태그 제외). 배포와 브라우저 검증 전에 실행한 결과이며, 배포 후 확인은 아래에 적었습니다.

### 배포 후 상태: 수정 반영, 종료와 파기 전체 검증은 미완료

`f546da52`를 Jenkins #46으로 배포했고 CI의 1,345개 검사도 통과했습니다. 진행 중 사건에서 배포 후 재연결과 서버 재시작 후 DB 이어받기, 지도 갱신, 마커 복원을 확인했습니다. 첫 SSH 확인 timeout과 반복 성공은 [문제 해결 기록 29](29-slow-sse-connection-blocks-live-delivery.md)에 구분해 기록했습니다.

운영 사건을 종료하거나 개인정보를 파기한 시험은 아닙니다. 위의 마지막 상태 조회 이후 경합도 남아 있으므로, 배포 성공을 이 이슈 전체의 해결로 처리하지 않습니다.
