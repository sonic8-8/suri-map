# [BE/FE] 상황판 경로를 나눠 조회해도 지도 표시와 전체 이력 로딩이 지연됨

## 문제 배경

상황판은 지휘관이 업무폰에서 기록한 수색 경로를 확인하는 화면입니다. 누적 경로를 한꺼번에 조회하던 방식에서, 구간을 나눠 받아 먼저 받은 구간부터 지도에 표시하는 방식으로 변경했습니다. 전체 이력을 기다리지 않고 현재까지 받은 경로를 확인할 수 있도록 하기 위한 변경입니다.

그러나 2026-10-07 배포 후 실제 브라우저에서 확인한 결과, 첫 구간 응답은 약 2초 만에 받았지만 첫 경로 표시가 계측되기까지는 약 31초가 걸렸습니다. 약 7분 37초까지 관찰했을 때도 전체 구간의 절반 미만을 받은 상태였습니다.

### 배포 후 확인한 지연

브라우저 1개로 경로 481개·구간 57,083개가 있는 상황판을 열었습니다. 구간은 한 경로를 구성하는 일부 도형이며, 이번 시험에서는 HTTP 응답 한 번에 최대 80구간을 받도록 설정했습니다. 새 좌표나 마커는 보내지 않았습니다.

| 확인 항목 | 관측 결과 |
|---|---|
| 첫 구간 응답 수신 | 상황판 진입 후 약 2.015초 |
| 첫 경로 표시 계측 | 상황판 진입 후 약 30.685초 |
| 약 457초까지 받은 구간 | 27,120 / 57,083개 |
| 완료한 경로 조회 | 346건: 구간 조회 339건·변경분 조회 7건 |
| 조회 실패 / 최대 동시 요청 | 0건 / 1건 |

관찰을 종료할 때 화면에는 일부 경로만 불러온 상태가 표시돼 있었습니다. 전체 이력 로딩이 끝나지 않아 관찰을 중단한 것이며, 요청 시간 초과나 데이터 누락이 확인된 것은 아닙니다. 전체 완료 시간도 아직 모릅니다.

첫 응답 수신과 지도 표시 사이의 지연, 전체 이력을 채우는 데 걸리는 시간을 구분해 확인해야 합니다. 이 확인이 끝나기 전까지 새 좌표 반영 Smoke 테스트와 본 부하테스트는 보류합니다.

### 문제 해결: 체크리스트

- [x] 전체 이력 수신을 기다리지 않고, 먼저 받은 구간을 지도에서 확인할 수 있는가?
- [x] 조회 대상의 모든 구간을 빠짐없이 받은 뒤 일부만 표시 중이라는 상태가 종료되는가?

위 항목은 [기존에 합의한 표시 동작](../features/situation-board.md)을 확인하기 위한 기준입니다. 허용할 표시, 로딩 시간은 아직 정하지 않았으므로, 기능 확인만으로 성능 문제까지 해결됐다고 판단하지 않습니다.

## 원인 분석과 선택지

### 작은 응답 단위와 반복 조회 비용

57,083구간을 한 번에 최대 80구간씩 받으려면 구간 조회만 최소 714번 필요합니다. 실제 관찰에서도 339번의 구간 조회로 27,120구간을 받았습니다. 한 번의 조회가 정상이어도 요청·응답을 반복하는 시간이 전체 로딩에 누적될 수 있습니다.

응답 한도를 늘리면 조회 횟수는 줄지만 한 번에 전송하고 지도에 반영할 데이터는 늘어납니다. 따라서 한도가 작다는 이유만으로 설정을 바꾸지 않고, HTTP 처리 시간과 응답 사이의 브라우저 처리 시간을 먼저 나눠 측정합니다.

### 데이터 수신과 지도 표시 사이의 지연

첫 구간을 받은 뒤 첫 경로 표시가 계측되기까지 약 29초의 차이가 있습니다. 지도 초기화, 받은 구간의 병합, 반복적인 지도 갱신, 계측 자체의 영향은 아직 분리하지 못했습니다. 계측 시각이 실제 첫 화면 표시와 일치하는지도 확인해야 합니다.

현재 확인한 것은 지연 현상이며 지배적인 병목이나 수정 방법은 확정하지 않았습니다. [문제 해결 기록 34](34-board-read-timeout-with-accumulated-paths.md)의 데이터베이스 커넥션 풀 대기 오류와 달리, 이번 관찰에서는 조회 실패 없이 지연이 발생했습니다. 기존 이슈 본문은 유지하고 새 조회 방식의 문제를 여기서 추적합니다.

배포 환경, 관찰 범위와 검증 한계는 [배포 후 검증 기록](../test-results/search-path-pages-deployment-20261007.md)에 남겼습니다.

## 변경 내용과 트레이드오프

본문에서 구분한 두 지연 중 "데이터 수신과 지도 표시 사이의 지연"에서, 경로가 일부만 늘어나도 지도 도형 전체를 다시 만들어 넘기던 처리를 고쳤습니다(3cd0dc3e, 2026-10-08). 바뀌지 않은 경로와 도형은 재사용하고, 지도 작업자(Web Worker)가 마지막으로 반영한 자료와 비교해 추가, 수정, 삭제된 도형만 넘깁니다. 작업자가 처리 중일 때는 최신 자료 하나만 보관했다가 처리가 끝나면 이어서 반영하므로, 응답마다 전체 작업이 쌓이지 않습니다. 최초 반영처럼 재사용할 도형이 없으면 기존처럼 전체를 넘깁니다.

로컬 합성 데이터(경로 481개, 구간 57,720개, 매회 서로 다른 80개 경로에 구간 하나씩 추가, 화면 계측 끔)에서 지도 갱신 시간은 평균 1,389ms에서 888ms로 줄었습니다. API, DB와 응답 한도(경로당 1구간, 응답당 80구간과 480좌표)는 바꾸지 않았습니다.

이 변경은 작은 응답을 반복하며 쌓이는 시간은 줄이지 않습니다. 반복 조회 비용과 그 개선은 [문제 해결 기록 38](38-repeated-search-path-page-queries.md)에서, 최초 이력을 한 번에 받은 뒤 남은 상황판 진입 지연은 [문제 해결 기록 40](40-board-entry-full-path-map-delay.md)에서 다룹니다.

## 검증 결과

이 변경의 배포본(Jenkins #60)에서 같은 사건과 차수(경로 481개, 구간 57,083개)를 1회 측정했습니다. WSL의 Headless Chrome 147(1440×900, 소프트웨어 그래픽 처리)로 상황판을 열었고, 새 좌표나 마커는 보내지 않았습니다.

| 확인 항목 | 결과 |
|---|---|
| 첫 경로 렌더링 계측 | 진입 후 3.62초 |
| 전체 이력 수신 | 734.54초(12분 14.54초), 경로 조회 793건(이력 786건, 변경분 7건), 실패 0건 |
| 받은 구간 ID | 57,083개, 측정 전후 DB 목록과 정렬 후 전체 일치 |
| 지도에 넘긴 구간 ID의 합집합 | 57,083개, DB 목록과 일치 |
| "일부 경로만 표시 중" 문구 | 전체 수신 완료 후 사라짐 |

- 전체 이력을 받는 데 12분이 넘게 걸리는 동안, 첫 경로는 3.62초에 지도에 그려졌습니다. 첫 번째 체크 항목의 근거입니다.
- 모든 구간을 빠짐없이 받은 뒤 일부만 표시 중이라는 문구가 사라졌습니다. 두 번째 체크 항목의 근거입니다.

두 체크 항목은 합의한 표시 동작을 확인한 것이며, 본문에 적은 대로 성능 문제의 해결을 뜻하지 않습니다. 734.54초는 마지막 구간이 실제로 그려진 시각이 아니라 수신과 캐시 반영이 끝난 시각입니다. 한 번 실행한 결과이고, 소프트웨어 그래픽 처리와 제품 계측 비용이 포함됐습니다.

- 표시 시간 목표는 2026-10-16에 진입 클릭부터 첫 표시와 전체 이력 지도 반영 각 5초로 정했습니다([경로 표시 목표](../features/situation-board.md#화면과-관측에서-남은-요구)). 같은 날부터 시험 사건의 최초 이력은 응답 한 건으로 받으므로, 이 사건에서는 나눠 받는 중의 표시가 더 이상 일어나지 않습니다. 응답이 나뉘는 규모의 표시는 이 측정 뒤 다시 확인하지 않았습니다.
- 이 측정 직후의 후속 검증에서, 축소한 지도에서 짧은 구간이 그려지지 않는 별도 문제를 발견했습니다([문제 해결 기록 41](41-zoomed-out-short-path-segments-hidden.md)).

측정 조건과 시간 분해는 [독립 Chrome의 전체 수색 경로 로딩 측정](../test-results/search-path-chrome-history-20261008.md)에 있습니다.
