# [FE] 나중에 읽은 Date.now()가 저장 시각보다 작아지면 상황판이 이전 차수의 경로를 다시 조회하지 않는 문제

## 문제 배경

상황판에서 지휘관은 수색 차수(OP) 범위를 골라 업무폰이 남긴 수색 경로를 봅니다. 예를 들어 1차만 볼 수도 있고, 1차와 2차를 함께 볼 수도 있습니다. 화면은 서버 상태를 TanStack Query로 관리하며, [경로 조회 훅 `useSearchPathPages`](../../frontend/src/features/path/api/searchPathPagesApi.ts)는 차수 범위마다 캐시 항목(query key)을 따로 둡니다. 그래서 같은 1차 경로가 "1차" 캐시와 "1차와 2차" 캐시에 각각 저장될 수 있습니다.

1차와 2차를 함께 보는 동안 1차 경로의 새 버전이 들어오면, "1차" 캐시에는 예전 버전이 남습니다. 그래서 1차만 보는 화면으로 돌아오면 훅은 다시 조회해야 합니다. 조회 함수는 다른 범위의 캐시에 있는 같은 경로를 먼저 합치고, 서버에 변경분(`/changes/query`)을 요청해 최신 상태를 확인합니다. 기존 코드는 이 동작을 위해 `staleTime: 0`을 지정했습니다. `staleTime`은 저장한 데이터를 얼마 동안 새 데이터로 볼지 정하는 값이고, 0은 "저장한 순간부터 오래된 데이터로 보고 돌아오면 항상 다시 조회한다"는 뜻으로 썼습니다.

그런데 2026-10-28 WSL2에서 커밋 `999ea9d0`의 코드를 바꾸지 않고 Frontend `npm test`를 3번 실행했더니, 2번은 `searchPathPagesApi.test.tsx`의 "이전에 방문한 차수 범위로 돌아와도, 계속 선택한 경로의 최신 구간과 진행을 유지한다" 하나가 실패했고 1번은 346개가 모두 통과했습니다. 같은 코드에서 결과가 실행마다 달랐으므로 실패만 보고는 어디가 잘못됐는지 알 수 없었습니다.

원인을 찾아보니 테스트가 아니라 제품 코드의 결함이었습니다. 먼저 읽은 `Date.now()`보다 나중에 읽은 `Date.now()`가 작아지면, 이전에 보던 차수 범위로 돌아와도 훅이 다시 조회하지 않았습니다. `Date.now()`는 컴퓨터의 현재 시각이라, 운영체제가 인터넷 시간 서버와 시각을 맞추며 앞서 가던 시각을 되돌리거나, 사용자가 시각을 더 이른 시각으로 바꾸거나, 노트북이나 가상 머신이 절전에서 깨어나 시각을 다시 맞출 때 이런 일이 생깁니다. 실제 상황판이라면 다음 순서로 지휘관이 예전 경로를 보게 됩니다. 아래 시각은 설명용 예시입니다.

| 순서 | 지휘관의 조작과 컴퓨터 상태 | 결과 |
|---|---|---|
| 1 | 1차를 본다 | 1차 경로를 저장한다. 이때 읽은 `Date.now()` 10:00:05가 저장 시각이다 |
| 2 | 1차와 2차를 함께 본다 | 이 범위에서 1차 경로의 최신 버전을 받는다 |
| 3 | 컴퓨터의 시각이 바뀐다 | 이제 `Date.now()`를 읽으면 10:00:03이 나온다 |
| 4 | 다시 1차만 고른다 | 다시 조회하지 않아 1단계에서 저장한 예전 1차 경로가 보인다 |

4단계의 화면은 다음 SSE 갱신 신호가 올 때까지 그대로입니다. SSE 갱신 신호를 받으면 화면은 오래됐는지 판정하지 않고 바로 다시 조회하기 때문에, 그 전까지만 예전 경로가 남습니다.

### 문제 해결: 체크리스트

- [x] 저장한 뒤 `Date.now()`가 먼저 읽은 값보다 작은 값을 돌려주게 하고 이전에 보던 차수로 돌아오면 경로를 다시 조회하는지 확인하는 회귀 테스트가, 보완 전 코드에서 실패하고 보완 뒤 통과하는가?
- [x] "이전에 방문한 차수 범위로 돌아와도..." 테스트를 300회 반복하는 실행을 보완 뒤 여러 번 해도 실패하지 않는가?
- [x] 컴퓨터의 시각이 바뀌지 않을 때의 차수 전환, SSE 갱신, 조회 제한 처리 테스트가 그대로 통과하는가?
- [x] Frontend `npm test`, `npm run typecheck`, `npm run build`가 통과하는가?

## 원인 분석과 선택지

조사를 시작할 때는 원인을 테스트 코드(대기 시간, 타이머, 실행 순서)에서 찾을지 제품 코드(경쟁 상태, 요청 순서)에서 찾을지 정하지 않았습니다. 다만 재시도를 붙이거나, 대기 시간만 늘리거나, 단언을 지워 통과시키는 방법은 처음부터 쓰지 않기로 했습니다. 실패의 원인이 제품 결함이면 그 결함을 그대로 둔 채 테스트만 조용해지기 때문입니다.

### 파일 하나 실행으로는 재현되지 않은 실패

먼저 테스트 파일 하나만 실행하는 `npx vitest run src/features/path/api/searchPathPagesApi.test.tsx`를 20번 실행했지만 한 번도 실패하지 않았습니다. 이 파일은 약 1.7초 만에 끝납니다.

그래서 대상 테스트 하나에 Vitest의 `{ repeats: 300 }` 옵션을 임시로 붙여 같은 테스트를 한 실행 안에서 반복했습니다. Vitest 4.1.5의 `repeats`는 첫 실행에 횟수를 더하므로 한 번 실행하면 테스트가 301번 돌고, 약 50초가 걸립니다. 이 명령은 보완 전 7번 중 6번 실패했습니다. 실패 메시지는 `AssertionError: expected '1' to be '3'`였고, 1차 범위로 돌아온 뒤 경로 버전이 3이 되기를 기다리는 `waitFor`가 1초 안에 끝나지 않은 것이었습니다. 실패 위치가 "돌아온 뒤 최신 버전을 다시 받았는가"였으므로, 돌아올 때 캐시를 어떻게 판정했는지 측정하기로 했습니다.

### 먼저 읽은 Date.now()보다 나중에 읽은 Date.now()가 작아진 측정값

측정에는 두 종류의 시각을 썼습니다. `Date.now()`는 컴퓨터의 현재 시각을 밀리초로 돌려주므로 컴퓨터의 시각이 바뀌면 값도 바뀝니다. `performance.now()`는 프로세스가 시작된 뒤 흐른 시간을 돌려주며, 컴퓨터의 시각을 바꿔도 줄어들지 않고 늘어나기만 합니다. 두 값을 같은 기준으로 비교하면 실제로 흐른 시간과 `Date.now()`가 말하는 시간이 다른지 알 수 있습니다.

실패한 반복 실행에 임시 로그를 넣어 다음 값을 기록했습니다. 로그는 측정 뒤 지웠습니다.

| 측정 | 값 | 의미 |
|---|---:|---|
| 1차 데이터를 저장할 때 읽은 `Date.now()`(저장 시각) | 1793237828344 | |
| 1차로 돌아오기 직전에 읽은 `Date.now()` | 1793237826705 | 저장 시각보다 1639ms(약 1.6초) 작다 |
| `performance.now()`로 잰 저장 시점과 실패 시점 | 30440ms, 31556ms | 실제로는 1116ms(약 1.1초)가 흘렀다 |
| 프로세스 시작 뒤 `Date.now()`와 `performance.now()` 기준 시각의 차이 | -1746.5ms | `Date.now()`가 약 1.7초 작아졌다 |

같은 실행에서 1차 query는 `fetchStatus: idle`, `isStale: false`였고 서버 요청(`post`)은 4번에서 멈춰 있었습니다. 돌아온 뒤 요청이 하나도 나가지 않았다는 뜻입니다. 응답이 늦거나 순서가 바뀐 것이 아니라 요청을 보내지 않았으므로, 테스트의 대기 시간이나 응답 순서로는 이 실패를 설명할 수 없습니다. 남은 질문은 "훅이 왜 다시 조회하지 않기로 판정했는가"였습니다.

### TanStack Query가 저장한 데이터를 오래됐다고 판정하는 방식

설치된 `@tanstack/query-core` 5.100.6 소스를 읽어 판정 경로를 확인했습니다. 화면이 같은 상태에서 query key만 바뀌면(1차와 2차에서 1차로 돌아오면) TanStack Query는 새 key의 저장된 데이터가 오래됐을 때만 다시 조회합니다. 이 경로는 `refetchOnMount` 옵션을 보지 않습니다.

오래됐는지는 다음 값으로 판정합니다. 이 값이 0이면 오래된 데이터입니다.

```ts
timeUntilStale = Math.max(저장 시각 + staleTime - Date.now(), 0)
```

시각이 바뀌지 않으면 나중에 읽은 `Date.now()`가 저장 시각보다 크거나 같습니다. 그래서 `staleTime: 0`일 때 괄호 안이 0 이하가 되고, 결과가 0이라 다시 조회합니다. 측정값을 넣으면 다릅니다.

```text
1793237828344 + 0 - 1793237826705 = 1639 > 0
```

결과가 0보다 크므로 TanStack Query는 1차 데이터를 "1.6초 뒤에 오래될 방금 받은 데이터"로 판정하고 다시 조회하지 않았습니다. 실제로는 1.1초 전에 저장한 데이터였고, 그사이 1차와 2차 범위에서 받은 버전 3도 합치지 못해 버전 1이 남았습니다. 결국 `staleTime: 0`은 "항상 다시 조회"가 아니라 "나중에 읽은 `Date.now()`가 저장 시각보다 크거나 같을 때만 다시 조회"였습니다.

이 실행 환경에서 `Date.now()`가 작아진 구체적인 이유(시간 서버 동기화, 가상 머신의 시각 보정 등)는 확인하지 않았습니다. 파일 하나 실행보다 `npm test`에서 더 자주 실패한 이유도 확인하지 못했습니다. 실행이 길수록 시각을 맞추는 순간과 겹칠 확률이 커지기 때문이라고 추정만 합니다.

### Date.now() 값과 관계없이 오래된 데이터로 판정하는 방법 선택

해결 기준은 "`Date.now()` 값과 관계없이, 이전에 보던 차수로 돌아오면 항상 다시 조회하고, 시각이 바뀌지 않을 때의 동작은 그대로 둔다"였습니다. 이 기준으로 다음 방법을 비교했습니다.

| 방법 | 동작 | 판단 |
|---|---|---|
| `staleTime: -Infinity` | `저장 시각 - Infinity - Date.now()`는 항상 음수라 판정 값이 항상 0이다. 데이터가 있으면 언제나 오래된 데이터다 | 선택. 옵션 한 줄이고, 시각이 바뀌지 않으면 `staleTime: 0`과 판정 결과가 같다 |
| 범위를 바꿀 때 이전 범위를 `invalidateQueries({ refetchType: 'none' })`로 표시 | 무효로 표시된 데이터는 시각과 관계없이 오래된 데이터다 | 범위 변경을 추적하는 코드가 늘어난다. 첫 방법을 받아들이지 못할 때의 대안으로 남겼다 |
| `refetchOnMount: 'always'` | 이름은 "항상 다시 조회"지만 query key가 바뀌는 이 경로에서는 보지 않는다 | 이 문제를 고치지 못한다 |
| 테스트에 재시도를 붙이거나 대기 시간을 늘린다 | 테스트만 통과한다 | 실제 상황판의 결함이 남으므로 쓰지 않는다 |

`staleTime: -Infinity`를 고른 이유는 변경이 가장 작고, 정상 상황의 동작을 바꾸지 않으며, 한 줄만 되돌리면 이전 동작으로 돌아가기 때문입니다. 설치된 소스에서 stale 타이머를 걸지 정하는 함수(`isValidTimeout`)가 음수를 걸러, 이 값에서는 타이머도 걸리지 않는 것을 함께 확인했습니다. 대가는 다음 절에 적었습니다.

## 변경 내용과 트레이드오프

[`c6f102c3`](https://github.com/sonic8-8/suri-map/commit/c6f102c3)에서 `useSearchPathPages`의 `staleTime: 0`을 `staleTime: -Infinity`로 바꾸고, 이유를 주석 한 줄로 남겼습니다. 같은 커밋에 회귀 테스트를 추가했습니다. 이 테스트는 `Date.now()`가 10000을 돌려주게 고정한 채 1차, 1차와 2차를 차례로 조회한 뒤 8000을 돌려주게 바꿉니다. 그리고 1차로 돌아왔을 때 다섯 번째 요청이 나가고 그 요청이 변경분 조회(`/changes/query`)인지 확인합니다. 실행마다 결과가 달랐던 원래 테스트는 바꾸지 않았습니다.

[`c39164f0`](https://github.com/sonic8-8/suri-map/commit/c39164f0)에서는 회귀 테스트 이름과 두 주석을 "먼저 읽은 `Date.now()`보다 나중에 읽은 `Date.now()`가 작아진다"는 표현으로 고쳤습니다. 동작은 바뀌지 않았습니다. [`8a52a37f`](https://github.com/sonic8-8/suri-map/commit/8a52a37f)에서는 [상황판 문서](../features/situation-board.md)에 "이전에 보던 차수 범위로 돌아오면 저장된 경로가 있어도 다시 조회한다"는 요구를 추가했습니다. 세 커밋은 [PR #24](https://github.com/sonic8-8/suri-map/pull/24)로 develop에 병합했습니다(`df82c998`).

바뀐 판정은 `useSearchPathPages`를 쓰는 상황판, 구역 상세, 차수 검토 화면의 경로 조회에만 적용됩니다. SSE 갱신 신호를 받았을 때 다시 조회하는 함수(`refreshSearchPathPages`), 조회 권한을 잃었을 때 경로를 지우는 함수(`restrictSearchPathPages`), 네트워크 재연결 때의 다시 조회는 그대로입니다. 같은 query key를 다른 `staleTime`으로 쓰는 화면도 없었습니다.

트레이드오프는 `staleTime: -Infinity`가 TanStack Query 문서에 적힌 값이 아니라는 점입니다. 타입이 `number`라 컴파일은 되지만, 위 판정은 query-core 5.100.6의 내부 계산에 기대고 있습니다. 라이브러리를 올릴 때 판정 식이나 음수 처리가 바뀌면 이 동작도 바뀔 수 있습니다. 회귀 테스트가 "`Date.now()`가 작아져도 돌아오면 다시 조회한다"는 결과를 검사하므로, 라이브러리를 올린 뒤 이 테스트가 실패하면 앞의 표에 남긴 `invalidateQueries` 방법으로 바꿀 수 있습니다.

| 테스트 파일 하나 실행 | 20번 중 0번 실패 | 20번 중 0번 실패 |
| 회귀 테스트(`Date.now()` 10000에서 8000으로) | 실패(`expected "post" to be called 5 times, but got 4 times`) | 통과 |

- **첫째 항목:** 회귀 테스트는 `staleTime: 0`에서 요청이 4번에서 멈춰 실패했고 `staleTime: -Infinity`에서 통과했습니다. 별도 검수에서 보완 전 소스를 사본으로 만들어 다시 실행했을 때도 요청이 5번이 아니라 4번이라 실패했고, 보완 뒤 소스에서는 통과했습니다.
- **둘째 항목:** 보완 뒤 300회 반복 실행을 세 차례에 걸쳐 모두 13번 했고 실패는 없었습니다.
- **셋째 항목:** 차수 전환, SSE 갱신, 조회 제한과 권한 상실 테스트(`searchPathPagesApi.test.tsx`, `useIncidentBoardEvents.test.tsx`, `usePagedIncidentBoardQuery.test.tsx`)는 본문을 바꾸지 않고 통과했습니다.
- **넷째 항목:** Frontend `npm test`가 63개 파일, 372개 테스트를 모두 통과했고 `npm run typecheck`, `npm run build`도 통과했습니다. 별도 검수 환경에서는 읽기 전용 폴더 때문에 build를 직접 실행하지 못해, 같은 커밋 `c39164f0`에서 따로 실행한 build 출력을 받았습니다. 이 출력에는 종료 코드가 없어서, 검수가 끝난 뒤 같은 커밋에서 build를 다시 실행해 종료 코드 0을 확인했습니다.

### 확인한 범위의 한계

- 보완 뒤 300회 반복 실행을 하는 동안 실제로 `Date.now()`가 작아졌는지는 기록하지 않았습니다. 보완 전 같은 조건에서 7번 중 6번 실패했다는 점이 간접 근거이고, `Date.now()`가 작아지는 상황 자체는 회귀 테스트가 값을 직접 바꿔 매번 같은 방식으로 재현합니다.
- 실제 브라우저에서 컴퓨터의 시각을 바꿔 상황판을 확인하지는 않았습니다.
- 이 실행 환경에서 `Date.now()`가 작아진 구체적인 원인과, `npm test`에서 더 자주 실패한 이유는 확인하지 않았습니다.
- TanStack Query를 올릴 때는 `staleTime: -Infinity`의 판정이 그대로인지 회귀 테스트로 다시 확인해야 합니다.
