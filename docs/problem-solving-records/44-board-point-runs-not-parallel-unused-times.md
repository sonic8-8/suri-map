# [BE] 상황판 경로 이력 요청에서 좌표 배열 SQL이 병렬로 실행되지 않고 응답에 쓰지 않는 측정 시각까지 계산되는 문제

## 문제 배경

상황판은 지휘관이 진행 중인 사건의 수색 상황을 보는 웹 화면이다. 현장 경찰관의 업무폰에서는 수색하며 지나간 위치를 GPS 좌표로 기록해 서버에 보낸다. 상황판에서는 이 GPS 좌표를 이은 수색 경로를 지도에 그린다. 사건의 수색은 수색 차수라는 기간 단위로 나뉜다. 상황판에서는 고른 수색 차수의 수색 경로를 보여 준다.

수색 경로는 경로 구간으로 나뉜다. 경로 구간은 수색 경로 안에서 같은 이동 유형(도보, 차량, 알 수 없음)으로 구분하는 부분이다. 한 경로의 GPS 좌표에는 수집한 순서대로 순번이 매겨진다. 경로 구간은 시작 순번과 끝 순번으로 자기 범위를 가진다. GPS 좌표마다 업무폰에서 그 좌표를 측정한 시각도 저장된다. 이 기록에서는 이 값을 측정 시각이라고 부른다.

지휘관이 상황판에 들어오면 웹에서 경로 이력(`POST /api/incidents/{incidentId}/board/search-paths/segments/query`)을 요청한다. 경로 이력은 페이지로 나눠 받는다. 상황판에 들어갈 때 나가는 첫 페이지 요청을 최초 이력 요청이라고 부른다. 최초 이력 요청의 응답을 받은 뒤에 웹에서 수색 경로를 지도에 그린다. 그 뒤에 생긴 변경은 경로 변경분 조회(`POST /api/incidents/{incidentId}/board/search-paths/changes/query`)로 받는다. 경로 변경분은 이미 받은 수색 경로에서 새로 추가되거나 수정된 경로 구간과 달라진 경로 상태다.

2026-11-13 실서버에서 사용자의 Chrome 탭으로 상황판에 3번 들어와, 수색 경로 전체가 지도에 그려질 때까지 걸린 시간을 쟀다. 결과는 3.78~5.13초였다([문제 해결 기록 43](43-board-entry-sse-full-replay.md#실서버에서-잰-상황판-조회-수와-sse-이벤트-수)). 이 시간은 최초 이력 요청의 응답을 기다리는 부분과, 응답을 받은 뒤 지도에 반영하는 부분으로 나뉜다. 같은 날 노트북 Chrome으로 성능 기록을 남긴 시간대(16:35~16:36, KST)에, 실서버 Backend의 Prometheus 지표(`http_server_requests_seconds_max`)에서 본 경로 이력 요청 처리 시간의 최댓값을 그 시간대에 3번 읽은 값은 1.55~1.60초였다. 이 지표의 값은 요청 하나하나를 기록한 값이 아니다. 지표를 읽은 시점에서 최근 약 2분 동안 처리한 요청 가운데 가장 오래 걸린 시간이다. 노트북 Chrome의 성능 기록에서 지도에 반영하는 부분은 1.8~2.3초였다. 세 값은 잰 방법이 달라서 두 부분을 더해도 전체 시간과 맞지 않는다. 이 기록은 응답을 기다리는 부분, 그중에서도 서버 처리에서 DB 조회에 드는 시간을 다룬다. 지도에 반영하는 부분은 따로 다룬다.

측정에 쓴 사건과 수색 차수에서 최초 이력 요청의 응답에는 경로 481개, 경로 구간 3,461개, GPS 좌표 341,069개가 담긴다. 응답 본문은 8,342,304자다. Backend에서는 이 응답을 만들 때 읽기 전용 트랜잭션 하나 안에서 SQL을 차례로 실행한다. 먼저 경로 구간 SQL(`findBoardSegments`)로 응답에 담을 경로 구간을 고른다. 이어서 좌표 배열 SQL(`findBoardPointRuns`)로 그 경로 구간의 GPS 좌표를 읽는다. 좌표 배열 SQL의 결과는 GPS 좌표 순번 범위마다 한 행이다. GPS 좌표 순번 범위는 응답에 담을 경로 구간 가운데 같은 경로에서 순번이 끊기지 않고 이어지는 경로 구간을 합친 순번 구간이다. 시작 순번부터 끝 순번까지의 GPS 좌표가 그 범위에 들어간다. 각 행에는 그 범위의 경도와 위도가 배열로 담긴다.

같은 날 같은 입력으로 SQL을 따로 `EXPLAIN ANALYZE`로 실행해 보니 DB 실행 시간은 합계 약 0.88초였다. 그 대부분이 좌표 배열 SQL의 실행 시간이었다. 이 값은 Backend가 요청을 처리하는 동안 잰 값이 아니다. 좌표 배열 SQL에서는 두 가지가 기대와 달랐다.

- 결과를 나눠 받도록 fetch size가 설정돼 있었다. fetch size는 JDBC에서 결과를 몇 행씩 나눠 받을지 정하는 값이다. 이 설정 때문에 PostgreSQL의 parallel worker가 쓰이지 않았다. parallel worker는 PostgreSQL에서 한 쿼리를 여러 프로세스로 나눠 실행할 때, 쿼리를 받은 연결의 서버 프로세스(leader) 말고 더 쓰이는 프로세스다. 실제 결과는 481행이라 나눠 받는 단위인 10000행보다 적었다. 그래서 나눠 받아 아낀 메모리도 없었다.
- 응답에 쓰지 않는 GPS 좌표별 측정 시각까지 계산해 받았다.

### 문제 해결: 체크리스트

아래 기준에서 경계 시각 SQL은 이번에 더한 SQL이다. 이 SQL로 경로 구간의 시작 순번과 끝 순번에 있는 GPS 좌표(경계 GPS 좌표)의 측정 시각을 읽는다. 무한 시각은 PostgreSQL `timestamptz`의 `infinity`와 `-infinity` 값이다. 경로 구간 묶기 migration은 업무폰의 전송 묶음마다 나뉘어 저장된 자동 분류(`AUTO`) 경로 구간 가운데, 순번이 이어지고 이동 유형이 같은 경로 구간을 합친 좌표가 120개를 넘지 않게 하나로 묶으려고 작성한 DB migration이다([Issue #34](https://github.com/sonic8-8/suri-map/issues/34)). 누적 경로 468개 성능 테스트는 로컬 DB에 경로 468개를 쌓아 두고 최초 이력 요청의 서비스 호출 시간을 재려고 작성한 `SearchPathBoardServiceTest.measure_first_page_with_accumulated_paths`다. Ops는 실서버와 따로 있는 운영 도구 서버다. k6는 HTTP 요청을 스크립트로 작성해 보낼 때 쓰는 부하 테스트 도구다.

## 원인 분석과 선택지

### fetch size 10000 때문에 parallel worker가 쓰이지 않던 원인

fetch size가 0이면 결과 전체를 한 번에 받는다. 이 프로젝트에서는 전역 기본값을 100으로 두고 SQL마다 따로 정한다.

2026-10-16에는 조회 트랜잭션 안에서 결과를 100행마다 받느라 DB와 3,370번 왕복했다. 이 왕복이 최초 이력 요청의 서버 처리 시간 대부분이었다([측정 근거](../test-results/search-path-initial-history-20261016.md#서버-처리-시간-분해와-fetch-size)). 그래서 경로 구간 SQL과 좌표 SQL에 fetch size 10000을 줬다. 당시 좌표 SQL의 결과는 GPS 좌표마다 한 행이라 약 34만 행이었다. 또 당시에는 바인딩 인자 수 상한 때문에, GPS 좌표 순번 범위가 5,000개를 넘으면 경로마다 첫 경로 구간의 시작 순번부터 마지막 경로 구간의 끝 순번까지를 한 범위로 합쳐 읽었다. 이때는 응답에 담지 않는 경로 구간의 GPS 좌표까지 읽혀, 실제로 읽는 행이 응답의 좌표 한도(실서버 40만 개)보다 많을 수 있었다. fetch size 0으로 한 번에 받으면 응답에 담지 않을 행까지 동시에 메모리에 올라갈 수 있었다. 그래서 0은 쓰지 않았다. 그때 로컬에서 0과 10000을 비교해 쟀을 때 뚜렷한 시간 차이는 없었다.

2026-10-20에 GPS 좌표 순번 범위를 경로 ID, 시작 순번, 끝 순번 배열 3개로 넘기도록 바꿨다. 그 뒤로는 바인딩 인자 수가 범위 수와 관계없이 3개라, 경로 전체로 합쳐 읽던 처리를 지웠다. 같은 날 좌표 SQL을, 결과가 GPS 좌표 순번 범위마다 배열 한 행인 좌표 배열 SQL로 바꿨다. 이때 fetch size 10000은 그대로 남았다. 바꾼 뒤 실서버 최초 이력 요청에서 좌표 배열 SQL의 결과는 481행이었다. 10000행보다 적으므로 실제로 나눠 받는 일은 없었다.

그런데 fetch size가 0보다 크면 결과가 적어도 비용이 생긴다. 트랜잭션 안에서 fetch size가 0보다 크면 PostgreSQL JDBC 드라이버에서 받을 행 수를 정한 Execute 메시지가 나간다. [PostgreSQL 문서](https://www.postgresql.org/docs/current/when-can-parallel-query-be-used.html)에 따르면 클라이언트에서 0이 아닌 행 수로 Execute 메시지를 보내면, 병렬 계획이 만들어져도 실행할 때 parallel worker가 시작되지 않는다. 이때는 계획 전체가 leader 프로세스 하나에서 실행된다. 결국 fetch size 10000으로 얻은 메모리 이득은 없었다. 병렬 실행만 빠졌다.

이 동작은 두 번 확인했다.

- 로컬 DB에서 실서버와 같은 병렬 계획을 강제해 실행했다. 로컬 DB의 기본 계획은 병렬이 아니었기 때문이다. fetch size 10000이면 계획에 parallel worker 2개가 잡혀도 실제로 시작된 parallel worker는 0개였다. fetch size 0이면 2개였다.
- 2026-11-14 실서버 DB에서 psql로 읽기 전용 트랜잭션을 열고 같은 좌표 배열 SQL을 비교했다. 나눠 받기는 psql 커서로 흉내 냈다. psql 커서에서는 처음부터 병렬 계획이 만들어지지 않는다. 그래서 이 비교는 병렬 계획이 없는 커서 실행과 parallel worker 2개를 쓴 일반 실행의 시간 비교다. JDBC에서 같은 병렬 계획을 두고 parallel worker 수만 다르게 한 비교는 아니다. 나눠 받으면 parallel worker 없이 1.28~1.35초였다. 한 번에 받으면 parallel worker 2개로 0.94~0.98초였다.

### 응답에 쓰지 않는 측정 시각 배열

응답에는 경로 구간마다 시작 시각과 끝 시각이 들어간다. 이 값은 경로 구간의 첫 GPS 좌표와 끝 GPS 좌표의 측정 시각이다. GPS 좌표마다 한 행을 받던 때에는 행마다 측정 시각이 붙어 있었다. 응답에는 그중 처음과 끝만 쓰였다. 2026-10-20에 배열로 묶을 때 응답 값이 바뀌지 않도록 측정 시각도 좌표와 같은 길이의 배열로 옮겼다.

그래서 좌표 배열 SQL에서는 측정 시각 약 34만 개를 모두 epoch 마이크로초 `bigint`로 바꿔 배열에 담았다. 응답에 쓰는 시각은 경로 구간마다 2개라 실서버 최초 이력 요청에서 약 6,900개다. 2026-10-31 실서버 측정에서는 이 측정 시각 계산에만 약 0.17초가 들었다.

측정 시각 배열 때문에 다시 읽는 처리도 있었다. epoch 마이크로초는 294247-01-10(UTC) 무렵에 `bigint` 범위를 넘는다. 그래서 무한 시각과 294247-01-01(UTC) 이후 시각은 `bigint`로 바꾸지 않고 배열에 0을 넣었다. 그런 시각이 있는 GPS 좌표 순번 범위에는 `has_out_of_range_client_ts` 열이 true로 나왔다. 서비스에서는 그런 범위를 모아 `findBoardPoints`로 한 번 더 읽었다. `findBoardPoints`의 결과는 GPS 좌표마다 한 행이었다. 응답에 쓰지 않는 중간 GPS 좌표의 시각 때문에 범위 전체를 다시 읽는 일도 생겼다.

### 좌표 배열 SQL만 한 번에 받고 경계 시각을 따로 읽는 방법 선택

fetch size는 좌표 배열 SQL만 0으로 바꾸기로 했다. 좌표 배열 SQL에서는 응답에 담기로 정한 경로 구간의 GPS 좌표만 읽는다. 결과 행 수는 GPS 좌표 순번 범위의 수다. 배열에 담기는 좌표 수는 응답의 좌표 한도를 넘지 않는다. 그래서 한 번에 받아도 응답에 담을 좌표보다 많은 양이 메모리에 올라가지 않는다. 2026-10-16에 0을 쓰지 않은 이유는 응답에 담지 않을 행까지 읽을 수 있다는 것이었다. 2026-10-20에 경로 전체로 합쳐 읽던 처리를 지운 뒤로는 응답에 담기로 정한 경로 구간의 좌표만 읽으므로 그 이유가 없어졌다. 경로 구간 SQL에서는 응답에 담을 경로 구간보다 많은 후보를 읽으므로 10000을 그대로 뒀다. 다른 조회는 결과를 나눠 받는다고 보고 작성됐으므로 전역 기본값 100도 바꾸지 않았다.

측정 시각은 좌표 배열 SQL에서 빼고, 경계 시각 SQL을 새로 더하기로 했다. 경계 시각 SQL에서는 응답에 담을 경로 구간마다 경계 GPS 좌표의 측정 시각을 `timestamptz` 그대로 읽는다. JDBC에서는 이 값을 `OffsetDateTime`으로 받는다. 그래서 `bigint`로 바꿀 일이 없다. 무한 시각과 294247-01-01(UTC) 이후 시각 때문에 다시 읽던 처리와 `findBoardPoints`도 지울 수 있다. 경계 시각 SQL은 경로 구간 수와 관계없이 요청마다 한 번 실행한다. 로컬 실험에서 경로 구간 배열을 `unnest`로 펼친 결과에 GPS 좌표를 바로 JOIN했을 때는 GPS 좌표 테이블 전체를 읽는 계획이 나왔다. 이때 `EXPLAIN ANALYZE` 실행 시간은 56~73ms였다. 경계마다 기본 키를 조회하도록 바꾸자 9~10ms였다. 이 실험의 실행 계획 원본은 남기지 않았다. 최종 구현에서는 경계마다 스칼라 하위 쿼리로 GPS 좌표 기본 키를 조회한다.

경로 구간 행에도 시작 시각과 끝 시각이 저장돼 있다. 이 값을 쓰면 GPS 좌표를 다시 조회하지 않아도 된다. 하지만 저장된 값이 GPS 좌표의 측정 시각과 언제나 같은지는 검증된 적이 없다. 그래서 지금처럼 GPS 좌표의 측정 시각을 쓰기로 했다.

다음 방법은 이번 범위에서 택하지 않았다.

| 방법 | 택하지 않은 이유 |
|---|---|
| 경도와 위도를 double로 저장 | DB schema를 바꿔야 한다 |
| 결과를 처음부터 이진 형식으로 받기(PostgreSQL JDBC의 `prepareThreshold` 조정) | 연결 공통 설정을 바꾸면 다른 SQL에도 영향이 간다. SQL 하나에만 적용하는 방법과 따로 비교해야 한다 |
| 경도와 위도를 `numeric`에서 `float8`로 바꾸는 계산을 parallel worker 쪽에서 하도록 SQL 모양 바꾸기 | PostgreSQL 플래너에서 하위 쿼리를 바깥 쿼리에 합치지 않는 동작에 기대야 한다. 이 동작이 공식 문서에 보장돼 있다는 근거를 찾지 못했다 |
| 경로 구간에 저장된 도형을 읽어 좌표를 대신하기 | "조회할 때 GPS 좌표를 순서대로 연결한다"는 [수색 경로 기능 정의 문서](../features/search-path.md)의 요구를 바꿔야 한다 |

2026-11-14 로컬 성능 테스트(경로 468개, GPS 좌표 336,960개)에서 두 변경을 함께 적용해 효과를 미리 확인했다. 시간은 좌표 배열 SQL의 Mapper 메서드를 호출해 결과를 받을 때까지 걸린 시간(Mapper 시간)으로 쟀다. 실서버와 같은 병렬 계획을 강제한 상태에서, 두 변경을 적용하자 좌표 배열 SQL의 Mapper 시간 중앙값이 줄었다. 같은 SQL을 반복해 실행하면 결과를 받는 형식이 텍스트 형식에서 이진 형식으로 바뀐다. 이 실험에서는 0부터 센 호출 순번 2~4의 결과가 텍스트 형식, 5~9의 결과가 이진 형식이었다. 그래서 두 형식을 나눠 쟀다. 호출 순번 0과 1은 예열이라 비교에서 뺐다. 텍스트 형식에서는 607.6ms가 327.6ms로, 이진 형식에서는 459.8ms가 257.6ms로 줄었다. 경계 시각 SQL의 Mapper 시간은 로컬 기본 계획에서 약 20ms였다. 같은 강제 계획 측정에서는 약 67ms였다. 이 값에는 JIT 컴파일 시간이 섞여 있다. JIT 컴파일은 PostgreSQL에서 계획 비용이 `jit_above_cost`보다 큰 쿼리의 식을 기계어로 컴파일하는 기능이다.

## 변경 내용과 트레이드오프

변경은 PR [#43](https://github.com/sonic8-8/suri-map/pull/43)으로 develop에 병합했다(merge commit `72c7056d`, 2026-11-15). 커밋은 두 개다.

- `5f96b3fa`([#41](https://github.com/sonic8-8/suri-map/issues/41)): [경로 Mapper](../../backend/src/main/resources/mapper/path/SearchPathMapper.xml)에서 좌표 배열 SQL의 fetch size를 10000에서 0으로 바꿨다. fetch size를 기록하는 서비스 테스트의 기대값을 바꿨다.
- `a0fbc06c`([#42](https://github.com/sonic8-8/suri-map/issues/42)): 좌표 배열 SQL에서 측정 시각 배열(`client_ts_epoch_micros`)과 `has_out_of_range_client_ts` 열을 뺐다. 경계 시각 SQL(`findBoardSegmentTimes`)을 fetch size 0으로 더했다. [`SearchPathBoardService`](../../backend/src/main/java/com/surimap/api/service/path/SearchPathBoardService.java)에서는 경계 시각 SQL로 읽은 시각을 경로 구간의 시작 시각과 끝 시각으로 담도록 했다. 경계 GPS 좌표가 없으면 지금처럼 `503 search_path_query_not_ready`로 거부한다. 다시 읽던 처리와 `findBoardPoints`를 지웠다. `findBoardPoints`를 확인하던 Mapper 테스트 2개 가운데 하나는 지웠다. 다른 하나는 경계 시각 SQL을 확인하는 테스트로 바꿨다. 서비스 테스트에 경계 시각 사례 3개를 더했다.

[상황판 기능 정의 문서](../features/situation-board.md)의 조회 fetch size 규칙과 경로 구간 시각 항목도 바뀐 동작과 이유에 맞게 고쳤다. 경로 이력과 경로 변경분 응답의 필드와 값, 오류 응답, DB schema는 바꾸지 않았다. 웹에서는 상황판, 수색 이력 화면, 인수인계 화면에서 이 API를 쓴다. Android 앱에서는 이 API를 쓰지 않는다. 그래서 Frontend와 Android는 바꾸지 않았다.

### 트레이드오프와 남은 한계

- 경계 시각 SQL에서는 경로 구간마다 기본 키 조회가 두 번 일어난다. 그래서 응답에 담을 경로 구간이 많으면 시간이 늘어난다. 경로 구간 묶기 migration을 적용하기 전의 로컬 성능 테스트 데이터에는 경로 구간이 56,160개 있었다. 이때는 기본 키 조회가 11만 번 넘게 일어났다. JIT 컴파일 시간도 더해졌다. 그래서 누적 경로 468개 성능 테스트에서 잰 서비스 호출 시간이 599~870ms에서 784~1,039ms로 늘었다. migration을 적용한 뒤의 데이터에서는 512~541ms가 427~453ms로 줄었다. 실서버 DB에는 이 migration이 2026-11-02에 적용됐다. 그래서 실서버는 적용한 뒤의 경우에 해당한다. 로컬 시간은 경우마다 한 번의 실행에서 5번씩만 쟀다. 흔들림은 따로 재지 않았다.
- fetch size를 0으로 바꾸면 parallel worker를 쓰지 못하던 제약만 없어진다. 실제로 병렬로 실행될지는 그때 PostgreSQL에서 고른 실행 계획과 남은 parallel worker 수에 달려 있다.
- 좌표 배열 SQL의 결과를 한 번에 받으므로 응답에 담을 좌표가 모두 동시에 메모리에 올라간다. 이 양은 응답의 좌표 한도를 넘지 않는다.

## 검증 결과

### 테스트로 확인한 동작

상황판 경로 조회 서비스 테스트(`SearchPathBoardServiceTest`)는 실제 PostGIS DB로 실행된다. fetch size를 기록하는 사례에서 좌표 배열 SQL의 기대값을 0으로 바꾸면 수정 전 코드에서 실패했다. 좌표 배열 SQL이 10000으로 실행됐기 때문이다. 수정한 뒤에는 경로 이력 조회와 경로 변경분 조회 모두에서 좌표 배열 SQL은 0으로, 경로 구간 SQL은 10000으로 실행됐다. 이것으로 첫째 기준을 확인했다.

새로 더한 사례 3개에서는 이어지는 경로 구간 두 개가 한 GPS 좌표 순번 범위로 읽혀도 각자의 시작 시각과 끝 시각이 나왔다. 무한 시각이 경로 구간의 중간 GPS 좌표에만 있어도 조회가 실패하지 않았다. 이때 좌표는 저장된 값과 같았다. 시작 시각과 끝 시각은 경계 GPS 좌표의 측정 시각과 같았다. 시작 순번에 GPS 좌표가 없으면 거부됐다. 마이크로초 시각, 무한 시각, 좌표 누락, 조회 도중 커밋된 경로 구간 사례처럼 지금 응답 값이 바뀌지 않는지 확인하던 기존 테스트는 단언을 고치지 않고 통과했다. SQL 실행 수 사례에서는 경계 시각 SQL이 더해져도 실행 수가 응답의 경로 수와 관계없이 같았다. 이것으로 둘째부터 다섯째 기준을 확인했다.

응답이 같은지는 누적 경로 468개(GPS 좌표 336,960개) 성능 테스트로 확인했다. 이때 한 페이지의 경로 수, 경로 구간 수, 좌표 수 한도를 임시로 실서버 한도로 키웠다. 경로 구간 묶기 migration을 적용하기 전과 뒤 두 경우 모두 develop(`1a37f0e0`), `5f96b3fa`, `a0fbc06c`에서 만든 공개 응답 JSON의 SHA-256이 같았다. 해시를 계산하는 임시 코드는 커밋하지 않았다. 이것으로 여섯째 기준을 확인했다. 같은 테스트에서 경계 시각 SQL을 `EXPLAIN ANALYZE`로 실행했다. 두 경우 모두 시작 시각과 끝 시각을 읽는 하위 쿼리는 GPS 좌표 기본 키 Index Scan으로 실행됐다.

`a0fbc06c`에서 `cd backend && ./gradlew test`는 1,469개가 통과했다(실패 0, 건너뜀 0). 이것으로 일곱째 기준을 확인했다.

### 실서버 배포 뒤 확인

PR #43을 병합하자 실서버에 자동 배포됐다. 실서버 컨테이너의 시작 시각은 Backend가 2026-11-15 02:49:47(KST), Frontend가 02:50:02(KST)였다. 2026-11-15에 2026-11-14 실서버 비교와 같은 사건과 같은 수색 차수로 세 가지를 확인했다.

실서버 DB에서 읽기 전용 트랜잭션을 열고 경계 시각 SQL을 `EXPLAIN ANALYZE`로 3번 실행했다. 시작 시각과 끝 시각을 읽는 두 하위 쿼리는 모두 GPS 좌표 테이블의 기본 키 Index Scan으로 실행됐다. 실행 시간은 41.7ms, 37.2ms, 33.2ms였다. 계획 비용은 59,339로 `jit_above_cost`(100,000)보다 낮아 JIT 컴파일은 없었다. 다만 psql에서는 경로 ID, 시작 순번, 끝 순번 배열을 문자열 리터럴로 SQL에 넣고 배열로 변환해 실행했다. 그래서 이번에 본 실행 계획은 Backend에서 JDBC prepared statement로 배열을 바인딩해 실행할 때의 계획과 다를 수 있다. 이것으로 여덟째 기준을 확인했다.

Ops에서 [경로 이력 요청 k6 스크립트](../../infra/k6/path-history-read.js)로 최초 이력 요청을 5번 보냈다. 사용자 PC 회선을 빼고 재려고 Ops에서 보냈다. 각 요청의 응답을 받은 뒤 5초씩 쉬고 다음 요청을 보냈다. 그동안 실서버 DB의 `pg_stat_activity`를 0.2초 간격으로 읽기 전용 조회했다. `pg_stat_activity`는 서버 프로세스마다 한 행씩 들어 있는 PostgreSQL 시스템 뷰다. parallel worker 행의 `leader_pid`에는 leader 프로세스의 ID가 담긴다. 5번 요청 모두에서, 좌표 배열 SQL을 실행하는 Backend 연결의 서버 프로세스 ID가 `leader_pid`인 parallel worker 행이 2개씩 보였다. 이것으로 아홉째 기준을 확인했다.

서버 처리 시간은 Frontend nginx 로그의 `uht`로 비교했다. Frontend nginx는 웹 파일을 내려 주고 `/api` 요청을 Backend로 넘기도록 설정한 nginx다. `uht`(nginx `$upstream_header_time`)는 Frontend nginx에서 Backend 응답 헤더를 받을 때까지 걸린 시간이다. `rt`(nginx `$request_time`)는 Frontend nginx에서 클라이언트 요청의 첫 바이트를 읽은 뒤 응답을 다 보낼 때까지 걸린 시간이다. 2026-11-13 값은 같은 k6 스크립트와 같은 명령으로 잰 값이다. 두 날 모두 응답 본문은 8,342,304자였다.

| 회차 | 2026-11-13 `uht` | 2026-11-15 `uht` | 2026-11-13 `rt` | 2026-11-15 `rt` |
|---:|---:|---:|---:|---:|
| 1 | 2.089초 | 1.742초 | 2.356초 | 2.005초 |
| 2 | 1.609초 | 1.098초 | 1.862초 | 1.345초 |
| 3 | 1.601초 | 1.124초 | 1.765초 | 1.328초 |
| 4 | 1.409초 | 1.103초 | 1.636초 | 1.330초 |
| 5 | 1.439초 | 1.108초 | 1.601초 | 1.277초 |

두 날 모두 5번 가운데 첫 번째 요청이 가장 느렸다. 첫 번째 요청이 느린 이유는 확인하지 않았다. 첫 번째 요청의 `uht`는 2.089초에서 1.742초로 줄었다. 나머지 네 번의 `uht`는 1.41~1.61초에서 1.10~1.12초로 줄었다. 배포 뒤 첫 번째 요청을 뺀 네 번은 모두 배포 전 다섯 번 가운데 가장 짧은 값(1.409초)보다 짧았다. 이것으로 열째 기준을 확인했다. 다만 두 날 모두 한 번씩 5번만 쟀다. 날마다 생기는 흔들림은 따로 재지 않았다. 또 실서버에서는 두 변경을 함께 배포했으므로, 줄어든 시간 가운데 fetch size 변경과 측정 시각 변경의 몫을 나눌 수 없다.

### 확인하지 못한 범위와 후속 작업

- 배포한 뒤 Chrome 탭으로 상황판에 들어와 수색 경로 전체가 지도에 그려지는 시간은 다시 재지 않았다. 그래서 지휘관이 기다리는 시간이 얼마나 줄었는지는 확인하지 않았다.
- Backend의 JDBC prepared statement로 실행한 경계 시각 SQL의 계획과 시간은 보지 않았다.
- 응답을 받은 뒤 브라우저에서 경로를 지도에 반영하는 시간(1.8~2.3초)은 이번 범위가 아니다. 따로 다룬다.
- 위 표에서 택하지 않은 방법들과, 로컬 DB와 실서버 DB에서 서로 다른 실행 계획이 선택되는 이유는 다루지 않았다.
