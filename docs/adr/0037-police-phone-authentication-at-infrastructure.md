# 업무폰 인증을 인프라 계층에서 담당

업무폰 인증은 기관 MDM, 망 접근 제어, IdP 같은 인프라 계층이 담당한다. 업무폰 인증은 요청이 기관에서 지급한 업무폰에서 왔는지 확인하는 일이다. 수리맵 서버에서는 업무폰 ID를 요청 허용의 근거로 쓰지 않는다. 업무폰 ID는 설치 상태, FCM 토큰처럼 업무폰별 기록을 찾는 키와 기록의 맥락으로만 쓴다.

앱 사용자의 업무폰 ID는 MDM 관리 구성에서 읽혀 문자열로 전송된다. 유효한 토큰과 등록된 업무폰 ID를 알면 다른 단말에서도 같은 값을 보낼 수 있다. 그래서 서버에서 등록 여부를 확인해도 요청이 그 업무폰에서 왔다는 것은 증명되지 않는다. [단말 신뢰 계층 조사](../research/device-trust-layer-research.md)에서 읽은 1차 자료에서도 단말은 MDM 등록, 하드웨어 키 증명, 클라이언트 인증서, IdP 조건부 접근으로 증명된다. 모두 인프라 계층의 수단이다. [업무폰 등록 확인 요구 조사](../research/device-check-requirement-research.md)에서 읽은 국가 사이버보안 기본지침, N2SF 해설서, CJIS Security Policy에도 업무 애플리케이션 서버가 단말 ID를 등록 목록과 대조하라는 요구는 없었다.

## 검토한 대안

- **수리맵 서버가 직접 증명한다.** MDM으로 업무폰마다 클라이언트 인증서를 배포하고 RFC 8705 인증서 결속 토큰을 쓰는 방법이다. 등록할 때 Android Key Attestation을 검증하는 방법도 있다. 인증서 발급과 폐기를 운영해야 한다. 실기기와 MDM 환경도 필요하다. 그래서 지금은 채택하지 않았다. 실제 기관 환경에 배포할 때 필요하면 다시 검토한다.
- **지금처럼 등록 확인을 권한 판단에 쓴다.** 요청이 그 업무폰에서 왔다는 것을 증명하지 못하면서 보안 경계처럼 보이므로 채택하지 않았다.
- **등록 목록과 대조하는 입력 검사로 남긴다.** 목록에 없는 ID를 거절하는 방법이다. 실서비스에서 그 목록을 채울 경로가 없으므로 채택하지 않았다.

## 결과

- 업무폰 등록 여부는 확인하지 않는다. 업무폰 ID는 헤더가 있는지와 UUID 형식만 확인한다.
- 업무폰 기록 행은 그 업무폰이 처음 요청을 보낼 때 만든다. 등록 API와 관리 화면은 두지 않는다.
- MDM과 망 접근 제어가 없는 환경에서는 유효한 계정 토큰만 있으면 아무 업무폰 ID나 보낼 수 있다. 이 한계를 받아들인다. 사건 권한은 업무폰이 아니라 계정으로 확인한다. 그래서 업무폰 ID를 바꿔 보내도 사건 권한 확인 결과는 달라지지 않는다.
- MDM과 망 접근 제어는 나중에 서버 앞단에 붙인다. [Knox와 MDM 도입 검토안](../proposals/knox-mdm.md)은 보류한다. 서비스를 완성한 뒤에 검토한다.

현재 확인: `@RequirePolicePhoneRegistered`가 붙은 APP 요청은 아직 `X-PolicePhone-Id` 헤더의 업무폰 등록 여부에 따라 거절된다. 위 결과는 별도 작업에서 구현한다. 여러 API에 공통으로 붙은 사건 권한 확인에서는 요청한 사건이 아니라 계정에 배정이 하나라도 있는지만 확인된다. 이 결함도 별도 작업에서 고친다.

기록: 2026-11-17 사용자 결정. 2026-05-18 API 명세(`abe7ec1e`)에 `police_phone`의 원천을 MDM으로 본 문장 "`police_phone`은 MDM/단말 관리 원천의 로컬 투영"이 적혀 있었다. 같은 명세에는 업무폰 ID를 권한 판정 기준에 넣은 문장도 있었다.
