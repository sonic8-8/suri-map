# Suri-Map 화면 설계 및 디자인 시스템 체크리스트

상태: 초안 v2 (2026-05-05 보완). 이 문서는 Suri-Map의 화면 설계와 디자인 시스템을 인터랙티브 프로토타입으로 넘기기 전에 확인해야 하는 순서를 고정한다.

## 목적

- 화면 구성 없이 프로토타입을 먼저 생성해 일반 지도 앱처럼 흐르는 문제를 방지한다.
- KRDS와 네이버 지도 디자인 패턴의 역할을 분리한다.
- Suri-Map 고유 도메인인 사건, OP, 수색 구역, 경로, 마커, 폴리폰 상태, 오프라인 동기화를 화면 설계의 중심에 둔다.
- 운영 dashboard·rugged field UI라는 두 정체성을 강제한다.

## 0. 전제 (Pre-conditions)

화면 설계 작업 시작 전에 모두 확인한다. 이 단계가 빠지면 시민포털 톤·일반 지도 앱 톤으로 흐른다.

### 0.0 도메인 사실 (자주 틀림)

[README.md "핵심 도메인 사실"](./README.md#핵심-도메인-사실-자주-틀리는-부분) 표를 먼저 읽는다. 화면 설계가 PRD/spec 정합성 위반으로 흐르는 가장 흔한 원인이다.

- [ ] 1팀(예: 6명) = 폴리폰 1대 (FR-33). 폴리폰 수 ≠ 인원 수.
- [ ] OP는 **재수색·범위 변경 단위** (FR-12). 인수인계는 **DutyShift** (FR-32, FR-37).
- [ ] 현장 마커 생성은 모든 폴리폰 계정에 허용. 수정·삭제만 권한 차등 (PRD §8.4).
- [ ] 사건 가져오기 = 실종팀 간부 + 지구대/파출소 팀장·당직자만 (PRD §8.4).
- [ ] 폴리폰에서 웹 상황판 접근 불가 (PRD §8.8).
- [ ] 동시 활성 OP는 사건당 1개. 사건 종료는 terminal (ADR-0022).
- [ ] 상세 권한 분기는 [permission-matrix.md](./permission-matrix.md) 참조.

### 0.1 현장 사용 맥락

- [ ] [field-context.md](./field-context.md)를 읽는다.
- [ ] 폴리폰 사용 환경(야외/장갑/무전기/단손/오프라인 30분+)이 모든 화면 결정의 전제임을 인지한다.
- [ ] 웹 상황판이 다중 사건·장시간·여러 사람 동시 시청 환경임을 인지한다.
- [ ] field-context §2의 정보 밀도 목표 슬롯이 비어 있다면 채울 책임자·일정을 정한다.

### 0.2 정체성 두 축

- [ ] 웹 상황판은 **운영 dashboard** 정체성을 가진다 (시민포털 아님).
- [ ] 폴리폰은 **rugged field UI** 정체성을 가진다 (일반 컨슈머 앱 아님).
- [ ] 두 정체성을 KRDS-Ops dense variant 토큰(`dense-tokens.md`)으로 강제한다.

### 0.3 금지 행동 카탈로그

- [ ] [anti-patterns.md](./anti-patterns.md)를 읽는다.
- [ ] PRD 금지 행동(자동 누락 확정·다음 구역 추천·위험도 판단)의 시각적 누설 패턴을 인지한다.
- [ ] KRDS/네이버 지도 패턴 오용 카탈로그를 인지한다.

### 0.4 라벨 표기 규칙

- [ ] [screen-labels.md](./screen-labels.md)를 읽는다.
- [ ] 도메인 객체별 화면 표기·짧은 표기·금지 표기를 인지한다.
- [ ] 액션·상태 라벨 표기를 인지한다.

### 0.5 사용자 리서치 소스

- [ ] [user-research-source.md](./user-research-source.md)를 읽는다.
- [ ] 자료 빈약성을 인지하고, 작업 중 만들어내는 결정의 출처/추론/임시값을 구분한다.

## 2. 사용자 흐름 정의

- [ ] 지구대/파출소 초동 대응 흐름을 작성한다.
- [ ] 실종팀 인계 흐름을 작성한다.
- [ ] 지원 부대 합류 흐름을 작성한다.
- [ ] 수색 시작부터 GPS 경로 동기화까지의 현장 앱 흐름을 작성한다.
- [ ] 마커 생성부터 상황판 반영까지의 흐름을 작성한다.
- [ ] 구역 완료와 새 OP 생성 흐름을 작성한다.
- [ ] 인수인계와 수색 이력 요약 확인 흐름을 작성한다.
- [ ] 사건 종료와 개인정보/로컬 데이터 파기 흐름을 작성한다.

## 3. 화면별 목적과 우선순위 정의

- [ ] 각 화면의 주 사용자 역할을 기록한다.
- [ ] 각 화면에서 반드시 수행해야 하는 핵심 행동을 1~3개로 제한한다.
- [ ] 각 화면에서 사용자가 즉시 파악해야 하는 상태를 정의한다.
- [ ] 각 화면에서 금지해야 하는 행동을 기록한다.
- [ ] 권한 없음, 오프라인, 로딩, 실패, 종료 사건 상태를 화면별로 정의한다 (상세 분기는 §3.5 매트릭스).

### 예시: Web 상황판 메인

- [ ] 현재 OP의 팀/순찰차 위치와 경로를 확인한다.
- [ ] 완료/미완료 수색 구역을 확인한다.
- [ ] 마커와 지원 요청을 확인한다.
- [ ] 폴리폰 stale/lost 상태를 판단한다.
- [ ] 오프라인 패키지 미완료 폴리폰을 식별한다.

### 기능 컷 우선순위 사다리

low-fi 검토에서 화면이 복잡하다는 결론이 나면 컷 우선순위를 정한다.

- [ ] 각 화면의 핵심 행동(P0), 보조 행동(P1), 후순위(P2)를 분류한다.
- [ ] 컷 결정 시 P2부터 제거하고 P0은 유지한다.
- [ ] 컷 사유와 결정자를 기록한다.

## 4. Low-fi 와이어프레임 작성

- [ ] 색상과 시각 장식을 배제하고 화면 구조만 잡는다.
- [ ] 지도 영역, 좌측 패널, 우측 상세 패널, 하단 패널, 플로팅 컨트롤 위치를 정한다.
- [ ] Web 상황판의 지도 레이어 구조를 잡는다.
- [ ] Android 수색 중 화면의 지도와 바텀시트 구조를 잡는다.
- [ ] 주요 CTA 위치를 정한다 (폴리폰은 thumb zone 안에).
- [ ] 화면 전환과 패널 열림/닫힘 상태를 표시한다.
- [ ] 상태별 empty/loading/error/permission 화면을 §3.5 매트릭스 기준으로 포함한다.

## 5. 디자인 시스템 역할 분리

### KRDS 담당 영역

- [ ] 공공 업무 시스템 톤과 정보 구조
- [ ] 접근성 기준
- [ ] 버튼, 폼, 탭, 모달, 알림
- [ ] 확인/취소/파기 같은 행정성 높은 절차 UI
- [ ] 오류, 권한 없음, 종료 사건, 개인정보 제거 안내
- [ ] 텍스트 계층과 한국어 가독성 기준

### 네이버 지도 참고 영역

- [ ] 지도 중심 레이아웃
- [ ] 지도 플로팅 컨트롤 위치와 크기
- [ ] 레이어 토글 조작감
- [ ] 모바일 바텀시트 조작감
- [ ] 지도 위 마커, 경로, 정보 카드의 직접 조작 패턴

### 적용 원칙

- [ ] KRDS를 base 디자인 시스템으로 둔다.
- [ ] **단, 시민포털 기본 토큰이 아니라 KRDS-Ops dense variant를 사용한다** (§7.5 참조).
- [ ] 한국 경찰 도메인이므로 KRDS 출처(`Korean Government UIUX Design System/`)는 참고 가치가 있다. 단, 그대로 쓰면 정보 밀도·rugged 정체성이 부족하므로 fork한다.
- [ ] 네이버 지도는 지도 조작 패턴만 참고한다.
- [ ] 검색, POI, 리뷰, 장소 저장, 길찾기 중심 흐름은 만들지 않는다 (anti-patterns §2).
- [ ] Suri-Map의 화면 중심은 사건, OP, 수색 구역, 경로, 마커, 폴리폰 상태다.

## 6. Suri-Map 도메인 시각 규칙 정의

- [ ] 수색 구역 상태별 색상과 패턴을 정의한다 (색만으로 구분 금지 — anti-patterns §3.1).
- [ ] 전체 수색 구역과 팀별 담당 구역의 시각 차이를 정의한다 (`area_level = OVERALL | UNIT | TEAM`).
- [ ] 팀 폴리폰 경로와 순찰차 폴리폰 경로 스타일을 정의한다.
- [ ] 차량 구간, 도보 구간, 구분 안 됨 구간 스타일을 정의한다 (FR-33).
- [ ] 현재 운용 중인 PolicePhone 경로 강조 규칙을 정의한다 (FR-25).
- [ ] **OP 비교 시 현재 OP와 과거 OP**의 중첩 표시 규칙을 정의한다 (FR-11). OP는 재수색·범위 변경 단위 — anti-patterns §1.6.1 참조.
- [ ] **DutyShift 인계 표현**을 OP와 시각적으로 분리한다 (FR-37). DutyShift는 같은 폴리폰의 근무 교대 timeline.
- [ ] 마커 유형별 아이콘과 색상을 정의한다 (5종: `CLUE`/`PERSON_FOUND`/`FIELD_CONDITION`/`SUPPORT_REQUEST`/`NOTE(운영 메모)`).
- [ ] 지원 요청 유형(`DRONE`/`POLICE_DOG`/`OTHER`)별 시각 규칙을 정의한다.
- [ ] 지원 요청과 실종자 발견 알림의 강조 규칙을 정의한다 (FR-17, FR-10).
- [ ] 폴리폰 online/stale/lost 상태 표시 규칙을 정의한다 (FR-24 — 색·outline·라벨 3중 인코딩).
- [ ] 오프라인 패키지 완료/미완료/stale/실패 상태 표시 규칙을 정의한다 (FR-31).
- [ ] 미전송 큐 pending/sending/acked/failed 상태 표시 규칙을 정의한다 (FR-28).
- [ ] 같은 좌표에 마커 N개 누적 시 cluster/fan-out 처리 규칙을 정의한다 (anti-patterns §3.2).
- [ ] 경로(LineString)와 구역(Polygon) 동시 표출 시 시각 분리 규칙을 정의한다 (FR-05, anti-patterns §3.3).
- [ ] 단순 보기 모드(FR-26)에서 화면별로 무엇이 숨겨지는지 명세한다.
- [ ] 사건 종료 사건(terminal)의 readonly 시각 표현을 정의한다 (ADR-0022, anti-patterns §1.6.7).

## 7. 디자인 토큰 확정

- [ ] 색상 토큰을 KRDS 기반으로 정의한다.
- [ ] 네이버 그린은 사용하지 않거나, 사용한다면 보조 강조색으로 한정한다.
- [ ] 긴급 색상은 지원 요청, 실종자 발견, 사건 종료 위험 행동에만 사용한다.
- [ ] 경고 색상은 stale, lost, 패키지 미완료, 동기화 실패에 사용한다.
- [ ] 한국어 본문 폰트를 확정한다 (Pretendard GOV 기본).
- [ ] 숫자, ID, 좌표, 시간 표기용 monospace 폰트 규칙을 정한다.
- [ ] radius, spacing, elevation, border 사용 규칙을 확정한다.
- [ ] 지도 위 플로팅 UI의 그림자와 배경 투명도 규칙을 확정한다.

## 7.5 KRDS-Ops Dense Variant 토큰 결정

- [ ] [dense-tokens.md](./dense-tokens.md)의 정보 밀도 목표(§1)를 결정한다.
- [ ] 목표를 만족하도록 토큰 값을 역산한다 (§2~§8).
- [ ] 색맹 검증을 통과한다 (§2.3).
- [ ] 폴리폰 토큰의 야외 가시성·터치 타깃을 검증한다.
- [ ] KRDS 원본 토큰과 fork 토큰을 같은 화면에 섞지 않는다.
- [ ] 적용 범위 매트릭스(§9)를 채운다.

## 8. 컴포넌트 명세 작성

각 컴포넌트마다 variant·size·state·responsive 분기를 매트릭스로 명세한다.

- [ ] 사건 카드
- [ ] 사건 상태 배지 (`OPEN`/종료/파기 중)
- [ ] OP 선택기 (사유 enum: `RE_SEARCH`/`AREA_CHANGED`/`OTHER`/`INITIAL` 표출)
- [ ] OP 비교 토글 (현재 OP + 과거 OP overlay)
- [ ] DutyShift timeline (같은 폴리폰의 근무 교대 표시)
- [ ] 지도 레이어 패널
- [ ] 지도 컨트롤 버튼
- [ ] 폴리폰 상태 배지 (online/stale/lost — FR-24)
- [ ] 경로 범례 (팀/순찰차 × 차량/도보)
- [ ] 마커 범례 (5종 유형)
- [ ] 구역 상태 칩 (활성/완료/취소)
- [ ] 미전송 큐 상태바
- [ ] 오프라인 패키지 진행률
- [ ] 지원 요청 / 실종자 발견 토스트 (강조 알림)
- [ ] 확인 모달
- [ ] 사건 종료 확인 모달 (terminal — ADR-0022)
- [ ] Android 마커 생성 바텀시트 (FR-30 엄지 중심)
- [ ] Android 로컬 경고 배너 (FR-29)
- [ ] 인수인계 메모 작성기 (DutyShift/OP/경로/구역 단위 — FR-37)
- [ ] 수색 이력 자동 요약 카드 (FAILED 상태 포함 — FR-39)

각 컴포넌트:

- [ ] variant (primary/secondary/긴급) 정의
- [ ] size (mobile/desktop, dense/comfortable) 정의
- [ ] state (default/hover/pressed/disabled/loading/error/success) 정의
- [ ] responsive 분기점 정의

## 9. High-fi 화면 설계

- [ ] Low-fi 구조에 KRDS-Ops 토큰을 적용한다.
- [ ] Web 주요 화면을 high-fi로 작성한다.
- [ ] Android 주요 화면을 high-fi로 작성한다.
- [ ] 지도 레이어가 실제 업무 상태를 구분할 수 있는지 검토한다.
- [ ] 긴급/경고/일반 상태가 서로 혼동되지 않는지 검토한다.
- [ ] KRDS 컴포넌트와 지도 패턴이 충돌하지 않는지 검토한다.
- [ ] §3.5 매트릭스의 모든 상태 분기 화면을 작성한다.

## 10. 인터랙티브 프로토타입 생성

- [ ] 화면 목록과 사용자 흐름을 입력으로 제공한다.
- [ ] KRDS-Ops dense variant와 네이버 지도 디자인의 역할 분리를 입력으로 제공한다.
- [ ] Suri-Map 도메인 시각 규칙을 입력으로 제공한다.
- [ ] 검색/POI/길찾기/장소 저장/리뷰/마이페이지 생성 금지를 명시한다.
- [ ] anti-patterns.md를 negative example로 함께 제공한다.
- [ ] Web 상황판과 Android 앱을 별도 프로토타입 흐름으로 만든다.
- [ ] 프로토타입에서 SC-01~SC-12의 주요 흐름이 관찰 가능한지 검토한다.

## 10.5 프로토타입 Agent Loop

- [ ] [prototype-agent-loop.md](./prototype-agent-loop.md)를 따른다.
- [ ] 컨텍스트 골격(§2.1)을 매 요청마다 주입한다.
- [ ] 화면 타깃 블록(§2.2)을 화면별로 작성한다.

- [ ] 3차 FAIL 시 사람이 직접 그리거나 화면 정의를 더 작게 분할한다.

## 11. 리뷰 기준

### 11.1 정성 리뷰

- [ ] 화면 중심이 일반 지도 검색이 아니라 사건 운영인지 확인한다.
- [ ] 지도 위에 경로, 구역, 마커, 폴리폰 상태가 동시에 올라와도 읽을 수 있는지 확인한다.
- [ ] 지휘 업무는 Web 중심, 현장 기록은 Android 중심으로 분리됐는지 확인한다.
- [ ] 앱 전용/웹 전용 조작 경계가 화면에서도 드러나는지 확인한다 (PRD §8.4 권한 매트릭스).
- [ ] OP와 DutyShift가 의미·시각·라벨 모두 분리되어 있는지 확인한다 (anti-patterns §1.6.1, G6-7).
- [ ] 오프라인, 동기화 실패, 권한 없음, 사건 종료 상태가 빠지지 않았는지 확인한다.
- [ ] 자동 누락 판단, 다음 구역 추천, 위험도 판단처럼 PRD에서 금지한 표현이 없는지 확인한다.
- [ ] KRDS의 공공성, 접근성, 상태 안내가 유지되는지 확인한다.
- [ ] 네이버 지도 패턴이 제품 정체성을 덮어쓰지 않았는지 확인한다.

### 11.2 정량 게이트 (measurement-gates)

- [ ] [measurement-gates.md](./measurement-gates.md)의 G1~G6 게이트를 단계별로 적용한다.
- [ ] 게이트 미달 시 reject + 재작업.
- [ ] 게이트 결과를 기록한다.

### 11.3 anti-pattern 검수

- [ ] [anti-patterns.md](./anti-patterns.md) §1~§6의 모든 anti-pattern이 화면에 없는지 확인한다.
- [ ] 새로 발견된 anti-pattern은 §7 실수 사례 로그에 기록한다.

## 프로토타입 요청 전 금지 프롬프트

아래처럼 요청하지 않는다.

```text
KRDS와 네이버 지도 디자인 시스템을 섞어서 인터랙티브 프로토타입을 만들어줘.
```

이 요청은 화면 IA와 업무 흐름이 없기 때문에 일반 지도 앱, 검색 앱, 장소 상세 앱으로 흐르기 쉽다. 또한 KRDS 시민포털 기본 토큰을 그대로 적용하면 운영 dashboard 정보 밀도가 부족하다.

## 프로토타입 요청 전 권장 프롬프트 골격

prototype-agent-loop.md §2.1의 컨텍스트 골격을 사용한다. 요약하면:

```text
Suri-Map은 경찰 실종 수색 운영 보조 시스템이다.
112 공식 기록 시스템이 아니다. 네이버 지도 앱이 아니다.
웹은 지휘 상황판, 폴리폰은 현장 입력 앱이다.

디자인 방향:
- KRDS를 base로 사용하되, 시민포털 기본 토큰이 아니라
  KRDS-Ops dense variant를 사용한다 (docs/screen-design/dense-tokens.md).
- 네이버 지도는 지도 조작 패턴만 참고한다.
- 검색/POI/길찾기/장소 저장/리뷰/마이페이지는 만들지 않는다.

현장 사용 맥락 (docs/screen-design/field-context.md):
- 웹: 1920×1080, 다중 사건 동시 운영.
- 폴리폰: 야외, 장갑, 무전기 동시 사용, 단손 조작, 30분+ 오프라인.

금지 사항 (docs/screen-design/anti-patterns.md):
- 자동 누락 확정·다음 구역 추천·위험도 판단 시각화 금지.
- 빈 영역 hatch/빨간 패턴, "추천 구역" 카드, 자동 "위험" 색 금지.

라벨 표기 (docs/screen-design/screen-labels.md) 규칙을 따른다.

먼저 아래 화면의 low-fi 구조를 만든다:
1. 웹 상황판 메인
2. 수색 구역 편집
3. OP 비교/인수인계
4. Android 수색 중 지도
5. Android 마커 생성 바텀시트

각 화면은 사건, OP, 팀/순찰차 경로, 수색 구역, 마커,
폴리폰 상태, 오프라인 상태를 중심으로 구성한다.

상태 분기는 docs/screen-design/screen-state-matrix.md의 해당 화면 행을 참조한다.
```
