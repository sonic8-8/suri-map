# Anti-Pattern 카탈로그

상태: 초안. 이 문서는 Suri-Map 화면 설계에서 **만들면 안 되는 시각/상호작용 패턴**을 모은다. PRD에서 금지한 행동(자동 누락 확정, 다음 구역 추천, 위험도 판단)이 시각적으로 어떻게 새어나오는지 사례화한다.

## 목적

- AI가 프로토타입을 만들 때 negative example로 사용한다.
- 디자인 리뷰의 reject 기준이 된다.
- 실제 작업 중 발견한 실수를 누적해 다음 작업에서 반복되지 않게 한다.

## 사용 방법

- 화면 설계·프로토타입 생성 전에 §1을 읽는다.
- 리뷰에서 §1의 패턴이 발견되면 reject한다.
- 실제 발견된 새 anti-pattern은 §3에 추가한다.

## 1. PRD 금지 행동의 시각적 누설

PRD §7 (FR-23 등) / ADR-0027에서 **자동 누락 확정·다음 구역 추천·위험도 판단**을 금지한다. 화면이 무심코 이걸 시각화하면 안 된다.

### 1.1 빈 영역에 hatch / 빨간 패턴

```
[잘못]
┌─────────────────────────┐
│ 수색 완료 영역 (초록)   │
│  ╱╱╱╱╱╱ 미확인 ╱╱╱╱╱╱  │  ← 빨간 hatch로 "여기 안 했음"을 시스템이 단정
│ 수색 완료 영역 (초록)   │
└─────────────────────────┘

[허용]
┌─────────────────────────┐
│ 수색 완료 영역 (초록)   │
│  (회색 base, 운영 메모 마커) │  ← 단순 base. 사람이 운영 메모 마커로 표시
│ 수색 완료 영역 (초록)   │
└─────────────────────────┘
```

- **금지 이유**: 시스템이 "여기는 누락"이라고 자동 확정하는 표현. PRD가 명시 금지.
- **대체**: 완료/미완료의 시각 차이는 두되, 미완료는 중립 색(회색·미배정 패턴)으로. 운영 메모(NOTE) 마커는 사람이 작성한 경우만.

### 1.2 "다음 추천 구역" 카드 / 화살표

- **금지 이유**: 다음 투입 구역 자동 지시 금지 (FR-23).
- **대체**: 인수인계 메모, OP별 경로/완료 구역/운영 메모(NOTE) 마커를 같이 보여주고 사람이 판단.

### 1.3 마커에 시간/위치 기반 자동 "위험" 색

- **금지 이유**: 위험도 판단 금지.
- **대체**: 마커 색은 유형(CLUE/PERSON_FOUND/운영 메모(NOTE) 등)에만 종속. 시간 경과는 별도 메타(라벨·outline)로 표현하되 "위험" 의미를 부여하지 않음.

### 1.3.1 구역 진척도 % / 자동 계산 진행률 표시

- **금지 사례**: 구역에 "진행률 60%", "활성 · 60%", "수색 완료도 25%" 같은 시스템 자동 계산 % 표시
- **금지 이유**: Suri-Map은 자동 누락 확정·다음 구역 추천·위험도 판단을 하지 않는다 (FR-23, ADR-0027). 진척도 %는 시스템이 수색 완료도를 계산하는 것처럼 보임.
- **대체**: 관찰 가능한 도메인 사실만.
  - "활성 · 경로 기록 중"
  - "완료 · 14:02 (기동대장)"
  - "기록된 경로 N개 · 최근 갱신 2분 전"
  - 사람의 판단(완료 처리)은 명시. 시스템 자동 계산 표현 금지.

### 1.4 AI 요약에 추측·지시 표현

- **금지 사례**: "이 구역은 재수색이 필요해 보입니다", "다음은 ○○ 일대를 수색하시기 바랍니다", "위험도 높음"
- **금지 이유**: ADR-0034 — 추천·누락 확정·위험도 판단·다음 구역 지시는 저장 전 guard에서 차단.
- **대체**: "OP 1차 동안 ○○ 일대를 도보로 수색했습니다" 같은 사실 진술만.

### 1.5 폴리폰 stale을 "위험"으로 표시

- **금지 사례**: stale 폴리폰을 빨간색 + "위험" 라벨로 표시
- **금지 이유**: stale은 통신 상태이지 위험도 판단이 아님. 사용자가 위험으로 오해.
- **대체**: stale은 경고 색(주황·옅은 회색)과 마지막 동기화 경과 라벨("12분 전")로 표현.

## 1.6 도메인 모델 오해 (PRD 정합성 위반)

### 1.6.1 OP를 인수인계/근무 교대 단위로 표현

- **금지 사례**: OP를 "OP 1차 (오전 근무)", "OP 2차 (오후 근무)"처럼 시간/시프트로 표시
- **금지 이유**: OP는 **재수색·범위 변경 단위**이지 인수인계 단위가 아님 (PRD FR-12, FR-32, ADR-0029). OP 사유 enum은 `RE_SEARCH`, `AREA_CHANGED`, `OTHER`. 인수인계·근무 교대는 **`DutyShift`** 가 담당.
- **대체**: OP는 사유와 함께 표시 (`OP 2차 — 재수색`). 근무 교대는 DutyShift timeline으로 별도 표출.

### 1.6.2 폴리폰 수를 인원 수와 동일하게 가정

- **금지 사례**: "폴리폰 96대 (16팀 × 6명)" 같은 표현
- **금지 이유**: 1팀(예: 6명) = 폴리폰 1대 (PRD FR-33). 폴리폰 수와 인원 수는 다름.
- **대체**: 폴리폰 수 단위 (팀 1개 → 폴리폰 1대). 인원 수가 필요하면 별도 메타로.

### 1.6.2.1 순찰차를 별도 운용 단위로 표기

- **금지 사례**: "지구대 폴리폰 + 순찰차 폴리폰"을 별개 카테고리로 카운트하거나 시각 분리
- **금지 이유**: 순찰차는 지구대/파출소 소속이다. 별도 운용 단위가 아니라 지구대/파출소 안의 폴리폰 한 종류.
- **대체**: 지구대/파출소 폴리폰 안에 팀 폴리폰·순찰차 폴리폰 둘 다 포함. 시각 구분이 필요하면 같은 소속 안의 sub-type으로 처리.

### 1.6.3 마커 생성 권한을 일부 계정으로 제한

- **금지 사례**: "마커 생성은 간부만"으로 표현하거나, 대원 화면에서 마커 생성 CTA 숨김
- **금지 이유**: 현장 마커 생성은 **모든 계정**에 허용 (PRD §8.4 권한 매트릭스). 권한 차등은 마커 **수정·삭제**에서만 발생 (간부 = 모든 마커, 대원 = 자기 계정 생성분만).
- **대체**: 모든 폴리폰 계정에 마커 생성 CTA. 마커 상세에서 수정·삭제 버튼만 권한 분기.

### 1.6.4 폴리폰에 웹 상황판 화면 표시

- **금지 사례**: 폴리폰 앱에 "상황판 보기" 메뉴
- **금지 이유**: 폴리폰에서 웹 상황판 접근은 **지원 대상 아님** (PRD §8.8). 데스크톱 전용.
- **대체**: 폴리폰은 현장 입력에 집중. 상황판 정보가 필요하면 폴리폰 전용 view로 별도 설계.

### 1.6.5 동시 활성 OP 여러 개

- **금지 사례**: 여러 OP가 동시 active 상태로 표시
- **금지 이유**: 사건당 활성 OP는 1개. OP 전환 시 이전 OP는 보존되지만 비활성 (FR-12).
- **대체**: 활성 OP는 1개로 강조. 비교 시 과거 OP는 overlay/dimmed 처리.

### 1.6.5.1 OP 비교를 직전 N차로 제한

- **금지 사례**: OP 비교 화면에서 "직전 1차만 비교" 같은 시스템 강제 제한
- **금지 이유**: 재수색은 실종자 발견 시까지 계속 진행 (FR-12). OP 차수가 50차+ 갈 수 있고, 사용자는 임의 OP를 선택해 overlay할 수 있어야 함 (FR-11 "1개 이상 선택").
- **대체**: OP 리스트는 시간순 전체 표시 + 사용자가 임의 N개 체크. 6차+ 선택 시 가독성 경고만 표시하고 막지 않음.

### 1.6.5.2 OP 차수 상한 표시

- **금지 사례**: "OP 최대 10차" 같은 상한 표시
- **금지 이유**: 재수색 진행 중 사건의 자연스러운 운영을 시스템이 임의로 제한.
- **대체**: 누적 OP는 무제한. 화면은 스크롤로 처리.

### 1.6.6 사건 가져오기를 모든 지휘 계정에 허용

- **금지 사례**: 지원 부서 간부 화면에 "사건 가져오기" CTA
- **금지 이유**: 사건 가져오기 권한은 **실종팀 간부 + 지구대/파출소 팀장·당직자**만 (PRD §8.4). 지원 부서 간부는 가져오기 권한 없음.
- **대체**: 권한 매트릭스에 따라 CTA 분기.

### 1.6.7 사건 재오픈 UI 노출

- **금지 사례**: 종료된 사건에 "재오픈" 버튼
- **금지 이유**: 사건 종료는 **terminal**. 사용자 대상 재오픈 UI/API 없음 (PRD §8.5, ADR-0022). 종료 실수 복구는 관리자 운영 절차.
- **대체**: 종료 사건은 readonly 표시. 재오픈 없음.

### 1.6.8 수색 구역 계층(OVERALL/UNIT/TEAM) 무시

- **금지 사례**:
  - OVERALL 안에 TEAM 구역만 평면적으로 그리기 (UNIT 계층 빠짐)
  - 모든 구역을 같은 시각 톤으로 표현 (계층 구분 없음)
  - 단일 구역 리스트로만 표시 (계층 트리 없음)
- **금지 이유**: spec(`search_area.area_level = OVERALL | UNIT | TEAM`)이 정의한 3계층 분할·할당 흐름을 화면이 무시하면, 사용자가 누가 누구를 어떻게 분할했는지 못 봄.
- **운영 흐름**:
  1. 실종팀 지휘관이 사건 가져온 후 OVERALL 그림 (1개 active)
  2. OVERALL 안을 UNIT으로 분할 → 각 부대(기동대 등)에 배정
  3. UNIT 안을 TEAM으로 분할 → 각 팀 폴리폰에 배정
- **대체**:
  - 시각 계층: OVERALL = 가장 굵은 outline (전체) / UNIT = 중간 outline + 부대명 라벨 / TEAM = 안쪽 fill + 팀 배정 정보
  - 계층 트리 또는 nested 표시
  - 같은 색 hue 안에서 채도/투명도로 계층 표현 가능

### 1.6.10 마커 카테고리와 라벨 의미 충돌

- **금지 사례**: CLUE 마커에 "발견" 라벨, PERSON_FOUND 마커에 "단서" 라벨 등 마커 enum과 화면 라벨이 다른 경우
- **금지 이유**: spec(`marker_type` enum)과 사용자 표기가 어긋나면 인계·요약·검색에서 의미 흐림.
- **대체**: marker_type enum과 화면 라벨을 1:1 매핑 (screen-labels §2). 단서는 항상 "단서", 발견은 항상 "발견".

### 1.6.11 마커를 아이콘만 또는 라벨만으로 표현

- **금지 사례**:
  - 마커가 아이콘만 표시되고 라벨 없음 (의미 모호한 마커는 식별 어려움)
  - 마커가 텍스트 라벨만 있고 아이콘 없음 (지도에서 빠르게 식별 안 됨)
- **금지 이유**: anti-patterns §3.1 "색+모양+라벨 3중 인코딩" 정책. 단일 채널만으로는 색맹·zoom·인지 부하 다양한 환경에서 식별 실패.
- **대체**: 모든 마커는 **아이콘 + 짧은 라벨 칩** 조합. 라벨 표시 정책(항상/줌 기반/토글)은 dense-tokens 정보 밀도와 함께 결정.

### 1.6.9 OVERALL 출처 오해 (mock 112가 그려준다고 가정)

- **금지 사례**: "112에서 전체 수색 구역도 받아옴" 가정
- **금지 이유**: mock 112에서 받는 건 **사건 + 실종자 정보 + incident_assignment**다. 전체 수색 구역(`OVERALL`)은 실종팀 지휘관이 사건 가져온 후 직접 그린다 (PRD FR-12, SC-04, ADR-0026 "지도 기준 범위 지정·수정 = 웹 전용").
- **대체**: 화면이 "전체 수색 구역" 없는 상태(empty)를 명확히 표현해야 함. 사건 가져온 직후 = OVERALL 0개 = 지휘관에게 그리기 CTA.

### 1.6.7.1 종료 사건의 실종자/위치 재노출 (tombstone 위반)

- **금지 사례**: 종료된 사건 화면에 "마지막 폴리폰 위치", "실종자 사진/이름/상세", 오프라인 패키지 재다운로드 링크, 실시간 stream 재구독 표시
- **금지 이유**: 사건 종료 시 실종자 개인정보·사진은 즉시 제거 (FR-22, PRD §8.5, ADR-0022). 폴리폰 위치/경로 좌표는 동기화 ack 후 파기. harness-scenarios SC-12 기준 sanitized tombstone만 노출.
- **대체** (`incident_closed` 상태 화면에서 남길 수 있는 것):
  - 사건 ID
  - 종료 상태 + 종료 시각
  - 쓰기 불가 사유
  - 파기 진행 상태 (각 항목별 완료/진행중)
  - 비식별 사건 메타 (운영 이력 조회 범위)
- **제거해야 하는 것**:
  - 실종자 이름·사진·인상착의·상세
  - 폴리폰 최신 위치·경로 좌표
  - 마커·구역의 좌표 데이터 (이력 메타만 OK)
  - 실시간 SSE stream 재구독
  - 오프라인 패키지 재다운로드 링크

## 2. KRDS / 일반 지도 앱 패턴 오용

### 2.1 시민포털 카드 패턴을 운영 dashboard에 그대로 사용

- **잘못**: KRDS 정책 카드(padding 40px, 본문 17px, 카드당 1개 정보)를 상황판에 그대로 사용 → 1920×1080에 정보 4~5개만 들어감.
- **대체**: dense-tokens.md의 KRDS-Ops variant를 사용.

### 2.2 네이버 지도식 검색바를 화면 상단 중앙에 배치

- **잘못**: 상황판 상단에 큰 검색 입력. Suri-Map은 검색 중심이 아님.
- **대체**: 사건/OP 컨텍스트 정보를 상단에. 검색이 필요하면 보조 위치(좌측 패널 안).

### 2.3 POI 상세 카드 형식

- **잘못**: 마커 클릭 시 사진·리뷰·주변 정보를 보여주는 네이버식 POI 카드.
- **대체**: 마커 메타(작성 계정, client_ts, 사진, 메모) 위주. 리뷰·평점 없음.

### 2.4 "내 위치로" 버튼이 화면 중심 액션

- **잘못**: 폴리폰에서 "내 위치" 버튼이 가장 큰 CTA.
- **대체**: 가장 큰 CTA는 마커 생성 또는 수색 시작/종료. 내 위치는 보조.

### 2.5 길찾기·경로 추천 패턴

- **잘못**: "여기까지 어떻게 가나요?" 식의 경로 추천 UI.
- **금지 이유**: 제품 정체성 외. 수색 경로는 자동 기록되는 것이지 추천되는 게 아님.

### 2.6 장소 저장 / 즐겨찾기 패턴

- **잘못**: 마커를 "즐겨찾기"로 저장하는 별 아이콘.
- **대체**: 마커는 사건 컨텍스트에만 귀속. 개인 즐겨찾기 없음.

---

## 3. 정보 밀도 / 가독성 anti-pattern

### 3.1 색 하나로만 상태 구분

- **잘못**: 차량/도보/구역/마커 상태를 색으로만 구분. 색맹 사용자 식별 불가.
- **대체**: 색 + 패턴(점선·실선·해치) + 아이콘 형태 + 라벨 4중 인코딩.

### 3.2 같은 좌표에 마커 N개 누적되면 겹쳐서 마지막 1개만 보임

- **잘못**: z-index만으로 처리.
- **대체**: cluster 카운트 또는 fan-out. PERSON_FOUND 같은 강조 마커는 항상 최상위.

### 3.3 경로(LineString)와 구역(Polygon)이 같은 색 계열

- **잘못**: 둘 다 파랑 계열 → 식별 불가.
- **대체**: 경로는 stroke만, 구역은 fill + 다른 hue. 또는 dash·opacity 차등.

### 3.4 "단순 보기 모드"에서 무엇이 사라지는지 명세 없음

- **잘못**: 토글만 있고 무엇이 숨겨지는지 화면마다 다름.
- **대체**: FR-26 단순 보기 모드의 숨김 항목을 화면별로 명세 (`screen-state-matrix.md`의 simple_mode 컬럼 참조).

### 3.5 지도 위 텍스트가 베이스맵과 contrast 부족

- **잘못**: 지도 위 라벨이 흰색 → 밝은 베이스맵에서 안 보임.
- **대체**: 지도 위 텍스트는 outline·halo·배경 칩 처리 필수.

---

## 4. 폴리폰 (현장 입력 앱) anti-pattern

### 4.1 primary CTA가 화면 상단에 위치

- **잘못**: "마커 생성" 버튼이 상단 toolbar.
- **금지 이유**: 단손·엄지 조작 가정 위반 (field-context §1.1).
- **대체**: thumb zone(화면 하단 1/3)에 배치.

### 4.2 destructive action에 confirm 없거나 confirm이 작음

- **잘못**: "수색 종료" 탭 한 번에 즉시 종료.
- **대체**: 큰 confirm dialog + 명시적 destructive 버튼. undo window는 서버/도메인에서 되돌릴 수 있는 액션에만 사용한다. 500ms 수준의 짧은 long-press를 유일 confirm 장치로 쓰지 않는다.

### 4.3 모달이 화면을 덮어 무전 알림 못 봄

- **잘못**: 큰 모달이 상태바 가림.
- **대체**: 모달 위에도 알림·통신 상태 배지가 떠야 함.

### 4.4 폰트 크기가 KRDS 본문 17px 그대로

- **잘못**: 야외·움직이는 환경에서 17px 한국어는 가독성 부족.
- **대체**: 폴리폰 본문 19~21px 검토. dense-tokens.md에서 결정.

### 4.5 오프라인 상태가 화면 어디에도 표시 안 됨

- **잘못**: 오프라인을 예외 상태로만 다룸 → 사용자가 모름.
- **대체**: 모든 화면에 동기화 상태 배지 상시 노출.

### 4.6 미전송 큐가 텍스트로만 "12건" 표시

- **잘못**: 숫자만으로는 정상/이상 판단 어려움.
- **대체**: 임계 초과 시 색·배지 변경 + tap하면 상세.

---

## 5. 웹 상황판 anti-pattern

### 5.1 사건 전환이 페이지 reload

- **잘못**: 다중 사건 운영 시 사건 클릭마다 풀 reload.
- **대체**: 탭/사이드 전환으로 즉시 컨텍스트 스위칭.

### 5.2 OP 비교가 별도 페이지

- **잘못**: 현재 OP 화면을 떠나야 비교 가능.
- **대체**: 같은 지도 위에 overlay 토글.

### 5.3 폴리폰 위치 마지막 갱신이 hover에서만 보임

- **잘못**: 평소엔 점만 보이고 hover하면 "12분 전".
- **대체**: 색·outline·라벨 3중 인코딩으로 hover 없이 식별.

### 5.4 사건 종료 버튼이 일반 버튼과 같은 위치·크기

- **잘못**: 다른 액션 버튼들 옆에 동일 스타일.
- **대체**: 별도 메뉴 안 + destructive 색 + confirm 모달 + 입력 확인.

---

## 6. 인터랙션 anti-pattern

### 6.1 toast가 너무 빨리 사라짐

- **잘못**: 지원 요청 알림이 3초 후 사라짐 → 무전 응대 중 놓침.
- **대체**: 강조 알림은 명시적 dismiss까지 유지. 또는 별도 알림 영역.

### 6.2 로딩이 spinner만

- **잘못**: 무한 spinner. 진행률·실패·재시도 정보 없음.
- **대체**: 진행률·소요 시간 추정·실패 시 재시도 버튼.

### 6.3 권한 없음 화면이 그냥 빈 화면

- **잘못**: 권한 없을 때 빈 화면 + 작은 에러 텍스트.
- **대체**: 명시적 권한 안내, 어떤 계정으로 다시 로그인해야 하는지, 누구에게 문의해야 하는지.

### 6.4 짧은 long-press를 destructive confirm으로 사용

- **잘못**: 수색 종료·마커 삭제 같은 파괴적 액션을 500ms long-press 하나로 확정.
- **금지 이유**: 장갑·습기·이동 중 조작에서는 접촉이 끊겨 false negative가 나거나, 반대로 누른 채 들고 있다가 false positive가 날 수 있다.
- **대체**: 기본은 큰 confirm dialog. hold-to-confirm progress ring은 1.5s 이상, 진행률 시각화, 취소 가능, 실 폴리폰 장갑 테스트를 통과한 경우에만 후보로 둔다.
