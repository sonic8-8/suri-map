# 현장 사용 맥락 (Field Context)

상태: 초안. 이 문서는 Suri-Map이 실제로 사용되는 물리·인지·운영 환경을 전제로 못박는다. 화면 설계, 토큰, anti-pattern, 측정 게이트가 모두 이 문서를 근거로 삼는다.

## 목적

화면 설계가 데스크톱 사무실 가정으로 흐르지 않게 한다. KRDS는 시민 포털 디자인 시스템이라 본문 17px·여백 40px 같은 토큰이 기본인데, Suri-Map의 **현장 단말 사용 맥락**은 그 가정과 다르다.

## 1. 사용자 환경

### 1.1 폴리폰 (현장 단말, Android)

> 운용 단위 사실: 1팀(예: 6명)이 **팀 폴리폰 1대**를 공유한다 (PRD FR-33). 폴리폰 = 팀 또는 순찰차 단위 공유 단말. 개인 단위 폰이 아니다. 같은 폴리폰을 다음 근무자가 이어 사용할 때 `DutyShift`로 구분된다.

각 항목을 화면 설계 결정에 반영한다.

#### 물리 환경

- [ ] **조도**: 직사광선(50,000 lux 이상) ~ 야간 무광(0 lux)까지 변동. 화면 contrast 목표를 정한다 (WCAG AAA 7:1 권장).
- [ ] **온도/습도**: 영하·우천·고습 환경. 정전식 터치 정확도 저하 가정.
- [ ] **장갑**: 방한 장갑·작업 장갑 착용 가능. 정전식 미인식 케이스 있음. 최소 터치 타깃 결정 필요.
- [ ] **물리 충격**: 러기드 케이스 사용. 떨어뜨림·찍힘 빈번.
- [ ] **이동 중 조작**: 도보·차량·뛰는 상태에서도 조작.

#### 인지 환경

- [ ] **무전기 동시 사용**: 한 손은 무전기·PTT 버튼, 한 손은 폰. 단손 조작 전제.
- [ ] **시각 분할**: 시야가 화면이 아니라 현장(지형·실종자·동료)에 있어야 함. 화면은 글랜스(glance) 위주.
- [ ] **인지 부하**: 무전 청취·현장 판단·동료 통신과 동시 진행. UI는 인지 부하 추가를 최소화.
- [ ] **실수 비용**: 잘못 누르면 물리적으로 위험할 수 있음. destructive action에 긴 undo window 또는 confirm 필수.

#### 네트워크 환경

- [ ] **장시간 오프라인**: 30분 이상 오프라인 가정 (PRD 안정성 기준). UI는 오프라인을 예외가 아니라 default 상태로 다룸.
- [ ] **간헐적 연결**: 짧게 붙었다 끊어지는 sync. 진행률·실패·재시도 표출.
- [ ] **전송 지연**: 위치·마커가 서버에 도달했는지 사용자가 인지 가능해야 함.

#### 배터리 환경

- [ ] **장시간 운용**: 1교대 8시간+ 가정. UI 자체가 배터리 부담을 증폭하지 않음.
- [ ] **저전력 모드**: 배터리 20% 이하에서 비핵심 UI 자동 축소 여부 결정.

### 1.2 웹 상황판 (지휘 PC)

> 운용 단위 사실: 폴리폰에서 웹 상황판 접근은 **지원 대상 아님** (PRD §8.8). 데스크톱 브라우저(Chrome/Edge 최신 2버전) 전용. 모바일 반응형 설계 금지.

#### 물리 환경

- [ ] **디스플레이**: PC 모니터(1920×1080 또는 1440p). 멀티모니터 가능. 모바일 접근 미지원.
- [ ] **위치**: 본부 PC, 지구대 PC, 본부 외 임시 거점 PC. 조명·소음 환경은 사무실 표준.
- [ ] **입력**: 마우스·키보드. 터치스크린 가정 안 함.

#### 인지 환경

- [ ] **동시 사건**: 실종팀 지휘 계정은 다중 사건 동시 운영 가능 (PRD §7.1 FR-01). 사건 간 전환 비용 최소화.
- [ ] **주의 분산**: 무전 청취·전화 응대·옆 사람 협의와 병행. 화면이 핵심 상태 변화를 시선 끌어주는 패턴 필요.
- [ ] **장시간 사용**: 1 근무 회차 8시간+ 응시. 눈 피로·시각 가독성 중요.
- [ ] **여러 사람 동시 시청**: 상황판 화면을 여러 명이 동시에 보는 케이스. 글자 크기·색 대비가 1m+ 거리에서도 식별되어야 할 수 있음.

## 2. 정보 밀도 목표

화면 설계 전에 정량 목표를 정한다. 토큰 산정의 역산 기준이 된다.

### 2.0 산정 전제

- **단말 수 = 폴리폰 수** (인원 수 아님). PRD FR-33: 1팀 = 폴리폰 1대.
- **OP 동시 활성 = 1개**. OP는 인수인계 단위가 아니라 재수색·범위 변경 단위 (PRD FR-12, FR-32).
- **OP 비교**는 현재 OP + 과거 OP overlay (FR-11). 동시 비교 차수는 별도.
- **DutyShift**는 같은 폴리폰의 근무 교대 구간. UI에서 폴리폰 1대당 timeline 형태로 표출 가능.
- 웹 상황판 기준 해상도: 1920×1080 (PRD §8.8 데스크톱 전용).
- 폴리폰 기준 해상도: 412×892 (Galaxy S22 이상, PRD §8.8).

### 2.0.1 1차 산정 운영 컨텍스트 (광주 광역시 시연 기준)

> **검증 필요**: 아래 숫자는 광주 광역시 한 사건의 최대 가정에서 추정한 1차 산정값이다. 다른 지역·다른 규모 운영의 일반화는 후속 검증 필요. user-research-source.md §3 참조.

| 단위 | 인원 (광주) | 폴리폰 | 비고 |
|---|---|---|---|
| 실종팀 | 1명 (광주 전체) | 1~2대 | 1명만 있어도 운용 단위로 1~2대 |
| 지구대/파출소 1팀 | 6명 추정 (검증 필요) | 팀 폴리폰 1대 + 순찰차 폴리폰 N대 | 순찰차는 지구대/파출소 소속. 별도 단위 아님 |
| 기동대 1부대 | 다수 | 약 6대 추정 | 대규모 수색 2부대 합류 시 약 12대 (사용자 추정) |

→ 합산 추정: 광주 광역 대규모 사건 시 **약 15~20대 안팎**. 정확값보다 "적당히 + cluster fallback" 정책이 본질.

### 2.2 폴리폰 (412×892 기준)

| 항목 | 1차 산정값 | 검증 필요 | 근거 |
|---|---|---|---|
| 지도 점유율 (바텀시트 닫힘) | **100%** | — | 지도 우선 |
| 지도 점유율 (바텀시트 펼침) | **최소 50%** | — | 바텀시트 ~360~400px 차지 시 지도 ~492px |
| 바텀시트 thumb zone 도달률 (primary CTA) | **100%** | — | field-context §1.1 단손 조작 |
| 한 화면 동시 정보 단위 상한 (배지) | **상시 배지 3 + 강조 알림 1** | — | 동기화 + 시스템 + 미전송 = 3 |
| 미전송 큐 강조 임계 | **5건** | — | GPS 5초 + 10초 배치 = 정상 1~2건 |
| 미전송 큐 경고 임계 | **20건** | — | 30초+ 전송 실패 |
| 마커 5종 동시 표출 (`CLUE`/`PERSON_FOUND`/`FIELD_CONDITION`/`SUPPORT_REQUEST`/`NOTE(운영 메모)`) | **5종 한 화면, 스크롤 없음** | — | FR-30 엄지 중심. 2×3 또는 5×1 그리드 |
| 활성 사건 컨텍스트 | **1 사건** | — | 1팀=1폰=1현장 = 1사건 |

### 2.3 검증 필요 (△ 항목)

- [ ] **광주 광역 사건 폴리폰 수 검증**: 기동대 2부대 약 12대 정확 여부, 지구대/파출소(팀+순찰차) 폴리폰 합산 대수, 실종팀 폴리폰 운용 대수
- [ ] **OP 동시 overlay 시각 권장 한계 검증**: 5차 이상 동시 overlay가 실제로 가독성을 잃는 시점
- [ ] **다중 사건 동시 모니터링 수 검증**: 광주 실종팀 1명이 한 번에 몇 사건 모니터링하는지
- [ ] **DutyShift 교대 패턴 검증**: 광주는 8시간 3교대인지, 12시간 2교대인지, 다른 패턴인지
- [ ] **다른 지역·다른 규모 일반화**: 위 숫자가 광주 외 지역(서울·도서지역 등)에 어떻게 변하는지

## 3. 운영 시나리오

화면별로 가정해야 하는 시나리오 목록.

### 3.1 폴리폰

- [ ] 산악 한밤, 후레쉬 + 폰 화면 병행
- [ ] 비 오는 도심 골목, 한 손 우산
- [ ] 차량 운전 중 동승자가 단말 조작
- [ ] 도보 추격 중 한 손 조작
- [ ] 1시간 오프라인 → 10초 재접속 → 다시 오프라인
- [ ] 장갑 낀 손으로 마커 생성

### 3.2 웹 상황판

- [ ] 실종팀 지휘 계정이 사건 N건 동시 모니터링 (N은 §2.1에서 결정)
- [ ] 인수인계 시점에 같은 사건의 직전 DutyShift 인계 메모와 현재 DutyShift 시작 (FR-37)
- [ ] OP 전환 시점에 직전 OP·현재 OP 경로 overlay 비교 (FR-11)
- [ ] 지원 부대 합류 직후 신규 폴리폰 N대 일괄 표출 (SC-02)
- [ ] 사건 종료 직후 purge 진행 중 화면 (SC-12)
- [ ] 차량/도보 구간 보정 화면에서 자동 분류 결과 검토 (FR-33)
- [ ] 수색 이력 자동 요약 표출과 실패(FAILED) 상태 (FR-39)

## 4. 금지 가정

화면 설계 시 가정하면 안 되는 것.

- [ ] 통신이 안정적이라고 가정하지 않는다.
- [ ] 사용자가 화면에 집중하고 있다고 가정하지 않는다 (글랜스 디자인).
- [ ] 사용자가 양손을 자유롭게 쓴다고 가정하지 않는다.
- [ ] 사용자가 한국어 외 언어로 UI를 본다고 가정하지 않는다 (i18n MVP 외).
- [ ] 사용자가 일반 시민용 앱 사용 패턴(검색·POI·길찾기)에 익숙하다고 가정하지 않는다.
- [ ] 데스크톱 브라우저가 최신 Chrome일 거라고 가정하지 않는다 (지구대 PC 환경 다양).
