# 커밋, PR, Issue 글쓰기 기준

커밋 메시지, PR과 Issue의 제목과 본문, Issue 댓글을 쓰거나 리뷰할 때 읽는다. 제목 형식(Area, type, scope)은 루트 `AGENTS.md`의 Git 절에 있다. 이 형식은 커밋할 때 `.githooks/` 훅으로 검사된다. 문장 규칙은 루트 `AGENTS.md` 공통 원칙의 글쓰기 규칙을 따른다. 이 문서에는 그 밖에 사람이 판단해야 하는 기준을 적는다.

## 쓰는 순서

1. 글을 쓰기 전에 초안 파일에 before와 after를 한 줄씩 쓴다. before는 바꾸기 전에 누가 무엇을 하지 못하거나 무엇이 잘못되는지다. after는 바꾼 뒤에 누가 무엇을 할 수 있게 되는지다. 둘 중 하나라도 쓰지 못하면 사용자 의도(why)를 모르는 것이다. 그때는 글을 쓰기 전에 사용자에게 묻는다.
2. 제목의 요약에 바꾼 내용을 쓰고, 그 안에 이유가 드러나게 쓴다. 리눅스 커널 커밋과 같은 방식이다([커밋 메시지 제목과 본문의 목적 배치 조사](../research/commit-message-purpose-research.md)). 바꾼 내용은 diff에서, 이유는 before나 after에서 가져온다.
   - 고치는 문제나 막을 동작을 바꾼 내용의 목적어나 꾸미는 말로 쓴다. 예: `Fix TOCTOU kernel stack disclosure`(리눅스 커널), `커밋, PR, Issue 글의 반복 지적을 막는 글쓰기 기준 추가`
   - 문서 추가처럼 바꾼 내용만으로 왜 필요한지 분명하면 이유를 붙이지 않는다. 예: `Add a maintainer entry profile for KVM/arm64`(리눅스 커널), `수색 구역을 관서와 팀에 배정하는 ADR-0038 추가`
   - 바꾼 내용만으로 오해가 생길 때만 `이유, 바꾼 내용` 순서로 짧은 이유 절을 붙인다. 커밋 순서처럼 이 변경 자체와 상관없는 사정은 본문에 쓴다. 예: `팀원 누구나 업무폰에서 팀의 수색 구역을 볼 수 있게, 수색 구역을 계정 대신 관서와 팀에 배정하도록 변경`
3. 상세한 내용은 본문에 쓴다.
   - 커밋 메시지 본문의 첫 문단에는 지금 동작과 그 문제(before)를 쓴다. 결함을 고쳤으면 원인과 재현 방법(명령, 출력, 오류 메시지)도 이 문단에 쓴다.
   - 둘째 문단에는 바꾼 방법과 그 이유를 "~하도록 ~했다"처럼 써서 after를 드러낸다. 바꾼 파일 목록 대신 바뀐 동작을 쓴다. 바꾼 것이 여럿일 때만 목록으로 쓴다.
   - 함께 바꾼 것은 문단을 나눠 쓴다. 호환성과 검증 결과는 그 뒤에 덧붙인다. 원인과 구현 방식은 겹치는 말 없이 쓴다.
   - 결함을 고친 커밋은 끝에 원인 커밋을 `Fixes: <커밋 번호> ("<제목>")`로 적는다.
   - PR 본문은 `/mattpocock-skills:pr`, spec과 티켓 본문은 `/mattpocock-skills:to-spec`과 `/mattpocock-skills:to-tickets`, Issue 댓글은 [오케스트레이터 절차](../../agents/orchestrator.md)의 형식으로 쓴다. 문장에는 아래 [기준](#기준)을 적용한다.
4. 아래 [기준](#기준)을 제목과 본문의 줄마다 적용해 고친다. 같은 브랜치의 다른 커밋이나 관련 Issue와 겹치는 말도 찾는다.
5. 사용자가 제안한 제목과 문장에도 4를 똑같이 적용한다. 걸린 곳은 고친 안과 함께 사용자에게 짚는다. 걸린 곳이 없으면 무엇을 확인했는지 한 줄로 적는다.

## 기준

- **이유:** 이 변경이 왜 필요한지를 사람이나 역할이 겪는 문제(before), 얻는 결과(after), 또는 없어지는 문제로 쓴다. 예: "반복 지적을 막는", "상황판 전체 재조회 없이". 겉보기와 부수 효과는 이유로 쓰지 않는다.
- **되풀이:** 이유를 따로 붙였으면, 바꾼 내용을 가리고 이유만 읽어도 왜 필요한지 알 수 있어야 한다.
- **바꾼 종류:** 바꾼 내용은 종류와 대상으로 쓴다. 종류는 추가(없던 것), 변경(있던 동작이나 구조를 다르게), 수정(결함), 제거 가운데 실제로 한 것이다. 대상은 `GLOSSARY.md`의 용어, ADR 번호, 코드의 이름으로 쓴다.
- **하나씩:** 제목에는 바꾼 내용을 하나만 쓴다. 이유를 따로 붙이면 이유도 하나만 쓴다. 바꾼 것이 여럿이면 제목에는 그것을 묶는 이름을 쓰고, 하나씩은 본문 목록에 쓴다.
- **이름:** 명사는 `GLOSSARY.md`, ADR, 코드에 있는 이름을 쓴다. 그 글에서 처음 묶은 명사는 무엇을 하는지 동사로 풀어 쓴다.
- **대상 있는 동사:** "동작하도록", "맞도록", "정하도록" 같은 동사에는 무엇이 어떻게 되는지를 붙인다.
- **도메인 묘사:** 업무폰, 계정, 사람, 팀, 관서의 관계를 쓸 때 `GLOSSARY.md`의 해당 항목과 관련 ADR을 읽고 그대로 쓴다. 예: ADR-0037에 따라 업무폰 등록 여부는 권한의 근거가 아니다. 그래서 동작은 계정과 권한을 기준으로 쓴다.

### 고친 예

처음 쓴 말은 사용자가 지적한 제목이다. 출처는 그 뒤에 게시하거나 사용자가 확정한 제목이다. 이 기준으로 쓴 제목은 같은 변경을 이 문서의 쓰는 순서 2로 다시 쓴 것이다.

| 처음 쓴 말 | 출처(게시하거나 확정한 제목) | 이 기준으로 쓴 제목 | 기준 |
|---|---|---|---|
| 상황판 전체를 다시 조회하지 않아도 통신 상태가 바뀌도록 | 커밋 `1553651d` | 통신 상태가 바뀔 때마다 하던 상황판 전체 재조회를 통신 상태 SSE로 변경 | 이유, 바꾼 종류 |
| 사건 접근 검사 추가 | Issue #44 | 권한 없는 계정의 사건 데이터 조회와 변경을 막는 권한 확인 추가 | 이름, 바꾼 종류("검사"는 테스트를 추가한 것으로 읽힌다) |
| 실제로 수색하는 관서와 팀이 수색 구역을 맡도록, 수색 구역 배정 대상을 계정에서 관서와 팀으로 바꾸고 팀 간 인수인계 추가 | 사용자가 확정한 spec 제목 | 팀원 누구나 업무폰에서 팀의 수색 구역을 볼 수 있게, 수색 구역을 계정 대신 관서와 팀에 배정하도록 변경 | 이름, 되풀이, 하나씩, 바꾼 종류(이유 절을 붙인 경우) |

## 리뷰와 검수 점검

- 리뷰어는 결과 파일에 "이 제목은 무엇을 왜 바꿨는가"를 한 문장으로 적는다. 제목만 읽고 이 문장을 쓸 수 없으면 `required_change`다.
- 리뷰어는 [기준](#기준)을 줄마다 적용하고, 걸린 곳마다 어느 기준인지 적는다.
- 검수자는 도메인 묘사를 `GLOSSARY.md`, ADR, 배정에 적힌 사용자 결정과 대조한다.
