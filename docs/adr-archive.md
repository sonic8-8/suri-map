## ADR-0008. 계정 모델 이원화 (개인 / 팀)

- **Status**: Superseded by ADR-0015, then ADR-0031
- **Date**: 2026-04-21

> Current note (2026-05-04): 아래 원문은 과거 계정 모델 기록이다. 현재 구현 기준은 운영 주체 `account`, 경로·FCM·오프라인 패키지 주체 `police_phone`, PostgreSQL 저장 `refresh_token`을 분리한다.

### Context

- 실종팀·현장 지휘관은 **개별 판단과 승인 책임**이 있음 → 이름 기반 감사 필요
- 현장 수색대원의 폴리폰은 **팀당 1대** 지급, 교대 사용
- 책임 단위가 팀

### Decision

- **개인 계정**: 실종팀, 현장 지휘관
- **팀 계정**: 현장 수색대원 (폴리폰 로그인)
- 계정 발급은 경찰 IT 부서 일괄 관리 (셀프 가입/복구 없음)
- 같은 계정 다른 기기 로그인 시 기존 세션 무효화

### Consequences

- **+** 감사 추적이 책임 단위와 일치
- **+** 폴리폰 교대 사용 실무와 자연스럽게 맞음
- **−** 마커 생성 주체가 "개인 or 팀"으로 나뉘어 권한 매트릭스 복잡도 증가
- **−** 팀 계정의 단서 수정 권한은 "자기 팀 생성분만"으로 별도 정의 필요 (권한 매트릭스 참조)

## ADR-0009. 현장 지휘관은 앱 주 조작자

- **Status**: Superseded by ADR-0016, then ADR-0026
- **Date**: 2026-04-21

> Current note (2026-05-04): 아래 원문은 과거 앱 중심 지휘 모델 기록이다. 현재 구현 기준은 웹 상황판이 구역·OP·인수인계 조작을 담당하고, 폴리폰 앱은 GPS 경로·마커·사진·오프라인 동기화에 집중한다.

### Context

- 초기 검토에서 현장 지휘관을 "웹 주 + 앱 보조"로 설정했으나, 실제 업무상 **현장에 나가서 조작**하는 것이 자연스러움
- 경찰청 예규(실종아동등 업무처리 규칙)에 사건 규모별 지휘관 기준 있음
- 구역 분할/할당, 완료 처리는 현장 상황 판단이 필요

### Decision

- 현장 지휘관의 **주 디바이스는 폴리폰 앱**, 보조는 웹
- 사건당 현장 지휘관 **1명** 지정
- 구역 분할/할당 권한은 **현장 지휘관 전용** (실종팀에는 부여하지 않음)
- 구역 완료 처리는 현장 지휘관 + 실종팀 모두 가능 (감사 로그에 주체 구분)

### Consequences

- **+** 현장 상황 판단이 빠르게 반영
- **+** 실종팀은 상황판 중심으로 "큰 그림" 판단에 집중
- **−** 현장 지휘관 앱 UX는 "웹에서 하던 조작"을 모바일에서 가능하게 만들어야 함 (구역 드로잉 등)
- **−** 현장 지휘관 GPS도 기록되므로 팀 경로와 시각적 구분 필요

## ADR-0010. ADR 단일 파일 관리 (MVP)

- **Status**: Superseded by ADR-0032
- **Date**: 2026-04-21

### Context

- 일반적인 ADR 관행: `docs/adr/NNNN-title.md` 디렉토리 + 결정별 파일
- MVP 5주, 팀 컨텍스트 공유 상태, 결정 수 제한적
- 결정별 개별 파일은 오버헤드

### Decision

- MVP 단계에서는 `adr.md` 단일 파일로 관리
- 결정은 섹션(ADR-NNNN)으로 구분
- 결정 수 증가 또는 수명 주기가 복잡해지면 디렉토리 구조로 전환

### Consequences

- **+** 문서 탐색 단순, 전체 결정을 한 파일에서 조망 가능
- **+** 5주 내 추가될 결정 수 기준으로 충분
- **−** 여러 결정을 동시에 수정할 때 머지 충돌 가능 (현재 팀 규모에서는 감수)
- **−** 결정 수가 20개 이상으로 늘어나면 가독성 저하

## ADR-0011. 베이스맵 / 타일 서버 전략 (자체 호스팅)

- **Status**: Superseded by ADR-0024
- **Date**: 2026-04-22

### Context

- 산악 수색에 적합한 지도(등산로·등고선·지형)가 필수
- Mapbox 라이선스·쿼터 리스크 (G-15), 상용 지도 API(카카오/네이버) 약관·내부망 호출 제약 (G-17)
- SSAFY가 EC2 xlarge를 제공 → 자체 타일 서버 운영 가능
- Android/Web 모두 MapLibre로 통일 (ADR-0004 개정)

### Decision

- **베이스맵 타일**: OSM(OpenStreetMap) 데이터 + OpenMapTiles 스타일을 자체 타일 서버(`tileserver-gl` 컨테이너)에서 호스팅
- **등산로/임도 오버레이**: 국토부 등산로 Open API(WMS) 또는 산림청 산림공간정보 데이터를 오버레이 레이어로 적용
- **항공사진/위성**: MVP 범위 외 (필요 시 2차 검토, 브이월드 항공 후보)
- **3D 지형**: MVP 제외 (등고선 레이어로 대체)
- **오프라인 배포**: Android 앱이 자체 타일 서버에서 사건 프리셋 단위로 타일을 다운로드, MapLibre Native의 오프라인 영역 관리 사용
- **대상 산 프리셋**: 북한산, 무등산, 지리산 등 운영 측과 협의한 프리셋 (사건 생성 시 선택)

### Consequences

- **+** 라이선스 비용·쿼터 리스크 제거
- **+** 내부망·업무 단말 장기 보관 약관 문제 없음
- **+** Android·Web이 동일 스타일을 공유 (베이스맵 일관성)
- **+** 오버레이 레이어(등산로) 추가·갱신을 자체 관리
- **−** OSM 지도 품질은 상용 대비 낮을 수 있음 (특히 산악 지역 미매핑 구간)
- **−** 타일 서버 운영 부담 (리소스·모니터링·장애 대응)
- **−** OSM은 ODbL 라이선스로 **타일 출력에 attribution 표시 필수**
- **−** 국토부 등산로 API 사용 시 공공기관 이용 신청·API 키 관리 필요

### 검토 필요 항목

- 북한산 등 시연 대상 산의 OSM 등산로 매핑 품질 확인
- 국토부 등산로 Open API vs 산림청 데이터 중 오버레이 소스 최종 선택 (Spec 단계)
- 타일 서버 캐시·스토리지 용량 산정

## ADR-0015. 개인 계정 중심 계정 모델 (ADR-0008 대체)

- **Status**: Superseded by ADR-0031
- **Date**: 2026-04-23
- **Supersedes**: ADR-0008

> Current note (2026-05-04): 아래 원문은 과거 개인 계정 중심 결정이다. 현재 구현 기준은 팀/순찰차/지휘 `account`와 업무폰 `police_phone`을 분리하고, refresh token은 PostgreSQL `refresh_token`에 저장한다.

### Context

- PRD2에서는 개인 책임과 감사 추적을 우선해 개인 계정 중심 모델을 검토했다.
- PRD v3에서 팀 업무폰·순찰차 업무폰 공유 전제가 확정되며 이 결정은 폐기됐다.

### Historical Decision

- 개인 계정 중심 모델을 채택하려 했으나, 현재 구현 기준이 아니다.

### Consequences

- **+** 개인 단위 추적은 명확하지만 MVP 현장 운용 전제와 맞지 않는다.
- **−** 폴리폰 교대 사용 시 로그인·로그아웃 절차가 현장 UX에 부담이 된다.
- **대체**: ADR-0031에서 팀 계정·순찰차 계정·지휘 계정으로 변경.

## ADR-0016. 현장 지휘관 N명 모델 + 웹 전용 조작 (ADR-0009 대체)

- **Status**: Superseded by ADR-0026
- **Date**: 2026-04-23
- **Supersedes**: ADR-0009

> Current note (2026-05-04): 아래 원문은 과거 지휘 권한 모델이다. 현재 구현 기준은 내부 지원 배정 API를 제공하지 않고, 사건·지원 배정은 112/mock polling/import 결과로 `incident_assignment`에 반영한다.

### Context

- ADR-0009는 "사건당 현장 지휘관 1명, 앱 주 조작"이었음
- 회의(2026-04-21) 결과, 실종팀 간부·기동대장·제대장 등이 **동등한 지휘 권한을 공유**해야 함 (PRD2 §0.1, §3.1)
- 지원 요청 이후에도 실종팀 간부의 지휘 권한이 유지되며, 기동대장·제대장 합류는 **권한 이양이 아닌 추가** (PRD2 §3.1)
- 구역 분할·완료·차수 관리는 지도 정밀 조작이 필요해 **웹 상황판에 적합**하며, 본부 PC에서 수행하는 것이 실제 운영에 맞음
- 폴리폰에서의 웹 상황판 접근은 지원 대상 아님 (PRD2 §8.8)

### Decision

- 사건당 현장 지휘관은 **복수(N명)** 지정 가능
- 지정 방식: 시드 데이터의 직책(기동대장·제대장 등) 기반 **자동 부여** + 실종팀 간부의 수동 추가·교체
- 실종팀 단독 수색 중에는 실종팀 간부가 현장 지휘관 역할을 겸임
- 현장 지휘 업무(AOI 지정·구역 분할/할당/완료·차수 관리)는 **웹 상황판 전용**이며 폴리폰에서는 수행 불가
- 현장 지휘관도 폴리폰으로 GPS 기록·마커 생성은 수행 (일반 사용자와 동일)

### Consequences

- **+** 실종팀과 지원 부서 간부가 동등한 협업 구조 (상하 관계가 아닌 동등 조직 모델과 일치)
- **+** 웹 전용 조작으로 현장 UX 단순화 (앱 구역 드로잉 UX 개발 부담 제거)
- **+** 지원 요청 이후에도 실종팀 지휘 연속성 유지
- **−** 웹 접근이 불가한 현장에서는 구역 완료 처리가 지연될 수 있음 (무전 + 본부 PC 반영 흐름으로 수용)
- **−** 현장 지휘관 다수가 동시에 같은 구역을 편집할 가능성 → 충돌 정책은 ADR-0003 last-write-wins로 커버, 감사 로그에 주체 기록

## ADR-0017. 채널별 조작 경계 (마커=앱 전용, 구역 완료=웹 전용)

- **Status**: Superseded by ADR-0026
- **Date**: 2026-04-23

> Current note (2026-05-04): 아래 원문은 과거 채널 경계 기록이다. 현재 구현 기준은 AOI/map boundary 별도 엔티티와 내부 부대 배정 workflow를 사용하지 않으며, 전체/부대/팀 구역은 `search_area`와 `search_area_assignment`로 관리한다.

### Context

- PRD2 FR-10, FR-14에서 **마커 생성은 폴리폰 앱 전용**으로 명시 (현장 GPS 자동 입력 전제)
- PRD2 FR-06, §5.1 10단계에서 **구역 완료 처리는 웹 상황판 전용**으로 명시 (앱 불가)
- 초기 아키텍처에는 이 채널 경계가 명시되지 않아, 구현 단계에서 UI 중복 개발 또는 의도치 않은 경로로 데이터가 생성될 위험
- 현장 입력(GPS 신선도 필요)과 본부 판단(다수 경로·구역 종합)이라는 성격 차이를 반영

### Decision

| 동작 | 허용 채널 | 비허용 채널 |
|---|---|---|
| 마커 생성 (단서/발견/지형/지원요청) | 폴리폰 앱 | 웹 (조회·수정·삭제만) |
| 구역 완료 처리 | 웹 상황판 | 앱 |
| AOI 지정/수정, 구역 분할/할당 | 웹 상황판 | 앱 |
| 새 차수 열기 | 웹 상황판 | 앱 |
| GPS 경로 자동 기록 | 폴리폰 앱 | 웹 |
| 사건 생성/가져오기, 종료, 부대 배정 | 웹 상황판 | 앱 |

- 서버 API는 위 경계를 **역할 + 클라이언트 출처** 조합으로 검증
- 웹 클라이언트에서 마커 생성 엔드포인트 호출 시 서버가 거부

### Consequences

- **+** 현장 GPS 신선도가 마커에 항상 반영됨 (웹 수동 입력 방지)
- **+** 구역 완료는 지도 전체 맥락에서 판단 (모바일 좁은 화면 오조작 방지)
- **+** UI 설계가 단일 채널 집중 → 개발·테스트 범위 축소
- **−** 현장에서 구역 완료 처리가 필요한 상황은 무전으로 본부 전달 후 웹에서 반영 (기존 무전 흐름 유지이므로 수용)
- **−** 서버에 클라이언트 출처 검증 로직 추가 필요

## ADR-0018. AOI 도입 및 사각지대 자동 하이라이트 연산 전략

- **Status**: Superseded by ADR-0027
- **Date**: 2026-04-23

### Context

- PRD2 §1.3에서 문제 정의 중 하나가 "중복 수색과 미수색 사각지대를 빠르게 파악하기 어렵다"
- PRD2 FR-23에서 **사각지대 자동 하이라이트**를 MVP 범위로 편입 (§1.3-3 직격 해법)
- 연산 기준으로 사건에 **수색 대상 경계(AOI)** 필드 신설 (PRD2 §6.1)
- "어떤 GPS 경로·완료 구역에도 닿지 않은 영역" 계산에 공간 연산 필요 → PostGIS(ADR-0002) 활용 전제
- 판단은 현장 지휘관·실종팀의 몫이며 시스템은 **시각 단서만 제공** (PRD2 FR-23)

### Decision

- `incident` 엔티티에 `aoi Polygon` 필드를 추가 (nullable — AOI 미지정 사건도 허용)
- AOI는 현장 지휘관 권한(실종팀 간부 + 지원 부서 간부)이 웹에서 지정·수정 (PRD2 §8.4)
- 사각지대 연산:
  1. `AOI` 폴리곤에서 완료 상태(`1차수색완료`/`재수색완료`)인 `search_area` 폴리곤들을 `ST_Difference`로 차감
  2. 결과에서 각 `search_path` LineString을 일정 거리(`buffer_m`)로 `ST_Buffer`한 영역을 추가 차감
  3. 남은 영역 중 `min_area_m2` 이상인 다각형을 사각지대 레이어로 반환
- 파라미터(`buffer_m`, `min_area_m2`, 연산 주기)는 SDD 단계에서 확정 — 현업 감각과 성능 실측 기반
- 연산은 **온디맨드 계산**으로 시작 (상황판 요청 시 계산). 부하 증가 시 주기적 캐시 또는 이벤트 기반 재계산으로 전환
- 결과는 상황판에만 표시 (앱 미노출)

### Consequences

- **+** PRD2 §1.3-3 핵심 문제를 직접 해결하는 기능
- **+** PostGIS 공간 연산으로 SQL 레벨 구현 가능, 별도 엔진 불필요
- **+** "시각 단서 제공, 판단은 사람" 원칙으로 오판 책임 소재 명확
- **−** AOI 미지정 사건에서는 기능 비활성 → 운영 관점에서 "AOI 먼저 지정" 흐름 유도 필요
- **−** 경로 버퍼 거리 등 파라미터 튜닝 없이는 결과가 과도하게 좁거나 넓음 (시범 시연에서 현업 피드백 필요)
- **−** 사건 규모·경로 밀도에 따라 연산 시간 증가 가능 (성능 게이트 대상)

### 검토 필요 항목

- 파라미터 기본값(버퍼 거리·최소 면적) 현업 검증
- 연산 주기 전략: 온디맨드 vs 주기적 캐시 vs 이벤트 기반
- AOI 외부에서 발생한 경로·마커의 취급 (경고 표시 여부)

## ADR-0019. 사건 오프라인 패키지 사전 적재

- **Status**: Superseded by ADR-0028
- **Date**: 2026-04-23

> Current note (2026-05-04): 아래 원문은 과거 결정이다. 현재 구현 기준은 `offline_package_manifest`, `offline_package_installation`, `incident_assignment`, `search_area(area_level=OVERALL|UNIT|TEAM)`를 사용하며 `incident_membership`, `op_assignment`, AOI/map boundary 별도 엔티티를 사용하지 않는다.

### Context

- PRD2 FR-31, §5.1 3단계에서 사건 진입 시 오프라인 운용에 필요한 항목을 **단일 흐름으로 사전 적재**해야 한다고 명시
- 기존 아키텍처(§3.6)는 지도 타일 프리셋 다운로드만 다뤘음 — 사건 메타·실종자 정보·담당 구역은 누락
- 현장 투입 전 **경찰청 Wi-Fi 환경**에서 한 번에 받아 두어야 산악 현장에서 조회 가능
- 항목별로 다운로드하면 UX가 산발적이고, 누락 시 현장에서 발견됨

### Decision

- 사건 배정 계정/단말이 사건 진입 시 폴리폰에서 **단일 다운로드 흐름**으로 다음을 일괄 적재:
  1. 사건 메타 (`incident`, `incident_membership`, active `operational_period`, active `op_assignment`)
  2. 실종자 정보 (`missing_person` + 사진)
  3. 담당 구역 (`search_area` 폴리곤 + 상태)
  4. 지도 타일 프리셋 (ADR-0011)
  5. AOI 폴리곤 (ADR-0018)
- 진행률은 항목별로 표시하고, 실패 항목은 개별 재시도 가능
- 적재 미완료 상태는 서버에 보고되어 **상황판 경고 배지**로 노출
- 사건 종료 시 전체 패키지 로컬 삭제 (서버 동기화 확인 후)

### Consequences

- **+** 현장 투입 전 준비 완료 여부를 단일 지표로 판단 가능 (배지 노출)
- **+** 실종자 사진·정보가 오프라인에서도 조회 가능 → 신원 확인 지연 방지
- **+** 담당 구역이 오프라인에서 표시되어 할당 구역 외 이탈 감지 가능
- **−** 실종자 사진 등 민감정보가 단말 로컬에 저장됨 → 서버 동기화 완료 후 삭제 정책 엄격 운영 필요 (PRD2 §8.5)
- **−** 다운로드 용량 증가 (타일 + 사진 + 폴리곤) → Wi-Fi 환경 전제 명시

### 검토 필요 항목

- 단일 다운로드 용량 상한 (프리셋별 용량 산정)
- 실종자 사진의 단말 저장 시 암호화 요구 (법무 검토)
- 담당 구역 변경 시 재적재 흐름

## ADR-0021. 차수의 내부 모델은 Operational Period(OP)로 관리

- **Status**: Superseded by ADR-0029
- **Date**: 2026-04-23

> Current note (2026-05-04): 아래 원문은 과거 OP 모델 기록이다. 현재 구현 기준은 사건 배정 `incident_assignment`, 구역 배정 `search_area_assignment`, 근무 교대 `duty_shift`를 분리하며 `incident_membership`과 `op_assignment`를 사용하지 않는다.

### Context

- PRD2 FR-11, FR-12, FR-13은 차수별 트랙/어사인먼트 분리, 새 차수 열기, 수색 횟수 표시를 요구함
- [2026-04-22_research_handling.md](./2026-04-22_research_handling.md)는 SAR 관행(CalTopo/SARTopo)을 근거로 **Operational Period(OP)** 를 1급 객체로 둘 것을 제안함
- 단순히 `search_area.round` 같은 숫자 필드만 두면 "지금 active 차수와 과거 차수"를 시각적으로 분리하기 어렵고, 트랙/마커/구역 상태 이력을 한 기준으로 묶기 힘듦
- CalTopo/SARTopo식 운영 모델에서는 사건 참가와 OP별 assignment를 사실상 분리해 다룬다. 같은 사건 참가자가 OP1에서는 A구역, OP2에서는 B구역을 맡을 수 있으며, 사건 참가 사실 자체는 유지된다

### Decision

- 내부 도메인 모델은 `OperationalPeriod`를 사용한다. 사용자 UI에서는 계속 `차수`라는 용어를 사용한다
- 사건당 active OP는 **1개만 허용**한다
- 사건 생성/가져오기 시 OP1을 자동 생성한다
- 새 차수를 열면 기존 active OP는 `closed`, 새 OP는 `active`가 된다
- 사건 수준 참여/접근 권한은 `incident_membership`으로 관리한다. `incident_membership`은 `op_id`를 갖지 않는다
- OP 수준 담당 배정은 `op_assignment`로 관리한다. `op_assignment`는 `op_id`를 가지며, 특정 OP에서 팀/계정/구역 책임을 기록한다
- `search_path`, `marker`, `search_area_history`, **`op_assignment`**는 모두 `op_id`를 가진다
- `search_area`는 현재 상태와 누적 `search_count`를 유지하고, 회차별 상세 이력은 `search_area_history`에 남긴다
- **현장 지휘관 역할은 사건 수준 권한**이므로 `incident_membership`에 둔다. OP가 바뀌어도 자동으로 사라지지 않는다
- **차수 전환 시 이전 차수의 `op_assignment`는 삭제·수정하지 않고 보존한다** — 새 차수를 열면 새 `op_assignment` 행이 새 `op_id`로 생성되고, 이전 차수는 `op_id` 필터로 그대로 조회 가능 (FR-12 "이전 차수 트랙·어사인먼트는 보존" 요구)
- 상황판은 active OP를 기본 표시하고, 이전 OP는 토글 또는 옅은 스타일로 표시한다

### Consequences

- **+** 재수색 시 트랙 누적으로 지도가 망가지는 문제를 줄일 수 있음
- **+** "1차에 어디까지 봤고 2차에 무엇을 다시 했는가"를 OP 단위로 자연스럽게 설명 가능
- **+** 사건 참가/접근 권한과 차수별 담당 배정의 의미가 분리되어 권한 모델이 덜 흔들림
- **+** 향후 OP별 타임라인/보고서/회고 기능으로 확장하기 쉬움
- **−** `operational_period`, `incident_membership`, `op_assignment`, `search_area_history` 테이블과 OP 토글 UI가 추가됨
- **−** active OP 전환 시점의 UX와 권한 검증이 필요함
