# 상황판 조회와 갱신

상황판의 데이터 조립·실시간 갱신·수색 차수 비교·사건 종료 표시를 바꿀 때 확인한다. 옛 S3-2 요구와 2026-09-21 정적 코드 대조 결과다. 테스트용 조립 결과와 실제 HTTP·SSE·브라우저 동작을 구분한다.

## 원본을 바꾸지 않는 조회

- 상황판은 사건·구역·경로·마커·업무폰·오프라인 패키지·차수·인수인계 정보를 모아 보여준다. 차수 비교, 필터, 단순 지도, 현재 계정·이동 유형 강조는 표시만 바꾼다. 원본 좌표·상태·버전을 수정하거나 다음 수색 구역·누락·위험도를 자동 판단하지 않는다. 마커 수정·삭제는 해당 기능의 API를 호출한다.
- [Controller](../../backend/src/main/java/com/surimap/board/IncidentBoardController.java)는 `/api/incidents/{incidentId}/board`에서 웹 채널·사건 접근·위치 조회 기록을 요구한다. [조회 서비스](../../backend/src/main/java/com/surimap/board/IncidentBoardQueryService.java) → [데이터 수집](../../backend/src/main/java/com/surimap/board/DefaultIncidentBoardSourceRowCollector.java) → [응답 조립](../../backend/src/main/java/com/surimap/board/BoardAssembler.java) 순서다. 애노테이션 선언만으로 사건별 권한 검사까지 완료됐다고 판단하지 않으며 [인증의 차이](authentication.md)를 함께 확인한다.
- `opIds`·`includeSlots`로 조회 범위를 지정한다. `sinceVersion`은 상황판 전체 응답의 이전 버전이지 각 원본 행의 증분 조회 기준이 아니다. 현재 수집기는 이 값으로 원본 행을 걸러내지 않는다. 서로 다른 원본의 버전을 하나의 순번처럼 비교하지 않는다.

## 경로 변경분 조회 설계

**2026-10-07 리뷰 보완·재검증:** 좌표가 하나인 구간의 HTTP 표시 형식, 차수 범위 간 캐시 병합과 미수신 이력 보존을 수정했다. 최초 기준이 다른 캐시의 이력·변경분 완료 정보는 공유하지 않는다. Backend 1,415개·Frontend 306개 테스트와 타입 검사·빌드를 통과했다. [문제·수정·검증 범위](../test-results/search-path-pages-frontend-20261007.md#코드-리뷰에서-발견한-문제와-수정)를 참고한다. 실제 서버 전환·HTTP·브라우저·부하는 여전히 미검증이다.

**2026-10-07 서버 시험 설정 합의:** 전체 조회 범위의 경로 수 상한(`max-known-paths`)은 로컬 시험과 같은 1,000으로 선택했다. 응답당 80경로와 다른 제한이며, 1,000개 처리 성능을 확인했다는 뜻은 아니다. [시험값·설정 전달·전환 전 확인](../api/search-path-pages.md#시험-한도와-활성화)에 정리했다. 실제 서버 적용·배포와 HTTP 요청 제한시간 결정은 남아 있다.

**2026-10-07 프런트엔드 연결·로컬 검증:** Q63 승인으로 새 두 API를 상황판 지도·구역 상세·차수 검토에 연결했다. 기존 board GET은 새 웹 흐름에서 경로를 제외한다. 페이지 교대·부분 표시·구간 버전 병합·SSE/저장 후 재조회·일시 실패 재시도·권한/종료/로그아웃 정리를 구현했다. Frontend 타입 검사·빌드·302개 테스트를 통과했다. HTTP 응답을 대체한 로컬 검사이며 실제 브라우저·Backend 통합·서버 전환·부하는 하지 않았다. 서버 API는 기본 비활성이고 요청 제한시간 숫자는 아직 넣지 않았다. [변경 파일·검증 범위·다음 작업](../test-results/search-path-pages-frontend-20261007.md)을 기준으로 아래의 과거 미구현 기록과 구분한다.

**2026-10-06 Backend 구현·로컬 검증:** 두 조회 API·입력 검증·사건 접근/종료/파기 제한·위치 조회 감사·페이지 조회를 구현했다. Backend 전체 1,413개가 통과했다(실패·오류·건너뜀 0, 기본 성능 태그 제외). 새 endpoint는 기본 비활성이고 한도 기본값은 미설정이다. 웹 연결·실제 서버 migration/배포·본 부하는 하지 않았다. 시험 한도별 측정 후 기본값을 정한다.

[로컬 검증·한도 후보 측정 결과](../test-results/search-path-pages-local-20261006.md)에 조건·수치·변경 파일을 기록했다. 이는 첫 페이지의 Service 조회·응답 직렬화 측정이며 전체 이력 완료나 실제 서버의 지도 반영 시간과 구분한다.

**웹 연결의 시험 한도 (2026-10-06 합의):** 응답당 최대 80경로·80구간·480좌표, 경로당 한 차례에 1구간으로 시작한다. 로컬 첫 페이지에서 20경로 후보보다 약 2.4배의 조회 시간으로 4배의 경로를 받은 결과를 근거로 선택했다. 운영 기본값이나 최적값은 아니며 실제 지도 첫 표시·전체 이력 완료·새 좌표 반영 시간을 확인한 뒤 조정한다. 요청/조회 범위 경로 수 한도와 요청 제한시간의 숫자는 이번 선택으로 확정하지 않았다. 서버 설정 변경·새 API 활성화·웹 연결·배포는 아직 하지 않았다.

2026-10-02부터 사용자와 합의한 방향이다. 2026-10-06 구간 순번·변경 경로 버전의 저장과 기존 자료 보완 SQL을 구현해 로컬 DB에서 검증했다. [저장 준비 결과](search-path.md#좌표-저장과-도형-조립)와 구분해, 새 조회 API는 위 범위로 구현했으며 웹 연결·실제 서버 전환은 아직 하지 않았다.

- 전체 응답 캐시보다 변경분 조회·반영을 먼저 설계한다. 기존 경로는 유지하고 추가·수정된 구간만 갱신하며, 남는 조회 비용에 서버 캐시를 비교한다.
- 화면은 경로별로 마지막 반영 버전을 기억한다. 서버는 각 구간이 해당 경로의 어느 버전에서 추가·수정됐는지 기록해 변경분을 찾도록 설계한다. 기존 구간 자체의 버전이나 SSE 수신 순번을 경로의 반영 버전으로 대신하지 않는다.
- **선행 쓰기 경합 수정 (2026-10-03, 로컬 검증·미배포)**: 좌표 추가와 일시정지가 겹칠 때 경로 버전이 중복·역행하는 문제를 재현하고, 공통 상태 변경이 기존 경로 행 잠금을 사용하도록 수정했다. [수색 경로의 수정·검증 결과](search-path.md#경로의-주체와-생명주기)에서 범위를 확인한다. 실제 서버의 발생·화면 누락·부하 개선을 확인한 것은 아니며, 변경분 조회의 API 진행 정보 계약과 구현은 아직 남아 있다.
- 재접속 때 기존 경로 데이터와 반영 버전이 유효하면 변경분만 보충한다. 해당 사건·수색 차수의 현재 경로 목록도 대조해 새 경로를 찾으며, SSE 이력이 없어도 경로 데이터 기준으로 복구하도록 설계한다. 기존 데이터를 활용할 수 없으면 전체 경로 조회로 돌아간다. 권한 상실·종료·파기 제한을 우선하고 SSE 재전송과 알림 기록의 복구는 유지한다.
- 최초 조회도 구간을 나눠 받아 도착한 부분부터 표시한다. 완료 전에는 경로를 불러오는 중이며 일부만 표시됐음을 명확히 알리고, 아직 받지 못한 구간을 실제 경로가 없는 상태로 취급하지 않는다. 첫 표시 시간과 전체 로딩 완료 시간은 별도로 측정한다.
- 초기 로딩 중에도 새 좌표·구간 보정을 반영한다. 기존 이력의 로딩 진행과 새 변경의 반영 진행은 구분하며, 새 변경을 받았다는 이유로 미수신 이력까지 완료 처리하지 않는다. 오래된 자료가 최신 보정을 덮어쓰지 않게 하고, 일반 갱신 요청 합치기는 유지한다.
- 최초 표시에서는 조회 대상 경로마다 끝부분을 먼저 보여주고 이전 구간을 채운다. 마지막 기록 지점을 실제 현재 위치로 보장하지 않으며, 이전 이력을 생략하거나 삭제하지 않는다. 미수신 구간 사이를 임의의 직선으로 연결하지 않는다.
- 같은 상황판의 경로 조회 범위에서는 진행 중인 HTTP 요청을 하나만 두고 작은 이력 페이지와 변경분 조회를 번갈아 진행한다. 새 변경이 현재 페이지 응답을 기다릴 수 있지만 전체 이력 완료까지 미루지는 않는다. 이벤트마다 요청을 쌓지 않고, 지속적인 새 변경 때문에 이력 조회가 멈추지 않게 한다. SSE 연결 수나 다른 자료의 HTTP 요청 수를 제한하는 합의는 아니다.
- 웹 상황판용 경로 조회 API를 별도로 제공한다. 기존 상황판 API는 새 웹 흐름에서 경로를 제외한 자료 조회에 사용하고, 기존 기본 응답과 Android가 사용하는 공용 경로 조회 계약은 유지한다. 같은 서버·DB에서 공통 도메인·Mapper를 재사용하며, 웹 채널·사건 접근·위치 조회 기록과 종료/파기 제한을 확인한다. URL·메서드·HTTP DTO 이름은 아래 합의를 따르며 세부 요청·응답 형태는 아래 API 예시에 정리했다.
- 웹 경로 조회는 최초·과거 이력 조회와 변경분 조회로 나눈다. 전자는 각 경로의 끝부분을 먼저 받고 이전 구간을 채우며, 후자는 마지막 반영 이후 추가·수정된 구간과 경로 상태를 받는다. 새 경로는 별도의 목록 조회 호출 없이 각 조회에서 발견한다. 이력 수신 진행과 변경 반영 버전은 따로 관리하되, 같은 조회 범위의 HTTP 요청은 한 번에 하나만 실행한다. 조회 종류를 나누는 것이 Service·DB를 따로 만드는 뜻은 아니다.
- 두 신규 조회 API는 `POST`의 JSON 본문으로 조회 조건과 경로별 진행 정보를 받는다. 긴 조건을 URL에 넣지 않으려는 선택이며, 경로 원본을 생성·수정하는 요청은 아니다. 위치 조회 감사 기록은 유지하고 기존 상황판·Android 공용 `GET` 계약은 바꾸지 않는다. 일반 HTTP 캐시는 `GET`과 같은 방식으로 기대하지 않으며, 합의한 조회 재시도 정책은 이 읽기 계약에 한정해 적용한다. DTO 필드는 아래 API 예시를 따르며, 요청 한도의 적용 기본값은 측정 후 결정한다.
- 구간 생성 시 계산하는 시작·끝 GPS 저장 순번을 해당 구간에 함께 저장한다. 별도의 구간 연속 번호는 추가하지 않는다. 같은 경로 안에서 구간을 정렬하고 미수신 구간을 확인하는 기준으로 사용하며, 이동 유형을 보정해도 좌표 범위는 유지한다. 저장 순번은 측정 시각 순서나 실제 이동의 연속성을 보장하지 않는다.
- 기존 구간의 변경 추적값은 데이터 보완 시점의 부모 경로 버전으로 초기화한다(2026-10-06 합의). 경로 버전·구간 자체 버전·좌표·이동 유형은 그대로 유지한다. 과거 수정 버전을 복원한 값이 아니라 새 조회의 변경 추적을 시작하는 기준이다. 이후 좌표 추가로 생긴 구간과 보정된 구간에만 해당 쓰기에서 증가한 경로 버전을 저장하고, 일시정지·재개·종료만으로 모든 구간을 갱신하지 않는다. 최초 조회는 기존 구간도 이력 페이지로 받고 그 기준 이후 변경을 추적한다.
- 실제 전환은 기존 백엔드와 시험 입력을 중단하고 진행 중인 쓰기가 종료된 것을 확인한 뒤 수행한다(2026-10-06 합의). 백업·기존 자료 보완·검증 후 새 쓰기 코드로 재개한다. 보완 실패나 불확실한 범위가 있으면 새 조회로 전환하지 않으며 기존 자료를 삭제·재생성하지 않는다. API·SSE 이용 중단을 허용하는 포트폴리오 서버의 일회성 전환 방식이며, Flyway 활성화나 배포 명령만으로 다른 쓰기 실행까지 차단됐다고 가정하지 않는다. 실제 중단·migration·배포를 수행한 기록은 아니다.
- 기존 데이터의 좌표 범위를 검증·보완한 뒤 새 상황판 조회로 전환한다. 범위를 확정하지 못한 경로가 있으면 전환을 보류하고 처리 방법을 먼저 정하며, 일부 경로만 새 방식으로 읽는 호환 흐름은 기본안에 추가하지 않는다. GPS 원본이 없는 자료나 반복 좌표를 추측으로 보완하거나 기존 이력을 삭제·재생성하지 않는다. 2026-10-06 Hetzner 앱 DB 읽기 전용 전수 검사에서 경로 481개·구간 57,083개가 GPS 340,985개와 유일하게 대응했고, 누락·중복 배정·순번 공백은 0이었다. API ID 규칙 923개·부하 입력 ID 규칙 56,160개도 일치했다. 이후 저장 컬럼·쓰기 연결·보완 SQL을 로컬에서 구현·검증했지만, 실제 서버의 컬럼 추가·자료 보완·새 코드 배포는 하지 않았다.
- 변경분 조회 회차마다 경로별 상한 버전을 고정한다. 해당 범위의 모든 페이지를 확인한 뒤 그 경로의 완료 기준을 올리고, 조회 중 발생한 상한 이후 변경은 다음 회차에서 받는다. 더 높은 버전의 일부 구간을 받았다는 이유로 미수신 변경까지 완료 처리하지 않는다. 보정으로 상한 밖으로 이동한 구간도 후속 조회에서 회수해야 한다. 이는 최신 상태로 따라잡기 위한 진행 기준이며 특정 과거 버전의 도형을 복원하는 계약은 아니다.
- 한 HTTP 응답에는 여러 경로의 구간을 함께 담되 경로·구간 개수와 총좌표 수를 함께 제한한다. 경로별 이력 진행·변경분 상한·완료 기준은 구분하며, 같은 범위의 HTTP 요청 하나 원칙은 유지한다. 항목 수와 좌표 처리량을 제어하는 기준이지 JSON 바이트 상한은 아니다. 구체적인 수치는 응답 시간·크기를 측정한 뒤 정하며, 구간 하나나 응답 하나를 고정된 좌표 묶음으로 취급하지 않는다.
- 여러 경로는 돌아가며 조회한다(2026-10-06 합의). 한 경로의 일부를 처리한 뒤 다른 경로에도 차례를 주고, 앞선 경로의 남은 구간은 다시 차례가 왔을 때 이어받는다. 경로 안에서는 끝부분 우선 순서를 유지한다. 특정 경로가 계속 응답 한도를 차지해 다른 경로의 조회가 밀리지 않게 하려는 선택이다. 서버가 응답에 다음 경로의 조회 시작 위치를 반환하고, 웹은 응답을 반영한 뒤 보관해 다음 요청에 그대로 보낸다. 웹이 요청의 경로 배열을 재정렬해 차례를 지정하지 않는다. 이는 경로 사이의 순환 위치이며 경로 안의 구간 조회 위치와 다르다. `segments`와 `changes`의 순환 위치는 각각 보관하고 해당 API의 다음 요청에 사용한다. 한 API의 응답으로 다른 API의 순환 위치를 바꾸지 않는다. 두 API의 교대와 경로별 진행 정보는 유지하며, 한 응답에서 각 경로에 한 차례씩 기회를 주고 차례별 구간 수는 시험 설정으로 제어한다. 기본값은 아직 정하지 않았다.
- 구간 하나는 여러 응답으로 분할하지 않고 통째로 전송한다. 정상 저장에서 생성 가능한 최대 구간 하나를 수용하도록 응답 한도를 정한다. 현재 페이지의 남은 한도에만 맞지 않으면 다음 페이지로 넘긴다. 구간 자체가 전체 한도를 넘는 자료는 전환 전 검사에서 확인하며, 실행 중 발견해도 조용히 누락하거나 한도를 초과해 반환하지 않고 오류로 알린다. 빈 페이지를 반복하며 진행한 것처럼 처리하지 않는다.
- 경로 순환 위치의 필드 이름은 `nextSearchPathId`로 정한다(2026-10-06 합의). 값으로 지정한 경로를 포함해 조회를 시작하며, 그 경로 다음부터 시작하는 뜻이 아니다. 두 API가 각각 이 값을 관리한다. 경로 사이의 순서는 경로 ID 오름차순으로 고정하고, 끝에 도달하면 처음으로 돌아간다. UUID의 순서를 경로 생성 시각이나 현장 우선순위로 해석하지 않는다. 경로 안의 끝부분 우선 조회와 기존 API의 정렬 계약은 바꾸지 않는다. 지정한 경로가 다음 요청에서 조회 대상에 없으면 그 ID보다 큰 조회 가능한 경로 중 첫 경로로 이어가며, 없으면 처음으로 돌아간다. 남은 경로의 구간 진행 정보는 유지한다. 올바른 형식의 순환 기준이 더 이상 대상에 없는 상황과 잘못된 요청 형식은 구분하고, 사건 접근·종료·파기 제한은 우선한다. 최초 순환 위치는 null이고 현재 조회를 마치면 null과 hasMore=false를 반환한다. 이는 새 API의 필드 합의이며 기존 공개 필드를 바꾸지 않는다.
- 응답 전체의 이어받기 여부는 `hasMore`로 별도 표시한다(2026-10-06 합의). 서버가 해당 API의 현재 조회 범위에서 더 확인하거나 받아야 할 내용이 남았는지 판단하며, 아직 응답에 등장하지 않은 경로도 고려한다. 경로별 `completed`나 순환 위치인 `nextSearchPathId`만으로 전체 완료를 추정하지 않는다. 두 API는 각각 판단하며 `false`이면 해당 이어받기를 멈춘다. 이미 수신했거나 이후 수신하는 새 변경의 후속 조회까지 막거나 다른 API의 로딩 완료를 뜻하지 않는다. 서버의 페이지 판정과 조회 중 추가/보정은 로컬 DB 테스트로 확인했으며 웹 반영은 검증 전이다.
- 최초 조회에 성공했지만 조회 대상 경로가 하나도 없으면 `200 OK`와 `{"paths": [], "nextSearchPathId": null, "hasMore": false}`를 반환한다(2026-10-06 합의). 본문 없는 `204`로 별도 처리하지 않는다. 권한 거부·조회 실패를 정상 빈 결과로 바꾸지 않으며, 경로는 있지만 좌표가 없는 경우와 구분한다. 이후 변경분 응답이 비었다는 이유로 기존 경로를 삭제하는 규칙도 아니다.
- 진행 정보의 HTTP 계약·입력 검증과 종료·파기 제한은 Backend에 연결해 로컬에서 검증했다. 현재 지도는 받은 구간의 끝점을 위치 점으로 만들고 배열상 이전 구간의 끝점과 연결하므로, 부분 수신에서도 위 표시 기준을 지키는지 검증해야 한다. 웹 연결·서버 전환의 구현·검증 범위는 별도로 합의한다. 위 재접속 방식의 웹 연결은 아직 구현 전이며, 다른 상황판 자료의 복구 방식을 변경하지 않는다.

API 이름은 `Segments`(경로 구간 조회)와 `Changes`(변경분 조회)로 합의했다. 다음은 구현 전 계약 이름이며 아직 호출할 수 있는 API가 아니다. 저장된 구간의 최신 상태를 읽으며, 과거 수정 상태를 복원하는 이력으로 오해하지 않도록 `History` 대신 `Segments`를 사용한다.

| 역할 | POST URL | 메서드·HTTP DTO |
|---|---|---|
| 최초·과거 구간 조회 | `/api/incidents/{incidentId}/board/search-paths/segments/query` | `getSearchPathSegments`, `SearchPathSegmentsQueryRequest` / `SearchPathSegmentsQueryResponse` |
| 변경분 조회 | `/api/incidents/{incidentId}/board/search-paths/changes/query` | `getSearchPathChanges`, `SearchPathChangesQueryRequest` / `SearchPathChangesQueryResponse` |

구현 중인 요청·응답 예시와 시험 설정은 [경로 페이지 API](../api/search-path-pages.md)에 정리한다. 기존 공용 경로 API 명세를 대체하지 않는다.

두 신규 API는 매 요청에 조회할 수색 차수 ID 목록 `opIds`를 명시한다(2026-10-06 합의). 서버가 생략된 값을 요청 시점의 현재 차수로 해석하지 않도록 하여, 같은 차수의 다음 페이지 조회와 다른 차수로의 전환을 구분한다. `opIds: []`는 조회 대상 없음으로 해석하고 정상 빈 결과를 반환한다. 현재 차수나 사건의 모든 차수로 자동 확대하지 않으며, 접근 권한·종료·파기 제한은 빈 요청에도 우선한다. 기존 상황판 API의 기본 조회 동작은 바꾸지 않는다. Backend 요청 계약은 구현했으며 웹 연결은 아직 하지 않았다.

같은 사건에서 선택한 차수가 바뀌면 계속 선택된 차수의 경로 데이터와 경로별 조회 진행 정보를 유지한다(2026-10-06 합의). 새로 선택한 차수는 최초 조회로 불러오고, 선택에서 빠진 차수는 표시·조회 대상에서 제외한다. 두 API의 전체 경로 순환 위치는 새 조회 범위에서 다시 시작하며 이전 범위의 `hasMore`로 새 범위의 조회 완료를 판단하지 않는다. 예를 들어 1차에서 1차·2차로 선택을 넓혀도 이미 받은 1차 경로를 처음부터 다시 받지 않는다. 선택 해제가 서버 원본 삭제를 뜻하지 않으며, 재접속·사건 전환·권한 상실에 관한 기존 합의는 유지한다. 웹의 상태 관리·응답 병합은 아직 구현·검증하지 않았다.

이어받기 정보는 의미가 드러나는 JSON 필드로 구분한다(2026-10-04 합의). 경로별 이력 조회 위치, 변경 반영 완료 버전, 진행 중인 변경분 조회의 상한과 페이지 위치를 하나의 불투명한 문자열로 묶지 않는다. 서버가 다음 조회에 필요한 정보를 응답하고, 웹은 응답 데이터를 반영한 뒤 그 정보를 보관해 다음 요청에 보낸다. 웹에서 조회 위치를 별도로 계산하는 방식은 아니다. 필드·HTTP 오류·검증 규칙은 아래 API 예시와 Backend 코드에 반영했다. 웹의 수신 상태 관리는 구현 전이다.

새 두 API의 경로·구간 버전과 진행 정보의 버전 값은 JSON에서 10진 정수 문자열로 주고받는다(2026-10-04 합의). JavaScript `number`로 변환하면서 Java `long` 값이 달라지는 일을 피하려는 선택이다. 크기 비교가 필요하면 정확한 정수로 변환해 비교하며 문자열의 사전순으로 비교하지 않는다. DB·도메인의 버전 자료형과 기존 API의 JSON 숫자 계약은 바꾸지 않는다. GPS 저장 순번은 아래 합의대로 JSON 숫자로 구분한다.

새 구간 응답의 시작·끝 GPS 저장 순번은 `startPointOrder`·`endPointOrder`로 이름짓는다(2026-10-06 합의). 두 값과 진행 정보의 `beforeStartPointOrder`는 JSON 숫자로 표현하며, 아직 정해지지 않은 조회 위치의 `null`은 유지한다. 순번은 경로 전체에서 0부터 매기는 저장 순서이고 시작·끝 모두 포함한다. 이번 응답의 좌표 배열 인덱스나 측정 시각 순서를 뜻하지 않는다. 현재 DB `integer`·Java `int` 범위는 JavaScript 숫자로 정확하게 표현할 수 있으므로 버전처럼 문자열로 변환하지 않는다. 기존 Java 내부의 `startIndex`·`endIndex`, DB 컬럼과 기존 공개 API는 이 명명만으로 바꾸지 않는다.

최초 요청에서 아직 정해지지 않은 조회 위치는 `null`로 표현하고, 응답에는 경로별로 이번 조회 범위를 모두 확인했는지 별도 값으로 명시한다(2026-10-04 합의). 정상 GPS 저장 순번 `0`을 미시작 표시로 사용하거나 구간 배열이 비었다는 이유만으로 완료를 추정하지 않는다. 기존 이력을 채우는 진행과 변경분 회차의 완료는 구분하며, 이번 범위의 완료가 이후 변경까지 없다는 뜻은 아니다. 변경분 회차 완료 후의 요청은 아래 합의를 따른다.

응답은 경로별 객체 안에 ID·상태·구간과 해당 경로의 조회 진행 정보를 함께 담는다(2026-10-04 합의). 데이터와 진행 정보를 별도 배열로 반환해 웹에서 경로 ID로 다시 연결하는 구조는 사용하지 않는다. 같은 응답 안에서도 경로별 완료 여부가 다를 수 있으며, 이 구조 선택이 모든 경로를 한 응답에 담거나 모든 진행 정보를 매번 반환한다는 뜻은 아니다.

진행 정보 필드 이름은 `segmentsProgress`와 `changesProgress`로 구분한다(2026-10-06 합의). 전자는 기존 경로 구간의 조회 위치·완료 여부, 후자는 변경분의 반영 완료 버전·현재 조회 범위·페이지 진행을 뜻한다. 각 API는 자기 역할에 해당하는 진행 정보를 반환하며 두 필드를 모든 응답에 함께 넣지 않는다. 수색 진행률이나 실제 경찰의 이동 진행 상태를 뜻하지 않는다.

해당 경로·API의 진행 정보를 아직 받아 반영하지 않았다면 요청의 진행 객체 전체를 `null`로 보낸다(2026-10-06 합의). 웹이 초기 필드 조합을 만들어 보내지 않고, 응답을 반영한 뒤부터 서버가 반환한 진행 객체를 보관·재전송한다. `null`은 변경이나 좌표가 없다는 뜻이 아니며, 완료한 객체를 다시 `null`로 바꾸지 않는다. 변경분 조회는 별도로 최초 구간 조회의 `baselineVersion`이 확보돼 있어야 시작한다.

각 요청에는 현재 사건·조회 조건 안에서 웹이 알고 있는 모든 경로의 ID와 해당 API의 진행 정보를 보낸다(2026-10-06 합의). `segments` 요청에는 `segmentsProgress`, `changes` 요청에는 변경 추적 기준과 `changesProgress`를 담고 다른 API의 진행 정보까지 함께 보내지 않는다. 좌표를 다시 보내는 것은 아니다. 서버는 조회 범위의 경로 목록과 비교해 새 경로를 발견하며, 별도의 경로 목록 발견용 페이지 진행 정보는 두지 않는다. 경로 수에 따라 요청이 커지므로 요청 크기와 비교 비용을 검증한다. 응답 한도와 서버의 접근 권한 검사는 유지하며, 세부 JSON 배치는 API 문서를 따른다.

`changes` 조회에서 새 경로를 발견하면 ID·기본 정보를 반환하고, 웹은 이어지는 `segments` 조회에서 해당 경로의 끝부분부터 불러온다(2026-10-06 합의). `changes`가 최초 구간 로딩까지 대신하지 않는다. `baselineVersion`은 발견 시점이 아니라 첫 구간 페이지와 같은 DB 조회 기준에서 확보하며, 그 뒤 변경분 추적을 시작한다. 첫 구간 조회가 필요한 상태는 `baselineVersion: null`로 구분하고 별도 최초 조회 필요 필드는 추가하지 않는다. 첫 조회를 정상 반영하면 서버에서 받은 기준 버전을 보관한다. 기준 버전은 있고 `changesProgress`만 `null`이면 최초 구간 조회를 다시 하는 것이 아니라 변경분 조회를 시작한다. 구간을 아직 받지 못한 상태를 빈 경로로 확정하지 않는다. 같은 범위의 HTTP 요청 하나·두 조회의 교대·응답 한도는 유지하며 세부 JSON 배치는 API 문서를 따른다.

두 조회에서 받은 구간은 같은 경로 안에서 구간 ID로 합치고, 해당 구간 자체의 버전이 더 높은 내용을 유지한다(2026-10-06 합의). 처음 받은 ID는 추가하고 같은 버전은 중복 반영하지 않으며, 낮은 버전으로 최신 내용을 덮어쓰지 않는다. 버전 비교는 새 API의 10진 정수 문자열을 정밀도 손실 없이 비교하는 기준을 따른다. 구간 버전은 화면의 구간 병합에 사용하고, 경로 버전은 변경분 조회 범위·반영 진행에 사용한다. 구간 병합만으로 경로의 `appliedVersion`을 올리지 않는다. 구현·동시 변경 검증은 아직 하지 않았다.

경로의 기록 중·일시정지·종료 상태는 어느 API에서 받았든 해당 상태와 함께 반환된 경로 버전이 더 높으면 반영한다(2026-10-06 합의). 처음 받은 경로는 초기 상태를 표시하고, 이후 낮은 버전의 상태로 되돌리지 않는다. 상태 표시의 최신성을 판단하는 경로 버전과 구간 병합에 쓰는 구간 버전은 구분한다. 상태를 갱신해도 미수신 구간을 받은 것으로 처리하거나 `appliedVersion`·`targetVersion`을 상태의 버전으로 바꾸지 않는다. Backend의 같은 조회 시점 읽기는 검증했으며 웹의 상태 병합은 구현·검증 전이다.

변경분 회차의 마지막 응답까지 반영하면 웹은 완료한 `changesProgress`를 보관하고 다음 요청에도 그대로 보낸다(2026-10-06 합의). 서버는 `completed: true`인 경로를 다음 조회 대상으로 처리할 때 `appliedVersion` 이후의 새 상한을 정하고 페이지 조회 위치를 새로 시작한다. 미완료이면 기존 상한·페이지 위치를 이어간다. 별도의 회차 시작 지시는 추가하지 않는다. 이 규칙은 다음 요청의 해석이며, 완료 즉시 요청을 무한 반복하거나 정상 상태의 주기적 조회를 추가한다는 뜻은 아니다. 기존 구간 로딩의 완료 상태는 별도로 유지한다.

요청의 진행 정보에 잘못된 버전 형식이나 중복 경로 ID가 있으면 요청 전체를 오류로 응답한다(2026-10-06 합의). 정상 경로만 부분 성공으로 반환하거나 잘못된 값을 조용히 보정하지 않는다. 웹은 이번 요청으로 진행 정보를 갱신하지 않고, 기존 화면 자료는 접근·종료·파기 제한 안에서 유지한다. 입력 오류는 통신 장애의 자동 재시도와 구분한다. 구현한 오류 코드와 검증 규칙은 API 문서에서 확인한다.

형식이 맞아도 서버 상태와 모순되는 진행 정보는 요청 전체를 오류로 처리한다(2026-10-06 합의). 예를 들어 현재 경로 버전보다 높은 반영 완료 버전을 보낸 경우다. 웹은 오류를 표시하고 진행 정보를 자동 초기화하거나 재조회하지 않는다. 서버보다 낮은 버전이나 정상적인 미완료 페이지는 오류·만료로 취급하지 않으며 기존 이어받기를 허용한다.

경로별 진행 정보에 지정한 사건·선택한 차수 범위 밖의 경로 ID가 섞여 있어도 요청 전체를 오류로 처리한다(2026-10-06 합의). 해당 항목만 제외한 부분 성공으로 반환하지 않고 오류 응답에 다른 사건의 경로 존재 여부를 노출하지 않는다. 이는 경로별 진행 항목의 검증이며, 조회 대상에서 사라진 `nextSearchPathId`를 다음 경로로 넘기는 순환 기준의 합의와 구분한다. Backend 검증·오류 처리는 구현했으며 웹의 오류 처리는 아직 연결하지 않았다.

| 위치 | 필드 | 의미 |
|---|---|---|
| 두 진행 정보 각각 | `beforeStartPointOrder` | 시작 GPS 저장 순번이 이 값보다 작은 구간을 이어서 조회하는 기준. 처음에는 `null`이며 구간을 좌표 단위로 잘라 보내는 기준이 아니다. |
| 두 진행 정보 각각 | `completed` | 해당 경로의 이번 조회 범위를 모두 확인했는지 나타내는 값. 두 조회의 완료 상태는 독립적이다. |
| 경로별 변경분 추적 시작 기준 | `baselineVersion` | 첫 구간 조회와 같은 DB 조회 기준에서 확보한 경로 버전. 변경 추적의 출발점이며 반영 완료 버전이 아니다. |
| `changesProgress` | `appliedVersion` | 변경분을 빠짐없이 반영한 마지막 경로 버전. 최초 값은 `null`이며 일부 페이지만 반영하고 올리지 않는다. |
| `changesProgress` | `targetVersion` | 이번 변경분 조회의 상한 경로 버전. 회차 도중 더 높은 버전이 생겨도 유지한다. |

변경분 추적은 경로의 첫 구간 조회와 같은 DB 조회 기준에서 확보한 경로 버전을 별도 시작 기준으로 삼는다(2026-10-06 합의). 이 필드를 `baselineVersion`으로 이름짓고 최초 `appliedVersion`은 `null`로 둔다. 최초 변경분 조회는 시작 기준 이후만 대상으로 하고, 미수신 기존 구간은 `segments` 조회로 계속 채운다. 시작 기준은 반영 완료 버전이 아니므로 첫 페이지를 받았다는 이유로 `appliedVersion`에 넣지 않는다. 두 값은 값이 있을 때 10진 정수 문자열로 표현한다.

변경분 조회의 하한은 반영 완료 버전이 없을 때 위 시작 기준, 이후에는 `appliedVersion`이다. 조회 대상은 하한 초과·`targetVersion` 이하이며 버전 값은 10진 정수 문자열이다. 서버가 응답한 진행 정보는 웹이 해당 데이터를 반영한 뒤 보관한다. 변경분 반영 완료는 별도로 진행 중인 기존 구간의 조회 완료를 뜻하지 않는다. 첫 페이지와 시작 기준 사이의 동시 쓰기, 기존 구간 조회와 변경분 조회가 같은 구간을 반환할 때의 병합은 구현·검증 전이다.

같은 경로의 변경 구간은 시작 GPS 저장 순번이 큰 구간부터 작은 구간으로 조회한다(2026-10-06 합의). 최근 보정 시각이나 변경 버전 순서가 아니라 경로 뒤쪽의 변경부터 반영하려는 선택이다. 이동 유형 보정은 구간의 좌표 범위와 정렬 위치를 바꾸지 않는다. 고정한 회차 상한 이후의 변경은 다음 회차에서 확인하며, 이 순서만으로 페이지 사이 변경 누락이 방지되거나 실제 현재 위치가 보장되는 것은 아니다. 순번 저장·보완 SQL은 로컬 검증을 마쳤지만 새 API의 이어받기 조건도 로컬 DB 테스트로 확인했다.

구간 조회에도 표시·계측에 필요한 경로 상태·계정·수색 차수 등을 함께 담는다. 기존 `SearchPathQuerySegmentResponse`는 개별 구간 DTO이며 이번 합의로 재명명하지 않는다. 세부 JSON 필드·검증 범위는 API 문서와 위 구현 결과를 따른다.

새 두 조회 API의 응답은 지도 표시·구간 병합에 필요한 정보로 제한한다(2026-10-06 합의). 경로에는 ID·계정·수색 차수·상태·버전·조회 진행 정보를, 구간에는 ID·자체 버전·시작/끝 GPS 저장 순번·이동 유형·좌표·시작/끝 시각을 담는다. 전체 경로 좌표를 중복해서 반환하지 않으며, 제외 좌표·이동 유형의 자동/수동 구분·보정자·보정 시각도 새 응답에서 제외한다. 이 정보의 DB 저장과 기존 API는 유지한다. 새 구간 순번의 이름·자료형은 위 합의를 따르며 세부 JSON 배치는 API 문서에 반영했다.

## 이벤트 수신과 최신 데이터 재조회

- **기존 요구**: 동일한 `eventId`는 중복 적용하지 않고 오래된 이벤트가 최신 화면을 되돌리지 않게 한다. 재전송이 불가능하거나 순번 누락을 확인하면 전체 조회로 복구한다. 경로 조회의 대체 설계는 위 '경로 변경분 조회 설계'에서 구분하며 아직 구현하지 않았다. SSE `id`는 사건별 재전송 순번이며 `data.eventId`와 다르다.
- [현재 화면 구독](../../frontend/src/features/situationBoard/presentation/hooks/useSituationBoardData.ts)은 연결 성공·새 이벤트·재조회 요구 시 React Query 캐시를 무효화해 REST 재조회를 요청한다. 이벤트 payload를 곧바로 모든 지도 행에 덮어쓰는 구조가 아니다. `eventId` 중복은 Set으로 막지만 순번 간격을 직접 검사하지는 않는다. 재시작·놓친 알림 복구 범위는 [이벤트 전달](event-delivery.md)에서 확인한다.
- **지도 갱신용 재조회 합의 (2026-09-24)**: 진행 중인 조회가 없으면 바로 요청한다. 조회 중 새 변경이 들어오면 현재 요청을 취소하지 않고 추가 변경이 있었다는 사실을 기억한다. 조회가 성공하면 그동안 받은 여러 변경을 후속 조회 하나로 합친다. 후속 조회 중에도 변경이 들어오면 같은 기준을 적용하며, 전체 요청을 두 번으로 제한하지 않는다. 같은 계정·사건·조회 조건의 일반 갱신 요청에만 적용하고, 개별 알림 처리나 종료·권한 처리를 미루지 않는다. 새 변경 반영이 현재 조회 완료까지 늦어질 수 있는 선택이다. 일시적 조회 실패·요청 시간 제한과 일반적인 사건 전환은 아래 합의를 따른다. 계정·권한·종료 처리는 별도로 구분한다. 로컬 구현 범위는 아래 기록을 따르며, 실제 서버의 요청 수·지도 반영 시간 검증은 남아 있다.
- **재조회 합치기 구현·로컬 검증 (2026-10-01)**: [공통 재조회 함수](../../frontend/src/features/board/api/incidentBoardApi.ts)의 같은 QueryClient·조회 키에는 진행 중 요청과 후속 요청 하나만 둔다. - **지도 조회 실패의 복구 합의 (2026-09-24)**: 해당 상황판을 사용하는 동안 재시도 가능한 일시적 HTTP 조회 실패는 횟수·총시간 제한 없이 간격을 두고 다시 조회한다. 새 이벤트나 사용자의 조작이 없어도 복구하려는 선택이며, 장애가 길어지면 재시도 요청도 계속 발생한다. 조회가 회복되면 실패 복구를 끝내고 일반 갱신 흐름으로 돌아간다. 정상 상태에서도 계속 조회하는 주기적 조회를 추가한 것은 아니다. 반영하지 못한 변경과 최신 상태 미확인 표시는 유지하고, 이벤트마다 별도 재시도 작업을 만들지 않는다. 정상인 SSE를 HTTP 실패 때문에 다시 연결하지 않으며, 권한 거부·로그아웃·사건 종료·화면 이탈은 별도로 처리한다. 재시도 대상·간격·숨김·오프라인 판정·서버 지정 대기시간과 요청 시간 제한은 아래 합의를 따른다. 구체적인 요청 제한시간 값은 아직 미정이다. 구현·장애 복구 검증 전 합의다.

HTTP 조회와 SSE의 실패 횟수·대기 상태는 각각 관리하고, SSE의 60초 정상 수신 후 초기화 기준을 HTTP 조회에 적용하지 않는다. 구현·장애 복구 시험 후 조정한다.
- **숨겨진 탭의 조회 재시도 합의 (2026-09-25)**: 브라우저가 숨김으로 판단한 탭에서는 실패한 지도 조회의 다음 재시도를 보류한다. 탭에 돌아왔을 때 기존 대기시간이 지났으면 다른 재시도 조건을 충족하는 대로 이어가고, 남아 있으면 마저 기다린다. 숨김·복귀만으로 실패 횟수나 대기시간을 초기화하지 않는다. 보지 않는 상황판의 반복 요청을 줄이는 선택이며, 복귀 후 조회가 성공할 때까지 이전 자료와 최신 상태 미확인 표시를 유지한다. 단순 입력 포커스 변경은 숨김이 아니고, 이미 진행 중인 요청·SSE 수신을 숨김만으로 취소하거나 종료·권한 처리를 미루지 않는다. 모든 최초 조회·일반 이벤트 조회를 숨김 중 금지한다는 합의는 아니다. 현재 상황판은 `retry: false`이므로 이 실패 재시도 동작의 구현·브라우저 검증은 남아 있다.
- **오프라인 판정과 지도 조회 합의 (2026-09-25)**: 브라우저가 오프라인이라고 알려도 필요한 지도 HTTP 조회와 재시도를 그 판정만으로 막지 않는다. 지휘 상황판의 자동 복구가 브라우저의 잘못된 판정 때문에 멈추지 않도록 하는 선택이며, 실제 연결이 끊겼을 때 실패하는 시도도 발생한다. 최초 조회와 실패 복구에 적용하되 정상 상태의 주기적 조회는 추가하지 않는다. 합의한 재시도 간격·숨김 보류·종료·권한 처리를 유지하며, 실제 조회 성공으로 복구 여부를 판단한다. - **지도 조회 재시도 대상 합의 (2026-09-25)**: 통신 실패와 HTTP `408·429·500·502·503·504`를 자동 재시도 대상으로 삼는다. 인증·권한 오류, 사건 종료, 의도적인 요청 취소, 정상 응답의 데이터 형식 오류·프로그래밍 오류는 제외한다. 500만으로 일시적 장애와 지속적인 코드 결함을 구분할 수는 없지만, 서버 회복 후 조회가 자동 복구되도록 포함했다. 코드 결함이면 실패 요청도 반복될 수 있으며, 성공 전까지 최신 상태 미확인 표시를 유지한다. [Google Cloud Storage의 오류 분류 사례](https://docs.cloud.google.com/storage/docs/retry-strategy)를 참고한 프로젝트 선택이지 모든 HTTP 요청의 필수 규칙은 아니다. 해당 사례의 횟수·시간 설정이나 쓰기 재시도 정책은 가져오지 않는다. 오류 응답 본문을 해석하지 못해도 수신한 HTTP 상태는 보존해 판정해야 하며, 408 응답과 브라우저의 요청 대기시간 제한은 구분한다. 오류 정보 보존·재시도 구현과 실제 실패 검증은 남아 있다.

[서버 안내 존중](https://learn.microsoft.com/en-us/azure/architecture/antipatterns/retry-storm/)과 [재시도 시각 분산](https://learn.microsoft.com/en-us/azure/architecture/best-practices/transient-faults)을 참고했으며, 합산 방식은 표준의 필수 공식이 아닌 프로젝트 선택이다. 설명에 쓴 60초는 예시일 뿐 새 기본값이 아니다. 숨김·종료·권한 처리와 재시도 대상 제한은 유지하고, 새 이벤트가 기존 대기를 우회하거나 별도 재시도를 만들지 않게 한다. 현재 코드의 헤더 보존·해석과 브라우저 검증은 남아 있다.

HTTP 재조회와 사건·계정 SSE의 상태를 구분하고 정상인 다른 갱신까지 멈추지 않는다. 최초 조회에 성공한 자료가 없으면 로딩·실패 상태를 표시한다. 종료·권한 거부·로그아웃·파기나 정상 응답의 빈 자료를 과거 값으로 되살리는 근거로 사용하지 않는다. 마지막 조회 성공 시각은 아래 합의에 따라 표시한다. 구체적인 문구·배치는 구현 화면에서 확인하며, 구현·브라우저 검증 전 합의다.
- **장애 안내의 조회 시각 합의 (2026-09-25)**: 갱신 장애 안내에 브라우저가 상황판 HTTP 조회에 마지막으로 성공한 시각을 함께 표시한다. 이전 자료를 참고하는 지휘관이 서버 자료를 언제 확인했는지 알 수 있도록 하려는 선택이다. 서버 응답 조립 시각인 `serverTs`, SSE 수신·GPS 기록·지도 표시 완료 시각과 구분하며, 실패·연결 확인 신호·캐시 자료 재표시만으로 갱신하지 않는다. 최초 조회도 성공하지 않았다면 성공 시각을 만들어 표시하지 않는다. 최근 조회 성공이 모든 업무폰의 GPS 기록이나 SSE 연결의 정상 상태를 보장하지는 않는다. `갱신 지연 · 마지막 조회 성공 14:03`은 설명용 예시이며, 표시 문구·배치와 실제 동작 검증은 남아 있다.
- `BoardRefetchGuard`의 중복·오래된 버전·누락 판정은 기존 테스트에서 호출한다. `src/main`의 실제 호출부는 찾지 못했다. 이 대역 기반 검증이 실제 이벤트 전달·화면 갱신까지 보장한다고 설명하지 않는다.
- **확인할 값의 의미**: 현재 여러 행의 `latestEventId`는 실제 발행 UUID 조회가 아니라 ID·버전으로 만든 문자열이다. `geometryHash`도 좌표 자체가 아닌 ID·상태·버전 해시를 합친 값이다. 원문의 ‘REST·SSE의 동일 이벤트 추적’·‘좌표 원본 불변 검증’이 이 필드만으로 충족됐다고 판단하지 않는다. 공개 필드는 이번 정리에서 바꾸지 않았다.

## 사건 종료와 빈 응답의 구분

- **기존 요구**: 종료·파기된 사건은 허용된 종료 정보만 표시하고 실시간 위치·개인정보·패키지 재적재·재구독을 노출하지 않는다. 허용 정보는 사건 ID, 종료·파기 상태와 시각, 쓰기 불가 이유, 로컬 파기 상태다. 종료와 실제 데이터 삭제는 [데이터 파기](data-retention.md)에서 구분한다.
- **알림 종료 범위 합의 (2026-09-24)**: 종료 정보만 표시하는 기준을 알림에도 적용한다. 목록 열람·확인 상태 변경의 중단과 기록 보존·파기의 구분은 [알림 합의](event-delivery.md#알림-목록과-확인-상태)를 따른다. 구현·검증 전 합의다.
- **현재 차이**: 서버는 종료 정보의 필드를 제한하고 업무폰 최신성 행을 숨기지만, 데이터 수집기는 경로·마커 등 나머지 조회도 계속 호출한다. 종료 정보가 있다는 이유만으로 전체 응답의 위치·개인정보가 제거되는 것은 아니다.
- [화면의 이전 값 병합](../../frontend/src/features/board/model/incidentBoardMerge.ts)은 주요 슬롯이 비면 이전 값을 되살린다. 삭제·종료로 의도적으로 비운 결과와 일시 조회 누락을 구분하지 않으므로 별도 재현·검증이 필요하다. 구독 중단·종료 배너만으로 데이터 제거까지 완료됐다고 보지 않는다.

## 화면과 관측에서 남은 요구

- 슬롯 이름과 연결은 [서버 등록부](../../backend/src/main/java/com/surimap/board/BoardSlotRegistry.java)와 실제 화면 소비자를 확인한다. `marker`는 원본 마커 표시, `marker_notification`은 지원 요청·발견 알림 데이터다. 알림을 토스트·팝업 중 무엇으로 보여주는지는 별도 책임이며 옛 Lane 소유권 표로 현재 UI 수정 범위를 제한하지 않는다.
- 업무폰 최신성은 색뿐 아니라 외곽선·경과 시간으로 구분한다. 미완료 패키지 경고, 차수·인수인계 메모·수색 이력의 연결을 유지한다. 타일 실패 때 가능한 업무 레이어를 보존하고, 요약 실패가 차수 비교·메모 조회까지 막지 않게 하는 것이 기존 요구다. 최초 지도 범위는 전체 수색 범위 → 최근 활동 → 기본 지역 순으로 정했던 배경을 보존한다.
- 원문의 조회 p95 2초·온라인 반영 3초는 과거 시험 목표다. 이번에 측정하거나 운영 기준으로 확정하지 않았다. 조회 지연, 슬롯별 조립 실패, 재조회 이유·마지막 수신 순번·응답 버전의 관측 여부를 [Issue #8](../issues/8-gps-collection-transmission-basis.md)의 후속 시험에서 따로 확인한다.

## 테스트 입력과 원문

- [공용 JSON](../../test-fixtures/common-fixtures.json)의 `boardAssembly`를 기존 상황판 테스트가 직접 읽도록 바꿨다. 13개 슬롯 행과 응답 ID·버전·시각은 원문과 일치한다. 사건 ID는 같은 파일의 `incidentSeed`를 재사용한다. 기존 `sourceSpec`·fixture ID·값은 유지했다.
- 공용 JSON에 상세 값이 없던 중복·오래된 버전·선행 순번 누락·재전송 불가·재조회 지연 5개 입력은 [테스트 리소스](../../backend/src/test/resources/board-api-assembly-failures.json)에 원문 그대로 보존했다. 기존 테스트의 기대값·검증 범위는 바꾸지 않았다.
- 원문의 `latestEventId` UUID 형식 설명과 fixture의 `evt-*` 값, 종료 fixture에 남은 위치 행 등은 일치하지 않는다. 이를 문서 정리 과정에서 새로운 API 요구로 확정하거나 데이터를 자동 수정하지 않는다. 코드·입력의 모호한 이름은 [정리 후보](../refactoring/codebase-naming-candidates.md)에서 추적한다.
- 과거 응답 schema·슬롯별 요구·실패 사례·테스트 계획은 [S3-2 원문](https://github.com/sonic8-8/suri-map/blob/28f8d4dfc13096295142e3b807e1bc869ad268cf/docs/spec/specs/S3-2.json)에서 복원한다. 이 기록이 구현·브라우저 검증 완료를 뜻하지 않는다.
