# 상황판 조회와 갱신

상황판의 데이터 조립·실시간 갱신·수색 차수 비교·사건 종료 표시를 바꿀 때 확인한다. 옛 S3-2 요구와 2026-09-21 정적 코드 대조 결과다. 테스트용 조립 결과와 실제 HTTP·SSE·브라우저 동작을 구분한다.

## 원본을 바꾸지 않는 조회

- 상황판은 사건·구역·경로·마커·업무폰·오프라인 패키지·차수·인수인계 정보를 모아 보여준다. 차수 비교, 필터, 단순 지도, 현재 계정·이동 유형 강조는 표시만 바꾼다. 원본 좌표·상태·버전을 수정하거나 다음 수색 구역·누락·위험도를 자동 판단하지 않는다. 마커 수정·삭제는 해당 기능의 API를 호출한다.
- [Controller](../../backend/src/main/java/com/surimap/board/IncidentBoardController.java)는 `/api/incidents/{incidentId}/board`에서 웹 채널·사건 접근·위치 조회 기록을 요구한다. [조회 서비스](../../backend/src/main/java/com/surimap/board/IncidentBoardQueryService.java) → [데이터 수집](../../backend/src/main/java/com/surimap/board/DefaultIncidentBoardSourceRowCollector.java) → [응답 조립](../../backend/src/main/java/com/surimap/board/BoardAssembler.java) 순서다. 애노테이션 선언만으로 사건별 권한 검사까지 완료됐다고 판단하지 않으며 [인증의 차이](authentication.md)를 함께 확인한다.
- `opIds`·`includeSlots`로 조회 범위를 지정한다. `sinceVersion`은 상황판 전체 응답의 이전 버전이지 각 원본 행의 증분 조회 기준이 아니다. 현재 수집기는 이 값으로 원본 행을 걸러내지 않는다. 서로 다른 원본의 버전을 하나의 순번처럼 비교하지 않는다.

## 이벤트 수신과 최신 데이터 재조회

- **기존 요구**: 동일한 `eventId`는 중복 적용하지 않고 오래된 이벤트가 최신 화면을 되돌리지 않게 한다. 재전송이 불가능하거나 순번 누락을 확인하면 전체 조회로 복구한다. SSE `id`는 사건별 재전송 순번이며 `data.eventId`와 다르다.
- [현재 화면 구독](../../frontend/src/features/situationBoard/presentation/hooks/useSituationBoardData.ts)은 연결 성공·새 이벤트·재조회 요구 시 React Query 캐시를 무효화해 REST 재조회를 요청한다. 이벤트 payload를 곧바로 모든 지도 행에 덮어쓰는 구조가 아니다. `eventId` 중복은 Set으로 막지만 순번 간격을 직접 검사하지는 않는다. 재시작·놓친 알림 복구 범위는 [이벤트 전달](event-delivery.md)에서 확인한다.
- **지도 갱신용 재조회 합의 (2026-09-24)**: 진행 중인 조회가 없으면 바로 요청한다. 조회 중 새 변경이 들어오면 현재 요청을 취소하지 않고 추가 변경이 있었다는 사실을 기억한다. 조회가 성공하면 그동안 받은 여러 변경을 후속 조회 하나로 합친다. 후속 조회 중에도 변경이 들어오면 같은 기준을 적용하며, 전체 요청을 두 번으로 제한하지 않는다. 같은 계정·사건·조회 조건의 일반 갱신 요청에만 적용하고, 개별 알림 처리나 종료·권한 처리를 미루지 않는다. 새 변경 반영이 현재 조회 완료까지 늦어질 수 있는 선택이다. 일시적 조회 실패·요청 시간 제한과 일반적인 사건 전환은 아래 합의를 따른다. 계정·권한·종료 처리는 별도로 구분한다. 로컬 구현 범위는 아래 기록을 따르며, 실제 서버의 요청 수·지도 반영 시간 검증은 남아 있다.
- **재조회 합치기 구현·로컬 검증 (2026-10-01)**: [공통 재조회 함수](../../frontend/src/features/board/api/incidentBoardApi.ts)의 같은 QueryClient·조회 키에는 진행 중 요청과 후속 요청 하나만 둔다. SSE 연결·새 이벤트·재전송 불가와 구역·마커·경로·인수인계 저장 후 갱신을 이 함수로 모았다. 실제 QueryClient·상황판 훅과 HTTP 응답 대역을 연결한 [회귀 테스트](../../frontend/src/features/situationBoard/presentation/hooks/useSituationBoardData.test.ts)에서, 첫 응답 전 50개 요청이 시작되던 입력이 요청 1개와 완료 후 후속 조회 1개로 처리됐다. 후속 조회 중 추가 변경, 저장 완료 처리, 마지막 화면 이탈 시 HTTP 취소, 다른 화면이 같은 조회를 쓰는 경우의 유지, SSE 401·403 취소와 종료 이벤트의 구독 중단·최종 조회도 확인했다. 실패하면 이전 자료와 오류를 표시하고 즉시 후속 조회를 반복하지 않는다. 아래의 자동 재시도·시간 제한·오프라인 정책 전체와 계정 전환은 이번 검증 범위가 아니다. Frontend 279개 테스트·타입 검사·빌드 통과이며, 배포·실제 DB 대기 오류 해소·지도 표시 완료는 미검증이다. 발견한 문제는 [로컬 이슈 18](../issues/local/18-board-read-timeout-with-accumulated-paths.md)에 남겼다.
- **지도 조회 실패의 복구 합의 (2026-09-24)**: 해당 상황판을 사용하는 동안 재시도 가능한 일시적 HTTP 조회 실패는 횟수·총시간 제한 없이 간격을 두고 다시 조회한다. 새 이벤트나 사용자의 조작이 없어도 복구하려는 선택이며, 장애가 길어지면 재시도 요청도 계속 발생한다. 조회가 회복되면 실패 복구를 끝내고 일반 갱신 흐름으로 돌아간다. 정상 상태에서도 계속 조회하는 주기적 조회를 추가한 것은 아니다. 반영하지 못한 변경과 최신 상태 미확인 표시는 유지하고, 이벤트마다 별도 재시도 작업을 만들지 않는다. 정상인 SSE를 HTTP 실패 때문에 다시 연결하지 않으며, 권한 거부·로그아웃·사건 종료·화면 이탈은 별도로 처리한다. 재시도 대상·간격·숨김·오프라인 판정·서버 지정 대기시간과 요청 시간 제한은 아래 합의를 따른다. 구체적인 요청 제한시간 값은 아직 미정이다. 구현·장애 복구 검증 전 합의다.
- **지도 조회 재시도 간격 합의 (2026-09-24)**: 실패 후 다음 시도까지 `1–2초 → 2–4초 → 4–8초 → 8–16초 → 이후 15–30초` 범위에서 매번 무작위로 기다린다. 여러 상황판의 요청 시각을 분산하려고 [SSE 재연결 초기값](event-delivery.md#연결-정리의-검증-범위)을 HTTP 조회에도 재사용한 선택이며, HTTP 표준의 권장 시간이나 검증된 운영값은 아니다. 첫 정상 조회는 지연하지 않는다. 대기시간에 요청 처리 시간·브라우저 실행 지연은 포함하지 않으며, 30초 안에 복구된다는 보장이 아니다. HTTP 조회와 SSE의 실패 횟수·대기 상태는 각각 관리하고, SSE의 60초 정상 수신 후 초기화 기준을 HTTP 조회에 적용하지 않는다. 구현·장애 복구 시험 후 조정한다.
- **숨겨진 탭의 조회 재시도 합의 (2026-09-25)**: 브라우저가 숨김으로 판단한 탭에서는 실패한 지도 조회의 다음 재시도를 보류한다. 탭에 돌아왔을 때 기존 대기시간이 지났으면 다른 재시도 조건을 충족하는 대로 이어가고, 남아 있으면 마저 기다린다. 숨김·복귀만으로 실패 횟수나 대기시간을 초기화하지 않는다. 보지 않는 상황판의 반복 요청을 줄이는 선택이며, 복귀 후 조회가 성공할 때까지 이전 자료와 최신 상태 미확인 표시를 유지한다. 단순 입력 포커스 변경은 숨김이 아니고, 이미 진행 중인 요청·SSE 수신을 숨김만으로 취소하거나 종료·권한 처리를 미루지 않는다. 모든 최초 조회·일반 이벤트 조회를 숨김 중 금지한다는 합의는 아니다. 현재 상황판은 `retry: false`이므로 이 실패 재시도 동작의 구현·브라우저 검증은 남아 있다.
- **오프라인 판정과 지도 조회 합의 (2026-09-25)**: 브라우저가 오프라인이라고 알려도 필요한 지도 HTTP 조회와 재시도를 그 판정만으로 막지 않는다. 지휘 상황판의 자동 복구가 브라우저의 잘못된 판정 때문에 멈추지 않도록 하는 선택이며, 실제 연결이 끊겼을 때 실패하는 시도도 발생한다. 최초 조회와 실패 복구에 적용하되 정상 상태의 주기적 조회는 추가하지 않는다. 합의한 재시도 간격·숨김 보류·종료·권한 처리를 유지하며, 실제 조회 성공으로 복구 여부를 판단한다. [TanStack Query의 기본 online 모드](https://tanstack.com/query/latest/docs/framework/react/guides/network-mode)와 다른 프로젝트 선택이다. 조회별 설정을 사용하고 기존 온라인 복귀 시 재조회까지 제거하지 않는다. 모든 API·쓰기·SSE 연결에 적용하는 전역 정책으로 확대하지 않으며, 구현·브라우저 검증은 남아 있다.
- **지도 조회 재시도 대상 합의 (2026-09-25)**: 통신 실패와 HTTP `408·429·500·502·503·504`를 자동 재시도 대상으로 삼는다. 인증·권한 오류, 사건 종료, 의도적인 요청 취소, 정상 응답의 데이터 형식 오류·프로그래밍 오류는 제외한다. 500만으로 일시적 장애와 지속적인 코드 결함을 구분할 수는 없지만, 서버 회복 후 조회가 자동 복구되도록 포함했다. 코드 결함이면 실패 요청도 반복될 수 있으며, 성공 전까지 최신 상태 미확인 표시를 유지한다. [Google Cloud Storage의 오류 분류 사례](https://docs.cloud.google.com/storage/docs/retry-strategy)를 참고한 프로젝트 선택이지 모든 HTTP 요청의 필수 규칙은 아니다. 해당 사례의 횟수·시간 설정이나 쓰기 재시도 정책은 가져오지 않는다. 오류 응답 본문을 해석하지 못해도 수신한 HTTP 상태는 보존해 판정해야 하며, 408 응답과 브라우저의 요청 대기시간 제한은 구분한다. 오류 정보 보존·재시도 구현과 실제 실패 검증은 남아 있다.
- **서버 지정 재시도 대기 합의 (2026-09-25)**: 재시도 대상 오류에 유효한 `Retry-After`가 있으면 서버가 안내한 대기시간에 해당 단계의 기존 무작위 대기를 더한다. 서버 안내가 길어도 요청 시각을 분산하려는 선택이며, 두 시간 중 긴 쪽만 기다릴 때보다 복구가 늦어질 수 있다. 서버 대기를 기존 30초 상한으로 줄이지 않는다. 헤더가 없거나 유효하지 않거나 안내 시각이 이미 지났으면 기존 무작위 대기를 적용한다. [서버 안내 존중](https://learn.microsoft.com/en-us/azure/architecture/antipatterns/retry-storm/)과 [재시도 시각 분산](https://learn.microsoft.com/en-us/azure/architecture/best-practices/transient-faults)을 참고했으며, 합산 방식은 표준의 필수 공식이 아닌 프로젝트 선택이다. 설명에 쓴 60초는 예시일 뿐 새 기본값이 아니다. 숨김·종료·권한 처리와 재시도 대상 제한은 유지하고, 새 이벤트가 기존 대기를 우회하거나 별도 재시도를 만들지 않게 한다. 현재 코드의 헤더 보존·해석과 브라우저 검증은 남아 있다.
- **지도 조회 요청 시간 제한 합의 (2026-09-25)**: 상황판 HTTP 조회 한 번마다 프런트엔드 대기 한도를 둔다. 한도를 넘으면 진행 중인 브라우저 요청·응답 본문 수신을 취소하고, 해당 상황판을 사용하는 동안 합의한 간격과 조건으로 다시 조회한다. 시간 초과는 복구 대상으로 삼되 화면 이탈·로그아웃 등의 의도적 취소와 구분한다. 반영하지 못한 변경·최신 상태 미확인 표시와 하나의 복구 흐름을 유지하며, 정상인 SSE를 다시 연결하지 않는다. 브라우저 요청 취소가 서버·SQL 작업 중단까지 보장하지는 않는다. [AWS의 클라이언트 시간 제한 지침](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_client_timeouts.html)을 참고했으며, 구체적인 시간 값은 아직 미정이다. SSE·SQL·k6의 시간 값이나 전체 복구 기한을 채택한 것이 아니다. 구현·실제 무응답 복구 검증은 남아 있다.
- **요청 제한시간 초깃값 결정 순서 (2026-09-25)**: 일반적인 상황판 조회와 데이터가 많이 쌓인 조회의 응답 시간을 먼저 측정한 뒤 초깃값을 함께 정한다. 느리지만 정상인 요청을 불필요하게 취소하지 않으려는 선택이며, 기존 GPS 저장 시험의 응답 시간·제한시간을 대신 사용하지 않는다. 측정만으로 적정값이 자동 결정되는 것은 아니므로 시험 조건과 한계를 함께 확인한다. 구체적인 시간 값·측정 조건과 실행은 아직 미정이며, 이번 합의로 부하테스트나 구현을 시작한 것은 아니다.
- **사건 전환 시 조회 취소 합의 (2026-09-25)**: 다른 사건으로 이동해 이전 조회를 더 이상 사용하는 화면이 없으면 진행 중인 브라우저 HTTP 요청을 취소하고, 그 조회의 후속 갱신·재시도를 끝낸다. 이전 응답·미반영 변경·재시도 상태를 새 사건에 섞지 않으며 돌아오면 필요에 따라 다시 조회한다. 다른 화면이 같은 조회를 여전히 사용하면 함께 취소하지 않고, 단순 탭 숨김에도 적용하지 않는다. 이미 받아둔 캐시나 DB 기록을 모두 삭제한다는 선택은 아니며, 브라우저 취소가 서버·SQL 중단을 보장하지는 않는다. 로그아웃·권한 거부·종료·파기 처리는 이 일반 이동 정책과 구분한다. HTTP 취소 신호는 2026-10-01 연결했으며, 실제 브라우저 검증은 남아 있다.
- **통신 장애 중 표시 합의 (2026-09-24)**: 진행 중이며 조회가 허용된 사건에서 일시적인 통신 장애가 발생하면 마지막으로 조회한 경로·마커·알림을 유지한다. 최신 상태를 확인하지 못하고 있음을 명확히 표시하고, 지도 확대 상태에서도 안내를 숨기지 않는다. 마지막으로 확인된 수색 상황을 참고할 수 있게 하는 선택이며, 이전 자료를 현재 상태처럼 표시하지 않는다. HTTP 재조회와 사건·계정 SSE의 상태를 구분하고 정상인 다른 갱신까지 멈추지 않는다. 최초 조회에 성공한 자료가 없으면 로딩·실패 상태를 표시한다. 종료·권한 거부·로그아웃·파기나 정상 응답의 빈 자료를 과거 값으로 되살리는 근거로 사용하지 않는다. 마지막 조회 성공 시각은 아래 합의에 따라 표시한다. 구체적인 문구·배치는 구현 화면에서 확인하며, 구현·브라우저 검증 전 합의다.
- **장애 안내의 조회 시각 합의 (2026-09-25)**: 갱신 장애 안내에 브라우저가 상황판 HTTP 조회에 마지막으로 성공한 시각을 함께 표시한다. 이전 자료를 참고하는 지휘관이 서버 자료를 언제 확인했는지 알 수 있도록 하려는 선택이다. 서버 응답 조립 시각인 `serverTs`, SSE 수신·GPS 기록·지도 표시 완료 시각과 구분하며, 실패·연결 확인 신호·캐시 자료 재표시만으로 갱신하지 않는다. 최초 조회도 성공하지 않았다면 성공 시각을 만들어 표시하지 않는다. 최근 조회 성공이 모든 업무폰의 GPS 기록이나 SSE 연결의 정상 상태를 보장하지는 않는다. `갱신 지연 · 마지막 조회 성공 14:03`은 설명용 예시이며, 표시 문구·배치와 실제 동작 검증은 남아 있다.
- `BoardRefetchGuard`의 중복·오래된 버전·누락 판정은 기존 테스트에서 호출한다. `src/main`의 실제 호출부는 찾지 못했다. 이 대역 기반 검증이 실제 이벤트 전달·화면 갱신까지 보장한다고 설명하지 않는다.
- **확인할 값의 의미**: 현재 여러 행의 `latestEventId`는 실제 발행 UUID 조회가 아니라 ID·버전으로 만든 문자열이다. `geometryHash`도 좌표 자체가 아닌 ID·상태·버전 해시를 합친 값이다. 원문의 ‘REST·SSE의 동일 이벤트 추적’·‘좌표 원본 불변 검증’이 이 필드만으로 충족됐다고 판단하지 않는다. 공개 필드는 이번 정리에서 바꾸지 않았다.

## 사건 종료와 빈 응답의 구분

- **기존 요구**: 종료·파기된 사건은 허용된 종료 정보만 표시하고 실시간 위치·개인정보·패키지 재적재·재구독을 노출하지 않는다. 허용 정보는 사건 ID, 종료·파기 상태와 시각, 쓰기 불가 이유, 로컬 파기 상태다. 종료와 실제 데이터 삭제는 [데이터 파기](data-retention.md)에서 구분한다.
- **알림 종료 범위 합의 (2026-09-24)**: 종료 정보만 표시하는 기준을 알림에도 적용한다. 목록 열람·확인 상태 변경의 중단과 기록 보존·파기의 구분은 [알림 합의](event-delivery.md#알림-목록과-확인-상태)를 따른다. 구현·검증 전 합의다.
- **현재 차이**: 서버는 종료 정보의 필드를 제한하고 업무폰 최신성 행을 숨기지만, 데이터 수집기는 경로·마커 등 나머지 조회도 계속 호출한다. 종료 정보가 있다는 이유만으로 전체 응답의 위치·개인정보가 제거되는 것은 아니다.
- [화면의 이전 값 병합](../../frontend/src/features/board/model/incidentBoardMerge.ts)은 주요 슬롯이 비면 이전 값을 되살린다. 삭제·종료로 의도적으로 비운 결과와 일시 조회 누락을 구분하지 않으므로 별도 재현·검증이 필요하다. 구독 중단·종료 배너만으로 데이터 제거까지 완료됐다고 보지 않는다.

## 화면과 관측에서 남은 요구

- 슬롯 이름과 연결은 [서버 등록부](../../backend/src/main/java/com/surimap/board/BoardSlotRegistry.java)와 실제 화면 소비자를 확인한다. `marker`는 원본 마커 표시, `marker_notification`은 지원 요청·발견 알림 데이터다. 알림을 토스트·팝업 중 무엇으로 보여주는지는 별도 책임이며 옛 Lane 소유권 표로 현재 UI 수정 범위를 제한하지 않는다.
- 업무폰 최신성은 색뿐 아니라 외곽선·경과 시간으로 구분한다. 미완료 패키지 경고, 차수·인수인계 메모·수색 이력의 연결을 유지한다. 타일 실패 때 가능한 업무 레이어를 보존하고, 요약 실패가 차수 비교·메모 조회까지 막지 않게 하는 것이 기존 요구다. 최초 지도 범위는 전체 수색 범위 → 최근 활동 → 기본 지역 순으로 정했던 배경을 보존한다.
- 원문의 조회 p95 2초·온라인 반영 3초는 과거 시험 목표다. 이번에 측정하거나 운영 기준으로 확정하지 않았다. 조회 지연, 슬롯별 조립 실패, 재조회 이유·마지막 수신 순번·응답 버전의 관측 여부를 [Issue #8](../issues/8-gps-collection-transmission-basis.md)의 후속 시험에서 따로 확인한다.

## 테스트 입력과 원문

- [공용 JSON](../../test-fixtures/common-fixtures.json)의 `boardAssembly`를 기존 상황판 테스트가 직접 읽도록 바꿨다. 13개 슬롯 행과 응답 ID·버전·시각은 원문과 일치한다. 사건 ID는 같은 파일의 `incidentSeed`를 재사용한다. 기존 `sourceSpec`·fixture ID·값은 유지했다.
- 공용 JSON에 상세 값이 없던 중복·오래된 버전·선행 순번 누락·재전송 불가·재조회 지연 5개 입력은 [테스트 리소스](../../backend/src/test/resources/board-api-assembly-failures.json)에 원문 그대로 보존했다. 기존 테스트의 기대값·검증 범위는 바꾸지 않았다.
- 원문의 `latestEventId` UUID 형식 설명과 fixture의 `evt-*` 값, 종료 fixture에 남은 위치 행 등은 일치하지 않는다. 이를 문서 정리 과정에서 새로운 API 요구로 확정하거나 데이터를 자동 수정하지 않는다. 코드·입력의 모호한 이름은 [정리 후보](../refactoring/codebase-naming-candidates.md)에서 추적한다.
- 과거 응답 schema·슬롯별 요구·실패 사례·테스트 계획은 [S3-2 원문](https://github.com/sonic8-8/suri-map/blob/28f8d4dfc13096295142e3b807e1bc869ad268cf/docs/spec/specs/S3-2.json)에서 복원한다. 이 기록이 구현·브라우저 검증 완료를 뜻하지 않는다.
