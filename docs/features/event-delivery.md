# 이벤트 전달과 재전송

SSE·FCM의 재연결, 실패 복구, 사건 종료 처리를 변경할 때 확인할 기록이다. 옛 S4의 동작 요구와 현재 구현의 차이를 보존한다. 아래의 **기존 요구**는 후속 작업에서 유효성과 범위를 다시 확인할 대상이며, 이번 문서 정리로 새 구현 기준을 확정한 것은 아니다.

현재 구현 설명은 2026-09-18 코드 대조를 기본으로 하며, 추가 대조 시점은 해당 항목에 표시했다. 날짜가 붙은 단계별 기록은 당시 상태다. DB 재전송은 아래 **DB 페이지 재전송 연결(2026-09-28)**, 이후 전송 수정·배포는 **실시간 전송 분리(2026-09-29)**를 따른다. 실제 FCM 전달·모든 종료 경합·부하 검증까지 완료했다는 뜻은 아니다.

**설계 판단 기준 (2026-09-23)**: [현장 수색자와 지휘관](../prd.md)이 장시간 수색과 불안정한 통신 환경에서 사용한다는 전제로 판단한다. 알림 보존·복구와 저장 상태의 명확성을 구현 편의보다 우선하며, 필요한 신뢰성을 충족하는 범위에서 구현을 단순화한다.

## SSE 이름과 책임 배치 (2026-09-30)

`eventhub`의 운영 코드를 역할별 기존 계층으로 옮겼다. 아래 이름은 현재 코드 기준이며, 날짜가 붙은 과거 기록의 클래스명은 당시 이름이다.

| 책임 | 현재 위치·주요 클래스 |
|---|---|
| HTTP 구독 요청 | `api/controller/sse/ServerSentEventController` |
| 상황판 구독·이력 조회 | `api/service/sse/ServerSentEventSubscriptionService`, `ServerSentEventHistoryService` |
| 연결·응답 쓰기·메시지 형식 | `global/sse/ServerSentEventConnectionRegistry`, `ServerSentEventConnection`, `ServerSentEventStream`, `ServerSentEventMessage`, `ServerSentEventFormatter` |
| DB 전송 작업·실시간 전달 | `global/sse/ServerSentEventJob`, `ServerSentEventJobService`, `ServerSentEventJobWorker`, `ServerSentEventJobMapper` |
| 공용 이벤트 발행·입력 검사 | `global/event/EventPublisher`, `DatabaseEventPublisher`, `CapturingEventPublisher`, `EventPublishRequest`, `EventPublishRequestValidator` |

Worker가 DB 순번 확정·커밋 뒤 실시간 전달을 조율하며 웹 구독 서비스에 의존하지 않는다. 구독 서비스는 연결 등록·이력 조회·전송 시작을 맡는다. 두 경로의 일반 이벤트는 기존 DB 상태 검사를 사용하고 종료·파기 알림의 예외 처리를 유지한다.

발행 입력·메시지는 `class`로 작성하고 값 동등성·기존 JSON 필드를 보존했다. 기록용 발행자는 중복 `CapturedPublish` 대신 입력 객체를 기록한다. 재조회가 필요한 요청의 HTTP 409 JSON 변환은 `GlobalExceptionHandler`로 모았으며, 전송 시작 뒤의 종료·복구 처리는 스트림에 남겼다.

URL·SSE 이벤트명·DB 테이블과 컬럼·설정 키·권한 정책·보관 기간은 변경하지 않았다. 배포·브라우저 재검증은 하지 않았다.

검증 결과: Docker 연결 복구 후 컨테이너에서 `./gradlew --no-daemon test --console=plain`을 실행해 1,348개가 통과했다(4분 45초, 실패·오류·건너뜀 0, 기본 설정의 `performance` 태그 제외). 실제 PostgreSQL/PostGIS를 사용하는 DB 테스트와 HTTP/TCP 스트림 테스트를 포함한다. HTTP 스트림 테스트의 인증 입력·DB 조회에는 대역을 사용하므로 실제 브라우저·인증·DB가 연결된 배포 검증을 대신하지 않는다. 변경된 테스트 이름으로 CI 결과 수집·검증도 통과했고, 결과 파일 누락 시 통과를 거부하는 동작도 확인했다.

## 알림 목록과 확인 상태

**기본 구조 합의 (2026-09-24)**: 종 아이콘·숫자 배지·알림 패널을 기본으로 삼는다. 종 아이콘을 누르면 지도 옆 패널에서 새 알림과 이전 기록을 확인한다. [알림 확인 상태](../../CONTEXT.md)는 같은 계정·사건의 탭에서 공유하며, 다른 계정의 상태까지 바꾸지는 않는다. 탭마다 팝업을 닫거나 넘긴 위치를 복원하는 방식은 제거 대상으로 삼는다. 구현·검증 전 합의다.

**기록 보존 합의 (2026-09-23, 유지)**: 패널을 닫거나 웹페이지를 다시 열어도 [마커 알림 기록](../../CONTEXT.md)은 남아 있고, 웹에서 지난 알림을 다시 조회할 수 있어야 한다. 확인 상태가 바뀌었다고 알림 원문을 삭제하지 않는다. 보존 기간·사건 파기 후 처리는 별도로 정한다.

**사건 종료 후 열람 합의 (2026-09-24)**: 사건이 종료되면 허용된 종료 정보만 표시하고, 알림 목록 열람과 계정별 확인 상태 변경을 중단한다. 종료 후 알림 원문까지 노출하는 기능은 이번 범위에 포함하지 않는다. 앞선 기록 보존 합의가 종료 후 열람 허용을 뜻하지 않으며, 알림 원문·확인 기록의 보존 기간과 파기는 별도로 정한다. 아래의 알림 열람·확인·안내 기준은 조회가 허용되는 사건에 적용한다. 화면·API의 종료 처리와 진행 중이던 요청의 처리는 구현·검증이 필요하다.

**조회 권한 합의 (2026-09-23, 유지)**: 조회 시점에 해당 사건·알림 유형의 조회 권한이 있으면 배정 전에 발생한 알림도 목록에서 볼 수 있다. 인수인계받은 지휘관도 이전 지원 요청·발견 내용을 확인할 수 있도록, 발생 당시 수신 대상에 포함됐는지로 목록을 제한하지 않는다. 알림 발송 대상은 바꾸지 않으며, 구현·권한 검증 전 합의다.

**발생 당시 내용 보존 (2026-09-23, 유지)**: 마커가 수정·삭제돼도 알림 목록에는 발생 당시 원문을 유지한다. 원문의 유형·업무폰·기록 시각·위치를 최신 마커 정보로 덮어쓰지 않고, 현재 마커의 수정·삭제 상태를 별도로 구분한다. 개별 마커 삭제를 이유로 알림 목록에서 제외하지 않는다. 사건 자료의 보존·파기 정책까지 확정한 것은 아니며, 구현·검증 전 합의다.

**대체한 설계 (2026-09-24)**: 같은 사용자의 알림 확인 상태가 탭마다 달라지는 혼선을 없애기 위해, 계정별 확인 상태를 제외했던 결정과 탭별 팝업 대기열·닫기/넘김 복구 설계를 대체했다. 팝업의 첫 접속·표시 순서·재표시 기준을 패널에 그대로 적용하지 않으며, 닫았던 상황판 선택이나 알림 복구용 화면 ID 설계도 진행하지 않는다. DB 기록 보존과 SSE 재전송 요구는 유지한다.

**배지 숫자 합의 (2026-09-24)**: 종 아이콘의 숫자는 해당 계정·사건의 [미확인 알림 수](../../CONTEXT.md)를 나타낸다. 패널을 열기만 해서는 줄이지 않고, 알림을 확인 처리하면 집계에서 제외한다. 아직 확인하지 않은 지원 요청·발견 알림이 패널을 열었다는 이유만으로 숫자에서 사라지는 것을 막기 위한 선택이다. 알림 원문은 확인 처리 후에도 목록에 남긴다. 구현·검증 전 합의다.

**최초 집계 범위 합의 (2026-09-24)**: 해당 계정·사건의 확인 기록이 없는 첫 사용에는 현재 조회 권한이 있는 보존 중인 과거 알림 전체를 미확인으로 집계한다. 배정 전에 발생했거나 당시 수신 대상에 포함되지 않았던 알림도 포함한다. 인수인계받기 전 알림을 확인 대상으로 드러내는 대신 첫 배지 숫자가 커질 수 있다. 새로고침·재접속·브라우저 데이터 삭제 시에는 서버에 저장된 확인 상태를 복원하며, 이미 확인한 알림을 미확인으로 초기화하지 않는다. 과거 알림을 모두 새 도착 안내로 표시한다는 뜻은 아니며, 구현·검증 전 합의다.

**확인 처리 합의 (2026-09-24)**: 사용자가 알림 항목을 직접 선택해 내용이 표시되면 해당 알림만 확인 처리한다. 별도의 확인 버튼은 요구하지 않는다. 패널 열기·목록 노출·자동 항목 선택·수신만으로 확인 처리하지 않으며, 선택했어도 내용을 표시하지 못했다면 미확인으로 남긴다. 이 상태는 알림을 열어본 기록이지 실제로 내용을 이해했거나 현장 지원을 완료했다는 증거가 아니다. 구현·검증 전 합의다.

**확인 상태 저장 합의 (2026-09-24)**: 알림 원문은 모두 보존하고, 계정이 확인한 알림의 조합만 DB에 별도로 기록한다. 현재 조회 권한이 있는 보존 중인 알림 가운데 해당 계정의 확인 기록이 없는 항목은 미확인으로 판단한다. 조회 실패를 확인 기록 없음으로 취급하지 않으며, 확인 기록이나 발생 당시 수신 대상이 현재 조회 권한을 대신하지 않는다. 계정별 미확인 행을 미리 만들거나 새 배정자의 과거 상태를 채우지 않는 대신, 조회 시 알림 원문과 확인 기록을 대조한다. 기존 알림의 생성·취소 상태와도 분리한다. 구체적인 테이블·컬럼, 중복 저장 방지와 보존·파기 기준은 후속 설계 대상이며, 구현·성능 검증 전 합의다.

**확인 상태 저장의 재시도 합의 (2026-09-24)**: 일시적인 통신 오류로 저장 여부를 알 수 없으면 간격과 횟수를 제한해 자동으로 재시도한다. 계속 확인되지 않으면 사용자가 직접 재시도할 수 있게 한다. 응답만 유실됐을 수 있으므로 같은 확인 요청을 다시 보내도 중복 기록이 생기지 않아야 한다. 저장 미확인 상태를 표시하되 다른 알림의 열람을 막지 않으며, 재시도를 중단했다는 이유만으로 저장 실패나 성공을 단정하지 않는다. 인증 만료·권한 거부 등 재시도로 해결되지 않는 오류는 구분한다. 구체적인 간격·횟수·오류 분류와 화면 종료·계정 전환 시 처리는 아직 정하지 않았다. 구현·검증 전 합의다.

**다른 상황판의 확인 상태 갱신 합의 (2026-09-24)**: 서버가 확인 상태 저장을 커밋한 뒤 기존 계정별 SSE로 같은 계정의 다른 상황판에 변경을 알린다. 사건 전체에 보내는 지도 갱신과 개인 확인 상태의 전달 대상을 분리하기 위한 선택이다. 서버는 인증된 계정을 기준으로 대상을 정하며, 개인 신호를 사건 전체에 보낸 뒤 화면에서 걸러내지 않는다. 신호를 받은 화면은 조회 권한을 확인하는 API로 해당 사건의 최신 확인 상태와 미확인 수를 다시 조회한다. 이 신호는 새 지원 요청·발견 알림이 아니므로 새 도착 안내로 표시하지 않는다. 다른 계정의 확인 상태나 배지 숫자를 바꾸지 않으며, 저장 내용은 DB를 기준으로 확인한다. 연결이 끊겼거나 숨겨졌던 화면은 앞선 재연결·복귀 조회 기준을 따른다. 구독 담당과 재연결 처리의 구체화는 남아 있으며, 즉시 동기화나 복구 완료를 검증한 것은 아니다.

**개인 확인 상태의 재연결 복구 합의 (2026-09-24)**: 계정별 SSE가 다시 연결되면 DB의 최신 확인 상태와 미확인 수를 조회한다. 화면에는 현재 상태가 필요하므로, 전달이 끝난 개인 확인 상태 변경 신호는 재전송용 이력으로 보존하지 않는다. 알림 원문·계정별 확인 기록의 DB 보존과 사건별 SSE의 재전송 합의는 유지한다. 서버가 아직 처리하지 못한 전송 작업의 복구를 생략한다는 뜻은 아니다. 구독·조회 중 변경이 발생해도 누락 없이 반영되는지와 조회 실패 처리는 구현·검증이 필요하다.

**상황판 SSE 연결 구성 합의 (2026-09-24)**: 정상적으로 열린 상황판 하나에서 사건 SSE 1개와 계정 SSE 1개를 사용한다. 사건 이벤트를 한 연결로 받아 지도 갱신과 알림 처리에 각각 전달하고, 사건 연결의 수신 위치·재연결·종료 관리를 한곳으로 모은다. 개인 확인 상태의 변경 신호는 계정 연결로 분리한다. 서로 다른 탭의 연결까지 공유하거나 대표 화면을 선정하는 방식은 도입하지 않는다. 최초 상황판 조회 전 알림 수신, 오류·종료 처리, 한쪽 처리 실패 시 다른 쪽의 누락과 수신 위치 갱신을 함께 검증해야 한다. 연결만 합치는 결정이며 지도·알림 처리 책임이나 사건별 재전송 요구를 제거하지 않는다. 구현·브라우저 검증 전 합의다.

**새 알림 표시 합의 (2026-09-24)**: 새 알림이 도착하면 배지를 갱신하고, 지도 작업을 막지 않는 짧은 안내(토스트)를 함께 표시한다. 지도를 보는 동안에도 지원 요청·발견 알림의 도착을 알아차리도록 돕기 위한 선택이다. 안내가 표시되거나 닫히거나 사라졌다는 이유로 확인 처리하지 않으며, 미확인 알림은 패널에 남는다. 탭별 팝업 대기열·닫기/넘김 복구를 다시 도입하지 않는다. 구현·검증 전 합의다.

**복원한 알림의 안내 합의 (2026-09-24)**: 첫 접속·재연결 후 알림 목록과 확인 상태의 조회가 완료되고 미확인 알림이 있으면, 전체 미확인 수를 한 번 요약해서 안내한다. 과거 알림을 하나씩 새 도착 안내로 띄우지 않는다. 안내의 숫자는 이번에 새로 도착하거나 놓친 개수가 아니며, 개별 내용은 패널에서 확인한다. 안내 표시로 확인 처리하지 않고, 일반 재조회마다 반복해서 안내하지 않는다. 조회 실패를 미확인 0건이나 복원 완료로 표시하지 않는다. 구현·검증 전 합의다.

**안내를 표시할 화면 합의 (2026-09-24)**: 새 알림의 짧은 안내와 복원 후 요약 안내는 브라우저가 표시 중으로 판단한 각 상황판에 표시한다. 숨겨진 탭은 표시 대상에서 제외하되, 입력 포커스가 있는 화면으로만 제한하지 않는다. 상황판 창 두 개가 나란히 보이면 양쪽에서 같은 안내를 볼 수 있다. 다른 작업을 하면서 상황판을 살피는 경우를 고려한 선택이며, 실제로 사용자가 보고 있다는 보장은 아니다. 안내 표시 여부로 이벤트 수신·알림 기록·계정별 확인 상태를 바꾸거나 대표 화면을 따로 선정하지 않는다. 구현·검증 전 합의다.

**탭 복귀 시 안내 합의 (2026-09-24)**: 연결이 유지된 채 숨겨진 탭으로 돌아오면 알림 목록과 계정의 확인 상태를 갱신한다. 숨겨진 동안 추가됐고 아직 미확인인 알림이 있을 때만 전체 미확인 수의 요약 안내를 새로 띄운다. 기존 미확인 알림만 남아 있으면 배지와 목록을 갱신하되 새 요약 안내는 추가하지 않고, 같은 계정의 다른 탭에서 이미 확인한 알림은 안내 조건에서 제외한다. 새 알림 여부를 전체 미확인 수의 증감만으로 판단하지 않는다. 기존 알림의 반복 안내를 줄이기 위한 선택이며, 최초 접속·재연결의 복원 안내는 앞선 합의를 유지한다. 구현·검증 전 합의다.

**비교 정보가 없을 때의 안내 합의 (2026-09-24)**: 현재 알림 목록과 확인 상태의 조회는 완료됐지만 과거와 비교할 정보가 없거나 불완전하면, 미확인 알림이 있을 때 전체 미확인 수를 한 번 요약 안내한다. 이를 새로 도착한 개수라고 표현하지 않는다. 비교 불가를 새 알림 없음으로 취급하지 않는 대신, 이미 알고 있던 알림에 대한 안내가 한 번 더 나타날 수 있다. 일반 재조회마다 반복하는 안내가 아니며, 정상적으로 비교할 수 있을 때는 앞선 탭 복귀 기준을 따른다. 조회·권한 확인 실패를 0건이나 복원 완료로 처리하지 않는다. 구현·검증 전 합의다.

**표시 중인 안내의 일시정지 합의 (2026-09-24)**: 안내가 표시된 도중 탭이 숨겨지면 남은 표시 시간을 멈춘다. 돌아오면 최신 확인 상태를 반영해 아직 미확인인 알림의 안내를 남은 시간만 이어 보여준다. 이미 확인한 알림은 다시 표시하지 않으며, 요약 안내의 숫자도 최신 상태로 갱신한다. 화면이 보이는 동안 입력 포커스만 바뀐 경우에는 시간을 멈추지 않는다. 전체 표시 시간을 처음부터 다시 시작하거나 새로고침 이후까지 타이머를 저장하지 않는다. 이는 현재 열린 페이지에서 이미 시작된 안내를 마무리하는 기준이며, 새 요약 안내가 필요한지는 앞선 복귀·복원 기준으로 판단한다. 구현·검증 전 합의다.

**기존 안내와 새 요약의 처리 합의 (2026-09-24)**: 복귀·복원 후 이어 보여줄 안내와 새 요약 안내가 함께 필요하면, 기존 안내를 최신 전체 미확인 수의 요약 하나로 대체한다. 기존 안내를 끝까지 표시한 뒤 요약을 따로 띄우지 않는다. 전체 미확인 수에 이미 포함된 기존 알림을 다시 더하지 않으며, 개별 내용과 기록은 패널에 남긴다. 안내 대체로 확인 처리하지 않는다. 새 요약이 필요 없는 경우에는 앞선 합의대로 남은 표시 시간만 이어 보여준다. 구현·검증 전 합의다.

**연속 도착 알림의 안내 합의 (2026-09-24)**: 안내가 표시 중일 때 다른 새 알림이 도착하면 전체 미확인 수의 요약 하나로 바꾸고, 이후 도착분도 같은 안내에 반영한다. 개별 안내를 여러 개 쌓거나 순서대로 표시할 대기열을 추가하지 않는다. 숫자는 새로 받은 개수가 아니라 해당 계정·사건의 현재 전체 미확인 수이며, 같은 알림의 재전송으로 중복 집계하지 않는다. 개별 내용과 기록은 패널에 남기고, 안내 갱신만으로 확인 처리하지 않는다. 구현·검증 전 합의다.

**새 알림에 따른 표시 시간 합의 (2026-09-24)**: 다른 새 알림으로 요약을 갱신하면 갱신된 요약이 화면에 표시될 때부터 표시 시간을 다시 센다. 종료 직전에 도착한 알림도 안내할 시간을 확보하는 대신, 알림이 계속 도착하면 안내가 오래 남을 수 있다. 같은 알림의 재전송·일반 재조회·다른 탭의 확인 처리만으로 시간을 다시 시작하지 않는다. 새 요약이 필요 없는 단순 탭 복귀에는 남은 시간만 이어 표시한다. 기본 표시 시간은 아직 정하지 않았으며, 구현·검증 전 합의다.

새 알림 여부를 판별할 비교 기준과 그 정보의 누락·불완전 여부를 확인하는 방법은 아직 정하지 않았다. 안내의 기본 표시 시간·위치·접근성과 반복 재연결 처리도 남아 있다. 배지와 안내만으로 현장 사용성 검증을 대신하지 않는다.

2026-09-24 코드 대조 결과이며, 실제 웹·DB 검증은 아직 하지 않았다.

- [MarkerNotificationService](../../backend/src/main/java/com/surimap/app/service/marker/MarkerNotificationService.java)는 알림 원문·당시 수신 대상·시각을 `marker_notification`에 저장한다. 알림 발생 기록이지 계정별 수신·표시·읽음 확인 기록은 아니다.
- [알림 조회 SQL](../../backend/src/main/resources/mapper/marker/MarkerNotificationMapper.xml)은 사건별 알림을 [상황판 응답 조립](../../backend/src/main/java/com/surimap/board/DefaultIncidentBoardSourceRowCollector.java)에 제공한다. 원문·수신 대상이 빠진 요약 조회이며 현재 계정별 수신 대상 필터도 없다. 이를 그대로 개인 알림 목록 API로 간주하지 않는다. 2026-09-25 추가 대조에서 `latest_event_id`는 완료 상태와 무관하게 `event_dispatch_job`에서 보충함을 확인했다. 재전송 대상에서 제외하는 것과 행을 삭제하는 것은 다르며, 이력 삭제 시 추적값에 미치는 영향도 확인해야 한다.
- 웹의 [팝업 목록](../../frontend/src/app/useMarkerNotificationQueue.ts)은 메모리에만 있다. 닫기는 이 목록을 비우며 DB 삭제를 호출하지 않는다. 종 아이콘·알림 숫자 배지·이력 패널과 계정별 확인 상태의 저장·탭 동기화는 확인하지 못했다. 현재 팝업의 숫자는 미확인 개수가 아니라 선택 위치와 목록 길이다.
- [SSE 연결 관리](../../backend/src/main/java/com/surimap/global/sse/ServerSentEventConnectionRegistry.java)에는 사건별 연결과 계정별 연결이 따로 있다. 웹의 계정 SSE 구독은 [사건 목록 페이지](../../frontend/src/features/incidents/presentation/pages/IncidentListPage.tsx)에 연결돼 있으며, 상황판의 알림 확인 상태 동기화로 연결된 것은 아니다. [공통 전송 경로](../../backend/src/main/java/com/surimap/api/service/sse/ServerSentEventSubscriptionService.java)는 사건 전체에 먼저 전달하므로, 향후 개인 확인 상태의 변경 신호를 추가할 때는 전달·재전송 대상을 분리해야 한다. 계정 SSE의 재연결·복구도 별도 보완이 필요하다. 정적 코드 대조이며 새 동기화를 구현·검증한 결과가 아니다.

## 합의한 복구 대상

연결 끊김이나 서버 재시작 후 **최신 지도와 놓친 지원 요청·발견 알림을 함께 복구한다**는 2026-09-22 합의는 유지한다. 알림은 탭별 팝업을 다시 띄우는 방식 대신, 저장된 목록과 계정 기준 확인 상태를 복원하는 방향으로 구현한다.

- 같은 브라우저에서 새로고침하거나 닫았다 다시 열어도, 같은 계정·사건의 알림 목록과 저장된 확인 상태를 복원한다. 이전 상황판을 사용자가 고르게 하지 않는다.
- 브라우저 데이터를 삭제해도 저장 완료된 상태를 보존한다는 합의에 따라 계정별 확인 상태도 서버 DB에 둔다. 확인한 계정·알림 조합만 기록하며, 구체적인 테이블·컬럼과 보존 기간·복구할 이력이 없을 때의 처리는 아직 정하지 않았다.
- 연결별 SSE 수신 위치와 계정별 알림 확인 상태는 다른 정보다. 한 탭이 알림을 수신했다는 이유만으로 확인 처리하거나, 다른 탭의 지도·알림 갱신을 생략하지 않는다.
- 처음 접속해도 이전 경로·마커를 포함한 최신 지도를 보여준다. 배정 전 알림의 목록 조회와 최초 배지 숫자는 위 권한·집계 합의를 따르며, 재접속할 때 이미 확인한 알림을 미확인으로 초기화하지 않는다.
- 저장 확인을 받지 못했다고 실패로 단정하거나 완료처럼 표시하지 않는다. 다른 알림의 열람을 막지 않고 저장 미확인 상태를 표시하며, 위 합의에 따라 제한된 자동 재시도와 직접 재시도를 제공한다. 저장 전에 화면이 종료되면 이전 확인 상태로 복원될 수 있다. 구체적인 재시도·오류 처리와 계정별 SSE 구독·재연결의 세부 처리는 후속 설계 대상이며, 연결이 끊긴 탭까지 즉시 같은 상태라고 보장하지 않는다.

위 내용은 구현·검증 전 합의다. 기존 팝업용 저장 흐름을 그대로 추가하지 않고, 계정 기준 상태에 필요한 최소 흐름을 정한다.

## 이벤트 저장과 전달

- **기존 요구**: 업무 데이터와 전송할 이벤트를 같은 트랜잭션에서 저장한다. 이벤트 검증·저장 실패 시 업무 데이터만 남기지 않으며, 커밋 이후 전달한다. 전달 과정에서 같은 `eventId`와 원본 데이터의 ID·상태·버전을 추적할 수 있어야 한다.
- 옛 공통 envelope는 `eventId`, `incidentId`, `type`, `schemaVersion`, `serverTs`, `payload`를 구분했다. 구체적인 payload는 이벤트별 생산자·소비자와 대조한다. 필드 이름이 같아도 업무 데이터의 버전, SSE 순번, 상황판 응답 버전이 같은 카운터라는 뜻은 아니다. 전체 옛 표는 [경계 원문](../guides/feature-verification.md#과거-문서의-차이와-복원)에서 확인한다.
- **현재 구현 (2026-09-26)**: [DbEventHub](../../backend/src/main/java/com/surimap/global/event/DatabaseEventPublisher.java)는 전송 작업을 DB에 저장하고 커밋 뒤 worker를 깨운다. [EventDispatchJobService](../../backend/src/main/java/com/surimap/global/sse/ServerSentEventJobService.java)는 순번·처리 상태를 DB 트랜잭션으로 저장하고, [EventDispatchJobWorker](../../backend/src/main/java/com/surimap/global/sse/ServerSentEventJobWorker.java)는 커밋된 순번으로 SSE를 전송한다. 전송 중에는 DB 트랜잭션을 유지하지 않는다. 완료 상태는 브라우저 표시나 FCM 전달 성공을 뜻하지 않는다.
- **현재 재접속 구현(2026-09-28)**: [SseReplayService](../../backend/src/main/java/com/surimap/api/service/sse/ServerSentEventHistoryService.java)가 DB의 확정 순번·이벤트를 읽는다. 운영 메모리 이력 저장소는 제거했다. DB 연결 테스트와 실제 서버 재시작·브라우저 복구 시험은 구분한다.

## SSE 재연결과 중복 처리

**DB 저장·조회 기반 구현 (2026-09-26, 첫 단계)**: [migration](../../backend/src/main/resources/db/migration/V20260926_001__add_sse_sequence.sql), 기존 Mapper와 필요한 작업 객체 매핑을 변경했다. 이후 전송 경로의 변경은 아래 Service·worker 기록과 구분한다.

- 사건 카운터는 `BIGINT NOT NULL DEFAULT 0`, 이벤트 순번은 배정 전 `NULL`이며 배정 후 양수다. 0은 마지막 확정 순번이 없다는 뜻이다. 같은 사건의 순번 중복은 DB unique index로 막는다.
- [IncidentMapper](../../backend/src/main/java/com/surimap/incident/repository/IncidentMapper.java)는 카운터 조회·증가를, [EventDispatchJobMapper](../../backend/src/main/java/com/surimap/global/sse/ServerSentEventJobMapper.java)는 순번 저장·범위 조회를 제공한다. 기존 완료·순번 미확정 작업에는 새 순번을 넣지 않고, 배정된 순번을 덮어쓰지 않는다. 범위 조회는 시작 순번 제외·끝 순번 포함이며 호출자가 조회 개수를 지정한다.
- [Mapper 테스트](../../backend/src/test/java/com/surimap/global/sse/ServerSentEventJobMapperTest.java)와 [migration 테스트](../../backend/src/test/java/com/surimap/database/SseSequenceMigrationTest.java)에서 실제 PostgreSQL/PostGIS의 저장·정렬·제약·롤백과 기존 작업·GPS·마커·알림 원문 보존을 확인했다. `UPDATE ... RETURNING` 선점 후에도 조회 캐시가 옛 상태를 반환하는 문제를 재현해, [MyBatis의 데이터 변경 설정](https://mybatis.org/mybatis-3/sqlmap-xml.html)에 맞춰 갱신했다.
- 이 단계에서는 SQL·매핑만 검증했다. Service·worker의 후속 구현은 아래에 기록하며, 운영 DB 적용·배포·이력 삭제·부하 시험은 하지 않았다.

검증: 새 DB 테스트 10개와 기존 전송 관련 테스트 5개 통과. `cd backend && ./gradlew test`는 전체 1,249개 통과(실패·건너뜀 0, 기본 설정상 성능 태그 제외)다. 기존 전송 관련 테스트에는 메모리 재전송 저장소·대역을 사용하는 검사도 포함된다.

**Service·worker 연결 (2026-09-26, 두 번째 단계)**

- 기존 Dispatcher를 `EventDispatchJobService`, PollingWorker를 `EventDispatchJobWorker`로 교체했다. 업무 커밋 → worker 깨우기 → 작업 선점 → 순번 확정·커밋 → SSE 전송 → 결과 저장 순서다. 동기 로컬 consumer는 업무 트랜잭션에 남겼다.
- `getOrAssignSseSequence(UUID jobId)`는 작업 행을 잠근 뒤 기존 순번을 반환하거나 카운터 증가·순번 저장을 함께 커밋한다. 같은 작업의 동시 요청도 같은 순번을 받으며, DB 저장 오류에는 카운터 증가도 롤백한다. 순번 없는 과거 완료 작업은 새로 배정하지 않는다.
- `SseStreamService`는 메모리에서 새 순번을 만들지 않고 DB에서 확정한 순번을 전달받는다. 이력이 이미 있다는 이유로 전송을 생략하지 않는다. 재시도는 같은 순번·이벤트 UUID를 사용하며, 중복 수신의 적용 방지는 소비자가 맡는다.
- 깨우기 신호는 작업마다 무제한 쌓지 않고 하나로 합친다. 기존 주기·묶음 크기 설정을 유지했으며 `polling-enabled=false`는 주기 조회만 끄고 커밋 후 깨우기는 허용한다. 이 값들을 새 운영 기준으로 검증한 것은 아니다.
- [Service 테스트](../../backend/src/test/java/com/surimap/global/sse/ServerSentEventJobServiceTest.java)는 실제 DB의 중복 배정·동시 요청·롤백·과거 완료 행을 검사한다. [Worker 테스트](../../backend/src/test/java/com/surimap/global/sse/ServerSentEventJobWorkerTest.java)는 전송 시점의 DB 커밋·트랜잭션 종료, 요청 반환, 업무 롤백, 실패 후 같은 순번의 재실행, 신호 없는 대기 작업의 주기 처리를 확인한다. 외부 전송 대상은 대역이며 브라우저 수신 검증이 아니다.
- **이 단계의 검증 범위**: 재시도 테스트는 실패 작업을 테스트에서 대기로 되돌렸으므로 자동 복구 완료의 증거가 아니다. 자동 복구의 후속 구현은 아래에 구분해 기록한다. 재연결 조회는 아직 메모리 저장소를 사용하며 부분 구현을 배포하지 않는다.

검증: 두 번째 단계의 Service 5개·Worker 7개·기존 스트림 7개가 통과했다. `cd backend && ./gradlew test`는 전체 222개 클래스·1,258개 통과(실패·오류·건너뜀 0, 기본 설정상 성능 태그 제외), 4분 48초다. 첫 두 단계의 관련 변경만 `d62d3521`로 임시 커밋했으며 푸시·배포·실제 서버 재시작은 하지 않았다.

**미완료 전송 작업 복구 (2026-09-26, 세 번째 단계)**

- 시작할 때 남아 있는 `DISPATCHING`을 회수한다. 주기 조회에서는 `FAILED`와 이전 회차에서 처리 결과를 남기지 못한 `DISPATCHING`을 다시 대기로 돌린다. 순번·이벤트 원문은 유지하며, 순번이 없는 미완료 작업만 새로 배정한다. 과거 완료 작업은 회수하지 않는다.
- 사건마다 먼저 처리할 작업 하나만 선점한다. 배정된 순번을 우선하고, 앞 작업이 실패하면 같은 사건의 뒤 작업을 먼저 보내지 않는다. 다른 사건은 계속 선점할 수 있다. worker는 완료한 다음 작업을 이어 처리하되 기존 회차별 묶음 크기를 넘기지 않는다.
- 회수·선점 시 DB에서 종료·파기 완료를 확인한 사건은 종료 정보만 대상으로 삼는다. 과거 작업은 상태·내용을 보존하며 다시 보내거나 완료로 꾸미지 않는다. 이미 선점한 뒤 사건이 종료되는 경합과 재연결 조회의 제한까지 해결한 것은 아니다.
- **운영 조건**: [현재 배포 설정](../../infra/docker/docker-compose.runtime.yml)은 백엔드 1개다. 전송과 회수는 같은 단일 worker 스레드에서 수행한다. 여러 백엔드가 동시에 처리하려면 작업 소유권·회수 방식을 먼저 바꿔야 한다. 기존 주기를 사용하며 지속 실패의 재시도 상한·추가 대기 정책은 도입하지 않았다.
- **남은 범위**: DB 재연결 조회, 재전송→실시간 전환, 느린 연결 격리와 실제 프로세스 재시작·브라우저 검증. 미확정 작업의 생성 시각이 같을 때 업무 호출 순서를 보존하는 검증도 남아 있다. 새 worker 객체를 시작한 테스트를 실제 서버 재시작 검증으로 세지 않는다.

검증: `cd backend && ./gradlew test`는 작업 트리 전체 222개 클래스·1,266개 통과(실패·오류·건너뜀 0, 기본 설정상 성능 태그 제외), 4분 46초다. 이후 재시도 테스트가 하나의 worker로 최초 전송과 재시도를 모두 수행하도록 준비를 정리하고 관련 30개를 재검증했다(38초, 모두 통과). 실제 PostgreSQL/PostGIS의 Worker 12개·Mapper 11개·Service 5개와 기존 fanout 2개이며 외부 SSE 전송 대상은 대역이다. 관련 8개 파일만 `49c182ff`로 임시 커밋했고 푸시·배포하지 않았다.

**DB 재전송 범위 조회 (2026-09-26, 네 번째 단계)**

- `EventDispatchJobService.readSseReplayPage`가 기존 Mapper로 DB 이력을 읽는다. 마지막 수신 순번은 제외하고, 재전송할 마지막 순번까지 호출부가 지정한 개수로 나눠 읽는다. 조회 중 새로 생긴 이벤트를 기존 범위에 섞지 않으며 전송 완료·실패 여부로 이력을 제외하지 않는다.
- 필요한 개수와 모든 순번의 연속성을 검사한다. 이력의 앞·중간·끝이나 전체가 없거나 요청 범위가 DB의 확정 순번보다 앞서면 `GoneRefetchRequiredException`을 반환한다. 부분 결과·빈 목록으로 정상 복구처럼 처리하지 않는다. 음수·역순 범위와 0 이하의 조회 개수도 거부한다.
- 종료·파기 완료·존재하지 않는 사건은 과거 이력을 조회하지 않는다. 행·원문·확정 순번은 변경하지 않는다. **이력 조회의 거부이지 종료 정보를 어떤 HTTP/SSE 응답으로 보낼지 정한 변경은 아니다.**
- 기존 새 트랜잭션 경계를 유지하고 이 메서드만 읽기 전용으로 표시했다([Spring의 메서드별 트랜잭션 설정](https://docs.spring.io/spring/reference/6.2/data-access/transaction/declarative/annotations.html)). 한 페이지를 읽은 뒤 트랜잭션을 끝내며 SSE 전송은 하지 않는다. 격리 수준은 새로 정하지 않았고, 상태 검사 후 종료·삭제와의 경합까지 해결한 것은 아니다. [PostgreSQL의 기본 Read Committed](https://www.postgresql.org/docs/16/transaction-iso.html)는 여러 SELECT를 항상 같은 시점의 조회로 묶지 않는다.
- **아직 연결하지 않은 부분**: `SseReplayService`·`SseStreamService`·`EventStreamConfig`는 기존 메모리 경로를 유지한다. 최초 접속의 시작 위치·계정 권한·종료 정보 응답·실시간 전환과 연결별 대기량 제한을 함께 연결해야 한다. 페이지 개수의 운영값·바이트 한도는 정하지 않았으며, 테스트의 작은 조회 개수를 운영 기본값으로 사용하지 않는다. 이번 단계는 실제 서버 재시작·브라우저 복구 검증이 아니다.

검증: 실제 PostgreSQL/PostGIS의 Service 20개·Worker 12개·Mapper 11개, 총 43개 통과(40초). `cd backend && ./gradlew test`도 작업 트리 전체 222개 클래스·1,281개 통과(실패·오류·건너뜀 0, 기본 설정상 성능 태그 제외), 4분 48초다. 새 테이블·클래스·설정·의존성은 추가하지 않았다. 실제 SSE 재접속 연결은 다음 단계이며 푸시·배포·실제 서버 재시작은 하지 않았다.

**SSE 초기 전송 시점 (2026-09-27, 연결 교체 준비)**

- `SseEmitter`는 유지하고, MVC가 응답과 종료 콜백을 준비한 뒤 `AsyncHandlerInterceptor.afterConcurrentHandlingStarted`에서 Servlet의 `AsyncContext.start`로 초기 전송을 실행한다. `connected` 주석과 재전송 이벤트를 emitter 초기화 전에 넣지 않는다. 별도 전송 스레드 풀·의존성·운영 한도는 추가하지 않았다.
- 당시 `SseStreamEmitter`가 사건·계정 구독의 시작 전 종료, 등록 해제, 전송 실패를 함께 처리했다. 2026-09-29 비차단 쓰기 구현에서는 [SseStreamResponse](../../backend/src/main/java/com/surimap/global/sse/ServerSentEventStream.java)로 교체했다. MVC 초기화 오류·작업 제출 거부를 처리하고, 직접 관리하는 출력의 I/O 실패는 등록 해제와 비동기 응답 종료로 정리한다.
- 기존 HTTP 409 사전 검사는 유지한다. 작업을 기다리는 동안 추가된 사건 이벤트를 포함하려고 전송 시작 시 메모리 이력을 다시 읽는다. **DB 페이지 조회 연결이나 재전송·실시간 전달의 순서 보장은 아직 구현하지 않았다.** 이력 조회와 등록 사이의 경합, 재전송 중 새 이벤트의 선행 전달, 계정 연결 수립 중 갱신·재조회는 후속 검증 대상이다.
- [EventStreamControllerTest](../../backend/src/test/java/com/surimap/api/controller/sse/ServerSentEventControllerTest.java) 16개, 기존 Stream 6개·Registry 10개가 통과했다. 실제 MVC 반환 처리와 Servlet 응답·실행 대역을 사용한 검사이며 실제 소켓·브라우저 시험은 아니다. 종료 사건 재접속 검사는 Service에서 Controller로 옮겨 전송 작업까지 실행한다. Worker 검사는 닫힌 emitter가 실제로 연결 목록에 남아 있는 조건을 보존하도록 준비를 수정했다.

전체 재검증: Docker 연결 후 `cd backend && ./gradlew test --rerun-tasks --console=plain`을 실행해 **222개 클래스·1,293개 모두 통과**했다(실패·오류·건너뜀 0개, 4분 23초, 기본 설정상 성능 태그 제외). 실제 PostgreSQL/PostGIS의 Service 20개·Mapper 11개·Worker 12개도 포함한다. DB 순번 저장·동시 배정·롤백·이력 범위 조회와 누락 검사·실패/중단 작업 복구를 확인했다. 앞선 Docker 부재의 984개 통과·244개 건너뜀은 부분 결과였으며, 이번에는 매개변수별 실행까지 포함해 다시 검증했다.

이번 재검증에서 제품 코드·테스트는 추가로 수정하지 않았다. 실제 초기 전송 중 연결 종료·Tomcat 정리 로그·재시작 복구·부하는 미검증이며, DB 조회 메서드의 통과를 운영 SSE 재전송 연결 완료로 보지 않는다. 이 중간 상태를 DB 전환 완료로 배포하지 않는다.

**DB 재전송의 마지막 순번 조회 (2026-09-27)**

[EventDispatchJobService](../../backend/src/main/java/com/surimap/global/sse/ServerSentEventJobService.java)의 `getSseReplayEndSequence`로 현재 DB에 확정된 마지막 순번을 읽는다. 호출부가 이 값을 페이지 조회의 끝 순번으로 유지하면, 조회 도중 추가된 이벤트까지 계속 쫓아 읽지 않는다. 사건 상태 검사는 기존 페이지 조회와 공유하며, 종료·파기·없는 사건은 거부한다. 별도의 클래스·SQL·운영 한도는 추가하지 않았다.

[실제 DB 검사](../../backend/src/test/java/com/surimap/global/sse/ServerSentEventJobServiceTest.java) 21개가 통과했다(실패·오류·건너뜀 0, 21초). 범위 확정 뒤 추가된 이벤트 제외, 호출한 트랜잭션의 미커밋 순번 제외, 원문·작업 상태·카운터 보존을 확인했다. `cd backend && ./gradlew test --console=plain`도 **222개 클래스·1,294개 모두 통과**했다(실패·오류·건너뜀 0, 4분 1초, 기본 성능 태그 제외). 실제 PostgreSQL/PostGIS의 Service 21개·Mapper 11개·Worker 12개를 포함한다.

이 조회는 DB를 잠그거나 SSE 연결을 등록하지 않는다. 연결 등록·실시간 대기·순서 전환과 실제 전송은 아직 연결하지 않았으며, 상태 조회 직후의 종료·파기 경합까지 해결한 것은 아니다. 페이지별 개수·연결별 대기 개수/바이트 한도의 수치는 정하지 않았다.

**연결별 재전송 대기 (2026-09-28, DB 연결 전 단계)**

- **확인한 문제**: 기존 초기 전송에서 새 이벤트가 과거 이력을 앞질러 `2번 → 1번`으로 전달되는 조건을 MVC 응답 쓰기 경계에서 재현했다. 조회 후 등록하던 순서도 등록 후 조회로 바꿨다.
- **변경**: [SseStreamService](../../backend/src/main/java/com/surimap/api/service/sse/ServerSentEventSubscriptionService.java)가 연결을 먼저 등록한다. 과거 이력을 보내는 동안 새 이벤트를 연결별로 대기시키고, 이력과 겹친 순번은 한 번만 보낸다. 대기분을 보내는 중 추가된 이벤트까지 처리한 뒤 실시간 전달로 전환한다.
- **한도 초과**: 개수·바이트 중 하나라도 넘으면 해당 구독을 제거하고 컨테이너 작업으로 HTTP 응답을 종료한다. 대기열의 내용만 비우며 저장된 이력이나 브라우저의 마지막 수신 순번을 바꾸지 않는다. 초과 로그에는 개수·바이트를 남기고 이벤트 원문은 넣지 않는다. 재전송 중 종료·파기를 수신하면 아직 보내지 않은 과거 내용 대신 종료 정보를 전달하고 닫는다.
- **계산 범위**: `id`, `event`, JSON `data`와 줄바꿈을 포함해 직렬화한 UTF-8 바이트를 대기시킨다. 전송 중인 대기 이벤트도 쓰기가 끝날 때까지 합계에 포함한다. JVM 전체 메모리, 직렬화 과정의 임시 객체, 과거 이력 목록, Spring·소켓 버퍼의 총량 제한은 아니다.
- **검증 범위**: Controller 27개·Registry 12개, 총 39개가 통과했다. 순서·중복·실시간 전환, 1,000/1,001개, 한글 바이트·합계 초과, 종료·파기, 별도 스레드에서 응답 쓰기가 막힌 동안 다른 연결의 전달과 초과 구독 제거, 마지막 수신 순번부터의 재접속을 검사했다. 실제 MVC 처리와 Servlet 응답 대역을 사용했으며 실제 네트워크 지연·브라우저 시험은 아니다.

**남은 작업**: 재접속 검사는 여전히 메모리 이력을 사용한다. 기존 DB 범위·페이지 조회를 100개씩 연결하고 운영 메모리 재전송 저장소를 제거해야 한다. 최초 접속·이력 누락·종료 응답, 실제 DB 복구·프로세스 재시작·브라우저 검증도 남아 있다. 실시간 전환 이후 느린 연결의 격리와 실제 소켓 해제 시점도 이번 시험으로 보장하지 않는다. DB 전환 완료로 배포하지 않는다.

**DB 페이지 재전송 연결(2026-09-28)**

- **변경**: `SseReplayService`가 기존 `EventDispatchJobService`·Mapper를 통해 DB를 읽는다. 연결 등록 → 마지막 확정 순번 조회 → 그 순번까지 100개씩 재전송 → 대기 이벤트 → 실시간 전달 순서다. 페이지를 읽은 트랜잭션은 SSE 쓰기 전에 끝난다. 100개/1,000개/1MiB는 앞서 합의한 시험 초기값이며 검증된 운영 상한은 아니다.
- **이어받기·새 연결**: 양의 마지막 수신 순번이 있으면 전체 범위의 누락을 응답 시작 전에 확인해 HTTP 409로 거부하고, 각 페이지에서도 연속성을 확인한다. 순번 없는 새 연결은 현재 남은 이력을 읽는다. 조회 중 추가된 이벤트는 최초 범위에 넣지 않으며, 순번 없는 과거 완료 작업은 그대로 두고 재전송하지 않는다.
- **종료·파기**: DB가 종료 상태면 확정된 종료 알림만 허용하고, 파기 완료라면 과거 이력을 거부한다. 다음 페이지 조회 도중 파기되더라도 이미 대기 중인 파기 알림은 보낸 뒤 닫는다. 조회 직후 종료되는 모든 경합을 직렬화한 것은 아니며, 원문 파기·실시간 전환 후 느린 연결 격리는 후속 작업이다.
- **운영 메모리 제거**: `SseStreamService`는 DB에 확정된 내용을 보내며 메모리 이력을 저장하지 않는다. 메모리 구현 3개는 옛 테스트의 입력용으로 `src/test`에 옮겼다. 기존 SSE 형식 검사는 `SseReplayServiceTest`로, 같은 작업 재시도 검사는 `SseStreamServiceTest`로 모으고 `SseSequenceEnvelopeReplayTest`는 제거했다. Git 이력에서 복원할 수 있다.

- **CI 연결**: [수집 스크립트](../../infra/ci/collect-s4-evidence.sh)의 옛 테스트 참조와 고정 성공률 문구를 제거했다. [검증 스크립트](../../infra/ci/verify-s4-evidence.sh)는 건너뜀·0개 실행·누락 결과를 통과로 처리하지 않는다. [Backend CI 구성](../../infra/ci/README.md)은 이미지 빌드에서 테스트를 컴파일하고, Docker 소켓을 연결한 새 컨테이너에서 실제 DB 검사를 실행하도록 변경했다. 실패해도 보고서를 회수하되 테스트 실패·필수 보고서 누락은 배포를 차단한다. 실제 Jenkins 실행은 아직 확인하지 않았다.

**브라우저 복구 재검증 완료(2026-09-28, #45 이후)**: 커넥션 대기 수정·배포와 API 오류를 성공 HTML로 바꾸던 호스트 Nginx 수정 후, 같은 상황판에서 Backend 재시작 → DB 이력 이어받기 → 지도 갱신 → 테스트 마커의 원래 위치 복원을 확인했다. 커넥션 대기·timeout은 0이었다. 상세 결과는 [로컬 이슈 11](../issues/local/11-board-query-database-connection-pool-exhaustion.md)·[로컬 이슈 12](../issues/local/12-api-errors-replaced-with-successful-html-response.md)를 따른다. 아래 경합·느린 연결·부하 조건까지 검증한 것은 아니다.

**남은 조건 점검(2026-09-28~29, 로컬)**: 기존 Replay 17개·Controller 28개·Registry 12개·Stream 6개, 총 63개가 통과했다. 별도 재현에서는 대조 조건 2개가 통과했지만, 실시간 쓰기가 막힌 연결 뒤의 전달과 그 대기 중 종료·파기되는 3개 조건은 실패했다. 같은 스레드의 순차 전송과 전송 시작 전 한 번의 상태 검사에서 원인을 확인했다. [로컬 이슈 13](../issues/local/13-slow-sse-connection-blocks-live-delivery.md)·[로컬 이슈 14](../issues/local/14-terminal-incident-race-sends-stale-events.md)에 재현·범위를 기록했으며 수정 전이다. 실제 MVC 또는 PostgreSQL/PostGIS·Service를 사용하되 연결 대역을 포함한 검사로, 실네트워크·운영 사건 종료·실제 데이터 파기 시험과 구분한다.

**실시간 전송 분리(2026-09-29, `6c19af0d`·Jenkins #46)**: 실시간도 기존 연결별 대기열·Servlet 비동기 작업으로 보내도록 수정했다. 연결마다 전송 작업 하나를 예약·실행하고 쓰기 중인 데이터도 기존 1,000개/직렬화 UTF-8 1MiB 한도에 포함한다. 일반 이벤트는 실시간·재전송 모두 실제 쓰기 직전 DB 상태를 다시 확인하며 조회 트랜잭션을 네트워크 쓰기 동안 유지하지 않는다. 종료 알림이 도착하면 아직 대기 중인 일반 내용 대신 그 알림을 보내고 닫는다. worker의 완료는 연결별 전송을 넘겼다는 뜻이지 브라우저 수신·표시 완료가 아니다.

- 검증: 관련 127개, 커밋 대상 로컬·Jenkins 전체 각각 1,345개 통과(실패·오류·건너뜀 0). 배포 전 열린 탭의 이어받기를 확인했다. 첫 재시작 시험은 SSH 확인 timeout으로 실패했지만 원래 자료를 복원했고, 같은 조건의 반복에서 40 → 41번 DB 이어받기·상황판·지도 이동·42번 복원을 통과했다. DB 커넥션 대기·timeout 0이며 상세 실패·성공 기록은 위 로컬 이슈를 따른다.
- 실제 소켓 진단(2026-09-29): 느린 연결 1개는 격리됐다. 진단용 Tomcat 스레드 4개를 느린 쓰기 4개가 차지하면 정상 SSE와 일반 HTTP 요청 모두 대기했고, 스레드 5개인 대조는 통과했다. 운영 동시 접속 한계나 권장 스레드 수를 측정한 것이 아니다. [로컬 이슈 13](../issues/local/13-slow-sse-connection-blocks-live-delivery.md)에 기록했으며 공용 HTTP 처리 자원 보호는 남아 있다.
- 남은 범위: 느린 쓰기의 실행기 점유 대책, 마지막 DB 조회와 쓰기 사이의 종료 경합 조율, 종료 API·실제 payload 파기 전체의 동시 검증. 이번 진단에서 제품 코드·운영 설정은 바꾸지 않았고 일반 브라우저 복구를 이 조건의 통과로 대신하지 않는다.

**비차단 쓰기 전환 합의(2026-09-29, 제품 적용 전)**: 전용 스레드 풀만 분리하는 대신 Servlet의 전송 가능 알림을 받아 쓰기를 멈추고 이어가는 방식으로 바꾼다. 실시간 대기열과 DB 페이지 재전송 모두 같은 흐름에 연결하며, 기존 MVC·MyBatis·DB 이력·공개 SSE 형식은 유지한다. 독립 Servlet·실제 TCP 대조에서는 느린 연결 4개/스레드 4개에서도 정상 SSE·HTTP 응답과 느린 연결의 전송 재개를 확인했다. 제품 MVC·인증·DB 재전송·종료 경합의 검증이나 수정 완료가 아니며, 상세 결과와 한계는 [로컬 이슈 13](../issues/local/13-slow-sse-connection-blocks-live-delivery.md)을 따른다. Kafka·Redis·전체 WebFlux 전환은 이번 범위에 넣지 않는다.

**비차단 쓰기 구현(2026-09-29, 미배포)**: `SseStreamResponse`가 Servlet의 `isReady()`·`WriteListener`로 출력 가능 여부를 확인하고 MVC `DeferredResult`로 응답 수명을 관리한다. [SseConnection](../../backend/src/main/java/com/surimap/global/sse/ServerSentEventConnection.java)은 재전송·실시간 대기·순서를 함께 관리한다. 소켓이 막히면 쓰기와 다음 DB 페이지 조회를 멈추며, 연결마다 전송 작업은 하나만 예약·실행한다. 종료 알림을 받으면 남은 재전송 페이지 참조와 실시간 대기분을 버리고 이미 시작한 프레임 뒤에 종료 알림을 보낸다. 기존 공개 형식·페이지 크기·대기 한도와 DB 저장은 유지한다. 실제 HTTP·회귀 검사 결과와 배포 여부는 위 로컬 이슈 13에 기록한다. DB 상태 조회 이후 종료·파기가 커밋되는 별도 경합은 해결하지 않았다.

- **재전송 이력의 의미**: 끊겼던 상황판에 다시 전달하려고 보관하는 이벤트 기록이다. 같은 이벤트를 여러 상황판에 보내거나 다시 보내도 이력 개수는 늘지 않는다. 전송 횟수·실제 수색 데이터·마커 알림 원문·계정별 확인 상태와 구분한다.
- **식별자 구분**: SSE의 `id`와 재연결 헤더 `Last-Event-ID`는 사건별 숫자 순번이다. `data.eventId`는 같은 이벤트인지 구분하는 UUID다. 재전송 위치와 중복 판정을 같은 값으로 취급하지 않는다.
- **합의한 변경 (2026-09-22)**: 재전송할 이벤트와 사건별 순번을 PostgreSQL에 보존하고, 재접속 때 DB에서 조회한다. 서버 재시작 후에도 이어받을 수 있도록 운영 경로의 메모리 전용 재전송 저장소를 교체한다. 현재 열린 SSE 연결의 메모리 관리와는 별개다. 2026-09-28 DB 조회 연결·배포·재시작 후 HTTP 재전송을 확인했으며, 브라우저 전체 검증의 한계는 위 배포 후 기록을 따른다.
- **합의한 저장 구조 (2026-09-22)**: 기존 `event_dispatch_job`의 이벤트 내용을 재사용하고 재전송 정보를 추가한다. 이벤트 이력과 전송 작업을 별도 테이블로 나누지 않는다. 전송 완료 행도 재전송 보존 기간 동안 유지하며, 작업의 완료·실패 상태와 화면별 재전송 조회는 구분한다. 보관 기간은 아래 측정·합의 순서로 정한다.
- **재전송 이력 삭제 합의 (2026-09-24)**: 서버 전송 처리가 끝난 이력은 아래 보관 시간 기준으로 오래된 기록부터 DB에서 삭제한다. 진행 중인 사건의 모든 이벤트를 끝까지 쌓지 않으려는 선택이다. 필요한 이력이 삭제된 재연결은 그 사실을 감지하고 최신 지도·보존된 알림 원문·계정별 확인 상태를 다시 조회해 복구한다. GPS 좌표·마커 등 원본과 알림 원문·확인 기록, 미처리·실패·순번 미확정 전송 작업은 이 삭제 대상이 아니다. 실제 삭제 조건·순번 누락 판정·조회와 삭제의 동시 처리·진단 기록 보존은 후속 설계·검증 대상이다. 종료·권한 거부·파기 제한을 우회해 복구하지 않으며, 아직 삭제 기능을 구현하거나 데이터를 삭제하지 않았다.
- **보관 시간 기준 합의 (2026-09-24)**: 기록 개수가 아니라 서버 전송 처리 완료 시점부터 지난 시간을 기준으로 삭제 대상을 정한다. 브라우저 수신·알림 확인·좌표 수집 시각과 구분한다. 이벤트가 몰려도 개수 제한 때문에 보관 기간이 짧아지지 않는 대신, 같은 기간의 저장량이 늘 수 있다. 구체적인 보관 기간·삭제 주기는 아직 미정이며, 별도의 개수 제한을 함께 채택하지 않았다. 완료 시각의 저장·중복 완료 처리와 순번이 뒤섞여 완료될 때의 누락 감지는 구현·검증 대상이다.
- **보관 기간 결정 순서 합의 (2026-09-24)**: 이벤트가 쌓이는 양과 DB 저장량, 재전송·최신 상태 조회에 걸리는 시간을 측정한 뒤 보관 기간을 함께 정한다. 운영에서 이력 삭제를 켜기 전에 기간을 확정하며, 임의의 기본값으로 삭제를 시작하지 않는다. 측정값만으로 적정 기간이 자동 결정되는 것은 아니며, 이력이 없을 때의 원본 재조회 복구는 유지한다. 아직 기간을 확정하거나 측정·삭제를 실행하지 않았다.
- **재조회와 보존의 구분**: 이벤트가 저장돼 있다는 이유만으로 조회가 반복되지는 않는다. 여러 변경 이벤트의 지도 조회 요청은 [상황판 재조회 합의](situation-board.md#이벤트-수신과-최신-데이터-재조회)에 따라 진행 중인 조회를 유지하고 후속 조회로 합친다. 재전송 이력 삭제를 중복 조회 최적화의 대체 수단으로 삼지 않으며, 알림별 처리·복구와 종료 처리는 별도로 보존한다. 구현·실제 요청 수 검증은 남아 있다.
- **순번 저장 위치·컬럼명 합의 (위치 2026-09-22, 이름 2026-09-25)**: SSE sequence (SSE 순번)는 한 사건 안에서 이벤트에 확정하는 순번이며, 처음 전송하거나 재전송할 때 같은 값을 사용한다. 사건의 마지막 DB 확정 순번은 `incident.last_sse_sequence`, 각 이벤트의 확정 순번은 `event_dispatch_job.sse_sequence`에 저장한다. 업무 `version`·이벤트 UUID·브라우저의 마지막 수신 위치·전송 완료 상태와 구분한다. 별도 관리 테이블과 행 생성 흐름을 추가하지 않는 대신 배정 변경·사건 종료와 행 잠금을 공유한다. 자료형·초기값·기존 행 보존 SQL은 위 2026-09-26 구현 기록을 따르며, 같은 작업의 동시 순번 배정은 위 Service 테스트로 확인했다. 파기 후 정리·여러 작업의 전달 순서 검증은 남아 있다. 공개 SSE `id`·`Last-Event-ID`, `data.eventId`와 기존 payload의 `sequence`는 바꾸지 않았다.
- **합의한 순번 확정 시점 (2026-09-22)**: 업무 데이터와 이벤트 내용을 같은 트랜잭션에서 먼저 커밋한다. 이후 별도의 짧은 DB 트랜잭션에서 사건별 재전송 순번을 확정·저장하고, 그 커밋 후 SSE로 전달한다. 순번 조율을 업무 트랜잭션에서 분리하는 대신 추가 트랜잭션과 미완료 처리 복구를 맡는 선택이다. 서버가 중간에 멈춰도 DB에 남은 순번 미확정 이벤트를 이어 처리해야 한다. 순번 확정·커밋 후 전송은 위 두 번째 단계에서 구현했다. 전체 중단 복구·성능 검증은 남아 있으며 순번 저장만으로 실제 전달 순서까지 보장되는 것은 아니다.
- **순번 확정 메서드 합의 (2026-09-25)**: worker가 순번을 확정할 때 호출할 서비스 작업은 `getOrAssignSseSequence`(기존 순번 조회 또는 신규 배정)로 이름짓는다. 이미 확정된 순번이 있으면 그 값을 반환하고, 없으면 사건 카운터 증가와 이벤트 순번 저장을 같은 짧은 DB 트랜잭션에서 처리한다. SSE 전송은 커밋 이후 별도로 수행한다. 순번 저장 직후 전송 전에 중단될 수 있으므로, 기존 순번이 있다는 이유만으로 전송을 생략하지 않는다. 이 메서드는 아래 합의대로 기존 Dispatcher를 재구성한 `EventDispatchJobService`에 둔다. 현재 `UUID jobId`를 받아 `long` 순번을 반환하며, 없는 작업과 새 순번을 배정할 수 없는 과거 완료 작업은 거부한다. 작업 행 잠금과 서비스 트랜잭션은 위 두 번째 단계에서 검증했다.
- **합의한 전송 담당 (2026-09-22)**: 기존 Spring 애플리케이션의 worker가 순번 확정과 정상 전송·미완료 처리 복구를 맡는다. 요청 쪽 `afterCommit`은 SSE를 직접 보내지 않고 worker에 처리할 일이 있음을 알린다. 신호를 놓치거나 서버가 재시작해도 주기적인 DB 조회로 남은 작업을 처리한다. 사건별 전송 순서는 이 공통 처리 경로에서 관리하도록 구현한다. 깨우기·주기 조회·미완료 회수와 배정된 순번의 전달 검증은 위 구현 기록을 따른다. 실제 재시작·재연결과 관련 이벤트의 업무 호출 순서 보존 검증은 남아 있다.
- **DB 처리와 전송의 역할·클래스명 합의 (2026-09-25)**: 기존 `EventDispatchJobDispatcher`는 `EventDispatchJobService`(전송 작업의 DB 처리), `EventDispatchJobPollingWorker`는 `EventDispatchJobWorker`(전송 작업 실행)로 이름짓고 책임을 재구성한다. worker는 서비스의 순번 확정·커밋 → SSE 전송 → 서비스의 처리 결과 저장을 차례로 호출한다. DB 처리는 서비스의 `@Transactional` 경계 안에 두고, SSE 전송은 DB 트랜잭션 밖에서 수행한다. 별도 서비스를 추가하지 않고 기존 두 클래스의 책임을 나누는 선택이다. 요청의 `afterCommit`은 worker에 알리기만 하며, `DbEventHub`의 동기 로컬 consumer는 기존 업무 트랜잭션에 남긴다. 작업 처리 결과는 브라우저 수신이나 FCM 성공의 증거가 아니다. 기존 테이블·Mapper와 같은 전송 작업을 가리키는 이름을 선택했으며, FCM 처리를 추가하거나 DB·공개 필드명까지 바꾸지 않는다. 클래스 교체·깨우기·주기 조회·순번 배정 동시성은 위 두 번째 단계에서 확인했다. 중간 중단 복구와 작업 간 전달 순서 검증은 남아 있다.
- **최초 DB 전환 합의 (2026-09-25)**: 메모리 재전송 저장소에서 DB로 처음 전환할 때는 열려 있는 상황판을 한 번 새로고침하고, 옛 수신 위치 대신 최신 지도·보존된 알림 원문·계정별 확인 상태를 조회해 복구한다. 기존 화면의 메모리 순번을 DB 이력과 이어 주는 호환 전환은 도입하지 않는다. GPS·마커·알림 원문·저장된 확인 상태와 미처리 전송 작업은 보존한다. SSE 연결만 끊으면 옛 순번으로 재연결할 수 있으므로 새로고침 여부와 전환 중 누락 방지를 검증해야 한다. 이후의 일반 배포·재시작에는 DB 순번을 이어 쓰며 반복 초기화하지 않는다. 새로고침만으로 복구가 완성되는 것은 아니며, 실제 DB 재조회 연결·전환 안내·미저장 화면 작업의 처리와 아래 기준에 따른 기존 행의 구분·복구는 후속 구현·검증 대상이다. 제품 코드·DB 변경이나 실제 전환은 아직 하지 않았다.
- **전환 전 완료 이력 합의 (2026-09-25)**: 최초 DB 전환 전에 서버 전송 작업이 `COMPLETED`로 기록됐고 DB SSE 순번이 없는 기존 행은 보존하되, 새 순번을 배정하거나 새 재전송 이력에 편입하지 않는다. 과거 마커·GPS·알림 원문과 저장된 확인 상태는 앞선 조회 복구 합의를 따른다. 미완료 작업과 새 이벤트는 DB 순번을 배정해 처리하며, 이미 배정된 순번은 재시도·재시작에도 유지한다. `PENDING`·`FAILED`·중단 후 남은 `DISPATCHING`을 과거 완료 이력으로 취급하지 않고 복구 대상으로 구분한다. DB 전환 이후 순번이 확정된 완료 이벤트는 정상 재전송 대상으로 유지한다. 기존 행·원본을 삭제하거나 과거 완료 시각을 추정해서 채우는 결정이 아니며, 권한·종료·파기 기준은 유지한다. 전환 구분·미완료 복구와 실제 조회는 구현·검증 전이다.
- **재전송과 실시간 전달의 연결 합의 (2026-09-25)**: 복구할 연결을 먼저 수신 대상으로 등록하고, 재전송할 마지막 확정 순번을 같은 조율 과정에서 정한다. 그 순번까지 DB 이력을 보내는 동안 들어오는 새 이벤트는 해당 연결에서 잠시 대기시켰다가 순서대로 이어 보낸다. 대기분을 보내는 중 도착한 이벤트도 먼저 보내거나 빠뜨리지 않으며, 이력과 실시간 경로에 겹쳐 잡힌 이벤트는 중복 적용하지 않는다. 정상인 다른 연결의 전달을 이 복구가 끝날 때까지 멈추지 않는다. 이벤트 원본·순번은 PostgreSQL에 보존하며, 연결별 임시 대기는 메모리 전용 재전송 저장소를 유지한다는 뜻이 아니다. [Mercure의 구독 등록·재전송 범위 조율](https://github.com/dunglas/mercure/blob/0ce390af83b1f8414374bc7ddf28e9fe39c7bb24/bolt.go#L147-L168)을 참고한 프로젝트 선택이다. 등록 순서만 바꾸면 해결되는 것은 아니므로 사건별 순번·실시간 전달·전환을 함께 구현·검증한다. 대기량 제한·초과 시 복구는 아래 합의를 따르며, 한도 수치와 동시 처리 검증은 남아 있다. 권한·종료·파기 제한은 유지한다.
- **대기량 초과 시 복구 합의 (2026-09-25)**: 재전송 중 새 이벤트의 연결별 임시 대기량이 한도를 넘으면 해당 사건 SSE 연결만 종료한다. 합의한 재연결 대기 후 브라우저의 마지막 실제 수신 순번부터 DB 이력을 다시 받는다. 기존 재연결·DB 재전송을 활용하기 위한 선택이며, 서버가 이벤트를 대기열에 넣거나 전송했다는 이유로 브라우저 수신 위치를 앞당기지 않는다. 정상인 다른 연결·업무 저장·DB 원본·미처리 작업은 유지한다. 필요한 이력이 없으면 기존의 최신 지도·보존된 알림 원문·확인 상태 조회로 복구하고, 권한·종료·파기 제한은 지킨다. 전달 지연이 지속되면 반복 종료될 수 있으므로 갱신 지연 안내와 원인 추적을 유지한다. 한도 수치와 전체 전송 경로의 메모리·느린 연결 검증은 남아 있으며, 아직 구현하지 않았다.
- **대기량 제한 기준 합의 (2026-09-25)**: 재전송 중 새 이벤트를 잠시 보관하는 각 연결에 이벤트 개수와 전송 데이터 총 크기(바이트)의 한도를 함께 둔다. 어느 하나라도 넘으면 위 합의대로 해당 연결만 종료하고 이어받는다. 작은 이벤트의 대량 누적과 큰 이벤트의 누적을 각각 제한하기 위한 선택이며 SSE 표준의 필수 기준은 아니다. DB 이력의 보관 기간이나 원본·알림 확인 기록의 보존 범위는 바꾸지 않는다. 바이트 수를 JVM 전체 메모리 사용량으로 간주하지 않으며, 실제 보관 형태·계산 범위와 초기 재전송 목록·Spring 내부 보관·전송 버퍼도 함께 검증한다. 구체적인 개수·크기 수치는 측정 근거를 확인한 뒤 함께 정하며, 아직 구현·측정하지 않았다.
- **기존 요구**: 이벤트는 한 번만 이력에 추가하고, 마지막 수신 순번 이후의 이벤트를 순서대로 재전송한다. 소비자는 `eventId`로 중복 적용을 막는다. 순번 누락이나 재전송 불가 시 상황판 전체 조회로 복구한다.
- **이력 누락 처리(2026-09-29 확인)**: [SseReplayService](../../backend/src/main/java/com/surimap/api/service/sse/ServerSentEventHistoryService.java)는 양의 마지막 수신 순번이 있으면 이후 범위의 누락을 확인한다. 필요한 범위의 일부·전체 이력이 없는 조건을 DB 검사로 확인했다. 순번 없는 새 연결은 남은 이력을 읽는다. 완료 이력의 주기 삭제·삭제와 조회의 동시 처리·최신 상태 재조회까지 모두 검증했다는 뜻은 아니다.
- **복구 범위 구분**: [상황판 구독](../../frontend/src/features/situationBoard/presentation/hooks/useSituationBoardData.ts)은 연결 성공·이벤트·오류에 재조회를 요청한다. [마커 알림 구독](../../frontend/src/features/markerNotifications/presentation/hooks/useIncidentMarkerNotifications.ts)은 별도로 동작하며, 재전송 불가 시 순번을 초기화한다. 상황판 재조회가 놓친 알림 팝업까지 복원하는 것은 아니다. 현재 두 소비자 모두 순번 간격을 직접 비교하는 누락 검사는 없다. 2026-09-24 코드 대조에서 알림 구독은 최초 상황판 조회 완료 전에도 시작하지만, 상황판 구독은 조회 결과가 있고 종료 상태가 아닐 때 시작함을 확인했다. 위 연결 구성 합의를 구현할 때 초기 수신 시점·오류·종료 처리의 차이를 함께 확인한다. 실제 브라우저 연결 수나 복구를 실행해 검증한 결과는 아니다.

## 연결 정리의 검증 범위

- **연결 등록·해제 경합 (2026-09-27)**: 마지막 기존 연결 해제와 새 연결 등록이 겹치면 새 등록이 목록에서 사라져 이벤트를 받지 못하는 문제를 사건·계정 구독에서 재현했다. 같은 구독 대상의 목록 변경을 원자적으로 처리하도록 수정했다. Registry 테스트 12개와 전체 Backend 1,296개가 통과했다(실패·오류·건너뜀 0, 전체 3분 48초, 기본 성능 태그 제외). 실제 HTTP 재접속이나 DB 재전송 전환 검증은 아니며, 원인·명령·검증 범위는 [로컬 이슈 6](../issues/local/6-sse-registration-lost-during-reconnect.md)에 기록했다.
- **배포 후 연결 검증 (2026-09-28)**: `d1f04fb7`의 Jenkins #35 배포와 SSE 순번 migration 적용을 확인했다. 실제 브라우저의 최초 진입·새로고침·화면 복귀·재차 새로고침에서 마커 4개·알림 4개·전송 작업 8개, SSE 순번 일치와 화면 갱신을 확인했다. 정확한 등록·해제 경합을 강제한 시험이나 DB 이력 재전송·서버 재시작 복구 검증은 아니다. 상세 결과는 위 로컬 이슈 6, 3건에서 관측한 관련 이벤트의 발행 호출 순서 불일치는 [로컬 이슈 8](../issues/local/8-marker-events-dispatched-out-of-publication-order.md)에 남겼다.
- **같은 요청의 발행 순서 수정 (2026-09-28, 로컬 검증)**: 같은 저장 시각에 무작위 UUID로 작업을 정렬하던 문제를 DB 테스트로 재현했다. 새 작업의 `insertion_order`를 DB 기본값으로 발급하고, `claimPending`에서 UUID보다 먼저 비교한다. 같은 트랜잭션의 `MARKER_CREATED` → `PERSON_FOUND` 순서를 보존하며 이미 확정한 SSE 순번과 재시도 우선순위는 유지한다. 과거 행의 저장 순서는 추정하지 않고 `NULL`로 남겨 종전 정렬을 유지한다. API·이벤트 필드는 그대로이며 서로 다른 트랜잭션의 커밋 순서까지 보장하는 변경은 아니다. 실제 PostgreSQL/PostGIS의 Mapper·Service·Worker·Migration 47개가 통과했다(실패·오류·건너뜀 0). 이 로컬 검증의 전송 대상은 대역이며, 이후 배포 결과는 아래에 구분한다. DB 재전송 연결은 남아 있다. 상세 재현·보존 검증은 [로컬 이슈 8](../issues/local/8-marker-events-dispatched-out-of-publication-order.md)에 기록했다.
  - 같은 작업 트리의 `cd backend && ./gradlew test`도 222개 클래스·1,298개 통과했다(실패·오류·건너뜀 0, 4분 8초, 기본 성능 태그 제외). 이 로컬 검증 단계에서는 커밋·푸시·서버 migration 적용을 하지 않았다.

- **초기 시간 설정 합의 (2026-09-24)**: 확인 신호는 15초마다 보내고, 마지막 수신 후 30초 동안 데이터가 없으면 재연결 절차를 시작하는 값으로 먼저 시험한다. - **숨겨진 탭의 무응답 처리 합의 (2026-09-24)**: 탭이 숨겨진 동안에는 30초 무응답을 이유로 한 재연결 판정만 보류한다. 숨겼다는 이유로 SSE 연결을 닫거나 수신을 막지 않으며, 명시적인 네트워크 오류·인증 만료·사건 종료 처리를 보류하지 않는다. 마지막 실제 수신 시각을 유지하고, 복귀 시 그 시각과 연결 상태를 점검해 필요한 연결만 다시 연결한다. 복귀 자체를 새 수신으로 기록하지 않는다. 최신 상태 조회와 사건 재전송·계정 확인 상태 복구는 앞선 합의를 따른다. 입력 포커스만 잃었지만 여전히 보이는 화면에는 보류하지 않는다. - **재연결 간격 합의 (2026-09-24)**: 재시도할 수 있는 연결 실패가 이어지면 다음 접속까지의 기준 대기시간을 늘리되 상한을 두고, 각 연결의 대기에 무작위 차이를 준다. 서버 재시작 등으로 여러 상황판이 함께 끊겼을 때 재접속 요청이 몰리는 것을 줄이려는 선택이다. 대신 서버가 복구돼도 다음 예약 시도까지 더 기다릴 수 있다. [WHATWG의 재연결 처리](https://html.spec.whatwg.org/multipage/server-sent-events.html#processing-model)는 반복 실패 시 증가하는 지연을 선택 사항으로 설명하고, [Microsoft 재시도 지침](https://learn.microsoft.com/en-us/azure/architecture/patterns/retry)은 여러 클라이언트의 요청을 분산하도록 권한다. 시간값과 정상 수신 후 초기화 기준은 아래 합의를 따르며, 구현·검증은 남아 있다. 이 대기는 확인 신호의 15초 주기·무응답 판정의 30초와 별개다. 사건·계정 연결별로 적용하며 정상인 다른 연결을 함께 끊지 않는다. 인증·권한 오류, 로그아웃·종료 처리와 숨김 중 무응답 판정 보류는 유지한다. 알림 확인 상태 저장의 재시도 횟수 제한을 SSE에 그대로 적용하지 않으며, SSE 재시도의 지속 범위는 아래 합의를 따른다. 구현·부하 검증 전 합의다.

- 2026-09-21에는 위 테스트 코드와 [옛 검증 설명](https://github.com/sonic8-8/suri-map/blob/403b383dc2693fd15d1616ee7206e6cb0e420df5/docs/evidence/backend/sse-stream-lifecycle.md)을 대조해 검증 범위를 이곳에 통합했다. 제품 테스트나 실제 연결 시험을 다시 실행한 결과는 아니다.

## 사건 종료와 데이터 파기

- **합의한 종료와 저장 순서 (2026-09-23)**: 서버에서 쓰기 허용 검사를 통과해 처리 중인 저장은 끝낸 뒤 사건 종료를 확정하고, 이후의 새 쓰기는 거부한다. 저장의 성공·롤백으로 처리 결과가 확정될 때까지 기다리는 것이며, 오프라인 업무폰의 미전송 기록이나 브라우저 알림 수신을 기다리는 정책은 아니다. 이미 허용한 현장 기록을 마무리하는 대신 종료가 저장 처리만큼 지연될 수 있다. 구현·동시 처리 검증 전 합의다.
- **기존 요구**: 종료됐지만 이력이 보존된 사건은 `INCIDENT_CLOSED`까지 재전송한 뒤 연결을 정상 종료한다. 이후 실시간 연결은 유지하지 않는다. 파기된 사건은 재전송 이력·대기 작업의 사건 데이터를 제거하고 다시 전송하지 않는다.
- **현재 한계(2026-09-29, #46 이후)**: [로컬 이슈 14](../issues/local/14-terminal-incident-race-sends-stale-events.md)의 전송 대기·페이지 조회 후 상태 변경을 쓰기 직전 검사로 차단하는 회귀 테스트는 통과했다. 추가 DB·TCP 진단에서는 마지막 조회 직후 종료·파기가 커밋되면 과거 경로 이벤트가 실제 수신됐다. 조회 전 커밋하거나 종료 알림이 먼저 도착한 대조는 차단됐다. 마지막 상태 조회와 쓰기는 원자적이지 않으며 이미 시작한 쓰기도 회수하지 않는다. 종료 API·실제 개인정보 및 전송 payload 파기 전체의 동시 검증은 남아 있고 이 이슈를 해결 완료로 처리하지 않는다.
- **추가 확인할 동시 처리 (2026-09-22)**: [마커의 OPEN 조회](../../backend/src/main/resources/mapper/marker/MarkerAccessMapper.xml)는 사건 행을 잠그지 않는다. 조회 뒤 사건 종료가 먼저 커밋되고 마커 기록이 나중에 커밋될 가능성을 재현해야 한다. 현재 [SSE 재전송](../../backend/src/main/java/com/surimap/api/service/sse/ServerSentEventHistoryService.java)은 종료 순번 뒤 이벤트를 제외하므로, 위 합의에 맞춰 저장·종료·이벤트 전달을 함께 검증한다. 코드 대조로 찾은 확인 대상이며 실제 발생·재현 결과는 아니다.

## 전송 실패와 관측

- **기존 요구**: 재시도할 대상을 구분해 이미 성공한 전달을 반복하지 않는다. 실시간 SSE 연결 실패는 재전송 이력으로 복구하고, FCM만 재시도할 때 SSE 이력을 중복 추가하지 않는다. FCM 수신자가 없으면 해당 전송만 생략하고 SSE 전달은 이어간다.
- **현재 차이 (2026-09-26)**: SSE 실패·중단 작업은 위 worker가 자동으로 다시 처리한다. 특정 수신자에게만 재시도하는 방식은 아니므로 일부 연결에 이미 보낸 이벤트가 다시 전달될 수 있다. FCM은 공통 SSE 전달 작업이 아니라 마커·사건 배정·사건 종료의 호출부에서 별도로 전송한다. [FCM 실패 반환 기록](../issues/local/4-fcm-delivery-failure-not-recorded.md)과 전달 시점·재시도 보장은 구분한다.
- **기존 관측 요구**: 이벤트 저장, 재전송 이력 추가, 실시간 전송, FCM, 상황판 재조회 단계의 실패를 구분한다. 이벤트 형식이 잘못되면 실패로 남기고 원인을 추적한다. 내부 전달 상태를 사용자 알림 상태와 혼용하지 않으며, payload에 정의되지 않은 개인정보를 덧붙이지 않는다.
- **기존 접근 요구**: 사건 접근권을 가진 WEB 연결만 허용하고 권한 만료 시 연결을 종료한다. Android는 상시 SSE 대신 FCM과 REST·미전송 기록 동기화를 사용한다. 연결 도중 권한 만료 처리가 실제로 보장되는지는 별도로 검증한다.

## 후속 작업에서 정할 기준

- 로컬 이슈 13·14에서 재현한 공용 실행기 점유와 마지막 상태 조회 이후의 종료·파기 경합을 조율할 방식을 정한다. 연결별 전송 수정·배포·일반 브라우저 DB 복구와 추가 DB·TCP 진단은 위 기록을 따른다. 완료 시각 기준의 보관 기간·삭제 주기와 삭제·조회 동시 처리는 별도 합의·구현 대상이다. 초기값은 페이지당 100개·연결당 대기 1,000개/1MiB이며 운영 적정값은 미검증이다.
- 알림 패널의 표시·정렬·조회 범위 제한과 보존·파기 범위. 발생 당시 원문과 현재 마커 상태를 구분하고, 위 조회 권한 합의가 실제 API·SQL에서 적용되는지 검증한다.
- 계정·사건별 확인 상태의 서버 저장·재시도·탭 동기화와 재전송 이력이 없을 때의 처리. 연결별 SSE 수신 위치를 계정의 확인 상태로 사용하지 않으며, 탭별 팝업 복구 설계는 이어가지 않는다.
- 탭 복귀 시 새 알림 여부를 판별할 비교 기준과 그 정보의 누락·불완전 여부를 확인하는 방법. 전체 미확인 수가 같아도 알림 구성이 달라진 경우와 다른 탭에서 이미 확인한 경우를 구분하고, 정상 비교와 비교 불가 시 요약 안내를 각각 검증한다.
- 안내의 기본 표시 시간·위치·접근성, 반복 재연결 처리와 뒤늦게 도착한 알림의 시각 표현. 배지·안내·패널 도입만으로 현장 사용성 검증을 대신하지 않는다.
- 실패 대상별 재시도, 중복 방지, 사건 종료·파기 시 정리 범위. 기존 DB 설계를 그대로 구현하는 것으로 미리 확정하지 않는다.
- 지연 목표. 원문의 ‘3초 이내’를 확정 기준으로 채택하지 않으며, [Issue #8](../issues/8-gps-collection-transmission-basis.md)의 측정·합의와 구분한다.
- 연결 확인의 초기 대기·수신 후 무응답 시간값, 숨김·복귀 처리와 재연결 대기 범위를 검증한다. 합의한 대기 초기화·재시도 지속 범위를 검증하고 오류 유형별 중단·인증·사건 종료 처리를 구체화하며, 초기 전송 중 연결 종료 처리는 [로컬 이슈 5](../issues/local/5-sse-initial-send-disconnect-cleanup.md)의 재현 결과를 이어서 검토한다.

## 테스트 입력

S4의 여섯 fixture는 [공용 fixture](../../test-fixtures/common-fixtures.json)의 `confirmed.eventFanout`에 보존돼 있다. 새 복제본을 만들지 않고 기존 소비자가 이 데이터를 사용한다. fixture의 기대값은 현재 제품 동작을 검증했다는 뜻이 아니다.

원문에만 있던 `fanout_failure_injection.expectedParentStatus`의 `PARTIAL_FAILED_THEN_DISPATCHED`는 직접 읽는 테스트가 없으므로 Git 원문에 보존한다. 이를 현재 상태값으로 채택하거나 새 fixture 필드로 추가하지 않는다. 일부 실패 후 복구 요구는 위 전송 실패 항목에서 이어서 확인한다.
