# 이벤트 전달과 재전송

SSE·FCM의 재연결, 실패 복구, 사건 종료 처리를 변경할 때 확인할 기록이다. 옛 S4의 동작 요구와 현재 구현의 차이를 보존한다. 아래의 **기존 요구**는 후속 작업에서 유효성과 범위를 다시 확인할 대상이며, 이번 문서 정리로 새 구현 기준을 확정한 것은 아니다.

현재 구현 설명은 2026-09-18 코드 대조 결과다. 서버 재시작·실제 FCM 전달·브라우저 복구를 실행해 검증한 결과와 구분한다.

## 이벤트 저장과 전달

- **기존 요구**: 업무 데이터와 전송할 이벤트를 같은 트랜잭션에서 저장한다. 이벤트 검증·저장 실패 시 업무 데이터만 남기지 않으며, 커밋 이후 전달한다. 전달 과정에서 같은 `eventId`와 원본 데이터의 ID·상태·버전을 추적할 수 있어야 한다.
- 옛 공통 envelope는 `eventId`, `incidentId`, `type`, `schemaVersion`, `serverTs`, `payload`를 구분했다. 구체적인 payload는 이벤트별 생산자·소비자와 대조한다. 필드 이름이 같아도 업무 데이터의 버전, SSE 순번, 상황판 응답 버전이 같은 카운터라는 뜻은 아니다. 전체 옛 표는 [경계 원문](../guides/feature-verification.md#과거-문서의-차이와-복원)에서 확인한다.
- **현재 구현 (2026-09-26)**: [DbEventHub](../../backend/src/main/java/com/surimap/eventhub/adapter/DbEventHub.java)는 전송 작업을 DB에 저장하고 커밋 뒤 worker를 깨운다. [EventDispatchJobService](../../backend/src/main/java/com/surimap/eventhub/adapter/EventDispatchJobService.java)는 순번·처리 상태를 DB 트랜잭션으로 저장하고, [EventDispatchJobWorker](../../backend/src/main/java/com/surimap/eventhub/adapter/EventDispatchJobWorker.java)는 커밋된 순번으로 SSE를 전송한다. 전송 중에는 DB 트랜잭션을 유지하지 않는다. 완료 상태는 브라우저 표시나 FCM 전달 성공을 뜻하지 않는다.
- **확인할 차이**: 재전송 이력은 [메모리 저장소](../../backend/src/main/java/com/surimap/eventhub/stream/EventStreamConfig.java)를 사용한다. 전송 작업이 DB에 남는다는 사실만으로 재시작 후 재전송까지 보장되지는 않는다.

## SSE 재연결과 중복 처리

**DB 저장·조회 기반 구현 (2026-09-26, 첫 단계)**: [migration](../../backend/src/main/resources/db/migration/V20260926_001__add_sse_sequence.sql), 기존 Mapper와 필요한 작업 객체 매핑을 변경했다. 이후 전송 경로의 변경은 아래 Service·worker 기록과 구분한다.

- 사건 카운터는 `BIGINT NOT NULL DEFAULT 0`, 이벤트 순번은 배정 전 `NULL`이며 배정 후 양수다. 0은 마지막 확정 순번이 없다는 뜻이다. 같은 사건의 순번 중복은 DB unique index로 막는다.
- [IncidentMapper](../../backend/src/main/java/com/surimap/incident/repository/IncidentMapper.java)는 카운터 조회·증가를, [EventDispatchJobMapper](../../backend/src/main/java/com/surimap/eventhub/adapter/EventDispatchJobMapper.java)는 순번 저장·범위 조회를 제공한다. 기존 완료·순번 미확정 작업에는 새 순번을 넣지 않고, 배정된 순번을 덮어쓰지 않는다. 범위 조회는 시작 순번 제외·끝 순번 포함이며 호출자가 조회 개수를 지정한다.
- [Mapper 테스트](../../backend/src/test/java/com/surimap/eventhub/adapter/EventDispatchJobMapperTest.java)와 [migration 테스트](../../backend/src/test/java/com/surimap/database/SseSequenceMigrationTest.java)에서 실제 PostgreSQL/PostGIS의 저장·정렬·제약·롤백과 기존 작업·GPS·마커·알림 원문 보존을 확인했다. `UPDATE ... RETURNING` 선점 후에도 조회 캐시가 옛 상태를 반환하는 문제를 재현해, [MyBatis의 데이터 변경 설정](https://mybatis.org/mybatis-3/sqlmap-xml.html)에 맞춰 갱신했다.
- 이 단계에서는 SQL·매핑만 검증했다. Service·worker의 후속 구현은 아래에 기록하며, 운영 DB 적용·배포·이력 삭제·부하 시험은 하지 않았다.

검증: 새 DB 테스트 10개와 기존 전송 관련 테스트 5개 통과. `cd backend && ./gradlew test`는 전체 1,249개 통과(실패·건너뜀 0, 기본 설정상 성능 태그 제외)다. 기존 전송 관련 테스트에는 메모리 재전송 저장소·대역을 사용하는 검사도 포함된다.

**Service·worker 연결 (2026-09-26, 두 번째 단계)**

- 기존 Dispatcher를 `EventDispatchJobService`, PollingWorker를 `EventDispatchJobWorker`로 교체했다. 업무 커밋 → worker 깨우기 → 작업 선점 → 순번 확정·커밋 → SSE 전송 → 결과 저장 순서다. 동기 로컬 consumer는 업무 트랜잭션에 남겼다.
- `getOrAssignSseSequence(UUID jobId)`는 작업 행을 잠근 뒤 기존 순번을 반환하거나 카운터 증가·순번 저장을 함께 커밋한다. 같은 작업의 동시 요청도 같은 순번을 받으며, DB 저장 오류에는 카운터 증가도 롤백한다. 순번 없는 과거 완료 작업은 새로 배정하지 않는다.
- `SseStreamService`는 메모리에서 새 순번을 만들지 않고 DB에서 확정한 순번을 전달받는다. 이력이 이미 있다는 이유로 전송을 생략하지 않는다. 재시도는 같은 순번·이벤트 UUID를 사용하며, 중복 수신의 적용 방지는 소비자가 맡는다.
- 깨우기 신호는 작업마다 무제한 쌓지 않고 하나로 합친다. 기존 주기·묶음 크기 설정을 유지했으며 `polling-enabled=false`는 주기 조회만 끄고 커밋 후 깨우기는 허용한다. 이 값들을 새 운영 기준으로 검증한 것은 아니다.
- [Service 테스트](../../backend/src/test/java/com/surimap/eventhub/adapter/EventDispatchJobServiceTest.java)는 실제 DB의 중복 배정·동시 요청·롤백·과거 완료 행을 검사한다. [Worker 테스트](../../backend/src/test/java/com/surimap/eventhub/EventDispatchJobWorkerTest.java)는 전송 시점의 DB 커밋·트랜잭션 종료, 요청 반환, 업무 롤백, 실패 후 같은 순번의 재실행, 신호 없는 대기 작업의 주기 처리를 확인한다. 외부 전송 대상은 대역이며 브라우저 수신 검증이 아니다.
- **남은 한계**: 재연결 조회는 아직 메모리 저장소를 사용한다. `FAILED`·중단 후 `DISPATCHING`의 자동 복구, 작업 간 순서·재전송→실시간 전환, 느린 연결 격리와 실제 재시작은 다음 단계다. 재시도 테스트는 실패 작업을 테스트에서 대기로 되돌렸으므로 자동 복구 완료의 증거가 아니다. 부분 구현이며 아직 배포하지 않는다.

검증: 두 번째 단계의 Service 5개·Worker 7개·기존 스트림 7개가 통과했다. `cd backend && ./gradlew test`는 전체 222개 클래스·1,258개 통과(실패·오류·건너뜀 0, 기본 설정상 성능 태그 제외), 4분 48초다. 커밋·푸시·배포·실제 서버 재시작은 하지 않았다.

- **재전송 이력의 의미**: 끊겼던 상황판에 다시 전달하려고 보관하는 이벤트 기록이다. 같은 이벤트를 여러 상황판에 보내거나 다시 보내도 이력 개수는 늘지 않는다. 전송 횟수·실제 수색 데이터·마커 알림 원문·계정별 확인 상태와 구분한다.
- **식별자 구분**: SSE의 `id`와 재연결 헤더 `Last-Event-ID`는 사건별 숫자 순번이다. `data.eventId`는 같은 이벤트인지 구분하는 UUID다. 재전송 위치와 중복 판정을 같은 값으로 취급하지 않는다.
- **합의한 변경 (2026-09-22)**: 재전송할 이벤트와 사건별 순번을 PostgreSQL에 보존하고, 재접속 때 DB에서 조회한다. 서버 재시작 후에도 이어받을 수 있도록 운영 경로의 메모리 전용 재전송 저장소를 교체한다. 현재 열린 SSE 연결의 메모리 관리와는 별개다. DB 순번 확정·최초 전송 연결까지 구현했으며 재접속 조회의 DB 교체는 남아 있다.
- **합의한 저장 구조 (2026-09-22)**: 기존 `event_dispatch_job`의 이벤트 내용을 재사용하고 재전송 정보를 추가한다. 이벤트 이력과 전송 작업을 별도 테이블로 나누지 않는다. 전송 완료 행도 재전송 보존 기간 동안 유지하며, 작업의 완료·실패 상태와 화면별 재전송 조회는 구분한다. 보관 기간은 아래 측정·합의 순서로 정한다.
- **재전송 이력 삭제 합의 (2026-09-24)**: 서버 전송 처리가 끝난 이력은 아래 보관 시간 기준으로 오래된 기록부터 DB에서 삭제한다. 진행 중인 사건의 모든 이벤트를 끝까지 쌓지 않으려는 선택이다. 필요한 이력이 삭제된 재연결은 그 사실을 감지하고 최신 지도·보존된 알림 원문·계정별 확인 상태를 다시 조회해 복구한다. GPS 좌표·마커 등 원본과 알림 원문·확인 기록, 미처리·실패·순번 미확정 전송 작업은 이 삭제 대상이 아니다. 실제 삭제 조건·순번 누락 판정·조회와 삭제의 동시 처리·진단 기록 보존은 후속 설계·검증 대상이다. 종료·권한 거부·파기 제한을 우회해 복구하지 않으며, 아직 삭제 기능을 구현하거나 데이터를 삭제하지 않았다.
- **보관 시간 기준 합의 (2026-09-24)**: 기록 개수가 아니라 서버 전송 처리 완료 시점부터 지난 시간을 기준으로 삭제 대상을 정한다. 브라우저 수신·알림 확인·좌표 수집 시각과 구분한다. 이벤트가 몰려도 개수 제한 때문에 보관 기간이 짧아지지 않는 대신, 같은 기간의 저장량이 늘 수 있다. 구체적인 보관 기간·삭제 주기는 아직 미정이며, 별도의 개수 제한을 함께 채택하지 않았다. 완료 시각의 저장·중복 완료 처리와 순번이 뒤섞여 완료될 때의 누락 감지는 구현·검증 대상이다.
- **보관 기간 결정 순서 합의 (2026-09-24)**: 이벤트가 쌓이는 양과 DB 저장량, 재전송·최신 상태 조회에 걸리는 시간을 측정한 뒤 보관 기간을 함께 정한다. 운영에서 이력 삭제를 켜기 전에 기간을 확정하며, 임의의 기본값으로 삭제를 시작하지 않는다. 측정값만으로 적정 기간이 자동 결정되는 것은 아니며, 이력이 없을 때의 원본 재조회 복구는 유지한다. 아직 기간을 확정하거나 측정·삭제를 실행하지 않았다.
- **재조회와 보존의 구분**: 이벤트가 저장돼 있다는 이유만으로 조회가 반복되지는 않는다. 여러 변경 이벤트의 지도 조회 요청은 [상황판 재조회 합의](situation-board.md#이벤트-수신과-최신-데이터-재조회)에 따라 진행 중인 조회를 유지하고 후속 조회로 합친다. 재전송 이력 삭제를 중복 조회 최적화의 대체 수단으로 삼지 않으며, 알림별 처리·복구와 종료 처리는 별도로 보존한다. 구현·실제 요청 수 검증은 남아 있다.
- **순번 저장 위치·컬럼명 합의 (위치 2026-09-22, 이름 2026-09-25)**: SSE sequence (SSE 순번)는 한 사건 안에서 이벤트에 확정하는 순번이며, 처음 전송하거나 재전송할 때 같은 값을 사용한다. 사건의 마지막 DB 확정 순번은 `incident.last_sse_sequence`, 각 이벤트의 확정 순번은 `event_dispatch_job.sse_sequence`에 저장한다. 업무 `version`·이벤트 UUID·브라우저의 마지막 수신 위치·전송 완료 상태와 구분한다. 별도 관리 테이블과 행 생성 흐름을 추가하지 않는 대신 배정 변경·사건 종료와 행 잠금을 공유한다. 자료형·초기값·기존 행 보존 SQL은 위 2026-09-26 구현 기록을 따르며, 같은 작업의 동시 순번 배정은 위 Service 테스트로 확인했다. 파기 후 정리·여러 작업의 전달 순서 검증은 남아 있다. 공개 SSE `id`·`Last-Event-ID`, `data.eventId`와 기존 payload의 `sequence`는 바꾸지 않았다.
- **합의한 순번 확정 시점 (2026-09-22)**: 업무 데이터와 이벤트 내용을 같은 트랜잭션에서 먼저 커밋한다. 이후 별도의 짧은 DB 트랜잭션에서 사건별 재전송 순번을 확정·저장하고, 그 커밋 후 SSE로 전달한다. 순번 조율을 업무 트랜잭션에서 분리하는 대신 추가 트랜잭션과 미완료 처리 복구를 맡는 선택이다. 서버가 중간에 멈춰도 DB에 남은 순번 미확정 이벤트를 이어 처리해야 한다. 순번 확정·커밋 후 전송은 위 두 번째 단계에서 구현했다. 전체 중단 복구·성능 검증은 남아 있으며 순번 저장만으로 실제 전달 순서까지 보장되는 것은 아니다.
- **순번 확정 메서드 합의 (2026-09-25)**: worker가 순번을 확정할 때 호출할 서비스 작업은 `getOrAssignSseSequence`(기존 순번 조회 또는 신규 배정)로 이름짓는다. 이미 확정된 순번이 있으면 그 값을 반환하고, 없으면 사건 카운터 증가와 이벤트 순번 저장을 같은 짧은 DB 트랜잭션에서 처리한다. SSE 전송은 커밋 이후 별도로 수행한다. 순번 저장 직후 전송 전에 중단될 수 있으므로, 기존 순번이 있다는 이유만으로 전송을 생략하지 않는다. 이 메서드는 아래 합의대로 기존 Dispatcher를 재구성한 `EventDispatchJobService`에 둔다. 현재 `UUID jobId`를 받아 `long` 순번을 반환하며, 없는 작업과 새 순번을 배정할 수 없는 과거 완료 작업은 거부한다. 작업 행 잠금과 서비스 트랜잭션은 위 두 번째 단계에서 검증했다.
- **합의한 전송 담당 (2026-09-22)**: 기존 Spring 애플리케이션의 worker가 순번 확정과 정상 전송·미완료 처리 복구를 맡는다. 요청 쪽 `afterCommit`은 SSE를 직접 보내지 않고 worker에 처리할 일이 있음을 알린다. 신호를 놓치거나 서버가 재시작해도 주기적인 DB 조회로 남은 작업을 처리한다. 사건별 전송 순서는 이 공통 처리 경로에서 관리하도록 구현한다. 커밋 후 깨우기·기존 주기의 PENDING 조회는 구현했다. FAILED·중단 후 DISPATCHING 복구와 사건별 실제 전달 순서 보장은 후속 대상이다.
- **DB 처리와 전송의 역할·클래스명 합의 (2026-09-25)**: 기존 `EventDispatchJobDispatcher`는 `EventDispatchJobService`(전송 작업의 DB 처리), `EventDispatchJobPollingWorker`는 `EventDispatchJobWorker`(전송 작업 실행)로 이름짓고 책임을 재구성한다. worker는 서비스의 순번 확정·커밋 → SSE 전송 → 서비스의 처리 결과 저장을 차례로 호출한다. DB 처리는 서비스의 `@Transactional` 경계 안에 두고, SSE 전송은 DB 트랜잭션 밖에서 수행한다. 별도 서비스를 추가하지 않고 기존 두 클래스의 책임을 나누는 선택이다. 요청의 `afterCommit`은 worker에 알리기만 하며, `DbEventHub`의 동기 로컬 consumer는 기존 업무 트랜잭션에 남긴다. 작업 처리 결과는 브라우저 수신이나 FCM 성공의 증거가 아니다. 기존 테이블·Mapper와 같은 전송 작업을 가리키는 이름을 선택했으며, FCM 처리를 추가하거나 DB·공개 필드명까지 바꾸지 않는다. 클래스 교체·깨우기·주기 조회·순번 배정 동시성은 위 두 번째 단계에서 확인했다. 중간 중단 복구와 작업 간 전달 순서 검증은 남아 있다.
- **최초 DB 전환 합의 (2026-09-25)**: 메모리 재전송 저장소에서 DB로 처음 전환할 때는 열려 있는 상황판을 한 번 새로고침하고, 옛 수신 위치 대신 최신 지도·보존된 알림 원문·계정별 확인 상태를 조회해 복구한다. 기존 화면의 메모리 순번을 DB 이력과 이어 주는 호환 전환은 도입하지 않는다. GPS·마커·알림 원문·저장된 확인 상태와 미처리 전송 작업은 보존한다. SSE 연결만 끊으면 옛 순번으로 재연결할 수 있으므로 새로고침 여부와 전환 중 누락 방지를 검증해야 한다. 이후의 일반 배포·재시작에는 DB 순번을 이어 쓰며 반복 초기화하지 않는다. 새로고침만으로 복구가 완성되는 것은 아니며, 실제 DB 재조회 연결·전환 안내·미저장 화면 작업의 처리와 아래 기준에 따른 기존 행의 구분·복구는 후속 구현·검증 대상이다. 제품 코드·DB 변경이나 실제 전환은 아직 하지 않았다.
- **전환 전 완료 이력 합의 (2026-09-25)**: 최초 DB 전환 전에 서버 전송 작업이 `COMPLETED`로 기록됐고 DB SSE 순번이 없는 기존 행은 보존하되, 새 순번을 배정하거나 새 재전송 이력에 편입하지 않는다. 과거 마커·GPS·알림 원문과 저장된 확인 상태는 앞선 조회 복구 합의를 따른다. 미완료 작업과 새 이벤트는 DB 순번을 배정해 처리하며, 이미 배정된 순번은 재시도·재시작에도 유지한다. `PENDING`·`FAILED`·중단 후 남은 `DISPATCHING`을 과거 완료 이력으로 취급하지 않고 복구 대상으로 구분한다. DB 전환 이후 순번이 확정된 완료 이벤트는 정상 재전송 대상으로 유지한다. 기존 행·원본을 삭제하거나 과거 완료 시각을 추정해서 채우는 결정이 아니며, 권한·종료·파기 기준은 유지한다. 전환 구분·미완료 복구와 실제 조회는 구현·검증 전이다.
- **재전송과 실시간 전달의 연결 합의 (2026-09-25)**: 복구할 연결을 먼저 수신 대상으로 등록하고, 재전송할 마지막 확정 순번을 같은 조율 과정에서 정한다. 그 순번까지 DB 이력을 보내는 동안 들어오는 새 이벤트는 해당 연결에서 잠시 대기시켰다가 순서대로 이어 보낸다. 대기분을 보내는 중 도착한 이벤트도 먼저 보내거나 빠뜨리지 않으며, 이력과 실시간 경로에 겹쳐 잡힌 이벤트는 중복 적용하지 않는다. 정상인 다른 연결의 전달을 이 복구가 끝날 때까지 멈추지 않는다. 이벤트 원본·순번은 PostgreSQL에 보존하며, 연결별 임시 대기는 메모리 전용 재전송 저장소를 유지한다는 뜻이 아니다. [Mercure의 구독 등록·재전송 범위 조율](https://github.com/dunglas/mercure/blob/0ce390af83b1f8414374bc7ddf28e9fe39c7bb24/bolt.go#L147-L168)을 참고한 프로젝트 선택이다. 등록 순서만 바꾸면 해결되는 것은 아니므로 사건별 순번·실시간 전달·전환을 함께 구현·검증한다. 대기량 제한·초과 시 복구는 아래 합의를 따르며, 한도 수치와 동시 처리 검증은 남아 있다. 권한·종료·파기 제한은 유지한다.
- **대기량 초과 시 복구 합의 (2026-09-25)**: 재전송 중 새 이벤트의 연결별 임시 대기량이 한도를 넘으면 해당 사건 SSE 연결만 종료한다. 합의한 재연결 대기 후 브라우저의 마지막 실제 수신 순번부터 DB 이력을 다시 받는다. 기존 재연결·DB 재전송을 활용하기 위한 선택이며, 서버가 이벤트를 대기열에 넣거나 전송했다는 이유로 브라우저 수신 위치를 앞당기지 않는다. 정상인 다른 연결·업무 저장·DB 원본·미처리 작업은 유지한다. 필요한 이력이 없으면 기존의 최신 지도·보존된 알림 원문·확인 상태 조회로 복구하고, 권한·종료·파기 제한은 지킨다. 전달 지연이 지속되면 반복 종료될 수 있으므로 갱신 지연 안내와 원인 추적을 유지한다. 한도 수치와 전체 전송 경로의 메모리·느린 연결 검증은 남아 있으며, 아직 구현하지 않았다.
- **대기량 제한 기준 합의 (2026-09-25)**: 재전송 중 새 이벤트를 잠시 보관하는 각 연결에 이벤트 개수와 전송 데이터 총 크기(바이트)의 한도를 함께 둔다. 어느 하나라도 넘으면 위 합의대로 해당 연결만 종료하고 이어받는다. 작은 이벤트의 대량 누적과 큰 이벤트의 누적을 각각 제한하기 위한 선택이며 SSE 표준의 필수 기준은 아니다. DB 이력의 보관 기간이나 원본·알림 확인 기록의 보존 범위는 바꾸지 않는다. 바이트 수를 JVM 전체 메모리 사용량으로 간주하지 않으며, 실제 보관 형태·계산 범위와 초기 재전송 목록·Spring 내부 보관·전송 버퍼도 함께 검증한다. 구체적인 개수·크기 수치는 측정 근거를 확인한 뒤 함께 정하며, 아직 구현·측정하지 않았다.
- **기존 요구**: 이벤트는 한 번만 이력에 추가하고, 마지막 수신 순번 이후의 이벤트를 순서대로 재전송한다. 소비자는 `eventId`로 중복 적용을 막는다. 순번 누락이나 재전송 불가 시 상황판 전체 조회로 복구한다.
- **현재 한계**: [SseReplayService](../../backend/src/main/java/com/surimap/eventhub/stream/SseReplayService.java)는 과거 순번을 받더라도 이력이 비어 있으면 항상 `409 gone_refetch_required`를 반환하지는 않는다. 따라서 이력 소실을 모두 감지한다고 설명할 수 없다.
- **복구 범위 구분**: [상황판 구독](../../frontend/src/features/situationBoard/presentation/hooks/useSituationBoardData.ts)은 연결 성공·이벤트·오류에 재조회를 요청한다. [마커 알림 구독](../../frontend/src/features/markerNotifications/presentation/hooks/useIncidentMarkerNotifications.ts)은 별도로 동작하며, 재전송 불가 시 순번을 초기화한다. 상황판 재조회가 놓친 알림 팝업까지 복원하는 것은 아니다. 현재 두 소비자 모두 순번 간격을 직접 비교하는 누락 검사는 없다. 2026-09-24 코드 대조에서 알림 구독은 최초 상황판 조회 완료 전에도 시작하지만, 상황판 구독은 조회 결과가 있고 종료 상태가 아닐 때 시작함을 확인했다. 위 연결 구성 합의를 구현할 때 초기 수신 시점·오류·종료 처리의 차이를 함께 확인한다. 실제 브라우저 연결 수나 복구를 실행해 검증한 결과는 아니다.

## 연결 정리의 검증 범위

- [SseConnectionRegistryTest](../../backend/src/test/java/com/surimap/eventhub/stream/SseConnectionRegistryTest.java)는 테스트용 연결을 100회 등록한 뒤 직접 해제해 목록이 비워지는지 검사한다. [SseStreamServiceTest](../../backend/src/test/java/com/surimap/eventhub/SseStreamServiceTest.java)는 사건 종료 이벤트를 전달한 뒤 연결을 닫고 등록을 제거하는지 검사한다.
- 이 검사들은 실제 HTTP 연결 종료 시 콜백이 호출되는지, 브라우저 화면 이동 후 자동 정리가 되는지, 메모리 누수가 없는지까지 증명하지 않는다. 실제 초기 전송 중 연결이 끊긴 뒤 다음 이벤트까지 참조가 남는 조건은 [로컬 이슈 5의 진단](../issues/local/5-sse-initial-send-disconnect-cleanup.md)에 별도로 기록했다.
- 2026-09-21에는 위 테스트 코드와 [옛 검증 설명](https://github.com/sonic8-8/suri-map/blob/403b383dc2693fd15d1616ee7206e6cb0e420df5/docs/evidence/backend/sse-stream-lifecycle.md)을 대조해 검증 범위를 이곳에 통합했다. 제품 테스트나 실제 연결 시험을 다시 실행한 결과는 아니다.

## 사건 종료와 데이터 파기

- **기존 요구**: 종료됐지만 이력이 보존된 사건은 `INCIDENT_CLOSED`까지 재전송한 뒤 연결을 정상 종료한다. 이후 실시간 연결은 유지하지 않는다. 파기된 사건은 재전송 이력·대기 작업의 사건 데이터를 제거하고 다시 전송하지 않는다.
- **현재 한계**: [메모리 저장소](../../backend/src/main/java/com/surimap/eventhub/stream/InMemorySseReplayEventStore.java)가 관측한 종료·파기 이벤트를 기준으로 처리한다. DB의 사건 상태를 직접 확인하거나 전송 작업의 payload까지 파기하는 흐름은 별도 확인이 필요하다. 메모리 상태만으로 재시작 이후의 종료·파기 처리를 보장하지 않는다.

## 전송 실패와 관측

- **기존 요구**: 재시도할 대상을 구분해 이미 성공한 전달을 반복하지 않는다. 실시간 SSE 연결 실패는 재전송 이력으로 복구하고, FCM만 재시도할 때 SSE 이력을 중복 추가하지 않는다. FCM 수신자가 없으면 해당 전송만 생략하고 SSE 전달은 이어간다.
- **현재 차이**: SSE 작업의 실패 상태를 자동으로 다시 처리하거나 대상별 재시도를 관리하는 구현은 없다. FCM도 공통 SSE 전달 작업이 아니라 마커·사건 배정·사건 종료의 호출부에서 별도로 전송한다. [FCM 실패 반환 기록](../issues/local/4-fcm-delivery-failure-not-recorded.md)과 전달 시점·재시도 보장은 구분한다.
- **기존 관측 요구**: 이벤트 저장, 재전송 이력 추가, 실시간 전송, FCM, 상황판 재조회 단계의 실패를 구분한다. 이벤트 형식이 잘못되면 실패로 남기고 원인을 추적한다. 내부 전달 상태를 사용자 알림 상태와 혼용하지 않으며, payload에 정의되지 않은 개인정보를 덧붙이지 않는다.
- **기존 접근 요구**: 사건 접근권을 가진 WEB 연결만 허용하고 권한 만료 시 연결을 종료한다. Android는 상시 SSE 대신 FCM과 REST·미전송 기록 동기화를 사용한다. 연결 도중 권한 만료 처리가 실제로 보장되는지는 별도로 검증한다.

## 후속 작업에서 정할 기준

- 재전송 이력의 저장 방식, 보존 기간·최대 개수와 서버 재시작 후 복구 범위. 원문에도 보존 기간·최대 개수는 미정이었다.
- 상황판 최신 상태 복구와 놓친 알림 복구를 각각 어디까지 보장할지, 재전송 이력이 없을 때 어떻게 복구할지.
- 실패 대상별 재시도, 중복 방지, 사건 종료·파기 시 정리 범위. 기존 DB 설계를 그대로 구현하는 것으로 미리 확정하지 않는다.
- 지연 목표. 원문의 ‘3초 이내’를 확정 기준으로 채택하지 않으며, [Issue #8](../issues/8-gps-collection-transmission-basis.md)의 측정·합의와 구분한다.
- 연결 확인 신호와 초기 전송 중 연결 종료 처리. [로컬 이슈 5](../issues/local/5-sse-initial-send-disconnect-cleanup.md)의 재현 결과를 이어서 검토한다.

## 테스트 입력

S4의 여섯 fixture는 [공용 fixture](../../test-fixtures/common-fixtures.json)의 `confirmed.eventFanout`에 보존돼 있다. 새 복제본을 만들지 않고 기존 소비자가 이 데이터를 사용한다. fixture의 기대값은 현재 제품 동작을 검증했다는 뜻이 아니다.

원문에만 있던 `fanout_failure_injection.expectedParentStatus`의 `PARTIAL_FAILED_THEN_DISPATCHED`는 직접 읽는 테스트가 없으므로 Git 원문에 보존한다. 이를 현재 상태값으로 채택하거나 새 fixture 필드로 추가하지 않는다. 일부 실패 후 복구 요구는 위 전송 실패 항목에서 이어서 확인한다.
